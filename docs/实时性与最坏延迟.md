# 实时性与最坏延迟

这份文档说明 Ark RTOS 怎么把「实时性」变成可读的数，以及这些数的边界在哪里。

一句话概括：**用 DWT 周期计数器，在真实的调度路径上取时间戳，报出「最坏值」而不是平均值**。
所有读数都来自真机（STM32F427 @96 MHz、2 kHz 节拍），不是估算，也不是仿真。

必须先把话说在前面：**这不是形式化 WCET 分析**。它给的是「本机、本配置、本固件，
在实测这段时间里出现过的最坏值」。形式化 WCET 需要静态路径分析与全部中断的
最坏嵌套模型，本模块不提供。第 3 节把三条边界写死。

---

## 1. 为什么不用节拍数近似

用 SysTick 的毫秒节拍去算延迟，分辨率就是 500 µs（本配置一个 tick）。而真正要看的量
——一次唤醒、一次临界区——就在几十微秒量级，用 500 µs 的尺子量它只会得到 0 或 1。

DWT 的 `CYCCNT` 是 32 位自由运行周期计数器，96 MHz 下**一个计数就是 10.4 ns**。
它的限制也明确：

- 32 位 → 96 MHz 下约 **44.7 秒**回绕一次。本模块所有时间戳都只用于**同一次测量内的差值**，
  差值远小于回绕周期；但如果你要把 `CYCCNT` 当绝对时间用，必须自己处理回绕。
- 需要 `DEMCR.TRCENA` 与 `DWT_CTRL.CYCCNTENA` 同时为 1。这两位的实际行为见第 5 节，
  那里有一个只有真机才会遇到的坑。

计数器不可用时本模块**如实报「不可用」**（`counter: NOT running`，`rt show` 的读数为空），
绝不退回节拍数凑一个看似正常的数。

## 2. 四项读数各自量的是什么

| 行 | 含义 | 起点 → 终点 |
|---|---|---|
| `tick.isr` | 节拍中断服务程序本体 | `SysTick_Handler` 进来 → 出去（见下方口径说明） |
| `wake.lo` | 低优先级任务被唤醒的延迟 | 「该被唤醒的那个 tick 时刻」→ 任务真正跑起来 |
| `wake.hi` | 高优先级任务被唤醒的延迟 | `sem_post` 返回前的时间戳 → 高优先级任务拿到时间戳的第一行 |
| `crit.max` | 临界区的最坏占用 | `arkrtos_port_enter_critical()` → `arkrtos_port_exit_critical()`，只记最外层 |

每行给出 `n / min / avg / max`，同时折算成 µs（按实测时钟与 `ARKRTOS_TICK_PERIOD_US` 换算）。
另外两项：

- **`jitter`**：`tick.isr` 的相邻两次间隔与理论节拍周期之差（有符号，单位周期）。
  它回答的是「节拍自己抖不抖」，不是「任务延迟多少」。
- **`late_n`**：超过一整拍才被唤醒的样本数。这类样本**单独计数、不计入 `wake.*`**——
  它是被更高优先级长时间挡住，不是唤醒路径的延迟，混进最小值/最大值只会污染读数。

### `tick.isr` 的口径（重要）

`tick.isr` 只覆盖 `arkrtos_kernel_tick_handler()` 本体。上下文切换不在里面：
`ARKRTOS_SWITCH_TASK()` 只是把 PendSV 挂起就返回，真正的寄存器压栈/出栈发生在
PendSV 异常里，退出节拍中断之后。

所以：**`tick.isr` 不能当作「节拍中断从进入到退出」的完整时间**。
要量完整的中断含切换，需要把时间戳下移到 PendSV 入口，本模块没有做（属于未做项，
见第 7 节）。写成「节拍 ISR 本体」而不是「节拍中断总耗时」，是刻意的。

### `crit.max` 为什么经常是 `no sample`

`crit.max` 只在**内核真的进入临界区**时才记账。`rt run` 会清空统计，而唤醒路径
（`task_wait` 到点被唤醒）不经过 `arkrtos_port_enter_critical()`。于是：

```
rt run            → crit.max (no sample)
rt reset
mpool test        → 进临界区
crash             → 进临界区
rt show           → crit.max n=16
```

表尾会打一行说明：某行没有样本，只代表「上次 reset 之后没有发生过这类事件」，
不代表「耗时 0」。

## 3. 三条边界（写在实现里，也写在这里）

1. **不是形式化 WCET。** 读数是实测最大值。没跑到过的路径，它的最坏值不在这张表里。
   增加压力（更多任务、更多中断、更长的临界区）会让这些数变大，这是正常的。
2. **`crit.max` 含测量开销。** 进出临界区各多几次寄存器读写，量级在十几个周期，
   但确实是被测对象的一部分，不能声称「纯临界区耗时」。
3. **与 `mdk_trace` 共用 DWT。** 两者都只做「把门控位打开」（`|=`），从不清零计数器，
   也从不关闭对方需要的位，所以可以同时开。反过来说：任何**清零 CYCCNT** 的新代码
   都会打断本模块的时间戳，制造出 −21 M 量级的假抖动——这条在实现里是硬约束。

另外：**默认关时全是死代码。** `ARKRTOS_USE_RTSTAT` 默认 0，五处 `#if` 里的代码
不进编译产物，体积与行为零变化；辅助任务栈（1024 B）也不会存在。

## 4. 上板实测读数

条件：STM32F427VGTx，系统时钟 96 MHz，节拍 2 kHz（500 µs），`ARKRTOS_USE_RTSTAT=1`，
2026-11-12 通过 DAP（`pyocd flash -t stm32f427vg`）烧录后串口（COM21）实测。

| 行 | N | min (cyc) | avg (cyc) | max (cyc) | min / avg / max (µs) |
|---|---|---|---|---|---|
| `tick.isr` | 7770 | 410 | 603 | 6870 | 4.3 / 6.3 / 71.6 |
| `wake.lo` | 3000 | 4356 | 4393 | 22074 | 45.4 / 45.8 / 229.9 |
| `wake.hi` | 3000 | 3978 | 5047 | 7727 | 41.4 / 52.6 / 80.5 |
| `crit.max` | 16 | 63 | 102 | 294 | 0.7 / 1.1 / 3.1 |
| `jitter` | 7770 | −2181 | — | +2167 | −22.7 / +22.6 |

另一次 `rt run 200` 的读数：`wake.lo` 2988/3908/4367 cyc、`wake.hi` 3944/5066/7654 cyc。
两次的 `late_n` 都是 0——在这套固件和这个负载下，没有样本被挡过一整拍。

怎么读这张表：

- `tick.isr` 的 6.3 µs 平均、71.6 µs 最坏，相对 500 µs 节拍有余量；最坏值出现在与
  shell、内存池等路径同时发生的时候。
- `wake.lo` 的 45.8 µs 平均里，主要部分是「节拍到期 → 中断里改就绪表 → 退出中断」
  这条链本身，不是调度器查找的开销。229.9 µs 的最坏样本是单次离群，不是稳态。
- `wake.hi` 41.4 µs 的最小值说明「`sem_post` 到高优先级任务第一行」这段的固定成本就在这个量级；
  80.5 µs 的最坏值出现在被节拍中断插入时。
- `jitter` 的 ±22 µs 是节拍中断被其它中断/临界区推迟的结果，与 `tick.isr` 的最坏值同源。

这些都是**本机本配置的实测值**，换芯片、换主频、加中断源都会变。不要把它们当芯片规格。

## 5. 两个只有真机才会遇到的坑

### 5.1 调试器断开清 `TRCENA`，CYCCNT 会冻住

实测现象：`pyocd` 刷完固件、断开连接之后，`DEMCR` 读回 `0x00000000`，
`CYCCNT` 停在约 1e7（相当于开机后 0.1 s），于是所有读数都是：

```
raw 10654352 -> 10654352
back-to-back 0 cyc
1 ms delay = 0 cycles
```

根因是**调试器断开时把 `DEMCR.TRCENA` 清掉了**，CYCCNT 随之停止计数。
软件本身没有错，错在「以为开机时打开一次就永远开着」。

修法：`arkrtos_rt_counter_alive()` 在**每次开测前**重新写 `DEMCR |= (1u<<24)`
与 `DWT_CTRL |= 1u`，然后跑一小段循环比较两次 `CYCCNT` 是否真的在变。
`rt run` 会先调 `arkrtos_rt_init()` 重新武装；`rt show` 会打印 `counter: running`
或 `counter: NOT running`。

真实工程里如果没人接调试器，这个问题不会出现；**一旦接了 DAP 调试/烧录，就必须按这条处理**。

### 5.2 绝对不要清零 CYCCNT

最初为了「让统计从 0 开始」，`arkrtos_port_cyccnt_init()` 里写了 `DWT_CYCCNT = 0`。
结果：已经记过 `last_tick_cyc` 之后计数器被清零，下一个节拍算出
`jitter = −21756208` 这样的巨大负数，全部统计作废。

CYCCNT 是自由运行计数器，**差值语义已经足够**，清零只会制造假抖动。
三个移植层里的清零语句已全部删除，这是硬约束，不是风格问题。

## 6. 怎么用

### 6.1 打开

两条路，选一条：

- Kconfig：`config ARKRTOS_USE_RTSTAT`（`config/kconfig/Kconfig.features`），`default n`。
- 直接定义：`-DARKRTOS_USE_RTSTAT=1`。

F427 的 `ARKRTOS_TEST` 测试工程当前**按开启档编**（`Define` 里带 `ARKRTOS_USE_RTSTAT=1`），
这是刻意的「编入档」：默认关的特性如果没有任何工程编过，它里面的错会一直躺着。
关掉它体积会少约 2.7 KB Code + 1.2 KB ZI（含 1024 B 辅助任务栈）。

### 6.2 Shell 命令

```
rt                 # 等同 rt show
rt show            # 打印四行读数 + jitter + counter 状态
rt reset           # 清空统计（不动计数器）
rt run [n]         # 先重新武装 + 清统计，再跑 n 次 wake 与 n 次 preempt，默认 200，范围 1..5000
```

`rt run` 是**主动制造**测量：它按顺序触发 `measure_wake(n)` 与 `measure_preempt(n)`，
所以这两行的 `n` 会相等且等于你给的值；`tick.isr` 的 `n` 只受运行时长影响。

失败时打印 `arkrtos_rt_last_error()` 的原因码：

| 码 | 含义 |
|---|---|
| 1 | `sem_hi` 创建失败 |
| 2 | `sem_ack` 创建失败 |
| `4 - tid` | 辅助任务登记失败（tid 为负） |

### 6.3 C 接口

`#include "arkrtos_rt.h"`（`ARKRTOS_USE_RTSTAT` 为 0 时整块是空的，调用点要自己 `#if`）：

```c
arkrtos_rt_init();                       /* 武装计数器 + 复位统计 */
arkrtos_rt_measure_wake(200);            /* 2 次 task_wait(1ms) 的唤醒延迟 */
arkrtos_rt_measure_preempt(200);         /* 200 次高优先级抢占延迟 */
arkrtos_rt_row_t rows[ARKRTOS_RT_ROWS];
uint32 n = arkrtos_rt_snapshot(rows, ARKRTOS_RT_ROWS);
int32 jmin, jmax; uint32 jn;
arkrtos_rt_jitter(&jmin, &jmax, &jn);
arkrtos_rt_reset();
```

`snapshot()` 返回实际填了几行；行名是静态字符串，不需要释放。
时间换算用 `unsigned long long`（内核没有 `uint64` 类型，这个坑踩过）。

## 7. 这道门禁防的是什么，以及还没做什么

### 门禁

`tools/rtstat_syntax_gate.py`，已挂进 `tools/ci_gate.py`（第 18 项）。

原因很直接：`ARKRTOS_USE_RTSTAT` 默认 0，两处测试工程之外按默认档编，
那五处 `#if` 平时**一个编译器都不经过**。改坏了照样全绿，直到有人在板上打开它。
门禁用 `armclang -fsyntax-only -DARKRTOS_USE_RTSTAT=1` 编 7 个文件
（内核 4 个 + m3/m4/m7 三个移植层），缺 armclang 判 FAIL 而不是跳过。

一个必须写下来的细节：编译端口层需要 `-DARKRTOS_BOARD_CONFIG="arkrtos_board_config.h"
-DSTM32F427xx -DUSE_HAL_DRIVER`。少了后两个，`stm32f4xx.h` 在选型处就 `#error` 退出，
`core_cm4.h` 根本不会被包含，报出来的是「`SCB` 未声明」——一个与被测改动毫无关系的假错误。
门禁里这几个宏是必需项，不是可选装饰。

**门禁只查语法。** DWT 在板上是否真的在跑、读数是否可信，门禁管不到。

### 未做（如实列出）

- **形式化 WCET**：没有静态路径分析，没有中断最坏嵌套模型。
- **完整中断延迟**：`tick.isr` 不含 PendSV 上下文切换（见 2 节）。
- **长时间漂移与温度/电压影响**：本表是单次运行读数，没有做小时级统计与角态扫描。
- **多优先级压力组合**：目前 `wake.hi` 只测「优先级 1 的辅助任务」，没有跑满优先级的
  抢占链，也没有把 `wake` 放在大量中断同时发生的场景里。
- **m3/m7 只有语法级验证**：没有对应的板上读数，F427 是 m4。
- **mempool/shell 等路径的临界区分解**：`crit.max` 只有一个总数，没有按调用点拆分。

这些不是「以后再补的欠账清单」的托辞，而是当下读数的适用边界：超出上面范围的结论，
本模块不出。
