# 实时性与最坏延迟

这份文档说明 Ark RTOS 怎么把「实时性」变成可读的数，以及这些数的边界在哪里。

一句话概括：**用 DWT 周期计数器，在真实的调度路径上取时间戳，报出「最坏值」而不是平均值**。
所有读数都来自真机（STM32F427 @96 MHz、2 kHz 节拍），不是估算，也不是仿真。

必须先把话说在前面：**这不是形式化 WCET 分析**。它给的是「本机、本配置、本固件，
在实测这段时间里出现过的最坏值」。形式化 WCET 需要静态路径分析与全部中断的
最坏嵌套模型，本模块不提供。第 3 节把三条边界写死。

---

## 1. 为什么不用节拍数近似

用 SysTick 的毫秒节拍去算延迟，分辨率就是 500 µs（本配置一个 tick）。而真正要看的量
——一次唤醒、一次临界区——就在几十微秒量级，用 500 µs 的尺子量它只会得到 0 或 1。

DWT 的 `CYCCNT` 是 32 位自由运行周期计数器，96 MHz 下**一个计数就是 10.4 ns**。
它的限制也明确：

- 32 位 → 96 MHz 下约 **44.7 秒**回绕一次。本模块所有时间戳都只用于**同一次测量内的差值**，
  差值远小于回绕周期；但如果你要把 `CYCCNT` 当绝对时间用，必须自己处理回绕。
- 需要 `DEMCR.TRCENA` 与 `DWT_CTRL.CYCCNTENA` 同时为 1。这两位的实际行为见第 5 节，
  那里有一个只有真机才会遇到的坑。

计数器不可用时本模块**如实报「不可用」**（`counter: NOT running`，`rt show` 的读数为空），
绝不退回节拍数凑一个看似正常的数。

## 2. 五项读数各自量的是什么

| 行 | 含义 | 起点 → 终点 |
|---|---|---|
| `tick.isr` | 节拍中断服务程序本体 | `SysTick_Handler` 进来 → 出去（见下方口径说明） |
| `wake.lo` | 低优先级任务被唤醒的延迟 | 「该被唤醒的那个 tick 时刻」→ 任务真正跑起来 |
| `wake.hi` | 高优先级任务被唤醒的延迟 | `sem_post` 返回前的时间戳 → 高优先级任务拿到时间戳的第一行 |
| `switch` | 只算切换、不含节拍体的那一段 | 节拍体最后一行（`arkrtos_rt_tick_exit()` 取时间戳处）→ 被唤醒任务的第一条指令 |
| `crit.max` | 临界区的最坏占用 | `arkrtos_port_enter_critical()` → `arkrtos_port_exit_critical()`，只记最外层 |

每行给出 `n / min / avg / max`，同时折算成 µs（按实测时钟与 `ARKRTOS_TICK_PERIOD_US` 换算）。
另外两项：

- **`jitter`**：`tick.isr` 的相邻两次间隔与理论节拍周期之差（有符号，单位周期）。
  它回答的是「节拍自己抖不抖」，不是「任务延迟多少」。
- **`late_n`**：超过一整拍才被唤醒的样本数。这类样本**单独计数、不计入 `wake.*`**——
  它是被更高优先级长时间挡住，不是唤醒路径的延迟，混进最小值/最大值只会污染读数。
- **`switch` 行上的 `skip_n`**：因为「节拍序号不配对」被丢弃的样本数。见 4.1 节，
  这类样本的起点是上一拍的 `tick_end`，差值没有物理含义，宁可丢弃也不计入。

### `tick.isr` 的口径（重要）

`tick.isr` 只覆盖 `arkrtos_kernel_tick_handler()` 本体。上下文切换不在里面：
`ARKRTOS_SWITCH_TASK()` 只是把 PendSV 挂起就返回，真正的寄存器压栈/出栈发生在
PendSV 异常里，退出节拍中断之后。

所以：**`tick.isr` 不能当作「节拍中断从进入到退出」的完整时间**。
要量完整的中断含切换，需要把时间戳下移到 PendSV 入口，本模块没有做（属于未做项，
见第 7 节）。写成「节拍 ISR 本体」而不是「节拍中断总耗时」，是刻意的。

### `crit.max` 为什么经常是 `no sample`

`crit.max` 只在**内核真的进入临界区**时才记账。`rt run` 会清空统计，而唤醒路径
（`task_wait` 到点被唤醒）不经过 `arkrtos_port_enter_critical()`。于是：

```
rt run            → crit.max (no sample)
rt reset
mpool test        → 进临界区
crash             → 进临界区
rt show           → crit.max n=16
```

表尾会打一行说明：某行没有样本，只代表「上次 reset 之后没有发生过这类事件」，
不代表「耗时 0」。

## 3. 三条边界（写在实现里，也写在这里）

1. **不是形式化 WCET。** 读数是实测最大值。没跑到过的路径，它的最坏值不在这张表里。
   增加压力（更多任务、更多中断、更长的临界区）会让这些数变大，这是正常的。
2. **`crit.max` 含测量开销。** 进出临界区各多几次寄存器读写，量级在十几个周期，
   但确实是被测对象的一部分，不能声称「纯临界区耗时」。
3. **与 `mdk_trace` 共用 DWT。** 两者都只做「把门控位打开」（`|=`），从不清零计数器，
   也从不关闭对方需要的位，所以可以同时开。反过来说：任何**清零 CYCCNT** 的新代码
   都会打断本模块的时间戳，制造出 −21 M 量级的假抖动——这条在实现里是硬约束。

另外：**默认关时全是死代码。** `ARKRTOS_USE_RTSTAT` 默认 0，五处 `#if` 里的代码
不进编译产物，体积与行为零变化；辅助任务栈（1024 B）也不会存在。

## 4. 上板实测读数

条件：STM32F427VGTx，系统时钟 96 MHz，节拍 2 kHz（500 µs），`ARKRTOS_USE_RTSTAT=1`，
2026-11-12 通过 DAP（`pyocd flash -t stm32f427vg`）烧录后串口（COM21）实测。

| 行 | N | min (cyc) | avg (cyc) | max (cyc) | min / avg / max (µs) |
|---|---|---|---|---|---|
| `tick.isr` | 7770 | 410 | 603 | 6870 | 4.3 / 6.3 / 71.6 |
| `wake.lo` | 3000 | 4356 | 4393 | 22074 | 45.4 / 45.8 / 229.9 |
| `wake.hi` | 3000 | 3978 | 5047 | 7727 | 41.4 / 52.6 / 80.5 |
| `crit.max` | 16 | 63 | 102 | 294 | 0.7 / 1.1 / 3.1 |
| `jitter` | 7770 | −2181 | — | +2167 | −22.7 / +22.6 |

另一次 `rt run 200` 的读数：`wake.lo` 2988/3908/4367 cyc、`wake.hi` 3944/5066/7654 cyc。
两次的 `late_n` 都是 0——在这套固件和这个负载下，没有样本被挡过一整拍。

怎么读这张表：

- `tick.isr` 的 6.3 µs 平均、71.6 µs 最坏，相对 500 µs 节拍有余量；最坏值出现在与
  shell、内存池等路径同时发生的时候。
- `wake.lo` 的 45.8 µs 平均里，主要部分是「节拍到期 → 中断里改就绪表 → 退出中断」
  这条链本身，不是调度器查找的开销。229.9 µs 的最坏样本是单次离群，不是稳态。
- `wake.hi` 41.4 µs 的最小值说明「`sem_post` 到高优先级任务第一行」这段的固定成本就在这个量级；
  80.5 µs 的最坏值出现在被节拍中断插入时。
- `jitter` 的 ±22 µs 是节拍中断被其它中断/临界区推迟的结果，与 `tick.isr` 的最坏值同源。

这些都是**本机本配置的实测值**，换芯片、换主频、加中断源都会变。不要把它们当芯片规格。

### 4.1 与 RT-Thread 同口径：`switch` 行（2026-11-14 新增）

上面那张表的问题不在数字，在**起点**：`wake.lo` 从节拍中断入口起算，里面装着整个节拍体
（guard、定时器链、延时链、记账）。而主流 RTOS 公开基准报的是「调度决策点 → 被选中任务
的第一条指令」，不含节拍体。两边起点不同，放在一起比较就是拿两把尺子量同一段。

RT-Thread 侧的事实边界：官方没有公开测量脚本；睿擎（工业平台）官网给的是结论
——任务响应 <1 µs、抖动 <5 µs——没有说怎么量的；社区/教程通行做法是两个线程信号量
ping-pong，用 DWT 或节拍记录「release → 对方第一行」，取典型值。所以本仓库的对齐目标
只能是**那一段区间的定义**，不是复刻某一份未公开的脚本。

于是新增 `switch` 行：起点从「节拍中断入口」挪到「节拍体最后一行」。
`wake.lo − switch` 就是节拍体本身，读的人不必猜对方的数字量的是哪一段。

**三档同码实测**（同一份源码，STM32F427 @96 MHz，2 kHz 节拍，`rt run 3000`，n=3000）：

| 编入档 | Code (B) | `switch` min / avg / max (cyc) | min / avg / max (µs) | `wake.lo` avg (cyc) | `tick.isr` avg (cyc) |
|---|---|---|---|---|---|
| 默认（观测全开） | 220290 | 983 / 3651 / 20960 | 10.2 / 38.0 / 218.3 | 4434 | 619 |
| 仅关 `MDK_TRACE` | 217714 | 744 / 744 / 745 | 7.75 / 7.75 / 7.76 | 1538 | 548 |
| 观测全关 | 211726 | 711 / 714 / 2841 | 7.4 / 7.4 / 29.6 | 1392 | 442 |

怎么读这三行：

- **默认档的 38 µs 不是切换本身的成本。** 关掉 `MDK_TRACE` 一项，`switch` 从 3651 掉到
  744 周期，**少了 2907 周期（30.3 µs）**。这一档同时按 Kconfig 依赖把 `SCHED_STAT` 也关了
  （见 6.1），所以这条差值里混着 `mdk_trace_send()` 的每次切换发送与 sched_stat 的收尾记账；
  两者**没有单独分开量**，从量级看差值是 trace 那一侧，但这条只是推断，不是读数。
  剩下的观测模块（guard / audit / stack check / cpu load / stack usage）加起来只占
  744 → 714 的 30 周期——**这一条是直接读数**。
  也就是说：默认档的数字里，实时性开销的大头是**可观测性**，不是调度器。
- **744 周期这一行几乎没有抖动**（min=max 相差 1 个周期）。去掉 trace 之后切换路径是
  确定性的；默认档那 218 µs 的 max 与被其它中断（板上 USB CDC 的 SOF 每 1 ms 一次）
  挤开同源——这一条同样是推断，没有单独关中断取证。
- **`switch` 与 `wake.lo` 的差就是节拍体**：默认档 4434 − 3651 ≈ 783 周期，与 `tick.isr`
  的 619 同量级（唤醒那一拍还多走了延时链与就绪表），互相对得上。

**这条过滤为什么存在**：节拍体里如果走「直接切走」路径（`FAST_TICK_SWITCH`，不起 PendSV），
被唤醒的任务会先跑，`arkrtos_rt_tick_exit()` 还没轮到执行，`tick_end_cyc` 仍是上一拍的值。
用它做减法会得到一个无法解释的数（早先一版读数里出现过 145 周期这种不可能的 min）。
现在用节拍序号配对：只有「记下的节拍体末尾」与「当前这一拍」同序号，样本才入账，
否则丢弃并计入 `skip_n`。本次 3000 个样本 `skip=0`，即没有走那条路径。

**可比与不可比，写清楚**：

| 要比的东西 | 用哪一行 | 说明 |
|---|---|---|
| 与 RT-Thread「任务响应」同类 | `switch`（**平均**） | 起点一致：调度决策点 → 任务第一条指令 |
| 抖动 | `switch` 的 min/max 或 `jitter` 行 | RT-Thread 报的抖动是同类量的极差 |
| 任务唤醒（含节拍体） | `wake.lo` | **不可**与 RT-Thread 的响应数字并列，多一个节拍体 |
| 同步唤醒 + 抢占 | `wake.hi` | 起点是 `sem_post` 之前，含调用开销 |
| 中断服务本体 | `tick.isr` | 不含 PendSV 与退出异常的开销 |
| 最长关中断 | `crit.max` | 只在真的进过临界区之后才有样本 |

三条仍然成立的限定：

1. **主频不同，周期数才可比。** 744 周期在 96 MHz 上是 7.75 µs；同样 744 周期放在 400 MHz
   上折合 1.86 µs。这是算术换算，**不是本机实测**，不要把换算值当成第二块板子的读数。
2. **本机的 96 MHz 是内部 RC（HSI）经 PLL**，配 3 个等待周期；换成外部晶振会有不同的抖动形态。
3. **板上还跑着 USB CDC shell**，USB SOF 每 1 ms 一次，会作为更高优先级中断插入。
   默认档那个 218 µs 的 max 与 `tick.isr` 的 78 µs max 同源，都是被这类中断挤开的结果。

想把这些数字拿去和 RT-Thread 的宣称并列，还差一步：744 周期里含着地址隔离与特权隔离，
下一节把它拆开。

### 4.2 与 RT-Thread 宣称的对照（2026-11-14 新增）

用户的问题是「对比 RT-Thread 同口径数据」。这一节只做一件事：把**能核实的东西**和
**核不到的东西**分开摆，再说明本机数字能对齐到哪一步。

#### 能核实的：官方原话

RT-Thread 官网「平台特性」页（睿擎平台，页面日期 2025-09-17）原文：

> 硬实时内核：睿擎平台集成 RT-Thread 专业版内核，微秒级中断延迟（≤1µs）、
> 微秒级任务响应（≤1µs）与极低抖动（≤5µs）

这是目前能找到的、由厂商自己写下的唯一一组实时性数字。

#### 核不到的：全部测量条件

上面这句话没有说明：

- 测在**哪个核**、主频多少；
- 用什么口径（GPIO 翻转 / DWT 周期计数 / 节拍时间戳），起点终点在哪里；
- 样本数与统计方式（典型值、平均值，还是最坏值）；
- 测试负载（单 ping-pong 双线程，还是带中断风暴）。

官方也没有公开测量脚本。社区与教程里的通行做法是两个线程信号量 ping-pong、用 DWT 记
「release → 对方第一行」、取典型值——那是**通行做法**，不等于睿擎那组数字就是这么做出来的。

#### 平台事实：连折算都定不下来

睿擎派所用 SoC 为 RK3506J，公开资料（RT-Thread 官方账号发布的睿擎 SDK V1.3.0 说明，
2025-08-30）给出的配置是 **3×Cortex-A7 @1.5 GHz + 1×Cortex-M0 @200 MHz**，其中
「CPU 2 作为硬实时核心」，实时任务可独占该核。于是那 1 µs 落在哪一侧，折算结果差 7.5 倍：

| 假设 1 µs 测在 | 折合周期上限 |
|---|---|
| 200 MHz Cortex-M0 | ≤ 200 周期 |
| 1.5 GHz Cortex-A7 | ≤ 1500 周期 |

**官方没说在哪一侧，所以连「谁更快」的方向都定不下来。** 这一条不是本仓库的缺口，
是对方公开信息本身的缺口；把它填平只能靠去问厂商，或者自己去测得同一个平台。

#### 本机这边：代价分解（三档同码，只差板级两个宏）

上一节的 744 周期是**带着地址隔离与特权隔离**的切换。RT-Thread 的公开内核不做按任务的
MPU 区域重写，所以要和它比，得把这两层剥掉再量。做法是把
`board/stm32f427/arkrtos_board_config.h` 里的 `ARKRTOS_USE_PRIV` / `ARKRTOS_USE_MPU`
临时置 0（这两个宏不是 Kconfig 符号，由 `ARKRTOS_ARCH_HAS_MPU` 派生，改板级头是最近路径），
三次构建其余源码完全相同，测完已还原。**这是测量变体，不是推荐配置，不入库。**

| 编入档 | Code (B) | `switch` min / avg / max (cyc) | min / avg (µs) |
|---|---|---|---|
| `MDK_TRACE` 关（MPU + PRIV 开） | 217714 | 744 / 744 / 745 | 7.75 / 7.75 |
| `MDK_TRACE` 关，PRIV 关 | 217646 | 723 / 725 / 2826 | 7.53 / 7.55 |
| `MDK_TRACE` 关，PRIV + MPU 关 | 216546 | 413 / 423 / 10988 | 4.3 / 4.4 |

三次各跑 `rt run 3000`，n=3000，`skip=0`。由此得到两个**直接读数**（不是推断）：

- **特权切换（`ARKRTOS_USE_PRIV`）≈ 20 周期 / 0.2 µs**：744 − 723 ≈ 20 周期，量级就是这么小，
  因为 `arkrtos_port_set_thread_priv()` 先比 CONTROL，只在真的需要变等级时才写并加 ISB；
  ping-pong 两侧都是内核任务，等级不变，所以它几乎免费。
- **MPU 地址隔离（`ARKRTOS_USE_MPU`）≈ 300 周期 / 3.1 µs**：423 → 723。两个任务的栈区
  不同区域，每次切换区域集都变，8 个区域逐个比对必然不命中，于是 24 次寄存器写 +
  一次 DSB/ISB 全程都付。**这是「带地址隔离的切换」与「不带地址隔离的切换」的差**，
  不是「同一功能两家实现」的实现质量差异。

`switch` 的 max 那一列不可当真：10988（114 µs）与 2826（29 µs）是单次离群，与板上
USB CDC 的 SOF（每 1 ms 一次）插入同源。min/avg 才是这段路径的成本。

#### 主频换算：算术练习，不是实测

423 周期（去掉 MPU/PRIV 的那一档）在不同主频上：

| 主频 | 折合 |
|---|---|
| 96 MHz（本机） | 4.4 µs |
| 168 MHz（F4 常见） | 2.5 µs |
| 200 MHz（睿擎 M0） | 2.1 µs |
| 480 MHz（H7） | 0.88 µs |

在这张表上，423 周期既可能对应「比对方宣称的 1 µs 慢」，也可能对应「比它快」。
**周期数是跨平台唯一可比的量，但「多少周期叫快」取决于对方没公开的那个前提。**
另外 Cortex-A7 与 Cortex-M4 同为 423 个周期也**不代表**同一段时间——A7 是超标量
乱序 + 流水深，同样一段 C 代码的指令条数完全不同。所以跨核折算是双重不可靠。

#### 明确不采信的二手数字

检索到的这几类一律不作证据、不入库：

- CSDN「STM32 实测 8 款 RTOS 性能」——正文带「墨衍会员·AI 创作全网分发」标记；
- CSDN「RT-Thread 实时操作系统性能优化实践」（称 1.2 µs @168 MHz M4）——同带 AI 标记；
- CSDN 问答（称 16 个通用寄存器切换约 8 µs @168 MHz）——与任何一份可实现的内核都对不上；
- 电子发烧友聚合页（称 M3 <5 µs @72 MHz）——方法用 `rt_tick_get()`，分辨率就是一个
  节拍，**物理上量不出微秒**。

采信它们的后果是：拿一个来源不明、方法自相矛盾的数字，与本机实测并列，得出一个看起来
权威但站不住的结论。按本仓库的规矩，这种情况宁可说「核不到」。

可信的学术来源只核到书目级：徐丽华、王宜怀、奚圣鑫《基于 Cortex-M4 内核的 RT-Thread
上下文切换机制剖析》，《计算机应用与软件》2025, 42(1): 213-216,302，
DOI `10.3969/j.issn.1000-386x.2025.01.030`。摘要里没有给出可比的周期数，正文未取到，
所以只能当「有人做过指令级剖析」的旁证，不能当数字来源。

#### 结论

**口径已对齐，数值不可直接并列。**

- 能对齐的是**区间定义**：本机的 `switch` 行与主流口径同为「调度决策点 → 被选中任务的
  第一条指令」。这是本次真正拿到的可比性。
- 数值上还不能并列：对方的 1 µs 缺测量平台与统计方式，本机是 96 MHz 内部 RC、2 kHz 节拍、
  3000 样本平均。把 4.4 µs 与 1 µs 放在一行里，只能得出「差 4.4 倍」这个**形式结论**，
  推不出「实现差多少」。
- 唯一干净的对照路径是：在**同一块 F427、同一 96 MHz、同一编译器**下移植 RT-Thread 开源
  内核，用同一套 ping-pong + DWT 脚本量它的 `switch`。**这一条没有做**——做了才有资格
  说「在相同条件下谁更快」。

## 5. 两个只有真机才会遇到的坑

### 5.1 调试器断开清 `TRCENA`，CYCCNT 会冻住

实测现象：`pyocd` 刷完固件、断开连接之后，`DEMCR` 读回 `0x00000000`，
`CYCCNT` 停在约 1e7（相当于开机后 0.1 s），于是所有读数都是：

```
raw 10654352 -> 10654352
back-to-back 0 cyc
1 ms delay = 0 cycles
```

根因是**调试器断开时把 `DEMCR.TRCENA` 清掉了**，CYCCNT 随之停止计数。
软件本身没有错，错在「以为开机时打开一次就永远开着」。

修法：`arkrtos_rt_counter_alive()` 在**每次开测前**重新写 `DEMCR |= (1u<<24)`
与 `DWT_CTRL |= 1u`，然后跑一小段循环比较两次 `CYCCNT` 是否真的在变。
`rt run` 会先调 `arkrtos_rt_init()` 重新武装；`rt show` 会打印 `counter: running`
或 `counter: NOT running`。

真实工程里如果没人接调试器，这个问题不会出现；**一旦接了 DAP 调试/烧录，就必须按这条处理**。

### 5.2 绝对不要清零 CYCCNT

最初为了「让统计从 0 开始」，`arkrtos_port_cyccnt_init()` 里写了 `DWT_CYCCNT = 0`。
结果：已经记过 `last_tick_cyc` 之后计数器被清零，下一个节拍算出
`jitter = −21756208` 这样的巨大负数，全部统计作废。

CYCCNT 是自由运行计数器，**差值语义已经足够**，清零只会制造假抖动。
三个移植层里的清零语句已全部删除，这是硬约束，不是风格问题。

## 6. 怎么用

### 6.1 打开

两条路，选一条：

- Kconfig：`config ARKRTOS_USE_RTSTAT`（`config/kconfig/Kconfig.features`），`default n`。
- 直接定义：`-DARKRTOS_USE_RTSTAT=1`。

F427 的 `ARKRTOS_TEST` 测试工程当前**按开启档编**（`Define` 里带 `ARKRTOS_USE_RTSTAT=1`），
这是刻意的「编入档」：默认关的特性如果没有任何工程编过，它里面的错会一直躺着。
关掉它体积会少约 2.7 KB Code + 1.2 KB ZI（含 1024 B 辅助任务栈）。

`ARKRTOS_USE_SCHED_STAT`（调度统计行）**依赖 `ARKRTOS_USE_MDK_TRACE`**：那组计数器的定义
和 `arkrtos_trace_last_cycles()` 都在 `arkrtos_trace.c` 的 trace 块里。这条依赖现在写进了
Kconfig（`depends on ARKRTOS_USE_MDK_TRACE`）。此前它没写，于是「关 trace、留 sched_stat」
这种组合能编过编译、倒在链接（`L6218E: Undefined symbol arkrtos_sched_stat_close`）——
这是 4.1 节做减法实验时踩到的真缺陷，已修。

### 6.2 Shell 命令

```
rt                 # 等同 rt show
rt show            # 打印五行读数 + jitter + counter 状态
rt reset           # 清空统计（不动计数器）
rt run [n]         # 先重新武装 + 清统计，再跑 n 次 wake 与 n 次 preempt，默认 200，范围 1..5000
```

`rt run` 是**主动制造**测量：它按顺序触发 `measure_wake(n)` 与 `measure_preempt(n)`，
所以这两行的 `n` 会相等且等于你给的值；`tick.isr` 的 `n` 只受运行时长影响。

失败时打印 `arkrtos_rt_last_error()` 的原因码：

| 码 | 含义 |
|---|---|
| 1 | `sem_hi` 创建失败 |
| 2 | `sem_ack` 创建失败 |
| `4 - tid` | 辅助任务登记失败（tid 为负） |

### 6.3 C 接口

`#include "arkrtos_rt.h"`（`ARKRTOS_USE_RTSTAT` 为 0 时整块是空的，调用点要自己 `#if`）：

```c
arkrtos_rt_init();                       /* 武装计数器 + 复位统计 */
arkrtos_rt_measure_wake(200);            /* 2 次 task_wait(1ms) 的唤醒延迟 */
arkrtos_rt_measure_preempt(200);         /* 200 次高优先级抢占延迟 */
arkrtos_rt_row_t rows[ARKRTOS_RT_ROWS];
uint32 n = arkrtos_rt_snapshot(rows, ARKRTOS_RT_ROWS);
int32 jmin, jmax; uint32 jn;
arkrtos_rt_jitter(&jmin, &jmax, &jn);
arkrtos_rt_reset();
```

`snapshot()` 返回实际填了几行；行名是静态字符串，不需要释放。
时间换算用 `unsigned long long`（内核没有 `uint64` 类型，这个坑踩过）。

## 7. 这道门禁防的是什么，以及还没做什么

### 门禁

`tools/rtstat_syntax_gate.py`，已挂进 `tools/ci_gate.py`（第 18 项）。

原因很直接：`ARKRTOS_USE_RTSTAT` 默认 0，两处测试工程之外按默认档编，
那五处 `#if` 平时**一个编译器都不经过**。改坏了照样全绿，直到有人在板上打开它。
门禁用 `armclang -fsyntax-only -DARKRTOS_USE_RTSTAT=1` 编 7 个文件
（内核 4 个 + m3/m4/m7 三个移植层），缺 armclang 判 FAIL 而不是跳过。

一个必须写下来的细节：编译端口层需要 `-DARKRTOS_BOARD_CONFIG="arkrtos_board_config.h"
-DSTM32F427xx -DUSE_HAL_DRIVER`。少了后两个，`stm32f4xx.h` 在选型处就 `#error` 退出，
`core_cm4.h` 根本不会被包含，报出来的是「`SCB` 未声明」——一个与被测改动毫无关系的假错误。
门禁里这几个宏是必需项，不是可选装饰。

**门禁只查语法。** DWT 在板上是否真的在跑、读数是否可信，门禁管不到。

### 未做（如实列出）

- **形式化 WCET**：没有静态路径分析，没有中断最坏嵌套模型。
- **完整中断延迟（port 级）**：`tick.isr` 不含 PendSV 上下文切换；`switch` 补上了
  「调度决策点 → 任务第一条指令」，但**中断引脚到 ISR 第一行**那一段（通常用 GPIO 翻转
  或示波器量）本模块没有做，不要拿 `tick.isr` 去代表它。
- **长时间漂移与温度/电压影响**：本表是单次运行读数，没有做小时级统计与角态扫描。
- **多优先级压力组合**：目前 `wake.hi` 只测「优先级 1 的辅助任务」，没有跑满优先级的
  抢占链，也没有把 `wake` 放在大量中断同时发生的场景里。
- **m3/m7 只有语法级验证**：没有对应的板上读数，F427 是 m4。
- **mempool/shell 等路径的临界区分解**：`crit.max` 只有一个总数，没有按调用点拆分。

这些不是「以后再补的欠账清单」的托辞，而是当下读数的适用边界：超出上面范围的结论，
本模块不出。

## 8. 这些读数能支持到什么程度的「实时性保证」

「有实测读数」和「有实时性保证」是两个不同的命题。前者给的是本板本配置的最大值，
后者要求一个与运行场景无关的上界。这一节把两者分开摆清楚，免得拿前者去冒用后者。

条件：STM32F427VGTx，96 MHz，节拍 2 kHz（预算 500 µs），`rt run 3000`。

### 8.1 有读数支撑的部分

| 路径 | 实测（min / avg / max） | 占节拍（avg / max） |
|---|---|---|
| 上下文切换本体（观测全关） | 711 / 714 / 2841 cyc = 7.4 / 7.4 / 29.6 µs | 1.5% / 5.9% |
| 上下文切换本体（仅关 trace） | 744 / 744 / 745 cyc = 7.75 / 7.75 / 7.76 µs | 1.6% / 1.6% |
| 上下文切换本体（默认全观测） | 983 / 3651 / 20960 cyc = 10.2 / 38.0 / 218.3 µs | 7.6% / 44% |
| 最长关中断 `crit.max` | 63 / 102 / 294 cyc = 0.7 / 1.1 / 3.1 µs | 0.2% / 0.6% |
| 节拍中断服务本体 `tick.isr` | 410 / 603 / 6870 cyc = 4.3 / 6.3 / 71.6 µs | 1.3% / 14% |
| 节拍唤醒全链 `wake.lo` | 4356 / 4393 / 22074 cyc = 45.4 / 45.8 / 229.9 µs | 9.2% / 46% |
| 节拍抖动 `jitter` | −22.7 … +22.6 µs | 4.5% |

五条可以直接写成结论的：

1. **切换路径是确定性的，不是统计性的。** 关掉 trace 后 `switch` 的 min 与 max 只差
   1 个周期（744 / 745）。实时性的地基是这条，不是平均值好看。
2. **抖动来自中断，不来自调度器。** `jitter` 的 ±22 µs 与 `tick.isr` 的 71.6 µs max 同源，
   都是被 USB SOF、shell 路径这类更高优先级中断挤开的结果；调度器本身不贡献抖动。
3. **没有一个样本漏过整拍。** 所有 3000 样本的实际等待都短于一个节拍，`late_n = 0`。
   这是「最坏也没赶上漏拍」，不是「平均赶得上」。
4. **开销大头是可观测性，不是调度。** 默认档 38 µs 的切换、关掉 trace 就回到 7.75 µs，
   关全部观测回到 7.4 µs。实时性不够时，关开关就有一条现成的余量，不用改架构。
5. **代价明码标价。** 地址隔离（MPU）300 周期 / 3.1 µs、特权切换 20 周期 / 0.2 µs
   （§4.2 的直接读数）。需要多硬的实时性，就能算出要付多少、或者关掉哪一层。

### 8.2 不能称为「保证」的部分

| 项目 | 现状 |
|---|---|
| 最坏值的身份 | 是「这块板、这个固件、这次采样里的最大值」，不是形式化上界 |
| `wake.lo` 的 229.9 µs | 单次离群样本，不是稳态，更不能当界 |
| 板上 USB CDC shell | SOF 每 1 ms 插入一次；没有做「去掉它之后」的对照实测 |
| 时钟源 | 内部 RC（HSI）经 PLL、3 个等待周期；外部晶振下的抖动形态未测 |
| 形式化 WCET / 中断嵌套模型 | 没有（详见 §7「未做」） |
| 中断引脚 → ISR 第一行 | 没有测（`tick.isr` 不含这段，不能拿来代表） |
| 长时间漂移、温度/电压 | 未做 |
| 多优先级满负载抢占链 | 未做（`wake.hi` 只测一个优先级 1 的辅助任务） |

### 8.3 一句话边界

**「当前配置下，最坏也没漏过一个 500 µs 节拍」——这条有读数支撑。
「存在一个数学上的最坏上界」——这条没有，本文从未这样写，也不要这样引用。**

要越过这条线，缺的不是更多采样，而是另一类工作：静态路径分析或中断嵌套形式化模型，
以及用 GPIO 翻转/示波器量引脚级中断延迟。那是另一种方法，不是把这五行的样本数加大。
