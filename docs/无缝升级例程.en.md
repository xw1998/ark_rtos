# Seamless upgrade walkthrough: upgrading a control loop while it runs

**[简体中文](无缝升级例程.md) | English**

> Condensed English edition. The Chinese page (无缝升级例程.md) is normative: every number below is
> copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no
> new claim and no new measurement.

This page is about the MiniApp pair `example/stm32f427/app_sdk/SEAMLESS_V1` and `SEAMLESS_V2`: a
control loop lives in RAM as a **MiniApp**, the new version is written into an **external NOR volume**
as a new file, and when the write finishes the new version takes over the same controlled variable.
Throughout, the loop is never frozen; the new program continues from the old program's state.

Verification tiers (the three-tier convention of `skills/arkrtos/SKILL.md` §6):

| Conclusion | Tier |
|---|---|
| Both versions compile, pack, and pass image self-check | Build-only |
| On board: V1 steady, V2 written to the volume, V2 takes over, iteration count and controlled variable continuous across versions | **Verified on board** |
| Negative cases: old version cannot take control back, new version exits when nobody releases, new version withdraws its request when giving up | **Verified on board** |
| Load stall: the kernel yields the scheduler in chunks inside the load loop; worst gap during load 242/381 ms → 45/64/72 ms | **Verified on board** (see §5.1) |
| Failure rollback / automatic version discovery | **Not done** (see §8) |

The example uses only existing pieces — MiniApp loading, the SVC facades (file, console, task,
heartbeat) and the file system — plus one **switchable chunked yield** added to the kernel for it
(`ARKRTOS_MINI_YIELD_CHUNKS`, §5.1) so the control loop keeps running during a load. Every number
comes from telemetry the device prints itself; nothing is host-side timing.

## 1. Why "MiniApp + external NOR"

The intuitive way to replace running control logic is A/B regions in on-chip Flash. That does not work
on this board: an on-chip erase under `sched_lock` stalls instruction fetch for about a second, as
`kernelsrc/src/arkrtos_installer.c` states ("an erase mid-frame stalls the CPU for about a second, the
RX interrupt cannot run"). External NOR has no such problem: erase/write blocks only **the task that
issued it**, never the CPU; the price is that somebody has to read the image back in order to execute
it — which is exactly the MiniApp usage:

- a MiniApp **is not installed and occupies no fixed slot**; it is read from the file system into RAM,
  and both memory blocks are returned on exit;
- the new version is just a new file in the volume, writing it never touches on-chip Flash;
- loading is the only action where the kernel holds the scheduler lock; it is now split into chunks
  with the lock released between reads, measured in §5.1.

## 2. Directory and artefacts

| Path | Content |
|---|---|
| `example/stm32f427/app_sdk/SEAMLESS_V1/` | 1.0.0, period 10 ms, the one being replaced; `Src/main.c` + `Src/seamless_proto.h` |
| `example/stm32f427/app_sdk/SEAMLESS_V2/` | 1.1.0, period 5 ms, the one taking over; `Src/main.c` + `Src/seamless_proto.h` |
| `build/seamless_v1.svcapp` / `build/seamless_v2.svcapp` | images with `type = miniapp`, `flags = no autostart` (build artefacts, not in the repo) |

The two projects' `seamless_proto.h` are **byte-identical**, deliberately duplicated: it is the
interface between the versions, so neither side may change it alone. The rule is one sentence — change
both copies in the same commit, and bump the trailing magic character together, so a new version can
never mistake an old version's record for its own.

## 3. Handover protocol: two records on the volume

File writes are not atomic, and a reader may catch a half-written record, so both records are
**fixed-length + magic + CRC32** (bitwise implementation, no table); the reader validates before use.

`/sx_state.bin` (64 B, writer = the current controller; **not** written while steady):

| Offset | Field | Meaning |
|---|---|---|
| 0 | magic | `SXS1` (`0x31535853`) |
| 4 | crc | covers 8..63 |
| 8 | seq | +1 on every write |
| 12 | owner | version identity: 1 = V1 (1.0.0), 2 = V2 (1.1.0) |
| 16 | phase | 1 = ACTIVE controlling, 3 = RELEASED handed over |
| 20 | tick_ms | wall time of the last control iteration |
| 24 | iterations | cumulative iterations |
| 28..40 | setpoint / pv / integ / out | controller and controlled variable, fixed point in thousandths |
| 44 | gap_max_ms | largest iteration gap so far |
| 48 | overruns | iterations whose gap exceeded 2× the period |
| 52 | period_ms | the writer's control period |
| 56,60 | reserved | 0 |

`/sx_req.bin` (32 B, writer = the new version):

| Offset | Field | Meaning |
|---|---|---|
| 0 | magic | `SXR1` (`0x31525853`) |
| 4 | crc | covers 8..31 |
| 8 | from_version | version the requester sees in place |
| 12 | to_version | the requester's own version |
| 16 | cmd | 1 = HANDOVER |
| 20 | req_tick_ms | when the request was written |
| 24,28 | reserved | 0 |

Both records carry **writer identity**, which yields two hard rules:

- only the current controller writes `/sx_state.bin`, and after writing `RELEASED` it touches nothing;
- only the requester writes `/sx_req.bin`, and **it withdraws it itself** (a giving-up requester must
  withdraw, see §7);
- the provider honours only requests where `to_version` is greater than its own; anyone else's request
  — including stubs left by a failed takeover — is not its business.

## 4. Handover sequence

```
V1 steady  ── reads /sx_req.bin every 100 ms (no request = quiet)
host       ── fs put writes V2 into the volume (NOR only, no on-chip Flash)
host       ── mini run V2   ← the only load stall
V2         ── reads state → writes /sx_req.bin → polls state every 50 ms for RELEASED (cap 5000 ms)
V1         ── sees the request → prints → writes RELEASED state once → deletes /sx_req.bin → returns (kernel returns both blocks)
V2         ── sees RELEASED → takes over → prints handover_gap → writes ACTIVE → enters its own loop
```

In the status line `gap=` is the **largest iteration gap so far**, `over=` counts iterations whose gap
exceeded 2× the period, `pr=` is the **longest duration of this poll's file read**; V2 has one more
column `last=` (the gap of the iteration just finished). V1 prints `[v1] v=1.0.0`, V2 prints
`[v2] v=1.1.0` — version, period and column count all tell you who is in control.

## 5. Measurements (F427, 115200, device-side telemetry)

> **Separate two numbers first** — later sections get them mixed up, they measure different phases:
> - **load stall**: while `mini run` reads the image into RAM the kernel holds the scheduler lock and
>   the loop gets no CPU; the chunked yield brought it down to 45/64/72 ms (§5.1).
> - **handover gap `handover_gap_ms`**: the blank instant between V1 releasing and V2 confirming; it
>   is **unrelated to loading** (the "handover" table in this section).
>
> The criteria differ too: loading is judged on `gap_max`, handover on `handover_gap < 1000 ms`.
> Neither is "downtime" — the loop keeps running while the image is uploaded and loaded.

**V1 alone (baseline)**: 93 iterations/s ⇒ actual period **10.7 ms** (nominal 10 ms), `gap=17` (the
round of "10 ms wait + 7 ms poll read"), `over=0`, `pr=7 ms`.

**Writing a new image into the volume (`fs put` 6116 B, no MiniApp started)**:

| Metric | Measured |
|---|---|
| Largest loop gap | never above 193 ms (carries the previous phase's record; not refreshed in this phase) |
| Iteration rate | ~90 /s (idle 93.5 /s) |
| Poll read duration | clearly longer: every poll in this window crosses the 2× period line (`over` grows at ~10/s) |

So writing the volume does **not** stop the loop, but it does stretch the loop's file read — the read
queues behind the uploader holding the file system.

**Loading another MiniApp (image already in the volume, load only, no volume write)** (baseline before
the change, after see §5.1):

| Metric | Measured |
|---|---|
| Largest loop gap | **193 ms** |
| Iterations in that second | 34 (idle 93) ⇒ about 0.5 s of loop time lost in the whole second |
| Poll read duration | up to **100 ms** |

### 5.1 The load stall: yielding the scheduler in chunks

The load loop used to hold the scheduler lock throughout, so during `mini run` the loop never got the
CPU and a 5.4 KB load was one uninterrupted stall (§5 measured 193 ms, another run 416 ms).
`arkrtos_mini_run` now unlocks and relocks after every `ARKRTOS_MINI_YIELD_CHUNKS` chunks of 256 bytes;
a single chunk read is still atomic inside the lock, and there is no intermediate state to protect
between reads, so releasing cannot let two loaders interleave reads of an image.

Same board, same firmware, same scripts, only this switch toggled (`0` = off, `1` = default on),
measuring the peak of V1's own `gap` (largest iteration gap so far) during the second of
`mini run V2`:

| `ARKRTOS_MINI_YIELD_CHUNKS` | Largest gap during load | Steady `gap` |
|---|---|---|
| `0` (off) | 242 ms, 381 ms | 18 ~ 22 ms |
| `1` (on, default) | 45 ms, 64 ms, 72 ms | 20 ~ 26 ms |

The yield cuts the worst load gap to **1/4 ~ 1/6**, and the remaining ~50 ms is the granularity limit
of "one chunk read": the lock still covers the whole of a single chunk read (open/read/close) and
others only get a turn once it finishes. Steady `gap` is the same order on both sides (18 ~ 26 ms, the
jitter of the polling file read, independent of the switch).

**Handover (four runs of the same script)**:

| Metric | Measured |
|---|---|
| request written → provider notices | 109 ~ 213 ms |
| `handover_gap_ms` (provider's `tick_ms` → new version's confirmation) | **27 / 31 / 224 / 407 ms** |
| of which "publish one state record" | normally 8 ~ 19 ms, once **218 ms** |
| iteration continuity | `it=994` → after takeover `resumed at it=994` (digit-for-digit, no reset to zero) |
| controlled-variable continuity | at takeover `pv=44.249 / 46.413 / 51.692`, not restarted from 0 |
| V2 period | 166 ~ 168 iterations/s ⇒ **5.9 ms** (nominal 5 ms) |
| `guard` | `verdict=0x0`, `starves=0`; the number of `fault` lines is unchanged across the handover (a graceful exit records no fault) |

Note that 407 ms is the blank at **the handover instant**, not downtime: the loop runs throughout
uploading and loading (worst load gap in §5.1). The worst case inside the handover window is 407 ms
against a criterion of < 1000 ms, all pass. In the 407 ms run the publish duration was not covered by
the instrumentation; the same 64 B record measured 218 ms in another run, so **the dominant term is
that one littlefs commit**, the rest being the polling intervals on both sides (provider 100 ms, new
version 50 ms).

## 6. Criteria and reproduction

Criteria (judged automatically by the script, all pass):

1. during upload the provider still publishes a status line every second (a `[v1] v=…` line is caught
   inside the upload window);
2. the provider prints both "request received" and "published and released";
3. the new version prints one "took over" and `handover_gap < 1000 ms`;
4. iteration count continuous across versions, controlled variable not reset to zero;
5. `gap_max < 1000 ms` (recorded on each side);
6. the number of `fault` lines is unchanged across the handover; `guard starves=0`.

Reproduction:

```bash
# pack (once per project)
py -3 tools/pack_app.py --project example/stm32f427/app_sdk/SEAMLESS_V1/MDK-ARM/seamless_v1.uvprojx \
        --type miniapp --no-autostart --out build/seamless_v1.svcapp
py -3 tools/pack_app.py --project example/stm32f427/app_sdk/SEAMLESS_V2/MDK-ARM/seamless_v2.uvprojx \
        --type miniapp --no-autostart --out build/seamless_v2.svcapp

# on board (device side, serial 115200; paths for `mini run` are absolute inside the volume)
fs rm /sx_state.bin                       # clear the previous run's site (optional)
fs put /seamless_v1.svcm 5088             # sent with tools/fs_put.py
mini run /seamless_v1.svcm                # V1 takes over, one status line per second
fs put /seamless_v2.svcm 6116             # write the new version into the volume while running
mini run /seamless_v2.svcm                # the new version requests and takes over
```

## 7. Two problems the board exposed and the fixes

**One: the poll interval may not equal the loop period.** The first version set the poll interval to
20 ms (period 10 ms) and the measured period became **23 ms** with `over` counting every iteration.
The cause is not scheduling but that file read: a 32 B record costs about **7 ~ 15 ms** for littlefs
open/read/close plus SPI NOR, so putting it in every period forces the loop to run at file-system
speed. Changing to 10× the period (V1 100 ms, V2 50 ms) brought the loop back to 10.7 ms / 5.9 ms.

**Two: giving up a takeover must withdraw your own request.** In the negative test (the state record
said "owner 1 is controlling" while nobody was running) the new version times out and exits — but it
left a request with `to_version = 1.1.0` on the volume. The provider only looks at
`cmd == HANDOVER`, so it would hand the loop over according to that stale stub while the requester had
already exited: **nobody in control**, worse than a failed upgrade. Both sides fixed:

- the new version deletes its own `/sx_req.bin` before giving up (whoever writes withdraws);
- the provider honours only requests whose `to_version` is newer than its own (`request_pending()` in
  `main.c`).

## 8. Boundaries and what is not done

- **The load stall is cut down in chunks but not eliminated**: after the kernel yields the scheduler
  in chunks inside the load loop, the worst gap during load fell from 242/381 ms to 45/64/72 ms (A/B in
  §5.1); the remaining ~50 ms is the granularity of a single chunk read (the lock is still held inside
  one chunk). Finer granularity costs more scheduling overhead and is not done for now.
- **No failure rollback / version downgrade**: when a takeover fails the new version exits and the old
  version keeps controlling; this is a deliberate consistency-first choice.
- **No automatic version discovery**: the new version is started explicitly by the host with
  `mini run`; there is no "scan the volume and upgrade itself" logic.
- **MiniApps have no API to "stop another MiniApp"**, so the handover channel is a file in the volume
  rather than an inter-process notification.
- **The `TASKKILL` line in `fault`**: a manual `mini stop` records one on the loader side (the
  bookkeeping of kicking a task out of the scheduler). A graceful exit records none; this acceptance
  run proves exactly that with "the number of `fault` lines unchanged across the handover".
- **`it=0` in `[v2] asking version 1.0.0 (owner 1, it=0)` is not a bug**: the provider does not write
  files while steady, so the ACTIVE record on the volume is still the snapshot it wrote at startup, and
  the iteration count is only refreshed at the moment of handover.
