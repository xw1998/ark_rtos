# Ark RTOS On-Board Unit Test Framework (utest)

> Condensed English edition. The Chinese page (单元测试框架.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

## In one sentence

The kernel contracts that only bite when misused — semaphore token conservation, FIFO
ring capacity, event-bit semantics, timer lifetime, audit-structure consistency — are
written as cases that can be re-run on the board with one command; break them and the
run goes red immediately, instead of some application crashing at a customer site at
night.

Shape follows RT-Thread's utest / Zephyr's ztest: cases **self-register**, assertions
**account without aborting**, the runner prints a ledger.

## How to use it

From the serial console (USART1 @ 115200 8N1 on F427):

```
ark> utest list              # list registered cases
ark> utest run               # run all
ark> utest run fifo_         # run only names containing "fifo_" (substring filter)
```

The command returns **the number of failed cases**, so scripts can judge red/green from
the return value:

```
ark> utest run
RUN   sem_token_flow
PASS  sem_token_flow
...
utest: 9 matched, 9 passed, 0 failed, 0 skipped; assertions 73 run / 0 failed
```

## Writing a case

A case is an ordinary function defined with `UTEST_CASE(id)`. It expands to a static
registration entry plus an `__attribute__((constructor))` function, so **no central
list needs maintaining**: add the file to the project and the case shows up in
`utest list` by itself.

```c
#include "arkrtos_utest.h"
#include "arkrtos_sync.h"

UTEST_CASE(sem_token_flow)
{
    int32_t h = arkrtos_sem_create("utsem", 2);
    UTEST_REQUIRE(h >= 0);              /* failure returns; later assertions do not run */

    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), 0);
    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), 0);
    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), -1);   /* tokens exhausted */

    arkrtos_sem_delete(h);
}
```

### Assertion macros

| Macro | Semantics | On failure |
|---|---|---|
| `UTEST_CHECK(expr)` | truth | account, continue |
| `UTEST_REQUIRE(expr)` | truth | account and `return` (precondition) |
| `UTEST_CHECK_EQ(a, b)` | `a == b` | account, continue |
| `UTEST_CHECK_NE(a, b)` | `a != b` | account, continue |
| `UTEST_CHECK_RANGE(lo, x, hi)` | `lo <= x <= hi` | account, continue |
| `UTEST_FAIL(msg)` | unconditional failure | account, continue |
| `UTEST_SKIP(reason)` | explicit skip | account and `return` |

Each assertion first increments `checks`, then decides whether it failed
(`failed_checks`); however many fail inside a case, they are all counted — the first
failure never swallows the rest.

### Summary ledger (`ark_utest_summary_t`)

| Field | Meaning |
|---|---|
| `cases` | cases actually executed |
| `passed` / `failed` / `skipped` | all-pass / any-failure / explicitly skipped case counts |
| `checks` / `failed_checks` | total assertions / failed assertions |
| `matched` | cases matched by the pattern (including skipped ones) |
| `overflow` | registration-table overflow count |

## Switch

`ARKRTOS_USE_UTEST` in `kernelsrc/include/arkrtos_features.h`, **default 1**; Kconfig
has a symbol of the same name (menuconfig → Services and components → Reliability and
operations) so it can be changed from a defconfig. At 0 neither the framework nor the
shell's `utest` command is compiled; size and behaviour are unchanged.

## Design points (each one exists because it bit us)

1. **All three toolchains can self-register.** Auto-registration relies on
   `__attribute__((constructor))`: armclang / GCC support it natively; ARMCC 5 lowers
   it into `.init_array`, called from `__main → __cpp_initialize__aeabi_` (verified by
   disassembling an armlink image). If a toolchain neither honours the attribute nor
   runs `.init_array`, the degraded symptom is `0 case(s) registered` — an explicit
   empty ledger, not a fake pass.
2. **Overflow is counted, not silently dropped.** The table is fixed-capacity
   (`ARKRTOS_UTEST_MAX_CASES`, default 64); excess registrations increment `overflow`
   and are reported, never quietly skipped.
3. **The framework does not depend on printf / shell.** Output goes through an
   injectable sink (`ark_utest_set_output`): console on the board, memory buffer on the
   host — the same core can therefore self-test on a PC.
4. **Cases never block.** They run in shell task context, so any call that could sleep
   uses `timeout == 0`, keeping the console alive.

## Gate

The `utest-host` check in `tools/ci_gate.py` compiles and runs
`tools/utest_host_selftest.c` with the host gcc, requiring exit code 0 and the line
`HOST-SELFTEST OK`. It proves **the framework's own accounting** (pass/fail/skip/
assertion counts/overflow/substring filter/auto-registration), nothing about the board;
change the framework and skew the accounting and the gate goes red.

## Host gates at a glance (board-independent)

Module-level "byte shuffling / ledger arithmetic" need not wait for the board: stub the
scheduler out and the same `.c` runs on a PC. These gates live in `tools/ci_gate.py`
(a missing host compiler is **FAIL, not skip**), and every test file states at its top
"what was verified / what was deliberately not verified":

| Gate item | Module under test | What it proves | Explicitly not proven |
|---|---|---|---|
| `sbuf-host` | `arkrtos_sbuf.c` | ring wrap, partial send, length-prefixed messages atomic as a whole, no cross-talk after a drop; **six exit classes of blocking send/recv** (no current task / cannot sleep / timeout / handoff granted / object deleted while waiting / user-mode poll) and "a half message must not release the reader" for mbuf | real sleep and real wakeup, real ISR handoff, timeouts driven by real ticks |
| `mempool-host` | `arkrtos_mempool.c` | block geometry and alignment checks, O(1) alloc/free, a rejected free leaves the pool untouched | SVC 0x20 argument checks |
| `mq-host` | `arkrtos_mq.c` | slot wrap, send/recv by declared length, truncation when the buffer is smaller but the message still fully consumed, refuse-when-full without overwrite, handle invalidated after delete | blocking / wakeup, waking waiters on delete |
| `sync-host` | `arkrtos_sync.c` | token conservation (take/exhaust/zero timeout/return), mutex ownership (re-entrant by holder refused, unlock by non-holder refused), all entry points refuse after delete | blocking / wakeup / token transfer, priority inheritance |
| `fifo-host` | `arkrtos_fifo.c` | create size threshold (≤ 8 refused without touching the buffer, usable capacity = size−9), write-when-full refused without overwrite, order preserved across wrap, short read, len ≤ 0 no-op, bad magic and NULL handle double-counted (read counts but loses no bytes), `write_refused` accumulated across FIFOs | concurrency beyond single-producer/single-consumer; uint16 truncation above size 65543 (known limit); division by zero on a hand-made size==0 header (caller violation) |
| `fault-host` | `arkrtos_fault.c` | empty table count 0; before full, 0 = oldest and order matches writes; count capped at `ARKRTOS_FAULT_RECORD_NUM`; after full, overwrite oldest and `0 = total − N`; out-of-range index returns NULL; tick per-record; re-init resets the cursor too; every record sits between paired critical sections | atomicity under real interrupt nesting (the stub makes critical sections no-ops, so pairing only shows pairing), the real HardFault path, the packed format read over SVC |
| `loader-host` | `arkrtos_loader.c` | image-header rejection order and boundaries (magic/compat version/type out-of-range and mask/image_size zero and wrap/entry out of range/reloc_offset and count and encoding version and payload_offset/entry alignment and past-end and ascending/ram_size zero and above single-block limit), relocation patch semantics (whole word added per ROM/RAM, MOVW+MOVT decoded into a 32-bit re-encode preserving instruction bits, block-end cutting an instruction returns the entry start with idx unchanged, `off < buf_off` skipped while the pointer advances) | load/stream install/Flash erase-write/pool relocation/unload/signature/CRC/crash counting, and **whether it actually boots** — those are evidenced by board cases and App examples (`utest` / `APP_DEMO` / T10–T12); `loader-host` does not stand in for them |

`sync-host` differs from the other three in one respect: it replaces
`arkrtos_task_get_current()` with a **settable** real pointer, so ownership judgements
such as "who may unlock" and "what counts as double-lock" are genuinely executed, not
merely compiled.

Standalone entry points: `py -3 tools/sbuf_host_gate.py` / `mempool_host_gate.py` /
`mq_host_gate.py` / `sync_host_gate.py` / `loader_host_gate.py` /
`fifo_host_gate.py` / `fault_host_gate.py` (`--gcc` picks the compiler, `--keep` keeps
the exe for reruns).

### `sbuf` blocking paths: programmable stub (2026-11-19)

`sbuf-host` used to cover only the non-blocking half. On 2026-11-19
`arkrtos_task_block_in_critical()` became a **programmable stub** (following the
"10. blocking send / 11. blocking receive" pattern in `mq-host`): depending on the mode it
returns "handoff now", "drain N bytes then hand off", "advance the kernel tick by 5000
before handoff", "object deleted", or "user-mode poll", and it can call `send_internal`
from inside the blocked window to feed data. That drives the whole "sleep → wake → exit
decision" path on the host. Every path runs all six exit classes:

| Exit | Trigger | Expectation |
|---|---|---|
| A no current task | `g_cur_task = 0` | `PARAM`, never sleeps |
| B cannot sleep | stub always returns `-1` (kernel context / scheduler locked) | `PARAM`, and `g_block_steps` equals the call count |
| C timeout | handoff once, then timeout | `TIMEOUT`, `g_block_steps == 2` |
| D handoff granted | space freed / data fed before handoff | actual byte count; partial success under stream semantics, FIFO byte order, mbuf `free` all correct |
| E handoff then immediate timeout | advance 5000 ticks before handoff | `TIMEOUT`, `g_block_steps == 1` |
| F object deleted while waiting | stub returns `ARKRTOS_WAKE_OBJ_DELETED` | `ARKRTOS_SBUF_ERR_DELETED` (-3) |
| G user-mode poll | kernel context but not declared in a handler | `WOULDBLOCK` (-6), `g_block_steps == 0` |

**Waiter-table hygiene is asserted both ways**: a case first runs G so the wait table
really registers once, then uses a `timeout 0` call to withdraw it and asserts
`g_ready_count` (the stub counts calls to `arkrtos_ready_add`) is back to 0; then it
reruns G and calls `reset_internal` directly, asserting `g_ready_count == 1` — that
second assertion proves the first one is not vacuous. Each case asserts 0 again after
`delete`, proving no waiter is left behind.

**The gate now checks a marker line**: `tools/sbuf_host_gate.py` used to look only at the
exit code; it now also requires `SBUF-HOST OK` in the output and echoes the test output.
Exit code alone cannot catch "not a single case ran".

**This set of cases found two real defects** (before the fix the cases hung / errored;
after it, 169 assertions are green):

1. **Treating "could not sleep" as a handoff ⇒ infinite loop.** The four exit blocks
   tested only the token bit (`(ret & ARKRTOS_WAKE_HANDOFF) == 0` means not granted),
   but "could not sleep" returns `-1`, every bit of which is 1, so the token test passed
   ⇒ treated as granted ⇒ re-sleep ⇒ interrupts toggled forever. The `mq` side already
   guarded with `if (ret < 0)` in `mq_send_after_block()`; `sbuf` did not. All four sites
   now read `if ((ret < 0) || ((ret & ARKRTOS_WAKE_HANDOFF) == 0))`.
2. **`ARKRTOS_SBUF_ERR_DELETED` (-3) was unreachable.** The header and
   [Stream and message buffers](流缓冲与消息缓冲.en.md) both list it, and `delete` really
   wakes waiters with `WAKE_OBJ_DELETED`, but the exit block flattened it to `PARAM`.
   All four sites now add
   `if (ret == ARKRTOS_WAKE_OBJ_DELETED) return ARKRTOS_SBUF_ERR_DELETED;`.

The cases are **regression gates** for both: delete the DELETED branch and the same test
reports `SBUF-HOST FAILED (4/169)`.

### `sbuf` closed to 100.00%: the 16th group, plus two pieces of structural dead code (2026-11-28)

What was left after the previous jump (19.43%, 99 lines) was not "needs a real
scheduler" but six entry points nobody had touched:

| Group | Lines | Judgement |
|---|---|---|
| Module entry / object table | `arkrtos_sbuf_module_init()` clears the whole table; `create_internal(NULL)` and `create_kernel_internal(NULL)` are parameter errors; the kernel entry pins `creator_id = 0`; the `ARKRTOS_SBUF_NUM+1`-th create returns `-1` | Fill four slots, the fifth must be refused; after `module_init` the old handle reports `is_alive == 0` |
| Handle resolution | the slot-out-of-range branch of `arkrtos_sbuf_get()`: `ARKRTOS_SBUF_HANDLE_FLAG \| ARKRTOS_SBUF_NUM` | seven entries (used / free / send / recv / reset / delete / peek) all return `PARAM` for it |
| Task teardown, `arkrtos_sbuf_release_task()` | invalid id returns at once, empty slots are skipped, both waiter tables of that task are pruned, a matching `creator_id` reclaims the whole object (kernel-owned ones survive) | a task-owned buffer disappears with task 1, the kernel-owned one stays **and that task's registration is gone** (one more byte then `g_ready_count == 0`); with an empty slot present, tearing down a second task must not touch it |
| Waiter-table exhaustion | the "table full = parameter error" exits of stream/message x send/recv, plus `wake_all` waking real waiters and `wake_one` skipping an `INVALID` one | `ARKRTOS_WQ_SLOTS` distinct tasks register through the user-mode path (register, never sleep); the next one must get `PARAM`; on `delete`, `g_ready_count` equals exactly the number registered |
| Infinite wait | with `timeout_ms < 0`, `remain_ms` returns `WAIT_INFINITE` and none of the four exit blocks may invent a local deadline | the stub hands off once and then times out; `g_block_steps == 2` proves the first round did not leave early on a local timer |
| Broken length header | `count < header`, header decodes to 0, header longer than the whole buffer, header without its body | the first three return `BADLEN` (`-1`); the fourth returns `-1` ("no whole message") instead of an absurd length |
| peek across the wrap point | the read pointer sits at capacity-2 and a 4-byte header is read across the end | the header splits in two pieces yet decodes to 5, and the whole `"hello"` comes back byte-identical |
| ISR entries | `arkrtos_sbuf_send_from_isr_internal()` and `arkrtos_mbuf_send_from_isr_internal()` in full | full buffer ⇒ `TIMEOUT` (never a half write), stream semantics report the bytes that fit, a message that does not fit reports `TIMEOUT` and leaves **no half header**, a registered reader really gets woken |

**The same round reshaped two pieces of structural dead code into reachable form**
(collapsing lines into one to please gcov would be fake green, not this):

1. `arkrtos_sbuf_put_bytes()` / `get_bytes()` used to split the length into two runs and
   clamp after each. The second clamp (after wrapping, the remaining length crosses the
   end again) **can never hold** while `len <= capacity`. They now loop "copy up to the
   end, wrap, copy the rest": one clamp, executed on every real wrap. Semantics are
   byte-identical (wrap, partial success and mbuf half-message cases all cover it).
2. `arkrtos_sbuf_peek_at()` took an `offset` parameter that its only caller always passed
   as `0`, so the "offset past the end" normalisation could never run. The parameter is
   gone; a header spanning the end is now covered by the `pos = 0` inside the loop.

Readings: `513/513 lines = 100.00%`, assertions **169 -> 277**, `SBUF-HOST OK` and
`py -3 tools/sbuf_host_gate.py` still green. **Boundary unchanged**: both ISR entries are
called directly on the host (`ENTER_CRITICAL` is a stub); ISR timing, real scheduler
wake-ups and real tick progression still need a board.

### `utest` closed to 100.00%: the failure and corner paths now really run (2026-11-28)

The framework's own self-test used to prove only five things (all-pass / one failure /
skip / filter / auto-registration). The remaining bookkeeping branches — failure detail
printing, overflow, zero assertions, no output sink — had never executed. This round
gives every branch a genuine call site; `tools/utest_host_selftest.c` went from 128 to
about 290 lines:

| Path | How it is exercised | Judgement |
|---|---|---|
| Failure printing (`ark_utest_fail` / `fail_num`) | assertions called directly from a case: negative `-5` (the sign branch of `put_l`), `detail == NULL`, `UTEST_FAIL`, `file == NULL`, and both `/` and `\` separators | `failed_checks == 6`; output contains `(got -5`, `(null):8: file.is.null`, `y.c:10: forwardslash` |
| Outside a case | `bump/fail/fail_num/skip/ctx_*` called from `main()` where `s_cur == NULL` | all return early, `ctx_failed()==0` and `ctx_skipped()==0`, no crash |
| Invalid registration | `register(0)`, missing name, missing function | none enters the table (`list()` count unchanged) |
| Empty pattern / no summary | `run("", &s)` and `run("...", 0)` | empty pattern runs everything (`matched == registered`) |
| Zero assertions | a case with an empty body | reports `PASS` with `[no assertions!]`, `checks == 0` |
| Over-long case name | a 299-character name | the line buffer fills and drops the rest; the printed line stays <= 159 characters, no overrun |
| Registry exhaustion | 64 distinct empty functions fill the table (dedup is by function pointer, so 64 different addresses are required) | `list()` reports `DROPPED (table full)`, `run()` reports `WARNING table full`, `summary.overflow > 0` |
| No output sink | `set_output(0)` then `list/run` | lines are still assembled and simply discarded, no crash |

**Two product-code changes in the same round** (neither is "merge lines to please gcov"):

1. `ark_utest_register()` now rejects `name == NULL`. It previously rejected only a null
   struct or a null function, so an unnamed case could enter the table and
   `name_matches()` would then dereference NULL at `*h != '\0'` — a real crash path, not
   defensive padding. The `NULL` fallback in `put_s` did **not** become dead code: when
   `ark_utest_fail(file == NULL)` is called, `base_name` still hands the NULL back.
2. The `n < (int)sizeof(tmp)` bound in `put_u()` is **never false**: `tmp[24]` is enough for
   a 64-bit unsigned value (20 decimal digits at most, 16 hex), and `base` is only ever
   10 or 16. The check is gone, with a comment saying why 24 bytes always suffice.

Readings: `208/208 lines = 100.00%`, branch directions 84/84, calls 97/97;
`HOST-SELFTEST OK` and the `utest` row of `tools/coverage_gate.py` stay green.
**Boundary**: the self-test proves the framework accounts and prints correctly for these
inputs; it does not prove the board-side `shell utest` wiring or `constructor`
auto-registration on each of the three toolchains — those are covered by per-board cases
and disassembly (see the header comment).

### `devid` closed to 100.00%: missing hooks, a wrong slot and two always-false branches (2026-11-28)

Thirteen lines (91.67%) were still unreached after the previous hop, in three shapes:

| Path | How it is exercised | Judgement |
|---|---|---|
| Secret slot too long | the board `_secret` stub returns 65 (> the 64-byte limit) | `boot()` returns `ERR_RANGE` and `ready == 0` -- half a key is never left behind for later use |
| Secret unreadable after boot | boot normally first (`ready == 1`), clear the stub's `g_sec_ok`, then call `prove()` | returns `ERR_NOKEY` and the MAC does not change by a single byte -- fail closed, never a MAC over a half-read state |
| Board hooks missing (weak fallback) | the new `test_devid_weak_host.c` is built two ways: one defines nothing (no UID hook), one supplies only the UID hook (no secret hook) | no UID -> `ERR_STATE`, source `none`, `prove()` returns `NOKEY`; UID but no secret -> boot `OK`, `ready == 0`, source `uid-only`, `prove()` returns `NOKEY` |

**Two always-false branches removed in the same round** (same precedent as `put_u` and
`peek_at`):

1. "Hash first when the key is longer than a block" in `devid_hmac()`. Both call sites hand
   the board hook a 64-byte buffer and return `ERR_RANGE` if more comes back; the built-in
   secret is clamped to 64 as well -- so `klen > 64` is never true. An over-long key should
   be rejected in the configuration layer, not silently rewritten inside the HMAC.
2. The second 32-byte clamp of `id_len` in `boot()`. `arkrtos_features.h` pins
   `ARKRTOS_DEVICE_ID_LEN` to 8..32 with `#error`, so an out-of-range value does not even
   compile; that check is never true either.

**The built-in secret grew from 32 to 72 bytes**: `DEVID_SECRET_DEF` in
`tools/coverage_gate.py` went from 32 to 72 bytes, so "clamp a built-in secret larger than
the 64-byte buffer to 64" in `boot()` and `prove()` really executes on the host -- that is
the shape of a genuine configuration error (someone stuffing long material straight into the
macro), and it must be clamped rather than overrun. The clamped 64 bytes are still a valid
key, so not a single assertion in the BUILTIN configuration changed.

Readings: `152/152 lines = 100.00%` (five-configuration union), and `DEVID-HOST OK` /
`DEVID-HOST BUILTIN OK` / `DEVID-WEAK OK` plus `DEVID-GATE OK` from
`tools/devid_gate.py` all stay green.
**Boundary unchanged**: both hooks are host strong/weak symbols; the real OTP / fuse read
timing, read failures and the power-loss window can still only be proven on the board.

## Line-coverage gate (`coverage-host`, 2026-11-17)

The `*-host` column above only answers "did the cases pass". A module whose cases pass
while covering 30% of its lines looks identical to one covering 80% in a gate report.
`tools/coverage_gate.py` turns that into one comparable number: recompile with the same
test sources and the same macro set plus `--coverage`, then read `gcov`'s

| Criterion | each module's **line coverage not below the baseline**; a missing host compiler or `gcov` is FAIL, not skip |
| Baseline file | `tools/coverage_baseline.json`, keyed by module base name, value = measured percentage |

Four rules are written down so this row of numbers is not over-read:

1. **Only the one `.c` linked by the host cases is measured** — not test files, not the
   whole repository. Most kernel lines (scheduler, SVC, drivers, shell) are never
   linked on the host, so these numbers **are not whole-kernel coverage**.
2. **The bar is "not below the current value", not an industry standard.** Adding code
   grows the denominator and can turn the gate red; the right response is to add cases,
   and to `--update` only with a written reason. Never quietly lower it.
3. **Board paths have a natural ceiling.** The low forties of `sync` / `mq` is exactly
   the part needing a real scheduler; `sbuf` now reaches the blocking **exit decisions**
   through a programmable stub, but real sleep, real ISR handoff and timeouts driven by
   real ticks still need the board — a design fact, not a defect; do not read `100%` as
   "this module is well tested".
4. `gcov` counts "declared but not executed" lines in the denominator, so large `#if`
   OFF blocks depress the percentage. Baselines were measured in the **default profile**
   (each case's own `-D` set); changing macros means re-pinning.

history. The gate now covers **77 modules = 135 host cases** (the authoritative,
per-module table is the Chinese page). One addition is `drvled`, the board GPIO

matching `drvblk.c`'s static adapters), which also cleared 5
`-Wmissing-prototypes` and 4 `unused-parameter` warnings with no behaviour change.
`kernelsrc/tests/host_stm32/stm32f4xx_hal.h` is the first STM32F4 HAL host stub; it
guards the register block with an `#ifndef GPIOA` probe so the real CMSIS headers can
still be included (`-Ikernelsrc/tests/host_stm32` must come before the F427 include
set). **Not proven**: real GPIO levels, clock gating and real HAL timing — the
`HAL_GPIO_*` functions are recording stubs and the port pointers are opaque handles
that would fault if dereferenced.

The same cut also wired up the board watchdog (`board/stm32f427/drvwdg.c`, 100.00%,
76 assertions). It does **not** go through the STM32 HAL: it pokes three absolute
register windows, so the case maps IWDG (`0x40003000`) and RCC (`0x40023874`) for real
in `main()`. `DBGMCU_APB1_FZ` (`0xE0042008`) cannot be mapped — Windows keeps a private
reservation starting at `0xE0000000` (`VirtualQuery` reports 0x1FFF0000 bytes of
MEM_RESERVE) — so the driver exposes that one address as an overridable
`WDG_DBGMCU_APB1_FZ_ADDR` and the case `-D`s it onto mapped RAM (`0x40004000`); only
the address changes, the read-modify-write semantics are still exercised. The case
pins: the prescaler search (smallest that fits 12 reload bits: 100 ms -> /4 * 800,
512 ms -> /4 * 4096, 513 ms -> /8 * 2052, 1 s -> /8, 1 ms -> 8 ticks, 32768 ms ->
/256 * 4096) and the timeout read-back from the registers in each; refusal of 0 ms,
32777 ms, a request that would wrap 32-bit arithmetic (134217856 ms) and
`0xFFFFFFFF` without touching a single register; refusal while the LSI never reports
ready (and the counter is never started); bounded spins with PVU / RVU stuck while the
configuration still lands; the debug-freeze bits being set each time without trampling
others; and `feed` writing only `0xAAAA`. **This cut fixed a real defect**: `timeout_ms
* 32` wraps in 32-bit unsigned, so 134217856 ms used to be accepted as 4096 ticks
(128 ms) and started an unstoppable counter; it is now refused before the multiply.
**Not proven**: the ordering of the three KR commands (KR is one address and plain RAM
only keeps the last write; the "start before unlock" rule is a board reading), the
real LSI frequency (nominal 32 kHz, about +/-50%, so the timeout is only ever
"roughly"), and whether a reset actually happens.

The board SPI-NOR driver (`board/stm32f427/drvnor.c`, 100.00%, 176 of 442 lines
executable, three profiles with 104 / 4 / 5 assertions) is wired up next. The driver
talks through STM32F4 HAL SPI, so the case installs recording stubs for
`HAL_SPI_Transmit` / `HAL_SPI_Receive` and puts a byte-level W25Q128 slave model behind
them (command / address / data phases, page buffer, capacity mask, WEL / WIP bits).
Transaction boundaries are inferred from the **call shape**, not by reading
`GPIOE->BSRR`: BSRR is write-only, so plain RAM only keeps the last asserted value and
the release is invisible; one command is one `Transmit` and the page-program payload is
the next one. Pinned: JEDEC `0xEF4018` identification and the 16 MiB capacity, SPI2
initialisation parameter by parameter plus CS high, an early return on repeated init,
in-page and cross-page programming (only in-page bytes move, WEL is set by WREN and
clears itself after programming), sector and range erase (alignment mask, only
intersecting sectors, the already-erased sector surviving a failure on the second),
WIP polling timeout, and every failure code on the transmit / receive / erase
injection paths. `nor_ready` and friends are statics that cannot be reset in one
process, so a capped capacity (`NOR_TEST_CLAMP`, id[2]=0x1F) and a device smaller than
one sector (`NOR_TEST_TINY`, id[2]=0x08) each get their own process. **This cut fixed a
real defect (four entries of the same shape)**: the 32-bit additions `addr + len` and
`addr + NOR_SECTOR_SIZE` wrap, so `read` / `write` used to accept
`addr=0xFFFFFFF0, len=32` as inside the device, and `erase_sector` / `erase` had the
same hole; the checks now compare `addr >= capacity` first and
`size > capacity - addr` second. **Not proven**: real SPI timing (clock polarity /
phase, CS setup and hold), the real page-program and write-cycle times, power-loss
windows, and pin-level constraints — those are board readings.

The on-chip flash controller (`board/stm32f427/drvflash.c`, 98.51%, 65 of 66
executable lines, two profiles with 93 assertions each) is wired up next. The driver
goes through the STM32F4 HAL flash API (`HAL_FLASH_Unlock/Lock`, `HAL_FLASHEx_Erase`,
`HAL_FLASH_Program`) but also **reads** `FLASH->OPTCR` (`0x40023C14`) and
`FLASH->OPTCR1` (`0x40023C18`) for the read-out-protection level and the write-protect
masks, so the case claims one 64 KiB page at `0x40020000` (the flash register block
shares it with GPIOB/GPIOE/RCC) via `VirtualAlloc` / `mmap(MAP_FIXED)` and installs
recording stubs for the three HAL entries. Pinned: the sector-size table (16K x4, 64K,
128K from sector 5) at its boundaries including the last byte and the off-chip cases
`base-1` / `base+SIZE` / `0xFFFFFFFF`; `Sector` / `NbSectors` / `TypeErase` /
`VoltageRange` field by field for a single-sector erase; the start and count of a
spanning erase (`base+0x1000, 0x40000` starts at sector 0 and covers 7); the per-word
address / data / programming type of a write; exactly one unlock and one lock per
operation with the controller left locked; still locked after an injected failure;
every illegal range rejected with -1 **before** the first HAL call, with zero unlocks
and zero erases; and the protection read-out (RDP plus the low 12 WRP bits of `OPTCR`,
the high 12 of `OPTCR1`) with the registers unchanged by the call. **This cut fixed two
real defects**: `erase` computed `end = addr + size - 1` and then mapped it back to a
sector, so a wrapped 32-bit sum could land below the start sector and
`last - first + 1` underflowed into `0xFFFFFFFF` sectors handed to the HAL; and
`write` validated no address range at all (an out-of-range write only failed inside
the HAL, after unlocking). Both now reject before the first HAL call by comparing the
offset from the base first and the size against what is left. The capacity is a
compile-time constant (`CHIP_FLASH_SIZE`, default 1 MB from the partition header), so
the 1 MB and 2 MB sector numbering each get their own process — hence two profiles; the
2 MB one also reaches the high 12 bits of `OPTCR1`. **One line left uncovered**
(`drvflash.c:115`) is the sentinel re-check after the sector number is computed:
unreachable behind the range check, kept as defence and reported honestly. **Not
proven**: real erase/program timing and write-cycle times, power-loss windows,
option-byte programming and read-back, and the real effect of RDP/WRP on the debug port
and bus access — only the board can show those.

The USART register-level driver (`board/stm32f427/drvuart.c`, 100.00%, all 99
executable lines, 130 assertions) came next. The upper half goes through the HAL
(two `HAL_GPIO_Init` calls for PA9/PA10, the eight `HAL_UART_Init` fields,
`HAL_NVIC_SetPriority` with a numerically lower priority than SVCall,
`HAL_NVIC_EnableIRQ`); the lower half reads and writes `SR` / `DR` / `CR1`
directly, so the case really claims `USART1`'s page (it `VirtualAlloc`s /
`mmap(MAP_FIXED)`s `0x40010000`) and turns those registers into writable memory.
The real CMSIS `__get_PRIMASK` / `__disable_irq` / `__set_PRIMASK` are ARM
assembly builtins that x86 cannot compile, so a minimal device header
(`kernelsrc/tests/host_stm32/min_cmsis/stm32f4xx.h`, the real F4 `USART_TypeDef`
layout: SR 0x00 / DR 0x04 / BRR 0x08 / CR1 0x0C / CR2 0x10 / CR3 0x14 / GTPR 0x18)
plus a shadow PRIMASK and a hook stand in; the hook samples `(tx_idle,
CR1.TXEIE)` both when the interrupt mask goes down and when it comes back, which
turns "the check for an empty ring and the kick of TXEIE happen inside one
critical section" from a code reading into an assertion. Pinned: the GPIO /
parameter / NVIC / CR1 state after open (RXNEIE only; TXEIE and TCIE off) and the
idempotence of a repeated open; a refused `HAL_UART_Init` makes open return 0
without recording the port as open, and the next open really retries; the receive
ISR reads SR then DR and pushes the byte; a write arms TXEIE, and when the ring
empties TXEIE drops and TCIE is armed until the last stop bit, after which TC
clears TCIE; a full ring returns 0 bytes and bumps
`arkrtos_fifo_write_refused()`; close clears RXNEIE/TXEIE/TCIE before clearing UE
and leaves `opened=0`, `tx_idle=1`, with no leftover enable on reopen; read after
close returns -1 instead of handing out stale bytes, write on a closed port
returns -1 instead of claiming "0 bytes written", and `ctrl` always returns -1
(nothing in the tree calls it). The FIFO is linked for real
(`kernelsrc/src/arkrtos_fifo.c`), compiled but not counted; usable capacity is
pinned at `UART_PIPE_SIZE - 9` (8-byte header plus one slot to tell full from
empty). **The same cut fixed six state/flag defects**: read handing out stale
bytes, write claiming 0, close leaving interrupt enables armed (an interrupt
storm once UE drops), ctrl reporting success for every command code, open
ignoring a failed `HAL_UART_Init`, and open not clearing a leftover TCIE.
**Not proven**: real UART timing (baud error, framing/overrun flags, actual stop
bit length), real NVIC preemption and interrupt-mask latency, and what a real
`HAL_UART_Init` would refuse - the stub only answers with the injected status.

The GDB remote serial protocol agent (`kernelsrc/src/arkrtos_gdbstub.c`,
100.00%, all 424 executable lines, 193 assertions) closes half of the "no gdb
remote stub" item. The case plays the gdb side: it builds `$body#cs` by the RSP
rule (low 8 bits of the byte sum), parses the replies and checks the acks.
Pinned: a bad checksum and an oversize packet are nacked with `-` and get no
reply (an oversize packet is discarded up to `#` so the buffer cannot be
overrun); `QStartNoAckMode` is itself still acked and afterwards neither side
sends an ack while replies keep flowing; `m` / `M` / `X` go through the board
hooks and answer `E01` for out-of-range or malformed arguments rather than
claiming success, and the `X` escape (`}` plus (c ^ 0x20)) round-trips byte for
byte; `p` / `P` / `g` / `G` go through the register hooks in little-endian and
answer `E01` when the board supplies no `reg_count` / `reg_read` / `reg_write`;
`qRcmd` hands the hex text to the hook and returns the hook's output hex, and
answers `E01` past the monitor buffer; `c` / `s` / `vCont` / `Z0` and every
unimplemented packet get the empty packet, never `OK` (gdb reads an empty packet
as "unsupported" and `OK` as success); byte-at-a-time and whole-buffer feeds go
through the same state machine, and `poll` pulls from `byte_get`; `feed` / `poll`
before `init` return -1. **The same cut replaced dead runtime code in `X` with a
compile-time contract**: a packet body is bounded by 512 bytes and therefore
always fits the output buffer, so the old `cnt >= GS_OUT_MAX` branch inside the
loop could never be taken; it became `#if (PKT_MAX > GS_OUT_MAX) #error`, so
"the body fits the scratch buffer" is an unbreakable contract instead of a line
no test can reach. **Not proven**: interoperation with a real gdb client (there
is no usable gdb on this machine), real UART baud/loss, and the mapping from
register numbers to any particular ABI; and it does not continue, step or set
breakpoints - the agent is polled by its caller and has no execution stream to
take over, so faking a stop would be worse than answering "unsupported". There
is no authentication either: it belongs on a debug port only, which is why it
ships off by default.

## Compiler-warning gate (`warn-clean`, 2026-11-17)

This machine has no cppcheck / MISRA / clang-tidy, and the host GCC 4.8 has no
`-fanalyzer` (GCC 10+ only); the only thing able to do path-sensitive analysis is the
local cross toolchain's `riscv64-unknown-elf-gcc-10.2.0`, which is the separate
`analyzer` item below. `warn-clean` does something smaller: turn the compiler's own
semantic analysis all the way up. `tools/warn_gate.py` compiles the **21 host-compilable
TUs** (10 host cases + the 10 modules they link + SDK stdio) with
`-Wall -Wextra -Wshadow` and requires **zero warnings**. (First reading, 2026-11-17. As of
2026-11-28 the option set is thirteen warnings and the set has grown to **279 TUs / 135
cases**; the Chinese page carries the per-profile breakdown.)

| Item | Value |
|---|---|
| Gate item | `warn-clean` (item 42 of `ci_gate.py`) |
| Standalone entry | `python tools/warn_gate.py` (`--selfcheck` first proves the gate is not blind) |
| Criterion | every TU compiles and the output contains no `warning:`; one is enough to go red |
| Anti-false-green | `--selfcheck` creates two TUs: one that must warn (unused parameter + read of uninitialised) and one with a non-static function that has no prototype. The first judges the gate blind if no warning appears; the second proves the interface-exposure set is really on the command line (`-Wall -Wextra` is silent on it) |

**It caught something real**: `p_tsk` in `arkrtos_sync_release_task()` was declared but
never assigned — all three tables' wait queues were comparing wild pointers, so dead
tasks stayed in the queues forever and their locks were never released. It compiles,
the board reports nothing; only reading the code or the warning finds it. The fix and
nine assertions pinning the behaviour are in the "task teardown" section of the
synchronisation page (removing the fix fails 7 assertions).

**The interface-exposure class joined the gate on 2026-11-18**
(`-Wmissing-prototypes` / `-Wstrict-prototypes` / `-Wold-style-definition`). Counted on
the same 21 TUs beforehand: 25 warnings, all `-Wmissing-prototypes` (**5 kernel + 20 test stubs**), in two families:

* **5 in the kernel** — `arkrtos_mq_send_from_isr` / `arkrtos_mq_recv_from_isr` in
  `arkrtos_mq.c`, plus `arkrtos_sem_post_from_isr` and the two host-only internal functions
  `arkrtos_mtx_propagate` / `arkrtos_mtx_recalc_priority` in `arkrtos_sync.c`. The first
  three have always been declared in the umbrella header `arkrtos.h`, but **the TU defining
  them includes only its module header**, which carried no prototype for them, so the
  compiler saw no prototype at the definition; the last two are non-`static` only under
  `ARKRTOS_SYNC_HOST_TEST` (host cases call them directly) and that branch had no
  prototypes either. Fix: add the identical prototypes to the module headers
  (`arkrtos_mq.h` / `arkrtos_sync.h`) and to the host-only branch. **No new public API was
  created.**
* **20 in test stubs** — 7 host cases replace kernel functions locally: 12 trace hooks
  (`test_sbuf_host` 3, `test_mq_host` 3, `test_sync_host` 4, `test_eset_host` 2), 2 port IRQ
  toggles and 4 ready probes in `test_waitmulti_host`, plus `arkrtos_fault_record` and
  `arkrtos_shell_print` one each. They were defined without a prior prototype; the fix is
  declare-before-define with a comment saying a stub is an interface too.

`-Wstrict-prototypes` and `-Wold-style-definition` reported **nothing** when enabled (every
signature in the tree carries prototypes); they are pinned to stop a regression to K&R
style. After the merge the default LA64 image is **byte-identical** (`9e59d693…`,
31,462,512 B, text 367512), and `arkrtos_sync.c` under armclang F427 `-O2 -c` is Code 9726
/ RO 288 / RW 4 / ZI 2248, exactly as before, with zero warnings.

**`-Wconversion` is enabled (2026-11-19)**: 33 reports on the same 21 TUs -- 6 narrowing
plus 27 sign. The old text listed `-Wconversion 33` and `-Wsign-conversion 27` side by side,
which double-counts: GCC's `-Wconversion` implies `-Wsign-conversion`, so the 27 are already
inside the 33. Two policy lines only:

1. Add **explicit casts** only; do not change types, comparison semantics or algorithms.
   Narrowing sites get `(uint8)` / `(uint16)` so the truncation that used to be implicit is
   written down; handle-mask comparisons become `((uint32)handle & MASK)` (int32 to uint32 is
   value-preserving, bit pattern identical).
2. The criterion is **not** "it compiled" but "the default LA64 image is byte-identical".

Where the 33 are: `arkrtos_sync.c` 15 (including the `cond_handle` / `mtx_handle` families),
`arkrtos_mq.c` 7, `arkrtos_eset.c` 5, `arkrtos_fifo.c` 3 (`fifo->size` and the two indices
after `%` are explicitly truncated to `uint16`), `arkrtos_sbuf.c` 2 (that TU compiles to an
empty object in the default profile, so the armclang switch-on build is what covers it), and
`kernelsrc/tests/test_eset_host.c` 1. Afterwards `warn_gate.py` is clean on all seven
options, the `objcopy -O binary` image is still `9e59d693…` / 31,462,512 B / text 367512
with `cmp -l` **0 bytes different**, and armclang F427 `-O2 -c` gives the same
Code/RO/RW/ZI for all five TUs as before, zero warnings.

**`-Wcast-qual` is enabled too (2026-11-19)**: the 2026-11-17 count was 14, all in
`kernelsrc/tests/test_eset_host.c`; the recount on the same day gives **0** -- those 14 were
already fixed by the intervening commits (the dropped `const` all lived in test stubs and went
away with the stub declarations). The count was redone before enabling rather than copying the
old number into the policy, because enabling on a stale number would just turn the gate red
once. No source change in this commit, so the default image cannot have moved (it was
re-verified as `9e59d693…` one commit earlier).

**`-Wwrite-strings` is enabled too (2026-11-19, nine options in total)**: the recount on the
same 21 TUs gives **20**, all `create("literal")` passing a literal to a `char *` parameter
(`test_sbuf_host` 6, `test_sync_host` 10, `test_mq_host` 4). The fix is not in the tests: the
`create`/`open` parameters of `sbuf`/`mq`/`sync`/`eset`/`dev`/`event`/`mpool` became
`const char *` -- **53 `name` parameters** (23 public headers / 16 kernel definitions /
14 SDK) plus **4** internal `copy_name(char *dst, const char *src)` `src` parameters. Before
touching them the tree was grepped for `name = name` assignments: only `arkrtos_rt.c` and
`arkrtos_sec.c` keep the name, and both already took `const char *`; every other site copies
it into a fixed array on the spot. So this is a **pure signature relaxation** -- callers
passing `char *` still compile, ABI and instructions unchanged (the tree already had a
precedent: `arkrtos_mempool_create_internal` always took `const char *`). The 14 now-redundant
`(char *)"literal"` casts in `test_eset_host.c` were removed at the same time.

**A lesson worth writing down: `-Wcast-qual` and `-Wwrite-strings` are coupled.** With only
`-Wcast-qual` on, a string literal is still `char[N]` and none of those 14 casts is reported;
only after `-Wwrite-strings` makes literals `const char[]` does the same batch immediately
report "discards qualifier". So "cast-qual alone reports 0" must not be read as "the casts
were already fixed"; the two options have to be read as one policy. After the change
`warn_gate.py` is clean on nine options over 21 TUs with both self-check probes still firing
(3 / 1), the default LA64 `objcopy -O binary` image is still `9e59d693…` / 31,462,512 B /
text 367512 with `cmp -l` **0 bytes different**, and armclang F427 `-O2 -c` gives identical
Code/RO/RW/ZI for all nine TUs (including the driver SDK `arkrtos_drv_oslib.c` with `-DARKRTOS_DRV_USER_MODE=1`), zero warnings. `docs/api/Ark RTOS_API参考.md` was
regenerated by `gen_api_doc.py --md` (22 lines) rather than hand-edited -- hand edits fight
the generator, and the `api-doc` gate is exactly "regenerate and `git diff` must be empty".
**The last three were pinned in the same pass (2026-11-19, twelve options in total)**:
`-Wpointer-arith` / `-Wundef` / `-Wbad-function-cast` each report **0** on the same TUs and
needed no source change. They never caught anything; they are enabled to pin against
regressions -- a pointer-arithmetic assumption, a `#if` without `defined`, or a cast of a
function result to a different type turns the gate red immediately. The set is now twelve
options, all clean on these TUs, with the same criterion of a byte-identical default LA64
image (`9e59d693…`, `cmp -l` 0) because these only add compile-time checks and emit no code.
**Zero warnings is not zero defects**: it only says these TUs show no breakage under these
twelve rules; logic problems are the job of the `analyzer` tier and the tests.

**Boundary written down**: this is not static analysis; do not read it as "static
analysis done". It runs only the 21 host-compilable TUs; the rest of the kernel depends
on architecture headers (`__svc`, CMSIS, LA64 CSRs, RISC-V PMP) and needs its own
toolchain. This gate does not claim to cover them, nor to find logic defects. The
path-sensitive half is the next section.

## Path-sensitive static analysis gate (`analyzer`, 2026-11-18)

2026-11-17 recorded "no static analysis tool on this machine". Re-checking the
toolchain found Luban-Lite's `riscv64-unknown-elf-gcc-10.2.0` locally — GCC 10 is the
release where `-fanalyzer` landed, so there is no need to wait for cppcheck or the
network (GitHub is reset, PyPI reachable but no matching binary package).

`tools/analyzer_gate.py` compiles TU by TU and catches path defects of the
"compiles fine, explodes on the board" kind: double-free / use-after-free /
null-dereference / resource leak / uninitialised.

| Item | Value |
|---|---|
| Gate item | `analyzer` (item 27 of `ci_gate.py`, right after `warn-clean`) |
| Standalone entry | `py -3 tools/analyzer_gate.py` (`--list` prints coverage and skip reasons) |
| Target ABI | fixed `-march=rv32imac -mabi=ilp32`: RV64 has 64-bit pointers and floods 32-bit address-to-pointer TUs with 21 (loader) / 152 (task) architecture noise |
| Coverage | 48 TUs: `kernelsrc/src` 47 minus 5 non-compilable, plus `sdk/app_sdk` 3 + `sdk/driver_sdk` 3 (driver side with `-DARKRTOS_DRV_USER_MODE`) |
| Skips | 5, each printing its reason: missing `lfs.h` / `ark_shell.h` / `ark_vfs.h` / `-DARK_BUS_*` profile macros |

**It caught one on the first run**: the crash-log variables in `arkrtos_crash.c` carry
`__attribute__((zero_init))`, an ARMCC-only attribute that both GCC and armclang treat
as an "ignored directive". It is now the `ARKRTOS_ZERO_INIT` macro (keeps the original
attribute under `__CC_ARM`, compiles away elsewhere). The edit deliberately keeps the
**line count of `arkrtos_crash.c` unchanged** (the macro definition lives in
`arkrtos_types.h`) — one extra line would shift every `__LINE__`-generated log line
constant and move the image by two bytes; the default-profile image is now
**byte-identical** to before (`objcopy -O binary` then sha256 `fbd1094e…`,
31,462,512 B).

**Boundary written down**: `-fanalyzer` is GCC's own path-sensitive analyser, not a
MISRA / certification tool, and has no external rule set; the 5 TUs and the whole
vendored tree are outside the judgement; it does not prove "no defects", only "this
analyser has nothing to say on these 48 TUs".

With `ARKRTOS_USE_MTX_RECURSIVE` / `ARKRTOS_USE_WAITMULTI` enabled in the board
configuration: **11 matched / 11 passed / 0 failed / 0 skipped, 110 assertions**
(2026-11-14, F427, kernel build Nov 14 2026 23:40). What that round caught on the board
was an **error in the case, not the kernel**: `waitmulti_probe_contract` initially
expected `-2` for the ANY result over "empty semaphore + idle mutex + unset event", while
the board reported `0` — an idle mutex does count as ready (it can be locked). The rule
is now pinned: ANY/ALL expectations are written from "which objects are ready by
definition", not from "which look empty".

Two cases yield the console, by design: `mtx_pi_chain_contract` **must** yield (otherwise
the higher-priority task never gets to run and build the inheritance chain; it sleeps
twice for 5 ms, plus two bounded 500 ms waits) and `sbuf_block_wake_contract`: it sends
data from a 20 ms one-shot timer callback and then blocks with a 400 ms timeout, a
**deliberate exception** to the "cases never block" design rule. The exception's
precondition is a **self-imposed ceiling**: all timeouts are milliseconds and far below
console keep-alive, so even a broken wakeup path at worst fails this case after 400 ms
and returns — it cannot hang the shell. On-board measurement: 40 ticks = 20.0 ms
(wakeup) and 60 ticks = 30.0 ms (timeout).
