# Verification carriers: a QEMU run counts as a board run, but not as silicon

In this repo "we measured it" carries three very different weights, and in prose
they look identical. This page turns the weight into a column that a gate can
check, so that "QEMU counts as a board run" has exactly one reading left.

## 1. Four levels

| Level | Name | Proves | Does not prove |
|---|---|---|---|
| **L1** | Compile surface | This configuration compiles, links, and has exactly the symbols it should (and none it should not) | Anything about behaviour (not one line has run) |
| **L2** | QEMU run | This exact reading came out of a **named** QEMU machine | Silicon timing, TLB/cache semantics, device models, interrupt latency |
| **L3** | Silicon | A serial log from a real board | Another board, another batch, another workload |
| **L0** | No carrier | Nothing (or a **compile-time refusal** - which is a design choice, not a debt) | - |

Two boundaries that get mixed up, stated up front:

- **A compile-time refusal is not an untested path.** `LA32` / `RV64GC`
  seamless hand-off is an `#error` on purpose: L0, but **not** a debt. It
  guarantees "no wrong answer", not "not yet done".
- **L2 is not L3.** Changing the machine (QEMU `virt` RV32 / LA64 / `mps2-an386`)
  changes the carrier, not the level. No L2 reading in this repo is written up
  as "on board".

## 2. The ledger is the single source of truth

Every claim's level, carrier and provenance live in `tools/evidence_levels.tsv`,
one row each. This page only explains; it does not duplicate the data - two
copies of the same fact drift apart sooner or later.

The ledger currently has 20 rows: **L3 = 4 (all STM32F427)**, L2 = 11, L1 = 3,
L0 = 2. In other words: **every reading in this repo that may be called "on
board" comes from one single board.**

`tools/evidence_gate.py` (CI item `evidence-levels`) checks row by row:

1. five fixed columns; `level` is one of L0/L1/L2/L3;
2. **an L2 carrier must be an existing `board/qemu_*` directory** - a typo in the
   machine name turns it red;
3. **an L3 carrier must be an existing real board directory and must not start
   with `qemu_`** - QEMU can never be upgraded to L3;
4. an L2/L3 evidence field must contain a commit that **actually exists in this
   repo's history** (`git cat-file -e`), which keeps "we measured it" from being
   a claim without provenance;
5. L1 evidence must be `gate:<script>` or a commit (the provenance of a compile
   surface is a gate, not a log);
6. an L0 carrier must be `none`;
7. **the L3 row count is frozen** at `L3_FROZEN = 4`. Adding a silicon reading
   means editing that constant too - a silicon reading can only be carried back
   by hand from a serial console, never grown by changing code, so it must be a
   deliberate act.

## 3. Why QEMU cannot become L3: three things this repo has already hit

Not the platitude "emulators are unreliable" - three concrete differences that
have already cost this repo time:

**(1) TLB / ASID semantics.** On the per-space ASID line (U-7), directed
invalidation through `invtlb` measured on QEMU: `op 0/1/2/6` = flush the whole
table and hit `KERNEL refill fatal` immediately, `op 4/5` = no-op, `op 7` =
illegal instruction, `op 3` = by VA and **ignoring ASID**. So `space_release`
has to keep the "switch ASID -> invalidate by VA -> switch back -> re-fill"
route. On silicon the `invtlb` op semantics are defined by the manual and need
not match QEMU; there is also a known QEMU defect (`tlbwr` does not refresh the
**odd page** of a large page - the "switch silently stopped working" incident in
the README). Those readings are L2: they prove the code is self-consistent on
**this emulator**, not on silicon.

**(2) Timing.** Since 2026-11-20 the real-time instrumentation
(`ARKRTOS_USE_RTSTAT`) reports cycle counts on all three tiers, but the readings
come from different sources: ARM uses DWT `CYCCNT` (silicon: `switch` 744 cyc =
7.75 us, `tick.isr` 6.3 us average / 71.6 us max); RV32 reads `mcycle`; LA64
reads a stable counter whose denominator can only be a board constant. Measured
on QEMU: RV32 `cycles per tick: 1554266 (3108533020 Hz [measured], 499 us)`,
`tick.isr N=805 AVG 38us MAX 7714us`; LA64 `cycles per tick: 50000 (cycle clock
100000000 Hz [board constant], tick 500 us)`. Both caveats have to be read
together: the RV32 `[measured]` frequency was measured inside QEMU and depends on
host scheduling, so it is **not** a silicon frequency; LA64's denominator is a
constant, so its numbers are self-consistent relatives. Cross-tier microsecond
figures are therefore neither comparable nor a worst case. QEMU still models no
cache, no pipeline and no bus arbitration, so on non-ARM these tiers prove
**structure and counting discipline** (every tick switches, the interrupt-off
window is bounded, cycles can be reported) but not **worst-case latency**.

**(3) Devices and real events.** The last-words mechanism (`ARKRTOS_HW_SAFE`) on
QEMU used to produce only ledger lines like `devs=0 owners=2 neutralized=0` - the
"bring devices back to a safe state" path was never walked. Since 2026-11-20 the
board stub registers three devices (a will callback and an led neutralise
callback), so the readings are RV32
`hwsafe: enabled, devs=3 owners=3 neutralized=2 (will=1 cb=1 none=0 fail=0 handover=0) last_owner=9`,
LA64 `neutralized=3 (will=1 cb=1 none=1 ...)`, and after the deaths
`[hwsafe] after deaths: ... safe_hits=1 led0=0 led1=0 led2=1`. The path is now
walked at L2, but it proves **the callback was called with the right arguments**,
not that an electrical state was restored: QEMU "devices" are board stubs with no
pins and no register side effects. The silicon F427 reading
`devs=3 owners=6 neutralized=6 last_owner=12` is still the only full-path reading.
Same shape elsewhere: crash-cause counters surviving reset, and real PHY / MDIO /
RMII (lwIP has only ever run over loopback).

## 4. Minimum work to move one row from L2 to L3

| Target | Hardware needed | Serial lines to capture | Decision string | Status |
|---|---|---|---|---|
| Cortex-M7 / H743 | The existing `board/stm32h743` + GCC project; **only needs `ARKRTOS_HW_SAFE` / `ARKRTOS_USE_RTSTAT` switched on and one flash** | `[HWS] devs=... owners=... neutralized=...`, the `switch ... cyc` line of `rt` | `neutralized` and `owners` both non-zero; `rt` prints cycles, not `-1` | L1 (switch defaults off, no reading) |
| Cortex-M3 | A board project (this repo's M3 side is only a Keil `AREA`/`PROC` context switch, no project) | `swap: PASS` | the same rule as the non-ARM targets | L1 |
| RV32IMAC | A real RV32IMAC board | the kernel self-test `swap: v1=7 -> 7 v2=100` | `swap: PASS` | L2 (QEMU `virt`, 5/5) |
| LA64 | LA64 hardware (2K1000 / 3A5000 class), expensive | same | same | L2 (QEMU `virt`, 3/3) |
| LA32 / RV64GC | No carrier on this machine (see the "LoongArch32 execution carrier" row of the debt ledger) | - | - | L0 (compile-time refusal) |

**This page adds no readings of its own.** The last two columns say what the
status *is*, not what is planned.

## 5. Boundaries

1. This page does not claim "a QEMU result also holds on silicon"; it claims
   **which carrier each result came from**, and that attribution is
   machine-checkable.
2. The ledger does not judge whether evidence matches the claim (that takes a
   human reading the log); it keeps **the ledger from fooling itself**.
3. The "a new feature is off by default and changes nothing" discipline is
   untouched: when a new feature enters the ledger, the level is whatever
   carrier its readings actually came from.
