# 发行版与版本策略

一句话：**本仓库的「发布」= 一个 git tag + 一份 `docs/Release-<tag>.md`。**
版本号的三个数字只在 `kernelsrc/include/arkrtos_version.h` 写一次，tag 名与
中英 README 的徽章必须与它一致，不一致由门禁拦下（`ci_gate` 的
`release-consistency`）。

这页存在的理由：`docs/欠账盘点.md` 里「发行版定义（发布物清单 / 变更控制 / LTS）」
长期未做，结果是 readme 写着「版本以 git tag 为唯一记法」，而仓库**一个 tag 都没有**
——那句话当时是空头承诺。现在把规则、发布物清单、ABI 升版判据和一次发版的
完整动作写死在这里，并由门禁盯住可自动检查的部分。

## 1. 版本号规则

| 字段 | 含义 | 什么时候动 |
|---|---|---|
| `MAJOR` | 对外承诺的稳定面 | 只在 1.0 时进位；0.x 期间恒为 0 |
| `MINOR` | 能力与 ABI | 新增能力，或 ABI 面变化（SVC 号增删、镜像头 / 共享分区表结构变、`ARKRTOS_HW_COMPAT_ID` 的兼容代次变） |
| `PATCH` | 修复 | 只做修复：调用方二进制、返回值语义、内存布局都不变 |

**`-preview.N` 只出现在 tag 上，不进 `arkrtos_version.h`。** 三个数字是打包进
`ARKRTOS_VERSION_NUM` 的数值，`ARKRTOS_VERSION_STRING` 由它们推导，带后缀会让
`version` 命令打印的字符串与固件里的数值版本对不上。预览语义由 tag 名与发布说明
承载，不由固件宏承载。

tag 命名：`v<MAJOR>.<MINOR>.<PATCH>[-preview.N]`，例 `v0.0.3-preview.1`。
**一个 tag 只能发一次**：不移动、不删除、不复用（要改就发下一个号）。

## 2. 三处必须一致，第四处必须有

| 位置 | 写什么 | 谁盯 |
|---|---|---|
| `kernelsrc/include/arkrtos_version.h` | `MAJOR` / `MINOR` / `PATCH` 三个数字 | 唯一事实源 |
| git tag | `v<ver>`，全部小写 | 发布动作第 6 步 |
| `readme.md` / `readme_en.md` 徽章 | `badge/release-<ver>-<color>.svg`（shields 里 `-` 写成 `--`） | `release-consistency` |
| `docs/Release-<tag>.md` | 本版发布说明，**必须含「未验证」一节**。正式版 tag 就是 `v<ver>`，文件名即 `Release-<ver>.md`；预览版按 tag 命名，如 `Release-0.0.3-preview.1.md` | `release-consistency` |

门禁怎么跑：

```bash
env -u PYTHONHOME -u PYTHONPATH py -3 tools/release_check.py   # 单独看
env -u PYTHONHOME -u PYTHONPATH py -3 tools/ci_gate.py         # 全套，含 release-consistency
```

它检查六件事：① `version.h` 三个数字能解析；② 中英 README 徽章都含
`release-<MAJOR.MINOR.PATCH>`；③ 两份 README 的「当前版本」段都含 `**<ver>**`；
④ `docs/发行版与版本策略.md` 存在；⑤ 发布说明存在（`docs/Release-<ver>.md` 或
`docs/Release-<ver>-*.md`，命中多个算歧义）且含未验证一节；
⑥ 若仓库已有 tag，**最新的 tag 必须以 `v<ver>` 开头**（防止「改了版本号忘了打标签」，
也防止「打了标签又悄悄改版本号」）。

## 3. 一个 tag 必须带什么（发布物清单）

| 项 | 内容 | 为什么必须有 |
|---|---|---|
| 源码 tag | gitee 上的 tag 对象，指向确切的提交 | 「版本以 tag 为唯一记法」的前提 |
| 构建复现 | 四套工程的构建命令 + 本次实测体积 | 别人拿到 tag 要能判断「和我看到的数是不是同一份」 |
| 体积账本 | 默认档 / 最小档 / 无 Shell 档的 Flash 与 RAM | 选型的第一个数字，且它是可回归的 |
| 发布说明 | `docs/Release-<tag>.md` | 变更、边界、升级注意事项的唯一出口 |
| 未验证项 | 明确列出，不许省略 | 预览版与正式版的唯一区别就在这一节 |
| 兼容声明 | `ARKRTOS_PARTITION_VERSION`、`ARKRTOS_HW_COMPAT_ID`、SVC ABI 是否有变 | 决定旧镜像能不能直接用 |

**二进制产物不入库**（ELF/HEX/BIN 都是构建产物）：发布说明给命令行与读数，
不贴二进制。第三方与 vendored 组件另有 `VENDOR.md` 记源提交，随 tag 一起冻结。

## 4. ABI 与升版判据

三个编号各自管一件事，改任何一个都要按 §1 升 `MINOR`：

| 编号 | 位置 | 当前值 | 管什么 |
|---|---|---|---|
| `ARKRTOS_PARTITION_VERSION` | `kernelsrc/include/arkrtos_share.h` | `10` | 共享分区表结构（App 与内核共读的那块） |
| `ARKRTOS_HW_COMPAT_ID` | `config/arkrtos_partition.h` | `0x42700005`（低 16 位 = 镜像兼容代次 5） | 镜像能不能装进这块板的内核 |
| SVC 服务号 / 子命令号 | `kernelsrc/include/arkrtos_svc_abi.h` | 17 个服务号、约 105 个子命令号 | App ↔ 内核唯一的 ABI 面 |

规则：

- **补丁版不得动这三个编号的数值**，也不得改结构体字段顺序。
- 动了就要在发布说明里写一句「**旧镜像必须重编 / 重装**」，并给出新的兼容代次。
- 已发布的编号不复用（删掉的子命令号留空，见 `SVC服务号与子命令表.md`）。

## 5. 预览版与正式版怎么分

| 档 | 判据 | 现状 |
|---|---|---|
| **预览版**（`-preview.N`） | 能构建、已登记能力在真机上跑通；**存在未验证项且已列出** | 当前档 |
| **正式版**（0.x 内的 release） | 未验证项为 0，或已转成「明确取舍」写进 [已知限制](已知限制.md)；四套构建 + 全量门禁 + 上板回归全绿 | 未达 |
| **1.0** | 下面五条全满足 | 未达 |

1. 至少一块板完成**真实以太网收发**（PHY 驱动 + MDIO + RMII 引脚，抓包证据）；
2. 软总线**物理线两节点**（两块板或板 + PC）完成一次事件 + 一次远程调用；
3. **shell 认证**与 **RDP/WRP 部署通路**（不可逆操作要有产线流程）；
4. **远程 CI**（Gitee Go 或等价）与**静态分析**（cppcheck / MISRA 任一条线）接入；
5. 内核 22 个 GBK 文件完成转码，`.clang-format` / `.editorconfig` 就位。

前三条决定「能不能给别人用」，后两条决定「别人能不能接手改」。

## 6. 发一次版的完整动作

```bash
# 1) 改 version.h 的三个数字
# 2) 写 docs/Release-<tag>.md：变更 / 体积账本 / 复现命令 / 未验证 / 兼容声明
# 3) 更新 readme.md 与 readme_en.md 的徽章和「当前版本」段
env -u PYTHONHOME -u PYTHONPATH py -3 tools/release_check.py     # 单看版本一致性
env -u PYTHONHOME -u PYTHONPATH py -3 tools/ci_gate.py           # 全套门禁
# 4) 四套构建复跑，记体积（F427/F401 Keil、F427/H743 GCC）
git add <具体文件> && git commit && git push origin master
# 5) 打标签并推标签（一次做完，不要只推 master 不推 tag）
git tag -a v<ver> -m "<一句话摘要>"
git push origin v<ver>
```

顺序不能反：**先推 master 再推 tag**，否则 tag 指到的提交在远端还不存在。

## 7. 明确不做的事

- 不移动 / 不删除已发布的 tag。历史是别人引用的对象，改了就变成「同一个版本号两份内容」。
- 不在预览版里静默改 ABI。要改就升 `MINOR`，并在发布说明里说清「旧镜像要重编」。
- 不把「仅编译通过」写成「上板验证过」。三层口径（仅编译 / 上板验证 / 未验证）见
  [readme](../readme.md) §验证状态 与 [已知限制](已知限制.md) 的分档说明。
- 不在发布说明里省略未验证项——预览版的诚实度全在这一节。

## 8. 这页怎么维护

- 版本号规则、发布物清单变了：改这页，并同步改 `tools/release_check.py` 的检查项。
- 每发一版：新增 `docs/Release-<tag>.md`（旧的不改不删），并更新
  [docs/README.md](README.md) 与 readme 的「当前版本」段。
- 正式版条件（§5 那五条）每完成一条：把证据写进对应功能文档，并在
  [欠账盘点](欠账盘点.md) 里把那一行结掉。
