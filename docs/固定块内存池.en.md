# Fixed-block memory pool (`arkrtos_mempool`)

**[简体中文](固定块内存池.md) | English**

> Condensed English edition. The Chinese page (固定块内存池.md) is normative: every number below is
> copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no
> new claim and no new measurement.

In one line: **carve equal-sized blocks out of a memory region you supply; allocate and free are
O(1), never fragment, and need no heap**. Default **on** (`ARKRTOS_USE_MEMPOOL=1`); with it off,
creation fails and allocation returns 0.

- kernel implementation: `kernelsrc/src/arkrtos_mempool.c` (the whole implementation is wrapped in
  `#if (ARKRTOS_USE_MEMPOOL == 1)`; the off profile keeps only call stubs)
- kernel-internal header: `kernelsrc/include/arkrtos_mempool.h`
- public API: `@defgroup mpool` in `kernelsrc/include/arkrtos.h` (`arkrtos_mpool_*`, what Apps use)
- App-side wrapper (through SVC 0x20): `kernelsrc/sdk/app_sdk/arkrtos_oslib.c`
- host regression: `kernelsrc/tests/test_mempool_host.c` + `tools/mempool_host_gate.py`
- on-board self-test: shell `mpool` (9/9 pass on board, through the kernel-side API)

## 1. Why not a heap

| | Heap (variable-size) | Fixed-block pool |
|---|---|---|
| worst-case alloc time | depends on the free-list length | **constant** (pop the head) |
| long running | repeated alloc/free fragments until some call fails | **never fragments**; block size fixed, no coalescing on free |
| capacity | you learn it is insufficient while running | fixed at creation: `block_size × block_count` |
| extra RAM | management structures cost more | **zero**: the first bytes of a free block hold `next` |

The price is "one block is one block": needing 20 bytes with only 32-byte blocks wastes 12 bytes.
That is exactly the kind of trade-off an industrial device can put into its real-time budget.

## 2. How an App uses it

The memory region is supplied by the **caller** — on device usually a static array, position and size
fixed at link time, so there is no irreproducible "allocation failed because memory ran out" failure
at runtime.

```c
#include "arkrtos.h"

/* pool memory: 8 blocks of 32 bytes. Must be RAM visible to this task and pointer-width aligned */
static uint32 g_pool_mem[(32u * 8u) / 4u];
static int32  g_pool;

int main(void)
{
    void *p;

    g_pool = arkrtos_mpool_create("blk", g_pool_mem, 32u, 8u);
    if(g_pool < 0)
    {
        return 1;                  /* duplicate name / bad geometry / table full / region not visible RAM */
    }

    p = arkrtos_mpool_alloc(g_pool);
    if(p != 0)
    {
        arkrtos_mpool_free(g_pool, p);
    }
    return 0;
}
```

> "Whoever creates it owns it": when a task goes offline the kernel reclaims the table entries of the
> pools that task created, so repeatedly installed/uninstalled Apps cannot fill the object table.
> Reclaiming an entry **does not touch the memory region** — that RAM belongs to the caller.

## 3. Interface

App side (`arkrtos.h`, all through SVC 0x20):

| Interface | Meaning |
|---|---|
| `int32 arkrtos_mpool_create(char *name, void *pool, uint32 block_size, uint32 block_count)` | create, returns a `>=0` handle |
| `void *arkrtos_mpool_alloc(int32 handle)` | take one block; **does not block**, returns 0 when empty |
| `int32 arkrtos_mpool_free(int32 handle, void *p)` | return one; a pointer not in this pool or misaligned is refused (pool state untouched) |
| `int32 arkrtos_mpool_query(int32 handle, arkrtos_mpool_stat_t *out)` | read-only snapshot |
| `int32 arkrtos_mpool_delete(int32 handle)` | destroy (frees only the table entry; the memory region is unaffected) |

Kernel side (`arkrtos_mempool.h`): the same names with an `_internal` suffix, plus
`arkrtos_mempool_is_alive()` and `arkrtos_mempool_release_task()`.

Fields of the snapshot `arkrtos_mpool_stat_t` (this order is the SVC fill order):

| Field | Meaning |
|---|---|
| `name` | pool name (max 7 bytes + terminator) |
| `block_size` / `block_count` | geometry |
| `free_count` | currently free blocks |
| `alloc_ok` / `alloc_fail` | cumulative successful / failed allocations ("failed" means the pool was empty) |
| `free_bad` | cumulative refused illegal frees |
| `peak_used` | historical maximum simultaneously used blocks (the basis for sizing) |

## 4. SVC 0x20 subcommands

| Subcommand | Argument block | Returns |
|---|---|---|
| 1 create | `p[1]=name, p[2]=pool, p[3]=block_size, p[4]=block_count` | handle / negative |
| 2 alloc | `p[1]=handle` | block address / 0 |
| 3 free | `p[1]=handle, p[2]=ptr` | 0 / -1 |
| 4 query | `p[1]=handle, p[2]=out` | 0 / -1 |
| 5 delete | `p[1]=handle` | 0 / -1 |

The argument block is a fixed 24 bytes (6 32-bit words); return codes follow the same convention as
the synchronisation primitives (0 success, negative failure).

**Two extra things are done at the boundary, both necessary**:

1. **The pool region must lie entirely inside RAM visible to this task** (SHARE_RAM / SLOT_RAM).
   Without that check an App could make the kernel hand out blocks at any address (including kernel
   RAM) — that is privilege escalation, not allocation.
2. **`block_size × block_count` must not wrap.** `free()` decides "is this pointer inside the pool"
   with that product; after a wrap, a pointer outside the pool computes as inside and the whole free
   list is corrupted.

## 5. Error basis: refuse rather than hand out a pool that looks usable

| Case | Behaviour |
|---|---|
| `block_size < pointer width` / not an integer multiple of pointer width | creation fails (the free list stores `next` inside the block) |
| pool base not pointer-width aligned | creation fails (block address = base + k×block_size; a skewed base skews the whole pool) |
| region size wraps | creation fails |
| empty name / length ≥ 8 / duplicate name | creation fails |
| object table full | creation fails |
| `free()` given an out-of-pool / misaligned / foreign pointer / NULL | refused, `free_bad++`, **pool state not moved by a single byte** |
| pool empty | `alloc` returns 0 (no blocking, no stealing someone else's block) |

The last row deserves a sentence: `free()` never does a best-effort insert. Inserting an
out-of-bounds pointer links the free list into memory outside the pool, and the next `alloc` returns
a wild pointer — in the field that shows up as "crashes occasionally", a hundred times harder to
diagnose than a failed creation.

## 6. Configuration

| Macro | Default | Effect |
|---|---|---|
| `ARKRTOS_USE_MEMPOOL` | 1 | off: the whole implementation leaves the binary, SVC 0x20 always returns -1, `alloc` returns 0 |
| `ARKRTOS_MEMPOOL_NUM` | 4 | number of object table entries (one per pool). The RAM a pool uses comes from the caller and is not counted here |

## 7. Evidence (tiered, never mixed)

**Verified**

- host: `kernelsrc/tests/test_mempool_host.c`, 47 assertions all pass (`MEMPOOL-HOST OK`), covering
  creation guards (block too small / block misaligned / pool base misaligned / region size wraps /
  empty name / duplicate name / zero block count), issuing and exhausting 16 blocks, **"a refused free
  must not move pool state"**, the statistics fields, handle invalidation after delete, and reclaim by
  creator task (`release_task(5)` takes only task 5's pools, `release_task(0)` does not touch kernel or
  unowned pools). Folded into `ci_gate` (`mempool-host`).
- real link (arm-none-eabi-gcc 12.3.1, default profile, `ARKRTOS_USE_MEMPOOL=1`): H743 FLASH
  445996 → **446532 B (+536 B)**, RAM unchanged; F427 FLASH 257324 → **257728 B (+404 B, 98.32%,
  4416 B left)**, still links.

**On board (STM32F427, 2026-11-13)**

- kernel-side shell self-test `mpool test`: `checks 9, failed 0 -- ALL PASS` (create / issue 4 blocks
  / exhaust / `stats free=0 fail=1` / reuse the same block after free / refuse a bad free / refuse a
  duplicate name / refuse a small block / delete). This is the reading **after** the change.
- the unprivileged channel (SVC 0x20) is covered by the example
  [MPOOL_DEMO](../example/stm32f427/app_sdk/MPOOL_DEMO/): built as a `.svcapp`, installed into an App
  slot, the pool region being the App's own static array and every call going through SVC into the
  kernel. **All 33 cases pass**; serial output verbatim:

```
--- mpool demo (SVC 0x20) ---
pool base=20010050 block=32 count=16
create -> 0
query  name=demo block=32 count=16 free=16 peak=0
alloc  a=20010050 b=20010070 c=20010090
query  free=13 alloc_ok=3 peak=3
free(foreign) -> -1
query  free=13 free_bad=1
ptr width=4 byte(s)
create demo2 -> 1
query  free=0 alloc_ok=4 alloc_fail=1
MPOOL: 33 pass, 0 fail
MPOOL: ALL PASS
```

- boundary behaviour confirmed on board: block addresses fall inside the App's own static array, are
  4-byte aligned and distinct; freeing a foreign pointer returns **-1**, `free_count` unchanged and
  `free_bad` +1 only (a refusal does not move pool state); duplicate name / block smaller than the
  pointer width (2 B) / unaligned block (30 B) / zero block count / name too long
  (`>= ARKRTOS_MEMPOOL_NAME_MAX`) / pool region not in the caller's RAM (using `main`'s entry address
  as the sample, since it falls in the ROM window) are **all refused**; after delete `alloc` returns
  null and `query` and `free` return negative, and the name can be reused.
- basis reminder: **the pointer width on ARM is 4**, so "block too small" must use 2, and
  `block_size=4` and `20` are both legal values — the first version of the example had these two
  criteria reversed, and the FAIL on the board was a fault of the criteria, not of the kernel.

**Not verified**

- M3 / M7 target boards: only STM32F427 (Cortex-M4F) has been run.
- "the kernel reclaims a task's pools when the App goes offline" was only tested on the host; there is
  no dedicated on-board scenario (the example deletes its two pools itself before finishing).

## 8. Comparison with other RTOSes

| | FreeRTOS | RT-Thread | Zephyr | this implementation |
|---|---|---|---|---|
| fixed-block pool | `heap_4/heap_5` (variable heap + coalescing) | mem pool (`rt_mp_*`) | `k_mem_slab` | `arkrtos_mempool` |
| storage | inside the heap | static array | static array | **supplied by the caller** (usually a static array) |
| extra RAM | management structures | management header | slab struct | **zero** (`next` lives inside the free block) |
| cross-privilege use | none | yes | yes (syscall) | **SVC 0x20**, both arguments and the memory region validated at the boundary |
