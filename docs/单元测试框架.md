# Ark RTOS 板端单元测试框架（utest）

**[简体中文](单元测试框架.md) | English([单元测试框架.en.md](单元测试框架.en.md))**

## 一句话

内核里那些"用错了才出事"的契约——信号量令牌守恒、FIFO 环形容量、事件位语义、
定时器生命周期、审计结构自洽——都被写成了板子上可以一键重跑的用例；改坏了立刻
变红，而不是等某个应用半夜崩在客户现场。

形态对齐 RT-Thread 的 utest / Zephyr 的 ztest：用例**自动注册**，断言**只记账不中断**，
运行器给出总账。

## 怎么用

在串口控制台（F427 上 USART1 @ 115200 8N1）里：

```
ark> utest list              # 列出已注册的用例
ark> utest run               # 跑全部
ark> utest run fifo_         # 只跑名字里含 "fifo_" 的（子串过滤）
```

命令返回**失败用例数**，所以脚本可以直接靠返回值判红绿：

```
ark> utest run
RUN   sem_token_flow
PASS  sem_token_flow
...
utest: 9 matched, 9 passed, 0 failed, 0 skipped; assertions 73 run / 0 failed
```

## 写一条用例

用例是普通函数，用 `UTEST_CASE(id)` 定义。展开后它是一个静态登记项 + 一个
`__attribute__((constructor))` 构造函数，所以**不需要维护任何中心清单**：
把文件加进工程，用例就自己出现在 `utest list` 里。

```c
#include "arkrtos_utest.h"
#include "arkrtos_sync.h"

UTEST_CASE(sem_token_flow)
{
    int32_t h = arkrtos_sem_create("utsem", 2);
    UTEST_REQUIRE(h >= 0);              /* 失败即 return，后面的断言不再执行 */

    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), 0);
    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), 0);
    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), -1);   /* 令牌用尽 */

    arkrtos_sem_delete(h);
}
```

### 断言宏

| 宏 | 语义 | 失败后 |
|---|---|---|
| `UTEST_CHECK(expr)` | 真值 | 记账，继续 |
| `UTEST_REQUIRE(expr)` | 真值 | 记账并 `return`（前置条件） |
| `UTEST_CHECK_EQ(a, b)` | `a == b` | 记账，继续 |
| `UTEST_CHECK_NE(a, b)` | `a != b` | 记账，继续 |
| `UTEST_CHECK_RANGE(lo, x, hi)` | `lo <= x <= hi` | 记账，继续 |
| `UTEST_FAIL(msg)` | 无条件失败 | 记账，继续 |
| `UTEST_SKIP(reason)` | 主动跳过 | 记账并 `return` |

每条断言先计数（`checks`），再判是否失败（`failed_checks`）；一条用例里失败多少条
都数得清，不会"第一条失败就把后面吞掉"。

### 汇总账（`ark_utest_summary_t`）

| 字段 | 含义 |
|---|---|
| `cases` | 实际执行的用例数 |
| `passed` / `failed` / `skipped` | 全通过 / 有失败 / 主动跳过 的用例数 |
| `checks` / `failed_checks` | 断言总条数 / 失败断言条数 |
| `matched` | 模式匹配到的用例数（含被跳过的） |
| `overflow` | 注册表溢出次数 |

## 开关

`kernelsrc/include/arkrtos_features.h` 里的 `ARKRTOS_USE_UTEST`，**默认 1**；
Kconfig 里也有同名符号（`menuconfig` → Services and components → Reliability and operations），
可改 defconfig 配置。
置 0 时框架与 shell 的 `utest` 命令都不参与编译，体积与行为零变化。

## 设计要点（都是踩过坑才这么写的）

1. **三种工具链都能自动注册。** 自动注册依赖 `__attribute__((constructor))`：
   armclang / GCC 原生支持；ARMCC 5 会把它落到 `.init_array`，
   并在 `__main → __cpp_initialize__aeabi_` 里被调用（已用 armlink 出的镜像
   反汇编核实）。若某个工具链既不认该属性、又不跑 `.init_array`，退化的表现是
   `0 case(s) registered` —— 是一个显式的空账，而不是造假通过。
2. **溢出计数，不静默丢弃。** 用例表容量固定（`ARKRTOS_UTEST_MAX_CASES`，默认 64），
   超出的登记计入 `overflow` 并报出来，绝不无声无息地少跑几条。
3. **框架不依赖 printf / shell。** 输出走可注入的汇（`ark_utest_set_output`），
   板端接到控制台，宿主机接到内存缓冲 —— 同一份核心因此能在 PC 上自测。
4. **用例一律非阻塞。** 用例跑在 shell 任务上下文，凡可能"睡"的调用一律
   `timeout == 0`，避免把控制台挂住。

## 门禁

`tools/ci_gate.py` 里的 `utest-host` 检查：用宿主 gcc 编译并运行
`tools/utest_host_selftest.c`，要求退出码 0 且打印 `HOST-SELFTEST OK`。
它证明的是**框架自身的记账**（通过/失败/跳过/断言条数/溢出/子串过滤/自动注册）
正确，跟板子无关；改了框架、记账歪了，门禁就会红。

### `sbuf` 阻塞路径：可编程桩（2026-11-19）

`sbuf-host` 原先只走非阻塞那一半。2026-11-19 把 `arkrtos_task_block_in_critical()` 换成
**可编程桩**（照 `mq-host` 第 10/11 段的写法）：桩可以按模式返回「立刻交接」「先收走 N 字节
再交接」「交接前把内核节拍推 5000」「对象被删除」「用户态轮询」，也可以在阻塞期间回调
`send_internal` 灌数据。这样「睡下 → 被唤醒 → 收尾判定」整段就能在宿主上驱动出来。
每条路径都走六类收尾：

| 收尾 | 触发 | 期望 |
|---|---|---|
| A 无当前任务 | `g_cur_task = 0` | `PARAM`，一次都不睡 |
| B 睡不下去 | 桩恒返回 `-1`（内核上下文 / 调度器锁定） | `PARAM`，且 `g_block_steps` 等于调用次数 |
| C 超时 | 第一次交接、第二次超时 | `TIMEOUT`，`g_block_steps == 2` |
| D 交接成功 | 交接前腾出空间 / 灌入数据 | 返回实际字节数；流语义的部分成功、FIFO 字节序、mbuf 的 `free` 都对 |
| E 交接后立刻超时 | 交接前推进 5000 拍 | `TIMEOUT`，`g_block_steps == 1` |
| F 等待期间对象被删除 | 桩返回 `ARKRTOS_WAKE_OBJ_DELETED` | `ARKRTOS_SBUF_ERR_DELETED`（-3） |
| G 用户态轮询 | 内核上下文但未声明在 handler 里 | `WOULDBLOCK`（-6），`g_block_steps == 0` |

**等待表卫生用双向断言**：用例先走 G 让等待表真的登记一次，再用 `timeout 0` 的收尾把登记
撤掉，断言 `g_ready_count`（桩里累加 `arkrtos_ready_add` 的调用次数）回到 0；随后重跑一次 G、
直接 `reset_internal`，断言 `g_ready_count == 1` —— 后一条证明前一条不是空转。每条用例末尾
`delete` 之后再断言一次 0，证明没有残留等待者。

**门禁加了标记行校验**：`tools/sbuf_host_gate.py` 原先只看退出码，现在同时要求输出里有
`SBUF-HOST OK` 并回显测试输出——只判退出码挡不住「一条用例都没跑」这类假绿。

**这组用例自身抓出了两个真实缺陷**（修复前用例直接挂死 / 报错，修复后 169 条断言全绿）：

1. **把「没能睡下」当成交接 ⇒ 原地死循环**。四处收尾块的条件只看令牌位
   （`(ret & ARKRTOS_WAKE_HANDOFF) == 0` 才算没拿到），而「没能睡下」返回 `-1`，它的每一位
   都是 1，令牌位判定为真 ⇒ 被当成拿到了 ⇒ 重睡 ⇒ 中断反复开关。`mq` 侧
   `mq_send_after_block()` 有 `if (ret < 0)` 早已规避，`sbuf` 没有。四处统一改为
   `if ((ret < 0) || ((ret & ARKRTOS_WAKE_HANDOFF) == 0))`。
2. **`ARKRTOS_SBUF_ERR_DELETED`（-3）从不可达**。头文件与《流缓冲与消息缓冲》都列了它，
   `delete` 也确实用 `WAKE_OBJ_DELETED` 唤醒等待者，但收尾块把它压成 `PARAM`。四处补上
   `if (ret == ARKRTOS_WAKE_OBJ_DELETED) return ARKRTOS_SBUF_ERR_DELETED;`。

用例对这两条都是**回归门禁**：把 DELETED 分支删掉，同一份用例报
`SBUF-HOST FAILED (4/169)`。

### `sync` 阻塞路径：可编程桩（2026-11-21）

`sync` 的阻塞收尾比 `sbuf` 复杂：一次等待醒来后，`sem_wait_classify` /
`mtx_lock_block_and_claim` / `cond_wait` 的收尾块要按「有没有 `HANDOFF` 位」「`wake_reason` 是不是
`OBJ_DELETED` / `TIMEOUT`」分别判成 `OK` / `TIMEOUT` / `DELETED` / `PARAM`。2026-11-21 把
`arkrtos_task_block_in_critical()` 换成**可编程阻塞桩 + 事件队列**：桩从队列里取一条
「睡下之后发生了什么」，按动作**真去调用被测接口**（不是伪造返回值），队列空时仍返回 `-1`
（等于「睡不下去」），原有非阻塞断言零改动。

| 动作 | 桩里做的事 | 覆盖的收尾 |
|---|---|---|
| `TIMEOUT` | 回来时 `wake_reason = WAKE_TIMEOUT` | `TIMEOUT` + 摘队 |
| `SPURIOUS` | `wake_reason = 0`、无 `HANDOFF` | 幽灵计数 + `TIMEOUT` |
| `BLOCK_REFUSED` | 直接返回 `-1` | `PARAM` + 撤销登记 |
| `SEM_POST` | 真调 `arkrtos_sem_post_internal` | `OK` + 令牌交接 |
| `MTX_UNLOCK` | 临时切成锁持有者真调 `mtx_unlock_internal` | 互斥锁交接 |
| `MTX_UNLOCK_AS_TIMEOUT` / `_AS_GHOST` | 先真交接，再把返回改成无 `HANDOFF` / 有 `HANDOFF` 无原因 | `mtx_lock_block_and_claim` 的两条互斥分支 |
| `COND_SIGNAL` / `COND_BROADCAST` | 真调 `cond_signal/broadcast_internal` | 唤醒后重新持锁 |
| `SEM_DELETE` / `MTX_DELETE` / `COND_DELETE` | 等待中删对象 | `DELETED` + 断链清理 |

断言 85 条 → 290 条，覆盖率 50.39% → 99.22%。除了阻塞链本身，这一批还补了**错误闸门与清盘
分支**：三张表各自填满后的 `NOSLOT`（互斥锁含递归入口）、句柄类型位错误、句柄越界、无当前
任务的 `CONTEXT`、条件变量等待表塞满的 `PARAM`、`wake_all` 跳过已失效任务（不回就绪队列）、
任务下线时持锁无人接手（owner/nest 清零）与「条件变量不随创建者消失」；另有一条直塞等待表
验优先级继承传播到收敛。剩下的 0.78% 是 `arkrtos_appq_set/get` 的空指针/下标越界四个
return——调用点已用 `if (p_tsk != 0)` 挡在前面，宿主不可达，属设计性死分支。

**这一跳不证明实时性**：桩只模拟「睡下之后别人动了一下」那一刻，不模拟时间流逝与任务切换，
所以谁先跑、切换开销、ISR 抢占窗口仍未验证。

### `mq` 阻塞路径：重试循环与一处真实缺陷（2026-11-21）

`mq` 的阻塞桩此前只有“按模式返回一个唤醒原因”，够不到「交接之后空间又被占走」这条
重试路径。2026-11-21 把桩扩成事件模式：第一次返回 `HANDOFF` 但不腾空间，第二次分别返回
超时 / `-1`（没能睡下）、可以在交接时把等待表塞满别的任务、也可以等无限期限
（`timeout < 0` → `remain_ms` 返回 -1）。用例因此覆盖了 send / recv 两条重试循环的每个出口。
断言 108 条 → 184 条，覆盖率 74.67% → 100%。

宿主档给对象表开了 `ARKRTOS_MQ_HOST_TEST`（源里 `#define ARKRTOS_MQ_STATIC`，
默认档仍是 `static`，符号集与镜像不变），于是这些只在清盘时走到的分支也能测：
模块初始化把整张表复位、内核队列不随创建者下线而消失、`release_task` 把死任务从等待表
摘掉（且不回就绪队列）、三张等待表填满时的 `NOSPACE`、两个 ISR 入口与 `delete` / `is_alive`
的句柄闸门、用户态轮询留下的登记被 `timeout 0` 的收尾撤掉。

**这组用例抓出一处真实缺陷**：重试循环写的是
`if((ret & ARKRTOS_WAKE_HANDOFF) == 0)`。`arkrtos_task_block_in_critical()` 返回 `-1`
（睡不下去：内核上下文 / 调度器锁定）时每一位都是 1，令牌位判定为真 ⇒ 被当成「已交接、
空间仍满」⇒ 无限重试。修复前把桩设成「第一次交接、第二次 -1」的用例直接把进程挂死
（只能终止），修复后 184 条断言全绿。修法与 `sbuf` 2026-11-19 那条一致：
`(ret < 0) || ((ret & ARKRTOS_WAKE_HANDOFF) == 0)`，send / recv 两处都改，用例作为回归门禁。

注意：这条修复动的是 ON 路径代码（默认档 `ARKRTOS_USE_MQ=y`），所以本笔**不**声称
LA64 镜像逐字节不变。

### `loader` 安装/搬移/回收：设备、Flash、分区表三面桩（2026-11-21）

`loader-host` 原来只覆盖头部校验与重定位补丁，安装/卸载/搬移这几条主路径完全没跑过
（覆盖率 53.41%）。这一轮分五批补，全部只动用例与桩，**不改 `arkrtos_loader.c` 一个字节**，
所以默认档镜像与板端行为不受影响。

三面桩各管一件事：

| 桩 | 形态 | 让哪些分支可测 |
|---|---|---|
| 设备读端 | `g_dev_rx/_len/_pos/_dry` + 写端只数 ACK/NAK | 流式安装的每一帧、断流、NAK、驱动入口连头都读不回来 |
| Flash | `g_flash_on/fail/erase_fail`、`g_flash_fail_at/from`、`g_flash_corrupt_at/from`，介质是 RAM 里的一块数组 | 擦写失败、表/负载分块写失败、落盘字节被改坏（回读复核） |
| 分区表 / 配置槽 | 真 `arkrtos_ptable_*` + 多槽配置 `g_slot_arr[4]`、`g_pt_move_fail` | 槽选址（类型/点名/装不下）、搬移改指失败、池压实 |

五批用例覆盖的内容：
1. 快照重定位（`reloc_apply` 的整字/MOVW、块尾切断、跨块续算）与 CRC 反算
   （`crc_recheck` 的 MOVW 逆运算、参数/长度/头坏/表项回退各负向）；
2. `load_buffer` 全链（校验 → 写入 → 提交），含固定槽选址的类型跳过、点名、
   点名装不下报 `SIZE`、无槽可装报 `NOSPACE`；
3. 流式安装：头 + 表分帧、负载三帧、ACK 计数、写失败与落盘篡改、断流、驱动入口；
4. 池内搬移：大镜像（表 792 B 跨两帧、负载 1100 B 跨三帧）、表/负载写失败、
   整段复核不过、提交失败、分区表改指失败、旧副本头坏（一个字节都不写）、空记录跳过；
5. 控制台重试与停镜像窗口（`start_manual` 在崩溃禁用档下的拒绝路径）。

断言 284 条 → 367 条（`-DARKRTOS_USE_IMAGE_CRC_RECHECK=1` 档 355 条），覆盖率
53.41% → 98.41%。余下 18 行分两类：**防御分支**（`off % 2` 在表项编码下不可达、
`find_clean` 尺寸为 0、`keep == want`、`r_base > addr`、搬移里的 `new_base == 0` /
越界 / 目标不干净）与**当前宏档不编入**（`ARKRTOS_USE_IMAGE_SIGN=1` 的签名闸门、
`ARKRTOS_MINI_ON_FAULT`）。搬移里的 `submit <= payload_offset + written` 一行要求
MOVW 表项正好落在负载最后 2 字节，而 `check_header` 会先把这种表项判越界，所以也走不到。

**这一跳不证明真实时序**：桩里的擦写是 RAM 上的 `memcpy`，没有扇区耗时、没有
掉电窗口、没有写保护；搬移的事务顺序（先 UNCOMMITTED、复核通过再写 VALID）是
**按源码断言**的，不是掉电实测。

1. **只量被宿主用例链接的那一个 `.c`**，不量测试文件，也不量整仓。内核绝大多数行
   （调度、SVC、驱动、shell）在宿主上根本没有被链接，所以这排数字**不是内核整体覆盖率**。
2. **门槛是"不低于当前值"，不是行业标准**。加代码导致分母变大、覆盖率下降时会红；
   正确的处置是补用例，只有在写明理由时才 `--update` 重钉基线。不许默默调低。
3. **上板路径天然有天花板**。`loader` 剩下的那一截（装载/擦写/启动）缺的正是板子；
   `sync` / `sbuf` / `mq` 靠可编程桩把阻塞的**收尾判定**都走到了，
   但真睡、真 ISR 交接、真节拍推进下的超时仍只有板子能证明——那是设计事实，不是缺陷；
   别把 `100%` 读成"这个模块测好了"。
4. `gcov` 报的行覆盖率把"只声明未执行"的行算进分母，所以大段 `#if` 关档代码会压低
   百分比。基线是在**默认档**（各用例自己带的那组 `-D`）下量的，改宏要一起重钉。

### 软定时器（`arkrtos_timer`，2026-11-21）

`arkrtos_timer.c` 此前也没有宿主用例。它的结构是「对象表 + tick 里倒计时 + 一个专用服务
任务执行回调」，而最贵的一类缺陷在两者的**交接**上：tick 只置 `expired`，回调由服务任务
跑；服务任务被唤醒的条件写错（例如只看任务号不看在不在 `WAIT`），结果要么回调永远不跑，
要么在一个正在运行的任务上硬改状态——两者都不会报错。

### 任务配置与任务表（`arkrtos_cfg`，2026-11-21）

`arkrtos_cfg.c` 此前也没有宿主用例。它是全内核唯一的 TCB 填表入口：应用 `main`、内核内置
服务任务、加载器拉起 App 都走 `arkrtos_task_register()`。这个函数错的方式都不出声：

* **槽位分配的判据写宽了**。它先扫「`INVALID` 且 `recover_pending == 0`」的槽复用，扫不到
  才扩表。少了 `recover_pending` 这一条，一个正等着被 `arkrtos_task_recover_pending`
  复活的任务会被当场覆盖——故障恢复断掉，没有任何报错。
* **参数闸门在槽位分配之后**。所以注册失败时 `count` 已经涨过了。真实行为是「失败槽仍是
  `INVALID`，下一次注册会把它捡回来」，`count` 不泄漏；这条只能靠观察，不能靠读代码猜。
* **表满与参数非法共用一个故障码** `ARKRTOS_FAULT_NOSLOT`，只能靠返回码区分（都是 -1）。
* **栈顶对齐**用 `~0x7UL`。地址已随 LA64 加宽到 `unsigned long`，掩码若写成 `~0x7U`
  就会在高位留下垃圾。
* **栈填充从下标 1 开始**（下标 0 是保护字），到 `words` 为止；从 0 开始会毁保护字，
  多填一格会越界。

| `cfg` | `STACK_USAGE=1`、`STACK_GUARD=0`（默认档） | 92 | `cfg_load` 清计数并重置就绪集；注册成功路径逐字段（`period_ms`→tick、`slice_tick`、优先级双写、NIL 链标记、`is_priv`/`status`、`ram_*`/`rom_*`）；保护字；MPU 构建与栈帧初始化被调用且参数正确；入就绪集的下标；返回「下标+1」；槽位复用三种顺序（可复用槽、`recover_pending` 跳过、跳过占用槽取下一个空槽）；表满 → -1 + `NOSLOT`；三道参数闸门（空 `entry` / 空栈 / 63 字节栈）各自 -1 + `NOSLOT` 且不写栈；64 字节边界通过；失败槽不被永久占用；栈填充（跳过下标 0、非 4 整除时尾部不动）；栈帧初始化（8 字节对齐、`peak_low` 基准、`entry`/`stack_ptr` 透传） |

### 内核符号导出表（`arkrtos_exports`，2026-11-21）

`arkrtos_exports.c` 此前同样没有宿主用例。它是**可下载模块唯一能看到的内核**：模块里的外部
引用由装载器按名字在这张表里解析，解析到的地址就是模块能调用的全部入口。它有两件事会安静
出错：

* **名字匹配写宽了**。改成前缀匹配或忽略大小写，模块写 `arkrtos_mod_print` 就能拿到
  `arkrtos_mod_printf` 的地址，而正常路径（名字拼对）照样跑得通——这种偏差不读源码看不见。
* **模块 printf 的边界**。它是模块唯一的输出通道：`%s` 传空指针、末尾一个孤立的 `%`、
  一行超长输出，都必须有确定的答案，既不能越界，也不能把缓冲区里的旧字节当成输出。

### 内核自检（`arkrtos_audit`，2026-11-22）

`arkrtos_audit.c`（581 行）默认开（`ARKRTOS_USE_AUDIT=1`），是内核**只读**的结构自检：它不修、
不猜原因，只回答「分区表 / 槽位记录 / 任务表里的字段，还满足内核其它部分假定它们满足的不变式吗」，
每组只报「第一个越界的下标」。这类缺陷的特征是**很久以后才炸**（调度器挑了一个不可运行的任务、
池子发出了两段重叠区间），所以一个静默的假「干净」是这一层最坏的结果。

一条开档用例 `audit`（97 条断言）+ 一条关档用例 `audit-off`（6 条）。开档的做法是：先把表建成
干净的，确认一次全绿；再**一次只掰一处**字段，确认恰好那一组亮灯、下标对、其余组不受牵连；
最后掰回去确认它又绿了。覆盖的组与钉住的语义：

| 组 | 掰什么 / 钉什么 |
|---|---|
| `PARTITION` | 魔数 / 版本 / 硬件 id / Flash 与 RAM 几何（长度、2 的幂、是否越出芯片窗口）；下标恒 `INDEX_NONE`——分区表是一整块，编造「第几条」比不报更坏 |
| `LAYOUT` | 布局模式、来源、回收标志、槽位上限这些旋钮的取值域 |
| `SLOTS` / `SLOT_RAM` / `SLOT_FLASH` | 槽记录字段与范围、每槽 RAM 块形状与是否重叠、Flash 区间是否重叠；**两处都坏时下标取先看到的那一条** |
| `TASKS` | 任务表字段与链表下标，以及第一个违规下标 |
| `SCHED` | 就绪位图 / 链与任务表是否对得上（调度自检桩故意报不一致） |
| 入口点 | 7 个位名的字符串映射、`run(NULL)`、`boot()` 干净 / 脏两路：脏时返回失败掩码、记一条 `ARKRTOS_FAULT_AUDITFAIL`、以 `error` 级别打日志且消息里带 `mask 0x` |
| 关档 | `run` 只清零、`last_mask`/`boot` 恒 0、`name` 恒 `"audit disabled"`——**关掉之后不假装检查过**，而不是伪造一张干净证明 |

**同一轮用例抓出 audit 自身两处除零真缺陷，本轮修在源码里**：

* `audit_part_pool()` 里 `pool_size / pool_sector`：`pool_sector == 0` 时直接除零；
* `audit_slots()` 里 `(slot_base - pool_base) % pool_alloc_unit`：`pool_alloc_unit == 0` 时取模除零。

自检的第一职责是「表坏得要命时仍能给出结论」；被它正在审计的坏字段打死，等于什么都没回答。
修法是两处各加一个 `!= 0` 短路守卫、只包住那一次除法/取模，判定语义与位定义一个没改，并各留
注释说明为什么守。这不是为让测试变绿去绕过用例——是把用例抓到的真缺陷修掉。

### MPU 任务窗口（`arkrtos_mpu`，2026-11-22）

`arkrtos_mpu.c`（383 行）是内核**唯一**的 MPU 入口：它不写寄存器，只决定「一个任务允许碰哪几段
地址」，把结果写进 TCB 里的架构无关上下文，由 port 层编码成硬件寄存器。所以用例 stub 掉五个
port 入口（init / reset / set_idle / set_app 只计数，encode 记录 `(idx, base, size, mem)` 并回填），
钉的是**送进硬件上下文的每一段窗口几何与属性**，以及那些「宁可失败关闭、绝不失败打开」的判定。

一条开档用例 `mpu`（71 条断言）+ 一条关档用例 `mpu-off`（2 条）。覆盖的面：

| 面 | 钉住的行为 |
|---|---|
| 内核任务 | `rom_start == 0` ⇒ 代码窗口是内核 Flash；数据窗口是整块芯片 RAM 上取整的 2 的幂；共享内存在这块 RAM 里，所以不再单列 |
| App 精确落点 | 已按自身大小对齐的镜像 ⇒ 代码窗口就是镜像本身，大小为 2 的幂 |
| App 紧贴落点 | 未对齐 / 跨对齐边界的镜像 ⇒ 窗口向低地址扩到最小对齐 2 的幂，并保证覆盖镜像尾；扩到池尾为止 |
| 池边界 | 镜像恰好止于池尾 ⇒ 接受；越过池尾 ⇒ 拒绝并落回内核 Flash，绝不跨过边界向外扩 |
| RAM 窗口 | 池内且形状合法 ⇒ 原样；非 2 的幂 / 未对齐 / 越池尾 / 小于最小块 / 大于最大块 ⇒ **区域留空（失败关闭）**，不退化成整块芯片 RAM |
| 非池 RAM | 根本不是镜像窗口的任务 ⇒ 整块芯片 RAM 兜底 |
| MiniApp | 代码在 RAM ⇒ 区域 0 必须是**可执行 RAM（RAMX）**而不是只读 Flash；数据块独立时保持不可执行；数据窗口与代码窗口重合时也必须保留执行权限 |
| MiniApp 坏块 | 块形状不合法 ⇒ 代码窗口留空，绝不向外扩成邻居可执行 |
| 上下文清理 | 每次 build 先清空整组区域：上一轮的窗口、或 encode 拒绝后的半写状态都不会残留 |
| 入口转发 | `module_init` / `set_idle` / `reset` / `set_app` 各自只转发一次；`set_app(NULL)` 不安装任何东西，`set_app(task)` 传的是该任务自己的 `mpu` |

余下 0 行未覆盖：开档 96 行全部走到，**100.00%**。注意这只证明「窗口算得对、坏形状关得死」，
不证明硬件真的按这些窗口执行——寄存器编码与真 fault 只有板子能证明（port 层的那些函数在宿主上
是桩，本用例一行都不执行它们）。

**这一跳只新增用例，`arkrtos_mpu.c` 一个字节没改。**

### 看门狗门控与心跳契约（`arkrtos_guard`，2026-11-22）

承诺；如果不，该不该让硬件结束这次运行。喂狗与装狗都走 port，所以宿主用例把邻居

### 实时性度量的算术与账目（`arkrtos_rt`，2026-11-22）

`arkrtos_rt.c`（524 行，`ARKRTOS_USE_RTSTAT` 默认关）不碰任何寄存器：所有时间戳都来自
port 的周期计数器，两个唤醒场景都走内核内部原语。所以宿主用例把周期计数器、信号量、
任务登记与延时全部桩掉，钉住的是**算术与账目**，不是实时性。

两条用例：`rt`（`RTSTAT=1` + `ARKRTOS_RT_HOST_TEST`，94 条断言）、`rt-off`（`RTSTAT=0`，
空目标）。覆盖的面：

| 面 | 钉住的行为 |
|---|---|
| 不可用口径 | 计数器起不来、或计数器在走但主频读不到：五个读数行保持 `n = 0`，微秒折算返回 0，不退回节拍计数凑一个差三个数量级的数 |
| 微秒换算 | 按千赫拆成「整秒项 + 余数项」，`100 MHz` / `96 MHz` / `100.123 MHz` 逐位可算；主频低于 1 kHz 时如实返回 0 而不是除零；不出现 64 位除法（RV32 没有 libgcc 那条） |
| 每拍周期数 | `clk × TICK_US / 1e6` 同样按兆赫 + 千赫余数拆开：`100 MHz/500 us → 50000`、`100.123 MHz → 50061`、低于 1 kHz 也抬成 1 而不是 0 |
| 节拍抖动 | 有符号（早到为负、晚到为正）；第一拍没有参照物、不计样本；取小与取大各自只动一侧 |
| tick.isr | 两次采样 200 / 123 周期：min / max 分明，avg 截断成 161，微秒按各自的值折算而不是从平均值折 |
| 唤醒样本 | 从节拍入口起算；超过一拍视为被更高优先级挡了一会儿，计入 `late_n`、不进统计；一个节拍都没见过时跳过而不伪造 |
| 切换样本 | 从节拍体最后一行起算；只有序号配对（同一拍收尾）才算，节拍体内直接切走的样本丢弃并计入 `skip_n` |
| 临界区 | 只记最外层；嵌套的内层不重复计时；不成对的出口既不计样本也不下溢 |
| 抢占场景 | 辅助任务按需创建一次（名字、初值、优先级 1、非周期、256 字静态栈都要对上）；两个信号量各自可失败、任务登记返回 0 与负数分别折算成 `last_error` 4 与 7；样本数不足报 -1 而不是补齐 |
| 辅助任务 | 采样结束后才到的唤醒不计数；睡不下去时回到循环而不是采样；一次唤醒跑两圈时第二圈不重复计数 |
| 快照 | 空缓冲 / 零行 / 短缓冲 / 超长缓冲四种；行序固定；未测量的行整行读 0 |
| 关档 | 空目标、零符号：用例只读开关宏，一个函数都不调（调了会在链接期失败） |

两档按行号并集 **100.00%**。

**这一跳给源码加了一个只在宿主档存在的钩子**：辅助任务体在目标上是 `for(;;)`，宿主上
必须能按预算返回，否则一调用就把门禁挂死。`#if defined(ARKRTOS_RT_HOST_TEST)` 段里
`ARKRTOS_RT_STATIC` 展开成空（函数可见）、加一个 `arkrtos_rt_helper_budget` 与循环里的
三条预算判断；默认档 `ARKRTOS_RT_STATIC` 展开成 `static`，预算符号与那三条判断都
**不编进目标文件**——与 `arkrtos_timer.c` 的服务任务预算同一手法。判定语义一个没改。

**这一跳不证明实时性**：真实节拍与真实调度器下的时序（谁先跑、切换开销）、DWT / mcycle
计数器的真实分辨率、只有上板才有的中断延迟与编译器指令数都不在宿主。用例量的是
「给定这些时间戳，算术与账目对不对」，不是「中断延迟是多少」。

### 安全基线自检（`arkrtos_sec`，2026-11-22）

`arkrtos_sec.c`（575 行，`ARKRTOS_USE_SECCHECK` 默认关）是一张**把已有机制凑到一起再核一遍**
的自检表，它自己不做安全、只回答「这条基线现在到底在不在」。`arkrtos_sec_run()` 依次跑
12 个检查项，返回 FAIL（`ARKRTOS_SEC_STATUS_FAIL`）的条数；每项的结果写回 `arkrtos_sec_report_t`
的槽位。项的顺序固定（枚举值就是槽位下标），关档时整个 TU 编成空目标、零符号。

| # | 检查项 | 判据 |
|---|---|---|
| 0 | `gates.kernel` | 位图契约：bit0 隔离（MPU=1 → iso=1、PAGING=1 → iso=2）、bit1 priv、bit2 stack_check、bit3 fault_recover、bit4 crash_log、bit5 audit、bit6 sign、bit7 hwsafe；`need = 63u`（前六位全要），缺一位 FAIL。向量 `v[0]=mask, v[1]=need, v[2]=iso, v[3]=(mask>>6)&3` |
| 1 | `mpu.slot_windows` | 每个已登记任务槽的窗口都合法（`arkrtos_mpu_task_windows` 成功）；不合法项计数 > 0 即 FAIL |
| 2 | `structures.audit` | 直接调 `arkrtos_audit_run`，它的失败条数原样转成本项读数 |
| 3 | `images.headers` | 槽里每份镜像的魔数先自己核一遍：魔数不对报 `SEC_HDR_ERR_MAGIC = 0x100` 且**不调 loader**（不把坏魔数喂给下行做二次判断）；魔数对才交 `arkrtos_loader_check_header`，读数 = slots/bad/first/err |
| 4 | `images.crc_recheck` | `IMAGE_CRC_RECHECK=1` 时：`rc==0` PASS、`rc==ERR_CRC(-5)` FAIL、其他负值记 unknown；`checked==0` 记 SKIP。**关档固定 SKIP 一句**——「没开这个复核」不等于「复核通过」 |
| 5 | `images.signature` | 签名开关与密钥是否存在；关档 SKIP |
| 6 | `hwsafe.deadman` | 死手（遗言）路径读数：`arkrtos_hwsafe_path_counts` / `dev_count` / `owner_count` 三项之和为 0 记 SKIP |
| 7 | `guard.watchdog` | 看门狗在岗（`WDG_ENABLE=1` 且没有违规心跳）PASS；关档 SKIP |
| 8 | `crash.journal` | 崩溃日志能读（`arkrtos_crash_boots/seq/disabled`）；被显式关掉记 SKIP |
| 9 | `console.auth` | 控制台鉴权开关在岗 |
| 10 | `flash.protection` | 调 port 的 `arkrtos_port_flash_protection`：返回非 0（含默认 weak 实现返回的 `ARKRTOS_SEC_ERR_NO_PORT = -1`）记 SKIP；返回 0 时 `rdp_level != 0` PASS、`rdp_level == 0` 记 FINDING（读出保护没开） |
| 11 | `rt.measured` | 实时性度量是否出过样本（`RTSTAT=1` 且计数非零）；关档 SKIP |

**四档配置**（`tools/coverage_gate.py` 的 `sec*` 四条 CASES，`ci_gate.py` 的 `sec-host` 项逐条复跑）：

| 档 | 关键宏 | marker |
|---|---|---|
| `sec` | `SECCHECK=1`、`IMAGE_CRC_RECHECK=1`、`IMAGE_SIGN=1` + 签名字节、`HW_SAFE=1`、`WDG_ENABLE=1`、`RTSTAT=1`，测试里提供强 Flash 端口 | `SEC-HOST OK  `（94 条断言） |
| `sec-min` | 十二项几乎全关（`MPU/PRIV/STACK_CHECK/FAULT_RECOVER/CRASH_LOG/AUDIT/IMAGE_SIGN/IMAGE_CRC_RECHECK/HW_SAFE/KERNEL_GUARD/WDG/RTSTAT=0`），`SEC_HOST_NO_PORT` 不给强端口，让 weak 兜底 | `SEC-HOST MIN OK  `（65 条） |
| `sec-page` | `ARCH_CORE=0x0302`（LA64）+ `USE_PAGING=1`、`MPU=0`、`PRIV=1`，走 `#elif (PAGING==1)` 的页表隔离分支 | `SEC-HOST PAGE OK  `（83 条） |
| `sec-disabled` | `SECCHECK=0` | `SEC-HOST DISABLED OK`（只读开关宏，一个函数都不调） |

四档按行号并集 **100.00%**（单档最高 99.04%，所以必须四档）。

**几条口径写死**：

1. **SKIP 不是 PASS**。`crc_recheck` 关档、`flash.protection` 没有端口、`hwsafe` 没登记设备、
   `rt` 没样本——这些都记 SKIP，理由写在 `detail` 里。把「没测」算成「通过」是这张表最
   容易出的假绿。
2. **`images.headers` 不冒充 loader**。魔数不对时自检自己报 `0x100` 就返回，不把坏头交给
   `arkrtos_loader_check_header`，避免「loader 恰好也拒了」被读成「自检对了」。
3. **`flash.protection` 走 weak 端口**。默认实现返回 `-1`（没有端口）⇒ SKIP；只有真板子提供
   实现、且能读到 `rdp_level` 时才判 PASS / FINDING。宿主用例提供一个强定义桩来走 PASS/FINDING 分支。
4. **这张表不证明上板安全**。它证明的是「这些开关与账目在给定读数下彼此一致」；RDP 真值、
   真看门狗复位、真 Flash 写保护只有板子能证明。

**宿主上的一个真坑（`-ffunction-sections`）**：`arkrtos_sec.c` 自带
`__attribute__((weak)) arkrtos_port_flash_protection()`。MinGW GCC 4.8 在 `-O0` 下会把这个
weak 函数定义 emit 进**调用者的 COMDAT 组**（接线后符号是 `.weak._arkrtos_port_flash_protection._arkrtos_sec_run`），
而调用点仍是 `U _arkrtos_port_flash_protection` ⇒ 链接结果指向错误入口，运行时直接段错误
（实测落在 `_sec_copy` 内、`0xC0000005`）。最小复现：同一 TU 内 `static` 辅助 + weak 函数 + 调用
⇒ 返回垃圾值；`-O1/-O2/-Os` 都正常，只有 `-O0` 坏。修法不是改生产代码，而是四档都加
`-ffunction-sections`（每个函数独立节，weak 自成一节）。该 flag 就写在 CASES 的 `defs` 里。

### 设备端布局解析（`arkrtos_layout`，2026-11-22）

`arkrtos_layout.c`（864 行）把配置区里一条 512 字节的 `arkrtos_cfg_record_t` 变成运行期布局：
槽表、AUTO/FIXED 模式、回收模式、崩溃重启上限、开机延时、日志级别、raw 镜像许可。它是一块
**纯算术 + 两个 Flash 端口**的模块，宿主上真映射 `[CONFIG_BASE, +CONFIG_SIZE)` 就能把整条
判定链走完。

一条用例 `layout`（200 条断言，`test_layout_host.c`），覆盖这些面：

| 面 | 钉住的契约 |
|---|---|
| 记录校验 | `validate()` 的顺序先头后身：NULL/魔数（`ERR_MAGIC`）→ 版本（`ERR_VERSION`）→ CRC（`ERR_CRC`）→ `hw_compat_id`（`ERR_HW`）→ 模式（`ERR_MODE`）→ `slot_count > SLOT_MAX`（`ERR_SLOT_COUNT_MAX`）；再逐槽查类型 / `flags`·`reserved` 非零（`ERR_RESERVED`）/ 池内范围 / 最小尺寸（表头 + 256）/ 分配粒度对齐 / 与已通过槽重叠；最后**模式与槽表必须一致**——FIXED 至少一个可用槽、AUTO 不许带槽表（`ERR_SLOTS_IN_MODE`），再查运行期纽子范围 |
| UNUSED 与越界槽 | `slot_count` 之外的槽与 `type == UNUSED` 的槽都跳过；`slot_count` 比实际用到的多不算错，少则越界项直接被忽略 |
| 扫描取最新 | 记录顺序追加：遇空位即停；魔数对但整条不过的记录跳过；多条有效时按 `seq` 取最大，且第二个输出参数回填它的下标 |
| 采纳与发布 | `init()` 无有效记录 → 编译期默认布局 + `source=default`；有 → `adopt()` 逐字段搬进运行期变量、`reason=0`；`publish()` 把只读快照交出去（`mode`/`source`/`slot_count`/`slots`/`slot(i)`/`slot_by_base`） |
| 原因码 | 被拒记录的 `ERR_x` 必须能被 `reason()` 读到、并能被 `reason_text()` 逐条翻成人话；读不到就是「串口永远报 0」的假绿 |
| 写入 | 只接受整条 512 字节且魔数 + CRC 自洽的输入；找第一个空位、记住现有最大 `seq`；**序号与硬件签名由内核盖章**（工具只给策略与槽表）；写完回读逐字节比对（`ERR_VERIFY`）；成功后 `adopt` + `publish` + `apply_runtime`，本机不用重启就生效；`p_erased` 如实报本次是否擦了整区 |
| 区满 | 没有空位时整区擦一次再从 0 号写（配置区唯一会丢内容的窗口，掉在这里回退编译期布局、不变砖），序号从 1 重新起算 |
| 擦除 | `erase()` 擦整区并清源码侧状态；区长为 0（没配记录数）时明确报 `NOREGION` 而不是假装成功 |
| 失败面 | 参数非法、区为 0、魔数/CRC 不过、擦失败、写失败、回读不符各自返回不同的负码，一个都不许并成「失败」 |

**本笔顺带修掉两处真缺陷**（用例抓出来的，同笔提交）：

1. **原因码永远为 0**。`scan()` 会先 `validate()` 再跳过坏记录，于是 `init()` 里那条
   `else { reason = rc; }` 永远不可达——现场只看到「回退默认布局」，串口显示 `reason=0`
   （= 一切正常），根本不知道是哪条记录、因为什么被拒。修法是扫描时把最后一条被拒记录
   的 `ERR_x` 记进 `arkrtos_layout_scan_reason`，`init()` 无有效记录时把它接到 `reason` 上。
2. **写进去的布局不生效**。`write()` 原来只 `publish()` 不 `apply_runtime()`，日志级别这类
   运行期纽子要重启才变，与「本机不用重启就能看到新布局」自相矛盾。补一行 `apply_runtime()`。

**余下 8 行未覆盖，逐条登记**（不为凑数去改 `config/arkrtos_partition.h` 的默认槽表——那是

### 跨复位崩溃日志（`arkrtos_crash`，2026-11-22）

两档：`crash`（真账本，141 条断言）与 `crash-off`（`USE_CRASH_LOG=0`，每个入口编成常量，29 条

| 面 | 钉住的契约 |

**本笔抓出并修掉一处真缺陷**（默认 ON 路径的行为变化，本笔不声称镜像逐字节不变）：

`scan_rebind()` 的「这个地址没人认领」分支对**本来就空的条目**也 `clear_entry()` 并置

### 板上直跑（`arkrtos_apprun`，2026-11-22）

`arkrtos_apprun.c`（473 行）是「编译 → 执行」链路上的最后一环：把 arkc 的 `cc -o` 写出来的
**裸文件**装进一个固定窗口，从镜像自带向量表的 `Reset_Handler` 起一个非特权任务。它不做任何
重定位——程序是按窗口地址链出来的，所以整条路径的判断都是「不完全是这个形状就拒绝，而且要说清
楚是哪种不完全是」。

`[SLOT_RAM_BASE, +SLOT_RAM_TOTAL)`（Windows `VirtualAlloc` / POSIX `mmap(MAP_FIXED)`），
映射失败直接 `return 1`，绝不跳过。窗口常量只在 `config/stm32h743/arkrtos_partition.h` 里，
宿主按同一组数值从命令行注入（`-DARKRTOS_APPRUN_*`），`test_geometry()` 再断言它们与映射区间
同形状：两块都落在池里、各自是 2 的幂、相邻、栈与镜像上限都装得下。

单档 **109 条断言**，`100.00%`（OFF 是空目标，零符号，覆盖率只由开档供给）。
自旋锁走 fallback 档（`-DARKRTOS_USE_SPINLOCK=0`），所以端口只要临界区、屏障、核号三个桩。

| 面 | 钉住的契约 |
|---|---|
| 并发 | 单实例闸门**先占位再干活**：装载中（`0xFFFFFFFF`）进来的第二个请求拿 BUSY，不借窗、不开文件；`task_id()` 把占位读成 0（装载中不算在跑）；任何失败路径都放掉闸门 |
| 借窗 | 向 SLOT_RAM 池借**指定的**两块（代码 8 KB / 数据 8 KB）；拿到的基址与大小必须逐字段等于窗口常量，首适配给了别处就**当场归还**并报 `WINDOW`——换地址跑等于让它跳进虚空 |
| 读文件 | 整份读进代码窗口，上限就是窗口大小；读失败、开失败都还窗；**刚好读满还要再 probe 一次**，多一个字节报 SIZE（不截断——截断会把一条跳转切成半条）；probe 自身读失败报 FS，不并成「太大」 |
| 认向量表 | +0 是初始 SP，必须**正好**等于数据窗口顶（说明这份镜像就是按这个窗口链的）；+4 是入口，去掉 Thumb 位后必须落在代码窗口内**且还装得下一条 16 位指令**；入口首半字必须是 arkc 的函数序言。三者任一不对就拒：跑一份为别的布局链出来的镜像等于执行任意字节 |
| 起任务 | 入口 = 向量表 +4；栈取数据窗口末尾 4 KB；`is_priv=0`；TCB 的 `rom_*`/`ram_*` 填成两块窗口并交给 MPU；池记录补上入口与任务号（`APP_SLOT_RUNNING`）；`activate` 只在锁外调一次 |
| 退出 | 钩子只认自己的主任务号：任务 0、别人的任务、没有在跑时一律返回 0 且**不还窗**；自己的任务退出才清状态并还窗；`mini_free` 返 -1（账已经乱了）照样清状态，只是留一条错误日志 |

**本笔修掉一处编译告警级缺陷**：`on_task_exit()` 里有一个从未使用的 `int32 ret`，只在把它接进
`warn-clean` 时才会暴露（此前这条 TU 不在那一批里）。删掉，行为零变化。

**这一跳不证明板端**：窗口是不是真的可执行 RAM、MPU 的 RAMX/RW 属性是否被硬件接受、裸文件在
真芯片上是否真的跑得起来，都只有板子能证明；用例量的是「给定字节与一组窗口常量，借窗/校验/
起任务的判定与账目对不对」。

### 产物落 Flash（`arkrtos_flashapp`，2026-11-22）

### 四遍差分打包（`arkrtos_apppack`，2026-11-22）

`arkrtos_apppack.c` 是 `cc --pack` 的产物侧：拿同一条负载在三份不同基址下的四个字节流（A 标称 /
B ROM+δ / C RAM+δ / D 由 A 按 δ 链出来的期望），反推「哪些字节是绝对地址、属于哪一类」，
再产出一份带重定位表与 CRC 头的镜像。它判错的后果不是编译错误，而是**装上去跑起来才在
无关地址上崩**，所以用例钉的不是"返回 0"，而是账目：

| 用例 | 断言 | 钉住的契约 |
|---|---|---|
| `apppack` | 90 | 四类表项各就各位（计数 2/2/1/1、偏移与类型位逐条相等）、负载还原成 A 后 CRC 覆盖「头 + 表 + 负载」、头逐字段、`check_header` 认账；每条参数闸门与四个拒绝出口（DIFF / ENTRY / VERIFY / SIZE） |

两个刻意的设计：

1. **链接真 `arkrtos_loader.c`，不抄一份校验规则**。产出的镜像必须由装载器自己的
   `arkrtos_loader_check_header()` 判过，这样"打包器 → 装载器"的兼容性有证据；抄规则等于
   造第二个事实源，两边一起错时用例照样绿。代价是给 loader 写一组宿主桩（本文件里全是
   返回 0/-1 的空实现），收益是这条断言不可伪造。`coverage_gate` 为此加了一个可选的
   `link` 字段：只编进来参与链接、不统计它的覆盖率（loader 有自己的 case）。
2. **四类表项必须都不为零**。某一类恒 0 时"镜像能过"这件事毫无意义——那说明这一类根本
   没被验证，所以场景里每一类都单独占一个位置，并且断言 `stats` 的四类计数。

**同一笔删掉打包器里一段重复实现**：`apppack_scan_movw_diff()` 里那段「再读一次立即数对、
判 db/dc」的代码，前置条件与第 0 步 `apppack_scan_movw_first()` 完全相同（同一个 `pos`、同样
要求三份都读得成 MOVW+MOVT），而第 0 步先跑且已经会消费掉 `db==δ && dc==0` 的形态，所以它的
两条合法出口（`return 1`）**在结构上永远走不到**，只剩一条 DIFF。留着它会让后来者以为这里还有
一条"能接受"的路径；已删除，扫描器在原处直接判 DIFF。删除后新写的两条"深水区"用例
（32 位非 MOVW/MOVT 半字、尾部放不下一对立即数）把剩下的判断边界钉住，九十条断言全部保留。

**余下 6 行逐条登记**：`apppack_read_pair` 的长度守卫（三个调用点都已先判 `pos+8<=len`，
删除重复实现后这里只剩防御）、`apppack_scan_movw_first` 的 `pos % 2` 守卫（扫描步长恒为 2/4/8，
`pos` 永远是偶数）、`apppack_write_table` 的"两遍计数不一致"（同一份输入、同一函数、确定性）、
`apppack_verify_payload` 的两个表项越界守卫（表由本函数自己生成）、以及 `apppack_write_table`
失败的回传点。这六行都不是"没测到"，是当前 API 下不可能命中。

**不证明板端**：真实四遍链接（`cc --pack` 的三份真实产物）、编译器实际吐出的指令流、
装载期按落点打补丁、CRC 在 Flash 上的回读复核，都只有板子能证明。

### 内核内安装器（`arkrtos_installer`，2026-11-22）

`arkrtos_installer.c` 是串口与文件两条入口共用的安装器：在字节流里找镜像头、按重定位表把负载落进
槽位、失败时回 NAK 并记一次 `INSTALLFAIL`。它的常驻形态是 `while(1)` 任务，而真正的验收点几乎都是
「流到一半断了会怎样」，所以用例钉的不是"装成功了一次"，而是**有界驱动下每一步的状态、返回值与调用账目**：

| 用例 | 断言 | 钉住的契约 |
|---|---|---|
| `init` | 4 | 清头缓冲、清已收字节、固定槽状态回到 `UNJUDGED` |
| `run_once_*`（param / timeout / commit_autostart / no_autostart / driver） | 34 | 未初始化与非法句柄直接返回 `PARAM`；空流撞上限返回 `TIMEOUT` 且**已收字节不被丢弃**；提交后写自启位并调 `loader_start`、不带自启位就不调；`TYPE_DRIVER` 走驱动注册入口而不是应用入口 |
| `run_once_refuse` | 12 | `check_install` 的三种拒绝（DUP / VERSION / COMPAT）各自原样回传，且**一个字节都不写槽位** |
| `drain_table_timeout` / `drain_quiet_slack` | 14 | 重定位表阶段每个字节等 300 ms、超时按失败收尾；帧尾 2 字节比静默窗口晚到也要被读走，不能提前判完 |
| `load_failure` | 10 | 落槽失败回 NAK `0x15`、只对串口路径排空、记一次 `INSTALLFAIL`，不写自启位 |
| `idle_limit_resumes` | 6 | 空转 20000 次后返回 `TIMEOUT`，此后再喂剩余字节仍能接着拼出一帧（断点续收） |
| `run_once_fixed_*`（no_hint / clear_fail / ok） | 20 | 未配置固定槽返回 `ERR_CONFIG`；清槽失败返回 `ERR_ERASE` 且不继续；配置齐了才 `slot_hint_set` |
| `tick_*`（open_fail / auto_commit / fixed_unusable） | 16 | 设备打不开时不得触碰状态机；AUTO 下固定槽状态从 `UNJUDGED` 走到 `READY`；槽不可用时帧被**静默排空**、不写 NAK |
| `frame_ok_states` | 12 | 只有 `READY` + 槽为空才放行；`DONE` 拒绝第二帧；`UNJUDGED` 一律拒绝 |
| `from_file_*`（gates / short / bad_magic / dev_fail / ok） | 36 | 未挂载 / NULL / stat 失败 / 是目录 / 超长 各自返回 `PARAM` 或 `SIZE`；头短读按 `SIZE` 而不是猜；magic 错按 `MAGIC`；`file_dev` 注册失败按 `PARAM`；正常路径按 17 字节分块读也能量对负载字节数 |
| `file_shim` | 4 | 文件设备垫片的 `drv_open` / `drv_close` 两个入口自身也被走到 |

**两处刻意的设计**：

1. **`while(1)` 不硬测，拆出一轮**。原任务的循环体是 `for(;;){ ...; task_wait(50); }`，宿主上调它
   永不返回。把循环体原样拆成 `arkrtos_installer_tick(int32 *p_dev)`，任务只剩
   `for(;;){ tick(&dev); task_wait_internal(50); }`——**行为等价**，默认构建里 `tick` 仍是 `static`、
   不产生新符号。宿主档靠 `ARKRTOS_INSTALLER_HOST_TEST` 拿到 `tick`、已收字节、头缓冲、固定槽状态与
   文件垫片的读写入口，其余全部走 `init` / `run_once` / `from_file` 真路径。这与 `timer` 的圈数预算、
   `eset` 的对象表导出口径一致：**只导出测试确实无法通过公开 API 触达的面**。
2. **设备、装载器、文件系统全部打桩，断言调用序列与参数**。桩只回答问题，不模拟时序，所以
   `test_idle_limit_resumes` 用「读 120 字节 → 读 30000 次空 → 再读剩余 136 字节」把断点续收钉成账目，
   而不是靠等待真实时间。

**余下 5 行登记**：`arkrtos_installer_task()` 里 `for(;;)` 循环与 `task_wait_internal(50)` 那 5 行——
该函数开中断后永不返回，宿主上调它会把门禁挂死。这是**结构性不可达**，不是"没测到"，也不造一次
假调用来把数字刷绿。

**不证明板端**：真实 Flash 写入与擦除时序、真实串口波特率下的丢字节与流控、重定位后的代码能否执行、
CRC 在 Flash 上的回读复核，都只有板子能证明；用户态安装（SVC）也不在宿主。

### 页表隔离后端（`arkrtos_paging`，2026-11-22）

`arkrtos_paging.c` 是 MMU 侧的隔离后端：给任务做窗口审计、切活动页表空间、发放动态映射，
并且是用户给的地址进入内核代码的**唯一通道**（`arkrtos_paging_user_copy`）。它整体落在
`#if (ARKRTOS_USE_PAGING == 1)` 里，关档是空目标、零符号。板级取 `board/qemu_loongarch64`
那份配置（页表后端在 ARMv7-M 上会被 `arkrtos_config.h` 直接 `#error` 拦掉），但这一层的语义
与具体 port 无关，所以 20 个 port 函数在用例里全是桩。

| 用例 | 钉住的契约 |
|---|---|
| `module_init` | 清空间表、清映射计数，并调一次 `port_paging_init` |
| `build_task` | `rom_start == 0` 时**不动**已有审计面；否则 ROM/RAMX/RAM 按槽位窗口分类；`size == 0` 的段不计 |
| `set_app` | NULL / 特权任务 / 下标越界各自被拒且**不触碰 port**；接受的调用才 `switch_to` |
| `space_forwards` | 六个空间查询入口逐个透传给 port，返回值不被改写 |
| `bind_and_of` | 共享段绑定与反查在空表与命中两种情形下的返回 |
| `release_and_pool` | 释放走 `space_release` 并把该槽清空；帧/对/窗口计数逐个透传 |
| `map_span` | size 0 / 非 4 KB（size、va、pa 三处）/ 超 16 页预算各自返回 -1，且**拒绝不消耗预算**；逐页 `alias`；半路失败原样透出且不递减已计页 |
| `unmap_span` | 逐页 `unalias`；半路失败时已释放的页仍要还账 |
| `user_copy` | 四级次序：-1 参数 / -2 无窗口 / -3 越界（写方向只认 RAM 窗口）/ -4 空间不匹配（**在窗口判定之前**）；成功路径两个方向都真搬字节 |
| `task_helpers` | 当前任务的空间查表、未登记任务返回 0 |

**口径写死**：宿主是 ILP32，`unsigned long` 32 位，回绕类断言只证分支行为、不证宽度
（LA64 是 64 位，宽度差异在板端）。**不证明**：TLB/TCB 的换表行为、真缺页异常、用户态实际
能否越界——那三件事只有 QEMU（算上板，不算真机）与真 LA64 板能证明。

**同一笔的两处零行为改动**：`arkrtos_paging.c` 里 `(volatile uint8 *)user` 与 `(void *)src`
经 `(unsigned long)` 中转，消掉 `-Wcast-qual` 以便这条 TU 进 `warn-clean`。用 LA64 交叉编译器
编同一份源码，改前/改后目标文件 `md5` 都是 `042c3c58787828acaf96f5c7b97718e3`（28832 B）——
**位模式与代码生成零变化**，不是口头声明。

### 控制台登录闸门（`arkrtos_shell_auth`，2026-11-22）

`arkrtos_shell_auth.c` 是 shell 的密码闸门（SEC-G01）：读入的口令与编译期注入的
`salt` + `sha256(salt || password)` 比对，32 字节全量累加、无提前退出；连续错
`ARKRTOS_SHELL_AUTH_TRIES`（默认 5）次锁到底，只有复位能恢复。此前它只有编译侧门禁
（`shell-auth`：开关接线、关档零符号、时序写法、命令注册位），**没有一条用例走过状态机**。

用例 `shellauth`（`test_shell_auth_host.c`，73 条断言）钉：

| 场景 | 钉住的契约 |
|---|---|
| 开机 | `init` 后锁定；`gate(NULL)` 返回 -1 且**不打印**（没有可说的名字） |
| 豁免词 | `login` / `logout` / `help` 在锁定状态返回 0，既不打印也不计错 |
| 锁定下别的词 | 返回 -1，打印「console is locked, type 'login <password>'」 |
| `login` 参数 | `argc != 2` 两个方向都打印 usage 并返回 1，状态不变 |
| 错误口令 | 每次返回 1、计数 +1、打印 `(n/TRIES)`；第 TRIES 次翻成锁到底 |
| 锁到底 | 正确口令也被拒（返回 1）且文案含 `reboot`；门禁改报 `console locked until reset` 并带上错次 |
| 正确口令 | 返回 0、解锁、清计数；此后门禁放行任意名字且不打印；再 `login` 答 `already logged in` |
| `logout` | 已锁 / 锁到底各自只打印；已解锁时锁回去并清计数（下次错口令从 1 开始） |

**盐与摘要是夹具**：盐 `0x00..0x0F`、口令 `s3cret!`、摘要是 `sha256(salt || "s3cret!")`
离线算出来的常量。这样「正确口令解锁」证明的是口令真算到了存下的摘要，而不是模块把
自己算出的值再比一遍。

**余下 1 行**：`auth_streq` 的 `if((a == 0) || (b == 0)) return 0;`——三个调用点传的都是
字符串常量，另有一个入口已先判 `name == 0`，公开 API 触达不到，属结构性不可达。

**不证明**：口令在串口上是明文、镜像泄漏后可离线爆破、真时序恒定性（只能看代码形状）、
以及板端控制台的实际介入。这一层是 ILP32 宿主，结论与指针宽度无关。

### 设备树控制台的消费（`arkrtos_fdt_console`，2026-11-22）

`arkrtos_fdt_console.c` 回答一个具体问题：树里说「控制台是这台设备」，和板级常量说的是不是同一台。
它不是驱动，**不写任何硬件寄存器**——控制台在解析设备树之前就已经起来了（打印本身要用它），
运行期改地址会把「谁在说话」变成随配置变化的量。所以它只做判断：一致回 `OK`，不一致回一个
**指得出是哪条事实不成立**的原因码，绝不「挑一个能用的就好」。

| 原因码 | 树里的哪条事实不成立 |
|---|---|
| `NO_STDOUT` | `/chosen/stdout-path` 不存在（或设备树未初始化） |
| `BAD_PATH` | 值写法不认识（不猜） |
| `NO_NODE` | 路径/别名指向的节点不存在 |
| `DISABLED` | 节点 `status` 不是 okay |
| `COMPAT` | `compatible` 与板级控制台不同 |
| `ADDR` | `reg` 首单元与板级控制台窗口不同 |
| `BAUD` | `stdout-path` 的选项与节点 `current-speed` 冲突 |
| `CLOCK` | `clock-frequency` 缺失（期望确定值时不接受「没写」）或与板级 UART 时钟不同 |

用例 `fdtconsole`（`test_fdt_console_host.c`，65 条断言）钉：九条出口逐个命中；报错时
**已读到的字段仍然填进 `out`**（日志能把「读到了什么」打出来）；`OK` 时 path / compatible /
reg / clock / baud / bits / parity 逐项等于夹具；`stdout-path` 写 115200 而节点 `current-speed`
不同 ⇒ `BAUD`；`expect == 0` 表示只解析不核对（五项都不比）；三个期望字段各自只比自己那一项；
127 字符顶格路径不截断、越界哨兵原封不动；原因码短名稳定、未知码回 `?`。

**同一笔修掉一处真缺陷**：`console_copy` 在目标缓冲装不下时直接 `return -1`，**不写终止符**，
于是 `out->compatible`（32 字节）在超长树字符串下会变成非 C 字符串，后续 `strcmp` 会读进
相邻字段。现在截断时把 `dst[cap-1]` 写成 NUL 再返回 -1——调用方看到的仍是合法前缀。
这是**行为改动**（不是纯加用例），用 LA64 交叉编译器编同一份源码：改前 `.o` 7856 B，改后 7816 B，
差异来自这条终止符存储与随之调整的分支布局。**不证明**：真实 DTB 的解析（`fdt` 用例负责）、板端控制台实际绑到哪个 UART、
以及 DTS 本身写错时的编译期检查。

## 编译器告警门禁（`warn-clean`，2026-11-17）

这台机器上没有 cppcheck / MISRA / clang-tidy，宿主那份 GCC 4.8 也没有 `-fanalyzer`
（GCC 10 才有）；真正能跑路径敏感分析的是本机交叉工具链自带的
`riscv64-unknown-elf-gcc-10.2.0`，那是下面单独一节的 `analyzer` 项。本节的
`warn-clean` 只做一件更小的事：把编译器自己的语义分析开到满。
`tools/warn_gate.py` 用十二条选项编**宿主可编的那 128 个 TU**（63 条用例配置，即测试文件 +
它们链接的模块，再加 SDK stdio；`sign` / `blk` / `dev` / `event` / `export` / `init` / `hwsafe` / `audit` / `mpu` 各按两档编两次，`guard` / `log` / `timer` / `cfg` 各按三档编三次，`rt` 按两档编两次，`sec` 按四档编四次（`sec` / `sec-min` / `sec-page` / `sec-disabled`）；`layout` 单档一次，`crash` 按两档编两次，`apprun` 单档一次，`flashapp` 单档一次，`trace` 按四档编四次，`fdtconsole` 单档一次），要求**零告警**。

| 条目 | 值 |
|---|---|
| 门禁项 | `warn-clean`（`ci_gate.py` 第 54 项） |
| 独立入口 | `python tools/warn_gate.py`（`--selfcheck` 先证明门禁不瞎） |
| 判据 | 每条 TU 编得过且输出里没有 `warning:`；有任何一条就红 |
| 防假绿 | `--selfcheck` 现场造两个 TU：一条必然告警的（未用参数 + 未初始化读）与一条「没有原型的非 static 函数」；前者看不到告警就判门禁瞎了，后者用来证明接口暴露那一档真在命令行上（`-Wall -Wextra` 对它是沉默的） |

**它抓到过真东西**：`arkrtos_sync_release_task()` 里的 `p_tsk` 声明了却从未赋值 ——
三张表的等待队列都在拿野指针比较，效果是死任务永远留在队列里、它持有的锁永远不交出去。
编译通过、上板不报错，只有读代码或看告警能发现。修法与 9 条钉住行为的断言见
[同步原语与令牌守恒](同步原语与令牌守恒.md) 的「任务下线收尸」一节（去掉修复后 7 条断言失败）。

**接口暴露那一档已于 2026-11-18 并入**（`-Wmissing-prototypes` / `-Wstrict-prototypes` /
`-Wold-style-definition`）。并入前在同一批 21 个 TU 上实测 25 条，全部是
`-Wmissing-prototypes`（**内核 5 + 测试桩 20**），分两族：

* **内核 5 条** —— `arkrtos_mq.c` 的 `arkrtos_mq_send_from_isr` / `arkrtos_mq_recv_from_isr`，
  以及 `arkrtos_sync.c` 的 `arkrtos_sem_post_from_isr` 与宿主档那两条内部函数
  `arkrtos_mtx_propagate` / `arkrtos_mtx_recalc_priority`。前三条在伞头 `arkrtos.h` 里一直有
  声明，可**定义它们的 TU 只 include 各自的模块头**，模块头里没有这几条原型 ⇒ 编译器在定义点
  看不见原型；后两条只在 `ARKRTOS_SYNC_HOST_TEST` 档里不是 `static`（宿主用例直接调），
  那个分支里也没有原型。修法是把同签名原型补进模块头（`arkrtos_mq.h` / `arkrtos_sync.h`）
  与宿主档分支，**没有制造新的公共 API**。
* **测试桩 20 条** —— 7 个宿主用例就地替掉内核函数：trace 钩子 12 条
  （`test_sbuf_host` 3、`test_mq_host` 3、`test_sync_host` 4、`test_eset_host` 2）、
  端口开关 2 条（`test_waitmulti_host`）、四个 ready 查询 4 条（同一个文件）、
  `arkrtos_fault_record` 与 `arkrtos_shell_print` 各 1 条。桩定义前没有原型，
  修法是「先声明后定义」，一行注释点明「桩也是接口」。

`-Wstrict-prototypes` 与 `-Wold-style-definition` 并入时**一条都没报**（全仓签名都带原型），
钉住它们是为了防以后退回 K&R 风格。并入后默认档 LA64 镜像 **逐字节不变**
（`9e59d693…`，31,462,512 B，text 367512）；`arkrtos_sync.c` 在 armclang F427 `-O2 -c` 下
Code 9726 / RO 288 / RW 4 / ZI 2248 与改动前完全相同、零告警。

**`-Wconversion` 已开（2026-11-19）**：同一批 21 个 TU 上它共 33 条 —— 6 条窄化 + 27 条
符号。旧文档把 `-Wconversion 33` 与 `-Wsign-conversion 27` 并列是重复计数：GCC 的
`-Wconversion` 本来就隐含 `-Wsign-conversion`，33 条里已经包含那 27 条。口径只有两条：

1. 只加**显式转换**，不改类型、不改比较语义、不改算法。窄化处写 `(uint8)` / `(uint16)`，
   把原本隐式发生的截断写明；句柄掩码比较写 `((uint32)handle & MASK)`（int32→uint32
   是保值转换，位模式逐位相同）。
2. 判据不是「编译过了」，而是**默认档 LA64 镜像逐字节不变**。

33 处分布：`arkrtos_sync.c` 15（含 `cond_handle` / `mtx_handle` 两族）、`arkrtos_mq.c` 7、
`arkrtos_eset.c` 5、`arkrtos_fifo.c` 3（`fifo->size` 与两个下标取模后显式截到 `uint16`）、
`arkrtos_sbuf.c` 2（默认档该 TU 编成空目标，由 armclang 开档那一次覆盖）、
`kernelsrc/tests/test_eset_host.c` 1。修完 `warn_gate.py` 七条选项零告警，
`objcopy -O binary` 的镜像仍是 `9e59d693…` / 31,462,512 B / text 367512，`cmp -l`
**0 处不同**；armclang F427 `-O2 -c` 五个 TU 的 Code/RO/RW/ZI 与改动前逐项相同、零告警。

**`-Wcast-qual` 也一并打开（2026-11-19）**：2026-11-17 记的是 14 条、全在
`kernelsrc/tests/test_eset_host.c`；同日复核为 **0 条** —— 那 14 条已被中间几笔改掉
（丢 `const` 都在测试桩里，随桩声明一起整理）。开档前特意重新数了一遍而不是照旧数字写口径：
照旧数字开档会让门禁先红一次，而「14 条」其实早就不成立。本笔源码零改动，
默认档镜像因此不可能变化（上一笔刚复核过 `9e59d693…`）。

**`-Wwrite-strings` 同日也开了（2026-11-19）**：开档前在同一批 21 个 TU 上
重数得 **20 条**，全部是 `create("literal")` 把字面量传给 `char *` 形参（`test_sbuf_host` 6 /
`test_sync_host` 10 / `test_mq_host` 4）。修法不是改测试，而是把 `sbuf`/`mq`/`sync`/`eset`/
`dev`/`event`/`mpool` 的 `create`/`open` 形参改成 `const char *`：**53 处 `name` 形参**
（公开头 23 / 内核定义 16 / SDK 14）加 **4 处**内部 `copy_name(char *dst, const char *src)`
的 `src`。改前 grep 过 `name = name` 一类赋值，只有 `arkrtos_rt.c` / `arkrtos_sec.c` 两处
保存名字，而它们形参本来就是 `const char *`；其余每一处都是当场拷进定长数组。所以这是
**纯签名放宽**：调用方传 `char *` 照样编过，ABI 与指令都不变（树里本来就有先例 ——
`arkrtos_mempool_create_internal` 一直收 `const char *`）。同时删掉 `test_eset_host.c`
里 14 处已多余的 `(char *)"literal"` 转型。

**这里记一条教训：`-Wcast-qual` 与 `-Wwrite-strings` 是耦合的** —— 单开 `-Wcast-qual` 时
字面量还是 `char[N]`，那 14 条一条都不报；只有 `-Wwrite-strings` 把字面量变成 `const char[]`
之后，同一批转型才立刻报「丢弃限定符」。所以「单开 cast-qual 得 0 条」不能读成「转型已经
被改掉」，两个选项要按同一件事的口径一起看。修完 `warn_gate.py` 对 21 个 TU
零告警、`--selfcheck` 两条探针照旧各报 3 条 / 1 条；默认档 LA64 `objcopy -O binary`
镜像仍 `9e59d693…` / 31,462,512 B / text 367512、`cmp -l` **0 处不同**；armclang F427
`-O2 -c` 九个 TU（含 driver SDK 的 `arkrtos_drv_oslib.c`，带 `-DARKRTOS_DRV_USER_MODE=1`）的 Code/RO/RW/ZI 逐项相同、零告警。`docs/api/Ark RTOS_API参考.md`
由 `gen_api_doc.py --md` 重生成（22 行改动），不手改 —— 手改会与生成器打架，
`api-doc` 门禁的判据就是「重生成后 `git diff` 为空」。

**同日把最后三条也钉上（2026-11-19，共十二条选项）**：`-Wpointer-arith` / `-Wundef` /
`-Wbad-function-cast` 在同一批 TU 上复核各 **0 条**，源码零改动。它们没抓到过东西，
开着是为了钉住防退化 —— 有人往指针算术里塞不该有的假设、写 `#if` 时不带 `defined`、
或把函数返回值强转成另一种类型，门禁立刻红。至此这批 TU 的选项集是十二条、全部零告警；
判据仍是默认档 LA64 镜像逐字节不变（`9e59d693…` / `cmp -l` 0 处），因为这几条只加
编译期检查、不产出代码。**零告警不等于零缺陷**：它只说明这批 TU 在这十二条规则下没露
破口，逻辑问题要靠 `analyzer` 那一档与用例。

**边界写死**：这不是静态分析，别读成"静态分析已完成"。它只跑宿主可编的 92 个 TU
（2026-11-22 由 88 再增至 92：加 `rt` / `rt-off` 两条 case 及其被测模块；再前一跳由 82 增至 88 是加 `guard` / `guard-nowdg` / `guard-off` 三条 case 及其被测模块；

`blk-off` / `dev` / `dev-nosafe` / `event` / `event-multi` 十条 case 及其被测模块，顺带补齐
`test_smp_host.c` 里 7 条 `-Wmissing-prototypes`）；

null-dereference / 资源泄漏 / 未初始化这类「编译通过、上板才炸」的路径缺陷。

| 条目 | 值 |
|---|---|
| 门禁项 | `analyzer`（`ci_gate.py` 第 55 项，紧跟 `warn-clean`） |

`ARKRTOS_ZERO_INIT` 宏（`__CC_ARM` 保留原属性、其余编译掉）。改的时候刻意保持

控制台保活，即使内核唤醒路径坏了，最坏也只是这个用例 FAIL 400 ms 后回来，
不会把 shell 挂死。板上实测 40 拍 = 20.0 ms（唤醒）与 60 拍 = 30.0 ms（超时）。
