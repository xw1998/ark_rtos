# Ark RTOS 板端单元测试框架（utest）

**[简体中文](单元测试框架.md) | English([单元测试框架.en.md](单元测试框架.en.md))**

## 一句话

内核里那些"用错了才出事"的契约——信号量令牌守恒、FIFO 环形容量、事件位语义、
定时器生命周期、审计结构自洽——都被写成了板子上可以一键重跑的用例；改坏了立刻
变红，而不是等某个应用半夜崩在客户现场。

形态对齐 RT-Thread 的 utest / Zephyr 的 ztest：用例**自动注册**，断言**只记账不中断**，
运行器给出总账。

## 怎么用

在串口控制台（F427 上 USART1 @ 115200 8N1）里：

```
ark> utest list              # 列出已注册的用例
ark> utest run               # 跑全部
ark> utest run fifo_         # 只跑名字里含 "fifo_" 的（子串过滤）
```

命令返回**失败用例数**，所以脚本可以直接靠返回值判红绿：

```
ark> utest run
RUN   sem_token_flow
PASS  sem_token_flow
...
utest: 9 matched, 9 passed, 0 failed, 0 skipped; assertions 73 run / 0 failed
```

## 写一条用例

用例是普通函数，用 `UTEST_CASE(id)` 定义。展开后它是一个静态登记项 + 一个
`__attribute__((constructor))` 构造函数，所以**不需要维护任何中心清单**：
把文件加进工程，用例就自己出现在 `utest list` 里。

```c
#include "arkrtos_utest.h"
#include "arkrtos_sync.h"

UTEST_CASE(sem_token_flow)
{
    int32_t h = arkrtos_sem_create("utsem", 2);
    UTEST_REQUIRE(h >= 0);              /* 失败即 return，后面的断言不再执行 */

    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), 0);
    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), 0);
    UTEST_CHECK_EQ(arkrtos_sem_take(h, 0), -1);   /* 令牌用尽 */

    arkrtos_sem_delete(h);
}
```

### 断言宏

| 宏 | 语义 | 失败后 |
|---|---|---|
| `UTEST_CHECK(expr)` | 真值 | 记账，继续 |
| `UTEST_REQUIRE(expr)` | 真值 | 记账并 `return`（前置条件） |
| `UTEST_CHECK_EQ(a, b)` | `a == b` | 记账，继续 |
| `UTEST_CHECK_NE(a, b)` | `a != b` | 记账，继续 |
| `UTEST_CHECK_RANGE(lo, x, hi)` | `lo <= x <= hi` | 记账，继续 |
| `UTEST_FAIL(msg)` | 无条件失败 | 记账，继续 |
| `UTEST_SKIP(reason)` | 主动跳过 | 记账并 `return` |

每条断言先计数（`checks`），再判是否失败（`failed_checks`）；一条用例里失败多少条
都数得清，不会"第一条失败就把后面吞掉"。

### 汇总账（`ark_utest_summary_t`）

| 字段 | 含义 |
|---|---|
| `cases` | 实际执行的用例数 |
| `passed` / `failed` / `skipped` | 全通过 / 有失败 / 主动跳过 的用例数 |
| `checks` / `failed_checks` | 断言总条数 / 失败断言条数 |
| `matched` | 模式匹配到的用例数（含被跳过的） |
| `overflow` | 注册表溢出次数 |

## 开关

`kernelsrc/include/arkrtos_features.h` 里的 `ARKRTOS_USE_UTEST`，**默认 1**；
Kconfig 里也有同名符号（`menuconfig` → Services and components → Reliability and operations），
可改 defconfig 配置。
置 0 时框架与 shell 的 `utest` 命令都不参与编译，体积与行为零变化。

## 设计要点（都是踩过坑才这么写的）

1. **三种工具链都能自动注册。** 自动注册依赖 `__attribute__((constructor))`：
   armclang / GCC 原生支持；ARMCC 5 会把它落到 `.init_array`，
   并在 `__main → __cpp_initialize__aeabi_` 里被调用（已用 armlink 出的镜像
   反汇编核实）。若某个工具链既不认该属性、又不跑 `.init_array`，退化的表现是
   `0 case(s) registered` —— 是一个显式的空账，而不是造假通过。
2. **溢出计数，不静默丢弃。** 用例表容量固定（`ARKRTOS_UTEST_MAX_CASES`，默认 64），
   超出的登记计入 `overflow` 并报出来，绝不无声无息地少跑几条。
3. **框架不依赖 printf / shell。** 输出走可注入的汇（`ark_utest_set_output`），
   板端接到控制台，宿主机接到内存缓冲 —— 同一份核心因此能在 PC 上自测。
4. **用例一律非阻塞。** 用例跑在 shell 任务上下文，凡可能"睡"的调用一律
   `timeout == 0`，避免把控制台挂住。

## 门禁

`tools/ci_gate.py` 里的 `utest-host` 检查：用宿主 gcc 编译并运行
`tools/utest_host_selftest.c`，要求退出码 0 且打印 `HOST-SELFTEST OK`。
它证明的是**框架自身的记账**（通过/失败/跳过/断言条数/溢出/子串过滤/自动注册）
正确，跟板子无关；改了框架、记账歪了，门禁就会红。

### `sbuf` 阻塞路径：可编程桩（2026-11-19）

`sbuf-host` 原先只走非阻塞那一半。2026-11-19 把 `arkrtos_task_block_in_critical()` 换成
**可编程桩**（照 `mq-host` 第 10/11 段的写法）：桩可以按模式返回「立刻交接」「先收走 N 字节
再交接」「交接前把内核节拍推 5000」「对象被删除」「用户态轮询」，也可以在阻塞期间回调
`send_internal` 灌数据。这样「睡下 → 被唤醒 → 收尾判定」整段就能在宿主上驱动出来。
每条路径都走六类收尾：

| 收尾 | 触发 | 期望 |
|---|---|---|
| A 无当前任务 | `g_cur_task = 0` | `PARAM`，一次都不睡 |
| B 睡不下去 | 桩恒返回 `-1`（内核上下文 / 调度器锁定） | `PARAM`，且 `g_block_steps` 等于调用次数 |
| C 超时 | 第一次交接、第二次超时 | `TIMEOUT`，`g_block_steps == 2` |
| D 交接成功 | 交接前腾出空间 / 灌入数据 | 返回实际字节数；流语义的部分成功、FIFO 字节序、mbuf 的 `free` 都对 |
| E 交接后立刻超时 | 交接前推进 5000 拍 | `TIMEOUT`，`g_block_steps == 1` |
| F 等待期间对象被删除 | 桩返回 `ARKRTOS_WAKE_OBJ_DELETED` | `ARKRTOS_SBUF_ERR_DELETED`（-3） |
| G 用户态轮询 | 内核上下文但未声明在 handler 里 | `WOULDBLOCK`（-6），`g_block_steps == 0` |

**等待表卫生用双向断言**：用例先走 G 让等待表真的登记一次，再用 `timeout 0` 的收尾把登记
撤掉，断言 `g_ready_count`（桩里累加 `arkrtos_ready_add` 的调用次数）回到 0；随后重跑一次 G、
直接 `reset_internal`，断言 `g_ready_count == 1` —— 后一条证明前一条不是空转。每条用例末尾
`delete` 之后再断言一次 0，证明没有残留等待者。

**门禁加了标记行校验**：`tools/sbuf_host_gate.py` 原先只看退出码，现在同时要求输出里有
`SBUF-HOST OK` 并回显测试输出——只判退出码挡不住「一条用例都没跑」这类假绿。

**这组用例自身抓出了两个真实缺陷**（修复前用例直接挂死 / 报错，修复后 169 条断言全绿）：

1. **把「没能睡下」当成交接 ⇒ 原地死循环**。四处收尾块的条件只看令牌位
   （`(ret & ARKRTOS_WAKE_HANDOFF) == 0` 才算没拿到），而「没能睡下」返回 `-1`，它的每一位
   都是 1，令牌位判定为真 ⇒ 被当成拿到了 ⇒ 重睡 ⇒ 中断反复开关。`mq` 侧
   `mq_send_after_block()` 有 `if (ret < 0)` 早已规避，`sbuf` 没有。四处统一改为
   `if ((ret < 0) || ((ret & ARKRTOS_WAKE_HANDOFF) == 0))`。
2. **`ARKRTOS_SBUF_ERR_DELETED`（-3）从不可达**。头文件与《流缓冲与消息缓冲》都列了它，
   `delete` 也确实用 `WAKE_OBJ_DELETED` 唤醒等待者，但收尾块把它压成 `PARAM`。四处补上
   `if (ret == ARKRTOS_WAKE_OBJ_DELETED) return ARKRTOS_SBUF_ERR_DELETED;`。

用例对这两条都是**回归门禁**：把 DELETED 分支删掉，同一份用例报
`SBUF-HOST FAILED (4/169)`。

### `sync` 阻塞路径：可编程桩（2026-11-21）

`sync` 的阻塞收尾比 `sbuf` 复杂：一次等待醒来后，`sem_wait_classify` /
`mtx_lock_block_and_claim` / `cond_wait` 的收尾块要按「有没有 `HANDOFF` 位」「`wake_reason` 是不是
`OBJ_DELETED` / `TIMEOUT`」分别判成 `OK` / `TIMEOUT` / `DELETED` / `PARAM`。2026-11-21 把
`arkrtos_task_block_in_critical()` 换成**可编程阻塞桩 + 事件队列**：桩从队列里取一条
「睡下之后发生了什么」，按动作**真去调用被测接口**（不是伪造返回值），队列空时仍返回 `-1`
（等于「睡不下去」），原有非阻塞断言零改动。

| 动作 | 桩里做的事 | 覆盖的收尾 |
|---|---|---|
| `TIMEOUT` | 回来时 `wake_reason = WAKE_TIMEOUT` | `TIMEOUT` + 摘队 |
| `SPURIOUS` | `wake_reason = 0`、无 `HANDOFF` | 幽灵计数 + `TIMEOUT` |
| `BLOCK_REFUSED` | 直接返回 `-1` | `PARAM` + 撤销登记 |
| `SEM_POST` | 真调 `arkrtos_sem_post_internal` | `OK` + 令牌交接 |
| `MTX_UNLOCK` | 临时切成锁持有者真调 `mtx_unlock_internal` | 互斥锁交接 |
| `MTX_UNLOCK_AS_TIMEOUT` / `_AS_GHOST` | 先真交接，再把返回改成无 `HANDOFF` / 有 `HANDOFF` 无原因 | `mtx_lock_block_and_claim` 的两条互斥分支 |
| `COND_SIGNAL` / `COND_BROADCAST` | 真调 `cond_signal/broadcast_internal` | 唤醒后重新持锁 |
| `SEM_DELETE` / `MTX_DELETE` / `COND_DELETE` | 等待中删对象 | `DELETED` + 断链清理 |

断言 85 条 → 290 条，覆盖率 50.39% → 99.22%。除了阻塞链本身，这一批还补了**错误闸门与清盘
分支**：三张表各自填满后的 `NOSLOT`（互斥锁含递归入口）、句柄类型位错误、句柄越界、无当前
任务的 `CONTEXT`、条件变量等待表塞满的 `PARAM`、`wake_all` 跳过已失效任务（不回就绪队列）、
任务下线时持锁无人接手（owner/nest 清零）与「条件变量不随创建者消失」；另有一条直塞等待表
验优先级继承传播到收敛。剩下的 0.78% 是 `arkrtos_appq_set/get` 的空指针/下标越界四个
return——调用点已用 `if (p_tsk != 0)` 挡在前面，宿主不可达，属设计性死分支。

**这一跳不证明实时性**：桩只模拟「睡下之后别人动了一下」那一刻，不模拟时间流逝与任务切换，
所以谁先跑、切换开销、ISR 抢占窗口仍未验证。

### `mq` 阻塞路径：重试循环与一处真实缺陷（2026-11-21）

`mq` 的阻塞桩此前只有“按模式返回一个唤醒原因”，够不到「交接之后空间又被占走」这条
重试路径。2026-11-21 把桩扩成事件模式：第一次返回 `HANDOFF` 但不腾空间，第二次分别返回
超时 / `-1`（没能睡下）、可以在交接时把等待表塞满别的任务、也可以等无限期限
（`timeout < 0` → `remain_ms` 返回 -1）。用例因此覆盖了 send / recv 两条重试循环的每个出口。
断言 108 条 → 184 条，覆盖率 74.67% → 100%。

宿主档给对象表开了 `ARKRTOS_MQ_HOST_TEST`（源里 `#define ARKRTOS_MQ_STATIC`，
默认档仍是 `static`，符号集与镜像不变），于是这些只在清盘时走到的分支也能测：
模块初始化把整张表复位、内核队列不随创建者下线而消失、`release_task` 把死任务从等待表
摘掉（且不回就绪队列）、三张等待表填满时的 `NOSPACE`、两个 ISR 入口与 `delete` / `is_alive`
的句柄闸门、用户态轮询留下的登记被 `timeout 0` 的收尾撤掉。

**这组用例抓出一处真实缺陷**：重试循环写的是
`if((ret & ARKRTOS_WAKE_HANDOFF) == 0)`。`arkrtos_task_block_in_critical()` 返回 `-1`
（睡不下去：内核上下文 / 调度器锁定）时每一位都是 1，令牌位判定为真 ⇒ 被当成「已交接、
空间仍满」⇒ 无限重试。修复前把桩设成「第一次交接、第二次 -1」的用例直接把进程挂死
（只能终止），修复后 184 条断言全绿。修法与 `sbuf` 2026-11-19 那条一致：
`(ret < 0) || ((ret & ARKRTOS_WAKE_HANDOFF) == 0)`，send / recv 两处都改，用例作为回归门禁。

注意：这条修复动的是 ON 路径代码（默认档 `ARKRTOS_USE_MQ=y`），所以本笔**不**声称
LA64 镜像逐字节不变。

### `loader` 安装/搬移/回收：设备、Flash、分区表三面桩（2026-11-21）

`loader-host` 原来只覆盖头部校验与重定位补丁，安装/卸载/搬移这几条主路径完全没跑过
（覆盖率 53.41%）。这一轮分五批补，全部只动用例与桩，**不改 `arkrtos_loader.c` 一个字节**，
所以默认档镜像与板端行为不受影响。

三面桩各管一件事：

| 桩 | 形态 | 让哪些分支可测 |
|---|---|---|
| 设备读端 | `g_dev_rx/_len/_pos/_dry` + 写端只数 ACK/NAK | 流式安装的每一帧、断流、NAK、驱动入口连头都读不回来 |
| Flash | `g_flash_on/fail/erase_fail`、`g_flash_fail_at/from`、`g_flash_corrupt_at/from`，介质是 RAM 里的一块数组 | 擦写失败、表/负载分块写失败、落盘字节被改坏（回读复核） |
| 分区表 / 配置槽 | 真 `arkrtos_ptable_*` + 多槽配置 `g_slot_arr[4]`、`g_pt_move_fail` | 槽选址（类型/点名/装不下）、搬移改指失败、池压实 |

五批用例覆盖的内容：
1. 快照重定位（`reloc_apply` 的整字/MOVW、块尾切断、跨块续算）与 CRC 反算
   （`crc_recheck` 的 MOVW 逆运算、参数/长度/头坏/表项回退各负向）；
2. `load_buffer` 全链（校验 → 写入 → 提交），含固定槽选址的类型跳过、点名、
   点名装不下报 `SIZE`、无槽可装报 `NOSPACE`；
3. 流式安装：头 + 表分帧、负载三帧、ACK 计数、写失败与落盘篡改、断流、驱动入口；
4. 池内搬移：大镜像（表 792 B 跨两帧、负载 1100 B 跨三帧）、表/负载写失败、
   整段复核不过、提交失败、分区表改指失败、旧副本头坏（一个字节都不写）、空记录跳过；
5. 控制台重试与停镜像窗口（`start_manual` 在崩溃禁用档下的拒绝路径）。

断言 284 条 → 367 条（`-DARKRTOS_USE_IMAGE_CRC_RECHECK=1` 档 355 条），覆盖率
53.41% → 98.41%。余下 18 行分两类：**防御分支**（`off % 2` 在表项编码下不可达、
`find_clean` 尺寸为 0、`keep == want`、`r_base > addr`、搬移里的 `new_base == 0` /
越界 / 目标不干净）与**当前宏档不编入**（`ARKRTOS_USE_IMAGE_SIGN=1` 的签名闸门、
`ARKRTOS_MINI_ON_FAULT`）。搬移里的 `submit <= payload_offset + written` 一行要求
MOVW 表项正好落在负载最后 2 字节，而 `check_header` 会先把这种表项判越界，所以也走不到。

**这一跳不证明真实时序**：桩里的擦写是 RAM 上的 `memcpy`，没有扇区耗时、没有
掉电窗口、没有写保护；搬移的事务顺序（先 UNCOMMITTED、复核通过再写 VALID）是
**按源码断言**的，不是掉电实测。

口径写死四条，避免把这排数字读大：

1. **只量被宿主用例链接的那一个 `.c`**，不量测试文件，也不量整仓。内核绝大多数行
   （调度、SVC、驱动、shell）在宿主上根本没有被链接，所以这排数字**不是内核整体覆盖率**。
2. **门槛是"不低于当前值"，不是行业标准**。加代码导致分母变大、覆盖率下降时会红；
   正确的处置是补用例，只有在写明理由时才 `--update` 重钉基线。不许默默调低。
3. **上板路径天然有天花板**。`loader` 剩下的那一截（装载/擦写/启动）缺的正是板子；
   `sync` / `sbuf` / `mq` 靠可编程桩把阻塞的**收尾判定**都走到了，
   但真睡、真 ISR 交接、真节拍推进下的超时仍只有板子能证明——那是设计事实，不是缺陷；
   别把 `100%` 读成"这个模块测好了"。
4. `gcov` 报的行覆盖率把"只声明未执行"的行算进分母，所以大段 `#if` 关档代码会压低
   百分比。基线是在**默认档**（各用例自己带的那组 `-D`）下量的，改宏要一起重钉。

### 软定时器（`arkrtos_timer`，2026-11-21）

`arkrtos_timer.c` 此前也没有宿主用例。它的结构是「对象表 + tick 里倒计时 + 一个专用服务
任务执行回调」，而最贵的一类缺陷在两者的**交接**上：tick 只置 `expired`，回调由服务任务
跑；服务任务被唤醒的条件写错（例如只看任务号不看在不在 `WAIT`），结果要么回调永远不跑，
要么在一个正在运行的任务上硬改状态——两者都不会报错。

| 用例 | 档 | 断言数 | 走到的分支 |
|---|---|---|---|
| `timer` | `USE_TIMER=1`（默认档） | 206 | `module_init` 清表；创建（最低空槽 / 句柄编码 / 名字 7 字符截断 / 表满 / 槽位复用）；`start` 的五道闸门与 `period_ms`→tick 换算（含 32 位乘法溢出成 0 被抬成 1 拍）；tick 倒计时与到期（oneshot 保 `active`、periodic 回填）；`task_id<=0` 不唤醒；服务任务在 `WAIT` 时交接（`READY` + `HANDOFF` + 清超时）而在 `READY` 时不动；`install` 登记的参数；服务任务一圈预算里的全部分支（空闲阻塞、回调快照、oneshot 自动停、periodic 保持、回调内 stop / delete 自己、`cb==0` 跳过、多个到期按槽位顺序）；`stop` 两道闸门；`delete` 闸门与「删未用槽返回 0」 |
| `timer-tickless` | 再加 `USE_TICKLESS=1` | 217 | 同上，另加 `next_ticks()` 的三条分支（无活动定时器 / 最近到期 / 本拍就到期返回 1）与未 arm 的槽不计入 |
| `timer-off` | `USE_TIMER=0` | 8 | 三个空函数不碰任务表、不登记任务；`create` / `start` / `stop` / `delete` 全部返回 -1，不静默成功 |

三档的读数**按行号并集**合并，并集 100.00%；单档各自 100.00%。

**服务任务的 `while(1)` 怎么测**：上板时它是任务主体，永不返回；宿主没有调度器，直接
调用会挂死。做法是加一个宿主档钩子 `ARKRTOS_TIMER_HOST_TEST`：它把服务循环与对象表的
存储类从 `static` 放开、加一个圈数预算 `arkrtos_timer_daemon_budget`，并在循环开头插

之前逐字节相同（唯一差异是符号表里记录的源文件名），这点每次改动都应复核。

**本笔顺带修的接口问题**：关档（`USE_TIMER=0`）时 `arkrtos_timer.h` 原来把函数原型也
一并裁掉，调用方只能得到隐式声明，与 `blk` 头的口径不一致；现在把原型移到功能开关
之外（对象类型与模式宏仍在开关内）。另把三处 `handle & ARKRTOS_HANDLE_MASK` 改成显式
`(uint32)`（与 `dev` / `eset` / `mq` / `sbuf` / `event` 同口径），位模式不变。

**两条只钉读数、未修源码的行为**（登记在 [欠账盘点](欠账盘点.md)）：
1. `arkrtos_timer_create_internal(NULL)` 不判空，`copy_name` 会解引用 —— 用例**不调用**
   它（会直接段错误），只在注释里写明；是否加闸门要先评估调用点。
2. `arkrtos_timer_delete_internal` 只查标志位与下标、不查 `used`，删一个从未用过的槽
   也返回 0（再删一次仍返回 0）。用例把这两条都断言成读数，不声称它是对的。

**这一跳不证明板端**：宿主里节拍是手工调的、服务任务是一个函数调用而不是被调度起来的
任务；真实节拍时序、回调真的跑在任务上下文中、以及 ISR 打断回调和 tick 的窗口，只有
板子与真调度能证明。

### 任务配置与任务表（`arkrtos_cfg`，2026-11-21）

`arkrtos_cfg.c` 此前也没有宿主用例。它是全内核唯一的 TCB 填表入口：应用 `main`、内核内置
服务任务、加载器拉起 App 都走 `arkrtos_task_register()`。这个函数错的方式都不出声：

* **槽位分配的判据写宽了**。它先扫「`INVALID` 且 `recover_pending == 0`」的槽复用，扫不到
  才扩表。少了 `recover_pending` 这一条，一个正等着被 `arkrtos_task_recover_pending`
  复活的任务会被当场覆盖——故障恢复断掉，没有任何报错。
* **参数闸门在槽位分配之后**。所以注册失败时 `count` 已经涨过了。真实行为是「失败槽仍是
  `INVALID`，下一次注册会把它捡回来」，`count` 不泄漏；这条只能靠观察，不能靠读代码猜。
* **表满与参数非法共用一个故障码** `ARKRTOS_FAULT_NOSLOT`，只能靠返回码区分（都是 -1）。
* **栈顶对齐**用 `~0x7UL`。地址已随 LA64 加宽到 `unsigned long`，掩码若写成 `~0x7U`
  就会在高位留下垃圾。
* **栈填充从下标 1 开始**（下标 0 是保护字），到 `words` 为止；从 0 开始会毁保护字，
  多填一格会越界。

### 内核启动顺序（`arkrtos_init`，2026-11-21）

`arkrtos_init.c` 此前也没有宿主用例。它自己不做事，只按固定顺序调用各模块的 init——它的
全部价值就是**顺序**，因为它是唯一的权威启动序列：某个工程的 `main` 一旦自己按别的顺序

* **SMP 要在调度启动前、且排在其它模块之后**。次核晚启动会看到一个不是自己拥有的正在跑的
  调度器。
* **软定时器服务任务**用 `arkrtos_task_register` 注册，必须排在 `arkrtos_cfg_load()` 之后、
  调度启动之前；在本文件的序列里它是设备初始化之后、MPU 之前的那一步。

| `init-on` | 再加 `USE_SBUF=1` / `USE_ESET=1` / `USE_SMP=1` | 30 | event → sync → mq → **sbuf** → **eset** → **smp** → mempool → timer → fault → dev → dev_board → timer_task → mpu → rt |

### 内核自检（`arkrtos_audit`，2026-11-22）

`arkrtos_audit.c`（581 行）默认开（`ARKRTOS_USE_AUDIT=1`），是内核**只读**的结构自检：它不修、
不猜原因，只回答「分区表 / 槽位记录 / 任务表里的字段，还满足内核其它部分假定它们满足的不变式吗」，
每组只报「第一个越界的下标」。这类缺陷的特征是**很久以后才炸**（调度器挑了一个不可运行的任务、
池子发出了两段重叠区间），所以一个静默的假「干净」是这一层最坏的结果。

一条开档用例 `audit`（97 条断言）+ 一条关档用例 `audit-off`（6 条）。开档的做法是：先把表建成
干净的，确认一次全绿；再**一次只掰一处**字段，确认恰好那一组亮灯、下标对、其余组不受牵连；
最后掰回去确认它又绿了。覆盖的组与钉住的语义：

| 组 | 掰什么 / 钉什么 |
|---|---|
| `PARTITION` | 魔数 / 版本 / 硬件 id / Flash 与 RAM 几何（长度、2 的幂、是否越出芯片窗口）；下标恒 `INDEX_NONE`——分区表是一整块，编造「第几条」比不报更坏 |
| `LAYOUT` | 布局模式、来源、回收标志、槽位上限这些旋钮的取值域 |
| `SLOTS` / `SLOT_RAM` / `SLOT_FLASH` | 槽记录字段与范围、每槽 RAM 块形状与是否重叠、Flash 区间是否重叠；**两处都坏时下标取先看到的那一条** |
| `TASKS` | 任务表字段与链表下标，以及第一个违规下标 |
| `SCHED` | 就绪位图 / 链与任务表是否对得上（调度自检桩故意报不一致） |
| 入口点 | 7 个位名的字符串映射、`run(NULL)`、`boot()` 干净 / 脏两路：脏时返回失败掩码、记一条 `ARKRTOS_FAULT_AUDITFAIL`、以 `error` 级别打日志且消息里带 `mask 0x` |
| 关档 | `run` 只清零、`last_mask`/`boot` 恒 0、`name` 恒 `"audit disabled"`——**关掉之后不假装检查过**，而不是伪造一张干净证明 |

修法是两处各加一个 `!= 0` 短路守卫、只包住那一次除法/取模，判定语义与位定义一个没改，并各留

   `arkrtos_loader_check_header`，避免「loader 恰好也拒了」被读成「自检对了」。
3. **`flash.protection` 走 weak 端口**。默认实现返回 `-1`（没有端口）⇒ SKIP；只有真板子提供
   实现、且能读到 `rdp_level` 时才判 PASS / FINDING。宿主用例提供一个强定义桩来走 PASS/FINDING 分支。
4. **这张表不证明上板安全**。它证明的是「这些开关与账目在给定读数下彼此一致」；RDP 真值、
   真看门狗复位、真 Flash 写保护只有板子能证明。

**宿主上的一个真坑（`-ffunction-sections`）**：`arkrtos_sec.c` 自带
`__attribute__((weak)) arkrtos_port_flash_protection()`。MinGW GCC 4.8 在 `-O0` 下会把这个
weak 函数定义 emit 进**调用者的 COMDAT 组**（接线后符号是 `.weak._arkrtos_port_flash_protection._arkrtos_sec_run`），
而调用点仍是 `U _arkrtos_port_flash_protection` ⇒ 链接结果指向错误入口，运行时直接段错误
（实测落在 `_sec_copy` 内、`0xC0000005`）。最小复现：同一 TU 内 `static` 辅助 + weak 函数 + 调用
⇒ 返回垃圾值；`-O1/-O2/-Os` 都正常，只有 `-O0` 坏。修法不是改生产代码，而是四档都加
`-ffunction-sections`（每个函数独立节，weak 自成一节）。该 flag 就写在 CASES 的 `defs` 里。

### 设备端布局解析（`arkrtos_layout`，2026-11-22）

`arkrtos_layout.c`（864 行）把配置区里一条 512 字节的 `arkrtos_cfg_record_t` 变成运行期布局：
槽表、AUTO/FIXED 模式、回收模式、崩溃重启上限、开机延时、日志级别、raw 镜像许可。它是一块
**纯算术 + 两个 Flash 端口**的模块，宿主上真映射 `[CONFIG_BASE, +CONFIG_SIZE)` 就能把整条
判定链走完。

一条用例 `layout`（200 条断言，`test_layout_host.c`），覆盖这些面：

| 面 | 钉住的契约 |
|---|---|
| 记录校验 | `validate()` 的顺序先头后身：NULL/魔数（`ERR_MAGIC`）→ 版本（`ERR_VERSION`）→ CRC（`ERR_CRC`）→ `hw_compat_id`（`ERR_HW`）→ 模式（`ERR_MODE`）→ `slot_count > SLOT_MAX`（`ERR_SLOT_COUNT_MAX`）；再逐槽查类型 / `flags`·`reserved` 非零（`ERR_RESERVED`）/ 池内范围 / 最小尺寸（表头 + 256）/ 分配粒度对齐 / 与已通过槽重叠；最后**模式与槽表必须一致**——FIXED 至少一个可用槽、AUTO 不许带槽表（`ERR_SLOTS_IN_MODE`），再查运行期纽子范围 |
| UNUSED 与越界槽 | `slot_count` 之外的槽与 `type == UNUSED` 的槽都跳过；`slot_count` 比实际用到的多不算错，少则越界项直接被忽略 |
| 扫描取最新 | 记录顺序追加：遇空位即停；魔数对但整条不过的记录跳过；多条有效时按 `seq` 取最大，且第二个输出参数回填它的下标 |
| 采纳与发布 | `init()` 无有效记录 → 编译期默认布局 + `source=default`；有 → `adopt()` 逐字段搬进运行期变量、`reason=0`；`publish()` 把只读快照交出去（`mode`/`source`/`slot_count`/`slots`/`slot(i)`/`slot_by_base`） |
| 原因码 | 被拒记录的 `ERR_x` 必须能被 `reason()` 读到、并能被 `reason_text()` 逐条翻成人话；读不到就是「串口永远报 0」的假绿 |
| 写入 | 只接受整条 512 字节且魔数 + CRC 自洽的输入；找第一个空位、记住现有最大 `seq`；**序号与硬件签名由内核盖章**（工具只给策略与槽表）；写完回读逐字节比对（`ERR_VERIFY`）；成功后 `adopt` + `publish` + `apply_runtime`，本机不用重启就生效；`p_erased` 如实报本次是否擦了整区 |
| 区满 | 没有空位时整区擦一次再从 0 号写（配置区唯一会丢内容的窗口，掉在这里回退编译期布局、不变砖），序号从 1 重新起算 |
| 擦除 | `erase()` 擦整区并清源码侧状态；区长为 0（没配记录数）时明确报 `NOREGION` 而不是假装成功 |
| 失败面 | 参数非法、区为 0、魔数/CRC 不过、擦失败、写失败、回读不符各自返回不同的负码，一个都不许并成「失败」 |

**本笔顺带修掉两处真缺陷**（用例抓出来的，同笔提交）：

1. **原因码永远为 0**。`scan()` 会先 `validate()` 再跳过坏记录，于是 `init()` 里那条
   `else { reason = rc; }` 永远不可达——现场只看到「回退默认布局」，串口显示 `reason=0`
   （= 一切正常），根本不知道是哪条记录、因为什么被拒。修法是扫描时把最后一条被拒记录
   的 `ERR_x` 记进 `arkrtos_layout_scan_reason`，`init()` 无有效记录时把它接到 `reason` 上。
2. **写进去的布局不生效**。`write()` 原来只 `publish()` 不 `apply_runtime()`，日志级别这类
   运行期纽子要重启才变，与「本机不用重启就能看到新布局」自相矛盾。补一行 `apply_runtime()`。

**余下 8 行未覆盖，逐条登记**（不为凑数去改 `config/arkrtos_partition.h` 的默认槽表——那是
板级/产品决策；也不为死参数造调用点）：

| 行 | 分支 | 为什么宿主不可达 |
|---|---|---|
| 80 / 82 | `align_up()` 的对齐进位 | 默认槽表全 0、FIXED 又要求 `ram_base != 0`，分配体在宿主不可达 |
| 177–179 | `pin_ram()` 的分配循环 | 同上：AUTO 模式根本不会调它 |
| 158 | `default_slot()` 的 `switch` `default:` | `i` 恒在 0..7，全落命名档 |
| 581 | `scan()` 里 `if (p_index != 0) *p_index = best_idx;` | 两个调用点都传 0，死参数 |

### 跨复位崩溃日志（`arkrtos_crash`，2026-11-22）

`arkrtos_crash.c`（821 行）记的是「复位之后还得算数」的那半本账：某个槽位连续崩了几次、为什么
崩、是不是已经被停用。它自己就是 `CRASH_LOG_BASE` 上那个 512 字节的全局结构体（靠链接段摆放，
不是绝对地址映射），所以宿主上直接链接就能驱动整条判定链；外部只依赖三样东西——分区表、
`arkrtos_kernel_tick`、临界区端口，用例给前两样做了记录型桩，日志宏用 `-DARKRTOS_LOG_LEVEL=0`
编掉（不为它再拉一个控制台进来）。

两档：`crash`（真账本，141 条断言）与 `crash-off`（`USE_CRASH_LOG=0`，每个入口编成常量，29 条
断言），两档按行号并集 **100.00%**（ON 270 行 + OFF 53 行）。

| 面 | 钉住的契约 |
|---|---|
| 身份是地址不是下标 | 账按**镜像在池内的地址**归档；`scan_apply` 第一遍把「账在旧下标、地址属于新下标」的条目整条搬过去并清源；同一地址不许在同一次扫描里被记两次 |
| 无人认领 | 第二遍清掉「表里已经没有这个地址」的条目（镜像卸载/搬走/表缩小后落在 `slot_max` 之外的尾巴），否则后来落到同一地址的镜像会替别人背锅 |
| 发布与压停用 | 第三遍把计数同步进分区表的 RAM 镜像，并对「上一轮已停用」或「开机就已到上限」的槽位清 autostart、写 `INVALID`、保留 `entry`（`app list` 不能读成「槽位空了」）；原因回落到最后一次故障的 reason，没有就 `FAULT`，`dis_tick` 记 0 表示「本次开机之前」 |
| 停用是粘性的 | 到达上限后后续故障只加计数，不改「停用原因 + 时刻」；`forget` 能清掉，越界/空槽明确不提交 |
| 上限 0 不是无限 | `limit()==0` 走编译期默认；配置永远读不到「不限次」 |
| 小程序 | 路径 FNV-1a 哈希（已知答案外部真值）+ 8 槽台账，`at()` 的六个出参越界也写 0，停用/遗忘与 App 侧同型 |
| OFF 档 | 零记账：不碰分区表、`fault` 恒 0、`count`/`disabled`/`boots`/`seq` 恒 0、区地址与区长为 0、`mini_at` 仍把出参清零；`reason_name(0)` 是 `none`，其余是 `crash journal disabled` |

**本笔抓出并修掉一处真缺陷**（默认 ON 路径的行为变化，本笔不声称镜像逐字节不变）：

`scan_rebind()` 的「这个地址没人认领」分支对**本来就空的条目**也 `clear_entry()` 并置
`*p_changed = 1`。后果是每次开机 `scan_apply` 都报「有变化」、白 commit 一次，序号每次开机
无意义地 +1，让「只在真有变化时落盘」这条注释与调用方的判据一起失效。修法是先判条目非空
（`base` / `crash_cnt` / 两个 reason / `dis_tick` 全零就是空），空的什么都不做。

**一处不是缺陷、改的是用例**：`scan_publish()` 对「已停用」的槽位**每次开机都重新**
`set_slot(INVALID)` 并清 autostart——这是有意的（操作员上一次会话里可能手工 `app start`
过，复位后必须重新压住）。所以用例 7 断言「再扫一次会再写一次」而不是「不写」，
只有「不再 commit」这条保留（publish 只在**新建**停用态时才置 changed）。

**这一跳不证明板端**：`.noinit` 段是否真在复位后保住内容、Flash 里那 512 字节区是否与
`CRASH_LOG_SIZE` 对齐、真掉电落在写半条记录中间时的后果，都只有板子能证明；用例量的是
「给定这本账，重扫/发布/停用的判定与账目对不对」。

### 板上直跑（`arkrtos_apprun`，2026-11-22）

`arkrtos_apprun.c`（473 行）是「编译 → 执行」链路上的最后一环：把 arkc 的 `cc -o` 写出来的
**裸文件**装进一个固定窗口，从镜像自带向量表的 `Reset_Handler` 起一个非特权任务。它不做任何
重定位——程序是按窗口地址链出来的，所以整条路径的判断都是「不完全是这个形状就拒绝，而且要说清
楚是哪种不完全是」。

模块按**绝对地址**读写窗口（`ARKRTOS_APPRUN_BASE` 来自板级分区头），所以 `main()` 先真映射
`[SLOT_RAM_BASE, +SLOT_RAM_TOTAL)`（Windows `VirtualAlloc` / POSIX `mmap(MAP_FIXED)`），
映射失败直接 `return 1`，绝不跳过。窗口常量只在 `config/stm32h743/arkrtos_partition.h` 里，
宿主按同一组数值从命令行注入（`-DARKRTOS_APPRUN_*`），`test_geometry()` 再断言它们与映射区间
同形状：两块都落在池里、各自是 2 的幂、相邻、栈与镜像上限都装得下。

单档 **109 条断言**，`100.00%`（OFF 是空目标，零符号，覆盖率只由开档供给）。
自旋锁走 fallback 档（`-DARKRTOS_USE_SPINLOCK=0`），所以端口只要临界区、屏障、核号三个桩。

| 面 | 钉住的契约 |
|---|---|
| 并发 | 单实例闸门**先占位再干活**：装载中（`0xFFFFFFFF`）进来的第二个请求拿 BUSY，不借窗、不开文件；`task_id()` 把占位读成 0（装载中不算在跑）；任何失败路径都放掉闸门 |
| 借窗 | 向 SLOT_RAM 池借**指定的**两块（代码 8 KB / 数据 8 KB）；拿到的基址与大小必须逐字段等于窗口常量，首适配给了别处就**当场归还**并报 `WINDOW`——换地址跑等于让它跳进虚空 |
| 读文件 | 整份读进代码窗口，上限就是窗口大小；读失败、开失败都还窗；**刚好读满还要再 probe 一次**，多一个字节报 SIZE（不截断——截断会把一条跳转切成半条）；probe 自身读失败报 FS，不并成「太大」 |
| 认向量表 | +0 是初始 SP，必须**正好**等于数据窗口顶（说明这份镜像就是按这个窗口链的）；+4 是入口，去掉 Thumb 位后必须落在代码窗口内**且还装得下一条 16 位指令**；入口首半字必须是 arkc 的函数序言。三者任一不对就拒：跑一份为别的布局链出来的镜像等于执行任意字节 |
| 起任务 | 入口 = 向量表 +4；栈取数据窗口末尾 4 KB；`is_priv=0`；TCB 的 `rom_*`/`ram_*` 填成两块窗口并交给 MPU；池记录补上入口与任务号（`APP_SLOT_RUNNING`）；`activate` 只在锁外调一次 |
| 退出 | 钩子只认自己的主任务号：任务 0、别人的任务、没有在跑时一律返回 0 且**不还窗**；自己的任务退出才清状态并还窗；`mini_free` 返 -1（账已经乱了）照样清状态，只是留一条错误日志 |

**本笔修掉一处编译告警级缺陷**：`on_task_exit()` 里有一个从未使用的 `int32 ret`，只在把它接进
`warn-clean` 时才会暴露（此前这条 TU 不在那一批里）。删掉，行为零变化。

**这一跳不证明板端**：窗口是不是真的可执行 RAM、MPU 的 RAMX/RW 属性是否被硬件接受、裸文件在
真芯片上是否真的跑得起来，都只有板子能证明；用例量的是「给定字节与一组窗口常量，借窗/校验/
起任务的判定与账目对不对」。

### 产物落 Flash（`arkrtos_flashapp`，2026-11-22）

`arkrtos_flashapp.c`（828 行）把 arkc 产物**烧回片内 Flash 应用区**，之后掉电不丢、复位后不必重烧：
内核只做「验元数据与向量表 → 借数据窗口 → 起任务」三件事，代码直接从 Flash 取指。
与 `app run` 共用同一段 RAM 数据窗口，所以两者同一时刻只跑得了一个——这不是额外闸门，是池分配器自己会拒。

宿主上要真映射两段绝对地址：`[ARKRTOS_FLASHAPP_BASE, +SIZE)`（读写都要，当 Flash 用）与
`[SLOT_RAM_BASE, +SLOT_RAM_TOTAL)`（借窗）。任一映射失败直接 `return 1`，绝不跳过。
常量来自 h743 的分区头，按同一组数值从命令行注入，`test_geometry()` 再核形状：
区顶 = `0x08200000`（2 MB Flash 末尾）、元数据占最后一个 32 字节 flash word、镜像上限 = 区大小 − 64、
数据窗口就是 APPRUN 那块。

单档 **175 条断言**，`99.70%`（OFF 是空目标、零符号）。日志不编译掉、改为把级别压到最低——
编译掉会让 `ARKRTOS_LOGI` 的三个参数在 `-Wextra` 下报未使用，这条 TU 也就进不了 `warn-clean`。

| 面 | 钉住的契约 |
|---|---|
| 写：先验后擦 | 空路径 `PARAM`、文件系统没挂 `STATE`、单实例闸门 `BUSY`；随后整份扫一遍算长度/CRC/向量表/入口序言。长度越界、SP 不等于数据窗口顶、入口在区外、入口超出负载、序言不对——五种形状错误都在**擦之前**原地返回，区里那份还能跑的程序分毫未动（用例把「擦除次数 == 0」逐条钉住） |
| 写：擦→写→验 | 擦整个区（地址/长度逐项断言）→ 按 1 KB 分块读+写 → **回读逐字节比**。底层写返回 0 不算数：一个字节被改就是 `VERIFY`；擦失败/写失败 `FLASH`；写入或回读阶段文件打不开/读不到 `FS`。**不回滚**：擦一旦开始，失败就是「区里现在是空的」 |
| 写：元数据 | 区尾 32 字节（魔数/长度/CRC/版本）最后写，写完也要回读。元数据回读不一致 `VERIFY`，且此后 `info()` 判「没有产物」——半截镜像不会看起来能跑 |
| 查 | 五道闸门：魔数、版本、长度 ∈ [8, 上限]、向量表 SP 等于窗口顶、入口非零；任一不对 `META`。`info` 不取锁（只读 32 字节元数据 + 8 字节向量表，任何中间态都自洽） |
| 跑 | claim → info → 入口复核（区内且首半字是 arkc 序言）→ 借窗 → 起任务 → 发布。首适配拿到的四个字段必须**逐项等于** APPRUN 代码窗 + FLASHAPP 数据窗，否则还块报 `WINDOW`；注册失败在本地还窗报 `LOADER_ERR_TASK`；TCB 的 `rom_*` 记 Flash 应用区、`ram_*` 记借到的块、`is_priv=0`；`task_out` 在 `activate` 之前带出去 |
| 退出 | 只认自己的主任务；任务 0 与别人的任务原样返回 0 且不还窗；自己的退出清状态并还窗；`mini_free` 返 -1（账已经乱了）仍清状态、只留一条错误日志 |

**余下 1 行**是 `flashapp_check_shape()` 的长度守卫：`flashapp_scan()` 已经把 `len < 8` 与 `len > 上限` 先拒掉，
这道是同一判定的防御性重复，宿主与板端都不可达——如实留白，不为让数字变绿去造一次假调用。

**这一跳只新增用例，`arkrtos_flashapp.c` 一个字节没改**。**不证明板端**：真 Flash 的读-改-写时序、
bank2 的 read-while-write（擦 bank2 时内核仍在 bank1 取指）、擦除期间掉电的后果，都只有板子能证明；
用例量的是「给定一组字节与窗口常量，写/查/跑的判定与账目对不对」。

|---|---|---|---|
| `trace-swd` | 压缩字节环 | 88 | `mdk_trace_swd_blob.ctrl`（cap / events / lost_events / head−drained） |
| `trace-buff` | 定长记录环 | 85 | 组件 API（capacity / total / lost）+ `flags` 的 WRAPPED 位 |
| `trace-none` | 无后端 | 79 | 恒 0，命令报「no on-chip backend」 |
| `trace-off` | `USE_MDK_TRACE=0` | 17 | 全空实现，命令返回 `ARKRTOS_TRACE_ERR_DISABLED` |

钉住的行为：一次切换 = 恰好一条 sched 事件且只给「切入方」加计数；越界 id 不进计数但事件照报；
关档后点事件 / sched / isr 一条不进、切换计数冻结（既不清零也不再涨）；`init` 清计数并装钩子
（`mdk_trace_arkrtos_init` 恰一次），`reset` 只清计数不动开关；PendSV 往返统计夹在
`isr(14, enter/exit)` 之间、**放在开关闸门之前**，所以 trace 关掉也能量；控制台五个子命令
（start / stop / reset / dump / mark）与逐字符相等的子命令匹配（`startx` 不当成 `start`）。

**一处源码补齐**：`arkrtos_sched_stat_close()` 在仓库里只有调用点就地 `extern` 声明，
单独编这个 TU 会触发 `-Wmissing-prototypes`；已在定义前补一条同签名原型（不改行为、不动签名）。
**这一跳只新增用例，其余源码零改动**；**不证明板端**：真实环编码 / 压缩由组件用例负责，
SWD 主机侧排空时序、DWT 真实周期与中断延迟都只有板子能证明。

### 四遍差分打包（`arkrtos_apppack`，2026-11-22）

`arkrtos_apppack.c` 是 `cc --pack` 的产物侧：拿同一条负载在三份不同基址下的四个字节流（A 标称 /
B ROM+δ / C RAM+δ / D 由 A 按 δ 链出来的期望），反推「哪些字节是绝对地址、属于哪一类」，
再产出一份带重定位表与 CRC 头的镜像。它判错的后果不是编译错误，而是**装上去跑起来才在
无关地址上崩**，所以用例钉的不是"返回 0"，而是账目：

| 用例 | 断言 | 钉住的契约 |
|---|---|---|
| `apppack` | 90 | 四类表项各就各位（计数 2/2/1/1、偏移与类型位逐条相等）、负载还原成 A 后 CRC 覆盖「头 + 表 + 负载」、头逐字段、`check_header` 认账；每条参数闸门与四个拒绝出口（DIFF / ENTRY / VERIFY / SIZE） |

两个刻意的设计：

1. **链接真 `arkrtos_loader.c`，不抄一份校验规则**。产出的镜像必须由装载器自己的
   `arkrtos_loader_check_header()` 判过，这样"打包器 → 装载器"的兼容性有证据；抄规则等于
   造第二个事实源，两边一起错时用例照样绿。代价是给 loader 写一组宿主桩（本文件里全是
   返回 0/-1 的空实现），收益是这条断言不可伪造。`coverage_gate` 为此加了一个可选的
   `link` 字段：只编进来参与链接、不统计它的覆盖率（loader 有自己的 case）。
2. **四类表项必须都不为零**。某一类恒 0 时"镜像能过"这件事毫无意义——那说明这一类根本
   没被验证，所以场景里每一类都单独占一个位置，并且断言 `stats` 的四类计数。

**同一笔删掉打包器里一段重复实现**：`apppack_scan_movw_diff()` 里那段「再读一次立即数对、
判 db/dc」的代码，前置条件与第 0 步 `apppack_scan_movw_first()` 完全相同（同一个 `pos`、同样
要求三份都读得成 MOVW+MOVT），而第 0 步先跑且已经会消费掉 `db==δ && dc==0` 的形态，所以它的
两条合法出口（`return 1`）**在结构上永远走不到**，只剩一条 DIFF。留着它会让后来者以为这里还有
一条"能接受"的路径；已删除，扫描器在原处直接判 DIFF。删除后新写的两条"深水区"用例
（32 位非 MOVW/MOVT 半字、尾部放不下一对立即数）把剩下的判断边界钉住，九十条断言全部保留。

**余下 6 行逐条登记**：`apppack_read_pair` 的长度守卫（三个调用点都已先判 `pos+8<=len`，
删除重复实现后这里只剩防御）、`apppack_scan_movw_first` 的 `pos % 2` 守卫（扫描步长恒为 2/4/8，
`pos` 永远是偶数）、`apppack_write_table` 的"两遍计数不一致"（同一份输入、同一函数、确定性）、
`apppack_verify_payload` 的两个表项越界守卫（表由本函数自己生成）、以及 `apppack_write_table`
失败的回传点。这六行都不是"没测到"，是当前 API 下不可能命中。

**不证明板端**：真实四遍链接（`cc --pack` 的三份真实产物）、编译器实际吐出的指令流、
装载期按落点打补丁、CRC 在 Flash 上的回读复核，都只有板子能证明。

### 内核内安装器（`arkrtos_installer`，2026-11-22）

`arkrtos_installer.c` 是串口与文件两条入口共用的安装器：在字节流里找镜像头、按重定位表把负载落进
槽位、失败时回 NAK 并记一次 `INSTALLFAIL`。它的常驻形态是 `while(1)` 任务，而真正的验收点几乎都是
「流到一半断了会怎样」，所以用例钉的不是"装成功了一次"，而是**有界驱动下每一步的状态、返回值与调用账目**：

| 用例 | 断言 | 钉住的契约 |
|---|---|---|
| `init` | 4 | 清头缓冲、清已收字节、固定槽状态回到 `UNJUDGED` |
| `run_once_*`（param / timeout / commit_autostart / no_autostart / driver） | 34 | 未初始化与非法句柄直接返回 `PARAM`；空流撞上限返回 `TIMEOUT` 且**已收字节不被丢弃**；提交后写自启位并调 `loader_start`、不带自启位就不调；`TYPE_DRIVER` 走驱动注册入口而不是应用入口 |
| `run_once_refuse` | 12 | `check_install` 的三种拒绝（DUP / VERSION / COMPAT）各自原样回传，且**一个字节都不写槽位** |
| `drain_table_timeout` / `drain_quiet_slack` | 14 | 重定位表阶段每个字节等 300 ms、超时按失败收尾；帧尾 2 字节比静默窗口晚到也要被读走，不能提前判完 |
| `load_failure` | 10 | 落槽失败回 NAK `0x15`、只对串口路径排空、记一次 `INSTALLFAIL`，不写自启位 |
| `idle_limit_resumes` | 6 | 空转 20000 次后返回 `TIMEOUT`，此后再喂剩余字节仍能接着拼出一帧（断点续收） |
| `run_once_fixed_*`（no_hint / clear_fail / ok） | 20 | 未配置固定槽返回 `ERR_CONFIG`；清槽失败返回 `ERR_ERASE` 且不继续；配置齐了才 `slot_hint_set` |
| `tick_*`（open_fail / auto_commit / fixed_unusable） | 16 | 设备打不开时不得触碰状态机；AUTO 下固定槽状态从 `UNJUDGED` 走到 `READY`；槽不可用时帧被**静默排空**、不写 NAK |
| `frame_ok_states` | 12 | 只有 `READY` + 槽为空才放行；`DONE` 拒绝第二帧；`UNJUDGED` 一律拒绝 |
| `from_file_*`（gates / short / bad_magic / dev_fail / ok） | 36 | 未挂载 / NULL / stat 失败 / 是目录 / 超长 各自返回 `PARAM` 或 `SIZE`；头短读按 `SIZE` 而不是猜；magic 错按 `MAGIC`；`file_dev` 注册失败按 `PARAM`；正常路径按 17 字节分块读也能量对负载字节数 |
| `file_shim` | 4 | 文件设备垫片的 `drv_open` / `drv_close` 两个入口自身也被走到 |

**两处刻意的设计**：

1. **`while(1)` 不硬测，拆出一轮**。原任务的循环体是 `for(;;){ ...; task_wait(50); }`，宿主上调它
   永不返回。把循环体原样拆成 `arkrtos_installer_tick(int32 *p_dev)`，任务只剩
   `for(;;){ tick(&dev); task_wait_internal(50); }`——**行为等价**，默认构建里 `tick` 仍是 `static`、
   不产生新符号。宿主档靠 `ARKRTOS_INSTALLER_HOST_TEST` 拿到 `tick`、已收字节、头缓冲、固定槽状态与
   文件垫片的读写入口，其余全部走 `init` / `run_once` / `from_file` 真路径。这与 `timer` 的圈数预算、
   `eset` 的对象表导出口径一致：**只导出测试确实无法通过公开 API 触达的面**。
2. **设备、装载器、文件系统全部打桩，断言调用序列与参数**。桩只回答问题，不模拟时序，所以
   `test_idle_limit_resumes` 用「读 120 字节 → 读 30000 次空 → 再读剩余 136 字节」把断点续收钉成账目，
   而不是靠等待真实时间。

**余下 5 行登记**：`arkrtos_installer_task()` 里 `for(;;)` 循环与 `task_wait_internal(50)` 那 5 行——
该函数开中断后永不返回，宿主上调它会把门禁挂死。这是**结构性不可达**，不是"没测到"，也不造一次
假调用来把数字刷绿。

**不证明板端**：真实 Flash 写入与擦除时序、真实串口波特率下的丢字节与流控、重定位后的代码能否执行、
CRC 在 Flash 上的回读复核，都只有板子能证明；用户态安装（SVC）也不在宿主。

### 页表隔离后端（`arkrtos_paging`，2026-11-22）

`arkrtos_paging.c` 是 MMU 侧的隔离后端：给任务做窗口审计、切活动页表空间、发放动态映射，
并且是用户给的地址进入内核代码的**唯一通道**（`arkrtos_paging_user_copy`）。它整体落在
`#if (ARKRTOS_USE_PAGING == 1)` 里，关档是空目标、零符号。板级取 `board/qemu_loongarch64`
那份配置（页表后端在 ARMv7-M 上会被 `arkrtos_config.h` 直接 `#error` 拦掉），但这一层的语义
与具体 port 无关，所以 20 个 port 函数在用例里全是桩。

| 用例 | 钉住的契约 |
|---|---|
| `module_init` | 清空间表、清映射计数，并调一次 `port_paging_init` |
| `build_task` | `rom_start == 0` 时**不动**已有审计面；否则 ROM/RAMX/RAM 按槽位窗口分类；`size == 0` 的段不计 |
| `set_app` | NULL / 特权任务 / 下标越界各自被拒且**不触碰 port**；接受的调用才 `switch_to` |
| `space_forwards` | 六个空间查询入口逐个透传给 port，返回值不被改写 |
| `bind_and_of` | 共享段绑定与反查在空表与命中两种情形下的返回 |

| `map_span` | size 0 / 非 4 KB（size、va、pa 三处）/ 超 16 页预算各自返回 -1，且**拒绝不消耗预算**；逐页 `alias`；半路失败原样透出且不递减已计页 |
| `unmap_span` | 逐页 `unalias`；半路失败时已释放的页仍要还账 |

**口径写死**：宿主是 ILP32，`unsigned long` 32 位，回绕类断言只证分支行为、不证宽度
（LA64 是 64 位，宽度差异在板端）。**不证明**：TLB/TCB 的换表行为、真缺页异常、用户态实际
能否越界——那三件事只有 QEMU（算上板，不算真机）与真 LA64 板能证明。

**同一笔的两处零行为改动**：`arkrtos_paging.c` 里 `(volatile uint8 *)user` 与 `(void *)src`
经 `(unsigned long)` 中转，消掉 `-Wcast-qual` 以便这条 TU 进 `warn-clean`。用 LA64 交叉编译器
编同一份源码，改前/改后目标文件 `md5` 都是 `042c3c58787828acaf96f5c7b97718e3`（28832 B）——
**位模式与代码生成零变化**，不是口头声明。

### 控制台登录闸门（`arkrtos_shell_auth`，2026-11-22）

`arkrtos_shell_auth.c` 是 shell 的密码闸门（SEC-G01）：读入的口令与编译期注入的
`salt` + `sha256(salt || password)` 比对，32 字节全量累加、无提前退出；连续错
`ARKRTOS_SHELL_AUTH_TRIES`（默认 5）次锁到底，只有复位能恢复。此前它只有编译侧门禁
（`shell-auth`：开关接线、关档零符号、时序写法、命令注册位），**没有一条用例走过状态机**。

用例 `shellauth`（`test_shell_auth_host.c`，73 条断言）钉：

| 场景 | 钉住的契约 |
|---|---|
| 开机 | `init` 后锁定；`gate(NULL)` 返回 -1 且**不打印**（没有可说的名字） |
| 豁免词 | `login` / `logout` / `help` 在锁定状态返回 0，既不打印也不计错 |
| 锁定下别的词 | 返回 -1，打印「console is locked, type 'login <password>'」 |
| `login` 参数 | `argc != 2` 两个方向都打印 usage 并返回 1，状态不变 |
| 错误口令 | 每次返回 1、计数 +1、打印 `(n/TRIES)`；第 TRIES 次翻成锁到底 |
| 锁到底 | 正确口令也被拒（返回 1）且文案含 `reboot`；门禁改报 `console locked until reset` 并带上错次 |
| 正确口令 | 返回 0、解锁、清计数；此后门禁放行任意名字且不打印；再 `login` 答 `already logged in` |
| `logout` | 已锁 / 锁到底各自只打印；已解锁时锁回去并清计数（下次错口令从 1 开始） |

**盐与摘要是夹具**：盐 `0x00..0x0F`、口令 `s3cret!`、摘要是 `sha256(salt || "s3cret!")`
离线算出来的常量。这样「正确口令解锁」证明的是口令真算到了存下的摘要，而不是模块把
自己算出的值再比一遍。

**余下 1 行**：`auth_streq` 的 `if((a == 0) || (b == 0)) return 0;`——三个调用点传的都是
字符串常量，另有一个入口已先判 `name == 0`，公开 API 触达不到，属结构性不可达。

**不证明**：口令在串口上是明文、镜像泄漏后可离线爆破、真时序恒定性（只能看代码形状）、
以及板端控制台的实际介入。这一层是 ILP32 宿主，结论与指针宽度无关。

### 设备树控制台的消费（`arkrtos_fdt_console`，2026-11-22）

`arkrtos_fdt_console.c` 回答一个具体问题：树里说「控制台是这台设备」，和板级常量说的是不是同一台。
它不是驱动，**不写任何硬件寄存器**——控制台在解析设备树之前就已经起来了（打印本身要用它），
运行期改地址会把「谁在说话」变成随配置变化的量。所以它只做判断：一致回 `OK`，不一致回一个
**指得出是哪条事实不成立**的原因码，绝不「挑一个能用的就好」。

| 原因码 | 树里的哪条事实不成立 |
|---|---|
| `NO_STDOUT` | `/chosen/stdout-path` 不存在（或设备树未初始化） |
| `BAD_PATH` | 值写法不认识（不猜） |
| `NO_NODE` | 路径/别名指向的节点不存在 |
| `DISABLED` | 节点 `status` 不是 okay |
| `COMPAT` | `compatible` 与板级控制台不同 |
| `ADDR` | `reg` 首单元与板级控制台窗口不同 |
| `BAUD` | `stdout-path` 的选项与节点 `current-speed` 冲突 |
| `CLOCK` | `clock-frequency` 缺失（期望确定值时不接受「没写」）或与板级 UART 时钟不同 |

用例 `fdtconsole`（`test_fdt_console_host.c`，65 条断言）钉：九条出口逐个命中；报错时
**已读到的字段仍然填进 `out`**（日志能把「读到了什么」打出来）；`OK` 时 path / compatible /
reg / clock / baud / bits / parity 逐项等于夹具；`stdout-path` 写 115200 而节点 `current-speed`
不同 ⇒ `BAUD`；`expect == 0` 表示只解析不核对（五项都不比）；三个期望字段各自只比自己那一项；
127 字符顶格路径不截断、越界哨兵原封不动；原因码短名稳定、未知码回 `?`。

**同一笔修掉一处真缺陷**：`console_copy` 在目标缓冲装不下时直接 `return -1`，**不写终止符**，
于是 `out->compatible`（32 字节）在超长树字符串下会变成非 C 字符串，后续 `strcmp` 会读进
相邻字段。现在截断时把 `dst[cap-1]` 写成 NUL 再返回 -1——调用方看到的仍是合法前缀。
这是**行为改动**（不是纯加用例），用 LA64 交叉编译器编同一份源码：改前 `.o` 7856 B，改后 7816 B，
差异来自这条终止符存储与随之调整的分支布局。**不证明**：真实 DTB 的解析（`fdt` 用例负责）、板端控制台实际绑到哪个 UART、
以及 DTS 本身写错时的编译期检查。

### 定时器 / 时基的设备树核对（`arkrtos_fdt_res`，2026-11-22）

`arkrtos_fdt_res.c` 回答「内核按什么频率在跑定时器」：这个数字既可能来自板级常量
（`ARKRTOS_PORT_TIMER_HZ` 一类），也可能写在设备树的 `/cpus/timebase-frequency`
与定时器节点的 `reg` / `clock-frequency` 里。MMU 档的口径是**树是权威描述、板级常量是它的落地，
两者必须一致**——不一致时返回具体原因码让调用方拒绝继续，绝不挑一个"看起来能用"的值：
按错频率算节拍的症状是时间走得快/慢，看上去像调度器坏了。本模块只读，不重编程定时器。

| 原因码 | 树里的哪条事实不成立 |
|---|---|
| `NO_CPUS` | `/cpus` 不存在（或设备树未初始化、入参为空） |
| `NO_TIMEBASE` | `/cpus` 没写 `timebase-frequency`，而调用方**期望**一个值 |
| `TIMEBASE_DIFF` | `timebase-frequency` 与板级常量不同 |
| `NO_TIMER` | 按 compatible 找不到 enabled 且匹配的定时器节点（含遍历报错） |
| `TIMER_NO_REG` | 定时器节点没写 `reg` |
| `TIMER_REG_DIFF` | `reg` 首单元与板级基址不同 |
| `TIMER_NO_HZ` | 定时器节点没写 `clock-frequency` |
| `TIMER_HZ_DIFF` | `clock-frequency` 与板级不同 |

用例 `fdtres`（`test_fdt_res_host.c`，62 条断言）钉：八个出口逐个命中；`expect` 的四个字段
置 0 表示「这一项不检查」（`timer_compat == 0` 在时基之后直接收工）；「期望 0 + 树没写」

### 扁平设备树解析器本体（`arkrtos_fdt`，2026-11-22）

前面三节（`fdt_console` / `fdt_res` 与更早的 `fdt` 家族接口）都在**消费**设备树，本节是第一
次直接测**解析器本身**：`arkrtos_fdt.c` 1477 行，负责把一块 DTB 变成「节点树 + 属性表」，
后面所有 FDT 相关模块都站在它上面。它整段在 `#if (ARKRTOS_USE_FDT == 1)` 内，默认档不编。

这一节最要紧的不是「能解出一棵树」，而是**坏 blob 必须被拒**。一个「几乎正确」的解析比拒绝更
危险：内核会从错的偏移读出节点名、或者走进一棵 END 不配平的树，之后每一个症状都像驱动 bug。
所以用例 `fdt`（`test_fdt_host.c`，295 条断言）自己按字节拼 DTB——头 + 结构块 + 字符串块 +
空 rsvmap——先拼一棵固定树（根 + `/aliases` + `/chosen` + 两个串口节点 + 四层深的叶子 +
`/soc/broken` + `/__symbols__`），再逐字段改坏：

- 头里每个能错的字段都有自己的码：空指针或不足 40 字节是 `ARG`、magic 不对是 `MAGIC`、
  版本低于 16 或 `last_comp` 高于 `version` 是 `VERSION`、`totalsize` 越过缓冲区是 `RANGE`、
  结构块/字符串块/rsvmap 偏移不对齐是 `ALIGN`；
- 结构块必须严格嵌套并在块尾正好收口：缺 END、END 时仍有节点未闭合、END 之后还有字节、
  深度 0 上出现 END、未知 token、节点名没有 NUL、属性名偏移落在字符串块外、属性声明长度
  超出块尾，全部是 `FORMAT`；
- 嵌套超过 `ARKRTOS_FDT_MAX_DEPTH` 是 `DEPTH` 而不是走到一半失败；
- `init` 是事务性的：坏 blob 失败后**上一棵树仍然可用**（用例先装好树、再装坏的、再查旧路径）。

读的那一面同样钉住：深度优先顺序、`node->depth` **从 1 起算**（根的直接子节点是 1，只有
`node_by_path("/")` 是 0，头文件注释里的「0」是旧说法）、meta 节点（`__symbols__` /
`__fixups__` / `__local_fixups__`）在计数与遍历里都**连同子树**被排除、属性查询 / 字符串 /
u32 cells / `status` 是否 `okay`、绝对路径、`phandle` 与 `linux,phandle`、`aliases` 的字符串
与 phandle 两种写法，以及 `stdout-path` 的三种形状（别名带选项 / 绝对路径 / 单个 phandle 单元）
与每一种必须被拒的选项拼法（重复的波特率、重复的 parity、非数字尾巴）。

**同一笔修掉一处真缺陷**：`fdt_scan()` 原来只跳过 meta 节点**自身**、不跳过它的子树，而
`arkrtos_fdt_next()` 是整段跳过的 —— 两条读路径对「有几个节点」的口径不一致。真实 dtb 里
`__local_fixups__` 通常挂着节点，所以这不是理论差异。修法是在 scan 里加一个 `skip_depth`
记号，进入 meta 节点时记下深度、退到该深度时清掉，期间不计数；用例里「`__fixups__` 带一个
`inner` 子节点」那一格就是这条修复的回归门禁（修前 `node_count` 会把 `inner` 数进去）。

LA64 交叉编译（`-march=loongarch64 -O2`）读数：`arkrtos_fdt.o` text 7868 → 7924 B
（+56 B，就是这层 `skip_depth` 记账），data 0 / bss 48 不变；默认档整镜像的差异只来自这一处。

实测覆盖率 **91.84%**（608 / 662 行）。余下 54 行逐条核过：绝大多数是 init 校验之后结构上
不可达的二次防御（对齐不变式使 `fdt_node_name` 的 pad 越界与属性 pad 越界两条恒不成立——
块尾必 4 字节对齐，任何「值装得下但补白越界」的组合都不存在）、多行条件的续行，以及
`fdt_build_path` 的 `pathcap < 2`（两个调用点传的都是 256 字节缓冲）。这里如实留白，不为了
把数字推到 100% 去造一次不可达的调用。

**不证明**：板端真实 dtb 能解（那是 `tools/fdt_gate.py` 对随镜像发布的那几份 dtb 的活）、
也不证明任何驱动真的用了它找到的节点。

### dtb overlay 重拼（`arkrtos_fdt_overlay`，2026-11-22）

上一节测的是「读一棵树」，这一节测的是「拿一棵树和一段 fragment 拼出新的一棵」。
`arkrtos_fdt_overlay.c` 2495 行，整段在 `#if (ARKRTOS_USE_FDT_OVERLAY == 1)` 内，默认 0。
它的实现是**两遍扫描 + 重拼**：第一遍只算 struct 段长度与 strings 上界（不写 dst），所有拒绝
条件都在这一遍暴露，于是失败时目标缓冲区一个字节都不会被写过；第二遍按算出的布局落笔，
strings 顺带去重；两遍之后核对「写出来的长度 == 第一遍算的」，不等就报错而不是交一块长度对
不上的 blob。

用例 `fdtovl`（`test_fdt_overlay_host.c`，308 条断言）把**基树与 fragment 两块 blob 都按字节拼**
（各自带 header + rsvmap + 结构块 + 字符串块），但断言方式刻意不是抠偏移：每次成功合并都把输出
blob 交给**真解析器** `arkrtos_fdt_init`，再用 `node_by_path` / `prop_str` / `prop_u32` 读回语义；
只有 header 与 reserve map 这类布局事实才逐字节断言。理由和上一节一样——一块「看起来对但
解不开」的输出比一次拒绝更糟。

钉住的语义：

- 两种 target 写法都走通：`target-path` 绝对路径，与 `target = <0xffffffff>` 占位值经 fragment 的
  `__fixups__`（`<label> = /fragment@N:target:0`）加基树 `__symbols__` 还原成路径；
- 合并内容：同名属性覆盖、新属性追加、新子节点（带孙节点，逼出递归拷贝）、后一个 fragment
  覆盖前一个；
- 删除：长度 0 的属性删属性，只带一条长度 0 的 `__delete` 属性的同名子节点删子节点；目标是
  基树里不存在时返回 `-16` 而不是静默跳过；
- 六个拒绝码各有自己的格子：`-11` 形状（没有 `__overlay__` / 两个 `__overlay__` / fragment 下
  多一个外来子节点 / 没有 target）、`-12` 目标（相对路径、路径不存在、已解析的 phandle、缺
  fixup、缺 symbol、`"//"`、尾随 `'/'`）、`-13` 同名新子节点（对基树与跨两个 fragment 各一格）、
  `-14` arena 不够、`-15` fragment 侧出现 `__symbols__` / `__local_fixups__`、`-16` 删除目标不存在；
- 深度：基树嵌套超过 `ARKRTOS_FDT_MAX_DEPTH`（16 层，加根那一层令牌）是 `-7`，16 层本身
  合法（两格对照）；
- reserve map 按 16 字节块找到全零项为止**原样搬走**（连同一项 `addr/size` 的 32 字节版本
  逐字节比对），以及参数闸门（NULL dst、NULL out_len、未对齐 arena、cap 低于文档下限）。

删除的编码（`__delete` 标记）是**本项目自定**的，不声称与 Linux dtbo 一致；真实 dtc 产出的
demo fragment 由另一条路覆盖——`tools/dts/test_fdt.py` 把 demo.dts 编译成 dtb 后交给同一个
overlay 函数，并检查基线节点数 +1、model 被覆盖；`fdt overlay` shell 命令也走这条。本用例的
价值是把**拒绝面**逐格钉死，那是真 blob 给不了的。

LA64 交叉编译（`-march=loongarch64 -O2`）读数：`arkrtos_fdt_overlay.o` 在板级配置打开时
（`qemu_loongarch64` 的 `arkrtos_board_config.h` 把开关设为 1）text **14979 B**、data 0 / bss 0；
开关为 0 时该 TU 是**空目标**——0 字节、0 个符号，默认档体积与行为零变化。

实测覆盖率 **86.40%**（978 / 1132 行）。余下 154 行逐类核过，都不是「没测到的主路径」：

1. **空指针与参数守卫**（如 `ovl_strlen` 的 `s == 0`、`ovl_seg_eq` 的同类分支）：公开入口已经
   判过，内部调用点传的都是非空指针；
2. **坏 blob 的深层早退**（1194 / 1224 / 1249 / 1676 / 1688 / 1697 一带）：这些函数只在 blob
   已经过 `ovl_blob_scan` 之后才被调用，而 scan 已保证 token 流合法、令牌长度不越界，所以这些
   `return 0` / `return cnt` 是二次防御；
3. **深度上限的另外三个检查点**（`ovl_skip_node`、`ovl_copy_node`、`ovl_emit_node`）：基树与
   fragment 在进这两步之前已被 scan 按 `MAX_DEPTH + 1` 拒掉，所以只有 scan 那一处能命中（已由
   「17 层」那一格覆盖）；
4. **`OVL_MAX_FRAGS` 的两个「不可能」分支**：`nfrags` 由扫描保证不超过上限；
5. **两遍对账失败与长度相加溢出**（2352 / 2430）：在当前实现下打不到（遍历不依赖输出状态、
   arena 在入口已按 cap 校验），保留作对账——真要命中说明实现有 bug，用例硬造反而是假的；
6. 其余是多行条件的续行与写越界置 `overflow` 的若干组合（会被 `-14` 那一格覆盖其中一条）。

这里如实留白，不为了把数字推到 100% 去造不可达调用。

**不证明**：真实 Linux .dtbo 能合并（删除编码不同，且 fragment 侧 `__symbols__` 被拒）、也不
证明合并出来的树能启动。

### littlefs → ark_vfs 桥（`arkrtos_vfs_lfs`，2026-11-22）

`arkrtos_vfs_lfs.c` 516 行，整段要求 `ARKRTOS_USE_VFS` / `ARKRTOS_USE_VFS_LFS` /
`ARKRTOS_USE_FS` 三个开关同时为 1，任一不成立时整个 TU 只剩一个 `typedef`（空目标）。
它不 include 任何 lfs 头，只把 `arkrtos_fs.h` 已经公开的入口接成 `ark_vfs_fsdrv_t`：
读用 `arkrtos_fs_read_at()`（随机访问，多 fd 可并发读），写用
`open_write/write_next/close_write`（文件缓存只有一份，因此同一时刻只允许一个写句柄）。

用例 `vfslfs`（`test_vfs_lfs_host.c`，213 条断言）在 RAM 里搭了一张定长节点表当假 littlefs，
15 个 `arkrtos_fs_*` 门面入口全部由用例实现，日志两个入口（`arkrtos_log_get_level` /
`arkrtos_log_emit`）也是桩，然后**直接调用驱动表的每个回调**——不走 ark_vfs 核心，这样
被测对象就只有桥本身。桩带失败注入，但只用来走到出错分支；返回码由桥决定，不拿 littlefs
的具体数字去猜。

钉住的语义：

- 挂载：`arkrtos_fs_mounted()==0` 时 `-11`（桥不自己去挂卷）；成功一次清空句柄表与写流标记；
- open：挂载根 `""` 是 `-5`；只读打开不存在是 `-1`；写意图 + stat 失败但**不是** NOENT 是
  `-11`，是 NOENT 才新建；父目录缺失（`open_write` 回 NOENT）也报 `-1` 而不是一律 `-11`；
  目录不带 `ARK_O_DIRECTORY` 是 `-5`，带了则成功且不带写意图；`ARK_MNT_RO` 上是 `-9`；
  第二个写句柄是 `-15`；句柄表满（`ARK_VFS_MAX_FDS` = 8）是 `-3`；`O_APPEND` 起点在文件尾；
- close：NULL 是 `-2`；写句柄关闭才是提交，失败报 `-11` 但句柄与写流标记仍然归还；
- read：NULL/目录句柄 `-4`，缓冲区 NULL `-2`，写句柄 `-2`，别人在写 `-15`，`n==0` 是 0，
  文件尾是 0 而不是错误，出错 `-11`，成功时 pos 前进（第二次读拿到剩余字节）；
- write：NULL/目录/非写句柄 `-4`，缓冲区 NULL `-2`，`n==0` 是 0，成功返回 n（全有全无），
  失败 `-11`；
- seek：NULL `-4`，写句柄 `-12`（顺序流），SET/CUR/END 三条，坏 whence `-2`，SEEK_END 时
  stat 失败 `-11`；
- stat：NULL 输出 `-2`，不存在 `-1`，文件 `ARK_S_IFREG|0644`、目录 `ARK_S_IFDIR|0755`，
  mtime/uid/gid 全 0，路径超 64 字节 `-13`；
- unlink / rename / mkdir：源不存在 `-1`、目标已存在 `-7`、后端失败 `-11`、成功；
- opendir / readdir：不存在 `-1`、不是目录 `-6`、fd 满 `-3`；readdir 跳过 `.` 与 `..`、
  名字超过 `ARK_VFS_NAME_MAX`（32）是 `-13` 且不前进 pos、到底 `-1` 且连续两次一样、
  列目录失败 `-11`；
- truncate：NULL `-4`、目录 `-5`、负长度 `-2`、只读挂载 `-9`、别人在写 `-15`；写句柄只认 0
  （打开时已清空），非零 `-12`；只读句柄走门面的 `arkrtos_fs_truncate()`，NOSPC 是 `-10`、
  其它失败 `-11`，成功后内容真的只剩前 n 字节；
- 驱动表：`chmod` / `chown` 为 NULL（核心会翻成 `-12`），`caps` 九位齐全。

实测覆盖率 **99.03%**（204 / 206 行）。余下两行是 `p_alloc()` 里 `ark_p_strcpy()` 的失败
分支：`p_abs()` 已把卷内路径限制在 `ARKRTOS_FS_PATH_MAX`（64）以内，目标缓冲同样是 64，
所以这次拷贝不可能失败——结构性不可达，不为它造一次假调用。

**不证明**：真 littlefs 的行为（那是 `arkrtos_fs` 的用例）、ark_vfs 核心的路径解析与
挂载表（那是 `ark_vfs` 的用例）、以及板端 NOR 上掉电窗口与擦写寿命。用例直接调驱动表，
所以「核心与驱动之间的契约」本身不在这里证。

### VFS 门面（`arkrtos_vfs`，2026-11-22）

`arkrtos_vfs.c` 1118 行，是内核对外的那层名字空间门面：`arkrtos_vfs_init()` 装根、
`mount_volume()` 把一块设备窗口接成持久卷、App 侧再拿到「tag + 序号 + 槽号」编成的句柄。
`ARKRTOS_USE_VFS=0` 时整段换成诚实空实现（全部 `-12`），本用例覆盖的是开档那一半。

用例 `vfs`（`test_vfs_host.c`，314 条断言）**链真 `ark_vfs_core.c` 与真 `ark_vfs_ramfs.c`**，
只把板级那一圈桩掉：端口层（`ark_vfs_port_init` / `blk_init`）、`arkrtos_fs_*` 六个门面、
littlefs 桥、日志与任务状态。这样「/dev 先挂、/ 后挂、最长前缀、挂载表、核心 fd 表」全是
生产代码在跑，只有设备与卷是假的。

用例按**启动阶段**组织，因为 `g_vfs_ready` 只 0→1 一次、没有反向的 deinit：

1. `test_not_ready`：未初始化时每条门面必须 `-2`（不是「假装成功」）；
2. `test_init_failures`：端口起不来把原因原样交出且不就绪；根被端口抢先占掉 → `-17`，
   且核心被拆干净（`ark_vfs_is_ready()==0`）；
3. `test_init_ok`：先塞 13 个目录占满目录槽，标准目录只剩 3 个能建，`/mnt` `/media`
   各告警一次而不是谎报成功；连调两次不重复装 `/dev`；
4. 之后才是挂载表 / 持久卷 / 门面读写 / App 句柄 / seek / readdir 各节。

钉住的语义（摘要）：

- `mount_volume`：**参数与就绪面先于能力判断**（坏参数报 `-2`，只有本构建真没有 littlefs
  桥才报 `-12`）；块窗口拒绝原样透出；卷挂不上报 `-11` 且不留下半挂状态；第二个卷 `-17`；
  几何不同/取不到几何一律 `-17`；挂点被占时必须把卷也卸掉；
- App 句柄是**能力不是号码**：tag 不对、槽号越界、序号不对、槽已空、不是本任务 → 全 `-4`；
  槽被回收后再发出去的号码与旧的不撞；死任务的槽只在「下一次要句柄」时回收（故障路径在
  中断上下文里不能做文件 I/O）；句柄表满时把刚拿到的核心 fd 还回去；
- 位置与大小由门面自己记账（ramfs 的 `lseek` 回新偏移、littlefs 桥回 0，直接用下层返回值
  会在某个卷上静默偏掉），溢出用 `INT32_MAX` 双侧判断而不是回一个负偏移；
- `read_file` 缓冲装不下是 `-10`，**不是**「截断成功」；`read_at` 短读当 EOF；
- `O_APPEND` 的**每一次写**都回文件尾（两个文件系统都只把「打开时定位」当一次性动作，
  所以门面自己补），与中间做过什么 seek 无关；
- `readdir` 名字装不下报 `-13`，**且把那一项留住**下次再交——否则调用方换个缓冲重列时
  这一条会凭空消失（本轮修的就是这条）。

两档（默认档 + `-DARKRTOS_USE_VFS_LFS=0`）按行号并集 **98.70%**（379 / 384 行）。余下 5 行
是两处 `p_copy()` 的溢出退出（`mount_volume` 写卷目标、`mount_info` 写挂载点）：`ark_vfs`
的归一化先拒掉长度 ≥ `ARK_VFS_PATH_MAX`（64）的路径，而两处目标缓冲同样是 64，所以这两次
拷贝不可能失败——结构性不可达，不为它造一次假调用。另外用例以 `-DARK_VFS_MAX_FDS=12` 编：
核心 fd 表比 App 句柄表（8）宽，「句柄槽用满、把核心 fd 还回去」那两条才走得到；8/8 时它们
同样是结构性不可达。

**这一跳改了三处生产代码**（`arkrtos_vfs.c`）：`app_write()` 的 `O_APPEND` 每次回尾、
`app_readdir()` 的「装不下的目录项留到下次」、`mount_volume()` 把参数/就绪校验提到

### 文件系统门面（`arkrtos_fs`，2026-11-22）

`kernelsrc/tests/test_fs_host.c`，1030 行，默认档 **347 条断言**、关档 **26 条**。

### socket 请求槽（`arkrtos_net`，2026-11-22）

被验的是这一层「请求槽服务」：App 侧入口把请求投进槽，网络服务任务取出来调协议栈，第二次

`DYNLOAD/TLS`、`EXIT_CODE/EXEC_SIGN` 各自一条），这些由 QEMU LoongArch64 上板覆盖。

余下 14 行未覆盖，按类登记：分页档的「先装空间再落笔」与 `paging_bind_task`、动态档的

### Linux 系统调用 ABI（`arkrtos_linux_abi`，2026-11-22）

`kernelsrc/tests/test_linux_abi_host.c`，开档 **270 条断言**、关档 **6 条**（关档时每个读数
都回答「没有这件事」，不是空成功）。

被验的是「一次系统调用从入口到返回值写回 a0」这条链，而不是「一个 Linux 程序真的跑起来了」：
入口分流（`0xFFFFFFFF` 不是 Linux 调用，交回 Ark 号表）、返回值分类（地址类按整字宽写回、
错误分类计数、exec 成功**不写返回值**）、fd 表（从 3 起、越界 EBADF、`O_*` 拒绝、失败时偏移
不前进也不重放）、管道（回绕、只剩写者时 EOF、EPIPE、`copy_to_user` 失败不得吃掉管道数据）、
信号（能力探测在参数校验之前、屏蔽字 `&= ~(SIGKILL|SIGSTOP)`、投递点在系统调用返回用户态
之前、`rt_sigreturn` 装回帧、端口不能投递时回 ENOSYS）、execve（argv 按 8 字节槽读、超上限
E2BIG、装载失败按 `ARKRTOS_ELF_ERR_*` 逐条映射 errno、只有装载成功才换帧、端口无换帧能力回
ENOSYS）、reset（fd / 管道 / 信号表清空，调用方寄存器不归它管）。

**三件它明确不证明的事**（写在文件头，也在 `linux-abi` 那条 QEMU 门禁里补）：

1. 用户内存是**模拟**的：`copy_from_user` / `copy_to_user` 在用例里是桩，地址落在
   `[WINDOW_BASE, WINDOW_BASE+WINDOW_SIZE)` 就从 `g_user[]` 读写，越界返回 -3。所以「合法 /
   非法 / 半路失效」三种情形能确定地造出来，但**不证明真分页后端的窗口判定**（`paging` 与
   `linux-abi` 的 QEMU 档覆盖那一半）。
2. 字宽是 32 位（MinGW ILP32，`unsigned long` = 4 字节）：信号帧头在这里占 16 字节、payload
   从字节偏移 16 开始；la64 的 64 位布局（头 32 字节）由 QEMU 上板覆盖，这里**不**伪装覆盖。
3. 帧长只测 256 字节这一档：`fbytes=1040` 在 32 位宿主上会写爆 536 字节的内核缓冲，那属于
   端口帧长与内核缓冲的老账，不是本用例要断言的行为。

**链接期一个坑（写进用例注释与 ci 检查的 docstring）**：错误路径上「端口不能换帧」由源文件里
一条 `__attribute__((weak))` 的默认实现回答，用例给同名强定义。MinGW 在 `-O0` 下会把同链接里
的弱定义解析到本地入口（`-ffunction-sections` 也救不回来，实测 `call` 落到段外地址直接崩溃），
所以两档都带 `-Wl,--wrap=arkrtos_port_svc_exec_frame` 链接，用例侧提供 `__wrap_...`。
`coverage_gate.CASES` 为此新增了可选的 `ldflags` 键（只影响链接）。

**不证明**：真 CPU 上的系统调用返回路径、真地址空间下的用户内存校验、la64 的 64 位信号帧布局。
宿主这一档只证明**返回值与 errno 是它声称的那些**。

### 迷你应用装载器（`arkrtos_mini`，2026-11-22）

`kernelsrc/tests/test_mini_host.c`，开档 **272 条断言**、关档 **3 条**（关档时六个入口
全部回答「没有这件事」；`nm` 核过 `arkrtos_mini.c` 在关档下编成空目标、只剩段标记）。

被验的是「一次小程序装载」这条链的六步账，而不是「一份镜像真的在板子上跑起来了」：

1. **路径与槽位**：空指针 / 空串 / 63 字节可放、64 字节必须拒绝（不截断，截断会让两条
   路径撞成同一身份）；同一路径重复装载 BUSY、运行时实例数到 `ARKRTOS_MINI_MAX` 为止、
   崩溃禁用名单命中时 `MINI_ERR_DISABLED`；
2. **头关**：读表前后各一次 `loader_check_header`（防「读表期间头被改」），第二次必须
   看见重定位表存在；`image_size + reloc_count*4 + 256` 的总额校验、`code_span` 取 2 的幂
   并核对池上限；
3. **借块**：`ptable_mini_alloc` 借两块（代码 + RAM），第二块失败时第一块必须还回；
4. **分块读**：256 字节一块，边读边算 CRC、边按重定位表打补丁；表项被切在两块之间时
   按 `arkrtos_loader_reloc_apply` 返回的「已处理到的镜像偏移」回退重读被切开的项
   （用例造 1 条表项、跨分块边界，断言第二次补丁从表项起点开始）；
5. **起任务**：栈大小 / 优先级 / 周期 / 入口（代码块基址 + `entry_offset`）/ 栈底（RAM 块顶
   减 `APP_TASK_STACK_SIZE`）/ TCB 两组窗口 / 非特权，逐项与借还凭据对账；
6. **提交**：实例表写入、`info` 可读、调度器放开；装载期间每段之后都放开过调度器锁
   （`YIELD_CHUNKS=1`）。

失败面逐条注错：路径读不到、短读（`SHORT_READ`）、两次头检查各失败一次、`image_size`
越界与**回绕**（`0xFFFFFF00`）、表读失败、CRC 不符、借块失败、起任务失败。每条都断言
「块还回去了、槽位空出来了、下一次装载能成功」，不是只看返回码。另有 A/B 热切换
（没在跑时 STATE、内核已有挂起切换时 BUSY、布局不同时 `SWAP_ERR_LAYOUT` 且归还新块、
`arm` 被拒也归还、只有目标任务的下一次系统调用才落地、落地时归还旧块）与自启清单
（解析、立即启动、回调返回非零即停、清单装不下时 `NOSPACE`）。

**用例抓到一处真缺陷并已修**：`arkrtos_mini_pow2_ceil()` 的 `while(r < v) r <<= 1;` 在
`v > 0x80000000` 时会进位成 0 并永远追不上 `v`，而此时调度器锁还握着——镜像头被改成
`0xFFFFFF00` 时装载**死等**，后面那条「回绕 ⇒ `LOADER_ERR_SIZE`」的自证永远没机会执行。
修法是先判 `v > 0x80000000` 直接返回 0，调用方按 `code_want < code_span` 正常报 SIZE；
`t_fail_size` 里的回绕用例就是这条的回归门禁（改回旧写法会挂死在门禁里）。

**开关为什么靠包装头**：qemu_loongarch64 的板级头对每一项都是 `#undef` + `#define`，
命令行 `-D` 一定被覆盖，所以 `kernelsrc/tests/mini_test_board.h` 先 `#include` 板级头、
再改四个宏（`MINIAPP=1`、`IMAGE_SIGN` / `EXEC_SIGN=0`、`TASK_SWAP=1`、`MINI_READ_VFS=1`）；
`mini_test_board_off.h` 在它之上把 `MINIAPP` 压回 0。两档各编一次，覆盖率按行号并集
**96.67%**（660 行里 22 行未覆盖）。

余下 22 行按类登记：重定位表 CRC（造表项的用例在读到表之前就失败）、换入路径的
「装载失败」收尾（`swap_abort_load` 整段，只有 `arm` 之后装载本身失败才走到）、自启清单的
「没有清单」与「回调返回非零」两种正常收尾，以及连续故障禁用、`busy` 早退等防御分支。
**不证明**：真 Flash 上的读时序与掉电窗口、真任务被调度起来的抢占与栈使用、A/B 两块在
板端物理地址上的隔离——那些只有板子（QEMU 也算上板）能证明。

### 任务与调度核心（`arkrtos_task`，2026-11-22）

`kernelsrc/tests/test_task_host.c`，2813 行、**18 个用例函数 / 511 条断言**，只打最后一行
`TASK HOST OK 511 checks`；单档板级头 `kernelsrc/tests/task_test_board.h`（`USE_TASK_SWAP=1`，
MiniApp / ELF / 进程文件系统 / VFS / 文件系统 / 块设备 / 软总线 / shell / 审计 / 崩溃日志 /

被验的是调度器与 SVC 分发这两块账，而不是"一个任务真的在 CPU 上被切走了"：

- **首次调度与就绪位图**：T0 首次调度重建（必须最先跑，否则后面的夹具建不起来）、

- **延时链与节拍**：延时链按到期时间排序、tick 推进与时间片耗尽、`wait_time` 的毫秒→节拍

- **调度锁与阻塞**：嵌套锁计数、`block_in_critical` 的 reason 只留低 7 位、阻塞态进入与退出；
- **线程生命周期与栈**：创建/挂起/恢复/删除、收尸、栈用量与栈哨兵（`info[3]` 是"距栈底
  剩余"）、任务换出（块按字节而不是 uint32 个数、take 时 LAYOUT 分支不可达）；
- **SVC 分发**：用 `svc_with_block()` 把参数块摆进 `g_svcb[]` 再逐号调 `arkrtos_svc_dispatch`

  线程、心跳、文件系统、应用管理、shell、日志、系统信息、`FAULT_GET`、`POOL_FREE`、`STACK_INFO`；
- **降级与故障**：`sched_is_switching`、fault handler（handler 内的 `sched_next` 会当场消费

**诚实边界（不能读成"用例抓出了内核缺陷"）**：补齐过程中出现的 40 条断言失败**全部是用例写法
或语义理解错**，`arkrtos_task.c` 没有因为用例改过一行逻辑；本笔对它唯一的改动是下面那批显式
转换。

**同一笔把告警清零，口径是"只加显式转换、只做变量搬运"**：`arkrtos_task.c` 在十二条选项下从
37 条降到 0（21 条 `-Wbad-function-cast` + 13 条 `-Wsign-conversion` + 2 条 `-Wsign-compare`
+ 1 条 `incompatible-pointer`）。统一写法是先把 `ARKRTOS_SVC_ARG(...)` 的返回值落到
`unsigned long a0;` 再转指针——**GCC 4.8 的 `-Wbad-function-cast` 会看穿中间同类型强转**，
直接写 `(T *)(unsigned long)ARKRTOS_SVC_ARG(...)` 仍然告警（与 `kernelsrc/src/arkrtos_net.c`
第 948 行附近的既有注释是同一条口径）。`arkrtos_stack_guard_watch_context` 里的指针声明保持
`arkrtos_svc_arg_t *`（换成 `uint32 *` 在宽参数档会改元素步长，那是真行为变更）。

余下 211 行（1601 行可执行行）按类登记：只有真端口 / 真 PendSV 才走得到的换栈入口与首次
上下文装填、真 MPU 区域下发的分支，以及大量 SVC 入口的"参数块为空指针 ⇒ 返回错误"防御出口
（用例总是给合法块，走不到）。**不证明**：真 PendSV 的寄存器保存与恢复、真栈帧在两块内存
之间搬运、真 MPU 区域真的写进了硬件、真节拍时序下的优先级反转——那些只有板子（QEMU 也算
上板）能证明。

### 为什么最后两个模块没有宿主用例（`arkrtos_modld` / `arkrtos_utest_cases`，2026-11-22）

`kernelsrc/src` 共 53 个 `.c`，宿主用例覆盖 **51 个**（覆盖率与告警门禁都按同一批 TU 走）。
剩下两个是**有意的空白**，不是漏掉的欠账：

- **`arkrtos_modld`（1494 行）编不到宿主上**：它读的是 **ELF64** 头与重定位项（`Elf64_*` 的
  字段宽度），并实现 LoongArch 的 **SOP 栈机**重定位；本机宿主是 MinGW **ILP32**（`long` 4 字节），
  把这些结构塞进 32 位宿主要么改类型（那就不是被测代码了）、要么根本放不下 64 位字段。
  它在自己的工具链档上有门禁：`tools/modld_gate.py`（默认关 + LA64 开档编两个 TU +
  导出表覆盖示例 `.o` 的名字），实跑读数来自 QEMU LA64 的 `ld` / `modules` 命令。
- **`arkrtos_utest_cases`（1319 行）是板端用例集本身，不是被测模块**：它的 12 条用例要求
  真任务被创建起来、真阻塞（`timeout==0` 的非阻塞形态）、多级优先级继承链、真定时器服务任务；
  在宿主上要把它跑起来，就得先造一套假调度器——那样测的是假设调度器，不是内核。
  它的判据在板端：F427 上 `utest run` 报 `12 matched / 12 passed / 0 failed`（190 条断言），
  另有两条需要真中断源的用例放在板级工程里（见「当前用例清单」）。

两条都写在 [欠账盘点](欠账盘点.md) 的覆盖率行里，口径是**「宿主可编」这个集合本身有边界**，
不是「这两个模块没有测试」。

## 编译器告警门禁（`warn-clean`，2026-11-17）

这台机器上没有 cppcheck / MISRA / clang-tidy，宿主那份 GCC 4.8 也没有 `-fanalyzer`
（GCC 10 才有）；真正能跑路径敏感分析的是本机交叉工具链自带的
`riscv64-unknown-elf-gcc-10.2.0`，那是下面单独一节的 `analyzer` 项。本节的
`warn-clean` 只做一件更小的事：把编译器自己的语义分析开到满。
`tools/warn_gate.py` 用十二条选项编**宿主可编的那 189 个 TU**（95 条用例配置，即测试文件 +
它们链接的模块，再加 SDK stdio；`sign` / `blk` / `dev` / `event` / `export` / `init` / `hwsafe` / `audit` / `mpu` 各按两档编两次，`guard` / `log` / `timer` / `cfg` 各按三档编三次，`rt` 按两档编两次，`sec` 按四档编四次（`sec` / `sec-min` / `sec-page` / `sec-disabled`）；`layout` 单档一次，`crash` 按两档编两次，`apprun` 单档一次，`flashapp` 单档一次，`trace` 按四档编四次，`fdtconsole` / `fdtres` / `fdt` / `fdtovl` / `vfslfs` / `vfs` / `vfsnolfs` / `fs` / `fsnofs` 各单档一次，`softbus` / `net` 各按两档编两次，`task` 单档一次，`shellmisc` / `ushell` / `shellmod` / `shellcfg` / `shellimage` / `shellcore` / `shellpmap` / `shelldiag` / `shellplat` 各单档一次），要求**零告警**。

| 条目 | 值 |
|---|---|
| 门禁项 | `warn-clean`（`ci_gate.py` 第 54 项） |
| 独立入口 | `python tools/warn_gate.py`（`--selfcheck` 先证明门禁不瞎） |
| 判据 | 每条 TU 编得过且输出里没有 `warning:`；有任何一条就红 |
| 防假绿 | `--selfcheck` 现场造两个 TU：一条必然告警的（未用参数 + 未初始化读）与一条「没有原型的非 static 函数」；前者看不到告警就判门禁瞎了，后者用来证明接口暴露那一档真在命令行上（`-Wall -Wextra` 对它是沉默的） |

**它抓到过真东西**：`arkrtos_sync_release_task()` 里的 `p_tsk` 声明了却从未赋值 ——
三张表的等待队列都在拿野指针比较，效果是死任务永远留在队列里、它持有的锁永远不交出去。
编译通过、上板不报错，只有读代码或看告警能发现。修法与 9 条钉住行为的断言见
[同步原语与令牌守恒](同步原语与令牌守恒.md) 的「任务下线收尸」一节（去掉修复后 7 条断言失败）。

**接口暴露那一档已于 2026-11-18 并入**（`-Wmissing-prototypes` / `-Wstrict-prototypes` /
`-Wold-style-definition`）。并入前在同一批 21 个 TU 上实测 25 条，全部是
`-Wmissing-prototypes`（**内核 5 + 测试桩 20**），分两族：

* **内核 5 条** —— `arkrtos_mq.c` 的 `arkrtos_mq_send_from_isr` / `arkrtos_mq_recv_from_isr`，
  以及 `arkrtos_sync.c` 的 `arkrtos_sem_post_from_isr` 与宿主档那两条内部函数
  `arkrtos_mtx_propagate` / `arkrtos_mtx_recalc_priority`。前三条在伞头 `arkrtos.h` 里一直有
  声明，可**定义它们的 TU 只 include 各自的模块头**，模块头里没有这几条原型 ⇒ 编译器在定义点
  看不见原型；后两条只在 `ARKRTOS_SYNC_HOST_TEST` 档里不是 `static`（宿主用例直接调），
  那个分支里也没有原型。修法是把同签名原型补进模块头（`arkrtos_mq.h` / `arkrtos_sync.h`）
  与宿主档分支，**没有制造新的公共 API**。
* **测试桩 20 条** —— 7 个宿主用例就地替掉内核函数：trace 钩子 12 条
  （`test_sbuf_host` 3、`test_mq_host` 3、`test_sync_host` 4、`test_eset_host` 2）、
  端口开关 2 条（`test_waitmulti_host`）、四个 ready 查询 4 条（同一个文件）、
  `arkrtos_fault_record` 与 `arkrtos_shell_print` 各 1 条。桩定义前没有原型，
  修法是「先声明后定义」，一行注释点明「桩也是接口」。

`-Wstrict-prototypes` 与 `-Wold-style-definition` 并入时**一条都没报**（全仓签名都带原型），
钉住它们是为了防以后退回 K&R 风格。并入后默认档 LA64 镜像 **逐字节不变**

**`-Wconversion` 已开（2026-11-19）**：同一批 21 个 TU 上它共 33 条 —— 6 条窄化 + 27 条

1. 只加**显式转换**，不改类型、不改比较语义、不改算法。窄化处写 `(uint8)` / `(uint16)`，
