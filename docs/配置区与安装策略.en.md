# Configuration Region and Install Policy

**[简体中文](配置区与安装策略.md) | English**

> Condensed English edition. The Chinese page (配置区与安装策略.md) is normative:
> every number below is copied from it as of 2026-11-18, but if the two disagree,
> the Chinese page wins. This page adds no new claim and no new measurement.

This page answers two questions: **where images are placed on this device**, and
**how to change that without touching the firmware**. Step-by-step operations live
in the application install and debug guide.

## 0. In one sentence

Image placement is **not hardcoded in the firmware**: the device has a separate
128 KB **CONFIG sector** holding a 512-byte **configuration record**. At boot the
kernel reads it first and follows it; if it cannot be read (or fails validation) the
build falls back to the **compile-time defaults** in `config/arkrtos_partition.h`.

So one firmware can have two faces:

| Scenario | Configuration | Effect |
|---|---|---|
| Hand to a customer for secondary development | `mode = fixed` | Every slot address is fixed; the customer can flash apps and drivers at **fixed addresses** with Keil or a programmer and set breakpoints under a debugger |
| Field upgrade / no programmer | `mode = auto` | The kernel does 1 KB-granular first-fit allocation inside the pool; images can move; uninstall compacts per policy |

**The two modes are one-or-the-other per device**, never mixed. Mixing destroys the
single answer to "whose address is this".

## 1. Flash partitions (F427, 1 MB)

```
0x08000000 +------------------------------+
           | KERNEL        256 KB         |  kernel (install task, shell, lwIP)
0x08040000 +------------------------------+
           | CONFIG        128 KB         |  device configuration record (first 512 B used)
0x08060000 +------------------------------+
           | IMAGE_POOL    640 KB         |  one pool shared by apps and drivers
           |  5 x 128 KB sectors          |
0x080FFFFF +------------------------------+
```

`IMAGE_POOL_SIZE` is the remainder of `CHIP_FLASH_SIZE - KERNEL_SIZE - CONFIG_SIZE`,
so **changing the chip size only means changing `CHIP_FLASH_SIZE`** and every address
plus every `.sct` is recomputed.

CONFIG occupies **one whole physical sector** (128 KB on F4) because it must be
erasable on its own: flash can only be erased back to all-ones per sector, so a record
that must be rewritten needs a sector to itself. The cost is one sector less pool:
F427's pool drops from 896 KB to 768 KB.

KERNEL is **256 KB** now (lwIP is compiled into the kernel), so the pool loses another
128 KB and is 640 KB (5 sectors; 512 KB allocatable after the compaction reserve).
KERNEL size must be a power of two (MPU region constraint); dropping
`ARKRTOS_USE_LWIP` lets a `-D` override bring it back to 128K.

F401 (512 KB) has the same shape; its pool is 256 KB over 2 sectors.

### 1.1 Pool allocation granularity

| Parameter | Value | Meaning |
|---|---|---|
| `IMAGE_POOL_SECTOR` | 128 KB | physical sector, the minimum **erase** unit |
| `ARKRTOS_POOL_ALLOC_UNIT` | 1 KB | allocation granularity, the minimum **placement alignment** |
| `POOL_RESERVE_SECTORS` | 1 | headroom kept out of allocation for compaction |
| `SLOT_MAX` | 16 | images the partition table can hold at once (apps + drivers) |

"Erase per sector, place per 1 KB" is the point of the design: a 10 KB app in auto
mode occupies about 11 KB, not a whole sector.

## 2. RAM layout (F427, 128 KB)

```
0x20000000 +-----------------+
           | SHARE_RAM   8 KB|  partition table (kernel/app data exchange surface)
0x20002000 +-----------------+
           | KERNEL_RAM 56 KB|  kernel data / kernel task stacks
0x20010000 +-----------------+
           | SLOT_RAM   64 KB|  image RAM pool (buddy allocator)
0x2001FFFF +-----------------+
```

An image's `.data/.bss/stack` all come out of `SLOT_RAM`; the block size must be a
power of two within `[SLOT_RAM_MIN_BLOCK, SLOT_RAM_MAX_BLOCK]` = `[1 KB, 32 KB]`.
This is not aesthetics: it is an **MPU region constraint** (a region must be a power
of two and aligned to its size).

`KERNEL_RAM_SIZE = CHIP_RAM_SIZE - SHARE_RAM_SIZE - SLOT_RAM_TOTAL` is **not** a power
of two, so the kernel tasks' MPU RAM window degrades to the whole chip RAM. Kernel
tasks are trusted code; isolation semantics are unaffected.

### 2.1 RAM windows for development slots

A raw image (§5) has no image header, so the scanner cannot read its `ram_size`; the
kernel therefore assigns each development slot a fixed window from a **static table**:

```
window base = SLOT_RAM_BASE + (start unit % ARKRTOS_DEV_SLOT_MAX) * ARKRTOS_DEV_RAM_WINDOW
```

That formula has **two implementations that must always agree**:

* kernel: `ARKRTOS_DEV_SLOT_RAM_BASE(unit)` in `config/arkrtos_partition.h`, bound to
  the slot by `arkrtos_ptable_ram_bind()` when the loader claims a raw image;
* toolchain: `dev_ram_base(unit)` in `tools/gen_scatter.py`, which generates the app's
  `.sct`.

If they differ, the app links believing its stack is at A while the kernel puts it at
B - the symptom is "downloads, starts, then crashes after a while".

F427: `ARKRTOS_DEV_RAM_WINDOW = 16 KB`, 4 development slots = 64 KB, **exactly filling
SLOT_RAM**. That means **with four development slots on, auto mode has no RAM left**.
The two policies are mutually exclusive (§3), so it normally does not happen; but
installing an auto image on a fixed device will fail to start for lack of a RAM block
(`ARKRTOS_LOADER_ERR_STATE`).

F401: `ARKRTOS_DEV_RAM_WINDOW = 8 KB`, 4 x 8 KB = 32 KB = `SLOT_RAM_TOTAL`.

## 3. The two install policies

`mode` (offset 12 of the record, also the return of `arkrtos_layout_mode()`):

| Value | Name | Placement | Uninstall |
|---|---|---|---|
| `0` | `ARKRTOS_LAYOUT_MODE_AUTO` | 1 KB-granular first fit inside the pool; the kernel decides the address | Erase this image's range; compact neighbours per `reclaim_mode` |
| `1` | `ARKRTOS_LAYOUT_MODE_FIXED` | Whole sectors are assigned per slot table; address = the one in the record | Erase this slot only, never move or compact, space does not return to the pool |

### 3.1 How hard auto mode reclaims

| Value | Behaviour |
|---|---|
| `0` | no compaction: erase the freed sectors (only if a whole sector is unused) |
| `1` | compaction: move later images forward to create contiguous space |

Flash's physical limit: **a sector is only really erased when all of it (128 KB on F4)
is free**. An image at the bottom of the pool cannot move down, so while somebody else
still occupies part of that sector the space stays pinned in the pool.

### 3.2 What fixed mode means

* flash placement fixed per slot;
* RAM window fixed per slot (§2.1);
* uninstall erases only this slot, **no compaction, no return to the pool** - the
  address belongs to this slot forever;
* the registered slot table comes from the record (`arkrtos_cfg_slot_t slot[8]`).

Overwriting in fixed mode is allowed: flash the same slot again. But a **running image
cannot be overwritten** (the kernel returns `ARKRTOS_LOADER_ERR_BUSY`), because erasing
under it would make it run wild on the spot.

#### 3.2.1 Board defect: in FIXED, `reclaim` still moved images (fixed)

Measured once on F427 where **fixed-slot semantics were violated**: `app install 2`
placed at `0x080A0000` (`app list` read it correctly and the image was `RUNNING`), but
after `reboot` the same image appeared at `0x08060000`, `0x080A0000` read back as
`FFFFFFFF` and the slot was written as `empty`.

The root cause was not on the install side but in the boot path: `main.c`
unconditionally calls `arkrtos_loader_scan_driver()` + `arkrtos_loader_reclaim()`, and
`arkrtos_loader_reclaim()` applied `reclaim_mode` only to "compact or not";
`compact_pool` was skipped, but **the per-sector move loop was not** - it moved LOADED
images into lower holes and erased the original sector, so the fixed slot's image moved
and its sector was erased.

The fix: `arkrtos_loader_reclaim()` returns 0 immediately when `layout_mode == FIXED`.
In fixed mode a slot address is a promise that it belongs to that slot forever, and
reclaim-move violates it; an early return covers more cases than adding exceptions to
compaction. **Re-verified**: install slot 2 -> `app list` shows `0x080A0000` -> `reboot`
-> still `0x080A0000` and `RUNNING`; installing slot 1 does not disturb slot 2.

## 4. Binary format of the configuration record

Written in the **first 512 bytes** of the CONFIG sector, little endian, no padding.
Defined in `kernelsrc/include/arkrtos_layout_def.h` (UTF-8 + LF); the host tool
`tools/arkrtos_layout.py` is the Python version of the same structure.

### 4.1 Record header

| Offset | Field | Meaning |
|---|---|---|
| 0 | `magic` | `0x47464353`, ASCII `"SCFG"` |
| 4 | `version` | currently `1` |
| 8 | `hw_compat_id` | chip compatibility id: F427 = `0x42700005`, F401 = `0x40100005` |
| 12 | `mode` | 0 = auto, 1 = fixed |
| 16 | `seq` | write sequence, monotonically increasing; decides which write is newer |
| 20 | `slot_count` | valid slot count (meaningful in fixed mode only, max 8) |
| 24 | `flags` | see §4.3 |
| 28 | `reclaim_mode` | see §3.1 |

`hw_compat_id` is the **cross-device** guard: writing an F427 record onto an F401 makes
the kernel reject it with `ARKRTOS_CFG_ERR_HW` instead of erasing somebody's flash at a
wrong address.

### 4.2 Slot table (fixed mode)

`arkrtos_cfg_slot_t slot[8]`, 32 bytes each:

| Offset | Field | Meaning |
|---|---|---|
| 0 | `base` | flash placement (fixed address) |
| 4 | `size` | range length |
| 8 | `type` | 1 = app, 2 = driver |
| 12 | `ram_base` | RAM window base |
| 16 | `ram_size` | RAM window length |
| 20 | `autostart` | start automatically at boot |
| 24 | `flags` | reserved, must be 0 |
| 28 | `reserved` | reserved, must be 0 |

### 4.3 `flags` bits

| Bit | Name | Meaning |
|---|---|---|
| `0x1` | `ARKRTOS_CFG_FLAG_RAW_ALLOW` | allow raw images flashed straight into the pool (development) |

**Unknown bits are rejected** (`ARKRTOS_CFG_ERR_RESERVED`). Treating an unread bit as
0 amounts to guessing the configuration on the device's behalf, and "written in the
configuration region but not honoured" is the hardest class of problem to diagnose.

### 4.4 Runtime parameters

| Offset | Field | Status |
|---|---|---|
| 288 | `log_level` | **effective**: kernel log level |
| 292 | `fault_restart_max` | **effective**: consecutive fault restart limit |
| 296 | `boot_delay_ms` | **effective**: busy-wait this long before autostart (cap `ARKRTOS_CFG_BOOT_DELAY_MAX` = 60000) |
| 300 | `watchdog_ms` | **rejected** (see below) |
| 304 | `heap_size` | **rejected** |
| 308 | `thread_stack_default` | **rejected** |
| 312 | `tool_version` | host tool version that wrote the record, provenance only |
| 316 | `reserved[48]` | reserved, must be 0 |
| 508 | `crc32` | CRC32 over 0..507 (**the crc field itself enters as 0**) |

Why three fields are rejected, recorded so nobody later assumes they were forgotten:

* **`watchdog_ms`**: there is no IWDG port layer. A 128 KB sector erase takes about two
  seconds and cannot feed the dog meanwhile; a watchdog timeout the kernel cannot honour
  is more dangerous than none.
* **`heap_size`**: the POSIX heap is an app-side static arena; the kernel holds no heap.
  An app that wants a bigger heap should declare it in its own project.
* **`thread_stack_default`**: thread stacks are declared by the caller
  (`pthread_attr` or an explicit stack); the kernel has no anonymous stack pool.

Rejecting them now is what makes it safe to implement them later: switching the field
from rejected to accepted will not change the meaning of old records.

### 4.5 Validation

Checked in order; any failure falls back to compile-time defaults as a whole:

| Code | Name | Meaning |
|---|---|---|
| 0 | OK | record valid |
| 1 | `ERR_MAGIC` | not `"SCFG"` (usually a blank sector) |
| 2 | `ERR_VERSION` | unknown version |
| 3 | `ERR_CRC` | CRC mismatch (power lost mid-write) |
| 4 | `ERR_HW` | `hw_compat_id` does not match this device |
| 5 | `ERR_MODE` | `mode` is not 0/1 |
| 6 | `ERR_COUNT` | `slot_count` out of range |
| 7 | `ERR_SLOT_TYPE` | slot type not 1/2 |
| 8 | `ERR_SLOT_RANGE` | slot outside the pool |
| 9 | `ERR_SLOT_SIZE` | illegal slot length |
| 10 | `ERR_SLOT_ALIGN` | slot fails alignment |
| 11 | `ERR_SLOT_OVERLAP` | slots overlap |
| 12 | `ERR_SLOT_RAM` | RAM window outside `SLOT_RAM` |
| 13 | `ERR_SLOT_COUNT_MAX` | more slots than `ARKRTOS_CFG_SLOT_MAX` |
| 14 | `ERR_RECLAIM` | unknown `reclaim_mode` |
| 15 | `ERR_KNOB` | runtime parameter out of range (e.g. `boot_delay_ms` over the cap) |
| 16 | `ERR_NOT_IMPL` | a code path this firmware does not have was requested |
| 17 | `ERR_RESERVED` | reserved field / unknown bit non-zero |
| 18 | `ERR_SLOTS_IN_MODE` | a slot table that must not appear in this mode |

**An invalid configuration is a fallback, not an error**: the kernel boots normally with
the compile-time layout and `cfg show` reports `record : none`.

## 5. Raw images and the development slot table

"Download the app from Keil and set breakpoints" uses a **raw image**: no 256-byte image
header, no CRC - a different format from the installed `.svcapp`.

The scanner cannot infer from a raw image "what type it is and how many sectors it
occupies", so a table must be declared explicitly in section 8 of
`config/arkrtos_partition.h`:

```c
#define ARKRTOS_DEV_SLOT_MAX   (4)
#define ARKRTOS_DEV_SLOT0_UNIT  (0)   /* starting sector unit */
#define ARKRTOS_DEV_SLOT0_UNITS (1)   /* how many sectors */
#define ARKRTOS_DEV_SLOT0_TYPE  (2)   /* 1=app, 2=driver, 0=entry unused */
...
```

F427 factory configuration: slots 0/2 are drivers, 1/3 are apps, one sector each.
`app_demo` flashed at `0x08060000` (pool base + 1 sector = unit 1) therefore hits SLOT1,
its RAM window = `0x20010000 + 1 x 16 KB` = `0x20014000`, matching `RW_IMG 0x20014000`
and `ARM_LIB_STACK 0x20018000` in `build/app_demo.sct` exactly.

### 5.1 Two layers of switch

| Layer | Switch | Effect |
|---|---|---|
| Build time | `APP_ALLOW_RAW_IMAGE` | decides whether this code **is in** the firmware. Release firmware sets it to 0 and only accepts `.svcapp` with a CRC |
| Run time | `RAW_ALLOW` bit in `flags` | decides whether this device **takes** the raw-image bypass |

The two layers are "capability" versus "policy": build-time off means the path does not
exist; build-time on with run-time off means this device goes by signed images.

### 5.2 Claim rules

The kernel claims development slots **only after** the headered-image scan; the order
cannot be reversed: development slots sit at the bottom of the pool, and the installer
also allocates from the bottom, so a "headered image that was installed" can well land
inside a development slot. Claiming first would treat it as a raw image, and its 256-byte
header would never be recognised again.

Three kinds of range are skipped when claiming:

1. the base holds `ARKRTOS_APP_MAGIC` (has a header, leave it to the headered scan);
2. already registered by a headered image (checked at both ends to catch boundary cases);
3. entirely `0xFF` (an empty slot is not an image).

On success the kernel does two things: **binds the RAM window of §2.1**, and sets the
autostart flag per `APP_AUTO_START` / `DRIVER_AUTO_START`.

### 5.3 Raw images do not take part in reclaim

A claimed raw image gets state `ARKRTOS_APP_SLOT_RAW` (value 5), not `LOADED` (value 1).
Compaction and reclaim move only `LOADED`, so raw images are **never moved and never
erased**; `uninstall` also refuses them explicitly (`ARKRTOS_LOADER_ERR_STATE`) - what a
developer flashed into the pool by hand is not something the kernel may decide the extent
of. When the task stops, the kernel reverts it to `RAW` based on "is there a header at the
base", so it cannot become `LOADED` and be moved by the next compaction.

## 6. How to use it

### 6.1 Host writes the configuration

Tool: `tools/arkrtos_layout.py`. It shares `config/arkrtos_partition.h` as the parameter
source, so addresses are never copied by hand.

```bash
# 1) template (fixed mode, slots expanded from the compile-time dev slot table)
python tools/arkrtos_layout.py template --mode fixed \
    --pool-base 0x08060000 --sector 0x20000 > layout.json

# 2) validate (out of range / overlap / sector alignment / RAM window), writes nothing
python tools/arkrtos_layout.py check --config layout.json

# 3) produce the 512-byte record plus one .sct per slot
python tools/arkrtos_layout.py build --config layout.json \
    --bin layout.bin --sct-dir build/fixed_slots

# 4) optionally emit a header fragment for config/arkrtos_partition.h
python tools/arkrtos_layout.py build --config layout.json --emit-header
```

Four subcommands only: `show` (print the compile-time fallback layout), `template`,
`check` (validate, write nothing), `build` (validate and produce). `--config` /
`--header` are optional and default to `config/arkrtos_partition.h` - every difference
between the two boards comes from that header; the tool computes no addresses itself and
does not allow hand-copied ones.

`layout.bin` has two landing paths:

1. a **programmer** writing directly to `CONFIG_BASE` (`0x08040000` on F427). The output
   is the first 512 bytes of the sector, so **the whole sector need not be erased before
   writing** - unless something else was written there before, in which case erase first;
2. **serial in-line write** (`tools/arkrtos_cfg.py`), no board teardown, no programmer
   (§6.3).

The GUI equivalent is `tools/arkrtos_host_gui.py` (§6.6).

### 6.2 On the device

```
cfg show      # effective mode, source, slot table, runtime knobs, record verdict
cfg load      # enter receive state, wait for the host to send the 512-byte record (§6.3)
cfg clear     # erase the CONFIG sector, fall back to compile-time defaults
```

> **`cfg load` does not mean "read the configuration again"**. The configuration region
> is read at boot; to re-read it, reboot. `cfg load` means **receive**: it prints a ready
> line, enters a receive loop, assembles 4 x 128 bytes from the host into one record,
> writes it to CONFIG only after validation, and answers the verdict with a flow-control
> byte (`0x06` continue / `0x15` stop). Typing `cfg load` by hand just waits 5 s and
> prints `cfg load: timed out waiting for the record`.

Typical `cfg show` output (AUTO, no record):

```
layout    : auto (source: compile-time default)
config    : 0x08040000 +128K, 256 record(s) per sector
reclaim   : global
knobs     : log 3 (record 0), restart max 3
boot      : hold 0 ms before autostart, raw images refused
record    : none, compile-time default in use
```

Typical `cfg show` output (FIXED, record from the configuration region with a slot table):

```
layout    : fixed (source: device config region)
config    : 0x08040000 +128K, 256 record(s) per sector
reclaim   : none
knobs     : log 3 (record 0), restart max 3
boot      : hold 0 ms before autostart, raw images refused
record    : accepted

slot  type  base        size     ram         auto
 0    app   0x08060000  131072   0x20010000  1
 1    drv   0x08080000  131072   0x20011000  1
```

`source` has exactly two values: `compile-time default` (no valid record, or a record
that failed validation) and `device config region`. In FIXED mode `reclaim` is always
`none` - fixed slots never compact, so reclaim strength is meaningless.

### 6.3 Serial in-line configuration write (`tools/arkrtos_cfg.py`)

```bash
python tools/arkrtos_cfg.py show  --port COM3
python tools/arkrtos_cfg.py write --port COM3 --config layout.json
python tools/arkrtos_cfg.py clear --port COM3
```

The 512-byte record exceeds the shell line buffer (128 bytes), so it goes as binary
chunks, not command-line arguments: 4 chunks x 128 bytes, the device answers each with a
flow-control byte, and **the flow-control byte of the last chunk is the verdict**. On
rejection the device first prints the reason line on the same serial port (`bad magic` /
`bad crc`) and the tool **relays it verbatim** rather than guessing.

Three protocol rules must hold; breaking any of them yields "the device received 512
bytes but says `bad magic`", a symptom pointing in the wrong direction:

| Rule | Why |
|---|---|
| End the command with **CR** (`cfg load\r`), not CRLF | the shell splits lines on CR; the extra LF of CRLF stays in the receive FIFO and shifts the whole record by one byte |
| The device flushes the receive FIFO **before** printing the ready line | the leftover byte must be dropped there; reversing the order swallows the first chunk the host sends right after seeing the ready line |
| The host waits for the **whole banner** (or a period of silence) before the first chunk | the device still prints two lines after `ready`; keying on `ready` alone lands in the most dangerous window |

Reading a failure: **suspect the start of the stream before the content**. A record
shifted by one byte and a record with entirely wrong content look identical on the device
side - both can only be reported by the final magic check.

### 6.4 Scope of effect and reboot

After `cfg load` / `cfg clear` the device asks for a reboot. That is not caution: the
record holds **layout policy and runtime knobs**:

| Takes effect | Items |
|---|---|
| immediately | log level (`arkrtos_log_set_level` is called on the spot) |
| only after reboot | install mode (`fixed`/`auto`), slot table, reclaim strength, partition geometry, RAM windows |

The pool scan and image start have already run early in boot under the then-current
layout. Change the policy without rebooting and the device sits in a split state -
`cfg show` reports the new layout while the load path follows the old one - so **images
land where you do not expect**.

### 6.5 Hardware acceptance (F427)

* `write` (4 x 128 chunks) -> `cfg load: ok, record N`; read back `source: device config
  region`, `reclaim minimal`, `knobs log 4 / restart max 5`;
* a bad-CRC record is rejected with the real reason `bad crc`, and the **existing valid
  record is unaffected**;
* after writing a `fixed` record and rebooting: `cfg show` says `fixed`, `pool` lists the
  two fixed slots from the record, and a direct read of the shared partition table shows
  `layout_mode = 1` (`0x20000000 + 52`, u32 little endian) consistently;
* after `clear`: back to `auto (source: compile-time default)`, `record : none`.

> **One state, one source of truth.** The authoritative copy of the layout is the
> **shared partition table** (`arkrtos_layout_init()` adopts the record and `publish()`es
> it); the loader reads that for its `FIXED` decision. The pool scan once used
> `arkrtos_ptable_init()`, which cleared the slot table and re-seeded the whole table with
> compile-time defaults, so "the record says fixed but the load path runs auto" - and the
> query command read the layout module's own state, so everything looked fine. Now the
> scan calls `arkrtos_ptable_clear_slots()` only. When touching this area keep the line:
> **do not reset "one class of records" by "re-seeding the whole table"**.

### 6.6 Host GUI

```bash
python tools/arkrtos_host_gui.py            # needs pyserial; tkinter ships with Python
```

Four tabs: **connect** (scan ports, open/close), **console** (type shell commands, see
echo), **install** (pick a `.svcapp`, watch progress and verdict), **layout** (`show` /
`write` / `clear` and template generation).

### 6.7 Recommended combination for customer development

```
mode          = fixed
slot[0..3]    = the development slot table from section 8 of config
flags         = RAW_ALLOW
boot_delay_ms = 0 (or a few hundred ms to let a debugger attach)
```

The customer gets a board where "every slot address is fixed, code can be flashed at
those addresses from Keil directly, and breakpoints work right after". Release firmware
instead sets `mode = auto`, clears `flags`, and accepts only `.svcapp` with a CRC.
