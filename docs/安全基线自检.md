# 安全基线自检（`sec` 命令）

## 1. 这份文档回答什么

- 这块板子**现在这套构建**，按安全基线该有的机制，哪些真的在、哪些不在了？
- 为什么有的项报 `SKIP` 而不是 `PASS`？
- `FINDING` 与 `FAIL` 的分界线在哪，谁能拿它当证据、不能拿它当什么证据？

配套文档：[安全认证准备](安全认证准备.md)（资产、威胁模型、标准差距表）、
[内存保护与App越权验证](内存保护与App越权验证.md) §5（已知边界）。

一句话定位：**`sec` 是"这套构建还是不是你以为了那套"的自检，不是合规声明，也不是渗透测试。**

## 2. 四档结论

| 档 | 含义 | 谁能用 |
|---|---|---|
| `PASS` | 基线要求如此，实测如此 | 可以作为"该项在本构建上成立"的证据 |
| `FAIL` | 基线要求如此，实测不如此 | 硬失败：配置和你想的不一样，先修再说 |
| `FIND` | 已知缺口：功能没做 / 没编进来 | 设备没坏，但认证清单要按缺口登记；**不计入 PASS** |
| `SKIP` | 这套构建里没有可走的路去证实 | 必须把原因写出来（格式串就是原因） |

为什么 `FINDING` 与 `SKIP` 必须分开：前者是"我们确实没做这件事"，
后者是"我们没有一条通路去看这件事做没做"。混成一档就会出现
"12 项全过"这种把缺口藏进总数的结论。

为什么没有 `WARN`：自检没有"建议"。要么基线要求（PASS/FAIL），要么登记缺口
（FIND），要么看不见（SKIP）。

## 3. 十二条检查

顺序即输出顺序，名字稳定、机器可读。

| # | 名字 | 问什么 | 判定 |
|---|---|---|---|
| 1 | `gates.kernel` | MPU / 特权剥离 / 栈检查 / 故障恢复 / 崩溃台账 / 结构审计 六项开关是否都编进来 | 六位全在 → PASS；缺任一位 → FAIL。签名与遗言单独报值（`sign/hwsafe=0xN`），不重复计分 |
| 2 | `mpu.slot_windows` | 每个非空槽位有没有 RAM 窗口 | 有槽没有窗口 → FAIL（没窗口 = 隔离这句话空转） |
| 3 | `structures.audit` | 分区表 / 槽位 / 任务表 / 调度链是否自洽 | `arkrtos_audit_run()` 的 mask 为 0 → PASS；否则 FAIL 并给首个越界下标 |
| 4 | `images.headers` | 池里每个镜像的头是否仍然成立 | 魔数 + `arkrtos_loader_check_header()`（字段、重定位表编码、条目对齐与升序）全过 → PASS；否则 FAIL 并给首个坏槽与错误码 |
| 5 | `images.crc_recheck` | 开机复核镜像 CRC | **永远 SKIP**：Flash 上躺的是打过重定位补丁的字节，头里的 `crc32` 是对标称形态算的，硬算会假失败 |
| 6 | `images.signature` | 镜像签名是否强制 | `ARKRTOS_USE_IMAGE_SIGN==1` → PASS；否则 FIND（任何拿到串口的人都能装自己的代码） |
| 7 | `hwsafe.deadman` | 崩溃/被杀之后有没有人把设备带回安全态 | `ARKRTOS_HW_SAFE==1` → PASS 并报 `devs/owners/will/cb`；否则 FIND |
| 8 | `guard.watchdog` | 看门狗是不是真的在咬人 | 守护 + `ARKRTOS_WDG_ENABLE` 都在 → PASS；只有守护 → FIND（"挂死的任务不会被复位"） |
| 9 | `crash.journal` | 跨复位的崩溃历史还在不在 | `boots!=0` → PASS 并报 `boots/seq/held_slots`；`boots==0`（magic/校验不过被重开）→ **FAIL** |
| 10 | `console.auth` | 控制台有没有认证 | 恒定 FIND：串口可达即 `install` / `reboot` / `stop` |
| 11 | `flash.protection` | Flash 读保护 / 写保护等级 | **永远 SKIP**：内核没有读选项字节的 HAL 通路，要用调试器读 RDP/WRP |
| 12 | `rt.measured` | 实时性有没有实测读数 | 计数器活着且 `rt` 有样本 → PASS 并报 `tick.isr max` 与每拍周期数；未编入或计数器没跑 → SKIP |

`arkrtos_sec_run()` 的返回值是 **FAIL 的条数**（0 = 没有硬失败），`FINDING` 不计入。

## 4. F427 上板实测（2026-11-12）

构建：`Code=219426 RO=19198 RW=896 ZI=120852`，96 MHz / 2 kHz 节拍，
`ARKRTOS_USE_SECCHECK=1`。串口 `sec` 的逐字输出：

```
sec: 12 checks - pass 8, fail 0, finding 2, skip 2
  [PASS] gates.kernel       mpu/priv/stk/fault/crash/audit bits=0xBF (need 0x3F), sign/hwsafe=0x2
  [PASS] mpu.slot_windows   slots=2 without_window=0 first=0
  [PASS] structures.audit   checks=32 mask=0x0 first_index=0
  [PASS] images.headers     slots=2 bad=0 first=0 err=0
  [SKIP] images.crc_recheck flash holds relocated bytes; header crc32 covers the nominal form
  [FIND] images.signature   not compiled (ARKRTOS_USE_IMAGE_SIGN=0): unsigned images are accepted
  [PASS] hwsafe.deadman     devs=3 owners=3 will/cb=0/0
  [PASS] guard.watchdog     kernel guard + board watchdog both active
  [PASS] crash.journal      boots=2 seq=7 held_slots=1
  [FIND] console.auth       shell has no authentication: serial access = install/reboot/stop
  [SKIP] flash.protection   no HAL path to option bytes: read RDP/WRP with a debug probe
  [PASS] rt.measured        tick.isr max=76 us over 25591 samples, 48000 cyc/tick
verdict: no hard failure (FINDING = known gap, SKIP = no path to see it)
```

读法：

- `bits=0xBF`：`0x3F` 六位全在，另加 bit7（`HW_SAFE`）；`sign/hwsafe=0x2` 说明
  签名位（bit6）为 0、遗言位被置上——与构建选项一致，不是猜的。
- `held_slots=1`：`HWSAFE_DEMO` 上次崩到上限后被禁用，台账跨复位保持住了
  （这正是 `90f8d2d` 修的那条缺陷，`sec` 现在每次开机都会复述）。
- `hwsafe ... will/cb=0/0`：本开次还没有 App 死过，所以两条通道的累计计数都是 0；
  它是"本次开机以来"的读数，不是历史总数。
- `rt.measured` 的 `76 us` 与 `rt show` 的 `tick.isr MAX` 同一来源：先跑 `sec`
  时只有 7999 个样本（当时最大 29 µs），随后跑出 76 µs，再跑 `sec` 复述的就是 76 µs。
  两处读数一致 ⇒ 该行不是另算的一套数。
- `first_index=0`：`mask==0` 时下标无意义，显式打 0 而不是 `4294967295`。

## 5. 怎么用

```
sec                 # 全部 12 项
sec pass|fail       # 只看某一档（find / finding 同义）
sec skip            # 只看"看不见"的项及原因
```

- 只读：不改任何结构、不装任何策略、不"顺手修好"。修好会让下一次自检失去证据。
- 报告结构 `arkrtos_sec_report_t` 在 shell 里是 `static`，**不放栈上**（内核任务栈不宽裕）。
- 内核里没有第二套 `snprintf`：自检项只给格式串与最多 4 个整数，由 shell 格式化。

## 6. 三条边界（别把 `sec` 读超）

1. **`sec` 不测攻击，只测"机制在不在"。** 越权拦截要由 App 去打
   （`APP_DEMO` 的 78 项自检、`APP_BAD` 的故意越权、`HWSAFE_DEMO` 的崩溃通道），
   命令末尾那行 `note:` 写的就是这件事。
2. **`FINDING` 不是"轻微问题"。** `console.auth` 与 `images.signature` 都是
   认证清单上的硬缺口，只是它们不是设备坏了，所以单独一档。
3. **`SKIP` 不等于合格。** `images.crc_recheck` 与 `flash.protection` 都写清了
   "为什么看不见"。要把它们变成 PASS，得先造出通路（重定位反算 / 选项字节读取），
   那是代码工作量，不是改判据。

## 7. 开关与体积

| 项 | 值 |
|---|---|
| 开关 | `ARKRTOS_USE_SECCHECK`（默认 0），`config/kconfig/Kconfig.features` 里 `depends on SHELL_ENABLE` |
| 默认关时 | `arkrtos_sec.c` 整个文件的实体在 `#if` 内，shell 命令表与 `need` 预算都不变：**体积与行为零变化** |
| F427 打开后 | `Code 217370 → 219426`（**+2056 B**），RO/RW/ZI 不变 |
| 命令表预算 | `register_kernel_commands()` 的 `need` 加 1，仍远小于 `ARK_SHELL_MAX_COMMANDS=56` |
