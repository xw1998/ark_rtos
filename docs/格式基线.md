# 格式基线：四条能被机器判的规则

> 一句话：没有 clang-format 也能有一条**真的会红**的格式基线 —— 只判"纯字节、改起来不需要重排版"的四条，其余交给 `.editorconfig` 当编辑器约定。

## 1. 为什么只四条

旧欠账是「无 `.clang-format`、无 `.editorconfig`、无提交前钩子，风格全靠人」。照抄现成做法在这里有两条硬障碍：

1. **这台机器没有 clang-format，网络也不通**（装不上）。
2. 仓库里 **UTF-8 与 GBK 并存**（`kernelsrc/src` + `include` 共 99 个文件：UTF-8 77 / GBK 22）。任何"整文件重排版"的工具都会顺手把 GBK 字节改坏，与「GBK 走字节级补丁、严禁转码」的约定直接冲突。

所以这里不做格式化，只钉住四条**不需要读懂代码、也不需要重新排版**的规则：

| 编号 | 规则 | 判据 |
|---|---|---|
| F1 | `.c/.h` 里没有制表符 | 行内不出现 `0x09` |
| F2 | 没有行尾空白 | 剥掉行尾 `\r` 后，行末不许留空格或制表符 |
| F3 | 文件以换行结尾 | 最后一个字节是 `\n` |
| F4 | 没有 UTF-8 BOM | 开头不是 `EF BB BF` |

四条都是纯字节判断：不解码、不转码、不碰换行风格，所以对 22 个 GBK 旧文件同样成立；改起来也只是删几个字节，不会触发整文件重写。

**刻意不管的事**（写清楚，别让人以为"格式已经统一了"）：

* 换行风格（CRLF / LF）不在这里判 —— 它由 `tools/ci_gate.py` 的 `encoding` / `mixed-eol` 两项负责，而那两项的口径是「**一个文件内部不许混**」，不是「全仓统一成一种」。
* 缩进宽度（4 空格）只是 `.editorconfig` 的编辑器约定，没有门禁：本机没有能安全重排 GBK 文件的格式化器，判了也只能报红不能改。
* 长行（>120 列）只由编辑器提示，不进判据：实测自研代码有 26 个文件超 120 列，多数是字符串表与注释，收进判据会逼人为了过门禁去截断可读的文案。

## 2. 谁被判、谁豁免

被判：`kernelsrc/` `board/` `config/` `example/` 下**已入库**的 `.c/.h`，以及 `.s/.S`（汇编只受 F2/F3/F4 管，F1 豁免 —— 制表符在 `kernelsrc/port/arm/*/arkrtos_context.S` 里是列对齐惯例）。

豁免（判据的一部分，不是补丁）：

```
kernelsrc/components/lwip/            third-party
kernelsrc/components/cm_backtrace/    third-party
kernelsrc/components/nr_micro_shell/  third-party
kernelsrc/components/arkc/            vendored（tools/sync_arkc.py 一字节对不上就红）
kernelsrc/components/arkvim/          vendored
kernelsrc/components/ark_softbus/     vendored（tools/sync_ark_softbus.py）
kernelsrc/fs/littlefs/                third-party
docs/.gen_utf8/                       生成的 utf8 副本
/Drivers/ /CMSIS/ /Middlewares/ /RTE/ /ARKRTOS_TEST/   ST 官方工程树
```

这些树的空白属于上游，改它们等于制造下一次同步冲突。

## 3. 怎么跑

```bash
py -3 tools/format_gate.py            # 先自检，再扫全仓；0 = 全过
py -3 tools/format_gate.py --list 40  # 违规明细最多列 40 条
py -3 tools/format_gate.py --selfcheck
```

它已接进 `ci_gate`（`format` 项，`ci_gate` 由 44 项变 **45 项**），所以 `py -3 tools/ci_gate.py` 会连带跑。

**自检（变异自检）是这项门禁的一半**：六个喂了毒的临时文件分别撞 F1/F2/F3/F4，一个干净对照、一个汇编对照（制表符必须放行），外加一条豁免表断言（`kernelsrc/components/lwip/src/core/tcp.c` 必须被判为豁免、`kernelsrc/src/arkrtos_task.c` 必须不被豁免）。任一条不符 → 退出码 2、`FORMAT-GATE selfcheck FAIL`，此时**绝不报"0 违规"**。理由很直白：走错目录、后缀写错、豁免表写宽了，都会让一个只会打印的门禁永远绿。

## 4. 它抓到的第一件真事：1143 行 `\r\r\n`

首次扫描（2026-11-17）报出 **2 个文件、1144 处**行尾空白，全部是同一个形态：行尾是 `\r\r\n`（多一个 CR），不是空格。

| 文件 | 行数 | 位置 |
|---|---|---|
| `kernelsrc/src/arkrtos_task.c` | 1143 | 第 555–2029 行 |
| `kernelsrc/include/arkrtos_shell.h` | 1 | 第 43 行 |

### 4.1 它不是"看起来脏"，它改坏了 `__LINE__`

多出来的那个 CR 在编译器眼里是**一个换行**。于是 `__LINE__` 从第 555 行往后整体偏移，偏移量正好等于它前面出现过的 `\r\r\n` 行数。取证（同一函数、同一地址、两棵树同参数编译）：

```
$ loongarch64-newlib-elf-objdump -d --start-address=0x216be0 --stop-address=0x216bf8 ...
# 修前（HEAD）  216be8: 03aab? -> lu12i.w $r6,1 / ori $r6,$r6,0x2ab   => line = 0x12ab = 4779
# 修后（工作区）216be4:              ori     $r6,$r0,0xe34            => line = 0x0e34 = 3636
```

4779 − 3636 = **1143**，正是该文件被修掉的多余 CR 数。而 `arkrtos_task.c` 全文只有 3919 行，**4779 这个行号在文件里根本不存在** —— 也就是说修之前，凡是从这个文件打出来的日志（`ARKRTOS_LOGI/W/E` 的 `line` 字段）与调试行号表，全都指向不存在的行。日志里最值钱的一列（在哪一行）在那 1143 行范围内是错的。

### 4.2 修法与证据

纯字节操作：`raw.replace(b"\r\r\n", b"\r\n")`，断言「被删字节数 == 命中数」+「去掉所有 CR 后两版逐字节相同」+「换行数不变」+「解码结果不变（GBK 仍是 GBK）」。

| 读数 | 值 |
|---|---|
| 改动行数 | 3919 → 3919（`git diff --numstat`：1146 / 1146，另 `arkrtos_shell.h` 1 / 1） |
| 默认档体积 | `text 367264 / data 440 / bss 767508`（修前修后**完全相同**） |
| 默认档镜像 sha256 | HEAD 树 `3a6c4ba7d84d1b0be333e3e2dd54e0f228a5f00e5ea544bc31af535c4da1c3a0` → 修后 `8f71a10f8684f61470aa820710469284076593f8a8634f31d872b8e22476a738` |
| 差异规模 | **58 字节**，集中在 `arkrtos_task_kill_internal` 一处 `log_emit` 的 `line` 常量与相邻 4 字节 |
| QEMU LA64 实跑 | `help` / `info` / `sched`（consistent）/ `utest run`（0 failed）全过 |

**这不是"零变化"**：镜像确实变了 58 字节，变的是 `__LINE__` 常量本身 —— 那是修复的内容，不是副作用。体积一位不变、行为路径不变，跑起来的输出只在日志行号上不同（而且从"不存在的行"变成"真实的行"）。

### 4.3 顺带钉住的两个 `.gitattributes` 例外

这两个文件是**全仓仅有的 index blob 为 CRLF 的两个**（其余 2093 个 `.c/.h` 的 blob 是 LF，工作区因 `core.autocrlf=true` 检出为 CRLF）。不处理的话，`git add` 会把它们整篇改写成 LF —— 一次删 3919 行、加 3919 行，而真正的改动（去掉 1143 个 CR）反而看不见。所以 `.gitattributes` 里给这两个文件写了 `-text`：

```
kernelsrc/src/arkrtos_task.c      -text
kernelsrc/include/arkrtos_shell.h -text
```

`.gitattributes` **刻意不写** `* text=auto` 或任何 `eol=`：本仓库 CRLF/LF 混杂是刻意的（GBK 旧文件在工作区就是 LF），任何全树 `eol=` 规则都会改写一半文件、制造几万行不可审 diff。单个文件内部不许混行尾，由 `ci_gate` 的 `mixed-eol` 项负责。

## 5. `.editorconfig` 写的是什么

`.editorconfig` 声明的是**编辑器行为**：4 空格缩进、删行尾空白、文件末补换行、120 列提示；`*.{s,S}` 与 `Makefile` / `*.mk` 用制表符（那里制表符是语法）；`*.md` 关掉「删行尾空白」（行末两个空格是硬换行）；`*.{yml,yaml,json}` 两空格。

不写 `charset`：仓库里 UTF-8 与 GBK 并存，任何全局 `charset = utf-8` 都会诱导编辑器把 GBK 旧文件转码 —— 那正是本项目最不能出的事。编码口径由 `ci_gate` 的 `encoding` 项按"能解成 UTF-8 就是 UTF-8，否则 GBK"判。

## 6. 加一条新规则的顺序

1. 先在 `tools/format_gate.py` 里写判据 + **喂毒的变异自检**；
2. 跑一遍全仓，确认违规数是你愿意改完的数字（否则先把违规清到 0 再进门禁，别让门禁一上线就红）；
3. 才写进 `.editorconfig` 与本文档的表格；
4. `git add` 后跑 `py -3 tools/ci_gate.py`（45 项）。

顺序不能反：先写文档再写判据，等于又回到"风格靠人"。

## 7. 边界（不许读成什么）

* 不是"格式已统一"：只管四条，缩进宽度、长行、注释风格、命名都还没管。
* 不是"静态分析"：那是 `warn_gate.py`（`-Wall -Wextra -Wshadow`）的事，且后者也只是编译器语义分析这一档。
* 不声称"GBK 文件已被格式化"：F1–F4 只是改几个字节。
* 汇编、Makefile、markdown 的空白习惯不在本门禁判据内。
