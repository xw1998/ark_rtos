# 安全认证准备：资产、威胁模型、标准差距与缺口寄存器

## 1. 这份文档是什么，不是什么

**是**：把 Ark RTOS 现在的安全能力摊开成一张可核对的表——资产在哪、信任边界在哪、
每个威胁今天被什么挡住、每条标准要求对应到"已具备 / 需配置 / 未实现"、
每个缺口谁负责、修它要动什么。所有"已具备"都能在板上用 `sec` 或例程复现。

**不是**：合规声明。本文列出的任何标准都**只做差距对照，不做符合性结论**。
真正的符合性结论只能由认可的实验室按标准原文出具，且必须以冻结的版本、
配置清单和测试报告为输入。

## 2. 资产（要被保护的东西）

| ID | 资产 | 位置 | 谁改了会出事 |
|---|---|---|---|
| A1 | 内核代码与常量 | Flash 0x08000000 起，只读 | 改了 = 整机行为不可信 |
| A2 | 镜像池（App / 驱动镜像） | Flash 统一镜像池 | 换了镜像 = 换掉应用逻辑 |
| A3 | 配置区记录 | Flash `0x08040000 + 128K`，双记录 + CRC | 改了 = 槽位映射/启动项被改 |
| A4 | 分区表（运行期共享窗口） | RAM，内核与 App 共享 | 改了 = App 看到的世界变形 |
| A5 | App 私有 RAM（代码段/数据/栈） | RAM 伙伴分配块，MPU 逐任务窗口 | 越界读 = 泄露，越界写 = 劫持 |
| A6 | 崩溃台账 | RAM `.noinit`，跨复位保持 | 清了 = 崩溃上限失效（可无限重试） |
| A7 | 故障环（最近 fault 记录） | RAM，复位即清 | 清了 = 现场证据丢失 |
| A8 | 硬件输出（LED/继电器/雷达等） | 板上设备 | 崩溃后停在"开"= 物理危险 |
| A9 | 控制台（串口 shell） | UART，115200 | 可 install / reboot / stop |
| A10 | 软总线 / 网络链路 | 板内 + 以太网 | 伪造节点 / 重放 / 中间人 |
| A11 | 时间基准（节拍、周期计数） | SysTick / DWT | 看门狗窗口、超时语义被绕过 |

## 3. 信任边界

1. **特权 / 非特权**：内核任务与驱动框架以特权态运行；App 以非特权态运行，
   受 MPU 窗口约束。这条边界由硬件强制，是唯一一条"App 绕不过去"的边界。
2. **安装期 / 运行期**：安装期内核会做整镜像 CRC、版本单调、`image_id` 去重，
   并按需验签；运行期的 `arkrtos_loader_accept` 只校验头。**安装期是唯一强校验窗口。**
3. **复位前 / 复位后**：RAM 内容复位即失；`.noinit` 跨复位保持（崩溃台账）；
   Flash 永久。三类存储的"可信度"不同，安全上不能混用。
4. **板内 / 板外**：串口与网络是外部可达面；软总线把板内节点也当"对端"处理
   （默认关闭的帧认证 / 载荷加密 / 防重放窗口）。
5. **受信输入 / 不受信输入**：镜像文件、串口命令行、软总线帧、网络报文、设备返回值
   全部视为不受信；内核自己的编译期常量视为受信。

## 4. 威胁模型（STRIDE，按信任边界列）

| 威胁 | 具体形态 | 现有缓解 | 状态 |
|---|---|---|---|
| **S**poofing | 串口上伪装成运维人员 | 无 | **未实现**（SEC-G01） |
| S | 用别人的 `image_id`/版本号装一个自制镜像 | 安装期 `image_id + version + size + crc` 去重；**无签名时全部可伪造** | 需配置（SEC-G02） |
| S | 软总线上伪装节点 | 帧认证（截断 HMAC-SHA256）＋ PSK 握手（X25519 + HKDF），默认关 | 已具备（需配置） |
| **T**ampering | App 直接写镜像池 / 配置区 | MPU ROM 窗口只读；配置区只经内核 SVC 写 | 已具备 |
| T | App 改分区表（共享窗口可写） | 无（见 §5 边界 2） | **未实现**（SEC-G03） |
| T | 掉电/中断打断安装，留下半截镜像 | 安装期写 `INSTALLING` 状态 + 复位后按 CRC 判 INVALID | 已具备 |
| T | Flash 被读保护关掉后整片 dump | 能读出 RDP/WRP 了（2026-11-13，`sec` 的 `flash.protection` 从 SKIP 变 FIND），但 RDP **设置**仍缺、还要产线写选项字节 | **半实现**（SEC-G04：读=已做，设置=未实现） |
| **R**epudiation | 装了什么、崩了什么查不到 | 崩溃台账（跨复位）+ 故障环（复位即清）+ `audit` 结构不变式 | 部分（SEC-G05） |
| **I**nformation disclosure | 非特权任务读内核/别的 App 内存 | MPU 逐任务窗口 + 特权剥离 | 已具备（上板 78 项自检） |
| I | 串口/网络侧信道 | 无认证、无加密（软总线载荷加密默认关） | 部分（SEC-G06） |
| **D**enial of service | App 崩溃后无限重启占满 CPU | 崩溃上限（默认 3 次）跨复位保持，超限置 INVALID 且不自启 | 已具备（`90f8d2d`） |
| D | 任务挂死，系统假活 | 内核守护 + 板级看门狗 | 已具备（需 `ARKRTOS_WDG_ENABLE`） |
| D | 内存/句柄耗尽 | 统一池 + 伙伴分配 + 固定块池 | 已具备（无配额上限，SEC-G07） |
| **E**levation of privilege | App 通过 SVC 参数越权 | SVC 入口逐参数校验 + 句柄校验 | 已具备 |
| E | App 注册的 shell 回调在特权态执行 App 代码 | 无（见 §5 边界 3） | **未实现**（SEC-G08） |
| E | 运行期 `loader_accept` 收下未校验负载 | 只信安装期（见 §5 边界 4） | 设计取舍（SEC-G09） |
| E | 签名机制是**对称**预共享密钥，设备端持有密钥即可伪造镜像 | `arkrtos_sign.h` 文件头已写明局限 | 需改造（SEC-G10） |

## 5. 与既有文档对齐：五条已知边界（不重复造词）

1. 只约束非特权任务；内核任务不受 MPU 限制——设计如此。
2. 共享窗口（分区表 + 崩溃日志）对 App 仍可写。
3. App 注册的 shell 回调在特权上下文执行 App 代码。
4. `arkrtos_loader_accept` 不校验负载 CRC / 签名（安装期校验，运行期不校验）。
5. 故障环复位后清空；跨复位崩溃计数由 `.noinit` 台账承担。

## 7. 缺口寄存器

严重度：**H** = 可被外部直接利用或使安全功能失效；**M** = 需前置条件或影响有限；**L** = 记录项。

| ID | 缺口 | 严重度 | 影响 | 修补形态（代价） | 状态 |
|---|---|---|---|---|---|
| SEC-G01 | 控制台无认证 | H | 串口可达 = 装/停/重启任意镜像 | shell 登录 + 口令派生密钥（中） | 未实现 |
| SEC-G02 | 无签名时镜像可伪造 | H | 任何拿到串口/文件系统的人都能换 App | 打开 `ARKRTOS_USE_IMAGE_SIGN`（配置） | 需配置 |
| SEC-G03 | 共享窗口对 App 可写 | M | 可篡改分区表视图 | 拆只读窗口 + SVC 代写（高） | 未实现 |
| SEC-G04 | 无 RDP/WRP 设置与读取 | H | Flash 可被整片 dump / 改写 | ① **读取已做**（板级 `arkrtos_port_flash_protection()` + 弱符号兜底，2026-11-13 上板验证，见 `安全基线自检.md` §4）② RDP/WRP **设置**仍缺：选项字节解锁/擦写/复位，且 RDP 0→1 不可逆，需产线配合 | 半实现（读=FIND 已生效，设置=未实现） |
| SEC-G05 | 无持久审计日志 | M | 事后无法溯源 | 审计环形日志落 Flash（中） | 未实现 |
| SEC-G06 | 串口/网络无加密 | M | 侧信道与重放 | 复用软总线加密（中） | 部分 |
| SEC-G07 | 无每 App 资源配额 | M | 一个 App 可耗尽池 | 配额字段 + 分配检查（低） | 未实现 |
| SEC-G08 | shell 回调在特权态跑 App 代码 | H | 提权 | SVC 蹦床 + 非特权栈（高） | 未实现 |
| SEC-G09 | 运行期 `loader_accept` 不校验负载 | M | 只影响运行期装载路径的信任假设 | 与安装期共用校验（中） | 设计取舍 |
| SEC-G10 | 签名是对称密钥 | H | 设备被逆向即得签名能力 | 改非对称（Ed25519/ECDSA）+ 设备只存公钥（高） | 未实现 |
| SEC-G11 | 无显式回滚策略 | M | 版本单调能防降级，但也挡住"回滚到已知良好版本" | 回滚白名单/计数器（中） | 未实现 |
| SEC-G12 | 无信任根 / 安全启动链 / 证明 | H | PSA L2+ 的必要条件 | BootROM → 内核 → 镜像的验签链（高，依赖芯片） | 未实现 |
| SEC-G13 | 无设备身份 | M | 无法做设备级认证 | 一机一密或一机一证书（中，需产线） | 未实现 |
| SEC-G14 | 无 RAM/Flash/时钟自检 | M | 61508 诊断覆盖率不足 | 启动自检 + 运行期巡检（中） | 部分 |
| SEC-G15 | 无 WCET 分析 | M | 无法证明最坏响应时间 | 静态分析 + 硬件追踪（高） | 未实现 |
| SEC-G16 | 故障注入与篡改检测无 | L | 物理攻击面 | 电压/时钟监测、看门狗外部化（高） | 未实现 |
| SEC-G17 | 镜像 CRC 开机不复核 | L | 静默损坏只能靠安装期拦 | 重定位反算标称形态后复核（中） | 未实现（`sec` 报 SKIP） |

## 8. 现在就能做的本地安全测试（不依赖实验室）

| # | 用例 | 做法 | 期望 |
|---|---|---|---|
| T1 | 基线自检 | `sec` | 8 PASS / 0 FAIL / 2 FIND / 2 SKIP（本文 §2 快照） |
| T2 | 结构不变式回归 | `audit` + `utest run` | mask=0；9/9 用例通过 |
| T3 | 非特权越权拦截 | 装 `APP_DEMO` 跑自检；装 `APP_BAD` 故意越权 | `pass=78 fail=0`；越权访问触发 MEMFAULT |
| T4 | 崩溃隔离与硬件回安全态 | 装 `HWSAFE_DEMO` 连崩 3 次 | `held=crash-limit`、LED 回灭、跨复位保持 |
| T5 | 崩溃上限跨复位 | 上一步后 `reboot`，观察是否再自启 | 不自启；`sec` 报 `held_slots>=1` |
| T6 | 镜像完整性 | 手工把 `.svcapp` 改一个字节后 `app install`（**已做**，2026-11-12） | 安装期 CRC 拒绝：`transfer crc: hdr .. rel .. end 0x3F3570ED want 0x4832407B` → `INSTALL:262 rejected: err -5`，`fault` 记 `INSTALLFAIL`，槽位表不变 |
| T7 | 版本防回滚 | 装高版本再装低版本 | 拒绝（版本单调） |
| T8 | 固定槽落点 | `app install <path> <slot>` 后 `reboot` | 仍在原地址（`90f8d2d` 修） |
| T9 | 安装期断电 | 安装中途断电，重启 | 槽位判 INVALID，可重装 |
| T10 | 看门狗 | 用调试器停掉 SysTick（`write32 0xE000E010 0x00000004`），喂狗链断掉、`arkrtos_guard_tick()` 不再运行（**已做**，2026-11-12） | 复位：停 8 s 后 `RCC_CSR(0x40023874)=0x2E000003`（bit29 `IWDGRSTF=1`，清标志前读过 `0x03000000`）、`0xE000E010` 从写入的 `00010004` 回到固件重配的 `00010007`、`crash` 的 `boots` 1→2 且槽 0 的 `faults=3 / held=crash-limit` 跨复位保持 |

T1–T9、T11 已在 F427 上做过并留了读数（T6 的读数见上表，T1–T5/T7–T9/T11 见各文档的上板验证表）。

最初始的 T1 快照是默认档（8 PASS / 2 FIND / 2 SKIP）；打开签名后同一个 `sec`
变成 9 PASS / 1 FIND / 2 SKIP——差的正是 `images.signature` 那一行。

**T10 怎么做出来的（不留后门）**：不在产品固件里加"停止喂狗"的命令（认证角度看就是后门），
而是让调试器把 SysTick 的 `ENABLE` 位清掉：tick 中断不进 → `arkrtos_kernel_tick_body()`
不跑 → `arkrtos_guard_tick()` 不喂狗。复位源一律读 `RCC_CSR`（硬件位），不靠串口是否吐 banner
——`pyocd` 每次开会话都会复位目标，靠串口判复位会得出假结论。

**T12 怎么做出来的（密钥不入库）**：

1. 密钥头文件 `arkrtos_sign_key_local.h` 放在工程 `Core/Inc`（已在 IncludePath 里），只写一行
   `#define ARKRTOS_IMAGE_SIGN_KEY { 0x.., ... }`；文件名被 `.gitignore` 的 `*_sign_key_local.h` 挡在库外。
2. 内核侧用**无引号开关**打开这条通道：`-DARKRTOS_SIGN_KEY_LOCAL=1`，
   `arkrtos_features.h` 里 `#if defined(ARKRTOS_SIGN_KEY_LOCAL) → #include "arkrtos_sign_key_local.h"`。
   **不要写成 `-DARKRTOS_SIGN_KEY_HEADER=\"xxx.h\"`**：Keil 的 Define 框里同一个字段放两个带引号的宏时，
   后面的 `ARKRTOS_BOARD_CONFIG` 会传不过去，`drvflash.c` / `arkrtos_port.c` 因缺 HAL/CMSIS 头
   报 39 个 `uint32_t` / `SCB` 未定义错误（实测踩过，已改回无引号开关）。
   通道本身就靠 `tools/sign_host_gate.py` 里新加的一组探针守着（`ci_gate` 的 `sign-host` 项）：
   给了开关就必须正好拿到 32 字节，不给开关就一个字节都不许进来（默认档零变化）。
3. 打包两份镜像：同一份负载、同一个 `image_id`（= 负载 CRC32），只有签名区不同。
   注意**版本闸门（`INSTALL:211`）在签名闸门之前**，所以测试镜像要把版本抬到比已装副本高
   （本次 `2.0.0.0`），否则先被"版本不递增"挡掉、根本走不到签名校验。
4. 测完把 `uvprojx` 的 Define 还原（工程里不能留 `ARKRTOS_SIGN_KEY_LOCAL`，那会引用一个不入库的头
   而让别人编译失败），重编重烧回默认档，`sec` 回到 8 PASS / 2 FIND / 2 SKIP。

## 10. 三条不能越界的话

1. **不能说"符合某标准"。** 本文所有表格都是差距对照；判定一栏的"已具备"只表示
   "该条目对应能力在本产品上存在且有上板证据"，不等于标准符合性。
2. **不能把 `sec` 的 PASS 当认证结论。** 它检查的是机制在不在，
   不是攻击能不能成功；攻击面验证靠 `APP_BAD` 与穿透测试。
3. **不能把"默认关"当"没有"。** 签名、软总线认证、载荷加密、看门狗
   都默认关；认证前必须先冻结一份**明确打开这些开关**的配置，
   并在那份配置上重跑 §8 的全部用例。
