# Cross-architecture matrix: last words / seamless hand-off / real-time

[中文版（normative）](跨架构机制矩阵.md)

This page answers one question only: **how far each of the three mechanisms has actually got on each class of
hardware.** Every cell is in one of three states, and they are never mixed:

| Mark | Meaning |
|---|---|
| **reading** | a serial log or on-board record, with the numbers and the commit id on the row |
| **compile surface** | it compiles and a gate covers it, but there is no runtime reading |
| **refused at compile time** | turning the switch on is a `#error`: not "untested", but "not implemented" |

## 1. The matrix

| Mechanism | Cortex-M3 / M7 (MPU) | Cortex-M4 (MPU) | RV32IMAC (PMP) | LA64 (MMU / page table) | LA32 (no carrier) |
|---|---|---|---|---|---|
| **Last words** (`ARKRTOS_HW_SAFE`) | architecture-independent; **an M7 board exists (`board/stm32h743` plus the GCC/Makefile project `example/stm32h743/kernel/ARKRTOS_TEST/GCC`, no Keil project), but it leaves `ARKRTOS_HW_SAFE=0`, so the tier is not enabled and has no readings; M3 has no board project** | **on-board, full path**: `devs=3 owners=6 neutralized=6 last_owner=12` (`c021168`), plus channel split, crash limit across reset, driver-callback channel | **QEMU ledger + in-test callback**: `devs=0 owners=2 neutralized=0`, `[PASS] hwsafe.deadman` | **QEMU ledger**: `owners=2 neutralized=8 last_owner=7` after 10 `exec` runs; `devs=0` | compile surface only |
| **Seamless hand-off** (`ARKRTOS_USE_TASK_SWAP`) | **compile surface** (`-mcpu=cortex-m3` / `cortex-m7`); the M7 H743 project keeps the switch off, no board readings | **on-board**: `mini swap`, `app swap`, reverse switch all pass; landing latency **108 / 233 / 58 ms** | **QEMU reading**: kernel self-test `swap: v1=7 -> 7  v2=100` / `swap: PASS`, 5/5 runs; frame rewrite uses `a0..a7` + `mepc` | **QEMU reading**: same self-test, 3/3 `PASS`; frame rewrite uses `a0..a7` + `ERA` | **refused at compile time** (`#error`, no carrier) |
| **Real time: structure** (tick / priority / critical sections) | available (same kernel path) | **readings**: `switch` 744 cyc = 7.75 µs; MPU 300 cyc = 3.1 µs; `tick.isr` 6.3 / 71.6 µs | QEMU runs (CLINT tick, PMP windows) | QEMU runs (paging + PLV user mode) | no carrier |
| **Real time: instrument** (`ARKRTOS_USE_RTSTAT`) | compile surface; DWT exists, the M7 H743 project keeps `ARKRTOS_USE_RTSTAT=0`, no board readings | **full readings** | **unavailable** (`cyccnt_init()` returns `-1`) | **unavailable** (same) | — |

## 2. Last words

The mechanism is instruction-set independent: the kernel keeps a per-task device-ownership ledger and runs a
"neutralise" callback when the task dies (self-exit, kill, fault recovery). What it needs is a device registry,
a task-termination path, and a stack that can run the callback. Whether it *does* anything therefore depends on
whether a driver on that board registered a callback.

- **Cortex-M4 / STM32F427, on-board** (`c021168`, reproduced on two independent fresh installs):
  `hwsafe: enabled, devs=3 owners=6 neutralized=6 (will=3 cb=0 none=3 fail=0 handover=0) last_owner=12`;
  stage 2 of `HWSAFE_DEMO 1.0.1` splits the channels (`will=1 cb=2 none=3 fail=0 handover=0`); the crash limit
  survives a `reboot` (`CRASH:3006 slot N disabled: crash-limit, 3 consecutive faults`).
  See [App崩溃硬件安全与遗言机制](App崩溃硬件安全与遗言机制.md).
- **RV32IMAC and LA64, QEMU**: `hwsafe: enabled, devs=0 owners=2 neutralized=0` (LA64 the same, owner ids 3/6);
  LA64 after ten `exec` runs: `devs=0 owners=2 neutralized=8 last_owner=7`. `owners=2` is the console device the
  kernel claimed itself. `devs=0` is the truth: no driver on these QEMU boards registers a safety callback, so
  the machine-wide `run_pending()` has nothing to do. What is proven is that the mechanism honours its contract
  — with the in-test callback, `run_pending()` returns 1, the arguments match, a second call returns 0 (idempotent),
  `path_counts.cb` increments exactly once, and a released owner no longer triggers on death.
- **Cortex-M3 / M7**: an M7 board does exist (`board/stm32h743` with the GCC/Makefile project
  `example/stm32h743/kernel/ARKRTOS_TEST/GCC`; there is no Keil project), but the board header never defines
  `ARKRTOS_HW_SAFE`, so it defaults to 0 and the tier is not enabled -- hence no readings. M3 has no board at
  all, only the `-mcpu=cortex-m3` compile surface. Neither is written up as "supported".
- **LA32**: the board header sets `ARKRTOS_HW_SAFE=1`, but there is no LA32 runtime carrier.
- **QEMU MPS2-AN386 (M4)**: the board header sets `ARKRTOS_HW_SAFE=0`; this tier does not enable it.

## 3. Seamless hand-off: on-board on ARM, QEMU readings on RV32 / LA64

### 3.1 Frame shape moved down to the port layer

`arkrtos_task_swap_take()` still does four things: copy the whole old RAM block to the new one, rewrite that one
frame into "the first line of the new image entry", make this exception return use the frame in the new block,
and bring the TCB windows and protection up to date. The first two depend entirely on the frame shape, so since
2026-11-20 that part lives in four port-layer functions and no register name appears in the kernel any more:

| Port function | Cortex-M3 / M4 / M7 | RV32IMAC | LA64 |
|---|---|---|---|
| `arkrtos_port_swap_frame_ok()` | `xPSR` Thumb bit set, `IPSR == 0` | `mepc != 0`, 2-byte aligned, `mstatus.MPP` in {U, M} | `ERA != 0`, 4-byte aligned, `PRMD.PPLV` in {0, 3} |
| `arkrtos_port_swap_frame_bytes()` | 32 (8-word basic frame) | 144 (36 words) | 256 (32 64-bit words) |
| `arkrtos_port_swap_rewrite()` | `R0-R3/R12/LR = 0`, `PC = entry & ~1`, `xPSR = 0x01000000` | `a0..a7 = 0`, `ra = 0`, `sp = frame end`, `mepc = entry & ~1`, `mstatus` keeps only MPP plus MPIE | `a0..a7 = 0`, `ra = 0`, `sp = frame end`, `ERA = entry`, `PRMD` keeps PPLV plus PIE |
| `arkrtos_port_swap_activate()` | `arkrtos_port_set_psp(new frame)` (the return pops from PSP) | recorded in a port static, consumed by `riscv_trap_c` after `SVC_Server` returns | same, consumed by `la_trap_c` |

On success `take()` also repoints `p_task->stack_ptr` at the new frame: on RISC-V / LoongArch the next switch
takes its frame from the trap C return value, and without that the TCB still points at the old block that is
about to be returned.

One RV32 criterion only showed up when it ran: **alignment must be judged at 2 bytes, not 4**. This port is
RV32**IMAC**, and the C extension lets an `ecall` (itself 32-bit) sit at 2 mod 4; a 4-byte test calls that a bad
frame and `swap` fails at random (`v1` keeps rising, `v2` stays 0), depending only on where the linker put the
instruction (measured `mepc=0x8002B80E`). `entry & ~1u` in `rewrite()` has the same origin.

The architecture gate in `arkrtos_features.h` narrowed accordingly: Cortex-M3/M4/M7, RV32IMAC (arch id `0x0201`)
and LA64 (`0x0302`) are allowed; RV64GC and LA32 are still a `#error`. The default (`0`) is untouched: nothing
compiled, no symbols, no size or behaviour change.

### 3.2 Evidence per tier

| Hardware | Evidence |
|---|---|
| Cortex-M4 / F427 | **on-board**: block swapped and old block returned (`1 of 4 in use` before and after), `app swap` keeps the old slot `LOADED`, reverse switch works; `arm` → landing **108 / 233 / 58 ms** |
| Cortex-M3 / M7 | **compile surface**: `-mcpu=cortex-m3` / `cortex-m7` through `tools/swap_syntax_gate.py` |
| RV32IMAC / LA64 (QEMU) | **QEMU reading**: the kernel self-test `swap` passes 5/5 (RV32) and 3/3 (LA64) — `v1` stops after the switch, `v2` starts running. RV32 always prints `swap: v1=7 -> 7  v2=100`; LA64's `v1` varies between 2 and 7 (how many rounds the stub ran before landing), `v2=100`. Eight runs, `fault=0` throughout |
| LA32 | **refused at compile time**: the gate takes a reading per real cross compiler — ON must exit non-zero with the refusal text, OFF must compile |

Those two readings come from the **kernel self-test command `swap`**, not from the small-program / App loaders:
it registers a loop stub `v1` on static block A, waits until the counter really rises, then arms "switch to
block B, entry `v2`", and the switch lands in `v1`'s own next `wait`. There are only two criteria — `v1`'s
counter no longer changes after the switch (the old image stopped) and `v2`'s counter rises (the new entry
runs). Both entries live inside the kernel image (`rom_start` is passed `CHIP_FLASH_BASE`), so what this reading
proves is **frame validation + whole-block copy + frame rewrite + the return path taking the new frame** —
**not image relocation**; PIC and loading belong to the mini/app loaders and are covered by the ARM on-board
reading, independently of the instruction set.

The gate also keeps one negative control: LA32 with the switch ON must still be refused. Verifying only "it
compiles" would go green the moment somebody deleted the `#error`.

Two facts from the same board session belong in the conclusion
(see [无缝升级-双缓冲热切换](无缝升级-双缓冲热切换.md) §5 / §9.2):

1. **Data is not continuous.** The start-up stub re-runs the `.data` copy and `.bss` clear, so the probe reads
   `bss=0 data=0x5A5AA5A5` and falls back to the initial values after 569 iterations. "Seamless" means no restart,
   no flash write, no trip through the scheduler — not "memory state is preserved".
2. **The heartbeat contract is briefly violated.** One of four `app swap` runs logged `GUARD:348 not feeding`;
   the contract period is 1000 ms and the watchdog 4000 ms, so it usually reconnects — not guaranteed.

## 4. Real time: the guarantee is structural, the reading needs an instrument

- **Structure** exists on every port: tick, priority preemption, critical sections, and the switch path
  (`PendSV`+`PSP` / `ecall`+`mret` / `syscall`+`ERTN`). The difference between tiers is whether somebody measured
  it, not whether the mechanism is there.
- **Instrument**: `arkrtos_port_cyccnt_init()` returns `-1` where the core cannot serve a cycle counter, and
  `arkrtos_rt_init()` then leaves `ready = 0`, reports `n = 0` for every item and the shell prints "unavailable".
  It deliberately does **not** fall back to the tick counter: a reading three orders of magnitude coarser is worse
  than none.

| Architecture | Counter | Reading |
|---|---|---|
| Cortex-M3 / M4 / M7 | DWT `CYCCNT` | available (10.4 ns per count at 96 MHz, wraps every ~44.7 s) |
| RV32IMAC | returns `-1` | unavailable |
| LA64 | returns `-1` (`rdtime` is a time base, not a cycle counter) | unavailable |
| LA32 | `rdtime` time base; no carrier | — |

Cortex-M4 readings (STM32F427, 96 MHz HSI via PLL, 2 kHz tick, `rt run 3000`):

| Quantity | Reading |
|---|---|
| `switch` (scheduler decision → first instruction) | 744 / 744 / 745 cyc = **7.75 µs**, almost no jitter (`MDK_TRACE` off) |
| `tick.isr` | 603 / 6870 cyc = 6.3 / 71.6 µs |
| `wake.lo` | 4393 / 22074 cyc = 45.8 / 229.9 µs |
| `jitter` | −22.7 / +22.6 µs |
| MPU isolation | ≈ 300 cyc = **3.1 µs** (423 → 723) |
| Privilege switch | ≈ 20 cyc = **0.2 µs** (744 → 723) |
| Default tier (all observers on) | `switch` 3651 cyc avg / 218.3 µs max; 744 once `MDK_TRACE` is off |

Conditions and limits: [实时性与最坏延迟](实时性与最坏延迟.md) §4.

## 5. Switches and zero size

| Switch | Default | When off |
|---|---|---|
| `ARKRTOS_HW_SAFE` | 0 | device open/close and task termination behave exactly as before the mechanism existed |
| `ARKRTOS_USE_TASK_SWAP` | 0 | primitives, both consumers, the SVC hooks and both shell commands are not compiled; an architecture that is not implemented (RV64GC / LA32) with the switch ON is a `#error` |
| `ARKRTOS_USE_RTSTAT` | 0 | no measurement code at all |

`qemu_loongarch64`, `qemu_riscv32` and `la32_generic` set `ARKRTOS_HW_SAFE` to 1 so the mechanism is compiled on a
real carrier; that is a board choice, not a change to the zero-size claim.

## 6. Gate coverage

| Gate | Covers | Does not cover |
|---|---|---|
| `swap` | 15 TUs with the switch ON under armclang (m3/m4/m7); LA64/RV32 **must compile when ON** (one real cross compiler each), LA32 **must still be refused** when ON, and all three must compile when OFF | runtime behaviour after the switch (F427 is on-board; RV32/LA64 are kernel self-test readings, not the loader path) |
| `rtstat` | 7 TUs compile with the switch ON | the "instrument unavailable" runtime branch on non-ARM |
| `elf` / `paging` / `linux-abi` | MMU-tier loading, page tables, syscall ABI | last words / hand-off on the MMU tier |
| `doc-index` | this page appears once in both indexes | — |

Last words has no dedicated gate: its evidence is board configuration plus on-board/UTEST readings, which a
compile-time gate cannot judge.

## 7. Boundaries

1. This page does **not** claim "all three mechanisms work on all architectures". It claims: last words holds on
   every architecture that has a carrier or a compile surface; hand-off has an on-board reading on Cortex-M and
   QEMU readings on RV32IMAC and LA64, while LA32/RV64GC are refused at compile time; the real-time structure
   holds everywhere, while the instrument exists only on ARM.
2. **"Refused at compile time" is not "unverified".** The first is a design choice (do not give a wrong answer);
   the second is a debt. The matrix keeps them apart.
3. **QEMU counts as a board run, not as silicon.** §2's two readings are marked QEMU, and the `devs=0` boundary is
   written next to them.
4. **The M3/M7 gap is not an architecture limit.** The M7 board project (H743, GCC/Makefile) is already in the
   repository; what is missing is one flash cycle with `ARKRTOS_HW_SAFE` / `ARKRTOS_USE_RTSTAT` on. M3 is missing
   a board project and that flash cycle. Neither is missing a kernel path.
5. **The RV32 / LA64 frame rewrites are done, and the QEMU reading is the acceptance criterion**: RV32 rewrites
   `a0..`, `sp`, `mepc`, `mstatus`; LA64 rewrites `a0..`, `sp`, `ERA`, `PRMD`; the two tiers have 5/5 and 3/3
   `swap: PASS` runs. What is still missing is **silicon** (QEMU is not a chip) and an equivalent reading for the
   **mini/app loader path on ARM** (the RV32/LA64 readings come from the kernel self-test).
6. **Each cell's level is a row in the ledger, not prose.** `tools/evidence_levels.tsv` spells out
   claim / arch / level (L0-L3) / carrier / provenance commit per row, and `tools/evidence_gate.py`
   (CI item `evidence-levels`) checks it mechanically: an L2 carrier must be an existing `board/qemu_*`,
   an L3 carrier may not be `qemu_*`, the provenance commit must exist in git history, and the L3 row
   count is frozen (4 rows today, all F427). The level definitions and why QEMU can never become L3 are
   in [验证载体分级.en.md](验证载体分级.en.md).
