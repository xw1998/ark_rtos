# 软总线接入（ark_softbus → 内核 + Shell `bus` 命令）

## 一句话

跨设备的事件 / 远程调用 / 数据平面总线 `ark_softbus` 已作为组件同步进
`kernelsrc/components/ark_softbus`，由 `ARKRTOS_USE_SOFTBUS` 门控（默认 **0**），
板级只提供三个钩子（毫秒时钟 + 临界区进/出），控制台上用 `bus` 命令驱动。

**结论分档（务必看清）**

| 项 | 状态 | 证据 |
|---|---|---|
| 编译 | **编译通过** | `tools/ci_gate.py --build` 11/11：F427 0 Error / F401 0 Error |
| 板内两节点端到端（协议编解码、发现、发布/订阅、定向+ACK、QoS 重传超时、RPC、数据平面分块、错误路径、主题表） | **上板验证过** | F427 上 `bus selftest`，逐项 PASS/FAIL + `checks N, failed 0`（见 §6） |
| 物理串口线上两个节点（两块板 / 板 + PC `bus_bridge`） | **未验证** | 板上只有一路 USART1 且被内核控制台独占，无空闲 UART；接法见 §8 |
| `src/transport/transport_sock.c`（POSIX socket 传输） | **未编译** | 内核工程不把它加进源列表（需要 POSIX socket） |

`bus selftest` 走的是**真实**的帧编解码 + 环形缓冲 + 收发 + QoS/RPC/流状态机，
时间与临界区来自真实的内核节拍与调度器锁；它不是模拟器，但也不是物理串口——
所以上面的分档把「板内」和「物理线」分成两行，不含糊。

## 1. 为什么用「板内 loopback 两节点」

这块 F427 板（STM32F427VGTx）上**只有一路 USART1**（PA9/PA10 → DAPLink VCP = COM3），
而且被内核 Shell 独占。没有第二个空闲串口，物理两节点在这块板上做不出来。

与其把「总线能不能跑」记成「未验证」，不如用一个诚实的替代：让**同一份固件里的
两个真实 `ark_bus_t` 实例**（本节点 `0x1001`、常驻对端 `0x1002`）通过组件自带的
loopback 传输层背靠背接起来（`ark_bus_loopback_init/a/b`，两个 1KB 环形缓冲）。

它真的走到了这些代码：帧编码/解码、CRC、逐字节重组、QoS 会话表与重传、
RPC 槽位、流分块与重组、设备表与发现；时钟钩子每轮都调内核节拍，临界区钩子真的
进/出调度器锁。**它没有走到**的是 UART 传输层的字节收发（`transport_uart.c`）
与真实线上的噪声/时序——那一层如实算「未验证」。

## 3. 构建接入（F427 内核工程）

`example/stm32f427/kernel/ARKRTOS_TEST/MDK-ARM/ARKRTOS_TEST.uvprojx`：

- 新增组 **`ARKRTOS/Softbus`**，18 个源文件：
  - 接入层 `kernelsrc/src/arkrtos_softbus.c`；
  - 板级 `board/stm32f427/arkrtos_bus_port.c`；
  - 组件 13 个 `src/*.c` + `src/transport/transport_loopback.c` + `src/transport/transport_uart.c`；
  - 端口 `port/ark_bus_hal_arkrtos.c`。
  （`transport_sock.c` 需要 POSIX socket，不进源列表。）
- include 路径追加：
  `kernelsrc\components\ark_softbus\{include,src,port}`。
- `Define` 追加 `ARKRTOS_USE_SOFTBUS=1`；`arkrtos_features.h` 里它默认是 **0**，
  撤掉这个宏即完全不编（体积与行为零变化）。
- `MiscControls` 追加 MCU 档 `-DARK_BUS_*`（见下）。

### MCU 档（必须与开关成对出现）

默认档（32 topic / 256B 载荷 / 全层开启）一个实例就要 ~6KB，128KB RAM 的板放不下两个。
工程侧给出：

```
-DARK_BUS_MAX_TOPICS=12 -DARK_BUS_MAX_DEVICES=4
-DARK_BUS_MSG_MAX_SIZE=128 -DARK_BUS_TOPIC_NAME_MAX=24
-DARK_BUS_QOS_MAX_SESSIONS=2
-DARK_BUS_RPC_MAX_SLOTS=4 -DARK_BUS_RPC_MAX_METHODS=4
-DARK_BUS_TASK_ENABLED=0 -DARK_BUS_COLL_ENABLED=0 -DARK_BUS_INFER_ENABLED=0
-DARK_BUS_STREAM_TX_SLOTS=1 -DARK_BUS_STREAM_RX_SLOTS=1
-DARK_BUS_STREAM_RX_MAX=256 -DARK_BUS_STREAM_MAX_BYTES=256
```

`arkrtos_softbus.h` 顶部有一段 `#error` 闸门：档位与约定不符就**编译期报错**，
而不是悄悄按默认档多占几 KB RAM（自测全绿、上板 RAM 不够是最难查的一类）。

档位取舍：关掉 task（协作任务）/ coll（集合通信）/ infer（推理）三个上层；
保留 qos（可靠投递）、rpc（远程调用）、stream（数据平面），因为自检与 `bus rpc/stream`
命令要验证它们。

## 4. 板级三钩子

`ark_softbus` 的端口面刻意只有三个函数（组件里 `port/ark_bus_port_arkrtos.h`）：

| 钩子 | 本板实现 | 说明 |
|---|---|---|
| `ark_bus_port_tick_ms()` | `arkrtos_kernel_get_tick() / (1000/ARKRTOS_TICK_PERIOD_US)` | 节拍周期默认 500us（2000Hz），每毫秒 2 拍 |
| `ark_bus_port_lock()` | `arkrtos_sched_lock_internal()` | 调度器锁（不关中断，可嵌套） |
| `ark_bus_port_unlock()` | `arkrtos_sched_unlock_internal()` | 配对的释放 |

两个口径：

1. **时钟用整除而不是「节拍 × 周期」**。总线的 QoS 重传（200ms）、心跳（3s）都按毫秒算，
   而内核节拍 500us；`节拍 × 500 / 1000` 在 32 位下约 71 分钟就回绕一次。改成
   `节拍 / 每毫秒节拍数` 且要求 `ARKRTOS_TICK_PERIOD_US` 能整除 1000us（不整除直接
   `#error`），回绕周期拉长到与 32 位毫秒同一量级。
2. **临界区用调度器锁而不是关中断**。总线加锁窗口都在表的增删改上（几十条指令），
   调度器锁足够，也允许嵌套（总线自己可能从回调里再发布）。

## 5. RAM 预算（实测，非估算）

从 `ARKRTOS_TEST.map` 逐符号读出（`arkrtos_softbus.o(.bss)` 合计 **5616 B**）：

| 符号 | 大小 | 用途 |
|---|---|---|
| `g_node` | 1460 B | 本节点 `ark_bus_t` |
| `g_peer` | 1460 B | 常驻对端 `ark_bus_t` |
| `g_lb_store` | 2048 B | loopback 两个 1KB 环 |
| `g_lb` | 72 B | loopback 端点/适配器 |
| `obj`（`bus stream` 静态缓冲） | 256 B | 数据平面发送缓冲 |
| `big`（自检错误路径） | 136 B | 超长载荷用例 |
| `g_peer_last_payload` 等零星 | ~180 B | 对端观察窗 |

`KERNEL_RAM` 约 56KB，5.6KB 占比约 10%，可接受。想再省就把档位再压小
（比如 `-DARK_BUS_STREAM_ENABLED=0` 并去掉第 7 段自检），但会失去数据平面验证。

## 6. 使用：控制台 `bus` 命令

命令在内核 Shell 里注册（`kernelsrc/shell/arkrtos_shell.c` 的
`register_kernel_commands()`），首次调用会懒初始化（装 HAL、建两节点、广播 DISCOVER）。

```
bus                       # 等价 bus info
bus info                  # 节点身份 / 档位 / 对端 / 收发计数
bus selftest              # 10 阶段端到端自检，逐项 PASS/FAIL
bus pump [n]              # 手动推进 n 轮事件循环
bus peers                 # 设备表
bus rx                    # 对端最后收到的内容
bus pub <topic> <text>    # 发一条广播（对端动态订阅该主题后应能收到）
bus rpc <text>            # 向对端发 ARK_BUS_M_PING（回文逐字节 +1）
bus stream <n>            # 发 n 字节对象（默认 200，>128 必然分块）
```

自检 10 阶段：`codec`（CRC 向量 0x29B1 / 大端 topic id / 坏 CRC / 坏 magic / 截断）、
`reader`（前导噪声里切出完整帧）、`discovery`（DISCOVER 双向入表）、
`pubsub`（发布/订阅 + 无订阅者计 `dispatch_errors`）、`directed+ack`（定向 + QoS1 ACK 后不重传）、
`rpc`（请求应答 + 槽位释放 + 异步语义）、`stream`（200B > 一帧，重组分块）、
`qos-timeout`（目标不存在 → 重传 N 次后恰好超时一次）、
`errors`（超长载荷 `E_INVAL`、自发帧不回环、坏 CRC 计数）、
`topics`（注册/查重/表满报 `E_FULL`）。

## 7. 未覆盖 / 未验证

- **物理串口两节点**：本文记录为**未验证**。板上没有空闲 UART。要验需一块转接板
  （第二路 UART）或第二块板，接法见 §8。
- **`transport_sock.c`**：同步进来了但不编译（需要 POSIX socket）；主机侧才用它。
- **`bus pub` 的对端订阅**：对端是「按需订阅」——`bus pub` 会先让对端订阅该主题
  再发（组件没有通配订阅）。这只影响这条交互命令的可用性，不影响发布/订阅语义本身。

## 8. 后续：接物理链路

组件已带 UART 传输层（`src/transport/transport_uart.c`）。上板接法：

1. 找一路空闲 UART（本板需换板或加转接），在板级初始化里
   `ark_bus_transport_uart_init(&u, &tp, io, write_fn)`；
2. RX 中断里 `ark_bus_transport_uart_feed_byte()`，其余在任务里 `ark_bus_poll()`；
3. 把 `g_node` 的 transport 从 loopback 换成这个 UART 适配器（接入层的 `sb_build()`
   里一行）；
4. 另一端用 PC 上的 `ark_softbus/tools/bus_bridge`（串口 ↔ TCP），即可与 PC 进程对话。

这条路径的**代码已经全部在树里**，缺的只是硬件那一路串口。
