# Seamless Upgrade: A/B Double-Buffer Hot Swap

> Condensed English edition. The Chinese page (无缝升级-双缓冲热切换.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

This page describes the mechanism behind `ARKRTOS_USE_TASK_SWAP`: **a running task is
replaced in place by another image — the task is not restarted, the scheduler does not
run, Flash is not written, the file system is not touched.**

It solves "the window nobody owns" during a version change. The old scheme (the seamless
upgrade example) used state and request records on the volume: the two programs poll and
each decides who should exit, with a measured handover hole of 27 / 31 / 224 / 407 ms and
218 ms to publish one state record (littlefs commit). This page moves the handover into
the **exception-return path**: the cost drops from "tens to hundreds of milliseconds" to
"one whole-block memcpy".

**Conclusions by grade** (grading rules in `skills/arkrtos/SKILL.md` §6):

| Conclusion | Grade |
|---|---|
| default-profile build passes with the switch off; with the switch at 1 the 7 affected TUs pass `armclang -fsyntax-only` | compiles |
| default-profile build: `0 Error(s), 4 Warning(s)` (all 4 in the untouched vendored `ark_vfs_procfs.c`) | compiles |
| `mini swap` moves the execution flow on a real board and returns the old blocks | **on-board verified** (F427 + DAPLink, §9) |
| `app swap` changes slots, keeps the old slot `LOADED`, switches back in reverse | **on-board verified** (§9) |
| kernel self-test `swap` switches frames on RV32IMAC / LA64 | **verified on QEMU as a board** (§9.3): 5/5 (RV32) and 3/3 (LA64) `swap: PASS` |
| "the data segment is continuous and not reset" after the swap holds on a real board | **measured false** (the startup stub re-runs `.data` copy and `.bss` clear, §5 and §9) |
| failure rollback script, batch upgrade orchestration | **not done** |
| an entry that skips the startup stub and truly preserves the data segment | **not done** (the only path that would make the previous row hold, §5 end) |

## 1. Why not a third buffer level

The requirement, verbatim, was "**adding one more level wastes memory and flash**". So the
number of buffers here is **exactly two**:

| Form | What the two are | What happens to the old one at the swap |
|------|------------------|------------------------------------------|
| small program (`.svcm`) | two **code blocks + RAM blocks** (two pairs in the pool) | **returned to the pool on the spot** (the frame is already in the new block, the instance table is repointed, no execution flow still references the old block) |
| App (`.svcapp`) | two **Flash slots** (each with a RAM block bound at install) | **not erased, not freed**, demoted to `LOADED` — that is the rollback capability |

Peak for small programs is two pairs (the same as the old scheme's "V1 runs in RAM, V2
loads a second RAM block", no increase); for Apps the old scheme had no second copy, and
now two slots coexist — but slots are A/B by definition, **no extra scratch area is
opened**, and the slot count in use before and after an upgrade is unchanged.

## 2. Mechanism: the exception stack frame is the rewritable scene

When an SVC enters the kernel, the hardware has already pushed the interrupted context
onto the task's PSP; `p_svc_ctx` is that frame:

```
[0] R0   [1] R1   [2] R2   [3] R3   [4] R12   [5] LR   [6] PC(=return address)   [7] xPSR
```

So "continue running with a different program" is four steps at the hardware level, all
done once at the SVC entry:

1. **Whole-block memcpy**: old RAM block → new RAM block (including the stack and the
   current frame). At this instant not one metadata word has changed; any failure leaves
   the task fully on the old image, never "half new, half old".
2. **Rewrite this frame inside the new block**: `R0..R3 = R12 = LR = 0`, `PC = new entry &
   ~1`, `xPSR = 0x01000000` (keep only the Thumb bit). That is "the first line of the new
   `main()`", the same shape as a freshly created task's initial stack frame.
3. **Move PSP**: `arkrtos_port_set_psp(same offset in the new block)`; the exception
   return pops the frame from the new block.
4. **Update TCB and MPU**: `rom_start/size`, `ram_start/size`, `stack_top/bottom`, `entry`,
   then `arkrtos_mpu_build_task()` + `arkrtos_mpu_set_app()` written to hardware
   immediately.

The block above is the **Cortex-M** spelling. Since 2026-11-20 the concrete form of steps 2
and 3 lives in the port layer (`arkrtos_port_swap_frame_bytes / rewrite /
activate`): RV32 rewrites `a0..a7 / sp / mepc / mstatus`, LA64 rewrites
`a0..a7 / sp / ERA / PRMD`, and the kernel only says "continue from this entry".
The per-tier table is in the cross-architecture matrix, §3.1.

The code is in `kernelsrc/src/arkrtos_task.c`: `arkrtos_task_swap_arm / take / cancel /
pending`. `take()` is the only place that really touches the scene, and it **may only be
called at the SVC entry** — the only moment at which it is certain that this frame belongs
to this task and is about to be popped back by hardware.

## 3. Two-phase API: arm only books, take lands

```
arm(task, new code area, new RAM area, new entry)   -> 0 / negative error    // booking only, cancellable anytime
   … the task keeps running the old image …
task's next system call -> SVC entry -> xxx_swap_take()   // switched at this instant
```

Two phases because loading (read file, verify CRC, relocate) releases the scheduler lock
and takes tens of milliseconds, while "change the frame" must be one indivisible instant.
`arm` does the former, `take` the latter.

**Only one swap may be in flight.** The kernel has a single pending slot
(`g_task_swap.task_id`); two consumers (small program / App slot) arming at the same time
would overwrite each other. Both modules' `swap` entry points check
`arkrtos_task_swap_pending()` first and return `ARKRTOS_LOADER_ERR_BUSY` on any non-zero
result. — Being able to queue a second one would amount to admitting a third buffer.

## 4. Three refusal boundaries (rather fail than guess)

| Refusal condition | Error code | Why it cannot be allowed through |
|---|---|---|
| new and old RAM blocks **differ in size** / new block is not a power of two or not aligned to itself | `ARKRTOS_SWAP_ERR_LAYOUT` / `_PARAM` | the copy is byte-wise over the whole block, so different sizes have no definite boundary; and one MPU region cannot cover both |
| another live task with the **same `rom_start`** exists | `ARKRTOS_SWAP_ERR_THREAD` | small programs create their own threads that inherit the creator's window; changing the block would leave them running on a returned block |
| the frame is **inside this task's stack window but of an unrecognised shape**: Cortex-M checks `xPSR` bit24 clear or `IPSR != 0` at the offset the `CONTROL.FPCA` shape implies (32-byte basic frame or 104-byte FPU extended frame); RV32 checks `mepc` alignment or `mstatus.MPP` not in {U, M}; LA64 checks `ERA` alignment or `PRMD.PPLV` not in {0, 3} | `ARKRTOS_SWAP_ERR_FRAME` | all of it is in `arkrtos_port_swap_frame_bytes()`, which returns 0 for "not my frame"; a frame outside the window is a no-op instead (an SVC from an ISR uses MSP). FPU extended frames are supported since U-45, see §9.5 |
| the frame is not in the old block's stack area (e.g. an SVC issued from an interrupt runs on MSP) | returns 0, **not a failure** | that is not this task's scene; wait for it to issue another one, do not guess |

Two further **layout-equality** conditions are refused outright rather than pretending to
be seamless:

- small program: `code_block`, `ram_block`, `ram_size` must each equal the old instance's;
- App: the two slots' `slot_type` must match (App→Driver is not an upgrade, it is swapping
  privilege), and both RAM blocks must be the same size.

Upgrades with a changed layout must use the handover protocol in the seamless-upgrade
example. **No version-compatibility judgement is made here**: the kernel cannot know
whether the new version can consume the old data layout — that is the packer's
responsibility.

## 5. Data segment: measurement contradicts the design expectation (important)

**The design expectation** was: the whole-block `memcpy` copies the old block's entire
content (globals, heap, stack), so the new version should start seeing the values left by
the old version rather than freshly initialised ones. The first few revisions of the
document were written to that expectation.

**It does not hold on the board** (F427 + DAPLink, §9). A pair of probe variables was
placed in the image — `g_probe_bss` with no initial value (lands in `.bss`) and
`g_probe_data` initialised to `0x5A5AA5A5` (lands in `.data`), each incremented once per
iteration — and after reaching `it=569`, `mini swap` to the same image printed:

```
[v1] seamless control loop v1.0.0 ...
[probe] bss=0 data=1515890085      <- 1515890085 = 0x5A5AA5A5, both back at their initial values
[v1] adopted state left by an earlier run: it=0, pv=0.000
```

The cause is step 2 of §2 itself: `PC` is rewritten to the **image entry**
(`new_entry & ~1`), and the entry is not the user `main()` but the startup stub — scatter
loading from `__main` on the Keil side, steps 1/2 of `arkrtos_mini_start_gcc.s` (`.data`
copy, `.bss` clear) on the GCC side. The startup stub of course overwrites what was just
copied in. The `data` value happening to equal the initial value also proves `.data` was
re-copied rather than accidentally preserved.

So the accurate semantics of a hot swap are:

> **swap the code area + swap the RAM block (the block really still holds the old block's
> content) + the task re-runs from the first line of the new image's `main()`.**

The block copy is not wasted work: it guarantees the stack area, the call chain on the
stack and the old block are byte-identical (the task keeps running on the old block between
`arm` and the landing, and that period's stack changes are included), and the three
properties "no task restart, no scheduler run, no file system touched" still hold. But
"global state is continuous across versions by nature" **does not hold**:

- control-loop state (integral term, setpoints, filter history) **must be serialised by the
  program itself**, written to an on-volume record as in the seamless-upgrade example; in
  the measurement V1 reconnected through the `/sx_state.bin` line `adopted state left by an
  earlier run`, not through memory;
- consequently the constraint "the new version must be able to consume the old data layout"
  **is no longer needed** — the startup stub has already reset the data segment to the new
  image's own initial values. Conversely, **the same A/B pair still requires identical
  layout** (block sizes), which is the memcpy boundary condition and has nothing to do with
  data semantics.

The only way to make "the data segment really is not reset" hold is: **point the entry at
the user `main()` rather than the startup stub at packing time** (the stack is already set
up by the kernel, `.data/.bss` keep the copied values). That first requires confirming that
`main()` has no hidden dependency on `__libc_init_array` / global constructors; **not done
in this round**, recorded in §9.

## 6. Two usage paths

### 6.1 Small program: `mini swap <index> <new image>`

```
mini                                   # list indices (dense numbering, same as mini stop)
mini swap 0 /seamless_v2.svcm          # replace instance 0 with the new image
```

`arkrtos_mini_swap_at(index, path)` in order:

1. check path length → crash-disable table (`crash_mini_disabled`) → three mutual
   exclusions (load serialisation / one in flight for this module / one in flight in the
   kernel) → take the `index`-th running instance (`arkrtos_mini_nth_running`);
2. snapshot the old instance's `task_id / ram_block / ram_size / code_block` (loading
   releases the lock; the values could change by read-back time);
3. `arkrtos_mini_load_image()` loads the new image into **a new pair of blocks** (this step
   releases `g_mini_lock`);
4. compare the three layout items; unequal ⇒ `ARKRTOS_SWAP_ERR_LAYOUT`;
5. `arkrtos_task_swap_arm(...)`;
6. release the load gate (other `mini run`s may proceed), while "one in flight" stays
   guarded by `g_mini_swap.active`.

Landing happens in `arkrtos_mini_swap_take()`: on `rc > 0` update the instance table
(`pt_index`, `ram_block`, `info.*`, path identity) and `ptable_mini_free(old pt_index)`; on
`rc < 0` return the new blocks to the pool, log `LOGE`, and the instance keeps running the
old image. If `mini stop` stops exactly the instance being swapped, it first calls
`arkrtos_task_swap_cancel(0)` and then reclaims the pending new blocks — otherwise they
would stay in the pool forever while the kernel still holds a swap pointing at a vanished
task id.

### 6.2 App: `app swap <running slot> <new slot>`

```
app install 1 /mnt/nor/app_v2.svcapp   # install the new version into the second slot first (LOADED)
app swap 0 1                           # let slot 0's task switch to slot 1's image
```

Preconditions for `arkrtos_loader_swap(old_slot, new_slot)`:

- `old_slot` must be `RUNNING` with a `task_id` (not running means nothing to be seamless
  about);
- `new_slot` must be `LOADED` with an `entry` (installed first, and not already running);
- both slots' `slot_type` must match, both RAM blocks the same non-zero size.

Landing happens in `arkrtos_loader_swap_take()`: old slot
`ptable_set_slot(old, LOADED, old_entry, 0)`, new slot
`ptable_set_slot(new, RUNNING, new_entry, task_id)`. **Neither the old slot's image nor its
RAM block is touched** — rolling back is switching again with the arguments reversed
(`app swap 1 0`). This step has no failure path (nothing erased or written), so the landing
is atomic.

### 6.3 Landing timing

Both hooks sit at the SVC entry, **before** `arkrtos_guard_svc()`:

```c
if(arkrtos_mini_swap_take(p_svc_ctx, arkrtos_current_task_id) > 0)  { ...; return; }
if(arkrtos_loader_swap_take(p_svc_ctx, arkrtos_current_task_id) > 0) { ...; return; }
/* Fresh liveness evidence: this task called into the kernel. */
arkrtos_guard_svc(arkrtos_current_task_id);
```

Two reasons: ① after a successful swap this frame is already the new image's `main()`, so
this system call must not run on (it must not "swap and then still return with the old
call's semantics"); ② it must not be recorded as the old image's liveness evidence.

The task does not switch immediately: it waits for **its own next system call**. So "how
soon after arm it takes effect" depends on how often it issues SVCs — a purely computing
loop may take a while. This is deliberate: the loader does not seize another task's
execution flow on completion.

## 7. Division of labour with the old handover scheme

| | this page (kernel hot swap) | the seamless-upgrade example (handover protocol) |
|---|---|---|
| who decides | the kernel lands it once at the SVC entry | the two programs poll records on the volume |
| handover hole | one whole-block memcpy (tens of µs, not measured on board) | measured 27 / 31 / 224 / 407 ms |
| can the layout change | **no** (three layout comparisons must be equal) | yes (the new version allocates its own memory) |
| needs a file system | no | yes (`/sx_state.bin`, `/sx_req.bin`) |
| fate of the old image | small program: returned to the pool at once; App: demoted to `LOADED`, rollback possible | the old version exits itself |
| data continuity | **not provided** (the startup stub resets `.data/.bss`, §5) | the program writes it into state records |

The two paths do not conflict: use hot swap for layout-identical versions and the handover
protocol for versions whose layout changed.

## 8. Switch and verification

```c
/* kernelsrc/include/arkrtos_features.h */
#define ARKRTOS_USE_TASK_SWAP   0   /* off by default */
```

Kconfig: `config ARKRTOS_USE_TASK_SWAP` (`bool`, `default n`); see the Kconfig page and the
feature-switch page.

- **Off by default**: the primitives in `arkrtos_task.c`, the consumers in `arkrtos_mini.c`
  / `arkrtos_loader.c`, the two hook lines at the SVC entry and the shell's `mini swap` /
  `app swap` branches are all excluded from compilation.
- **Default-profile measurement** (F427 `ARKRTOS_TEST`, Keil AC6): `0 Error(s), 4
  Warning(s)` (all 4 in the untouched `ark_vfs_procfs.c`), `Code = 219882`, `RO-data =
  19198`, `RW-data = 896`, `ZI-data = 120852`. Against the pre-introduction baseline `Code
  = 219834` that is **+48 B** — because `arkrtos_mini_run()` now calls the extracted
  `arkrtos_mini_load_image()` and is no longer inlined; **not a byte-identical zero
  change**, recorded honestly.
- **Anti-false-green when on**: `tools/swap_syntax_gate.py` forces
  `ARKRTOS_USE_TASK_SWAP=1` and runs `armclang -fsyntax-only` over the 15 affected TUs
  (`arkrtos_task.c` / `arkrtos_mini.c` / `arkrtos_loader.c` / every split shell source plus
  three `arkrtos_port.c` for cortex-m3/m4/m7), printing
  `SWAP-GATE OK (15 files, USE_TASK_SWAP=1; LA64/RV32 compile both ways, LA32 still refused when ON)`;
  a missing armclang is **FAIL, not skip**.
- **The other direction is part of the same gate contract (set 2026-11-19, flipped
  2026-11-20)**: now that frame rewriting is in the port layer, LA64 / RV32 are an
  **implementation**, not a refusal, so the contract became two directions over three tiers
  — LA64 / RV32 with the switch ON **must compile** (one real cross compiler each, against
  the `qemu_loongarch64` / `qemu_riscv32` board projects), LA32 with the switch ON **must
  still be refused** (the negative control: verifying only "it compiles" goes green the
  moment the `#error` is deleted), and all three must compile with the switch OFF. The
  `#error` in `arkrtos_features.h` is now the object of that negative control. Registered
  in `tools/ci_gate.py` as the `swap` item (gate count 52).

**Why it is not on by default**: it changes where the exception return lands. Without
on-board verification, the default profile should not carry such a capability — a single
wrong frame rewrite shows up as a runaway task, not as an error code.

## 9. On-board measurement (F427 + DAPLink, 2026-11-13)

Environment: STM32F427 (`pyocd -t stm32f427zi`, DAPLink CMSIS-DAP), serial COM21 at 115200,
kernel built with `ARKRTOS_USE_TASK_SWAP=1` (at the time by editing the Keil project macro;
since 2026-11-14 project macros are cleared, so the same experiment now needs
`ARKRTOS_USE_TASK_SWAP=y` in `config/arkrtos_defconfig` and a regenerated autoconf.h).

**Sizes with the switch on** (F427 `ARKRTOS_TEST` / Keil AC6, `0 Error(s), 4 Warning(s)`,
all 4 in the untouched `ark_vfs_procfs.c`):

| | Code | RO-data | RW-data | ZI-data |
|---|---|---|---|---|
| default profile | 219914 | 19198 | 896 | 120852 |
| switch on | 222614 | 20114 | 896 | 121116 |
| delta | **+2700** | **+916** | 0 | **+264** |

### 9.1 Four on-board conclusions

| Acceptance item | Result | Reading |
|---|---|---|
| `mini swap` moves the execution flow and returns the old blocks | **pass** | `mini swap: 0 -> /swap_probe.svcm armed; it switches at the next syscall…`; `mini` shows the code block `0x20010000`→`0x20018000`, RAM block `0x20016000`→`0x2001A000`, `block entries` `1 of 4 in use` both before and after (the old two blocks were returned) |
| after `app swap` the old slot is still `LOADED` | **pass** | `LOADER:2936 swap done: task 4 now in slot 1 (slot 0 kept LOADED for rollback)`; `app list`: slot 0 `LOADED` / slot 1 `RUNNING task 4` |
| reverse `app swap` switches back | **pass** | `app swap 1 0` → `swap done: task 4 now in slot 0 (slot 1 kept LOADED for rollback)`; both switches land at the next system call (within ~30–110 ms) |
| iteration count and controlled variable continuous after `mini swap` | **does not hold** | see §5: probes `bss=0 data=0x5A5AA5A5`, back to initial values after 569 iterations; the control loop's state reconnected through `/sx_state.bin`'s `adopted state`, not through memory |

Switch latency: between `arm` and landing only the task's next system call is awaited. The
device log's three `app swap` readings are **108 ms / 233 ms / 58 ms** (`LOADER:2902 swap
armed` → `SWAP:3327 task 4 now runs …`); on the `mini swap` side, because V1's loop issues
at least one SVC every 10 ms, what the board shows is the new image's banner as the very
next output line after the command returns (the host serial timestamp stays inside the same
1 s tick).

### 9.2 Two things the board exposed

**One: the heartbeat contract can be briefly violated.** In four `app swap` runs one
`GUARD:348 not feeding: verdict 0x2 (audit 0x0, violating 1)` was observed and that slot got
a `heartbeat` fault (`crash`: `slot 0 faults=1`). The cause is that after the swap the task
re-runs from the new `main()` and did not feed on the tick before registering the new
contract; contract period 1000 ms, watchdog 4000 ms, so most of the time it reconnects, but
**not guaranteed**. The other three runs (including both directions) were completely clean,
`guard verdict=0x0`. Eliminating it needs the kernel to carry the old contract over after
`take` lands, or one extra `arkrtos_guard_svc()` at landing. **Fixed in U-44**: after
`arkrtos_loader_swap_take()` lands, it calls `arkrtos_guard_rebase()` to restart that
task's contract window from "now" (period unchanged, only the beat stamp moves), so the
tick no longer counts as a violation; the rollback judgement is armed in the same place.
See §9.4.

**Two: layout equality is not semantic compatibility.** Swapping the running `APP_DEMO`
(28672 B) with `APP_DEMO2` (19456 B) — their RAM blocks happened to be the same size — passed
`arm` and landed successfully, but the new image did not feed the heartbeat per contract, was
judged by the guard and halted (`crash`: `slot 0 faults=1 last=heartbeat`), and the recovery
flow then restarted the old image. This is exactly the real-world consequence of "the kernel
compares layout only, never semantics": **upgrades with unequal layout are refused;
upgrades with equal layout but incompatible semantics are caught by the protection mechanism
instead of being executed.**

### 9.3 QEMU readings (RV32IMAC / LA64, 2026-11-20)

There is exactly one real board (F427), so the two non-ARM tiers are measured on QEMU. The
criterion is not "the switch compiles" but a kernel self-test command:

```
swap            # run the self-test once (one run per boot)
swap stat       # read the counters only, touch nothing
```

`swap` registers a loop stub `v1` on static block A (4 KB, 4096-aligned) that issues one
`arkrtos_task_wait()` every 2 ms. Once `v1`'s counter really rises, it arms "switch to
block B, entry `v2`" (`arkrtos_task_swap_selftest_arm()` + `arkrtos_task_swap_arm()`), and
the switch lands in `v1`'s own next `wait`. Two criteria only: after the switch `v1`'s
counter stops changing, and `v2`'s counter rises.

| Target | Invocation | Result |
|---|---|---|
| RV32 (`build/rv32_swap/ark_qemu_rv32.elf`) | `tools/qemu_shell_drive.py --arch riscv32 --cmd swap` | 5/5 runs `swap: v1=7 -> 7  v2=100` / `swap: PASS (old image stopped, new entry running)`, `fault=0` throughout |
| LA64 (`build/la64_swap/ark_qemu_la64.elf`) | `tools/qemu_shell_drive.py --arch loongarch64 --cmd swap` | 3/3 runs `swap: PASS`, `v2=100`; `v1` varies between 2 and 7 (how many rounds the stub ran before landing) |

**Three honest boundaries:**

1. **Both entries live inside the kernel image** (`rom_start` is `CHIP_FLASH_BASE`), so this
   reading proves **frame validation + whole-block copy + frame rewrite + the return path
   taking the new frame** — **not image relocation**. PIC and loading belong to the
   mini/app loaders and are covered by the F427 on-board reading in §9, independently of
   the instruction set.
2. **QEMU counts as a board run, not as silicon.** Neither tier has a chip reading.
3. The self-test **does not go through** the mini / loader `take` functions: each keeps its
   own in-flight ledger (slot, buffer ownership), and the self-test would pollute it and be
   blocked by their slot checks. It therefore has a direct hook
   (`arkrtos_task_swap_selftest_arm / take`) placed first in `SVC_Server()`.

**Two defects found and fixed while taking these readings (both appear only when it runs):**

- **RV32 judged frame alignment at 4 bytes, which showed up as a random FAIL.** The C
  extension of RV32IMAC lets an `ecall` (itself 32-bit) sit at 2 mod 4; a measured
  `mepc=0x8002B80E` was called a bad frame and the reading was "`v1` keeps rising, `v2`
  stays 0" — which looks like "the switch never takes". Fix: the test became `(mepc & 1u)`
  and `entry & ~3u` in `rewrite()` became `& ~1u`.
- **`v1`'s SVC arrived first and deregistered the self-test early.** `arm` and `swap_arm`
  are two calls and the target task outranks the shell, so it can issue an SVC one tick
  later; at that instant `swap_take()` returns 0 (the pending item is not set yet), and an
  unconditional deregistration there orphans the real pending item — the same random FAIL.
  Fix: deregister only when `rc != 0`.

One **unexplained** observation stays on the books: before those two fixes there was one
`[PMP] fault mcause=5 mtval=0x00000048 mepc=…arkrtos_shell_ext_trampoline…` (the
trampoline's `lw a5,72(s0)` dereferencing `0x48` with `s0=0`). After the fixes, five
consecutive RV32 runs and three LA64 runs had `fault=0` and it never reappeared — but
"why it jumped to the trampoline" **has no independent explanation**, and this must not be
read as "proven harmless".

### 9.4 QEMU reading for automatic rollback after a failed swap (LA64, 2026-11-28)

The first item of §9.2 (the one tick that may be violated right after a swap, and may charge
a `heartbeat` fault to the slot) and the §10 "failure rollback script" are closed together in
U-44: the switch `ARKRTOS_USE_SWAP_ROLLBACK` (default off) makes
`arkrtos_loader_swap_take()` call `arkrtos_guard_rebase()` right after the swap lands, so the
contract window restarts from "now" (this also removes the §9.2 jitter), and judges whether
the new image keeps the promise the old one was already keeping, over a window of **three
heartbeat periods**. If it does not, the old slot is started again. The judgement only sets
flags inside the tick; the action runs in task context (the SVC entry) — stopping an image
closes VFS handles, which must not happen in an ISR.

The criterion is the **heartbeat contract**, not a timer of our own: a task is judgeable only
after it declared `arkrtos_guard_beat(id, period)` (no contract, no arming — refuse rather
than roll back a healthy image). Window = three periods (floor two ticks).

QEMU LA64 run (`make -f example/qemu_loongarch64/Makefile 
EXTRA_CFLAGS="-DARKRTOS_USE_TASK_SWAP=1 -DARKRTOS_USE_SWAP_ROLLBACK=1"`; the demo task is
`task_rb_demo` in `example/qemu_loongarch64/main.c`):

```
[swaprb] arm rc=0 task=10 window=600
SWAP:125 rollback armed: task 10 in slot 1, 600 tick(s) (100 ms x 3) to keep its heartbeat or slot 0 comes back
[swaprb] healthy state=2 reason=0
SWAP:230 rollback: task 10 kept its contract through the window; slot 1 stands
[swaprb] rearm rc=0
[swaprb] failing state=3 misses=1
SWAP:160 rollback: task 10 broke its heartbeat contract in slot 1 (0 -> 1 misses); slot 0 will be restarted
[swaprb] service state=5 last_rc=-9
SWAP:259 rollback: stopping slot 1 reported -9; starting slot 0 anyway
SWAP:280 rollback failed: slot 0 would not start (-9); no image is running this task
```

Reading: `state` runs `2=confirmed` (healthy, keep the new slot), `3=failed` (violated,
awaiting action), `5=gave up` (the old slot would not start — honestly reports "no image is
running this task", no retry, no pretending). `last_rc=-9` is the faithful result when the
slot holds no real image (`ARKRTOS_LOADER_ERR_*`) — exactly "rather report it did not come up
than pretend the rollback succeeded".

**Honest boundaries:**

1. This demo **does not really swap images** (that needs a pair of App slots and two
   `.svcapp` files); it verifies the orchestration itself: the arm criterion, the window
   countdown, the violation verdict, and the stop/start order with its failure degradation.
2. A kernel task (`task_rb_demo`) **does not go through the SVC**, so `service()` is called
   directly here as a stand-in for the "SVC entry" hook. That hook
   (`arkrtos_swap_rollback_service()` in `SVC_Server`) is guaranteed compiled by
   `tools/swap_syntax_gate.py` and executed by the host test; on real hardware it runs on
   every system call and is naturally in task context.
3. Cross-reset rollback (the new image crashes the system, and after a reset the old image
   must come back) is not done: it needs a trial-boot marker in Flash and boot-selection
   logic to fall back to the old slot after some "boots then crashes". Recorded in §10.

### 9.5 FPU extended frames: from "refuse outright" to "shape decided by FPCA" (2026-11-28, U-45)

On Cortex-M4F / M7F a task that has **used the FPU** gets an extended frame at the SVC
entry: the hardware pushes S0-S15, one reserved word and FPSCR below the basic frame,
0x68 = 104 bytes in total. R0 therefore moves from word 0 to word 18, PC to 24 and xPSR
to 25. This used to be refused outright (`ARKRTOS_SWAP_ERR_FRAME`) because "rewriting it as
a basic frame corrupts the FPU scene".

It is now recognised, with exactly three rules:

1. **The hardware decides the shape; content is only a cross-check.** `CONTROL.FPCA` is the
   hardware's answer to "was this task using the FPU at the moment of the exception", and it
   is what made the hardware push an extended frame, so the port believes it and then
   validates the xPSR. Why not guess from content: in an extended frame `[7]` is the bit
   pattern of S4, which happens to look like Thumb=1 / IPSR=0 with probability 1/512 —
   guessing is "twenty wrong runs in ten thousand".
2. **The criterion and the size are one pure function**:
   `kernelsrc/port/arm/arkrtos_arm_swap_frame.h`. The kernel calls a single port entry,
   `arkrtos_port_swap_frame_bytes(frame, bytes_left)`: 0 means "this frame is not mine",
   anything else is the frame's real size. M3 passes `fpu_frame = 0` (it cannot push an
   extended frame), M4/M7 pass FPCA. That also stops "32 / 104" from being a hard-coded
   constant: a constant used for the bounds check rejects an extended frame that sits at the
   top of the stack and lets through a basic frame that does not fit.
3. **The rewrite zeroes the FPU scene**: `S0-S15`, the reserved word and `FPSCR` are all
   written to 0, then `R0-R3/R12/LR/PC/xPSR` are rewritten at the shifted offsets. A hot
   swap does not carry task state across (§5: `.data` / `.bss` return to their initial
   values), and the FPU scene is treated the same way; zeroing also gives the new image a
   deterministic floating-point environment (`FPSCR = 0`: round to nearest, no traps).

**Readings (host + syntax level, no silicon):**

- `kernelsrc/tests/test_arm_swap_frame_host.c`: 21 assertions pinning five dangerous shapes —
  FPCA says extended but only 103 bytes are left: **never read `[25]` past the block end**
  (returns 0); `[25]` is not an xPSR: refuse, **never fall back to a basic rewrite**; both
  `[7]` and `[25]` look like xPSR: the shape follows FPCA (32 vs 104); a bad `[7]` is never
  rescued by a good `[25]`; the constants agree with each other (26 words = 104 bytes,
  `R0+6 = PC`, `R0+7 = xPSR`).
- The header measured on its own with gcov: **21/21 lines, 100.00%** (the case is run-only,
  `mods` is empty, so it does not take part in the per-module coverage baseline).
- `tools/swap_syntax_gate.py` gained two `-DARKRTOS_USE_FPU=1` builds (M4F / M7F): the FPU
  switch is off by default, and without these the extended-frame half would never meet a
  compiler.

**Honest boundaries:**

1. There is no board reading and no QEMU M-core reading of "a task really used the FPU, was
   hot swapped, and the new image kept running". The board reading is still the §9 F427 data
   (taken with the FPU switch off).
2. `S16-S31` are not part of the frame the hardware pushes (they are AAPCS caller-saved
   registers handled by PendSV's software stacking). Hot swap copies the whole RAM block, so
   they travel with the old block and are never used; the new entry is a startup stub and
   does not rely on them.
3. The criterion covers exactly two shapes: basic frame and FPU extended frame. The M33
   TrustZone secure frame (xPSR at `[7]` but with the S bit in `EXC_RETURN`) is still out of
   scope, see §10.

## 10. Not done, and known limits

- ~~**Failure rollback script**~~: **done in U-44** (`ARKRTOS_USE_SWAP_ROLLBACK`, default
  off). The criterion is the heartbeat contract: `app swap` landing triggers
  `arkrtos_guard_rebase()`, and a violation within three periods restarts the old slot;
  no contract means no arming, a failed restart is not retried. QEMU LA64 reading in §9.4.
  What is **still not done** is cross-reset trial-boot fallback (the new image crashes the
  system; boot selection must return to the old slot) — that needs a trial-boot marker in
  Flash.
- **Batch upgrade orchestration**: only one swap in flight; upgrading many tasks means
  queueing them one by one.
- ~~**No FPU extended frames**~~: **done in U-45**. The shape comes from `CONTROL.FPCA`;
  an extended frame is 104 bytes with R0/PC/xPSR at `[18]/[24]/[25]`, and the FPU scene is
  zeroed. 21 host assertions plus two `FPU=1` syntax builds; readings and boundaries in
  §9.5. **Still missing**: a board or QEMU M-core reading of a real FPU-using task being
  hot swapped.
- **TrustZone secure frames are still refused**: the M33 `EXC_RETURN` S-bit frame is not in
  the criterion (and this repository has no M33 board).
- **Layout must be identical**: differing block size, slot type or RAM size means no swap.
  This is not a defect; it is "rather fail than guess".
- **Between `arm` and landing the old image keeps running**: during that window the new
  blocks already hold the pool/slot. If the task never issues a system call, those blocks
  stay held — `cancel` can reclaim them from outside (`mini stop` does so).
- **The data segment is still reset** (§5). Making it truly continuous requires pointing the
  packed entry at the user `main()` rather than the startup stub; the precondition is
  confirming `main()` does not depend on `__libc_init_array` / global constructors. This
  round only records it — not implemented, not verified.
- **Non-ARM has QEMU readings only** (§9.3). The RV32 / LA64 frame rewrites are implemented
  and pass 5/5 and 3/3 times, but there is no silicon reading; and that reading's entries
  live inside the kernel image, so it does not cover the PIC / loading path.
- **One unexplained trap observation** (end of §9.3). Before the RV32 alignment fix there
  was one PMP fault that jumped to `arkrtos_shell_ext_trampoline`; eight runs after the fix
  never reproduced it. The phenomenon itself is unexplained.
- ~~**The heartbeat contract is not carried over**~~ (§9.2). **Fixed in U-44**:
  `arkrtos_loader_swap_take()` calls `arkrtos_guard_rebase()` after landing, restarting the
  window from "now" and removing that one-tick jitter; the period still belongs to the task,
  not the image. See §9.4.
