# 设备树

**[简体中文](设备树.md) | English([设备树.en.md](设备树.en.md))**

Ark RTOS 用一份设备树描述"这块板子上有什么"。它和分区头分工明确：

* **设备树**说硬件事实——哪个 USART 在什么地址、NOR 挂在哪个 SPI 上、板上有几颗
  灯。这些是芯片/板子决定的，不随固件布局变。
* **分区头**（`config/arkrtos_partition.h`）说固件布局——槽位、池、地址只在那一处
  定义。

设备树由 `tools/dts/dtc_lite.py` 编译成一张纯 C 的平表，运行期用一组查询 API 访问，
不需要动态内存、不解析字符串、不碰硬件。

## 1. 为什么是"子集"而不是完整 dtc

MCU 上只需要一件事：驱动按 `compatible` 找到节点的寄存器窗口和几个属性。没有 MMU、
没有地址翻译、没有中断控制器层级。所以 `dtc_lite` 只支持表达这些所需的语法，
**遇到不认识的指令一律报错**，绝不静默产出一棵空树——一个拼错的属性名应该立刻
失败，而不是等到板上"这个驱动怎么没绑上"。

支持的语法：

```
/dts-v1/;                       版本标记（接受并忽略）
/include/ "file"  或 #include "file"   包含
/ { ... };                      根节点
name[@unit] { ... };            节点
label: name { ... };            带标签的节点
&label { ... };                 overlay：往已有节点合并属性
/delete-node/ name;             删除子节点
/delete-property/ name;         删除属性
prop = "str", "str2";           字符串属性
prop = <0x1234 5 &other>;       单元属性（&ref 解析成 phandle）
prop = [00 11 22];              byte string 属性
/memreserve/ ...                接受并忽略
```

## 2. 目录布局

```
dts/stm32f4.dtsi               # SoC 共有部分：cpus、usart1-3、spi1-2、gpioa-e、iwdg
dts/stm32f427.dts              # 板：model、chosen、leds、overlay 使能外设、NOR
dts/stm32f401.dts              # 另一块板
kernelsrc/include/arkrtos_dt.h # 手写的稳定查询 API
board/<chip>/arkrtos_dt.c      # 生成产物（入库）
tools/dts/dtc_lite.py          # DTS 子集编译器 + C 生成器
tools/dts/test_dt.c            # 主机自测（断言 API 的回答）
tools/dts/host/                # 主机编译用类型垫片
```

`dtsi` 里每个外设默认 `status = "disabled"`，板级文件用 `&label { status = "okay"; }`
把它打开。只有"打开"的设备会被 `arkrtos_dt_find()` 返回。

## 3. 查询 API

```c
uint32 arkrtos_dt_count(void);
const arkrtos_dt_node_t *arkrtos_dt_node(uint32 idx);
const arkrtos_dt_node_t *arkrtos_dt_find(const char *compatible);
const arkrtos_dt_node_t *arkrtos_dt_find_next(const char *compatible,
                                              const arkrtos_dt_node_t *from);
const char *arkrtos_dt_model(void);
const arkrtos_dt_prop_t *arkrtos_dt_prop(const arkrtos_dt_node_t *node, const char *name);
int32 arkrtos_dt_prop_u32(const arkrtos_dt_node_t *node, const char *name,
                          uint32 idx, uint32 *out);
const char *arkrtos_dt_prop_str(const arkrtos_dt_node_t *node, const char *name);
int arkrtos_dt_str_eq(const char *a, const char *b);
```

约定：

* `is_device` 当节点带 `compatible` 时为 1；
* `arkrtos_dt_find*` **只返回已使能的设备**（status 缺省或 `okay`），把 disabled
  的节点排除在外；
* 找不到就是 0 / -1，不猜一个"看起来像"的结果。

## 4. 生成与校验

```bash
# 生成某块板的数据文件
py -3 tools/dts/dtc_lite.py --dts dts/stm32f427.dts --out board/stm32f427/arkrtos_dt.c

# 只看树结构，不生成代码
py -3 tools/dts/dtc_lite.py --dts dts/stm32f427.dts --dump

# 校验入库的 .c 是否与 .dts 一致（CI 用）
py -3 tools/dts/dtc_lite.py --dts dts/stm32f427.dts \
      --out board/stm32f427/arkrtos_dt.c --check

# 主机自测：编译并运行生成的表，验证 API 回答和 DTS 说的一致
py -3 tools/dts/test_dt.py
```

生成的 `board/<chip>/arkrtos_dt.c` 会随内核一起编译；它引用 `arkrtos_dt.h` 里的
类型和 API 声明。

### 4.1 同一份 DTS，两个出口

带 MMU 的档位（LA64 等）不 link 那张 C 表，它要的是一块标准 `.dtb`——正常的
Linux 形态项目都是把 blob 放进镜像、启动时解析。所以同一个编译器有第二个出口：

```bash
# 生成标准扁平设备树（Devicetree Specification v0.4，version 17）
py -3 tools/dts/dtc_lite.py --dts dts/qemu_loongarch64.dts \
      --out build/qemu_loongarch64/arkrtos.dtb --format dtb
```

两个出口共用**同一次解析**（`build()` 之后分叉），所以它们不会互相矛盾；不存在
"表里说有、blob 里没有"这种形态。

`--format` 默认是 `c`，MCU 档的命令行和产物一字不变；`--check` 对两种格式都做
字节比对。

`tools/dts/dtb_verify.py` 是独立的**读侧**实现，用来验 blob 本身合规：

```bash
# 六块板逐个：编译成 dtb、按规范校验、再和 DTS 逐节点逐属性比对
py -3 tools/dts/dtb_verify.py --all

# 单块板，或验一块已经存在的 dtb
py -3 tools/dts/dtb_verify.py --dts dts/stm32f427.dts
```

它不复用写入侧的编码函数——复用了就等于让端序/对齐的错误自己给自己作证。校验
四类：

| 类 | 内容 |
|---|---|
| 头部 | magic `0xd00dfeed`、version 17 / last_comp 16、totalsize 与实际长度一致、各段偏移 4 字节对齐且不越界 |
| 内存预留块 | 起始偏移 8 字节对齐、以全零对终止 |
| 结构块 | `BEGIN_NODE`/`END_NODE` 严格嵌套、节点名以 NUL 结尾、`nameoff` 落在 strings 段内、属性值 4 字节对齐、`FDT_END` 恰好落在 `off_struct + size_struct` |
| 语义 | 与 DTS 模型逐节点、逐属性、逐字节相同 |

CI 里是 `devicetree-dtb` 一项：对 `dts/*.dts` 全量跑上面第一条命令。

### 5.1 MMU 档：内核解析镜像里的 dtb（`fdt` 命令）

MCU 档把 DTS 编成 C 平表（`arkrtos_dt.c`）直接链进镜像；MMU 档走的是另一条路：
同一个 DTS 编成标准 dtb（§4.1），用 `elf_blob.py` 包成字节数组嵌进镜像，
开机由内核自己的解析器读回来。开关是 **`ARKRTOS_USE_FDT`（默认 n）**，
这一档的定法就是「板级层」：`config/qemu_loongarch64_defconfig` 请求 `=y`，
由 `genboard.py` 的第七块（设备树 / MMU 档）写成 `#undef` + `#define 1`；
共享的 `arkrtos_autoconf.h` 里它恒为 0，MCU + MDK 档一个符号都不多。

解析器（`kernelsrc/src/arkrtos_fdt.c`）只读、零分配、不递归，深度上限
`ARKRTOS_FDT_MAX_DEPTH = 16`。任何偏移 / 长度 / 对齐先核后读，越界就返回错误码，
**不夹取**：把「dtb 坏了」变成一个悄悄少掉的设备是更坏的失败。

| 错误码 | 值 | 含义 |
|---|---|---|
| `ARKRTOS_FDT_OK` | 0 | 解析成功 |
| `ERR_ARG` | -1 | 空指针 / 长度不足一个头部 |
| `ERR_MAGIC` | -2 | 头 4 字节不是 `0xd00dfeed` |
| `ERR_VERSION` | -3 | version / last_comp 不认识 |
| `ERR_RANGE` | -4 | 段偏移或 totalsize 越界 |
| `ERR_ALIGN` | -5 | 段偏移没 4 字节对齐 |
| `ERR_FORMAT` | -6 | 结构块不严格嵌套 / `FDT_END` 不在块尾 |
| `ERR_DEPTH` | -7 | 嵌套深度超过上限 |
| `ERR_NOT_INIT` | -8 | 还没 `arkrtos_fdt_init` 就查询 |
| `ERR_NOT_FOUND` | -9 | 路径 / 别名 / 属性不存在 |
| `ERR_PATH` | -10 | 路径或 stdout-path 格式不认识 |

开机在 shell 起来之前打一行读数（QEMU LA64 实测）：

```
[fdt] blob=924 rc=0 model=QEMU virt loongarch64 nodes=8
```

`blob=` 是嵌进镜像的 dtb 字节数，可以和 `build/qemu_loongarch64/arkrtos.dtb`
的 `stat` 大小直接对账。解析失败时打 `-n` 错误码与 ` (blob refused, tree NOT parsed)`，
启动继续，但**不会**拿 C 平表凑一棵树出来。

`fdt` 命令的输出格式与 `dt` 逐字一致，所以两条读路径可以直接对账
（一次 QEMU 启动，前后两条命令）：

```
$ dt
model=QEMU virt loongarch64 nodes=8
  cpu@0 compat=loongarch reg=0x0/0x0 okay
  soc compat=simple-bus reg=0x0/0x0 okay
  serial@1fe001e0 compat=ns16550a reg=0x1fe001e0/0x100 okay
  ramdisk@0 compat=ark,ram-blk reg=0x0/0x80000 okay
$ fdt
（与上一段逐行相同）
```

### 5.2 动态换树、/chosen 与 stdout-path（2026-11-20）

上一版这里写的是「只解析编进镜像的那一份树」。现在多做了三件事：动态换树、
stdout-path 的消费、以及 overlay 的最小子集（见 §5.3）。

**换树是事务性的。** `arkrtos_fdt_load(dst, cap, src, len)` 先把字节拷进调用方
RAM，再走同一条 `init`；`init` 开头给当前视图拍一张快照，任何一步失败都恢复
这张快照并返回错误码——坏 blob 换来的只是一个错误码，**不会让这台机器"突然
一个设备都没有"**。主机自测单独钉住这条：先 load 好树，再把魔数改坏 load
一次，`ready==1`、`node_count` 与 `model` 都必须与之前一致。

**按路径 / 别名 / phandle 查节点**：`node_by_path()`（`/` 是根）、`alias()`
（字符串与 phandle 两种别名值都收）、`path_of_phandle()`、
`node_by_phandle()`。这里修掉了两个会静默给出错答案的实现错误，写出来是因为
它们正好说明"为什么必须做往返自测"：节点深度比较少算了根节点这一层（任何
绝对路径都查不到），以及拼路径时把根节点的空名字也当成一个组件（得到
`//soc/...`）。两者都不报错，只是答案不对。

**stdout-path 的消费**（开关 `ARKRTOS_USE_FDT_CONSOLE`，默认 n）：
`arkrtos_console_from_fdt(expect, bind)` 只做判定，**不改控制台、不碰硬件**。
它按顺序核：节点是否存在 → `status` 是否 okay → 树自己是否自洽（`stdout-path`
写 115200、节点 `current-speed` 却是别的，报 `baud_conflict`）→ 与板级的
`compatible` / `reg` 是否一致。不一致就保留板级默认并给出原因码，不是
"挑一个能用就好"。

| 原因码 | 值 | 含义 |
|---|---|---|
| `ARKRTOS_CONSOLE_OK` | 0 | 树与板级一致 |
| `NO_STDOUT` | -1 | 没有 `/chosen/stdout-path` |
| `BAD_PATH` | -2 | 路径或选项写法不认识 |
| `NO_NODE` | -3 | 解析出的节点不存在 |
| `DISABLED` | -4 | 节点 `status` 不是 okay |
| `COMPAT` | -5 | `compatible` 与板级不符 |
| `ADDR` | -6 | `reg` 基址与板级不符 |
| `BAUD` | -7 | 树内 `current-speed` 与 `stdout-path` 冲突 |

QEMU LA64 实测（2026-11-20，同一次烧录）：

```

[fdt] console path=/soc/serial@1fe001e0 baud=115200 reason=ok match=1
...
$ fdt chosen

  path=/soc/serial@1fe001e0 baud=115200 bits=8 parity=n alias=1
$ fdt path /soc/serial@1fe001e0

  compat=ns16550a reg=0x1fe001e0/0x100
$ fdt phandle 1
phandle 1 -> /soc/serial@1fe001e0
$ fdt save /mnt/ram/b.dtb
fdt: save /mnt/ram/b.dtb rc=0 bytes=924
$ fdt load /mnt/ram/b.dtb
fdt: load /mnt/ram/b.dtb rc=0 bytes=924 nodes=8 (was 8)
$ fdt load /mnt/ram/empty.bin
fdt: load /mnt/ram/empty.bin rc=-1 bytes=0 -> refused, previous tree kept (nodes=8)
```

为了让别名真的能用，LA64 的 dts 已改成 Linux 标准形态
（`stdout-path = "serial0:115200n8"` + `/aliases { serial0 = &uart0; }`），
并且 `dtc_lite.py` 现在会给每个带 label 的节点补一个 `phandle` 属性——此前
它只把标签记在自己手里，树里根本没有 phandle，于是 `&uart0` 这种写法在这个
blob 上无从还原。六块板的 C 平表随之重新生成。

`fdt save/load` 证明的是「RAM 副本 + 文件往返 + 坏 blob 回滚」，**不是**
bootloader 交 dtb、也不是镜像重定位。真机读数仍然没有（QEMU 算上板）。

门禁 `tools/fdt_gate.py`（CI 项名 `fdt`）现在 13 项：上面的 A–G 之外再加
H（开机 `[fdt] console` 行必须与树一致，四种坏法被判红）、I（`fdt chosen` /
`path` / `phandle` 必须指向同一个节点，`save`+`load` 往返 nodes 不变，空文件
被拒且旧树保留，同样四种坏法被判红）与 J（overlay，见 §5.3，七种坏法被判红）。

### 5.3 overlay 子集：`target-path` / `target = <&label>` / 覆盖 / 删除（`ARKRTOS_USE_FDT_OVERLAY`，2026-11-20）

做的是**最小子集**，说清楚做了什么比说「支持 overlay」有用：

| 接受 | 拒绝（返回错误码，树一字节不动） |
|---|---|
| `fragment@N { target-path = "<绝对路径>"; __overlay__ { ... }; }` | `__local_fixups__` 节点（`ERR_OVERLAY_TAG`）——本实现不做本地 phandle 重编号 |
| `fragment@N { target = <&label>; __overlay__ { ... }; }` | `target` 不是 4 字节、或占位值不是 `0xffffffff`（"已经解析过的 phandle"）：本模块不反查数字、不猜它指谁（`ERR_OVERLAY_TARGET`） |
| 属性**同名覆盖**（值长度不同也可以） | `__overlay__` 里长度 0 的属性 = **删该属性**；目标没有这条属性 → `ERR_OVERLAY_DEL (-16)` |
| 追加**新子节点**（可带自己的属性与孙节点） | `__overlay__` 里的同名子节点若只有一条长度 0 的 `__delete` 属性 = **删该子节点**；目标没有这个子节点 → `ERR_OVERLAY_DEL` |
| 目标已存在同名**属性**时的覆盖 | 目标节点下已存在**同名子节点**（`ERR_OVERLAY_DUP`，不合并、不静默覆盖） |
| | fragment 自身结构不认识（`ERR_OVERLAY`）、尺寸不够（`ERR_OVERLAY_SIZE`） |

`target = <&label>` 走的是 Linux 那一套，没有自创格式：

1. dtc 在 `target` 里写占位值 `0xffffffff`，并在 fragment 侧生成
   `__fixups__ { <label> = "/fragment@N:target:0"; }`；
2. 基树用 `__symbols__ { <label> = "<绝对路径>"; }` 给出 label 的落点；
3. 运行期按 `"/fragment@N:target:0"` 找到 label 名，再用基树的 `__symbols__`
   换成路径，然后才在那个路径上合并。

两条删除编码的出处必须讲清楚：

- **删属性 = 长度 0 的属性**：这是 Linux overlay 的既有约定（属性赋空即删除）。
- **删子节点 = 一条长度 0 的 `__delete` 标记属性**：`/delete-node/` 在 dtb 里的
  编码本仓库**没有核实到权威原文**（本机没有 dtc 可执行、外网取原文被拦），
  所以这里用**本项目自定义的表示法**，并明确**不声称与 Linux dtbo 逐字节一致**。
  C 侧只认这一种形状：该子节点里恰好一条 `__delete`、没有别的属性、没有子节点；
  别的形状按 `ERR_OVERLAY` 拒绝，不猜。

删除目标不存在一律 `ERR_OVERLAY_DEL`，不静默跳过——`/delete-node/` 名字拼错
却"什么都没发生"是最难查的一类静默失败。

`__symbols__` / `__fixups__` / `__local_fixups__` 是 dtc 的标签表，**不算树的
节点**：`arkrtos_fdt_node_count()`、节点迭代器、以及 MCU 档的 `dt` 平表都不含
它们，这样「`dt` 与 `fdt` 两条独立读路径打出同样的 `nodes=`」这条对账关系继续
成立（`tests` 与门禁 A/E 就是拿它当判据的）。它们确实在 blob 里，
`fdt path /__symbols__` 照样查得到。

实现上**不做原地改字节**：属性必须排在子节点之前，插入一个属性会顶掉后面
所有偏移，那条路上全是「不报错只给错答案」的坑。所以是**重拼整棵树**到调用
方给的 arena 里（`ARKRTOS_FDT_OVERLAY_MIN_ARENA` = 4096）。两遍扫描：第一遍
只 measure（dst 一个字节都不写，所有拒绝条件在这一遍暴露，包括删除目标是否
存在），第二遍落笔；两遍结果不一致报 `ERR_OVERLAY`。失败时调用方的树保持
原样，arena 内容不承诺有效。

净变化 `nodes=10 (was 10)` 是**故意**的：这份 fragment 追加 1 个新节点
（`overlay-demo-node`）、删掉 1 个子节点（`victim-child`），正好抵消。三条
新判据各自都有反假绿：把 `victim-child` 的名字改错，`fdt overlay` 必须报
`rc=-16 (delete target not found) -> refused, tree kept (nodes=10)`（本机实测
过这条负样本，然后原样还原）。

那四条 `fragment@N` 来自 `tools/dts/overlay/demo_label.dts`，走和基树同一条
链路（dts → dtb → `elf_blob.py` 生成的 C 数组），由板级
`arkrtos_board_fdt_overlay_demo()` 提供，**不参与启动**——不应用 overlay 的
镜像行为与之前逐字节相同（`ARKRTOS_USE_FDT_OVERLAY` 默认 0，只有 LA64 板级
打开）。为什么另起一份而不是改 `tools/dts/overlay/demo.dts`：主机自测把
`demo.dts` 喂给六块板的树，而 `&uart0` / `&victim` 只在 LA64 的树里存在；
label 引用写进去，别的板必然失败。所以 `demo.dts` 保持 board-agnostic，
`demo_label.dts` 是它的超集、只嵌进 LA64 镜像。

`fdt overlay` 成功后把新树装进同一个 RAM 缓冲（`dst == src` 的逐字节自赋值，
实测安全），所以随后的 `fdt get` / `fdt path` / `fdt` 读的都是应用后的树。
门禁 J 组真正的反假绿闸门是**应用前那一组读数**（节点查不到、`victim-child`
在、`victim-prop="before"`、控制台 115200）：只断言应用后的结果，分不出
「overlay 真改了」和「树里本来就是这样」。
