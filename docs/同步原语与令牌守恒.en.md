# Synchronisation Primitives and Token Conservation

**[简体中文](同步原语与令牌守恒.md) | English**

## 1. The conclusion in one sentence

The kernel **cannot complete a blocking wait inside the SVC handler**, because `PendSV` can
never preempt `SVC` (`arkrtos_port_switch_task()` in
`kernelsrc/port/arm/cortex-m4/arkrtos_port.c` only sets `SCB->ICSR = SCB_ICSR_PENDSVSET_Msk`,
and the comment says so). A wait issued from an App is therefore split in two:

| Who | What it does |
|---|---|
| Kernel (inside the SVC handler) | **Registers only**: links the waiter onto the object's wait queue, then returns `ARKRTOS_SYNC_ERR_WOULDBLOCK` |
| App-side oslib (thread state) | **Polls and yields**: asks once per millisecond, and on failure sleeps with `arkrtos_task_wait(1)` |

**Token conservation lives on that dividing line**: when a dispatcher (post / unlock / signal
/ broadcast) sees a user-mode waiter at the head of the queue, it **does not pop it**; it
records the token in the object's own `count` and lets the next poll take it through the fast
path. So at any instant a token is in exactly one of two states — sitting in `count`, or
already handed to a specific ready task — and there is no third state.

## 2. Three contracts (read before touching this code)

### Contract 1: user-mode waiters only register; the actual yield happens in user mode

- The kernel-side predicate is `arkrtos_sync_in_handler()`, delegating to
  `arkrtos_port_in_isr()` (reads `IPSR`) — the only place in the tree that reads IPSR; do not
  write a second one elsewhere.
- A wait issued in handler state returns `ARKRTOS_SYNC_ERR_WOULDBLOCK(-4)`, and the caller
  **must** treat it as "registered, go poll", never as an error.
- oslib polls with `ARKRTOS_APP_POLL_MS = 1` ms; the body is `arkrtos_task_wait()`.

### Contract 2: dispatchers use `peek(only_kernel=1)` to skip user-mode waiters

`arkrtos_waiters_peek(waiters, only_kernel)` looks without popping. With `only_kernel=1`,
waiters carrying the appq marker are skipped, so a dispatcher either hands the token to a
kernel-state task that **can be resumed in place**
(`wake_reason |= ARKRTOS_WAKE_HANDOFF`) or records it in `count` for the next user-mode poll to
take on the fast path. Popping a user-mode waiter directly hands the token to a task nobody is
serving — that is a leak, not a dispatch.

### Contract 3: one token, one owner

Either one sits in `count`, or a ready task holds one. Both never hold at once. Violations
appear as "the semaphore was posted but the waiter never gets it", or conversely "two tasks
both think they own the lock".

## 3. Return values and wake reasons

### 3.1 Error codes (all negative; 0 = success)

| Name | Value | Meaning |
|---|---|---|
| `ARKRTOS_SYNC_OK` | 0 | success |
| `ARKRTOS_SYNC_ERR_PARAM` | -1 | invalid argument (handle outside its type range, out of bounds, …) |
| `ARKRTOS_SYNC_ERR_TIMEOUT` | -2 | wait timed out |
| `ARKRTOS_SYNC_ERR_DELETED` | -3 | object deleted while waiting |
| `ARKRTOS_SYNC_ERR_WOULDBLOCK` | -4 | **registered, not yet acquired** — not an error |

`WOULDBLOCK` is defined in `arkrtos_def.h:49` and `arkrtos.h:37`, each behind an `#ifndef`
guard; the driver SDK adds another same-value guard in `arkrtos_driver_sdk.h`. All four values
must agree.

### 3.2 Wake reasons are **bits**, not values

| Name | Value | Meaning |
|---|---|---|
| `ARKRTOS_WAKE_NORMAL` | 0 | normal wake (claimed by a dispatcher) |
| `ARKRTOS_WAKE_TIMEOUT` | 1 | wait timed out |
| `ARKRTOS_WAKE_OBJ_DELETED` | 2 | object deleted |
| `ARKRTOS_WAKE_HANDOFF` | 4 | dispatcher explicitly claimed this task |

> `reason == 0` is **not** proof of "got the token". A wake without
> `ARKRTOS_WAKE_HANDOFF` may come incidentally from a tick or an object deletion. Treating
> `reason == 0` as success reports failures as successes.

## 4. Handle encoding

The top 12 bits are a type tag, the low 20 bits an object index
(`ARKRTOS_HANDLE_MASK = 0xfff00000`):

| Object | Type tag | App-side create entry |
|---|---|---|
| event | `ARKRTOS_EVENT_HANDLE_FLAG` = `0x01100000` | `arkrtos_event_create()` |
| semaphore | `ARKRTOS_SEM_HANDLE_FLAG` = `0x01300000` | `arkrtos_sem_create()` |
| mutex | `ARKRTOS_MTX_HANDLE_FLAG` = `0x01400000` | `arkrtos_mutex_create()` |
| message queue | `ARKRTOS_MQ_HANDLE_FLAG` = `0x01500000` | `arkrtos_mq_create()` |
| timer | `ARKRTOS_TIMER_HANDLE_FLAG` = `0x01600000` | `arkrtos_timer_create()` |
| condition variable | `ARKRTOS_COND_HANDLE_FLAG` = `0x01700000` | `arkrtos_cond_create()` |

Each object's wait-queue capacity is `ARKRTOS_WQ_SLOTS`: by default
`ARKRTOS_MAX_SYNC_WAITERS = 4`, and the fifth waiter gets `-2` (see §6 rule 1), **which is not
an error**; with `ARKRTOS_USE_WAIT_UNBOUNDED` it grows to the task-table size (48 slots on
this board), see §5.9.

## 5. Semantics of each primitive

### 5.1 Semaphore / mutex / message queue / timer

All are "count / ownership" objects with one wait path: kernel registers → `WOULDBLOCK` →
oslib polls → fast path takes it.

### 5.2 Event

`arkrtos_event_wait(handle, timeout)`'s flag fast path returns 0 directly from the kernel
without polling. oslib's `arkrtos_event_wait()` timestamps its own start and end, and at the
timeout instant **sends one more `timeout=0` request** so the kernel removes the registration
and answers `TIMEOUT` (see §6 rule 2).

### 5.3 Condition variables (three steps, not one)

App-side `arkrtos_cond_wait()` is assembled from three SVC subcommands; the kernel **never
blocks during it**:

```
1. cond enqueue (SYNC_CTRL subcommand 14)  link self onto the condition's wait queue (idempotent)
2. mutex unlock  (subcommand 7)            release the lock; on failure cond abort and return the error
3. poll cond poll (subcommand 15)          1 = popped by signal/broadcast, <0 = error
   on timeout, cond abort (subcommand 16)   remove own registration
4. mutex lock (subcommand 6, timeout=-1)   the lock must be reacquired before returning, whatever happened
```

Subcommand 10 = `arkrtos_cond_wait_internal()` (one-step, kernel-side blocking) still exists
but **the App SDK does not use it**: it would block inside the SVC handler, hitting exactly the
constraint in §1. It is kept for in-kernel callers; Apps and drivers always use 14/15/16.

### 5.4 32-bit event set (`ARKRTOS_USE_ESET`, off by default)

`arkrtos_event_*` is a **single flag**: one flag per object, setting it broadcasts to all
waiters and a hit auto-clears it. That is insufficient when several independent conditions
exist and one task must wait for any subset (e.g. a driver with "data ready | error | timeout"
arriving from different interrupts). The 32-bit event set fills exactly that gap:

| | `event` (existing) | `eset` (this module) |
|---|---|---|
| Number of flags | 1 | 32 independent bits |
| Wait test | only that single flag | `mask` + `OR` (any bit) or `AND` (all bits) |
| After delivery | auto-clear | bits **accumulate**; only `CLEAR` clears the bits that were handed out |
| Wake scope | broadcast to all waiters | wakes only the waiters satisfied this time |
| Handoff value | none (wake = clear) | computed at handoff time and stored in the wait slot; read, never recomputed |
| Switch | always on | `ARKRTOS_USE_ESET` (default 0; off compiles `arkrtos_eset.c` to an empty object) |

**Semantic points** (read before modifying):

1. **Bits accumulate**: `set(handle, mask)` only does `flags |= mask`; it never overwrites or
   clears. Bits arriving between two `set` calls are not lost — exactly what `event` cannot do.
2. **Exactly one test**: `opt` must be either `OR` or `AND`; giving both, or neither, is
   `PARAM`.
3. **`CLEAR` is executed exactly once, by the side that got the bits**: for kernel-state waits
   `set` clears at handoff, for user-mode waits the polling consumer clears. So one bit is
   never handed to two waiters.
4. **The handoff value is not recomputed**: `got = flags & mask` computed at the `set` instant
   is stored in the wait slot; even if new bits arrive before the waiter runs, it receives the
   batch that satisfied its condition.
5. **`mask == 0` is an argument error**, not "wait for any bit" — this avoids degrading into a
   permanently true wait.

**User-mode (App / driver) waits do not register a waiter** (a deliberate special case of the
§1 dividing line, with the reason stated): bits accumulate, so the SVC only needs to "test the
condition and consume"; if unsatisfied it returns `WOULDBLOCK` for oslib to poll. Once the
condition holds it holds, and nothing is missed by not registering. Therefore at the timeout
instant there is **no need to settle with the kernel**, nor to mark the task READY from an
exception.

`arkrtos_eset_delete()` matches the other objects: all pending waiters are woken with
`ARKRTOS_WAKE_OBJ_DELETED`, and every subsequent interface returns `DELETED`. On task teardown
`arkrtos_eset_release_task()` removes it from all wait queues and reclaims the event sets it
created whose `creator_id` points at it (waking nobody, same rationale as `event`).

**On-board readings for the App-side channel** (2026-11-15, F427, example
`example/stm32f427/app_sdk/ESET_DEMO`): through **SVC 0x21** in an unprivileged task, the full
create / get / set / wait / clear / delete sequence gave `ESET: 37 pass, 0 fail`. Coverage per
item: bits **accumulate** (`set(bit1)` ORs rather than overwrites); the `got` written back by
an OR wait contains **only the bits that held at that instant**; an OR wait without `CLEAR`
does **not** clear the object; an AND shortfall gives `-2`
(`ARKRTOS_SYNC_ERR_TIMEOUT`) with `got = 0`, a complete set gives `0` with `got == mask`;
`OR|CLEAR` **clears only the two bits handed out** and leaves the rest untouched; `clear` is
bit-precise; six classes of invalid argument (no OR/AND, both given, `mask 0`, `p_got NULL`,
`set(mask 0)`, `get NULL`) all return `-1` **with the object state untouched**; two objects
have distinct handles and never cross bits; after `delete` all four entries return `-1`. The
full unit run from the same flash stayed at `11 matched / 11 passed / 129 assertions`, so
enabling the profile changed no existing case.

**On-board readings for the kernel-side and SVC-side ISR entry** (2026-11-15, F427,
`utest run eset_from_isr`): `PASS eset_from_isr_contract` with **61 assertions, 0 failures**;
full run `12 matched / 12 passed`, **190 assertions**, identical across three consecutive runs.
That one case covers two things.

(A/B/C) **Wake semantics of the internal kernel API inside a real EXTI0 handler** — the same
trigger path as the MQ case in §5.5 (`EXTI->SWIER = 1` enters the real handler, and the handler
checks `IPSR != 0` to exclude "called as an ordinary function"): a waiter genuinely blocked in
`wait_internal(..., 500)` is registered first, then `set` runs inside the handler, and the
assertion is that **when the handler returns the waiter is only `READY`, not switched in**
(reading `arkrtos_task_table[id-1].status` inside the handler gives `ARKRTOS_TASK_READY`) — the
real switch must wait for exception return and PendSV. After waking, `rc == 0`, `got` contains
only the bits that held at that instant, and `flags` is cleared per the CLEAR rule. The AND
case goes "ISR sets one bit → no wake (state still `WAIT`) → task context sets the other → only
then handoff". Invalid `mask 0` in the handler returns `ARKRTOS_ESET_ERR_PARAM` with `flags`
untouched.

(D) **Real SVC-in-ISR**: the same handler issues `SVC 0x21` — the ABI the App-side
`arkrtos_eset_set_from_isr()` → `arkrtos_call_eset_ctrl()` takes (one `SVC` instruction plus a
24-byte argument block, landing in `svc_eset_ctrl()`'s `ARKRTOS_ESET_SUB_SET` branch). Both
hard preconditions of this cell are written as assertions, not comments:

- **The SVC priority must be higher than this interrupt.** `arkrtos_port_irq_init()` gives
  SVCall 0x01; the case sets EXTI0 to logical level 4 in `isr_test_arm()` (**0x40** in
  `NVIC->IP`, SVCall 0x10), and the D section asserts `NVIC_GetPriority(EXTI0) == 4`,
  `NVIC->IP[EXTI0] == 0x40`, and `GetPriority(EXTI0) > GetPriority(SVCall)`. **Mind the CMSIS
  convention**: `NVIC_SetPriority()` takes a logical level (4-bit implementations, 0x00..0x0F),
  not the IP byte; passing 0x40 gets truncated to 0x00 by `(0x40 << 4) & 0xFF`, which would
  raise EXTI0 above SVC.
- **The argument block must live in user-visible RAM.** `svc_eset_ctrl()` first validates the
  24-byte argument block with `arkrtos_kernel_svc_args_ok()` against the `SHARE_RAM` /
  `SLOT_RAM` windows; the kernel stack is not inside. The case places the block at shared-RAM
  offset 0x800 (partition table at 0x0, crash log at the tail 0x1E00, nothing in between; one
  compile-time `#error` and one runtime assertion guard the boundary).

Readings: the shared-RAM block's `SVC` returned **0** and the waiter was set `READY` (not
switched in, since the handler had not returned); on waking `rc == 0`, `got == BIT0|BIT2`, and
`flags` was cleared by `CLEAR`. **A second SVC in the same handler with a block on the kernel
stack returned `-1`** (`ARKRTOS_ESET_ERR_PARAM`), and the probe `BIT3` did not land in the
bitmap at all — that contrast is the guard proving "argument-window validation is not fake

### 5.5 What is allowed inside an interrupt

Only four `_from_isr` entries: `arkrtos_sem_post_from_isr()`, `arkrtos_event_set_from_isr()`,
`arkrtos_mq_send_from_isr()` and `arkrtos_mq_recv_from_isr()` (the latter two delegate their
second half to `arkrtos_mq_recv_from_isr_internal()`; receiving does not go through user-mode
polling), plus `arkrtos_eset_set_from_isr()` when the switch is on. No other synchronisation
call is guaranteed safe in handler state.

`arkrtos_mq_send_from_isr()` previously had **a declaration but no definition** — it exploded
at link time, and only for those who used it. `88ea969` added the definition; host case 7b has
6 assertions on it, and it now has board readings too.

Validation level: **verified on board** (2026-11-15, F427, `utest run mq_from_isr`).

The board case `mq_from_isr_contract`
(`example/stm32f427/kernel/ARKRTOS_TEST/Core/Src/arkrtos_isr_case.c`) uses a **real interrupt**,
not "fill the wait queue by hand and read it":

- It occupies no pin: `EXTI->IMR |= 1` + `NVIC_EnableIRQ(EXTI0_IRQn)` + `EXTI->SWIER = 1`, and
  the handler clears `EXTI->PR` before doing work. In `startup_stm32f427xx.s`, `EXTI0_IRQHandler`
  is a `[WEAK]` stub, so defining the same name at board level overrides it with no vector-table
  change.
- The handler records `__get_IPSR()` and asserts it is non-zero — this excludes the fake pass
  where "someone called the handler as an ordinary function".
- The four paths each assert the return value **and the side effect**, not just the code:
  successful send → the task side must receive the same message (same word count and contents);
  successful receive → the queue must be empty afterwards; empty queue →
  `ARKRTOS_MQ_ERR_EMPTY(-1)` with no registration and no block; full queue →
  `ARKRTOS_MQ_ERR_FULL(-1)` with all 8 old messages verified one by one.
- Teardown disables the source (`NVIC_DisableIRQ` plus clearing `IMR`/`SWIER`/`PR`), deletes the
  queue, and asserts the handle is neither a live object nor usable, so `utest run` is
  repeatable.

Measured: `PASS mq_from_isr_contract` with 36 assertions and 0 failures; full run
`12 matched / 12 passed`, 169 assertions, identical over two consecutive runs.

**Negative control** (the gate carries its own anti-fake-green check): replacing the
implementation of `arkrtos_mq_send_from_isr()` with "do nothing, `return 0`" — the most likely
degenerate form of "declared but not defined" — produced 5 red lines in the same case after

Boundary: only the "one message in, one message out" contrast is covered; **waking a blocked
sender after an ISR receives a message** (`arkrtos_mq_wake_one` only sets READY, no switch) has
no separate board reading — that needs a multi-task case and is the next level of debt.
Additionally the `eset` `set` wake semantics inside a real handler and the SVC 0x21 ABI used by
the App-side `arkrtos_eset_set_from_isr()` are both on board (§5.4,
`eset_from_isr_contract`, 61 assertions including the 1-positive/1-negative contrast on the
argument block location); **still uncovered** is "unprivileged App code + handler state" — no
ABI to register an ISR exists, so the unprivileged side cannot enter handler state.

### 5.6 Recursive mutex (`ARKRTOS_USE_MTX_RECURSIVE`, off by default)

A normal mutex is **not recursive**: locking again from the owner returns
`ARKRTOS_SYNC_ERR_RECURSIVE(-1)`. That is deliberate — recursive semantics must be an explicit
choice, otherwise "same-task re-entry" is silently accepted and mismatched depth/unlock pairings
become invisible.

With the switch on, an extra create entry appears, `arkrtos_mtx_create_recursive()`
(SVC 0x15 subcommand 17):

| Action | Normal lock | Recursive lock |
|---|---|---|
| owner locks again | `-1` (refused) | `0`, `nest++` |
| owner unlocks (`nest>0`) | n/a | `0`, `nest--`, **not released** |
| owner unlocks (`nest==0`) | release / hand off to a waiter | same |
| non-owner unlocks | `-1` | `-1` |

Boundaries and costs:

- Only locks **explicitly created through the recursive entry** are recursive; normal locks in
  the same table keep their semantics (`recursive` is an object field).
- With the switch off, the create function, the SVC subcommand `case` and the SDK wrapper are
  not compiled in, so size and behaviour are bit-identical.
- `nest` is `uint8`: more than 255 levels wraps; in practice nesting depth should be treated as
  a design error rather than normal use.
- Recursive does not mean cross-task: ownership stays on `owner`, and priority inheritance
  applies to the owner.

Validation level: **verified on board** (2026-11-14, F427). The board case
`mtx_recursive_contract` passes under `utest run`: three consecutive locks from the same task
all succeed, three unlocks pair down level by level, the lock can be reacquired after release,
and **a normal lock in the same table still refuses re-entry** (recursion is an object property,
not a global semantic). The host `sync-host` case also covers nest counting and unlock pairing;
the default profile link stayed at `Code=220290`.

### 5.7 Multi-level priority inheritance

Priority inheritance previously only raised the holder for the direct waiter. It now
**propagates** along the wait chain:

```
C(7) waits for a lock held by B → B(5) is raised to 7
B(5) is itself waiting for a lock held by A(3) → A(3) is raised to 7 too
after C releases / times out, the raise unwinds level by level to each original priority
```

The evidence is the chained host scenario `A(3) → B(5) → C(7)` (commit `a715887`, 5 assertions):
it checks the **effective priority of the holder at the end of the chain** and **the level-by-level
unwind after release**, not a single waiter's wake-up. Boundary: `syncinfo` prints only the
effective priority, not "who raised it"; deleting an object anywhere in the chain wakes
everything level by level with `OBJ_DELETED`, with no guarantee of original-priority order.

Validation level: **verified on board** (2026-11-15, F427, `utest run pi_chain`).

The board case `mtx_pi_chain_contract` (`kernelsrc/src/arkrtos_utest_cases.c`) builds the chain
with **real tasks**, not by stuffing pointers into the wait queue as the host case does:

```
console(14) holds L1  ──>  MID(10) holds L2, waits for L1  ──>  HIGH(6) waits for L2
```

The criterion is **the console's own effective priority** — a one-hop implementation stops at
MID's level (10), while chain propagation must reach HIGH's level (6). Measured:

```
RUN   mtx_pi_chain_contract
PASS  mtx_pi_chain_contract
utest: 1 matched, 1 passed, 0 failed, 0 skipped; assertions 20 run / 0 failed
```

**The same assertion was run as a negative control**: changing the propagation condition from
"the waiter's current priority" to "the waiter's base priority" (equivalent to one hop, no
chain) and reflashing made the same case fail immediately, with the failing value exactly the
middle link:

```
! arkrtos_utest_cases.c:722: p_self->priority == high_prio  (got 10 / 0xA, want 6 / 0x6)
FAIL  mtx_pi_chain_contract   (1/20 assertions failed)
```

After restoring and reflashing, `utest run` gives 10 of 10 cases passing and 93 assertions with
0 failures (identical over two consecutive full runs, task slots reusable, no leak). Boundary:
only one chain of three levels and a single holding relation; multiple waiters raising the same
holder, an object deleted mid-chain, and a task killed during escalation still have no board
readings.

### 5.8 Probing several objects for readiness (SVC 0x22, `ARKRTOS_USE_WAITMULTI`, off by default)

Ask once which of a group of handles is ready, and get a 32-bit mask:

```c
int32 arkrtos_wm_probe_internal(const uint32 *handles, uint32 n, uint32 opt, uint32 *ready_mask);
/* 0 = condition met; -1 = invalid argument/handle; -2 = not yet satisfied */
```

| Item | Value |
|---|---|
| `opt` | `ARKRTOS_WM_OPT_ANY` (any handle ready) or `ARKRTOS_WM_OPT_ALL` (all ready) |
| Supported handles | `sem` (has a token) / `mtx` (not held) / `mq` (has a message) / `event` (flag set) |
| Unsupported | the 32-bit event set (each entry would need its own mask, beyond the "one handle one bit" model), bare indices |
| Consumption | **none**: the probe is read-only and the token stays in the object |
| Limit | `ARKRTOS_WAITMULTI_MAX_OBJS` per call (default 16); the 32-bit mask is a hard limit |

App-side `arkrtos_wait_multi()` with a timeout is a **polling** wait
(`ARKRTOS_APP_POLL_MS = 1`): once the probe reports readiness, the caller takes each object
with its own `timeout=0`. Two boundaries must be stated:

1. **The wake latency bound is one polling period** (1 ms), not zero;
2. The window between "probe saw it ready" and "caller takes it" **cannot be eliminated** — the
   inherent cost of a non-destructive probe, since the kernel registers no waiter and therefore
   has no atomic handoff.

Why not "register a waiter in the kernel and block once": registering a waiter on a semaphore
would make `sem_post` hand the token to the prober under HANDOFF without consuming it, losing
the token; a dedicated notify registry would need hooks in sem / mq / event for an intrusion far
bigger than the benefit.

Validation level: **verified on board** (2026-11-14, F427). The board case
`waitmulti_probe_contract` passes: one bit per handle, correct ANY/ALL decisions, **the token
still present after repeated probes** (a following `timeout=0` take succeeds, proving the probe
non-destructive), and an invalid handle rejecting the whole group with the mask cleared. The
host side adds 24 assertions plus `-fsyntax-only` over 6 files at the ON profile.

### 5.9 Waiter capacity scaled to the task table (`ARKRTOS_USE_WAIT_UNBOUNDED`, off by default)

| | Off (default) | On |
|---|---|---|
| `ARKRTOS_WQ_SLOTS` | `ARKRTOS_MAX_SYNC_WAITERS` (4) | `ARKRTOS_TASK_MAX_NUM` (48 on this board) |
| Queue structure | static array, fixed length | the same static array, just longer |
| Logic | unchanged | unchanged (not even one branch) |

The reasoning: **a task can only wait on one object at a time**, so the waiter count on any
object cannot exceed the task count — for this kernel that is "unbounded", with no linked list
and no heap required. The cost is that every object table grows linearly (4 bytes per slot ×
the queue count of each table).

**This is not a linked-list unbounded design**: truly decoupling waiter count from the task
table would mean changing 46 wait-queue sites (sync 24 + mq 8 + sbuf 7 + event 7), risk out of
proportion to benefit, so it was not done.

Validation level: **the ON profile does not fit on this board** (the only profile rejected by
hardware). Adding `ARKRTOS_USE_WAIT_UNBOUNDED=1` to the F427 test image breaks the link:
`L6406E: No space in execution regions`, 108 errors, `aggregate size 0x2958 bytes could not fit
into .ANY selector(s)` — every object table grows from 4 slots to 48 at once. So there is **no
board-level behavioural reading**, only the `sync` host behaviour check (76 checks,
`WQ-SLOTS=48`) and the ON-profile compile layer for `mq` / `sbuf` / `event` (array lengths
derive correctly). Verifying on board would first require trimming the test image to fit
(disabling lwIP / VFS / SBUF and so on); that was not done.

### 5.10 SMP skeleton (`ARKRTOS_USE_SMP`, off by default)

**The conclusion first: this is not multi-core support.** The scheduler is still single-core —
one global current task id (`arkrtos_current_task_id`), one global ready bitmap, one global
delay queue. Enabling the switch does not run tasks on two cores simultaneously, nor make object
tables per-core.

What it provides is a multi-core foundation:

| Item | Content |
|---|---|
| `ARKRTOS_CPU_NUM` | 1..8 (the online mask is `uint32`, and up to 8 cores is still auditable by hand) |
| Per-core state `arkrtos_smp_cpu_t` | `online` / `started` / `current_task_id` / `tick` / `ipi_count` / `idle_count` |
| `arkrtos_smp_init()` | CPU0 comes online directly, 1..N-1 go to the port's `arkrtos_port_cpu_start()`; returns the number of cores whose start request was accepted |
| Secondary entry | `arkrtos_smp_secondary_main(cpu)`: mark online → enable interrupts → **spin in WFI**, taking no part in scheduling |
| Inter-core interrupt | `arkrtos_smp_send_ipi()` → `arkrtos_port_send_ipi()`; receiver `arkrtos_smp_ipi_handler()` (counts only by default; an application may override with a same-name strong symbol) |
| Single-core port | `arkrtos_port_cpu_start()` / `arkrtos_port_send_ipi()` return `-1` (explicitly "no such path", never fake success) |

Three deliberate design points:

1. **`started` and `online` are tracked separately**: an accepted start request does not mean
   the core is running; the online bit is set by the secondary core itself.
2. **Out-of-range core numbers never land**: `arkrtos_smp_cpu_online()` ignores them;
   `arkrtos_smp_cpu_self()` clamps to core 0 when it reads an out-of-range number — a misread
   core number must not become an out-of-bounds write.
3. **CPU0 is brought up by `arkrtos_kernel_module_init()`** (before the scheduler starts): a
   secondary core starting after the scheduler would see a scheduler that is not its own.

Validation level: **not verified (no multi-core board)**. Existing evidence is "the skeleton is
self-consistent": 44 host assertions (online mask, out-of-range core numbers, no fake online
when start is refused, IPI only to online cores, re-initialisation clears state, per-core
counters only on the current core) plus `-fsyntax-only` over 5 files at the ON profile. Real
secondary-core startup, IPI delivery and latency, and CAS contention when several cores set the
mask simultaneously have **no** board readings.

## 6. Two hard rules (learned the hard way)

### Rule 1: `-2` from a duplicate registration is not an error

On the second poll the task is already on the wait queue, and `waiter_add` returns `-2`
(already registered). **Call sites must distinguish `-2` from a real failure.** Once,
`arkrtos_event.c` and the condition-variable branch of `arkrtos_sync.c` tested `< 0`, treated
"already registered" as failure and returned immediately; the symptom was `evt.wait_timeout`
coming back after only 1 ms (board self-test FAIL).

> The fix is not "ignore -2" but writing, at every call site,
> `if((added < 0) && (added != -2)) { ... }`. Someone writing `if(added < 0)` will hit this again.

### Rule 2: `timeout == 0` must remove your own registration

`timeout=0` on the wait path does not mean "do not wait" but "remove my registration and answer
TIMEOUT". The kernel does not arm a timer for user-mode waiters, so this removal can only be
issued explicitly by oslib at the timeout instant. Miss it and the waiter stays on the queue
forever, and every later dispatch looks at a task that has already gone.

### Aside: service-layer idempotence is not kernel-strict semantics

`arkrtos_fs_mount()` refuses a duplicate mount (it would leak the old `lfs_t`); that is **kernel
strict semantics and must not be removed**. The App-side "ensure it is mounted" need is met at
the FILE_SYS service layer (`arkrtos_task.c`, case 6):
`(arkrtos_fs_mounted() != 0u) ? 0 : arkrtos_fs_mount_default()`. The shell keeps strict
mount / unmount pairing.

## 7. Troubleshooting entry points

### 7.1 `syncinfo` — a health check for synchronisation objects

```
sem  used  count  owner  creator  waiters
 0   1     3      -1     1         t4
  sem 0: posts=12 takes=9 queued=1 last_waiter=t4 qbefore=2 woke=t4 reason=4
sync diagnostics: ghost=0 dup=940
sync ghost  : n=0 idx=-1 tid=t0
sync appwait: hit=480
```

| Field | How to read it |
|---|---|
| `count` | tokens currently sitting in the object; `owner` is the mutex holder |
| `waiters` | tasks on the queue, as `t<id>` |
| `posts` / `takes` | dispatch / take counts |
| `qbefore` | how many waiters were queued at the instant of dispatch |
| `woke` / `reason` | who the last dispatch woke, and the reason bit (4 = HANDOFF) |
| `ghost` | wakes treated as success without `ARKRTOS_WAKE_HANDOFF`; **must be 0** |
| `dup` | duplicate registrations. Normal under the polling model (every poll hits `-2` once); not an error |
| `appwait hit` | user-mode registration count, i.e. how often the polling path ran |

### 7.2 `log` — console and token conservation

```
console   : lock_giveup=0 tx_drop=0 B fifo_full_retries=134831
fifo      : bad_header=0 bytes_lost=0
sync      : ghost=0 dup=940
```

`tx_drop` is the real number of lost bytes; `fifo_full_retries` is the number of **rejected
attempts**, not losses. Non-zero `bad_header` / `bytes_lost` means the FIFO buffer header was
overwritten (historically a main-stack overflow), and output on that path is silently dropped.

### 7.3 `task <id> [any third argument]` — one task's state on the spot

```
task 4 sp=0x2001A3B0 st=SUSPENDED frame words:
  sp+0    0x2001A3B8
  ...
  blocks=137 last_reason=4
```

The third argument only adds the `blocks=` / `last_reason=` lines. The frame is **all 56 words
verbatim**: whether the FPU extended frame is present decides which word is the PC, and guessing
turns a backtrace into a wrong answer, so no "parsed" view is offered.

## 9. Capacity budget of the kernel synchronisation tables (multiple concurrent Apps)

The five tables — semaphore, mutex, event, message queue, condition variable — are **globally
fixed-size**, with capacities in `kernelsrc/include/arkrtos_config.h`
(`ARKRTOS_SEM_NUM` / `ARKRTOS_MTX_NUM` / `ARKRTOS_EVENT_NUM` / `ARKRTOS_MQ_NUM` /
`ARKRTOS_COND_NUM`).

Key point: **when a table is full, `arkrtos_sem_create_internal()` returns -1 without
distinguishing "duplicate name" from "no slot"** (`kernelsrc/src/arkrtos_sync.c`). The POSIX
layer maps that -1 to `ENOMEM`, so it surfaces as a `pthread_create` failure — **it looks like
out-of-memory, but it is a full table**.

### 9.1 How many slots each user takes

| User | Semaphore slots |
|---|---|
| Each POSIX thread (`pthread_create`) | 2 (named like `pth<id%10>g` / `pth<id%10>d`) |
| Each `sem_t` (`sem_init` / `sem_open`) | 1 |
| COND waiter gate | each waiting condition-variable waiter takes additional slots |

So **capacity must be sized for the sum of all concurrent users**, not a single App's peak.

### 9.2 A measured case: boot self-test 109/6 → 116/0

The same APP_DEMO image once produced "boot auto-start self-test `pass=109 fail=6` (all six are
`posix.cond_*`)" while a runtime `app stop/start` gave `pass=116 fail=0`.

- First, field-by-field comparison of the image header (`crc32=0xE59BED1F`, `nominal_base`,
  `image_size`, `entry_offset`) proved the board was running **a byte-identical build of the
  current sources**, ruling out "stale image";
- Then the accounting: at boot, POSIX_DEMO's two threads are alive and take 4 + 1; APP_DEMO
  needs 4 + 2 more → **11 > `ARKRTOS_SEM_NUM`(8)**, so the table must overflow;
- On a runtime restart of APP_DEMO, POSIX_DEMO's threads had joined and returned their slots,
  so it passed.
- Fix: `ARKRTOS_SEM_NUM` 8 → 24. After rebuilding and reflashing the F427, **the boot auto-start
  self-test returned to `pass=116 fail=0`**.

> Lesson: **a full table disguises itself as ENOMEM.** When adding or removing threads and
> semaphores in a multi-App / multi-thread scenario, re-check these table capacities.

## Host gate: these contracts are now re-runnable

`tools/sync_host_gate.py` (the `sync-host` item of `ci_gate`) compiles `arkrtos_sync.c` verbatim
on a PC, and the test replaces `arkrtos_task_get_current()` with a **settable** real TCB
pointer, so ownership decisions ("who may unlock", "what counts as a duplicate lock") are really
executed. 51 assertions cover:

- **Count conservation**: taking tokens one by one from the initial count → at count 0,
  `timeout == 0` returns `ARKRTOS_SYNC_ERR_TIMEOUT`; a timed-out wait neither creates nor
  destroys a token; a post with no waiters leaves the token in the count, where it can be taken
  **exactly once**.
- **Ownership**: the owner locking again is refused (not recursion); a non-owner unlock is
  refused with the owner unchanged; after unlock another task can take it; deleting a held lock
  makes it no longer count as "held", and every interface rejects it afterwards.
- **Delete semantics**: `sem_delete` / `mtx_delete` now check `used` too (previously a `delete`
  on a non-existent object returned 0 = "deleted"), consistent with `cond_delete` and
  `send/recv` — under the "fail rather than lie" rule, reporting "nothing was deleted" as
  success is a wrong answer.

### Task teardown cleanup: `arkrtos_sync_release_task()` (2026-11-17)

When a task dies the synchronisation layer must do three things, all in this one function: remove
it from the wait queues of the cond / sem / mtx tables, hand its mutex to the highest-priority
waiter if it holds one, and reclaim the objects it created. This path used to carry a **silent**
defect: the local pointer `p_tsk` was declared but never assigned, so all three table scans
compared against a wild pointer — the effect was that a dead task **stayed forever** in other
tasks' wait queues (and would later be woken as a task that no longer exists), and its lock was
**never handed over**.

It compiled, and at the default profile it ran without complaint; the `-Wall -Wextra`
(`warn-clean` gate) surfaced it: `'p_tsk' may be used uninitialized`. The fix adds
`p_tsk = &arkrtos_task_table[task_id - 1];` (the same function's `appq_set` already assumed a
valid `task_id`), plus 9 assertions in the host gate that pin the behaviour: the lock handed to
the highest-priority waiter, the receiver back to ready, the wake reason carrying
`ARKRTOS_WAKE_HANDOFF`, the receiver no longer on the original queue, the dead task removed from
the semaphore queue, **other tasks' registrations on the same queue surviving**, and the debug
view's owner/waiter matching. Removing the fix makes 7 of those 9 fail (anti-fake-green).

**Boundary**: this is the "task teardown" path, reached only when a real task is destroyed; on
the host it is called directly, so what it proves is **correct state transition**, not "the real
destroy flow has been exercised" — that still needs the board.

**Not proven**: blocking, wake-up, token handover, the priority-inheritance chain — those need a
real scheduler and tick; the test's `block_in_critical()` returns -1 directly, so the
`timeout > 0` branch is unreachable. The board case remains the only evidence for those.
