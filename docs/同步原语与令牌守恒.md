# 同步原语与令牌守恒

> 这份文档讲一件事：**Ark RTOS 里一个同步令牌（信号量计数、互斥锁所有权、条件变量的一次唤醒）
> 为什么必须、以及如何保证始终只有一个属主。** 前面先给结论，再给机制，最后给排障入口。

适用版本：`ark-rtos` master，F427 / F401 双板。
文中标注的验证档位只有三档：**仅编译通过 / 上板验证过 / 未验证**。

---

## 1. 一句话结论

内核**不能在 SVC 处理器内部完成一次阻塞等待**，因为 `PendSV` 永远不能抢占 `SVC`
（`kernelsrc/port/arm/cortex-m4/arkrtos_port.c` 的 `arkrtos_port_switch_task()` 只做
`SCB->ICSR = SCB_ICSR_PENDSVSET_Msk`，注释写明了这一点）。因此从 App 发起的等待被拆成两半：

| 谁 | 做什么 |
|---|---|
| 内核（SVC 处理器内） | **只登记**：把等待者挂到对象的等待队列，然后返回 `ARKRTOS_SYNC_ERR_WOULDBLOCK` |
| App 侧 oslib（Thread 态） | **轮询 + 让出**：每 1 ms 问一次，问不到就 `arkrtos_task_wait(1)` 睡一会儿 |

**令牌守恒就落在这条分界上**：派发方（post / unlock / signal / broadcast）看到队首是用户态等待者时
**不弹队列**，改为把令牌记进对象自己的 `count`，等下一次轮询从快路拿走。
于是任何时刻令牌只有两种状态——躺在 `count` 里，或者已经交给一个具体的就绪任务——不存在第三种。

---

## 2. 三条契约（改这块代码前必读）

### 契约一：用户态等待者只登记，真正让出发生在用户态

- 内核侧判据是 `arkrtos_sync_in_handler()`，它委托 `arkrtos_port_in_isr()`（读 `IPSR`）——
  全工程只有一处读 IPSR，别在别处再写一份。
- 处于 handler 态的等待调用返回 `ARKRTOS_SYNC_ERR_WOULDBLOCK(-4)`，
  调用方**必须**把它识别成"已登记，去轮询"，不能当成错误。
- oslib 的轮询粒度是 `ARKRTOS_APP_POLL_MS = 1` ms，轮询体是 `arkrtos_task_wait()`。

### 契约二：派发方用 `peek(only_kernel=1)` 跳过用户态等待者

`arkrtos_waiters_peek(waiters, only_kernel)` 是"看不弹"的查看函数。`only_kernel=1` 时，
带 appq 标记的等待者被跳过，于是：

- 派发方要么把令牌交给一个**能被就地恢复**的内核态任务（`wake_reason |= ARKRTOS_WAKE_HANDOFF`），
- 要么把令牌记进 `count`，等用户态等待者下一次轮询从快路取走。

直接 `pop` 一个用户态等待者等于把令牌交给一个没人服务的任务——那是泄漏，不是派发。

### 契约三：一个令牌只有一个属主

`count` 里有一个，或某个就绪任务手里有一个。两者不会同时成立。
违反这条契约的表现是"信号量明明 post 过、等待方却永远拿不到"，或反过来"两个任务同时认为拿到了锁"。

## 3. 返回值与唤醒原因

### 3.1 错误码（都是负值，0 = 成功）

| 名称 | 值 | 含义 |
|---|---|---|
| `ARKRTOS_SYNC_OK` | 0 | 成功 |
| `ARKRTOS_SYNC_ERR_PARAM` | -1 | 参数非法（句柄不在本类型区间、越界等） |
| `ARKRTOS_SYNC_ERR_TIMEOUT` | -2 | 等待超时 |
| `ARKRTOS_SYNC_ERR_DELETED` | -3 | 等待期间对象被删除 |
| `ARKRTOS_SYNC_ERR_WOULDBLOCK` | -4 | **已登记，尚未拿到**——不是错误 |

`WOULDBLOCK` 在 `arkrtos_def.h:49` 与 `arkrtos.h:37` 各有一份定义，都带 `#ifndef` 守卫；
驱动 SDK 侧在 `arkrtos_driver_sdk.h` 另加同值守卫。四处的值必须一致。

### 3.2 唤醒原因是**位**，不是值

| 名称 | 值 | 含义 |
|---|---|---|
| `ARKRTOS_WAKE_NORMAL` | 0 | 正常唤醒（已被派发方认领） |
| `ARKRTOS_WAKE_TIMEOUT` | 1 | 等待超时 |
| `ARKRTOS_WAKE_OBJ_DELETED` | 2 | 对象已删除 |
| `ARKRTOS_WAKE_HANDOFF` | 4 | 派发方明确认领了本任务 |

> `reason == 0` **不是**"拿到令牌"的证明。一次没带 `ARKRTOS_WAKE_HANDOFF` 的唤醒，
> 有可能是节拍、对象删除等原因顺带产生的。把 `reason == 0` 当成成功判据，
> 就会把失败报成成功。

## 4. 句柄编码

句柄高 12 位是类型标记，低 20 位是对象下标（`ARKRTOS_HANDLE_MASK = 0xfff00000`）：

| 对象 | 类型标记 | App 侧创建入口 |
|---|---|---|
| 事件 | `ARKRTOS_EVENT_HANDLE_FLAG` = `0x01100000` | `arkrtos_event_create()` |
| 信号量 | `ARKRTOS_SEM_HANDLE_FLAG` = `0x01300000` | `arkrtos_sem_create()` |
| 互斥锁 | `ARKRTOS_MTX_HANDLE_FLAG` = `0x01400000` | `arkrtos_mutex_create()` |
| 消息队列 | `ARKRTOS_MQ_HANDLE_FLAG` = `0x01500000` | `arkrtos_mq_create()` |
| 定时器 | `ARKRTOS_TIMER_HANDLE_FLAG` = `0x01600000` | `arkrtos_timer_create()` |
| 条件变量 | `ARKRTOS_COND_HANDLE_FLAG` = `0x01700000` | `arkrtos_cond_create()` |

每个对象的等待队列容量是 `ARKRTOS_WQ_SLOTS`：默认 `ARKRTOS_MAX_SYNC_WAITERS = 4`，
第 5 个等待者会拿到 `-2`（见 §6 规则一），**这不是错误**；打开
`ARKRTOS_USE_WAIT_UNBOUNDED` 后它放大到任务表容量（本板 48 槽），见 §5.9。

## 5. 各原语语义

### 5.1 信号量 / 互斥锁 / 消息队列 / 定时器

都是"计数/所有权"型对象，等待路径统一：内核登记 → `WOULDBLOCK` → oslib 轮询 → 快路取走。

### 5.2 事件

`arkrtos_event_wait(handle, timeout)` 的 flag 快路在内核侧直接返回 0，不进轮询。
oslib 的 `arkrtos_event_wait()` 自己记账起止时间，超时那一刻会**再发一次 `timeout=0` 的请求**，
让内核摘除自身登记并回答 `TIMEOUT`（见 §6 规则二）。

### 5.3 条件变量（三步式，不是一步式）

App 侧 `arkrtos_cond_wait()` 由三个 SVC 子命令拼成，内核侧**全程不阻塞**：

```
1. cond enqueue (SYNC_CTRL 子命令 14)  把自己挂到条件的等待队列（幂等）
2. mutex unlock  (子命令 7)            放锁；放锁失败就 cond abort 后返回错误
3. 轮询 cond poll (子命令 15)          1 = 被 signal/broadcast 弹出，<0 = 出错
   超时则 cond abort (子命令 16)       摘除自身登记
4. mutex lock (子命令 6, timeout=-1)   不管怎么结束，返回前必须把锁拿回来
```

内核里还留着**子命令 10 = `arkrtos_cond_wait_internal()`**（一步式、内核侧阻塞）。
App SDK **不使用它**：它会在 SVC 处理器里阻塞，正好撞上 §1 那条硬约束。
它保留给内核自身调用者，App/驱动一律走 14/15/16。

### 5.4 32 位事件集（`ARKRTOS_USE_ESET`，默认关）

`arkrtos_event_*` 是**单标志**：一个对象一个 flag，置位后广播唤醒所有等待者，命中即自动复位。
这在"多个条件各自独立、一个任务要等其中任意几个凑齐"的场景不够用（例如驱动里
"数据就绪 | 错误 | 超时"三路信号分属不同中断）。32 位事件集补的就是这一块：

| | `event`（既有） | `eset`（本模块） |
|---|---|---|
| 旗帜数量 | 1 个 | 32 个独立位 |
| 等待判定 | 只等那一个 flag | `mask` + `OR`（任一位）或 `AND`（全部位） |
| 交付后 | 自动复位 | 位**累加**保留；只有 `CLEAR` 选项才按"拿走的那些位"清除 |
| 唤醒范围 | 广播给所有等待者 | 只唤醒本次被满足的那些等待者 |
| 交班值 | 无（唤醒即复位） | 交接时刻算定并存进等待槽，醒来只读不重算 |
| 开关 | 常开 | `ARKRTOS_USE_ESET`（默认 0，关时 `arkrtos_eset.c` 编为空对象） |

**语义要点**（改这块代码前必读）：

1. **位是累加的**：`set(handle, mask)` 只做 `flags |= mask`，不覆盖、不清零。
   两次 `set` 之间到来的位不会丢——这正是 event 做不到的事。
2. **判定二选一**：`opt` 必须且只能给 `OR` 或 `AND` 之一，两个都给或都不给一律 `PARAM`。
3. **`CLEAR` 只由"拿到位的那一方"执行一次**：内核态等待由 `set` 在交接时清，
   用户态等待由轮询到的消费者清。因此同一位不会被两个等待者各拿一份。
4. **交班值不重算**：等待者在 `set` 那一刻被算出的 `got = flags & mask` 会存进它的槽位，
   即使它醒来前又有新的位被置上，它拿到的仍是**满足它条件的那一批**。
5. **`mask == 0` 是参数错误**，不是"等任意位"——避免退化成恒真等待。

**用户态（App / 驱动）的等待不登记等待者**（与 §1 分界的特例，理由要写清）：
位是累加的，SVC 内只需要"判条件 + 消费"，未满足就返回 `WOULDBLOCK` 让 oslib 轮询；
条件一旦成立就是成立，不会因为没登记而错过。于是超时那一刻**不需要回内核清账**，
也不需要在异常里把任务置 READY。

`arkrtos_eset_delete()` 与其它对象一致：把还挂着的等待者全部以
`ARKRTOS_WAKE_OBJ_DELETED` 唤醒，之后的接口一律返回 `DELETED`。
任务下线时 `arkrtos_eset_release_task()` 会把它从所有等待队列摘除，
并回收它创建的、`creator_id` 指向它的那些事件集（不唤醒任何人，与 `event` 同理由）。

**App 侧通道的上板读数**（2026-11-15，F427，例程
[`example/stm32f427/app_sdk/ESET_DEMO`](../example/stm32f427/app_sdk/ESET_DEMO/README.md)）：
经 **SVC 0x21** 在非特权任务里跑完 create / get / set / wait / clear / delete 全程，
`ESET: 37 pass, 0 fail`。逐条覆盖：位**累加**（`set(bit1)` 是或上去不是覆盖）；
OR 等待写回的 `got` **只含当时成立的那些位**；不带 `CLEAR` 的 OR 等待**不清对象**；
AND 短板 → `-2`（`ARKRTOS_SYNC_ERR_TIMEOUT`）且写回 0、凑齐 → `0` 且 `got == mask`；
`OR|CLEAR` **只清交出的那两位**、其余位原样保留；`clear` 精确到指定位；
六类非法参数（无 OR/AND、两者同给、`mask 0`、`p_got NULL`、`set(mask 0)`、
`get NULL`）全部 `-1` **且对象状态一位不动**；两个对象句柄不同、位不串台；
`delete` 之后四个入口全 `-1`。
同一次烧录的全量单测仍是 `11 matched / 11 passed / 129 assertions`，开档没有改变既有用例。

**内核侧与 SVC 侧 ISR 入口的上板读数**（2026-11-15，F427，`utest run eset_from_isr`）：
`PASS eset_from_isr_contract`，**61 条断言 0 失败**；全量 `12 matched / 12 passed`、
**190 条断言**，连跑三遍同结果。这一条用例同时覆盖两件事。

(A/B/C) **内核内部 API 在真 EXTI0 handler 里的唤醒语义**——走的是与 §5.5 的 MQ 用例同一条
触发路径（`EXTI->SWIER = 1` 进真 handler，handler 里断 `IPSR != 0` 排除“被当普通函数调了一下”）：
先登记一个真阻塞在 `wait_internal(..., 500)` 上的等待者，再在 handler 里 `set`，断言
**handler 返回时等待者只是 `READY`、没有被切换进去**（在 handler 内直接读
`arkrtos_task_table[id-1].status`，等于 `ARKRTOS_TASK_READY`）——真正切换必须等异常返回走 PendSV；
醒来后 `rc == 0`、`got` 只含当时成立的那几位、`flags` 按 CLEAR 规则被清。
AND 场景走「ISR 只补一位 → 不唤醒（状态仍是 `WAIT`）→ 任务上下文再补一位 → 才交班」；
非法 `mask 0` 在 handler 里返回 `ARKRTOS_ESET_ERR_PARAM` 且 `flags` 一位不动。

(D) **真 SVC-in-ISR**：同一个 handler 里发 `SVC 0x21`——就是 App 侧
`arkrtos_eset_set_from_isr()` → `arkrtos_call_eset_ctrl()` 走到的那一条 ABI
（一条 `SVC` 指令 + 24 字节参数块，落到 `svc_eset_ctrl()` 的 `ARKRTOS_ESET_SUB_SET` 分支）。
这一格的两条硬前置都写成断言，不是注释：

- **SVC 的优先级必须高于本中断**。`arkrtos_port_irq_init()` 给 SVCall 的是 0x01；
  用例在 `isr_test_arm()` 里把 EXTI0 设成逻辑档位 4（`NVIC->IP` 里是 **0x40**，SVCall 是 0x10），
  D 段断言 `NVIC_GetPriority(EXTI0) == 4`、`NVIC->IP[EXTI0] == 0x40`、
  且 `GetPriority(EXTI0) > GetPriority(SVCall)`。**注意 CMSIS 的口径**：`NVIC_SetPriority()`
  收的是逻辑档位（4 位实现，0x00..0x0F），不是 IP 字节；直接传 0x40 会被
  `(0x40 << 4) & 0xFF` 截成 0x00，等于把 EXTI0 提到比 SVC 还高。
- **参数块必须落在用户可见 RAM**。`svc_eset_ctrl()` 先用 `arkrtos_kernel_svc_args_ok()`
  校验 24 字节参数块是否在 `SHARE_RAM` / `SLOT_RAM` 窗口里；内核栈不在窗口内。
  用例把参数块放在共享 RAM 偏移 0x800（分区表在 0x0、崩溃日志在尾部 0x1E00，中间无人使用；
  用例里有编译期 `#error` 与运行期断言各一道边界检查）。

读数：共享 RAM 参数块那次 `SVC` 返回 **0**，等待者被置 `READY`（handler 还没返回，没被切进去），
醒来 `rc == 0`、`got == BIT0|BIT2`、`flags` 被 CLEAR 清空；**同一次 handler 里再拿内核栈上的
参数块发一次，返回 `-1`**（`ARKRTOS_ESET_ERR_PARAM`），且试探用的 `BIT3` 一位都没落到位图上——
这条对照就是“参数窗口校验不是假绿”的闸门。

**三组负对照**（都做过、都还原，还原后 `git diff` 为空）：

1. 注掉 `arkrtos_eset_set_internal()` 里的 `arkrtos_eset_ready(idx, p_w->task)`：
   场景 A 就报红（`waiter_state` 停在 `2`/`WAIT`、`wait_rc == -2`、`got` 仍是初值 `0xFFFFFFFF`），
   `18/40` 条断言跑到 3 条失败即中止。
2. 让 `arkrtos_kernel_svc_args_ok()` 无条件放行：D 段两条红——
   `s_isr_eset_svc_ret_kstack` 拿到 `0`（应为 `-1`）、`flags` 变成 `0x8`（被拒的那次 `set(BIT3)`
   真落到位图上了），`FAIL (2/61 assertions failed)`。
3. 把 EXTI0 的优先级改回复位值 0（高于 SVCall）后跑同一条用例：**D 段直接把板子打复位**——
   串口上没有任何 `PASS`，只有内核重启横幅；`crash` 的 `boots` 计数 +1、没有槽位崩溃记录
   （内核上下文故障不进槽位账）。这与「`SVC` 在优先级不高于当前中断时升级为 HardFault，
   本工程的 `HardFault_Handler` 是 `while(1)`，随后 IWDG（4000 ms）复位」一致；
   **这一格只写观察到的“复位”，没有从 CFSR 读到 `UFSR.SVCALL` 位**。

边界（写清这一格没覆盖什么）：**调用方是内核 handler（handler 态天生特权）**，不是
“未特权 App 代码在 handler 里发 SVC”——本工程没有“App/驱动注册 ISR”的 ABI，未特权侧在
架构上就进不了 handler 态。所以证据链是：**同一条 SVC 0x21 ABI** 在**真 handler 上下文**里
跑通（thread 态那条已由 `ESET_DEMO` 覆盖），而“未特权 + handler 态”这个组合在本工程里
没有可构造入口。另有两处本板降配：F427 测试镜像放不下默认 8 个事件集对象，
`ARKRTOS_ESET_NUM` 在 `board/stm32f427/arkrtos_board_config.h` 里降到 **4**（432 B），
降的只是“同时存在几个”，每对象等待槽仍是 4；新增的等待者任务栈要 512 B，而该镜像原本
只剩 84 B，于是把**测试工程自己的 idle 栈**从 512 words（2 KB）收到 256 words（1 KB）
（`example/stm32f427/kernel/ARKRTOS_TEST/Core/Src/main.c`，idle 只做睡眠与上下文切换），
本轮再加两格静态量（`RW` +8 B）后收在 `RW 996 + ZI 121840 = 122836 B`，
余量 **44 B**——这块镜像再添静态量就得另找地方让位。

### 5.5 中断里能做什么

只有四个 `_from_isr` 入口：`arkrtos_sem_post_from_isr()`、`arkrtos_event_set_from_isr()`、
`arkrtos_mq_send_from_isr()` 与 `arkrtos_mq_recv_from_isr()`（后两个的后半截是
`arkrtos_mq_recv_from_isr_internal()`，收消息不经过用户态轮询），以及（开关打开时的）
`arkrtos_eset_set_from_isr()`。
其余同步调用都不保证能在 handler 态安全完成。

`arkrtos_mq_send_from_isr()` 此前**只有声明没有定义**——链接期才会炸，且只有真用它的人
才会炸。`88ea969` 补齐定义；它与 `recv_from_isr` 在宿主用例第 7b 节有 6 条断言，现在
板上也有读数。

验证档位：**上板验证过**（2026-11-15，F427，`utest run mq_from_isr`）。

板上用例 `mq_from_isr_contract`（`example/stm32f427/kernel/ARKRTOS_TEST/Core/Src/arkrtos_isr_case.c`）
走的是**真中断**，不是"把等待队列手工塞满再读"：

- 触发路径不占任何引脚：`EXTI->IMR |= 1` + `NVIC_EnableIRQ(EXTI0_IRQn)` + `EXTI->SWIER = 1`，
  handler 里先清 `EXTI->PR` 再干活。`startup_stm32f427xx.s` 里 `EXTI0_IRQHandler` 是
  `[WEAK]` 空桩，板级工程定义同名函数即覆盖，向量表不用动。
- handler 里记 `__get_IPSR()`，断言它非 0——这条用来排除"有人顺手把 handler 当普通函数
  调了一下"这种假通过。
- 四条路径各自断言返回值与**副作用**，不是只看返回码：发成功 → 任务侧必须取到同一条消息
  （同一字数与内容）；收成功 → 取走后队列必须真空；空队列 → `ARKRTOS_MQ_ERR_EMPTY(-1)`，
  不登记、不阻塞；满队列 → `ARKRTOS_MQ_ERR_FULL(-1)`，且 8 条旧消息逐条核对一条不少。
- 收尾关中断源（`NVIC_DisableIRQ` + 清 `IMR`/`SWIER`/`PR`）、删队列，并断言删后句柄
  既不是活对象、也不能再收发，所以 `utest run` 可反复跑。

实测：`PASS mq_from_isr_contract`，36 条断言 0 失败；全量 `12 matched / 12 passed`，
169 条断言，连跑两遍同结果。

**负对照**（闸门自带防假绿）：把 `arkrtos_mq_send_from_isr()` 的实现换成
「什么都不做、直接 `return 0`」——即接口报成功、消息其实没进去，这正是"有声明没定义"
最可能的退化形态。重编烧板后同一用例报 5 条红：

```
! arkrtos_isr_case.c:200: got == 2  (got -1 / 0xFFFFFFFF, want 2 / 0x2)
! arkrtos_isr_case.c:231: s_isr_send_ret == ARKRTOS_MQ_ERR_FULL  (got 0 / 0x0, want -1 / 0xFFFFFFFF)
FAIL  mq_from_isr_contract   (5/36 assertions failed)
```

改回原文后 `git diff --stat kernelsrc/src/arkrtos_mq.c` 为空，复绿。

边界：只覆盖"一条消息进、一条消息出"的对照；**ISR 里取走消息后唤醒一个阻塞发送者**
（`arkrtos_mq_wake_one` 只置 READY、不切换）在板上没有单独读数——这条要把用例跑到
多任务，属于下一档欠账。另外 `eset` 的 `set` 在真 handler 里的唤醒语义、以及 App 侧 `arkrtos_eset_set_from_isr()`
走的那条 SVC 0x21 ABI 在 handler 里的读数，都已在 §5.4 上板（`eset_from_isr_contract`，

handler 态”这个组合——本工程没有 App/驱动注册 ISR 的 ABI，未特权侧进不了 handler 态。

### 5.6 递归互斥锁（`ARKRTOS_USE_MTX_RECURSIVE`，默认关）

普通互斥锁**不可递归**：持有者再锁一次返回 `ARKRTOS_SYNC_ERR_RECURSIVE(-1)`。
这是刻意的——递归语义必须由调用者显式选择，否则"同一任务重入"会被静默接受，
而重入深度与解锁配对的错误再也没人看得出来。

打开开关后多一个创建入口 `arkrtos_mtx_create_recursive()`（SVC 0x15 子命令 17）：

| 动作 | 普通锁 | 递归锁 |
|---|---|---|
| 持有者再次 lock | `-1`（拒绝） | `0`，`nest++` |
| 持有者 unlock（`nest>0`） | 不适用 | `0`，`nest--`，**不释放** |
| 持有者 unlock（`nest==0`） | 释放 / 交接给等待者 | 同左 |
| 非持有者 unlock | `-1` | `-1` |

边界与代价：

- 只有**显式用递归入口创建**的锁可递归；同一张表里的普通锁语义不变（`recursive` 是对象字段）。
- 默认关时创建函数、SVC 子命令 `case`、SDK 包装都不编进来，体积与行为逐位不变。
- `nest` 是 `uint8`：超过 255 层重入会回绕，实际使用中应把嵌套深度当成"设计错误"而不是常态。
- 可递归不等于可跨任务：所有权仍在 `owner` 上，优先级继承按持有者生效。

验证档位：**上板验证过**（2026-11-14，F427）。板上用例 `mtx_recursive_contract` 在
`utest run` 里通过：同任务连加三次全部成功、三次解锁逐级配对、释放后能重新拿到，
且**同一张表里的普通锁重入仍被拒**（可重入是对象属性，不是全局语义）。宿主 `sync-host`
另覆盖重入计数与解锁配对；默认档链接 `Code=220290` 未变。

### 5.7 多级优先级继承

优先级继承此前只有"直接等待者抬持有者"一级。现在沿等待链**传递**：

```
C(7) 等 B 持有的锁 → B(5) 被抬到 7
B(5) 自己又在等 A(3) 持有的锁 → A(3) 也被抬到 7
C 放锁 / 超时后，抬高逐级回落到各自原优先级
```

证据是宿主用例里的链式场景 `A(3) → B(5) → C(7)`（提交 `a715887`，5 条断言）：
断言检查的是**链尾持有者的有效优先级**与**释放后逐级回落**，不是单个等待者的唤醒。
边界：`syncinfo` 只打印有效优先级，不打印"是谁抬的"；链上任意一环删除对象时按
`OBJ_DELETED` 逐级唤醒，不保证按原优先级次序。

验证档位：**上板验证过**（2026-11-15，F427，`utest run pi_chain`）。

板上用例 `mtx_pi_chain_contract`（`kernelsrc/src/arkrtos_utest_cases.c`）用**真任务**造这条链，
而不是像宿主那样直接往等待队列里塞指针：

```
控制台(14) 持 L1  ──>  MID(10) 持 L2、等 L1  ──>  HIGH(6) 等 L2
```

读数判据是「控制台自己的有效优先级」——只提升一跳的实现会停在 MID 的档（10），
沿链传播的实现必须到 HIGH 的档（6）。实测：

```
RUN   mtx_pi_chain_contract
PASS  mtx_pi_chain_contract
utest: 1 matched, 1 passed, 0 failed, 0 skipped; assertions 20 run / 0 failed
```

**同一个断言做过负对照**：把传播条件从「等待者的当前优先级」改成「等待者的基准优先级」
（等价于只提一跳、不沿链）后重编上板，同一用例立刻报红，且失败值正好是中间那一环：

```
! arkrtos_utest_cases.c:722: p_self->priority == high_prio  (got 10 / 0xA, want 6 / 0x6)
FAIL  mtx_pi_chain_contract   (1/20 assertions failed)
```

恢复后重编上板复跑 `utest run`，10 用例 10 通过、93 条断言 0 失败（全量连跑两遍同结果，
任务槽位可复用、不泄漏）。边界：只覆盖三档一条链、单一持有关系；多等待者同时抬同一持有者、
链上对象中途被删除、提升中途任务被 kill 这三条仍无板级读数。

### 5.8 多对象同时就绪探测（SVC 0x22，`ARKRTOS_USE_WAITMULTI`，默认关）

一次问一组句柄"谁已就绪"，返回 32 位掩码：

```c
int32 arkrtos_wm_probe_internal(const uint32 *handles, uint32 n, uint32 opt, uint32 *ready_mask);
/* 0 = 条件满足；-1 = 参数/句柄非法；-2 = 暂不满足 */
```

| 项 | 值 |
|---|---|
| `opt` | `ARKRTOS_WM_OPT_ANY`（任一句柄就绪）或 `ARKRTOS_WM_OPT_ALL`（全部就绪） |
| 支持的句柄 | `sem`（有令牌）/ `mtx`（未被持有）/ `mq`（有消息）/ `event`（flag 已置） |
| 不支持的 | 32 位事件集（每个条目要自带掩码，超出"一个句柄一个位"的模型）、裸下标 |
| 消费 | **不消费**：探测只读，令牌仍留在对象里 |
| 上限 | 一次 `ARKRTOS_WAITMULTI_MAX_OBJS`（默认 16），掩码 32 位是硬上限 |

App 侧 `arkrtos_wait_multi()` 带超时的等待是**轮询**（`ARKRTOS_APP_POLL_MS = 1`）：
探测到就绪后，调用者再用各对象自己的 `timeout=0` 取走。两条必须写明的边界：

1. **唤醒延迟上限 = 1 个轮询周期**（1 ms），不是 0；
2. "探测到就绪、取用前被别人拿走"的窗口**不可消除**——这是非破坏性探测的固有代价，
   内核没有登记等待者，也就没有原子交接。

不选"内核登记等待者 + 一次阻塞"的理由：在信号量上登记等待者会让 `sem_post` 把令牌
按 HANDOFF 交给探测者而不消费，令牌就丢了；专用 notify 注册表则要给 sem / mq / event
全部加钩子，侵入面远大于收益。

验证档位：**上板验证过**（2026-11-14，F427）。板上用例 `waitmulti_probe_contract`
通过：一条句柄一个位、ANY/ALL 判定正确、**探测多次之后令牌仍在**（随后 `timeout=0`
取用成功，证明探测非破坏性）、非法句柄整组拒绝且掩码清零。宿主另有 24 条断言 +
6 个文件 ON 档 `-fsyntax-only`。

### 5.9 等待者容量：按任务表放大（`ARKRTOS_USE_WAIT_UNBOUNDED`，默认关）

| | 关（默认） | 开 |
|---|---|---|
| `ARKRTOS_WQ_SLOTS` | `ARKRTOS_MAX_SYNC_WAITERS`（4） | `ARKRTOS_TASK_MAX_NUM`（本板 48） |
| 排队结构 | 静态数组，固定长度 | 同一个静态数组，只是更长 |
| 逻辑 | 不变 | 不变（一行分支都没有） |

理由是**一个任务同一时刻只能等一个对象**，所以任何对象的等待者数不可能超过任务数——
对本内核来说这就是"无上限"，不需要链表，也不需要堆。代价是所有对象表一起线性变大
（每槽 4 字节 × 各表的排队数）。

**这不是链表式无上限**：真要"等待者数与任务表无关"，得改 46 处等待队列代码
（sync 24 + mq 8 + sbuf 7 + event 7），风险与收益不成比例，所以没做。

验证档位：**开档在本板放不下**（这也是唯一一条被硬件否决的档位）。把
`ARKRTOS_USE_WAIT_UNBOUNDED=1` 加进 F427 测试镜像后链接直接爆：
`L6406E: No space in execution regions`，108 个 error、`aggregate size 0x2958 bytes
could not fit into .ANY selector(s)`——所有对象表一起从 4 槽变 48 槽，测试镜像塞不进去。
故**没有板级行为读数**，只有 `sync` 的宿主行为验证（76 checks，`WQ-SLOTS=48`）与
`mq` / `sbuf` / `event` 的 ON 档编译层（数组长度派生正确），
没有"队列塞满仍能再挂一个等待者"的板级验证。要在板上验，得先把测试镜像裁到放得下
（关掉 lwIP / VFS / SBUF 等），这件事没做。

### 5.10 SMP 骨架（`ARKRTOS_USE_SMP`，默认关）

**先把结论写在前面：这不是多核支持。** 调度器仍是单核的——全局当前任务号
（`arkrtos_current_task_id`）、全局就绪位图、全局延迟队列。打开开关不会让两个核
同时跑任务，也不会把对象表变成每核一份。

它提供的是多核地基：

| 项 | 内容 |
|---|---|
| `ARKRTOS_CPU_NUM` | 1..8（在线掩码是 `uint32`，且 8 核以内人工对账还做得动） |
| 每核状态 `arkrtos_smp_cpu_t` | `online` / `started` / `current_task_id` / `tick` / `ipi_count` / `idle_count` |
| `arkrtos_smp_init()` | CPU0 直接上线，1..N-1 交给 port 的 `arkrtos_port_cpu_start()`；返回"启动请求被接受"的核数 |
| 次核入口 | `arkrtos_smp_secondary_main(cpu)`：标记上线 → 开中断 → **WFI 空转**，不参与调度 |
| 核间中断 | `arkrtos_smp_send_ipi()` → `arkrtos_port_send_ipi()`；收端 `arkrtos_smp_ipi_handler()`（默认只计数，应用可用同名强符号覆盖） |
| 单核 port | `arkrtos_port_cpu_start()` / `arkrtos_port_send_ipi()` 返回 `-1`（明确"没有这条路"，不假装成功） |

三条刻意设计：

1. **`started` 与 `online` 分开记**：启动请求被接受不等于核已经在跑，在线位由次核自己置。
2. **核号越界一律不落地**：`arkrtos_smp_cpu_online()` 越界直接忽略；
   `arkrtos_smp_cpu_self()` 读到越界核号时收敛到核 0——核号读错不应该变成越界写。
3. **CPU0 由 `arkrtos_kernel_module_init()` 引导**（在调度器启动之前）：次核若在调度器
   跑起来之后才启动，会看到一个不属于它的调度器。

验证档位：**未验证（无多核板）**。已有证据只有"骨架自洽"：宿主 44 条断言
（上线掩码、越界核号、拒绝启动时不许虚报上线、IPI 只发在线核、重复初始化清零、
每核计数只落当前核）+ 5 个文件 ON 档 `-fsyntax-only`。真实次核启动、IPI 投递与延迟、
多核同时置掩码的 CAS 竞争都**没有**任何板级读数。

## 6. 两条硬规则（踩过才知道）

### 规则一：重复登记返回 `-2` 不是错误

轮询第二次进内核时，任务已经在等待队列里，`waiter_add` 返回 `-2`（已登记）。
**调用点必须能区分 `-2` 与真正的失败。** 曾经 `arkrtos_event.c` 与 `arkrtos_sync.c` 的
条件变量分支按 `< 0` 判错，把"已经登记"当成失败直接返回，表象是
`evt.wait_timeout` 只过了 1 ms 就回来（上板自检 FAIL）。

> 修法不是"忽略 -2"，而是让每个调用点显式写出
> `if((added < 0) && (added != -2)) { ... }`。写成 `if(added < 0)` 的下一个人还会再踩。

### 规则二：`timeout == 0` 必须摘除自身登记

`timeout=0` 在等待路径上的语义不是"不等待"，而是"把我的登记撤掉并回答 TIMEOUT"。
内核不会给用户态等待者 arm 定时器，所以这条摘除只能由 oslib 在超时那一刻显式发起。
漏了它，等待者会一直挂在队列上，之后每次派发都会去看一个已经走了的任务。

### 附带：服务层幂等 ≠ 内核严格语义

`arkrtos_fs_mount()` 拒绝重复挂载（会泄漏旧的 `lfs_t`），这是**内核的严格语义，不能删**。
App 侧"确保已挂载"的诉求在 FILE_SYS 服务层（`arkrtos_task.c` 的 case 6）满足：
`(arkrtos_fs_mounted() != 0u) ? 0 : arkrtos_fs_mount_default()`。
shell 仍保持严格的 mount / unmount 配对。

## 7. 排障入口

### 7.1 `syncinfo` —— 同步对象体检

```
sem  used  count  owner  creator  waiters
 0   1     3      -1     1         t4
  sem 0: posts=12 takes=9 queued=1 last_waiter=t4 qbefore=2 woke=t4 reason=4
sync diagnostics: ghost=0 dup=940
sync ghost  : n=0 idx=-1 tid=t0
sync appwait: hit=480
```

| 字段 | 怎么读 |
|---|---|
| `count` | 令牌当前躺在对象里的数量；`owner` 互斥锁持有者 |
| `waiters` | 挂在队列上的任务，`t<id>` 形式 |
| `posts` / `takes` | 派发 / 取走次数 |
| `qbefore` | 派发那一刻队列里已有几个等待者 |
| `woke` / `reason` | 上一次派发唤醒了谁、原因位是多少（4 = HANDOFF） |
| `ghost` | 没带 `ARKRTOS_WAKE_HANDOFF` 却被当成成功的唤醒，**必须为 0** |
| `dup` | 重复登记次数。轮询模型下这是正常量（每次轮询都会撞一次 `-2`），不是错误 |
| `appwait hit` | 用户态登记次数，也就是"走了轮询路径"的次数 |

### 7.2 `log` —— 控制台与令牌守恒

```
console   : lock_giveup=0 tx_drop=0 B fifo_full_retries=134831
fifo      : bad_header=0 bytes_lost=0
sync      : ghost=0 dup=940
```

`tx_drop` 才是真实丢失字节数；`fifo_full_retries` 是**被拒尝试数**，不等于丢失。
`bad_header` / `bytes_lost` 非 0 说明 FIFO 缓冲头被写穿（历史上是主栈溢出），
这条路上输出是被静默丢掉的。

### 7.3 `task <id> [任意第三参]` —— 单个任务的现场

```
task 4 sp=0x2001A3B0 st=SUSPENDED frame words:
  sp+0    0x2001A3B8
  ...
  blocks=137 last_reason=4
```

第三个参数只为多打 `blocks=` / `last_reason=` 两行。帧是**原样 56 个字**：
带不带 FPU 扩展帧决定哪个字是 PC，猜哪个字是 PC 就会把回溯变成错答案，
所以这里不给"解析后"的视图。

## 8. 本轮修掉的四个失败（F427 上板自检，均已转绿）

| 自检项 | 表象 | 根因 | 修法 |
|---|---|---|---|
| `evt.wait_timeout` | 1 ms 就返回 | 轮询第二次进内核，`waiter_add` 返回 -2，调用点按 `< 0` 判错 | `arkrtos_event.c` / `arkrtos_sync.c` 显式容忍 -2 |
| `fs.mount` | App 里挂不上，shell 里能 | `arkrtos_fs_mount()` 有意拒绝叠挂（现场回 `littlefs error -1004: a volume is already mounted`） | 内核保留严格语义，FILE_SYS case 6 做幂等 |
| `fs.list_has_new_name` | 新文件名匹配不上 | `names_has` 按 NUL 分隔解析，而 `arkrtos_fs_list_names()` 输出是 `\n` 分隔 + 结尾一个 NUL | App 侧改按 `\n` 分隔 |
| `cond.delete` | 返回 0 但报 FAIL | SYNC_CTRL `case 13` 漏 `break`，落到 case 14，返回值被 `arkrtos_cond_enqueue_internal()` 覆盖（对象刚删必 -1） | 补 `break` |

> 教训：**switch 漏一个 `break` 会让上层拿到一个"看起来成功了"的返回值。**
> 这类错误的返回值本身不报错，只能靠自检抓。

## 9. 内核同步对象表的容量预算（多 App 并发）

信号量、互斥锁、事件、消息队列、条件变量这五张表是**全局定容**的，容量写在
`kernelsrc/include/arkrtos_config.h`（`ARKRTOS_SEM_NUM` / `ARKRTOS_MTX_NUM` /
`ARKRTOS_EVENT_NUM` / `ARKRTOS_MQ_NUM` / `ARKRTOS_COND_NUM`）。

关键点：**表满时 `arkrtos_sem_create_internal()` 只返回 -1，不区分「名字重复」和「没槽位」**
（`kernelsrc/src/arkrtos_sync.c`）。POSIX 层把这个 -1 映射成 `ENOMEM`，
于是表现为 `pthread_create` 失败——**看起来像内存不够，实际是表满**。

### 9.1 每个使用者要占几个槽

| 使用者 | 占用的信号量槽 |
|---|---|
| 每个 POSIX 线程（`pthread_create`） | 2 个（名字形如 `pth<id%10>g` / `pth<id%10>d`） |
| 每个 `sem_t`（`sem_init` / `sem_open`） | 1 个 |
| COND 的等待者 gate | 每个等待中的条件变量等待者另有占用 |

所以**表容量要按「所有并发使用者之和」定，不是按单个 App 峰值定**。

### 9.2 实测案例：开机自检 109/6 → 116/0

同一份 APP_DEMO 镜像曾出现「开机 auto-start 自检 `pass=109 fail=6`（6 项全是 `posix.cond_*`），
运行期 `app stop/start` 却 `pass=116 fail=0`」。

- 先用镜像头逐字段比对（`crc32=0xE59BED1F`、`nominal_base`、`image_size`、`entry_offset`）
  证明板上跑的**与当前源码构建逐字节同源**，排除「旧镜像」这个方向；
- 再按表算账：开机时 POSIX_DEMO 的两个线程活着，占 4 + 1；APP_DEMO 再要 4 + 2 →
  **11 > `ARKRTOS_SEM_NUM`(8)**，必爆表；
- 运行期重启 APP_DEMO 时，POSIX_DEMO 那边的线程已 join、槽位已归还，所以能过。
- 修法：`ARKRTOS_SEM_NUM` 8 → 24。F427 重新编译烧录后**开机 auto-start 自检回到 `pass=116 fail=0`**。

> 教训：**表满会伪装成 ENOMEM。** 多 App / 多线程场景下加减线程、加减信号量，
> 都要回头核一遍这几张表的容量。

## 宿主门禁：这些契约现在是可复跑的

`tools/sync_host_gate.py`（`ci_gate` 的 `sync-host` 项）把 `arkrtos_sync.c` 原样编到 PC 上，
测试里把 `arkrtos_task_get_current()` 换成一个**可设置的**真实 TCB 指针，所以归属类判定
（"谁能解锁""什么算重复加锁"）是真跑过的。51 条断言覆盖：

- **计数守恒**：初始计数逐个取用 → 计数 0 时 `timeout == 0` 返回 `ARKRTOS_SYNC_ERR_TIMEOUT`；
  超时的 wait 既不生也不灭令牌；无人等待的 post 把令牌停在计数里，且**只**能被取一次。
- **归属**：持有者重复加锁被拒（不是递归）；非持有者解锁被拒且持有者不变；解锁后别的任务能取；
  删除一把被持有的锁之后它不再计为"被持有"，且所有接口一律拒绝。
- **删除语义**：`sem_delete` / `mtx_delete` 现在也查 `used`（此前对一个已经不存在的对象
  `delete` 会返回 0 = "删掉了"），与 `cond_delete`、`send/recv` 的判定一致——
  按"宁可报错"的口径，把没删到东西报成成功是错答案。

**没证明的**：阻塞、唤醒、令牌转交、优先级继承链——这些要真实调度器与节拍，
测试里的 `block_in_critical()` 直接返回 -1，`timeout > 0` 的分支走不到。上板用例仍是唯一的证据。
