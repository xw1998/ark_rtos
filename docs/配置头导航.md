# Ark RTOS 配置头导航

## 一句话

「改一件事该动哪个头」在这套仓库里不靠记忆：地址只有一个源头，开关只有一个落脚点，
生成物禁止手改，四条门禁会把这些规则变成红的。本文是那张地图——**只讲边界与落点，
不重复讲工具怎么用**（工具在 [Kconfig配置系统.md](Kconfig配置系统.md)，逐项开关语义在
[功能开关.md](功能开关.md)）。

## 0. 我要改的东西 → 该动哪个文件

| 我要改的 | 动这里 | 不要动 | 改完必须做 |
|---|---|---|---|
| 某个对象表大小、队列深度、超时/容量上限（`SEM_NUM`、`MQ_DEPTH`、`POSIX_FD_MAX`…） | `config/arkrtos_defconfig`（必要时连带 `config/kconfig/Kconfig.capacity` 的 `range`） | `kernelsrc/include/arkrtos_autoconf.h`（生成物） | 重新生成 autoconf.h；`config-generated` 门禁 |
| 打开 / 关闭一个功能开关 | Kconfig 符号（`config/kconfig/Kconfig.features` + defconfig）；代码里的 `#if` 落脚点仍是 `arkrtos_features.h` | 把 `arkrtos_features.h` 的默认值从 0 改成 1（等于偷偷改构建形状，且 menuconfig 看不见） | 全关档编译一次、全开档编译一次 |
| 这颗芯片**有**什么（FPU / MPU / 特权级 / 主频 / 看门狗） | `board/<chip>/arkrtos_board_config.h` | `arkrtos_config.h` 里的能力兜底默认值 | 该板工程重新编译 |
| Flash / RAM 地址、分区尺寸、镜像池粒度、槽位表、任务表 `ARKRTOS_TASK_MAX_NUM`、`SHELL_ENABLE` | `config/arkrtos_partition.h`（F427）或 `config/stm32f401|stm32h743/arkrtos_partition.h` | 任何 `.sct`、任何 C 文件、任何脚本里的硬编码地址 | `gen_scatter.py --check`、重新生成 `.sct`、评估是否要重烧配置区 / 重装镜像 |
| App / 驱动想知道布局与槽位 | 运行期经 SVC `0x18`（`arkrtos_share.h` 的分区表） | 在 App 侧 `#include "arkrtos_partition.h"` | `no-app-partition-include` 门禁 |
| 设备端持久配置记录的字段与语义（安装策略、固定槽表、运行期旋钮） | `kernelsrc/include/arkrtos_layout_def.h`（格式）+ `tools/arkrtos_cfg.py`（写入） | 把地址写进这个头 | 编译期尺寸断言；上位机工具与固件成对升级 |
| 句柄标志、SVC 调用号、返回码、唤醒原因 | `kernelsrc/include/arkrtos_def.h` | 各处散落的十六进制魔数 | SDK 侧与内核侧同改 |
| 节拍周期、设备/定时器/故障记录数量、MPU 外设窗口、栈填充图案 | `kernelsrc/include/arkrtos_config.h` | — | 该板重新编译 |
| 任务表声明、启动装载入口、任务栈初始化 | `kernelsrc/include/arkrtos_cfg.h` | — | 该板重新编译 |

> 三个分区头是**同一个角色的三个实例**：`config/arkrtos_partition.h` 是 STM32F427 的，
> `config/stm32f401/` 与 `config/stm32h743/` 各有一份。工程靠 Include Path 选中其中一个，
> 脚本靠 `gen_scatter.py --header <path>` 指过去。三者互相独立，不存在「主头 + 覆盖头」的关系。

## 1. 包含顺序（顺序本身是契约）

```
board/<chip>/arkrtos_board_config.h      ← 能力层；由 -DARKRTOS_BOARD_CONFIG="arkrtos_board_config.h" 载入
        │  被 arkrtos_config.h 的第一件事 include
        ▼
kernelsrc/include/arkrtos_types.h
        └── arkrtos_autoconf.h           ← Kconfig 生成物；符号名 = 宏名，全部包 #ifndef

arkrtos_config.h
        ├── config/<chip>/arkrtos_partition.h   ← 地址与容量唯一事实源
        ├── arkrtos_arch.h                      ← 架构族 / 核心 / 能力派生
        └── arkrtos_features.h                  ← 选配层（53 个 gate）

arkrtos_def.h        ──► arkrtos_types.h        ← 句柄标志 / SVC 号 / 返回码 / 唤醒原因
arkrtos_cfg.h        ──► def.h + task.h + config.h
arkrtos_layout_def.h ──► types.h（**只有它**，绝不含分区头）
```

顺序里有两处不是巧合，改顺序会静默改语义：

1. **板级配置先于一切**。它要能覆盖 `ARKRTOS_ARCH_CORE` 与各项 gate 默认值，
   所以必须排在 `arkrtos_arch.h` / `arkrtos_features.h` 之前。
2. **`autoconf.h` 挂在 `arkrtos_types.h` 上**。`types.h` 是内核和 SDK 每个翻译单元
   都会到达的最底层头，生成的值因此对 App 侧（POSIX / socket 容量）与内核侧同时生效。

## 2. 七个头逐个说边界

### 2.1 `config/<chip>/arkrtos_partition.h` —— 唯一地址事实源

- 全工程唯一允许出现物理 Flash / RAM 地址的文件；F427 版本共 95 个 `ARKRTOS_*` 宏，
  `.sct`、C 文件、脚本都不得硬编码地址。
- 结构是「三节 + 推导区」：一、芯片物理参数（移植只改这几行）；二、分区大小策略；
  三、以下全部自动推导，**禁止手改**。推导区里有 `IMAGE_POOL_BASE`、`SLOT_RAM_BASE`、
  `ARKRTOS_MPU_*` 窗口、`CRASH_LOG_BASE` 等。
- 容量也在这里：`ARKRTOS_TASK_MAX_NUM` / `ARKRTOS_TASK_TABLE_RAM_MAX` 明确从
  `arkrtos_config.h` 迁到了这里，理由写在注释里——容量变化不能和布局各说一套。
- 既有配置项也在这里，且**不是** Kconfig 符号：`SHELL_ENABLE`、`INSTALLER_ENABLE`、
  `APP_AUTO_START`、`DRIVER_*`。Shell 的整文件门控认的就是 `SHELL_ENABLE`，
  不要再在 `arkrtos_features.h` 里造第二个 shell 开关。
- 连带代价必须一起算：改 `IMAGE_POOL_SECTOR` 会让池基址整体上移，设备端配置区旧内容
  与池里已安装的镜像全部对不上（注释里 F427 从 128K 改 256K 的实测账就是这条）。
- App / 驱动侧禁止 include 本头，布局只能经 SVC `0x18` 在运行期取。

### 2.2 Kconfig 链 → `kernelsrc/include/arkrtos_autoconf.h`（生成物）

- 输入：根 `Kconfig` + `config/kconfig/{Kconfig.capacity,Kconfig.features,Kconfig.net,Kconfig.posix}`
  + `config/arkrtos_defconfig`；输出：`arkrtos_autoconf.h`（入库，为了克隆即可构建）。
- 生成器 `tools/kconfig/genconfig.py` 的 `--check` 模式就是门禁 `config-generated`：
  手改生成物、或改了 Kconfig/defconfig 忘了重新生成，都会红。
- 生成物里每个宏都包了 `#ifndef`，所以工程 `-D`、板级配置仍然能覆盖它。
  这是「不用 Kconfig 时行为零变化」的实现方式，不是巧合。
- 装有 87 个 `ARKRTOS_*` 符号；其中 53 个对应 `arkrtos_features.h` 的功能 gate，
  由门禁 `features-switches` 保证「一个不漏」。

### 2.3 `kernelsrc/include/arkrtos_features.h` —— 选配层

- 只回答一个问题：**这次构建要哪些功能**。53 个 `#ifndef ARKRTOS_USE_*`（含少量
  非 `USE_` 前缀的旋钮，如 `ARKRTOS_MINI_MAX`、`ARKRTOS_TICKLESS_MAX_TICKS`）。
- 默认值一律写在 `#ifndef` 里，板级 / 工程可覆盖；关掉后要么整块不编入、要么有明确
  stub，不许变成链接错误。开关之间的依赖用 `#error` 显式报出。
- 三个能力开关（`ARKRTOS_USE_FPU / _MPU / _PRIV`）**不在这里**，它们属于能力层，
  留在 `arkrtos_config.h` 与板级配置里。

### 2.4 `kernelsrc/include/arkrtos_config.h` —— 能力兜底 + 数值参数

- 32 个 `#ifndef ARKRTOS_*` 参数：能力兜底（FPU/MPU/PRIV）、MPU 外设窗口与外部 RAM
  窗口、节拍周期、事件/信号量/互斥锁/POSIX 等待者、设备表、内存池、消息队列、
  条件变量、流缓冲、定时器、故障记录、时间片、栈底标志。
- 它只放「参数」，不放地址：「任务表容量」已迁到分区头、「共享内存地址」已删除、
  「系统时钟」改成只认 CMSIS `SystemCoreClock`（`ARKRTOS_SYSTEM_CLOCK_HZ` 是有意删掉的
  死宏，注释里写了它当年与硅片不符的实测）。
- 派生宏（如 `ARKRTOS_MS_TO_TICK`）不包 `#ifndef`——它不是配置项。

### 2.5 `kernelsrc/include/arkrtos_def.h` —— 跨边界的常量契约

- 句柄标志（`EVENT/DEV/SEM/MTX/MQ/TIMER/COND/SBUF`）与掩码；SVC 调用号（`0x10`…`0x20`）；
  同步返回码（`OK/PARAM/TIMEOUT/DELETED/WOULDBLOCK`）；唤醒原因（`NORMAL/TIMEOUT/
  OBJ_DELETED/HANDOFF`）。
- 这些常量内核与 SDK 共用，改值等于改 ABI：两侧必须同时改，且旧 App 会被新内核误解释。
- 「超时必须返回负值」「对象被删时等待者必须收到 `OBJ_DELETED`」这类语义写在注释里，
  改动前先读 [同步原语与令牌守恒.md](同步原语与令牌守恒.md)。

### 2.6 `kernelsrc/include/arkrtos_layout_def.h` —— CONFIG 区持久记录

- 定义设备端配置记录的标识、几何、校验结果码与结构体；记录住在 CONFIG 区（内核与
  镜像池之间一个物理擦除单位），由上位机 `tools/arkrtos_cfg.py` 写入、内核上电读取。
- 与分区头的分工是「值同源、头不同头」：回收模式、槽表枚举这类值在两边都有定义，
  因为本头要给**不包含分区头**的代码（宿主工具、驱动侧）用。它只 include `types.h`。
- 运行期旋钮里真正被内核读的只有 `log_level`、`fault_restart_max`、`boot_delay_ms`
  与 `flags` 的 `RAW_ALLOW` 位；其余字段写非 0 会被**拒绝**（`ARKRTOS_CFG_ERR_NOT_IMPL`），
  不是默默忽略。理由（没有 IWDG 端口层 / 内核不持堆 / 没有匿名栈池）逐条写在注释里。

### 2.7 `kernelsrc/include/arkrtos_cfg.h` —— 任务表与启动装载

- 声明全局任务表 `arkrtos_task_table[ARKRTOS_TASK_MAX_NUM]`、`arkrtos_task_count`、
  `arkrtos_cfg_load()`、`arkrtos_task_stack_init()`，以及 `ARKRTOS_USE_STACK_USAGE=1`
  时的 `arkrtos_task_stack_fill()`。
- 容量仍然来自分区头（经 `arkrtos_config.h` 进来），本头不定义任何数值。

## 3. 五条规则

1. **一个开关只属于一层**：能力层（板级）/ 选配层（`features.h`）/ 既有配置（分区头）。
   给同一个能力起两个名字，迟早出现「看着关了其实还开着」。
2. **地址只写一次**：只允许出现在分区头。改了它，`.sct` 由生成器重出，不要手工编辑。
3. **生成物不手改**：`arkrtos_autoconf.h`、各板 `arkrtos_dt.c`、`.sct` 都是产物；
   前两者入库但必须由生成器产出，`.sct` 明确不入库（`sct-not-tracked` 门禁盯着）。
4. **App / SDK 布局无关**：只经 SVC `0x18` 取布局，编译期不 include 分区头。
5. **默认关 = 零变化**：新开关默认关时体积与行为必须和引入前逐字节一致；
   「编入档」要能证明真的编进去了。

新增一个开关的完整清单在 [功能开关.md](功能开关.md) §「新增一个开关的清单」。

## 4. 谁在盯着这些规则

| 门禁（`tools/ci_gate.py`） | 盯的问题 | 红了说明 |
|---|---|---|
| `config-generated` | `autoconf.h` 是否等于「Kconfig + defconfig」的当前输出 | 手改了生成物，或改了输入忘了重新生成 |
| `features-switches` | `arkrtos_features.h` 的每个 gate 是否都在 Kconfig 有同名 `config` | 新开关只能被 `-D` 改，menuconfig 里看不见 |
| `no-app-partition-include` | App / SDK 侧是否 include 了分区头 | 编译期耦合进了布局，换板就得重编 App |
| `layout-check` / `sct-not-tracked` | 分区头自身是否有重叠/越界；`.sct` 是否被误入库 | 布局算错，或有人把生成物提交了 |
| `doc-index` | 本页是否在 `docs/README.md` 里 | 新增文档没进索引，等于没人能找到 |

`doc-index` 这条对本页同样有效：新增或改名页面必须同步 `docs/README.md`。

## 5. 三种改法的完整命令

```bash
# A. 改容量：改 defconfig（或 menuconfig），再重生生成物
env -u PYTHONHOME -u PYTHONPATH py -3 tools/kconfig/menuconfig.py
env -u PYTHONHOME -u PYTHONPATH py -3 tools/kconfig/genconfig.py \
    --defconfig config/arkrtos_defconfig \
    --out kernelsrc/include/arkrtos_autoconf.h
env -u PYTHONHOME -u PYTHONPATH py -3 tools/kconfig/genconfig.py --list   # 核对取值

# B. 改布局：只动分区头的「一、二」两节，然后校验（生成 .sct 走各工程自己的构建）
env -u PYTHONHOME -u PYTHONPATH py -3 tools/gen_scatter.py --check
env -u PYTHONHOME -u PYTHONPATH py -3 tools/gen_scatter.py --header config/stm32h743/arkrtos_partition.h --check

# C. 改能力：动 board/<chip>/arkrtos_board_config.h，然后重编该板工程

# 收尾：全量门禁（含 Keil 构建与全部宿主门禁）
env -u PYTHONHOME -u PYTHONPATH py -3 tools/ci_gate.py
```

## 6. 常见症状 → 落点

| 症状 | 先看 |
|---|---|
| `macro redefined` / 板级覆盖不生效 | `arkrtos_config.h` 里该宏有没有被 `#ifndef` 包住；板级配置是否真的先被 include |
| 改了 defconfig 但板上行为没变 | `autoconf.h` 有没有重新生成；工程是不是用 `-D` 又盖回去了 |
| menuconfig 里找不到某个开关 | 它只在 `features.h` 或分区头里，Kconfig 没有对应 `config`（`features-switches` 会报） |
| App 编译报找不到 `arkrtos_partition.h` | 这是**对的**：App 侧不该 include 它，布局走 SVC `0x18` |
| 镜像装不上 / 起了旧版本 | 分区头的池基址或池粒度变过，配置区与已安装镜像需要重写/重装 |
| 配置记录写进去内核不认 | `layout_def.h` 的运行期旋钮里只接受那四个字段；其余非 0 会被 `ARKRTOS_CFG_ERR_NOT_IMPL` 拒绝 |

## 8. 验证状态

- 本文所有数量（53 个 gate、32 个 `config.h` 参数、95 个分区头宏、87 个 Kconfig 符号）
  均由当前仓库文件直接统计得出；包含顺序逐条对照源文件确认。
- 门禁名称、判定条件对照 `tools/ci_gate.py` 源码确认。
- **本文没有引入任何代码改动**，因此不涉及上板验证；其中「改分区头要重烧配置区/重装镜像」
  一类连带代价，结论来自分区头注释里已记录的实测，不是本文新增的实测。
