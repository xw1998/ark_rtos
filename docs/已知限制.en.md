# Ark RTOS known limitations

**[简体中文](已知限制.md) | English**

> Condensed English edition. The Chinese page (已知限制.md) is normative: every number below is
> copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no
> new claim and no new measurement.

This is the single "limitations list" page. These limits used to be scattered across the
Linux-gap page, the MiniApp page, the certification page, the lwIP page, the softbus page and the
real-time page, so a reader had to assemble the boundary himself. Every row says whether it is a
**trade-off** (by design we do not do it: written down so nobody expects it) or a **debit** (it
should be done but is unfinished or unverified; `docs/欠账盘点.md` has the matching entry), plus
where the evidence lives.

## 1. Execution model

| Limitation | Nature | Notes and evidence |
|---|---|---|
| **No-MMU profile: no virtual address space.** With `ARKRTOS_USE_MPU=1` an App runs inside a fixed RAM window of its partition; all tasks share **one address space** plus per-task MPU/PMP windows. | Trade-off (window backend) | See [内存保护与App越权验证](内存保护与App越权验证.md) |
| **MMU profile: per-App address-space mechanism exists, but no concurrency and no allocator.** `ARKRTOS_USE_PAGING=1` (actually run on LoongArch64) turns isolation from windows into page-table entries plus PLV. Since 2026-11-17 `set_app` **rewrites the PS=20 entry of the App window** (space number = frame number, VA fixed at `0x02000000`), so "same VA, two physical memories" holds. U-3 has all three stages done: 4 KB frame pool (`ARKRTOS_USE_PAGING_FRAMES`), page-level App window (`ARKRTOS_USE_PAGING_PAGES`, 256 PS=12 entries instead of one 2 MB PS=20; 512 frames per space, so `used` is 512), on-demand faulting (`ARKRTOS_USE_PAGING_DEMAND`, i.e. U-5; window empty after `activate`, two frames per 8 KB pair, `used` down to 14; `tlb_refill_entry` therefore saves/restores all GPRs and retries). Space reclaim was added 2026-11-17 (`arkrtos_paging_space_release()` withdraws window entries before returning frames; the reverse order silently shares physical pages), `pmap rel <n>` prints the frame count before and after. **Only the page-level stage has been run under QEMU**; the `-3` branch (caller standing inside the window) has no run. Page replacement defaults off (`ARKRTOS_USE_PAGING_SWAP=0`: empty pool falls back to the original fatal path); when on it swaps out an 8 KB pair, but the swap area lives in kernel `.bss`, so **it saves no memory**, and there is still no dirty-page test. Default profile has **no ASID and no TLB shootdown** (the ASID profile U-7 is done and measured, see §5.28; shootdown still absent — U-7b probed every op on QEMU: this target's `invtlb` has no usable ASID-directed invalidation, see §5.29), and refill **does not look at PLV** (kernel copy through the window and the App's own access take the same path). `copy_from_user` (U-6) is done; the exit-code channel (U-8) is done but only enabled on the LA64 board profile; `wait <task id> [timeout ms]` and `main` return-value conversion (App / MiniApp / downloadable module paths) were added 2026-11-17, but that is a shell-side 20 ms task-table poll, **not** POSIX `wait()` (no parent/child, no zombie queue, a recycled slot yields the new task's code); driver_sdk deliberately has none (a driver task has no observer). See [MMU进程模型与ELF装载](MMU进程模型与ELF装载.md) §6 U-1..U-7. Do not describe this profile as "Ark has processes" or "two programs ran at the same time". | Partial debit (M2) | All three stages open only on this LA64 board profile or in the on-demand profile's separate `BUILD` directory; every other board is byte-identical with the switches off. Readings: `pmap frame` / `pmap look` / `pmap ftest` |
| **`fork` exists (default off, fork tier); no swap; `execve` only replaces the image of the same task.** The shell's `exec` means "start a task and wait for it"; `execve` (Linux ABI nr 221, 2026-11-21, run under QEMU LA64) replaces the **current task's** image in place - same task id, fds kept, heap cursor reset - fork tier (`ARKRTOS_USE_LINUX_FORK`, 2026-11-23, 21 checks passing under QEMU LA64) adds **parent/child**: per-process fd tables with inheritance, cross-task `SIGCHLD`, and a really blocking `wait4` (restartable syscall). Copy-on-write is done (`ARKRTOS_USE_PAGING_COW`, 2026-11-23, default off, 26 checks under QEMU LA64: 8 KB pairs with refcounts, **forced-private stack pages** because the trap frame lives on the App stack). Still no paging out. **Threads are done** (`ARKRTOS_USE_LINUX_THREAD`, default off, 2026-11-24, 186 checks in the ninth QEMU LA64 tier): shared address space, per-thread trap frame and user stack, one process slot and one fd table per group, `CLONE_SETTLS` / `getpid`=tgid / `gettid`, `exit` ends only the caller while `exit_group` ends the group, and join via `CHILD_CLEARTID` + `FUTEX_WAIT`. | Trade-off + partly closed | See [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.en.md) sections 5 and 8.10 and [与Linux差距盘点](与Linux差距盘点.en.md) |
| The thread tier is verified on **one core** only; `exit_group` under SMP has no protocol. | Open (verification tier) | The group's `exit_group` has to stop tasks that may be running on another core, and this kernel has only a single-core ready set and no inter-core stop protocol (see the "single core; SMP is only a skeleton" row). The ninth QEMU tier runs `-machine virt` with one core, so there is **no** multi-core reading at all. Judgement: until `-smp 2` readings for `exit_group` and thread exit exist (including the state on the killed core), this tier must not be read as "threads work on multiple cores". See section 8.10 of [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.en.md) |
| `execve` from a **non-leader thread** is undefined. | Open (semantic gap) | `execve` replaces the image of **the current task**; the Linux semantics are "end the whole group and keep only the caller". This kernel neither tears down the group nor rejects the call on a non-leader thread, so the other threads keep pointing at the old address space and behaviour is undefined. Known boundary, not covered by the fixture. Judgement: look at the thread-group test near `lx_execve` in `kernelsrc/src/arkrtos_linux_abi.c`; the fix is either tearing down the group or returning `-EINVAL` for a non-leader. See section 8.10 of [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.en.md) |
| `CLONE_SETTLS` with 0 cannot express "set `$tp` to 0". | Trade-off (interface expressiveness) | The kernel treats `tls == 0` as "not supplied" (`$tp` is inherited from the parent thread) because a LA64 frame has no "uninitialised" state for `$tp`. Distinguishing "set to 0" from "not supplied" would need one more flag, and glibc never does this (it always passes a non-zero TCB address). Judgement: `grep -n "child_tls != 0ul" kernelsrc/port/loongarch/la64/arkrtos_port.c` |
| MPU is region-level, not page-level. | Trade-off (hardware) | Cortex-M MPU has 8 regions, 32 B minimum granularity, power-of-two alignment; "one 4 KB protected page" is not reachable. See [内存保护与App越权验证](内存保护与App越权验证.md) |
| **Single core; SMP is only a skeleton.** The scheduler is one ready set: one global current-task id, one global 256-bit ready bitmap, one global delay queue, **no per-CPU scheduling structure**. `ARKRTOS_USE_SMP` (default off) only supplies groundwork: per-core state table, online mask, secondary-core entry (unstarted cores spin in WFI), IPI path, `ARKRTOS_CPU_NUM` 1..8; the single-core port's two hooks return `-1` instead of pretending success. **Flipping the switch does not make you multi-core**, and there is no board reading on a genuinely multi-core part (only 44 host assertions, 5 files ON-path syntax, and an LA64 pin U). LA64 gained secondary-core parking and a real core id (SMP profile), but QEMU `-kernel` direct boot parks the secondary core in `slave_boot_code` in pflash, so the parking branch is unreachable locally (verdict `smp_park_unreachable_on_qemu_kernel_boot`, §9.5 of the QEMU page). | Trade-off + debit | See [同步原语与令牌守恒](同步原语与令牌守恒.md) §5.10 and 缺口 ⑦ in [与成熟RTOS对比](与成熟RTOS对比.md) |
| Waiter capacity **not on board**; plus a list of verified-vs-unverified sync combinations (recursive mutex, multi-object wait, PI chains, message send/receive inside an ISR, 32-bit event-set App channel / kernel-side ISR entry / App-side SVC 0x21 in an ISR, POSIX rwlock and barrier). | Debit (verification tier) | Recursive mutex and multi-object wait **verified on F427** (2026-11-14, `utest`, 110 assertions, including the switches-on build). Multi-level priority inheritance **verified on F427** (2026-11-15, real task three-level chain `mtx_pi_chain_contract`, 20 assertions 0 failures, with a negative control that only looks at the base priority: `got 10 / want 6`). POSIX rwlock / barrier **verified on F427** (same day, `POSIX_DEMO`: `rwlock : PASS (0 violations)`, `barrier : PASS (arrived=2 serial=1 bad=0)`), but that covers only the single-task lock state machine and a one-shot 3-participant barrier — **overlapping concurrent readers and "no writer starvation under writer preference" still have no board reading**. Message send/receive directly inside an ISR **verified on F427** (2026-11-15, `mq_from_isr_contract`, software-triggered EXTI0 into the real handler, send/receive/empty/full, 36 assertions 0 failures, with a "send silently drops but reports success" negative control), but **"ISR dequeues a message and wakes the blocked sender" has no separate board reading** (needs multiple tasks). 32-bit event sets: the **App-side SVC 0x21 channel is verified** (2026-11-15, `ESET_DEMO`, 37 assertions 0 failures, covering OR/AND masks, CLEAR granularity, illegal arguments rejected without state change, all-reject after destroy); the **kernel-side ISR entry is also on board** (same day, `eset_from_isr_contract`: real EXTI0 handler sets, asserts the waiter is only made READY without switching, AND short board does not wake, `mask 0` rejected with no bit moved; 40 assertions 0 failures, with "remove `arkrtos_eset_ready`" as a negative control reporting 3 reds); and the **SVC 0x21 ABI used by `arkrtos_eset_set_from_isr()` ran in a real handler** (after lowering EXTI0 priority to IP `0x40`, below SVCall's `0x10`: argument block in shared RAM returns 0 and wakes the waiter, the same handler using a kernel-stack argument block is rejected `-1` and the probe bit is not set; `eset_from_isr_contract` grew to 61 assertions, 190 total, 0 failures; two negative controls — unconditional parameter-window check → 2 reds; priority restored to reset value 0 → board resets). **The uncovered combination is "unprivileged App code + handler mode"** (this project has no ABI for App/driver ISR registration). On this board `ARKRTOS_ESET_NUM` was lowered to 4 instead of the default 8 to fit 120 KB kernel RAM, and the test image shrank the idle stack from 2 KB to 1 KB for this case plus 8 B of static for SVC-in-ISR, ending at `RW 996 + ZI 121840 = 122836 B` with 44 B left. Waiter capacity **does not fit in the F427 test image with the switch on** (`L6406E`, 108 errors); only `sync` 76 checks (`WQ-SLOTS=48`) plus `mq`/`sbuf`/`event` compile-level. **Multi-object wait with timeout is a 1 ms poll** (`ARKRTOS_APP_POLL_MS`), and the window between "probe says ready" and "caller consumes" cannot be eliminated. | | See [同步原语与令牌守恒](同步原语与令牌守恒.md) §5.6–§5.9 |
| User-state waiting is "register + poll", not kernel blocking. | Trade-off (price of SVC isolation) | Unprivileged code cannot suspend itself, so it registers and the kernel peeks at dispatch points. Semantically equivalent, one extra poll layer. See [同步原语与令牌守恒](同步原语与令牌守恒.md) |
| On QEMU a `clock_gettime` call occasionally returns a positive value of 3 with no source. | Defect (open) | Seen while running the fork eighth tier on QEMU LA64: one call the fixture spun on, reading `CLOCK_MONOTONIC`, came back with `a0 == 3` - neither `-ENOSYS` nor the kernel-accounted millisecond value. The kernel side has no `rc=3` record and no Linux-dispatch fall-through record either; the hit rate is roughly 1 in 4 to 1 in 12 runs of the same binary, with no pattern found. The only thing it broke was the "spin on the user-mode clock" construction, and the fixture no longer depends on that read: the child waits with three kernel-accounted 100 ms timed `futex(WAIT)` calls and reads no user-mode clock at all, while the parent reads the wall clock twice with 8 retries. Open item: the next hit needs `a0`/`a1` captured verbatim, the kernel dispatch counters and a QEMU `-d int` trace. See section 8.9 of [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.en.md) |
| Supported cores: Cortex-M3 / M4 / M7. | Debit (out of scope) | No M0/M0+/M23/M33 port and no TrustZone (SAU/secure world). M33 would need a new port plus SVC redirection |

## 2. Application shapes

| Limitation | Nature | Notes and evidence |
|---|---|---|
| Application shapes are decided by two independent switches; either or both may be on. | Design decision | **Window/MPU profile**: `.svcapp` (app/driver), arkc bare images (`app run` / `app flash`), MiniApps — all fixed-ABI images ([API参考](api/Ark%20RTOS_API参考.md), `arkrtos_app_image.h`). **Page-table/MMU profile** adds two more: `ARKRTOS_USE_ELF` (native ELF: LA64 ELF64/PLV3, RV32 ELF32/PMP+U mode, `exec /path/prog`) and `ARKRTOS_USE_MODLOAD` (VxWorks-style downloadable `.o`, PLV0). All four combinations compile; ELF and modules are **two parallel models, not replacements**. | See [MMU平台可下载模块-VxWorks式](MMU平台可下载模块-VxWorks式.md) |
| ELF and downloadable modules have **no** dynamic linking or shared libraries. | Trade-off (current implementation) | `PT_INTERP` on the ELF side is `ERR_FORMAT`; the module side only does `ET_REL` relocation and loads no dependencies. Both require addresses resolvable at load time |
| MiniApps have count and size caps. | Trade-off | Concurrency `ARKRTOS_MINI_MAX` defaults to 2 (1..4, out of range is `#error`); size is bounded by the load window. See [小程序设计](小程序设计.md) |
| A crashed MiniApp is disabled across resets. | Design decision | The crash count is persisted; past the limit it no longer autostarts and must be uninstalled/reinstalled manually. No automatic rollback |
| C++ is basically unusable. | Debit | Only `arkrtos_app_image.h`, `arkrtos_blk.h`, `arkrtos_fs.h` carry `extern "C"`; no global constructor table, no exception support |

## 3. System services

| Limitation | Nature | Notes and evidence |
|---|---|---|
| POSIX is a subset. | Trade-off | pthread / mutex / sem / time / socket / select; no POSIX signal API, no fork, no file locking, no process groups (`mmap` has a minimal file-mapping tier only on the Linux-ABI profile; see section 8.5 of the Linux ABI page). The Linux-ABI profile (`ARKRTOS_USE_LINUX_ABI`) has a signal tier instead - self-delivery plus cross-task delivery (2026-11-23), always delivered before a syscall returns, never preemptive, no real-time signals, no `siginfo`; see [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.en.md) section 7. See [POSIX与Windows兼容层说明](POSIX与Windows兼容层说明.md) |
| VFS has no Unix permission model. | Trade-off | No owner/permission bits/`chmod`; access control is "who can reach which SVC". See [VFS路径命名空间](VFS路径命名空间.md) |
| File systems are littlefs single volume + ramfs. | Trade-off | No journaling FS, no concurrent multi-volume writes, no quotas |
| Shell has exactly one serial console. | Trade-off | The console owns USART1, which is why the softbus cannot get the physical serial port (the direct cause of "two-node not verified") |
| Real Ethernet is not wired up. | Debit | No PHY driver, no MDIO access, no `eth_` interface, no RMII pin assignment; the network path runs on a loopback netif. See [lwIP协议栈接入](lwIP协议栈接入.md) §1 |
| The softbus is verified only over in-board loopback. | Debit | Two nodes over a real serial cable (two boards, or board + PC) is unverified; MCU profiles still need `-DARK_BUS_*` supplied by the project. See [软总线接入](软总线接入.md) §7 |

## 4. Reliability and security

| Limitation | Nature | Notes and evidence |
|---|---|---|
| Low-frequency INE halt in the fork+shm tier (**root cause located and fixed, 2026-11-25**) | Defect (fixed; deterministic repro + gate) | Symptom: with the five/ten switches on, after a child task exits the machine occasionally jumps to the zero page (`ecode=0x0d` INE). **Root cause (mechanism level)**: `LWIP_THREAD_STACK_W` in `kernelsrc/components/lwip/port/sys_arch.c` used to give 8 KB only when `ARKRTOS_USE_NET_VIRTIO=1` and 2 KB otherwise; but **whenever `ARKRTOS_USE_LINUX_SOCKET=1`** (exactly the QEMU ten-tier build), the tcpip thread also runs netconn/socket traffic and select wake-ups, far deeper than "call `tcpip_init` once". Four hard pieces of evidence: (1) not a single byte of the 0xcd fill pattern survives in the whole 2044-byte `g_thread_slot[0].stack` region (100% consumed); (2) the 528-byte trap frame runs past the bottom of that slot and writes `0x26c564` into the slot's `used` word (that value is precisely the return address of `bl la_trap_c` inside `eentry`); (3) it keeps going into the neighbouring `g_lwip_task_stack` (task 11 = `arkrtos_lwip_task`) and rewrites the saved ra at `0x8f4bd8` to `0x800`; (4) task 11 resumes with `ld.d $r1,$r3,8` loading 0x800 and the trailing `jirl` of `arkrtos_port_enable_irq` lands on the zero page => INE. **Why low-frequency, and why it previously "ran green with no lead"**: the stack-bottom guard is actually on for this board (`board/qemu_loongarch64/arkrtos_board_config.h` forces `ARKRTOS_USE_STACK_GUARD=1`), and it **did** report task 12 (`[STK] task 12: stack bottom flag overwritten`, 112 lines before the halt) -- but it reports *after* the fact: removing task 12 does not restore the neighbour frame it already clobbered. `ARKRTOS_USE_STACK_CHECK` judges `old_psp < stack_bottom`, and here sp always stayed inside its own stack, so it never fired either; lwIP itself prints nothing. **Fix**: give the socket tier 8 KB too (`LWIP_THREAD_STACK_W = 2048`); the ARM F427/F401 tiers have no socket and stay at 2 KB (`RW_KERNEL` is only 56 KB, and two 8 KB slots stop Keil at `L6406E`). **Deterministic repro (the key asset of this line)**: under `-icount shift=5,align=off,sleep=off` the pre-fix build hit 3/3 with byte-identical output; after the fix a 45 s pure run produced zero hits and the `stack` reading shows task 12 peaking at 1992 B of 8192 B (24%, 6200 B headroom). **Gate**: `tools/icount_stack_gate.py` (the `icount-stack` item of `ci_gate`) -- source pins (the 8 KB `#if` must mention both `NET_VIRTIO` and `LINUX_SOCKET`; `g_lwip_task_stack` is 4 KB in the socket tier; `sys_thread_new`'s bound still follows `LWIP_THREAD_STACK_W`) + a ten-tier rebuild + a pure `-icount shift=5` run asserting no FATAL, `[fork] PASS`, still running for many rounds after fork, `stack: check ok`, and that only the demo task is reported by the stack guard + restoring the default build afterwards. **Evidence discipline (new)**: gdb single-stepping perturbs the `-icount` phase -- a write watchpoint single-stepped through 3177 hits without ever landing on the fault (roughly 2449 hits were expected); this kind of forensics must use "break, then one bulk dump", never step-per-hit. **Historical leads (kept; no longer the conclusion)**: the two earlier signatures were `era=0x0025229b` and `era=0x26c58b` (both inside `eentry`'s GPR save loop, both not multiples of 4), the same shape as this one, "ertn out of an already-corrupted frame"; the three real defects fixed earlier (stale read-only COW entry, 64-bit fatal print, ERA-alignment swap gate) were never the root cause, and "72 repeated fork rounds with zero hits" only meant the deeper call path was never reached. **Still not covered**: real hardware (no LA64 board here); the ARM tiers have no socket and therefore no such path; `NET_VIRTIO=1 with LINUX_SOCKET=0` was not run separately (that combination has always been 8 KB anyway). |
| Image signing is symmetric HMAC, not a chain of trust. | Trade-off (current implementation) | A 32-byte key is compiled in: **whoever can sign can verify**. No asymmetric signature, no certificate chain, no key rotation. Keys never enter the repo (`*_sign_key_local.h` is gitignored) |
| The asymmetric profile only changes the verification credential, not the trust chain. | Trade-off (current implementation) | With `ARKRTOS_USE_IMAGE_SIGN_ED25519` the device stores a 32-byte Ed25519 public key, so reversing it no longer yields signing capability; but that key is **compiled into the firmware**, and guaranteeing it was not replaced is still SEC-G12's problem. No multiple keys, key versions, revocation or certificate chain. Still **one check at install time**; the verify path has no side-channel measurement for constant-time behaviour (about 5.7 ms/verify on a host at x86 -O1, not representative of the board). See 安全认证准备.en.md, SEC-G10 row |
| The trust root only answers where the public key came from; it is not a secure boot chain. | Trade-off (current implementation) | `ARKRTOS_USE_TRUST_ROOT` (2026-11-25, SEC-G12, **off by default**, hard-depends on `ARKRTOS_USE_IMAGE_SIGN_ED25519`) pins the SHA-256 of the image public key into a board slot at boot: a blank slot is written (TOFU, the first-boot window), an existing value is compared byte by byte, and a mismatch **latches** and refuses every later claim (`loader_accept` returns `FAIL_STATE`). It answers only "is the key compiled into the firmware still the one I first saw". It does **not** verify the kernel (the kernel has its own CRC recheck), does **not** sign images (signing still uses the same key at install/claim time), has **no attestation, no rotation, no revocation, no key versions**, leaves the **TOFU first-boot window open** (anyone can occupy the slot before the very first boot), and its **OTP one-time semantics are unverified on hardware** -- `arkrtos_port_trust_pin` is a weak symbol and the default board reports "unavailable", in which case sec reports SKIP rather than PASS. A slot read/write failure also does not latch (a missing part is not evidence of an attack). See 安全认证准备.en.md, SEC-G12 row |
| In the default profile signatures are checked only at install time. | Trade-off | A default build does not re-check the **signature** at runtime, so a modified running image is not noticed (MPU and the crash ledger have to catch that). Re-verification at claim time exists behind `ARKRTOS_USE_IMAGE_ACCEPT_VERIFY` (2026-11-25, SEC-G09, **off by default**): when on, `loader_accept` re-runs the install-time coverage rule. The image **CRC** also has a boot-time recheck (`ARKRTOS_USE_IMAGE_CRC_RECHECK`, default off, SEC-G17), but that only answers "are the bytes intact", not "who wrote them" |
| What the claim-time recheck proves depends on the signature profile | Trade-off (current implementation) | One switch, two readings: with a signature profile (`ARKRTOS_USE_IMAGE_SIGN`) it is **authentication** -- covered bytes plus a credential, so forgery is caught; **with no signature it is integrity only** -- it falls back to a CRC reverse computation, and a CRC has no credential, so anyone can compute a matching value and that profile cannot stop forgery. Another boundary: an unpatched `runtime_ram_base` makes this path report "cannot compute" (`ERR_PARAM`), which is neither a pass nor a failure; only `ARKRTOS_LOADER_ERR_SIGN` means "does not match". The host gate checks the pure function only; the real claim inside a pool scan and the boot ordering still need a board or QEMU. See [安全认证准备](安全认证准备.en.md) SEC-G09 |
| Boot CRC recheck covers only slots in the pool, and only records. | Trade-off (current implementation) | It covers slots with `slot_type != FREE` and `slot_base != 0`; when `runtime_ram_base` is not fixed or the image header cannot be read, that copy is reported `unknown` and recorded without a conclusion (neither pass nor fail). A mismatch only reports FAIL and counts it — **no automatic disable, no rollback**; the policy needs a separate decision |
| No reading for ionizing bit flips on real Flash. | Debit (verification tier) | Every reading so far comes from QEMU LA64. QEMU "Flash" is ordinary DRAM; this board only RAM-backs the image-pool range in `arkrtos_port_board_init()` (erase to `0xFF`, byte writes) and **does not model bit flips, does not require erase-before-write, does not retain content across reset or power loss**. Neither "one byte of the relocation table corrupted" nor long-term silent corruption has been tested on real hardware |
| The version gate runs before the signature gate. | Design decision | A non-increasing version is stopped at `INSTALL:211` and never reaches signature checking at `LOADER:1046` |
| No differential OTA, no A/B rollback. | Trade-off | Upgrade means "install the new image + hand over control"; failures rely on the crash limit and manual uninstall |
| Hot swap requires the new and old versions to have **identical layout**. | Design decision | `ARKRTOS_USE_TASK_SWAP` copies the whole RAM block and switches Flash slots, so block size, slot type and RAM size must match item by item (`ARKRTOS_SWAP_ERR_LAYOUT`), otherwise it refuses. Layout-changing upgrades must use the handover protocol of [无缝升级例程](无缝升级例程.md) |
| Hot swap **resets the data segment** (measured correction). | Measured | The block copy does move the old contents, but the image entry is a startup stub (`__main` / `MINISTART`) which re-runs `.data` initialisation and `.bss` zeroing after landing; probes show both back at initial values (see §5 of [无缝升级-双缓冲热切换](无缝升级-双缓冲热切换.md)). Cross-version state must therefore be serialised by the application, not assumed to persist in memory |
| Tasks that have used the FPU (Cortex-M) cannot hot swap. | Debit | The test lives in the port layer: in an ARM extended frame `[7]` is S6, not xPSR, so rewriting it as a basic frame corrupts the context and such frames are refused (`ARKRTOS_SWAP_ERR_FRAME`); RV32 checks `mepc` alignment and `mstatus.MPP`, LA64 checks `ERA` alignment and `PRMD.PPLV`, and an unrecognised frame is refused the same way. Supporting FPU frames needs the whole S0–S31 block moved |
| Hot swap has a silicon reading only on STM32F427. | Coverage boundary | Old-block return, old slot kept `LOADED`, switching back, and 58–233 ms per swap are all F427 + DAPLink readings; M3/M7 and other boards untested. RV32IMAC / LA64 have **QEMU kernel self-test** readings instead (5/5 and 3/3 `swap: PASS`), but both entries live inside the kernel image, so they do **not** cover the PIC / loading path, and they are not silicon. See §9 / §9.3 of the hot-swap page |
| Hot swap may break the heartbeat contract once. | Known limitation | One of four swaps showed `GUARD ... violating 1` (`crash` recorded `slot 0 faults=1 last=heartbeat`): the tick before the new image registers its new contract does not feed the dog. The contract does not carry across a swap; no fix implemented. See §9.2 and §10 of the hot-swap page |
| Hot swap has no automatic rollback orchestration. | Debit | `app swap` keeping the old slot is only the raw material; "swap back if no heartbeat within N seconds" needs "who decides the new version failed" defined first |
| Only one hot swap in flight at a time. | Design decision | The kernel has a single pending slot; a second `mini swap` / `app swap` returns `BUSY`. Multi-instance upgrade must queue |
| The crash limit of 3 disables an image and needs manual recovery. | Design decision | See §1.7 of [崩溃恢复与镜像版本把关](崩溃恢复与镜像版本把关.md) |
| Real-time figures are not a hard-real-time certification basis. | Debit (basis) | `rt` reports DWT-cycle measurements (tick.isr / wake.lo / wake.hi / crit.max); there is no WCET analysis and no worst-case execution proof. See [实时性与最坏延迟](实时性与最坏延迟.md) |
| tickless is on board on F427 only, and current was not measured. | Status | Board reading: `rt` reports `isr=18605 sleeps=18682 skipped=48728 of 67333 tick(s)`, interrupts down to 27.6%, 20 s idle without losing a tick. The two non-ARM tiers have QEMU readings since 2026-11-20 (LA64 `isr=381 sleeps=126 skipped=376 of 757 tick(s) cap=8`, RV32 `isr=557 sleeps=351 skipped=2319 of 2876 tick(s) cap=8`), but those are emulator scheduling behaviour. **No tier has an ammeter reading**, only the indirect evidence of "sleeps longer". See §8 of [低功耗与tickless](低功耗与tickless.md) |
| Security certification has not been submitted. | Status | `sec` T1–T12 are **local test cases**, not any certificate; `docs/安全认证准备.md` is a gap table and register, not a compliance statement |
| Shell authentication exists but is still a weak password, and Flash option bytes are read-only. | Partial debit | Shell login = SEC-G01, **implemented (2026-11-17, default off, `ARKRTOS_USE_SHELL_AUTH`)**. Remaining limits: password crosses the serial port in clear text, the digest can be brute-forced offline for weak passwords, the hard lock clears only on reset, no runtime password change, and it is not a device identity (device identity is still SEC-G13). Option-byte **reading** is done (2026-11-13, `sec` `flash.protection` reports the real RDP/WRP); **setting** them (RDP/WRP writes, irreversible, production-line) is the other half, SEC-G04. See §7 of [安全认证准备](安全认证准备.md) |
| The per-App resource quota covers the task table and the fixed-block pool, not the general heap. | Implemented with stated bounds (SEC-G07) | The **task table** (2026-11-24): `ARKRTOS_USE_APP_QUOTA` + `ARKRTOS_APP_MAX_TASKS` (2026-11-24, default off), where fork and `clone(CLONE_THREAD)` return `-EAGAIN` once the owner's live task count reaches the cap. Three boundaries: (1) it covers the task table and, since 2026-11-25, the fixed-block pool (`ARKRTOS_APP_MAX_POOL_BLOCKS`, default 0: blocks are charged to the caller's `app_owner`, a take past the cap goes back on the free list and returns 0, at most 128 blocks and 8 owners are tracked per pool, accounting only with no ownership validation) -- the fd table is already capped per process (`LX_MAX_FD`), page frames are already bounded by the App's own 2 MB window, and **the general heap still has no per-App quota**; (2) a thread has `stack_size == 0`, so under COW the stack pair is classified by a 32 KB hint window below the stack top (`LA_PG_THREAD_STACK_HINT`) -- that is a **classification hint, not a stack-bottom guarantee**, and stack guards / overflow checks must not rely on it; (3) concurrent processes are bounded by `ARKRTOS_PAGING_APPS_MAX` (2 on this board) and `ERR_QUOTA` and `ERR_BUSY` both map to `-EAGAIN` in `lx_fork_errno()`, so the return value cannot tell "quota exhausted" from "address space exhausted" -- only the `[appq]` log line (or the fact that a thread takes no new address space) separates them. See section 7 SEC-G07 of [安全认证准备](安全认证准备.md) |

| Limits of the persistent audit ring | Trade-off (current implementation, SEC-G05) | `ARKRTOS_USE_AUDIT_LOG` (default off) writes nine classes of security events into an on-volume ring file (`/audit.bin`, a 32 B header plus N x 32 B records; 64 records by default = 2080 B). Five boundaries: (1) **task context only** -- the panic path never touches the file system (the crash may well be in the file system), so fault provenance stays with the crash ledger; (2) **single writer** -- a concurrent `record()` returns `BUSY` and counts `dropped`, it neither merges silently nor queues (queueing means doing it in a critical section, and the cost does not match the benefit); (3) **no key** -- anyone who can write the volume can delete, alter or forge records, so tamper detection needs SEC-G10 or append-only media; (4) **no cross-reset claim** -- the host volume and the QEMU NOR are both RAM arrays and lose content on reset, so cross-reset only holds on real Flash, and writing during power loss has not been measured; (5) it occupies 32+N x 32 bytes on the volume and the path is a **volume-absolute path** (`/audit.bin`), not the VFS `/mnt/...` form. See section 7 SEC-G05 of [安全认证准备](安全认证准备.md) |
| Limits of the rollback whitelist | Trade-off (current implementation, SEC-G11) | `ARKRTOS_USE_ROLLBACK` (default off) lets an older image that is already in the pool be installed again. Five boundaries: (1) **RAM only** -- the entries are gone after a reset, which is a security premise rather than a defect (a persistent entry is a permanent downgrade ticket), so the operator has to arm it again every boot; (2) **it does not judge versions** -- "known good" is the operator's assertion and the module only guarantees that the assertion is explicit, content-bound, bounded and recorded; (3) **it does not delete the bad copy** -- after a rollback both versions sit in the pool and which one starts is the autostart / `app start` decision; (4) **the crc32 binding** assumes the whole device uses the same crc32 implementation (the install-time recheck shares that assumption), so changing CRC parameters invalidates it; (5) **the host cannot prove a cross-reset story** -- the host pool is a RAM array and loses content on reset, so the downgrade/rollback chain on real Flash has no on-board reading. See section 7 SEC-G11 of [安全认证准备](安全认证准备.md) |
| Limits of the component self-test | Trade-off (current implementation, SEC-G14) | `ARKRTOS_USE_SELFTEST` (default off) runs four diagnostics: RAM window patterns, 12 known-answer CPU vectors, a read-only-region crc baseline, and a clock-ratio cross-check. Four boundaries: (1) **two readings off the same source cannot see a crystal error** -- it compares this side's tick against this side's counter, so one bad crystal pulls both the same way; it catches gross failures (frozen counter, frozen tick, wrong divider) and is not a frequency reference; (2) **RAM covers the dedicated window only** (`ARKRTOS_SELFTEST_RAM_BYTES`, 512 B by default) -- writing patterns into someone else's memory at runtime turns diagnosis into fault injection, and a whole-memory scan belongs to early boot, which this module does not claim; (3) **the read-only item only proves 'changed since the boot baseline'** -- the baseline is the crc32 this side computed at boot, so it detects a runtime modification but not a forged factory image (that is the signature chain's job); (4) **the verdict is SKIP, not PASS** -- when a board does not implement the hook, that item reports SKIP, so 'not measured' is never counted as 'passed'. See section 7 SEC-G14 of [安全认证准备](安全认证准备.md) |
| Fault injection covers only the three software-reachable decisions | Trade-off (current implementation, SEC-G16 software half) | `ARKRTOS_USE_FAULT_INJECT` (default off) injects kernel **decisions**: an allocation failure, a task-creation failure and a skipped tick. Four boundaries: (1) **not bit flips** -- writing bits into someone else's memory is damage, not injection, and would turn the self-test itself into a counterexample; voltage/clock glitches and peripheral errors are also out of scope (they need hardware monitoring, which is SEC-G15 and the physical half of this item); (2) **the watch baseline is taken at registration** -- a span forged before it was registered is invisible, and catching that needs the signature chain (SEC-G12 / SEC-G09); (3) `fi test` uses the module's own static buffer, so it validates the watch path itself and does not claim arbitrary addresses work; (4) **the budget auto-disarms when spent**, so "the injection took effect" and "the budget disarmed" must be read together (`mpool test` reporting FAIL and then ALL PASS is exactly those two readings); one failure alone does not prove the next call will pass. See section 7 SEC-G16 of [安全认证准备](安全认证准备.md) |
| The read-only shared window does not hold on RV32 | Trade-off (current implementation, SEC-G03) | Shared RAM (partition table + crash journal) is "privileged read/write, unprivileged read-only" on ARM (M3/M4/M7) through the new `ARKRTOS_MPU_MEM_RAM_RO` kind (AP=0b010), so an unprivileged App can only read it. **RV32 cannot do this**: PMP has no privilege bit, an entry applies to M-mode as well, so making it read-only would also block the kernel's own store inside the SVC handler (the task's PMP is still installed when the trap enters) — that trades "a hole" for "cannot install images". That port therefore encodes read/write and the mitigation does **not** hold on RV32; doing it properly needs a "clear PMP on trap entry, re-install before return" design, which is registered as a debit and not implemented. LA64 isolates with page tables and the share window lives in the kernel PLV0 identity map, which an unprivileged task cannot reach anyway, so behaviour there is unchanged. See §7 SEC-G03 of [安全认证准备](安全认证准备.en.md) |

## 5. Development and toolchain

| Limitation | Nature | Notes and evidence |
|---|---|---|
| The non-ARM instrument frequency is not a silicon figure. | Status | RV32's `3108533020 Hz [measured]` is measured inside QEMU and depends on host scheduling; LA64's denominator is the board constant `ARKRTOS_PORT_RDTIME_HZ = 100000000`. Microsecond figures on these two tiers are therefore self-consistent within one tier only, **not comparable across tiers and not worst-case latency**; only ARM's DWT `CYCCNT` denominator comes from a real clock. |
| The overlay `/delete-node/` encoding is project-defined. | Trade-off | Deleting a child node in a dtb is expressed as one zero-length `__delete` marker property. The Linux dtbo encoding of `/delete-node/` was not confirmed from an authoritative source here (no `dtc` on this machine, fetching the original text was blocked), so it is **not claimed to be byte-identical with a Linux dtbo**. The `target = <&label>` half (`__fixups__` + `__symbols__`) does follow the Linux mechanism. |
| The three QEMU targets are covered unequally. | Status | `board/qemu_riscv32` and `board/qemu_loongarch64` are **run and evidenced**; `board/la32_generic` stops at compile/link (this machine has no LA32 execution carrier). See the three-target matrix in §8 of [QEMU模拟器移植与验证](QEMU模拟器移植与验证.md) |
| No gdb remote stub; real-board debugging depends on Keil. | Debit | Debugging goes through Keil UV4 + pyocd + the `mdkdebug` MCP. QEMU restarts in seconds but has no single-step or breakpoint interface, so only kernel self-reported readings |
| Source encodings are mixed. | Status constraint | Old sources are GBK, new ones UTF-8; `ci_gate`'s `encoding` check only guarantees each file decodes, not uniformity. Changing a GBK file requires a **byte-level patch**; whole-file transcoding turns the diff into a full rewrite |
| The GCC example depends on an external toolchain. | Status | The `GCC构建指南` set needs `arm-none-eabi-gcc`, which the repo does not ship and this machine may not have (build status is in that guide's "verification status" section) |
| `pyocd` readings cannot be used as evidence. | Status constraint | With the target **running**, `read32` on peripherals returns constant fake values (`RCC_CR` / `FLASH_OPTCR` / `GPIOC_ODR` all give `0x03000000`), so only `halt` gives truth; but `halt → read → go` has been measured to reset the target (watchdog), zeroing `hwsafe`'s `handover` and restarting `tick.isr`. Instantaneous state must come from the kernel's own counters via shell, see §9.6 of [小程序设计](小程序设计.md) |
| No real static analysis; overall kernel coverage still missing. | Partial debit (2026-11-17) | Coverage: `coverage-host` is wired but measures only the 10 modules the host tests link (`tools/coverage_baseline.json`), with a "not below the pinned value" threshold; scheduler, SVC, drivers and shell are not linked on the host, so **kernel-wide coverage is still absent** and there is no board collection either. Code checking: `warn-clean` is wired (21 host-compilable TUs with zero `-Wall -Wextra -Wshadow` warnings; it already caught an uninitialised pointer in `sync`), but there is **no cppcheck / MISRA / clang-tidy** — cppcheck is not installed here and GCC 4.8 has no `-fanalyzer`; kernel files that depend on architecture headers are outside the warning gate |
