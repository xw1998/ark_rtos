# Ark RTOS Apps and Drivers: Full Install and Debug Flow

> Condensed English edition. The Chinese page (Ark RTOS应用安装与调试指南.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

> This is the **operating manual** — it answers "how do I get work done today". For the
> principles behind the config area and the two install strategies, and the design rationale of
> the image format, see 配置区与安装策略.md.

## 0. Three landing paths at a glance

The same App/driver project can reach the board three ways, and **all three converge on the same
boot flow** (kernel scans the pool → identifies images → registers slots → creates tasks):

| Path | Used for | Artifact | How it lands | Kernel restart needed |
|---|---|---|---|---|
| **A dev/debug** | daily coding, breakpoints | bare image (`.axf`) | Keil Download straight into the fixed dev slot | no |
| **B serial install** | field upgrade, no programmer | `.svcapp` | kernel receives over serial and writes into the pool | no |
| **C programmer write** | first article, batch | `.svcapp` or bare image | programmer writes directly to the slot address | no (but the kernel is usually flashed too) |

Where they land is decided by the **install strategy**:

- **fixed mode**: fixed landing, path A is the main route (customer secondary development);
- **auto mode**: the kernel allocates inside the pool, path B is the main route (field upgrade).

> Path B supports both apps and drivers (the kernel routes by the image header's `type`).
> Multi-slot support on the image side used to be a gap; see §10 item 6 (now closed).

## 1. Quick reference

### 1.1 Flash partitions (F427, 1 MB; source `config/arkrtos_partition.h`)

| Partition | Address range | Size | Contents |
|---|---|---|---|
| KERNEL | `0x08000000 ~ 0x0803FFFF` | 256 KB | kernel (shell, install logic, lwIP stack; see [lwIP协议栈接入](lwIP协议栈接入.md)) |
| CONFIG | `0x08040000 ~ 0x0805FFFF` | 128 KB | on-device config records (only the first 512 B used) |
| IMAGE_POOL | `0x08060000 ~ 0x080FFFFF` | 640 KB | **unified image pool**: apps and drivers share it, 5 × 128 KB sectors |

Pool allocation granularity is 1 KB (`ARKRTOS_POOL_ALLOC_UNIT`), erase granularity is a sector
(128 KB). A 10 KB app occupies about 11 KB in auto mode instead of a whole sector.

> KERNEL went from 128 KB to 256 KB because of lwIP (`ARKRTOS_USE_LWIP=1`): an MPU region must be
> a power of two, so the next tier up was the only option, at the cost of 128 KB of pool. See
> [lwIP协议栈接入](lwIP协议栈接入.md) §6 for the cost and how to remove it.

**F401 (512 KB)**: KERNEL 128 KB + CONFIG 128 KB + pool 256 KB (2 sectors).

> **Changing chip capacity means changing `CHIP_FLASH_SIZE` only**; all other addresses and all
> `.sct` files are recomputed automatically.

### 1.2 Development life cycle

Four app/driver projects and their fixed landing points (decided by the dev-slot table in §8 of
`config/arkrtos_partition.h`; `.sct` generated by `tools/gen_scatter.py`):

| Project | Type | Flash landing | RAM window | Stack top |
|---|---|---|---|---|
| `DRV_DEMO` | driver | `0x08060000` (unit 0) | `0x20010000 +16 K` | `0x20014000` |
| `APP_DEMO` | app | `0x08080000` (unit 1) | `0x20014000 +16 K` | `0x20018000` |
| `BLED_DRV` | driver | `0x080A0000` (unit 2) | `0x20018000 +16 K` | `0x2001C000` |
| `BLED_APP` | app | `0x080C0000` (unit 3) | `0x2001C000 +16 K` | `0x20020000` |

The matching `.sct` files are `build/drv_demo.sct` / `app_demo.sct` / `bled_drv.sct` /
`bled_app.sct`.

### 1.3 RAM layout (F427, 128 KB)

| Partition | Address range | Size | Purpose |
|---|---|---|---|
| SHARE_RAM | `0x20000000 ~ 0x20001FFF` | 8 KB | partition table (kernel↔app data exchange) |
| KERNEL_RAM | `0x20002000 ~ 0x2000FFFF` | 56 KB | kernel data / kernel task stacks |
| SLOT_RAM | `0x20010000 ~ 0x2001FFFF` | 64 KB | image RAM pool |

An image's `.data/.bss/stack` is carved from `SLOT_RAM` by **buddy allocation**; blocks must be a
power of two within `[1 KB, 32 KB]` (a hard MPU region constraint).

**The install path and the power-up scan must produce the same window.** Both bind the RAM block
from the `ram_size` declared in the image header (rounded up to a power of two); the `ram_size`
registered for a fixed slot is only the **upper bound** of that window, and an image asking for
more makes install fail outright. If the install path bound by the config value instead, the same
image would get two differently sized windows for "installed and started immediately" versus
"rescanned after reboot", and the stack would sit a window-difference away — while the stack
overflow criterion (saved PSP < stack bottom) is computed against that window, so it would fire on
a wrong threshold. In the field this looks like "the app stops early in the same power cycle it
was installed, `fault` shows one `STACKOVF`, and after a reboot everything is normal".

**One field case (2026-11-14, POSIX_DEMO)**: that image declares `ram_size = 16384` (RW/ZI 4348 +
stack 4096 + heap 2048 = 10492, rounded up to a power of two), while all 3 fixed slots registered
`ram_size = 0x2000` (8 KB). After `install 2` opened the receive window, `send_image.py` was
rejected right at the header + relocation-table frame: `INSTALL: rejected: err -4, type 1,
payload 10532 B, reloc 56` — `err -4` is `ARKRTOS_LOADER_ERR_SIZE`, "the image wants more than the
slot's registered bound". The fix is to rewrite one config record without touching other fields:
`tools/arkrtos_layout.py build --config <json> --bin layout.bin --seq <new seq>` to produce the
record, then `tools/arkrtos_cfg.py write --port COMx --bin layout.bin --reboot`. The config area is
**append-only** (writes go to the next free record slot, old records are not erased), so a bad
write can be walked back; but `cfg clear` erases the whole config area and drops straight to
compile-time defaults (the default table is empty) — do not use it unless that is what you want.

> **`cfg show` does not print the per-slot `ram_size`**; it only shows Flash base, size and RAM
> base — the window bound is invisible from the console. To see it you must read the record in the
> config area (`0x08040000`, 512 B each, slot table from +0x20, 32 B per slot, `ram_size` at +16
> within the slot), **and you must `halt` first**: while the target runs, reading the same Flash
> range via pyocd / pyOCD cmd intermittently mixes in garbage words (measured: the same address
> read twice gave `2808b51c`, `b169d20e` and similar values not belonging to that sector), while
> after halt two consecutive reads are byte-identical. The toolchain-side equivalent check is
> rebuilding the old record with `tools/arkrtos_layout.py build ... --seq <old seq>` and comparing
> it byte for byte (including the CRC) against the 512 bytes read back from the board.

**Dev slots use static windows**: 16 KB per slot (`ARKRTOS_DEV_RAM_WINDOW`), and 4 slots exactly
fill `SLOT_RAM`. Window base formula:

```
window base = SLOT_RAM_BASE + (start unit % ARKRTOS_DEV_SLOT_MAX) × ARKRTOS_DEV_RAM_WINDOW
```

This formula is implemented twice — `ARKRTOS_DEV_SLOT_RAM_BASE(unit)` in
`config/arkrtos_partition.h` and `dev_ram_base(unit)` in `tools/gen_scatter.py` — and **the two
must agree**, otherwise the app links believing the stack is at A while the kernel puts it at B,
which shows as "downloads fine, starts fine, crashes after a while".

The stack is carved from the **top** of the window: app 4 KB (`APP_TASK_STACK_SIZE`), driver 1 KB
(`DRIVER_TASK_STACK_SIZE`). The remainder after subtracting the stack is the RW/ZI ceiling —
**if RW would collide with the stack, the link fails**, it does not wait for runtime.

Neither apps nor drivers generate `ARM_LIB_HEAP`; for dynamic memory use `arkrtos_posix_malloc`
(see POSIX与Windows兼容层说明.md).

### 1.4 Strategy switches

**Compile time** (`config/arkrtos_partition.h`):

| Macro | Default | Effect | When to change |
|---|---|---|---|
| `APP_ALLOW_RAW_IMAGE` | 0 in `config/`; both boards set it to 1 in `arkrtos_board_config.h` | allows **bare images** in the pool (development). At 0 only headed `.svcapp` are recognised | remove the board override or set 0 in release firmware |
| `APP_AUTO_START` | 1 | start a valid app automatically after the scan | set 0 when debugging so the kernel does not start it before your breakpoint |
| `DRIVER_AUTO_START` | 1 | same for drivers | as above |
| `APP_CRASH_RESTART_MAX` | 3 | consecutive fault restarts before disabling; 0 = unlimited | per reliability requirement |
| `SHELL_ENABLE` | 1 | kernel shell console task (takes the serial read right); value comes from Kconfig `ARKRTOS_USE_SHELL` | set `ARKRTOS_USE_SHELL=n` in defconfig when no console is wanted |
| `INSTALLER_ENABLE` | 1 | build the in-kernel install logic | set 0 when not using serial install |
| `INSTALLER_AUTO_START` | 1 | start the app immediately after install | set 0 for "install first, start later by hand" |

Changing any switch **requires rebuilding the kernel only** (`.sct` is regenerated before the
build).

**Runtime** (on-device CONFIG sector; changing it needs no rebuild):

| Item | Effect |
|---|---|
| `mode` | 0 = auto placement, 1 = fixed slots (one per device) |
| `flags` | bit0 = `RAW_ALLOW`: whether this device accepts the bare-image bypass |
| `boot_delay_ms` | busy-wait before autostart (leaves the debugger an attach window), max 60000 |
| `log_level` / `fault_restart_max` | kernel log level / crash restart limit |
| slot table | landing point, type, RAM window, autostart flag in fixed mode |

Writing method and field list: 配置区与安装策略.md §4/§6.

## 2. Path A: development and debugging (the daily route)

### 2.1 One-time preparation

The app / driver / kernel projects are already configured. Check three things (project → Options
for Target):

1. **Target → do not use the Target Dialog memory layout** (`<umfTarg>0`, so the scatter file takes effect)
2. **Linker → Scatter File** points at the matching `.sct`:
   - kernel → `build/kernel.sct`
   - `APP_DEMO` → `build/app_demo.sct`; `BLED_APP` → `build/bled_app.sct`
   - `DRV_DEMO` → `build/drv_demo.sct`; `BLED_DRV` → `build/bled_drv.sct`
3. **User → Before Build/Rebuild** left empty (the `.sct` is already generated in `build/`)

To regenerate `.sct` (for example after changing the slot table or RAM window):

```bash
# kernel
python tools/gen_scatter.py --target kernel --output build/kernel.sct
# bare images (--raw --dev-slot picks the dev slot number; apps and drivers share target=image)
python tools/gen_scatter.py --target image --raw --dev-slot 1 --type app    --output build/app_demo.sct
python tools/gen_scatter.py --target image --raw --dev-slot 0 --type driver --output build/drv_demo.sct
python tools/gen_scatter.py --target image --raw --dev-slot 3 --type app    --output build/bled_app.sct
python tools/gen_scatter.py --target image --raw --dev-slot 2 --type driver --output build/bled_drv.sct

python tools/gen_scatter.py --dump      # print the current layout, confirm addresses before generating
```

> `.sct` is a **build artifact, never edit it by hand**: the next generation overwrites it, and a
> hand-edited address silently diverges from what the kernel derives.

### 2.2 Debugging an app (steps)

1. Confirm the development settings:
   - `APP_ALLOW_RAW_IMAGE = 1` (both boards already set it in `arkrtos_board_config.h`)
   - `APP_AUTO_START = 1`
   - a little `boot_delay_ms` (say 500 ms) to leave the debugger an attach window
2. Build the kernel → flash to `0x08000000`
3. Open the app project (e.g. `APP_DEMO`) → confirm the Scatter File is `build/app_demo.sct`
4. **Keil Download directly** (writes `0x08060000` per the `.sct` load region)
5. Reset and run
6. Kernel scans the pool → identifies a bare image → entry = `0x08060000 | 1` → binds the RAM
   window `0x20014000` → registers the task and starts it
7. Set a breakpoint in app code → it hits

### 2.3 Debugging a driver

Same steps, except:

- use `DRV_DEMO` / `BLED_DRV` and `build/drv_demo.sct` / `build/bled_drv.sct`
- download addresses are `0x08060000` / `0x080A0000`
- the kernel starts the driver first (priority 9, above the app's 10), then the app

### 2.4 Re-downloading the app without re-flashing the kernel

**This is path A's core value**: the kernel does not move.

As long as the app's **link base has not changed** (slot table and RAM window unchanged, `.sct`
unchanged), just rebuild + Download the app; after a reset the kernel rescans and starts the new
version.

### 2.5 Why an app must run where a kernel exists

An app project has **no startup file and no vector table**; it is not a firmware that resets from
the beginning:

- its entry `APPSTART` is jumped into by the kernel **as a task function**;
- it calls SVCs for kernel services, and the SVC handler lives in the **kernel's vector table**
  (`0x08000000`).

App and kernel are symbiotic: debugging an app requires a running kernel on the board.

### 2.6 Debugging tips

| Tip | Reason |
|---|---|
| `APP_AUTO_START = 0` | the kernel will not start a slot before your breakpoint |
| `boot_delay_ms` 300~1000 | the kernel pauses after coming up, making attach easy |
| keep the board-level `APP_ALLOW_RAW_IMAGE = 1` | otherwise bare images are not recognised and the app does not start |
| one Keil instance at a time | multiple instances contend for the shared UVSOCK port |

## 3. Path B: serial install

> **Once the kernel shell is on, the serial read right belongs to the console.** With the default
> `SHELL_ENABLE = 1`, type `install` in the console to open a one-shot receive window, then send
> the image — this prevents two readers from randomly splitting the bytes of one serial FIFO. Full
> commands and examples: 内核Shell控制台使用说明.md.

### 3.1 Protocol

**No extra framing at all** — send the `.svcapp` file to the serial port unchanged:

| Item | Note |
|---|---|
| Device | `INSTALLER_DEV_NAME` (default ttyS0) |
| Baud rate | `INSTALLER_DEV_ARG` (default 115200) |
| Format | 8N1, no flow control |
| Sync | the kernel searches the byte stream for the image header magic `SVCA`, **re-synchronising byte by byte**; stray bytes are skipped |
| End | no terminator needed; the kernel stops once it has read `image_size` bytes from the header |
| Routing | the kernel looks at the header's **`type`** and decides the destination itself |

### 3.2 Packing

```bash
# pack straight from a Keil project (recommended: compiles four passes for differential
# relocation and resolves the entry symbol automatically)
python tools/pack_app.py --project example/stm32f427/app_sdk/APP_DEMO/MDK-ARM/app_demo.uvprojx \
    --type app --version 1.0.0 --name "LED blink demo" \
    --out build/APP_DEMO/APP_DEMO.svcapp

# driver: same tool, only --type becomes driver (type = 2 in the package, entry symbol DRVSTART)
python tools/pack_app.py --project example/stm32f427/driver_sdk/DRV_DEMO/MDK-ARM/drv_demo.uvprojx \
    --type driver --name DRV_DEMO \
    --out build/DRV_DEMO/DRV_DEMO.svcapp

# offline packing from existing .bin files (offline mode: A/B/C are mandatory, D validates at pack time)
# A = nominal base, B = ROM +delta, C = RAM +delta, D = ROM +2delta & RAM +delta
python tools/pack_app.py \
    --bin-a build/pack/APP_DEMO/payload_A.bin \
    --bin-b build/pack/APP_DEMO/payload_B.bin \
    --bin-c build/pack/APP_DEMO/payload_C.bin \
    --bin-d build/pack/APP_DEMO/payload_D.bin \
    --entry-offset 0x0 \
    --type app --version 1.0.0 --name "LED blink demo" \
    --out build/APP_DEMO/APP_DEMO.svcapp
# instead of a numeric entry offset you may pass --axf <the .axf of the nominal-base pass>:
# the tool resolves the entry from the symbol table and verifies that pass really linked at the
# nominal payload base. --axf alone without --bin-a/--bin-b/--bin-c does not work:
# the relocation table comes from the three-pass difference.

python tools/pack_app.py --info build/APP_DEMO/APP_DEMO.svcapp      # inspect the header
python tools/pack_app.py --verify build/APP_DEMO/APP_DEMO.svcapp    # verify integrity
```

The header's `hw_compat_id` must match the device (F427 = `0x42700005`, F401 = `0x40100005`),
otherwise the kernel refuses the install — this is the guard against installing an F427 image on
an F401.

Entry symbol convention:

| Symbol | Note |
|---|---|
| `APPSTART` / `DRVSTART` (default) | SDK startup entry: initialises the C runtime (`.data` copy, `.bss` clear) and then enters the app's `main` / the driver's `DrvMain`. **Required if the image has initialised globals** |
| `main` (app) / `DrvMain` (driver) | enter the business function directly, skipping runtime init |

### 3.2.1 Where the version number comes from, and the version gate at install

**The version number has exactly one source** (`tools/pack_app.py` looks in this order):

| Priority | Source | Note |
|---|---|---|
| 1 | command line `--version 1.1.0` | explicit, highest priority |
| 2 | `app_version.txt` in the project root | one level above `MDK-ARM`; first non-empty, non-`#` line is the version |
| 3 | neither | **error**, no more silently packing `0.0.0.0` |

Item 3 is deliberate: the install path now enforces monotonic versions by `image_id`, and a silent
v0 would make both "install a second time" and "roll back an older build" look like legal installs.

**Version gate before the commit point** (kernel `arkrtos_loader_check_install()`, comparing only
within the same `image_id`; `image_id` is the payload identity = crc32 of the nominal form, so two
packs of the same app that differ only in version number share an `image_id`):

| Case | Result |
|---|---|
| version > highest installed | allowed (upgrade) |
| same version and identical `image_size` and `crc32` | refused, `err -17`: `identical image already installed (id 0x…, v1.0.0.0, 17768 B) - nothing to do` |
| anything else (downgrade re-feed, same-version rebuild) | refused, `err -16`: `version not increasing (id 0x…, incoming v1.0.0.0 <= installed) - bump the version` |

The two messages are reported separately so the operator sees the next step at a glance: the first
means "no need to install", the second "bump the version".

Only copies in state `LOADED` / `RUNNING` are counted: a copy disabled by the crash-limit policy
(`INVALID`) does not count as installed — reinstalling the same version is precisely the way out of
a crash storm (see 7.3).

**The `signature[64]` field in the header is reserved and currently all zero; the kernel does not
read it and there is no signature check by default.** The install path verifies `hw_compat`,
length, the relocation table and CRC32 — those guard against "transferred badly / installed the
wrong thing", not against "someone modified it". Do not treat it as evidence of signing.
(`ARKRTOS_USE_IMAGE_SIGN=1` turns on a real HMAC-SHA256 check; see §10 item 2 and §11.4.)

### 3.3 Sending

1. Kernel flashed and reset, serial console shows the `ark>` prompt
2. Type `install` (auto mode) or `install <slot>` (fixed mode) to open the receive window.
   **Fixed mode must name the slot**: the kernel does not know which slot to erase before it sees
   the header, so a bare `install` in fixed mode answers
   `usage: install <slot>   (fixed-slot mode needs an explicit slot)`
   **and that slot is wiped first**: before telling you "you may send", the kernel stops the image
   running in that slot and erases the whole slot (device log `install: slot %u still running (id
   %u), stopping it before the erase`, followed by the unloader's `LOADER:183 halt task N`). So the
   price of naming the wrong slot is that the old image there is already gone — **including when
   the type does not match and the frame is finally rejected (`err -7`)**. To put a driver package
   on the board, the target slot must be one whose config says `type = driver`.

> **This "stop before erase" was only added on 2026-11-14.** Earlier versions of this document said
> "the kernel first stops the image running in that slot", but `cmd_install` only erased and did not
> stop — the headless installer (`arkrtos_installer_fixed_prepare` in `arkrtos_installer.c`) had
> always stopped first, the console path had missed it. The consequence is plainly visible on the
> board: while an app is fetching instructions from that slot, `install <slot>` erases the flash
> under its feet to `0xFF`, three `USGFAULT`s hit the crash limit and the whole slot is disabled.
> Measured sequence before the fix (F427):
>
> ```
> fault:  0 18062 5 USGFAULT | 1 18062 5 RECOVER | 2 18062 5 USGFAULT
>         3 18062 5 RECOVER  | 4 18063 5 USGFAULT | 5 18063 5 TASKKILL | 6 18063 5 APPDISABLED
> dmesg:  [   84.031] LOADER:183 halt task 5: taken out of the scheduler
>         [   84.031] CRASH:3161 slot 1 disabled: crash-limit, 3 consecutive faults
> ```
>
> After the fix the same path leaves only one `TASKKILL` (orderly stop), with no `USGFAULT` and no
> `APPDISABLED`, and `install: ok` plus the restart all behave. `Code=220290 → 220382` (+92 B).
3. Send the `.svcapp` to the serial port in **binary mode** (text mode rewrites line endings)
   - `copy /b build\APP_DEMO\APP_DEMO.svcapp COM3`
4. When sending finishes, `INSTALLER_AUTO_START` decides whether it starts immediately
5. `app list` to see the result

### 3.4 What happens on power loss or interruption

During install the slot state is **`INSTALLING`**, and only after **everything is written and the
CRC read-back matches** does it become `LOADED`.

> Half-written then power loss → the state disappears with RAM → on the next power-up the kernel
> CRC-checks the half-written slot → CRC fails → judged `INVALID` → **it will not be started**.

So interrupting an install is safe: it never leaves a "looks usable" bad slot. Just send it again.

## 4. Path C: pack then write with a programmer

When production or a first article needs kernel + images flashed in one go:

| Image | Address | Source |
|---|---|---|
| kernel | `0x08000000` | kernel project build output |
| config records (optional) | `0x08040000` | output of `tools/arkrtos_layout.py build --bin` |
| driver `.svcapp` | any free pool slot (auto) or the slot named in config (fixed) | `pack_app.py` output |
| app `.svcapp` | as above | `pack_app.py` output |
| bare image | the address given by the dev-slot table (§1.2) | the app project's `.axf`/`.bin` |

- `.svcapp` is "256-byte header + payload" as a whole; **write it from the start straight to the
  slot base**, no splitting needed.
- Note: **a slot holds either a `.svcapp` or a bare image, never both** — a headed image's entry is
  `slot base + 256 + entry_offset` while a bare image's entry is `slot base`; the two layouts differ
  by 256 bytes and mixing them runs off into the weeds.
- The only difference between a driver and an app is the header's `type`: `--type driver` produces
  `type = 2`, and the kernel finds the slot by type (auto mode looks for a free record, fixed mode
  accepts slots whose config says `type = driver`). Installing into a `type = app` slot is refused
  with `err -7`, plus a separate line explaining the config slot type versus the image type.

## 5. Power-up sequence (kernel view)

```
main()
 └─ arkrtos_kernel_init()
     ├─ module init (log / mutex / partition table / layout)
     ├─ arkrtos_layout_init()        read the CONFIG sector; fall back to compile-time defaults
     ├─ boot_delay_ms non-zero ?  → busy wait (attach window for the debugger)
     ├─ scan the pool → identify headed images
     ├─ RAW_ALLOW ?                → claim dev slots and bind RAM windows
     ├─ reclaim (per reclaim_mode) → compact / erase empty sectors
     ├─ start drivers (DRIVER_AUTO_START)
     ├─ start apps (APP_AUTO_START)
     └─ shell console
 ...
 scheduler starts
```

Drivers start **before** apps because drivers should be ready for them.

## 6. Image identification rules (how the kernel decides what is in the pool)

The scan starts at the pool base and walks linearly at 1 KB granularity, deciding at each position:

| First word | `APP_ALLOW_RAW_IMAGE` | Verdict | Entry |
|---|---|---|---|
| `SVCA` | — | headed image → verify compat signature and CRC | `base + 256 + entry_offset` |
| not `SVCA`, not erased | 1 and hits the dev-slot table | **development bare image** | `base` (ARM Thumb bit set) |
| not `SVCA`, not erased | 0 or misses the slot table | invalid | — |
| `0xFFFFFFFF` / `0x00000000` | — | empty | — |

- Content present but identification failed → slot marked `INVALID` (**never started by mistake**),
  distinguished from `EMPTY`
- A bare image's slot state is `RAW` (value 5); **it takes no part in compaction or reclaim** and
  cannot be uninstalled

**The claim order must not be reversed**: scan headed images first, claim dev slots second. The
installer also allocates from the pool base upward, so an "installed headed image" can perfectly
well land inside a dev slot; claiming first would treat its 256-byte header as part of a bare image,
the slot table would never see it again, and it would never autostart.

## 7. Fault handling: crash restart and disabling

### 7.1 Policy

```
app/driver task HardFault
   → that slot's crash counter +1
      ├─ below the limit (APP_CRASH_RESTART_MAX, default 3) → rebuild the frame, reschedule
      └─ at the limit                                       → disable: set INVALID, leave the scheduler
```

- the counter **accumulates per slot** and is not cleared by a restart; **reinstalling the image
  clears it**
- the limit may also come from the on-device config record's `fault_restart_max`
- kernel tasks (belonging to no slot) are unaffected

### 7.2 How to observe

```c
uint32 st  = arkrtos_app_status(0);      /* 3(INVALID) and previously RUNNING → most likely disabled */
int32  cnt = arkrtos_fault_record_count();
uint32 rec[3];
for (int32 i = 0; i < cnt; i++) {
    arkrtos_fault_record_read(i, rec);
    /* rec[0]=type  rec[1]=task id  rec[2]=tick */
}
```

Serial console: `fault` shows fault records, `app list` shows slot states and crash counters.

Fault types:

| Value | Meaning |
|---|---|
| 1 | HardFault |
| 2 | task stack overflow |
| 3 | task killed |
| 4 | task fault recovery (restarted once) |
| 5 | blocking API called while the scheduler is locked (programming error) |
| 6 | app disabled after reaching the consecutive-fault limit |

### 7.3 How to recover from being disabled

Reinstall the image (send again via path B, or rewrite via path A/C) — a successful install clears
the counter.

Slot reuse rules: empty / disabled (INVALID) / stopped (LOADED) can all be overwritten directly;

- **`install <slot>` erases that slot (the whole sector) before printing the ready line**, and only
  then should the host start sending. Overwrite install works precisely because of this step; a
  fixed slot's base/size are whole multiples of 128 KB, so the erase touches only it. The order
  cannot be reversed: while a 128 KB sector is being erased the CPU is stopped, interrupts cannot
  fire, and the serial receive FIFO cannot move bytes either (the hardware DR holds 1 byte), so if
  you erase only after the host has started sending header/table, those dozen bytes are lost in
  hardware — the install then reports `err -4` halfway, **with no `LOADER` line at all** — and only
  reading the flash back shows it.
- **With `SHELL_ENABLE=0` the destination comes from config**: with no command line there is no
  "erase then announce" moment, so `INSTALLER_FIXED_SLOT` (config slot index, default `-1`) tells
  the resident install task the target. Set to N, it prepares after power-up and before opening the
  window: if an image is running in that slot it stops it first (`arkrtos_loader_stop()`, equivalent
  to `app stop <slot>` in the console; otherwise the erase would wipe code being fetched), then
  erases the whole slot and prints `fixed slot N cleared, send the file now`; one power cycle
  accepts exactly one frame, the second is refused with `one image already installed this boot:
  reboot before sending another one`, so another install needs a reboot. Left at `-1`, the resident
  task refuses every frame in fixed mode instead of guessing a slot to erase.

Only "RUNNING" is not acceptable — `app stop 0` first, otherwise install is refused (`ERR_BUSY`).
The full single-slot in-place update of an app is: `stop 0` → install → `start 0`.

### 7.4 Known boundary

The counter lives in **shared RAM** and is cleared by power loss. Therefore:

- it stops the "app crashes repeatedly → restart → crash again" loop
- it does **not** stop the "crash causes a whole-device reset" boot loop (power-up → autostart →
  crash → reset → …)

Closing the boot loop needs the counter persisted. On the chip, the cheapest option is **RTC backup
registers** (STM32F427 has 20×4 bytes, retained across reset and power loss, no flash wear) — a
board-level TODO.

## 9. Troubleshooting table

| Symptom | Likely cause | Action |
|---|---|---|
| app downloaded but does not run | `APP_ALLOW_RAW_IMAGE = 0`, or the runtime `RAW_ALLOW` bit is off | turn both on during development |
| app does not run, `app list` state is 3 | content identification failed (bad format or CRC) | repack/download; check with `pack_app.py --verify` |
| `ram` column shows `0x00000000` | the bare image's RAM window was not bound (kernel bug or slot table miss) | check the dev slot table's `UNIT`/`TYPE` against the `.sct` addresses |
| pool looks empty (`app list` no output) | wrong download address, nothing written to a slot | check the `.sct` and the flash address (§1.2) |
| link error: RW region does not fit | `.data+.bss` exceeds window minus stack | trim static variables, or enlarge `ARKRTOS_DEV_RAM_WINDOW` and regenerate `.sct` |
| downloads, starts, crashes after a while | `.sct` RAM window disagrees with the kernel's derivation | generate both sides with the same `tools/gen_scatter.py`; never hand-edit `.sct` |
| build fails saying `gen_scatter.py` not found | `python` is not on PATH inside Keil's Before Build | add Python to PATH, or generate `.sct` beforehand |
| serial install does nothing | `install` not typed first; serial port held by a debug session; text-mode send | type `install`, release the port, send binary |
| install immediately reverts to INVALID | transfer dropped bytes so CRC fails | lower the baud rate or add flow control, resend |
| `cfg show` says `record : none` | no valid record in the config area (normal fallback) | to pin a layout, write with `tools/arkrtos_cfg.py write` or `tools/arkrtos_host_gui.py` |
| `cfg load` reports `bad magic` although the record checks out on the host | the stream was shifted: the command line used CRLF and the stray LF took byte 1 of the record | use `tools/arkrtos_cfg.py` (CR-terminated); do not hand-write a sender; see 配置区与安装策略.md §6.3 |
| `cfg load` reports `bad crc` / `bad hw` / another reason | the record really is bad (content modified, chip signature mismatch) | the cause line comes from the device; fix the record accordingly; a bad record does not affect the existing config |
| `cfg show` says `fixed` but `pool` lists no fixed slots and installs land wrong | layout field of the shared partition table overwritten (historical defect `7459e1d`, fixed) | reboot and recheck; if it recurs, compare `layout_mode` at `0x20000000+52` with `cfg show` |
| writing config then installing immediately lands somewhere unexpected | the layout strategy only fully takes effect after a **reboot** (pool scan and boot already happened early) | reboot as the device asks, then install |
| changing `CHIP_FLASH_SIZE` changes every address | by design (addresses are defined once) | rebuild the kernel and every image; no other file needs editing |
| half lines or garbled characters on serial output | fixed: the console has a line-level lock and one whole-string SVC (commit `01b9728`) | if it still happens, check the `lock_giveup` / `tx_drop` counters of the `log` command before blaming concurrency |

### Not yet supported (by priority)

1. ~~console line-level mutual exclusion~~ — **done** (commit `01b9728`): the console has a
   line-level lock, `app_puts` became one whole-string SVC, and `lock_giveup` / `tx_drop` counters
   were added (visible via the `log` command). Long real-machine runs (hundreds of KB of output)
   show `tx_drop = 0`.
2. ~~image signature verification~~ — **implemented, default off**: with
   `ARKRTOS_USE_IMAGE_SIGN=1` the install path recomputes `signature[64]` as HMAC-SHA256 and
   compares it with the header, refusing on mismatch; the pack side uses
   `tools/pack_app.py --sign-key`. This is a **symmetric** scheme (whoever can read the key in the
   device can sign), not the full "device holds only the public key" trust chain — that one is still
   missing, see `kernelsrc/include/arkrtos_sign.h`. Verified on the board (§11.4): a signed image
   installs; a tampered image with one payload byte changed and the CRC recomputed to match is
   refused (`err -18`). Verification runs on the **streamed nominal** bytes as they arrive on the
   wire — the on-flash form is relocation-patched, so the signature does not cover it.
3. ~~crash counter persistence~~ — **implemented**: the cross-reset counter lives in a UNINIT diary
   at the tail of shared RAM and closes the "crash → reset → crash again" boot loop (see
   崩溃恢复与镜像版本把关.md §1). Still not done is surviving **power loss** — UNINIT clears on
   power loss, which would need RTC backup registers or flash.
4. **slot metadata persistence** — version numbers and upgrade/rollback cannot currently survive power loss.
5. **A-B rollback** — the pool supports multiple slots, but there is no upgrade/rollback policy yet.
6. ~~multi-slot on the image side~~ — **done**: relocation is a linear increment
   (`landing + payload_offset - nominal_base`), and the header's `nominal_base` is merely "where
   that pass linked", not a criterion for the kernel, so the same image works in any slot. Real
   board evidence in §11.4: `install 2` lands at `0x080A0000`, `install 0` at `0x08060000`, both
   `RUNNING`.
7. **SVC boundary zero trust** — user pointers are refused if they point into kernel RAM/flash, but
   handles are still bare indices.

## 11. Scripting and automated debugging

This project's operating surface is **deterministic and scriptable**: sources, config source of
truth, host tools and the debug channel all have stable inputs and outputs, so the same actions can
be performed by a person or driven by a script.

### 11.1 The skill inside the project

`skills/arkrtos/SKILL.md` is the operations manual for this flow, covering four things:

| Content | Purpose |
|---|---|
| project facts | addresses defined only in `config/arkrtos_partition.h`, `.sct` is a build artifact, encoding and line-ending conventions |
| command closure | exact commands and exit-code meanings for build / flash / install / start-stop / status |
| serial closure | shell command table, install protocol, the three handshakes for writing config |
| debug channel | read/write memory, variables and registers via MCP tools through `mdk_agent_mcp` ([gitee](https://gitee.com/xw19981010/mdk_agent_mcp.git)) instead of manual breakpoints |

The GUI `tools/arkrtos_host_gui.py` is for manual work; automation uses the command-line scripts
under `tools/` (same protocol, parseable output).

### 11.2 Why this project suits automation

- **one address source**: change `CHIP_FLASH_SIZE` and partitions, pool, `.sct` and every slot are
  all recomputed; callers need not keep numbers in sync across files;
- **tools do not guess causes**: when the device refuses a config record it prints the real cause
  line on serial and the host forwards it verbatim (§6.3 / §9) — the caller gets the device's words,
  not the tool's guess;
- **state is directly readable**: the authoritative copy of the layout is in the shared partition
  table, `layout_mode` at `0x20000000 + 52` (F427, u32 little-endian), readable with a debugger
  without depending on any command's output format;
- **conventions for failure**: 0 errors / 1 warning on compile (inherited `arkrtos_context.S
  A1581W`); `UV4 -r` returning 1 means only "there were warnings" but **stops a chained `-f` behind
  `&&` from running**.

### 11.3 Hand-over checklist

After changing anything layout-related, verify in this order before handing over:

1. build the kernel for both boards once (`-r`, F427 + F401);
2. flash F427 (`-f`, called separately, not chained with `-r` behind one `&&`);
3. `app list` to confirm a single instance is running (two APP_DEMO autostarting at once interleave
   output byte for byte and the later registrant reports `shell.register ... FAIL (-2)`);
   **stopping and restarting the same instance also hits this name**: in the 2026-09-20 re-test slot
   0 had already been stopped to `LOADED` (`task` column 0) with only slot 2 running on the board,
   and restarting it still reported the same `-2`. In other words the occupancy comes not only from
   another instance but also from the registration left by this instance's previous run — after
   `app stop` the user commands are not reclaimed. This is an **observed fact**; the reclaim timing
   was not investigated further, so a clean self-test result requires the kernel to rebuild the
   command table (reset) or the leftover instance to be uninstalled;
4. config changes go `arkrtos_cfg.py write` → read back with `cfg show` → **reboot** → `cfg show`
   again (policy fields do not take effect before the reboot);
5. installs go through `send_image.py` or the GUI, reading the device-side `INSTALL` log rather than
   the host-side "sent successfully".

### 11.4 Real-machine verification record (F427, 2026-09-19)

Run item by item on the board through `tools/arkrtos_host_gui.py`'s own code path (UI hidden,
`messagebox` stubbed); conclusions are tiered as "compile only / verified on board / unverified":

| Item | Conclusion | Evidence |
|---|---|---|
| fixed-slot config written, rebooted, read back | verified on board | `cfg show` shows `layout : fixed` and `pool` lists 3 fixed slots (`0x08060000` / `0x08080000` / `0x080A0000`, 128K each) |
| landing point of a fixed-slot install | verified on board | `install 2` → device answers `install: fixed slot 2 -> 0x080A0000`; `app` shows the new instance with `base 0x080A0000`, `ram 0x20014000`, `size 131072` |
| incompatible image refused immediately | verified on board | device answers `[E][INSTALL:150] rejected: err -3` and the host finishes in **0.7 s** (before the fix it waited the full 5 s ACK timeout) |
| image signature check (`ARKRTOS_USE_IMAGE_SIGN=1`) | verified on board | signed image `install ok` (`[I][INSTALL:286] slot 0 committed`); a tampered image with one payload byte changed and the CRC recomputed, leaving only the signature stale, is refused: `[E][LOADER] signature mismatch: image rejected` → `rejected: err -18` |
| device returns to a clean prompt after a failed install | verified on board | before returning, the installer drains the rest of the frame's relocation table by `reloc_count` (device log `[I][INSTALL] drained N B of the rejected frame (table M B)`). Measured: installing an image with a broken `hw_compat_id` gives `rejected: err -3`, and the screen shows only `install: failed or timed out` plus a clean prompt, with no more `Command not found` |
| app-side FPU (unprivileged VFP + context switching) | verified on board | `APP_DEMO`'s self-test adds an 8c section, all seven items pass: `fpu.usr_vfp_math` / `fpu.s16_hold` / `fpu.thread_create` / `fpu.s16_ctx_main` / `fpu.s16_ctx_worker` / `fpu.float_vs_double`. The criterion is "values written into S16-S19 read back equal after one task switch", with two execution flows using different seeds interleaved over 20 rounds without cross-contamination. The `shell.register ... FAIL (-2)` in the same round is the known occupancy issue of §11.3, unrelated to FPU |
| restore flow after uninstall and config erase | partially verified | the step that caused trouble is fixed: the GUI split "config slot index" and "partition table slot number" into two labelled inputs (see below), so the wrong index cannot be picked; the complete `app uninstall` + `cfg clear` restore flow **has not been re-run** |

Three usage conventions:

- **In fixed-slot mode two numbering schemes coexist, and commands take the partition-table slot
  number.** The config slot index (0, 1, 2 as seen in `arkrtos_layout.py` / the GUI layout page) is
  only "which fixed slot"; after it lands, the kernel assigns each image a **partition table slot
  number**, and `install: ok, slot N`, the `id` column of `app` / `drv` listings, and the arguments
  of `app uninstall <n>` / `app start <n>` all use the latter. In the example above the image went
  into config slot 2 but its partition slot number is 1: `pool`'s `fixed slots` section shows config
  slot 2 as `RUNNING` while the `app` listing shows `id 1`. **To confirm the landing point look at
  `base`, do not cross-reference the two schemes.**
- **A frame rejected at the "header" stage has its remaining relocation table drained by the
  installer.** So the device can verify the relocation table, header and table must arrive
  back-to-back; the compatibility decision, however, looks only at the 256 B header and NAKs early
  while that table is already in flight. Before returning, the installer reads it out by
  `reloc_count` and hands control back to the shell, so the console does not print an extra
  `Command not found`.
