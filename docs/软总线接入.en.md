# Softbus Integration (ark_softbus → kernel + shell `bus` command)

> Condensed English edition. The Chinese page (软总线接入.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

## 0. One line

The cross-device event / remote-call / data-plane bus `ark_softbus` is synced in as a component under `kernelsrc/components/ark_softbus`, gated by `ARKRTOS_USE_SOFTBUS` (default **0**). The board side supplies only three hooks (millisecond clock + critical-section enter/exit). The console drives it with the `bus` command.

## 1. Verdict tiers (read these first)

| Item | Status | Evidence |
|---|---|---|
| Build | **compiles** | `tools/ci_gate.py --build` 11/11: F427 0 Error / F401 0 Error |
| Two nodes inside the board, end to end (codec, discovery, pub/sub, directed+ACK, QoS retransmit timeout, RPC, data-plane chunking, error paths, topic table) | **verified on hardware** | `bus selftest` on F427, per-item PASS/FAIL plus `checks N, failed 0` (§6) |
| Two nodes over a physical serial line (two boards, or board + PC `bus_bridge`) | **not verified** | the board has only USART1 and the kernel console owns it; no free UART. Wiring in §8 |
| `src/transport/transport_sock.c` (POSIX socket transport) | **not compiled** | the kernel project does not add it to the source list (needs POSIX sockets) |

`bus selftest` exercises the **real** frame codec, ring buffers, transmit/receive, and the QoS/RPC/stream state machines; time and critical sections come from the real kernel tick and scheduler lock. It is not an emulator, but it is also not a physical serial line — hence the two separate rows above.

## 2. Why an in-board loopback of two nodes

This F427 board (STM32F427VGTx) has **only one USART1** (PA9/PA10 → DAPLink VCP = COM3), and the kernel shell owns it. A physical two-node link cannot be built on this board.

Instead of recording "can the bus run" as "not verified", two real `ark_bus_t` instances in the same firmware (local node `0x1001`, resident peer `0x1002`) are wired back to back through the component's own loopback transport (`ark_bus_loopback_init/a/b`, two 1 KB ring buffers).

Code it really reaches: frame encode/decode, CRC, byte-wise reassembly, QoS session table and retransmit, RPC slots, stream chunking and reassembly, device table and discovery; the clock hook calls the kernel tick every round and the critical-section hook really enters/leaves the scheduler lock. Code it does **not** reach: the UART transport byte path (`transport_uart.c`) and on-wire noise/timing — that layer is honestly recorded as "not verified".

## 4. Build integration (F427 kernel project)

`example/stm32f427/kernel/ARKRTOS_TEST/MDK-ARM/ARKRTOS_TEST.uvprojx`:

* new group **`ARKRTOS/Softbus`**, 18 source files:
  * integration layer `kernelsrc/src/arkrtos_softbus.c`;
  * board layer `board/stm32f427/arkrtos_bus_port.c`;
  * 13 component `src/*.c` + `src/transport/transport_loopback.c` + `src/transport/transport_uart.c`;
  * port `port/ark_bus_hal_arkrtos.c`.
  (`transport_sock.c` needs POSIX sockets and is not in the source list.)
* include path adds `kernelsrc\components\ark_softbus\{include,src,port}`.
* `Define` adds `ARKRTOS_USE_SOFTBUS=1`; in `arkrtos_features.h` it defaults to **0**, and removing the macro compiles nothing of it (zero size and zero behavior change).
* `MiscControls` adds the MCU profile `-DARK_BUS_*` (below).

### MCU profile (must come paired with the switch)

Default profile (32 topics / 256 B payload / all layers on) costs ~6 KB per instance; a 128 KB RAM board cannot hold two. The project supplies:

```
-DARK_BUS_MAX_TOPICS=12 -DARK_BUS_MAX_DEVICES=4
-DARK_BUS_MSG_MAX_SIZE=128 -DARK_BUS_TOPIC_NAME_MAX=24
-DARK_BUS_QOS_MAX_SESSIONS=2
-DARK_BUS_RPC_MAX_SLOTS=4 -DARK_BUS_RPC_MAX_METHODS=4
-DARK_BUS_TASK_ENABLED=0 -DARK_BUS_COLL_ENABLED=0 -DARK_BUS_INFER_ENABLED=0
-DARK_BUS_STREAM_TX_SLOTS=1 -DARK_BUS_STREAM_RX_SLOTS=1
-DARK_BUS_STREAM_RX_MAX=256 -DARK_BUS_STREAM_MAX_BYTES=256
```

The top of `arkrtos_softbus.h` holds an `#error` gate: a profile that disagrees with the conventions **fails at compile time** rather than silently taking several extra KB of RAM (self-tests all green but RAM short on the board is the hardest class to debug).

Profile trade-off: the three upper layers task / coll / infer are off; qos (reliable delivery), rpc and stream (data plane) stay on because the selftest and the `bus rpc/stream` commands must verify them.

## 5. The board's three hooks

`ark_softbus` deliberately has a three-function port surface (`port/ark_bus_port_arkrtos.h`):

| Hook | Implementation on this board | Note |
|---|---|---|
| `ark_bus_port_tick_ms()` | `arkrtos_kernel_get_tick() / (1000/ARKRTOS_TICK_PERIOD_US)` | tick period default 500 us (2000 Hz), 2 ticks per millisecond |
| `ark_bus_port_lock()` | `arkrtos_sched_lock_internal()` | scheduler lock (does not disable interrupts, nestable) |
| `ark_bus_port_unlock()` | `arkrtos_sched_unlock_internal()` | paired release |

Two conventions:

1. **The clock divides instead of multiplying.** Bus QoS retransmit (200 ms) and heartbeat (3 s) are in milliseconds while the kernel tick is 500 us; `ticks × 500 / 1000` would wrap in about 71 minutes at 32 bits. Using `ticks / ticks_per_ms`, and requiring `ARKRTOS_TICK_PERIOD_US` to divide 1000 us evenly (otherwise `#error`), pushes the wrap period to the same order as 32-bit milliseconds.
2. **Critical sections use the scheduler lock, not interrupt masking.** Bus lock windows all sit on table insert/remove/update (a few dozen instructions), the scheduler lock suffices, and it allows nesting (the bus may publish from its own callback).

## 6. RAM budget (measured, not estimated)

Read symbol by symbol from `ARKRTOS_TEST.map` (`arkrtos_softbus.o(.bss)` total **5616 B**):

| Symbol | Size | Purpose |
|---|---|---|
| `g_node` | 1460 B | local node `ark_bus_t` |
| `g_peer` | 1460 B | resident peer `ark_bus_t` |
| `g_lb_store` | 2048 B | loopback's two 1 KB rings |
| `g_lb` | 72 B | loopback endpoint/adapter |
| `obj` (`bus stream` static buffer) | 256 B | data-plane transmit buffer |
| `big` (selftest error path) | 136 B | oversized-payload case |
| `g_peer_last_payload` and misc | ~180 B | peer observation window |

`KERNEL_RAM` is about 56 KB, so 5.6 KB is about 10% — acceptable. To save more, shrink the profile further (e.g. `-DARK_BUS_STREAM_ENABLED=0` and drop selftest stage 7), at the cost of losing data-plane verification.

## 7. Usage: the console `bus` command

The command is registered in the kernel shell (`kernelsrc/shell/arkrtos_shell.c`, `register_kernel_commands()`); the first call lazily initializes (installs HAL, builds both nodes, broadcasts DISCOVER).

```
bus                       # same as bus info
bus info                  # node identity / profile / peer / tx-rx counters
bus selftest              # 10-stage end-to-end selftest, per-item PASS/FAIL
bus pump [n]              # manually advance n event-loop rounds
bus peers                 # device table
bus rx                    # last content the peer received
bus pub <topic> <text>    # broadcast (peer subscribes to that topic dynamically, then should receive it)
bus rpc <text>            # send ARK_BUS_M_PING to the peer (reply echoes bytes +1)
bus stream <n>            # send an n-byte object (default 200; >128 necessarily chunks)
```

The 10 selftest stages: `codec` (CRC vector 0x29B1 / big-endian topic id / bad CRC / bad magic / truncation), `reader` (cut a complete frame out of leading noise), `discovery` (DISCOVER registers both directions), `pubsub` (publish/subscribe + counting `dispatch_errors` when there is no subscriber), `directed+ack` (directed + no retransmit after QoS1 ACK), `rpc` (request/reply + slot release + async semantics), `stream` (200 B > one frame, chunked reassembly), `qos-timeout` (target absent → exactly one timeout after N retransmits), `errors` (oversized payload `E_INVAL`, self-originated frame not looped, bad-CRC counting), `topics` (register / duplicate check / `E_FULL` when the table is full).

## 8. Not covered / not verified

* **Two nodes over a physical serial line**: recorded as **not verified**. The board has no free UART. Verifying needs an adapter board (second UART) or a second board; wiring in §9.
* **`transport_sock.c`**: synced in but not compiled (needs POSIX sockets); only the host side uses it.
* **Peer subscription for `bus pub`**: the peer subscribes on demand — `bus pub` first makes the peer subscribe to that topic, then publishes (the component has no wildcard subscription). This only affects this interactive command, not publish/subscribe semantics themselves.

## 9. Next: attach a physical link

The component already ships a UART transport (`src/transport/transport_uart.c`). On-board wiring:

1. find a free UART (this board needs a different board or an adapter), and in board init call `ark_bus_transport_uart_init(&u, &tp, io, write_fn)`;
2. in the RX interrupt call `ark_bus_transport_uart_feed_byte()`; the rest happens in a task via `ark_bus_poll()`;
3. switch `g_node`'s transport from loopback to this UART adapter (one line in `sb_build()` of the integration layer);
4. on the other side use `ark_softbus/tools/bus_bridge` on a PC (serial ↔ TCP) to talk to a PC process.

All the code for this path is already in the tree; only the hardware UART is missing.
