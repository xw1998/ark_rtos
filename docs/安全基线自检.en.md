# Security Baseline Self-Check (the `sec` command)

> Condensed English edition. The Chinese page (安全基线自检.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

## 1. What this document answers

* With **this build** on this board, which mechanisms the security baseline expects are really present, and which are not?
* Why do some items report `SKIP` rather than `PASS`?
* Where is the line between `FINDING` and `FAIL`, and who may use it as evidence — and as what may it not be used?

Companion documents: 安全认证准备.md (assets, threat model, standards gap table), 内存保护与App越权验证.md §5 (known boundaries).

In one line: **`sec` is a self-check for "is this build still the one you think it is", not a compliance statement and not a penetration test.**

## 2. Four verdict tiers

| Tier | Meaning | Who may use it |
|---|---|---|
| `PASS` | the baseline requires it and measurement agrees | usable as evidence that "this item holds in this build" |
| `FAIL` | the baseline requires it and measurement disagrees | hard failure: the configuration is not what you think — fix it first |
| `FIND` | known gap: the feature was not built or not compiled in | the device is not broken, but the certification list must record the gap; **not counted as PASS** |
| `SKIP` | this build has no path to establish it | the reason must be printed (the format string is the reason) |

Why `FINDING` and `SKIP` must stay separate: the first is "we really did not do this", the second is "we have no path to see whether it was done". Merging them produces conclusions like "all 12 passed" that hide gaps inside the total.

Why there is no `WARN`: a self-check has no "suggestions". Either the baseline requires it (PASS/FAIL), or it is a recorded gap (FIND), or it cannot be seen (SKIP).

## 3. The twelve checks

Order is output order; names are stable and machine-readable.

| # | Name | Asks | Verdict |
|---|---|---|---|
| 1 | `gates.kernel` | are all six compiled in: **address-isolation backend** / privilege stripping / stack check / fault recovery / crash ledger / structural audit | all six bits present → PASS; any missing → FAIL. Signature and will are reported as separate values (`sign/hwsafe=0xN`) and not scored twice. The source of the isolation bit is in "bit0 and `iso`" below |
| 2 | `mpu.slot_windows` | does every non-empty slot have a RAM window | a slot without a window → FAIL (no window = the word "isolation" is idling) |
| 3 | `structures.audit` | are partition table / slots / task table / scheduler chain self-consistent | mask 0 from `arkrtos_audit_run()` → PASS; otherwise FAIL with the first out-of-range index |
| 4 | `images.headers` | does every image header in the pool still hold | magic + `arkrtos_loader_check_header()` (fields, relocation-table encoding, entry alignment and ordering) all pass → PASS; otherwise FAIL with the first bad slot and the error code |
| 5 | `images.crc_recheck` | re-check image CRC at boot | **always SKIP**: what lies in Flash is relocated bytes, but the header's `crc32` covers the nominal form, so a hard check would fail falsely |
| 6 | `images.signature` | is image signing enforced | `ARKRTOS_USE_IMAGE_SIGN==1` → PASS; otherwise FIND (anyone with serial access can install their own code) |
| 7 | `hwsafe.deadman` | after a crash or kill, does anyone bring the device back to a safe state | `ARKRTOS_HW_SAFE==1` → PASS and report `devs/owners/will/cb`; otherwise FIND |
| 8 | `guard.watchdog` | is the watchdog really biting | guard + `ARKRTOS_WDG_ENABLE` both present → PASS; guard only → FIND ("a hung task will not be reset") |
| 9 | `crash.journal` | is the cross-reset crash history still there | `boots!=0` → PASS and report `boots/seq/held_slots`; `boots==0` (magic/checksum failed, reopened) → **FAIL** |
| 10 | `console.auth` | does the console have authentication | constantly FIND: serial reachability means `install` / `reboot` / `stop` |
| 11 | `flash.protection` | Flash read/write protection level | if the board implements `arkrtos_port_flash_protection()`, read the true values: `rdp_level==0` → FIND (readable equals no read protection), `rdp_level>=1` → PASS and report the two WRP masks (bit=1 means that sector is protected); **a board without this hook is still SKIP**, worded byte-identically to before |
| 12 | `rt.measured` | are there measured real-time readings | counter alive and `rt` has samples → PASS and report `tick.isr max` and cycles per tick; not compiled or counter not running → SKIP |

The return value of `arkrtos_sec_run()` is **the number of FAILs** (0 = no hard failure); `FINDING` is not counted.

### bit0 and `iso`: the isolation bit does not require "an ARM MPU"

bit0 asks "is there an implementation managing address isolation", not "must there be an MPU block". Either path counts, and which one is reported:

| `iso` | Meaning | Source |
|---|---|---|
| `0` | **no isolation backend at all** | bit0 of `bits` is also 0 → `gates.kernel` FAIL |
| `1` | window backend (ARM MPU / RISC-V PMP) | `ARKRTOS_USE_MPU == 1` |
| `2` | page-table backend (TLB mapping + PLV/U privilege level) | `ARKRTOS_USE_PAGING == 1` |

The criterion **reads only "which backend this build uses"**, never `ARKRTOS_ARCH_HAS_PAGING_HW` — the latter is a hardware fact about "does this core have a TLB/page table". RV64GC's hardware bit is 1, but this repo has no RV64 port and no page-table init, so judging by the hardware bit would make a build with paging completely off report `iso=2`, which is a false green. The division of labour between the two symbols is in 内存保护与App越权验证.md §7.3.

Why not use MPU as the sole criterion: LoongArch has no MPU block; isolation comes from paging + PLV3 (see `la_mmu_init` in the LA64 port). Requiring an MPU would require a part that does not exist on that chip — then this bit would be permanently FAIL, and a FAIL that keeps appearing gets filed as "legacy" and left hanging, which is less honest than a wrong reading.

## 4. Measured on F427 (2026-11-12)

Build: `Code=220094 RO=19198 RW=896 ZI=120852` (rebuilt on 2026-11-13 after the option-byte path was added; the earlier `Code=219426` build read `finding 2, skip 2`), 96 MHz / 2 kHz tick, `ARKRTOS_USE_SECCHECK=1`. Verbatim serial output of `sec`:

```
sec: 12 checks - pass 8, fail 0, finding 3, skip 1
  [PASS] gates.kernel       mpu/priv/stk/fault/crash/audit bits=0xBF (need 0x3F), sign/hwsafe=0x2
  [PASS] mpu.slot_windows   slots=2 without_window=0 first=0
  [PASS] structures.audit   checks=32 mask=0x0 first_index=0
  [PASS] images.headers     slots=2 bad=0 first=0 err=0
  [SKIP] images.crc_recheck flash holds relocated bytes; header crc32 covers the nominal form
  [FIND] images.signature   not compiled (ARKRTOS_USE_IMAGE_SIGN=0): unsigned images are accepted
  [PASS] hwsafe.deadman     devs=3 owners=3 will/cb=0/0
  [PASS] guard.watchdog     kernel guard + board watchdog both active
  [PASS] crash.journal      boots=2 seq=7 held_slots=1
  [FIND] console.auth       shell has no authentication: serial access = install/reboot/stop
  [FIND] flash.protection   rdp=0 (0=none), wrp lo=0x0000 hi=0x0000, bit=protected
  [PASS] rt.measured        tick.isr max=76 us over 25591 samples, 48000 cyc/tick
verdict: no hard failure (FINDING = known gap, SKIP = no path to see it)
```

How to read it:

* `bits=0xBF`: all six bits of `0x3F` are present plus bit7 (`HW_SAFE`); `sign/hwsafe=0x2` says the signature bit (bit6) is 0 and the will bit is set — consistent with the build options, not guessed. **Note this log was captured on 2026-11-12 in the old format** (the format string had no `iso` field then); a rerun with the current version prints `iso(1=mpu 2=page)` before `bits` and `, iso=N` after. The same F427 build should read `iso=1`; on LA64 QEMU it is `iso=2`. Both values are measured in 内存保护与App越权验证.md §7.5. Do not check the `iso` field against this old log — it was not in the string then, which is not the same as being empty.
* `held_slots=1`: `HWSAFE_DEMO` crashed up to its limit last time and was disabled; the ledger survived the reset (this is exactly the defect fixed by `90f8d2d`, and `sec` now recites it at every boot).
* `hwsafe ... will/cb=0/0`: no App has died since this boot, so both channels' cumulative counters are 0; it is a "since this boot" reading, not a historical total.
* `rt.measured`'s `76 us` comes from the same source as `rt show`'s `tick.isr MAX`: the first `sec` run had only 7999 samples (max 29 µs then), later runs reached 76 µs, and running `sec` again recites 76 µs. The two readings agree ⇒ the line is not a separate computation.
* `first_index=0`: when `mask==0` the index is meaningless, so it prints 0 explicitly rather than `4294967295`.
* The `flash.protection` reading was cross-checked with the debugger: after halting the target, `FLASH->OPTCR=0x0FFFAAED` read directly (bit1 RDP bit is 1 ⇒ level 0, no read protection), `OPTCR1=0x0FFF0000` (nWRP all 1 ⇒ no write protection), matching the kernel's `rdp=0 / wrp lo=0x0000 hi=0x0000`. Note this cross-check **must halt**: with the target running, `read32` on peripherals returns the constant fake value `0x03000000`, while halting resets the target — both traps are written up in 小程序设计.md §9.6.

## 5. How to use it

```
sec                 # all 12 items
sec pass|fail       # only one tier (find / finding are synonyms)
sec skip            # only the "cannot see it" items and their reasons
```

* Read-only: it changes no structure, installs no policy, does not "fix things along the way". Fixing would destroy the evidence for the next self-check.
* The report struct `arkrtos_sec_report_t` is `static` in the shell, **never on the stack** (kernel task stacks are tight).
* There is no second `snprintf` in the kernel: each item supplies a format string plus at most 4 integers, and the shell formats them.

## 6. Three boundaries (do not read `sec` past them)

1. **`sec` does not test attacks, only whether the mechanisms are present.** Interception must be attacked by Apps (`APP_DEMO`'s 78 self-checks, `APP_BAD`'s deliberate violation, `HWSAFE_DEMO`'s crash channel); the trailing `note:` line says exactly this.
2. **`FINDING` is not "a minor issue".** `console.auth` and `images.signature` are hard gaps on the certification list; they are only in their own tier because the device is not broken.
3. **`SKIP` does not mean acceptable.** `images.crc_recheck` and (on boards without the hook) `flash.protection` both state clearly "why it cannot be seen". Turning them into PASS requires building the path first (reverse relocation / option-byte read), which is code work, not a criterion change.

## 7. Switch and size

| Item | Value |
|---|---|
| switch | `ARKRTOS_USE_SECCHECK` (default 0), with `depends on ARKRTOS_USE_SHELL` in `config/kconfig/Kconfig.features` (the `sec` command hangs off the shell command table) |
| when off by default | the whole body of `arkrtos_sec.c` sits inside `#if`, and neither the shell command table nor the `need` budget changes: **zero change in size and behaviour** |
| F427 with it on | `Code 217370 → 219426` (**+2056 B**) → `220094` (option-byte path adds **+668 B** more), RO/RW/ZI unchanged |
| command-table budget | `need` in `register_kernel_commands()` goes up by 1, still far below `ARK_SHELL_MAX_COMMANDS=56` |
