# Releases and Version Policy

> Condensed English edition. The Chinese page (发行版与版本策略.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

In one line: **a "release" of this repository = one git tag plus one `docs/Release-<tag>.md`.** The three numbers of the version live once, in `kernelsrc/include/arkrtos_version.h`; the tag name and the badges in both READMEs must agree with them, and the gate (`release-consistency` in `ci_gate`) blocks any disagreement.

Why this page exists: the item "release definition (artefact list / change control / LTS)" in 欠账盘点.md stayed undone for a long time, with the result that the readme said "the version is recorded only as a git tag" while the repository had **no tag at all** — that sentence was an empty promise at the time. The rules, the artefact list, the ABI bump criteria and the complete set of actions for one release are now pinned down here, and the gate watches whatever can be checked automatically.

## 1. Version numbering

| Field | Meaning | When it moves |
|---|---|---|
| `MAJOR` | the stability surface promised to outsiders | only at 1.0; stays 0 throughout 0.x |
| `MINOR` | capability and ABI | new capability, or a change to the ABI surface (SVC numbers added/removed, image header / shared partition-table structure changed, `ARKRTOS_HW_COMPAT_ID` compatibility generation changed) |
| `PATCH` | fixes | fixes only: caller binaries, return-value semantics and memory layout all unchanged |

**`-preview.N` appears only on the tag, never in `arkrtos_version.h`.** The three numbers are packed into the numeric `ARKRTOS_VERSION_NUM` and `ARKRTOS_VERSION_STRING` is derived from them; carrying a suffix would make the string printed by the `version` command disagree with the numeric version in the firmware. Preview semantics are carried by the tag name and the release notes, not by a firmware macro.

Tag naming: `v<MAJOR>.<MINOR>.<PATCH>[-preview.N]`, e.g. `v0.0.3-preview.1`. **A tag is published once**: never moved, deleted or reused (to change something, publish the next number).

## 2. Three places must agree, a fourth must exist

| Location | What is written | Who watches |
|---|---|---|
| `kernelsrc/include/arkrtos_version.h` | the three numbers `MAJOR` / `MINOR` / `PATCH` | single source of truth |
| git tag | `v<ver>`, all lowercase | step 6 of the release actions |
| `readme.md` / `readme_en.md` badges | `badge/release-<ver>-<color>.svg` (`-` written as `--` in shields) | `release-consistency` |
| `docs/Release-<tag>.md` | this version's release notes, **must contain an "unverified" section**. A stable tag is `v<ver>` and the file is `Release-<ver>.md`; a preview is named after its tag, e.g. `Release-0.0.3-preview.1.md` | `release-consistency` |

How the gate runs:

```bash
env -u PYTHONHOME -u PYTHONPATH py -3 tools/release_check.py   # on its own
env -u PYTHONHOME -u PYTHONPATH py -3 tools/ci_gate.py         # full set, includes release-consistency
```

It checks six things: (1) the three numbers in `version.h` parse; (2) both README badges contain `release-<MAJOR.MINOR.PATCH>`; (3) both READMEs' "current version" sections contain `**<ver>**`; (4) `docs/发行版与版本策略.md` exists; (5) release notes exist (`docs/Release-<ver>.md` or `docs/Release-<ver>-*.md`, multiple hits count as ambiguous) and contain an unverified section; (6) if the repository already has tags, **the newest tag must start with `v<ver>`** (preventing both "bumped the version and forgot the tag" and "tagged and then quietly changed the version").

## 3. What a tag must carry (artefact list)

| Item | Content | Why it is mandatory |
|---|---|---|
| source tag | the tag object on gitee, pointing at the exact commit | the premise of "the version is recorded only as a tag" |
| build reproduction | build commands for the four projects + the sizes measured this time | whoever takes the tag must be able to tell "is this the same numbers I see" |
| size ledger | Flash and RAM for default / minimal / no-Shell configurations | the first number in selection, and it is regressable |
| release notes | `docs/Release-<tag>.md` | the only outlet for changes, boundaries and upgrade notes |
| unverified items | listed explicitly, never omitted | the only difference between a preview and a stable release is this section |
| compatibility statement | `ARKRTOS_PARTITION_VERSION`, `ARKRTOS_HW_COMPAT_ID`, whether the SVC ABI changed | decides whether old images still work |

**Binary artefacts are not committed** (ELF/HEX/BIN are build products): release notes give commands and readings, not binaries. Third-party and vendored components keep their source commits in `VENDOR.md`, frozen together with the tag.

## 4. ABI and bump criteria

Three numbers each govern one thing; changing any of them requires a `MINOR` bump per §1:

| Number | Location | Current value | Governs |
|---|---|---|---|
| `ARKRTOS_PARTITION_VERSION` | `kernelsrc/include/arkrtos_share.h` | `10` | shared partition-table structure (the block App and kernel both read) |
| `ARKRTOS_HW_COMPAT_ID` | `config/arkrtos_partition.h` | `0x42700005` (low 16 bits = image compatibility generation 5) | whether an image can be installed into this board's kernel |
| SVC service / subcommand numbers | `kernelsrc/include/arkrtos_svc_abi.h` | 17 service numbers, about 105 subcommand numbers | the only ABI surface between App and kernel |

Rules:

* **A patch release must not touch the values of these three numbers**, nor reorder struct fields.
* If one changes, the release notes must say "**old images must be rebuilt / reinstalled**" and give the new compatibility generation.
* Published numbers are never reused (a deleted subcommand number is left empty, see SVC服务号与子命令表.md).

## 5. Preview versus stable

| Tier | Criteria | Status |
|---|---|---|
| **Preview** (`-preview.N`) | builds, and registered capabilities run on real hardware; **unverified items exist and are listed** | current tier |
| **Stable** (a release within 0.x) | zero unverified items, or they have been converted into "explicit trade-offs" written into 已知限制.md; four builds + full gate + board regression all green | not reached |
| **1.0** | all five items below satisfied | not reached |

1. at least one board completes **real Ethernet transmit/receive** (PHY driver + MDIO + RMII pins, with capture evidence);
2. the soft bus completes one event and one remote call over a **two-node physical link** (two boards, or board + PC);
3. **shell authentication** and an **RDP/WRP deployment path** (irreversible operations need a production-line process);
4. **remote CI** (Gitee Go or equivalent) plus **static analysis** (either cppcheck or MISRA) wired in — since 2026-11-17 `.workflow/ci.yml` + `ci_gate --remote` exist (16 checks missing a toolchain are explicitly skipped, not counted as passing), but it has **not actually run on a runner**; static analysis was wired on 2026-11-18 with `-fanalyzer` on local GCC 10 (the `analyzer` item), yet remote CI itself still has not run on a runner ⇒ this item is still not met; see 远程CI与门禁裁剪.md;

   Note: the Chinese page lists "约 105 个子命令号" here and 远程CI与门禁裁剪.md carries its own wording; both are copied as-is, this page adds nothing.

5. the kernel's 22 GBK files are transcoded, with `.clang-format` / `.editorconfig` in place.

The first three decide "can this be given to someone else to use", the last two decide "can someone else take over and modify it".

## 6. The complete set of actions for one release

```bash
# 1) edit the three numbers in version.h
# 2) write docs/Release-<tag>.md: changes / size ledger / reproduction commands / unverified / compatibility
# 3) update the badges and "current version" sections in readme.md and readme_en.md
env -u PYTHONHOME -u PYTHONPATH py -3 tools/release_check.py     # version consistency alone
env -u PYTHONHOME -u PYTHONPATH py -3 tools/ci_gate.py           # full gate
# 4) rerun the four builds and record sizes (F427/F401 Keil, F427/H743 GCC)
git add <specific files> && git commit && git push origin master
# 5) tag and push the tag (do it in one go, do not push master without the tag)
git tag -a v<ver> -m "<one-line summary>"
git push origin v<ver>
```

The order cannot be reversed: **push master first, then the tag**, otherwise the tag points at a commit that does not yet exist on the remote.

## 7. Explicitly not done

* Never move or delete a published tag. History is what others cite; changing it turns one version number into two different contents.
* Never change the ABI silently inside a preview. Bump `MINOR` and say "old images must be rebuilt" in the release notes.
* Never write "compiles only" as "verified on board". The three tiers (compiles only / verified on board / not verified) are explained in readme.md §verification status and in 已知限制.md.
* Never omit unverified items from release notes — the honesty of a preview lives entirely in that section.

## 8. How this page is maintained

* If the numbering rules or the artefact list change: edit this page and update the checks in `tools/release_check.py` together.
* On every release: add `docs/Release-<tag>.md` (old ones are neither edited nor deleted) and update the "current version" sections of docs/README.md and readme.md.
* Each time one of the five stable-release conditions in §5 is met: put the evidence into the corresponding feature document and close that row in 欠账盘点.md.
