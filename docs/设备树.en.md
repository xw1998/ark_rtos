# Device Tree

> Condensed English edition. The Chinese page (设备树.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

Ark RTOS uses one device tree to describe "what is on this board". It divides labour with the partition header:

* **Device tree** = hardware facts: which USART sits at what address, which SPI the NOR hangs off, how many LEDs the board has. Decided by chip/board, independent of firmware layout.
* **Partition header** (`config/arkrtos_partition.h`) = firmware layout: slots, pools and addresses are defined only there.

`tools/dts/dtc_lite.py` compiles the tree into a plain C flat table. At runtime a small query API reads it: no dynamic memory, no string parsing, no hardware access.

## 1. Why a subset instead of full dtc

On an MCU only one thing is needed: a driver finds a node by `compatible` and reads its register window plus a few properties. No MMU, no address translation, no interrupt-controller hierarchy. So `dtc_lite` supports only the syntax needed to express that, and **rejects anything it does not recognise** rather than silently producing an empty tree — a misspelt property name must fail immediately, not turn into "why didn't this driver bind on the board".

Source: `docs/设备树.md`

```
/dts-v1/;                        version marker (accepted, ignored)
/include/ "file"  or #include "file"   include
/ { ... };                       root node
name[@unit] { ... };             node
label: name { ... };             labelled node
&label { ... };                  overlay: merge properties into an existing node
/delete-node/ name;              delete a child node
/delete-property/ name;          delete a property
prop = "str", "str2";            string property
prop = <0x1234 5 &other>;        cell property (&ref resolves to a phandle)
prop = [00 11 22];               byte-string property
/memreserve/ ...                 accepted, ignored
```

## 2. Layout

```
dts/stm32f4.dtsi               # SoC common part: cpus, usart1-3, spi1-2, gpioa-e, iwdg
dts/stm32f427.dts              # board: model, chosen, leds, overlay enabling peripherals, NOR
dts/stm32f401.dts              # the other board
kernelsrc/include/arkrtos_dt.h # hand-written stable query API
board/<chip>/arkrtos_dt.c      # generated artefact (checked in)
tools/dts/dtc_lite.py          # DTS-subset compiler + C generator
tools/dts/test_dt.c            # host self-test (asserts what the API answers)
tools/dts/host/                # type shims for host builds
```

Every peripheral in a `dtsi` defaults to `status = "disabled"`; a board file turns it on with `&label { status = "okay"; }`. Only enabled devices are returned by `arkrtos_dt_find()`.

## 3. Query API

```c
uint32 arkrtos_dt_count(void);
const arkrtos_dt_node_t *arkrtos_dt_node(uint32 idx);
const arkrtos_dt_node_t *arkrtos_dt_find(const char *compatible);
const arkrtos_dt_node_t *arkrtos_dt_find_next(const char *compatible,
                                              const arkrtos_dt_node_t *from);
const char *arkrtos_dt_model(void);
const arkrtos_dt_prop_t *arkrtos_dt_prop(const arkrtos_dt_node_t *node, const char *name);
int32 arkrtos_dt_prop_u32(const arkrtos_dt_node_t *node, const char *name,
                          uint32 idx, uint32 *out);
const char *arkrtos_dt_prop_str(const arkrtos_dt_node_t *node, const char *name);
int arkrtos_dt_str_eq(const char *a, const char *b);
```

Conventions:

* `is_device` is 1 when the node carries a `compatible`;
* `arkrtos_dt_find*` returns **enabled devices only** (status absent or `okay`), disabled nodes are excluded;
* not found means 0 / -1. It never guesses a "looks like it" result.

## 4. Generate and verify

```bash
# generate the data file for a board
py -3 tools/dts/dtc_lite.py --dts dts/stm32f427.dts --out board/stm32f427/arkrtos_dt.c

# dump the tree structure only, no code
py -3 tools/dts/dtc_lite.py --dts dts/stm32f427.dts --dump

# check that the checked-in .c still matches the .dts (CI)
py -3 tools/dts/dtc_lite.py --dts dts/stm32f427.dts \
      --out board/stm32f427/arkrtos_dt.c --check

# host self-test: build and run the generated table, assert API answers match the DTS
py -3 tools/dts/test_dt.py
```

The generated `board/<chip>/arkrtos_dt.c` is compiled with the kernel; it references the
types and API declarations in `arkrtos_dt.h`.

### 4.1 One DTS, two outputs

The MMU tier (LA64 and friends) does not link that C table. It wants a standard
`.dtb` blob in the image, parsed at boot - the shape every Linux-style project
has. So the same compiler has a second output:

```bash
# produce the standard flattened device tree (spec v0.4, version 17)
py -3 tools/dts/dtc_lite.py --dts dts/qemu_loongarch64.dts \
      --out build/qemu_loongarch64/arkrtos.dtb --format dtb
```

Both outputs come from the **same parse** (`build()` then a fork), so they cannot
disagree; there is no state where the table lists a node the blob lacks.

`--format` defaults to `c`, so MCU-tier command lines and products are byte-for-byte
unchanged; `--check` compares bytes for either format.

`tools/dts/dtb_verify.py` is an independent **reader-side** implementation that
validates the blob itself:

```bash
# all six boards: compile to dtb, validate against the spec, compare to the DTS
py -3 tools/dts/dtb_verify.py --all

# one board, or an existing dtb file
py -3 tools/dts/dtb_verify.py --dts dts/stm32f427.dts
```

It deliberately does not reuse the writer's encoding helpers - reusing them would
let a byte-order or padding bug corroborate itself. Four classes are checked:

| Class | What |
|---|---|
| Header | magic `0xd00dfeed`, version 17 / last_comp 16, totalsize matches the actual length, every block offset 4-byte aligned and in range |
| Memory reservation | starts 8-byte aligned, terminated by an all-zero pair |
| Structure block | `BEGIN_NODE`/`END_NODE` strictly nested, node names NUL-terminated, `nameoff` inside the strings block, property values 4-byte aligned, `FDT_END` exactly at `off_struct + size_struct` |
| Semantics | node for node, property for property, byte for byte identical to the DTS model |

In CI this is the `devicetree-dtb` check, which runs the first command over every
`dts/*.dts`.

### 5.1 MMU tier: the kernel parses the dtb in the image (`fdt` command)

The MCU tier links the DTS as a C table (`arkrtos_dt.c`). The MMU tier takes the
other route: the same DTS becomes a standard dtb (section 4.1), gets wrapped by
`elf_blob.py` into a byte array, is linked into the image, and the kernel's own
parser reads it back at boot. The switch is **`ARKRTOS_USE_FDT` (default n)**, and
the board layer is what turns it on: `config/qemu_loongarch64_defconfig` requests
`=y`, and block seven of `genboard.py` (device tree / MMU tier) writes `#undef` +
`#define 1`. The shared `arkrtos_autoconf.h` keeps it at 0, so the MCU + MDK tier
gains no symbol at all.

The parser (`kernelsrc/src/arkrtos_fdt.c`) is read-only, allocates nothing and
does not recurse; nesting is capped at `ARKRTOS_FDT_MAX_DEPTH = 16`. Every offset,
length and alignment is checked before it is used, and an out-of-range value is
reported as an error code rather than clamped: turning a broken dtb into a
silently missing device would be the worse failure.

| Error code | Value | Meaning |
|---|---|---|
| `ARKRTOS_FDT_OK` | 0 | Parsed |
| `ERR_ARG` | -1 | Null pointer / buffer shorter than the header |
| `ERR_MAGIC` | -2 | First four bytes are not `0xd00dfeed` |
| `ERR_VERSION` | -3 | Unknown version / last_comp |
| `ERR_RANGE` | -4 | Block offset or totalsize out of range |
| `ERR_ALIGN` | -5 | Block offset not 4-byte aligned |
| `ERR_FORMAT` | -6 | Struct block not strictly nested / `FDT_END` not at its end |
| `ERR_DEPTH` | -7 | Nesting deeper than the cap |
| `ERR_NOT_INIT` | -8 | Queried before `arkrtos_fdt_init` |
| `ERR_NOT_FOUND` | -9 | Path / alias / property does not exist |
| `ERR_PATH` | -10 | Path or stdout-path syntax not recognised |

One line is printed before the shell comes up (QEMU LA64, measured):

```
[fdt] blob=1146 rc=0 model=QEMU virt loongarch64 nodes=10
```

`blob=` is the byte size of the dtb embedded in the image, so it can be checked
against `stat` on `build/qemu_loongarch64/arkrtos.dtb`. On failure the line
carries `-n` and ` (blob refused, tree NOT parsed)`: boot continues, but the C
table is **not** used to fake a tree.

The `fdt` command prints exactly the same format as `dt`, so the two read paths
can be compared directly (one QEMU boot, two commands):

```
$ dt
model=QEMU virt loongarch64 nodes=10
  cpu@0 compat=loongarch reg=0x0/0x0 okay
  soc compat=simple-bus reg=0x0/0x0 okay
  serial@1fe001e0 compat=ns16550a reg=0x1fe001e0/0x100 okay
  ramdisk@0 compat=ark,ram-blk reg=0x0/0x80000 okay
$ fdt
(identical, line for line)
```

### 5.2 Runtime tree swap, /chosen and stdout-path (2026-11-20)

The previous version of this page said "only the tree compiled into the image is
parsed". Three more things are done now: swapping the tree at runtime, consuming
stdout-path, and a minimal overlay subset (see 5.3).

**Swapping the tree is transactional.** `arkrtos_fdt_load(dst, cap, src, len)`
copies the bytes into caller RAM and then runs the same `init`; `init` takes a
snapshot of the current view first and restores it on any failure, returning an
error code. A bad blob therefore costs one error code - it does **not** leave the
machine "with no devices all of a sudden". The host self-test pins this down: load
a good tree, corrupt the magic, load again, and `ready`, `node_count` and `model`
must all be unchanged.

**Lookup by path / alias / phandle**: `node_by_path()` (`/` is the root),
`alias()` (accepts both string and phandle alias values), `path_of_phandle()`,
`node_by_phandle()`. Two silent-wrong-answer bugs were found and fixed here, and
they are recorded because they are exactly why round-trip tests are needed: the
depth comparison forgot the root level (so no absolute path ever matched), and
path building treated the root's empty name as a component (yielding `//soc/...`).
Neither raised an error; both simply answered wrong.

**Consuming stdout-path** (switch `ARKRTOS_USE_FDT_CONSOLE`, default n):
`arkrtos_console_from_fdt(expect, bind)` only judges - it does **not** change the
console and does not touch hardware. It checks, in order: does the resolved node
exist, is `status` okay, is the tree self-consistent (`stdout-path` says 115200
while `current-speed` says something else is a `baud_conflict`), and does it agree
with the board's `compatible` / `reg`. On mismatch it keeps the board default and
reports a reason code instead of picking "whatever works".

| Reason code | Value | Meaning |
|---|---|---|
| `ARKRTOS_CONSOLE_OK` | 0 | Tree and board agree |
| `NO_STDOUT` | -1 | No `/chosen/stdout-path` |
| `BAD_PATH` | -2 | Path or options not recognised |
| `NO_NODE` | -3 | Resolved node does not exist |
| `DISABLED` | -4 | Node `status` is not okay |
| `COMPAT` | -5 | `compatible` differs from the board |
| `ADDR` | -6 | `reg` base differs from the board |
| `BAUD` | -7 | `current-speed` conflicts with `stdout-path` |

Measured on QEMU LA64 (2026-11-20, one single boot):

```
[fdt] blob=1146 rc=0 model=QEMU virt loongarch64 nodes=10
[fdt] console path=/soc/serial@1fe001e0 baud=115200 clk=25000000 reason=ok match=1
...
$ fdt chosen
chosen stdout-path="serial0:115200n8"
  path=/soc/serial@1fe001e0 baud=115200 bits=8 parity=n alias=1
$ fdt path /soc/serial@1fe001e0
path=/soc/serial@1fe001e0 name=serial@1fe001e0 depth=2 props=6 okay
  compat=ns16550a reg=0x1fe001e0/0x100
$ fdt phandle 1
phandle 1 -> /soc/serial@1fe001e0
$ fdt save /mnt/ram/b.dtb
fdt: save /mnt/ram/b.dtb rc=0 bytes=1146
$ fdt load /mnt/ram/b.dtb
fdt: load /mnt/ram/b.dtb rc=0 bytes=1146 nodes=10 (was 10)
$ fdt load /mnt/ram/empty.bin
fdt: load /mnt/ram/empty.bin rc=-1 bytes=0 -> refused, previous tree kept (nodes=10)
```

For aliases to work at all, the LA64 DTS now uses the Linux form
(`stdout-path = "serial0:115200n8"` plus `/aliases { serial0 = &uart0; }`), and
`dtc_lite.py` now stamps a `phandle` property on every labelled node. Before
that it only kept labels in its own bookkeeping, the tree carried no phandle, and
`&uart0` could not be resolved from the blob. All six boards' C tables were
regenerated.

`fdt save/load` proves "RAM copy + file round trip + rollback on a bad blob",
**not** a bootloader handing over a dtb and not image relocation. There is still
no silicon reading (QEMU counts as a board run here).

The gate `tools/fdt_gate.py` (CI item `fdt`) now has 14 checks: A-G above plus H
(the boot `[fdt] console` line must agree with the tree, both device address and
console clock; four bad samples must be rejected), I (`fdt chosen` / `path` /
`phandle` must name the same node, `save`+`load` keeps `nodes` unchanged, an
empty file is refused with the old tree kept; again four bad samples must be
rejected) and J (overlay, see 5.3; seven bad samples must be rejected).

### 5.3 Overlay subset: `target-path` / `target = <&label>` / overwrite / delete (`ARKRTOS_USE_FDT_OVERLAY`, 2026-11-20)

What is implemented is a **minimal subset**; stating what is in and what is out
beats claiming "overlays are supported":

| Accepted | Rejected (error code, tree untouched) |
|---|---|
| `fragment@N { target-path = "<absolute path>"; __overlay__ { ... }; }` | `__local_fixups__` node (`ERR_OVERLAY_TAG`) - this implementation does no local phandle renumbering |
| `fragment@N { target = <&label>; __overlay__ { ... }; }` | `target` not 4 bytes, or its placeholder not `0xffffffff` ("an already resolved phandle"): this module does not reverse-look-up a number and does not guess whom it names (`ERR_OVERLAY_TARGET`) |
| Overwriting a property **of the same name** (length may differ) | A zero-length property inside `__overlay__` = **delete that property**; the target does not have it -> `ERR_OVERLAY_DEL (-16)` |
| Appending **new child nodes** (with their own properties and grandchildren) | A same-named child node inside `__overlay__` carrying exactly one zero-length `__delete` property = **delete that child node**; the target does not have it -> `ERR_OVERLAY_DEL` |
| Overwriting a property when the target already has one of that name | A **child node** of the same name already existing under the target (`ERR_OVERLAY_DUP`; no merging, no silent overwrite) |
| | Unrecognised fragment structure (`ERR_OVERLAY`), arena too small (`ERR_OVERLAY_SIZE`) |

`target = <&label>` follows the Linux mechanism, no home-grown format:

1. dtc writes the placeholder `0xffffffff` into `target` and emits
   `__fixups__ { <label> = "/fragment@N:target:0"; }` beside the fragment;
2. the base tree supplies `__symbols__ { <label> = "<absolute path>"; }`;
3. at run time the string `"/fragment@N:target:0"` yields the label name, which
   is resolved through the base tree's `__symbols__` into a path, and only then
   is the fragment merged at that path.

Where the two deletion encodings come from has to be stated plainly:

- **delete a property = a zero-length property**: this is the existing Linux
  overlay convention (assign nothing and the property is removed).
- **delete a child node = one zero-length `__delete` marker property**: the
  dtb encoding of `/delete-node/` was **not** confirmed from an authoritative
  source here (no `dtc` executable on this machine, fetching the original text
  was blocked), so this is a **project-defined representation**, and it does
  **not** claim to be byte-identical with a Linux dtbo. The C side accepts exactly
  one shape: that child contains a single `__delete`, no other properties and no
  child nodes; anything else is refused as `ERR_OVERLAY`, not guessed.

A missing deletion target is always `ERR_OVERLAY_DEL`, never a silent skip - a
mis-spelt `/delete-node/` that "did nothing" is the hardest kind of silent
failure to find.

`__symbols__` / `__fixups__` / `__local_fixups__` are dtc's label tables and are
**not counted as tree nodes**: `arkrtos_fdt_node_count()`, the node iterator and
the MCU-tier `dt` flat table all skip them, which keeps the existing cross-check
"`dt` and `fdt` print the same `nodes=`" valid (that is what the host test and
gates A/E use as a criterion). They are in the blob all the same and
`fdt path /__symbols__` still finds them.

The implementation does **not** patch bytes in place: properties must precede
child nodes, so inserting one shifts every later offset and that whole road is
full of silent-wrong-answer traps. Instead the whole tree is re-emitted into the
caller's arena (`ARKRTOS_FDT_OVERLAY_MIN_ARENA` = 4096). Two passes: the first
only measures (not one byte of `dst` is written, every rejection surfaces here,
including whether the deletion target exists), the second writes; if the two
disagree, `ERR_OVERLAY`. On failure the caller's tree is left exactly as it was
and the arena contents are not promised to be valid.

Measured on QEMU LA64 (2026-11-20, a separate boot that first measures "before"):

```
$ fdt
model=QEMU virt loongarch64 nodes=10
  cpu@0 compat=loongarch reg=0x0/0x0 okay
  soc compat=simple-bus reg=0x0/0x0 okay
  serial@1fe001e0 compat=ns16550a reg=0x1fe001e0/0x100 okay
  ramdisk@0 compat=ark,ram-blk reg=0x0/0x80000 okay
$ fdt path /overlay-demo-node
fdt: path /overlay-demo-node rc=-5          # the node does not exist yet
$ fdt get /soc/serial@1fe001e0 current-speed
/soc/serial@1fe001e0 current-speed len=4 cells=0x1c200     # 115200
$ fdt path /overlay-victim/victim-child
path=/overlay-victim/victim-child name=victim-child depth=2 props=1 okay
$ fdt get /overlay-victim victim-prop
/overlay-victim victim-prop len=7 str="before"
$ fdt overlay
fdt: overlay ok bytes=1176 nodes=10 (was 10) model=fdt-overlay-demo
$ fdt get / model
/ model len=17 str="fdt-overlay-demo"
$ fdt get /overlay-demo-node overlay-value
/overlay-demo-node overlay-value len=4 cells=0x2a
$ fdt path /overlay-demo-node
path=/overlay-demo-node name=overlay-demo-node depth=1 props=2 okay
  compat=ark-overlay-demo reg=0x0/0x0
$ fdt get /soc/serial@1fe001e0 current-speed
/soc/serial@1fe001e0 current-speed len=4 cells=0x2580     # 9600, from target=<&uart0>
$ fdt path /overlay-victim/victim-child
fdt: path /overlay-victim/victim-child rc=-9               # /delete-node/ took effect
$ fdt get /overlay-victim victim-prop
fdt: /overlay-victim has no property 'victim-prop'          # zero-length property = delete
```

The net change `nodes=10 (was 10)` is **intentional**: this fragment appends one
new node (`overlay-demo-node`) and deletes one child (`victim-child`), which
cancels out. Each of the three new criteria has its own anti-false-green reading:
rename `victim-child`, and `fdt overlay` must report
`rc=-16 (delete target not found) -> refused, tree kept (nodes=10)` (that negative
sample was actually run on this machine, then restored byte for byte).

Those four `fragment@N` come from `tools/dts/overlay/demo_label.dts` and travel
the same road as the base tree (dts -> dtb -> C array from `elf_blob.py`), exposed
by the board as `arkrtos_board_fdt_overlay_demo()`. It takes **no part in boot**:
an image that never applies an overlay behaves byte for byte as before
(`ARKRTOS_USE_FDT_OVERLAY` defaults to 0 and only the LA64 board turns it on).
Why a second file instead of editing `tools/dts/overlay/demo.dts`: the host test
feeds `demo.dts` to all six boards' trees, while `&uart0` / `&victim` only exist
in the LA64 tree; a label reference there would necessarily fail on the other
boards. So `demo.dts` stays board-agnostic and `demo_label.dts` is its superset,
embedded into the LA64 image only.

A successful `fdt overlay` installs the new tree into the same RAM buffer (a
byte-for-byte self-assignment with `dst == src`, measured safe), so the following
`fdt get` / `fdt path` / `fdt` all read the post-overlay tree. The only real
anti-false-green gate in group J is **the reading taken before applying**: without
it, post-apply readings cannot tell "the overlay really wrote this" apart from
"the tree already had it".
