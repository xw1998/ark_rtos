# MiniApp: the third kind of user-state application, living in the file system

**[简体中文](小程序设计.md) | English**

> Condensed English edition. The Chinese page (小程序设计.md) is normative: every number below is

> new claim and no new measurement.
>

> item by item in §9; F401 is build-only (that board has `ARKRTOS_USE_MINIAPP` switched off).

A MiniApp (image header `type = 3`) exists to solve exactly one problem: **some programs are not
worth a full "install"**. It lies in the file system as an ordinary file, is loaded into RAM when it
should run, and its RAM is returned the moment it exits; running it again loads it again — trading a
little efficiency for the whole apparatus of "partition / slot / version / install window".

## 1. How the three kinds of user-state application relate

| Item | App | Driver | MiniApp |
|---|---|---|---|
| image type | `type = 1` | `type = 2` | `type = 3` |
| resident location | Flash image pool (one slot) | Flash image pool (one slot) | **one file in the file system** |
| placement | decided by the loader at install, fixed until uninstall | same as App | **RAM borrowed per run, returned on exit** |
| code execution | XIP (execute in place from Flash) | XIP | **copied into RAM and executed** (no XIP) |
| install procedure | required (`install` window + version gating) | required | **not required** |
| memory use | one copy in Flash + declared RAM block | same as App | **a code block plus a RAM block in RAM** |
| start command | `app start <slot>` | `drv start <slot>` | `mini run <path>` |
| upper bound | free pool space | free pool space | code block ≤ `SLOT_RAM_MAX_BLOCK` (default 32 KB) |

The container is the same: 256-byte image header + relocation table + payload, and the same entry
convention (`APPSTART` / `DRVSTART` / `MINISTART` are all stubs that jump into the C runtime
`__main`); `arkrtos_oslib.c`, the one SVC facade, is shared by all three. The only difference is the
header's `type` field, which decides which load path is taken.

## 2. Memory model: two blocks, not one

One load borrows **two** power-of-two-aligned blocks from the RAM pool (both inside the pool that
starts at `SLOT_RAM_BASE` with total size `SLOT_RAM_TOTAL`):

| Block | Size | Contents |
|---|---|---|
| code block | `pow2_ceil(align8(payload length))`, floored at `SLOT_RAM_MIN_BLOCK` | the payload itself, starting at the block base |
| RAM block | `ram_size` declared in the header (must itself be a power of two) | RW/ZI; the stack is cut from the top down by `APP_TASK_STACK_SIZE` |

The two blocks **live and die together**: first find room for the code block and record it in the
local occupancy table, then find room for the RAM block; if either step fails the whole thing is
abandoned, never leaving a half-borrowed intermediate state (the return path recognizes exactly one
state).

### Why not "stuff both into a single pow2 block"

The first version did exactly that, on the reasoning "one block is cheaper than two". That reasoning
is **wrong**:

```
pow2_ceil(code + RAM)  >=  pow2_ceil(code) + RAM        always holds
```

because `pow2_ceil(code) >= code` and `code + RAM` must be rounded up to a power of two. In the most
common case — code much smaller than RAM — the two are close to **double**:

| code | RAM | single block | two blocks |
|---|---|---|---|
| 1 KB | 8 KB | 16 KB | **9 KB** |
| 4 KB | 4 KB | 8 KB | **8 KB** |

A single block only breaks even when the two are very close and happen to straddle a power-of-two
boundary. Two blocks also cleanly split the MPU: one region for the code window, one for the data
window, so the data window no longer has to accommodate the code window's "executable" attribute.

### Compared with the four ways ELF uses less memory

| What ELF does | Can we copy it | Result |
|---|---|---|
| demand paging, map only what is really touched | no (a machine without an MMU has no paging) | the whole thing must be moved into RAM |
| segment mapping: code stays in the file and is mapped by the MMU, using no RAM | the equivalent is XIP; but the requirement explicitly says "load into memory" | code must occupy RAM |
| header and metadata are not kept resident | yes | the 256-byte header + relocation table are **dropped after reading**, never written to RAM |
| the copy process keeps no extra copy in memory | yes | read a segment, patch a segment: the payload is read straight to the code block base, **no staging buffer**; the relocation table is packed to 4 bytes per entry |
| process exit releases all mappings | yes | the task-exit hook returns both blocks immediately |

So this scheme's footprint is the **mathematical lower bound**: `pow2(payload) + ram_size`. The only
remaining savings are the two already done — header/table never land in RAM, and no staging buffer.

## 3. The load procedure (six steps)

```
1. read the 256-byte header  -> arkrtos_loader_check_header(p_rel = 0, mask = MINI)
2. read the relocation table   reloc_count * 4 bytes into a static table (4 KB = 1024 entries max)
                               then check_header again (this time with the table): both passes must succeed
3. size checks                 code_want = pow2_ceil(align8(image_size))
                               over the limit / RAM not a power of two / ram_size < stack  -> ERR_SIZE
                               code_want < code_size (wrap-around self-check)              -> ERR_SIZE
4. borrow blocks               arkrtos_ptable_mini_alloc(): code block + RAM block
5. copy payload + patch        read in 256-byte segments, compute the nominal CRC first, then walk the relocation table
6. start the task              entry = code block base + entry_offset (with the Thumb bit)
                               stack top = top of the RAM block; four TCB window fields filled back; build the MPU
```

Loading is **serialized** by the global gate `g_mini_busy`: only one load or teardown runs at a
time. The file system has only one cache, so a **single read** (one 256-byte chunk) must complete
inside the scheduler lock and cannot be interrupted — two tasks interleaving reads of an image would
shift each other's windows. But between two reads there is no intermediate state to protect, so the
load loop unlocks and re-locks every `ARKRTOS_MINI_YIELD_CHUNKS` chunks (default 1), letting
higher-priority tasks get the CPU during a load; setting that switch to 0 restores the old
"hold the lock for the whole stretch" behaviour (the A/B in 无缝升级例程.md §5.1). What can be
"simultaneous" is **running**, not loading — each instance borrows its own two blocks and has its own
task and MPU windows, so they never overwrite each other.

How many can run at once is decided by two gates: compile-time `ARKRTOS_MINI_MAX` (struct sizes, the
shared table array and crash accounting capacity are all sized by it) and runtime `mini count <n>`
(**can only tighten, never widen**; out of range reports `PARAM`, never clamps). The actual count is
further limited by free pool space: with no two contiguous blocks available, the N-th reports
`NOSPACE` and **never** evicts a running one or lets two instances share a block.

The stop order cannot be reversed either: **first kick the image (including the threads it created)
out of the scheduler, then return the blocks**; the other way round, the block could immediately be
taken by the next loader and written with code while the old task is still running.

## 4. Size limit: tightenable at runtime, never widenable

| Layer | Value | Notes |
|---|---|---|
| compile-time ceiling | `SLOT_RAM_MAX_BLOCK` (F427 = 32 KB) | at once the physical single-block pool limit, the App image check limit and the MPU data window limit |
| runtime limit | default = ceiling, tightenable with `mini limit <bytes>` | out of range reports `PARAM`, **never clamps** |

**Why only tighten**: widening would push `arkrtos_mpu_ram_window()`'s decision onto the "kernel RAM
fallback window" branch — a failure that **silently** puts a task in the wrong window. That must not
be triggerable by a single tuning call. To genuinely raise the ceiling you change
`SLOT_RAM_MAX_BLOCK` and satisfy the pool and MPU static assertions at the same time.

**Why not clamp**: clamping would turn "I asked for 64 KB and got 32 KB" into a lie nobody can see.
Out of range reports `ARKRTOS_LOADER_ERR_PARAM` directly.

**Why not persist it**: writing it into the device configuration area would change the configuration
record ABI (version 1 → 2, freeing a `reserved` field) and invalidate records already on the board.
This round is runtime only (shell + kernel API). Making it survive a reboot means going through the
configuration-record upgrade — a different job.

## 5. How to use it

Packing uses **exactly the same four-pass differential link pipeline as an App** (nominal / ROM+delta
/ RAM+delta / double-delta verification), differing only in the type:

```bash
py -3 tools/pack_app.py --project example/stm32f427/app_sdk/MINI_DEMO/MDK-ARM/mini_demo.uvprojx \
        --type miniapp --name MINI_DEMO --ram-size 8192 --out build/mini_demo.svcapp
```

Packing also blocks two classes of image that would be packed but could never run:

- relocation table entries > `ARKRTOS_APP_RELOC_MAX` (the kernel loader has no sliding window and
  cannot read a table that long);
- code block > `SLOT_RAM_MAX_BLOCK`, or code block + RAM block > `SLOT_RAM_TOTAL`.

Putting it into the device file system (the `fs put` receive window; host side is
`tools/fs_put.py`):

```bash
py -3 tools/fs_put.py --port COM3 --path /mini_demo.app build/mini_demo.svcapp
```

(The file system has no `mkdir` command, so the path is just a file name at the volume root; the
`/mini/...` in the README is only an illustration of "once directories exist".)

Running and observing:

```
mini run /mini_demo.app          # load and start
mini / mini list / mini stat     # list running MiniApps: index / task id / two block bases and sizes / entry / CRC
mini count                       # how many can run at once, how many currently run
mini count 2                     # tighten the concurrency limit to 2 (tighten only)
mini limit                       # show the size limit and its default
mini limit 8192                  # tighten the size limit to 8 KB
mini stop                        # stop all and return both blocks (mini stop <n> stops only index n)
mini forget /mini_crash.app      # clear the crash memory of one path so a disabled MiniApp can run again
```

### Autostart / not starting at boot

MiniApps **do not autostart by default** (dropping one into a volume does not run it). To have it run
at boot, register it in a text list inside the volume, `/mini.autostart`
(`ARKRTOS_MINI_AUTOSTART_FILE`; one path per line, `#` starts a comment, empty lines ignored, whole
list capped at `ARKRTOS_MINI_AUTOSTART_MAX` = 1024 B):

```
mini autostart                    # list: each path, whether it exists in the volume, whether disabled
mini autostart add /mini_demo.app # register: run it at the next boot
mini autostart del /mini_demo.app # undo: do not run it at the next boot
mini autostart now                # run the list right now (without waiting for a reset)
```

**Why a list file instead of an `AUTOSTART` flag in the image header** (which is what Apps and
drivers use):

- a MiniApp's **identity is its path** — crash accounting is keyed by a hash of the path, and the
  list uses the same identity, so the two never disagree about "the same program under two names";
- toggling only takes **one line of text**: changing a header flag invalidates the image's own CRC
  and requires rewriting the whole image, while "this file is broken" means the program is a write-off
  for a MiniApp — cost and benefit are wildly disproportionate;
- "not starting at boot" is simply **not being listed**; no second state is needed.

To avoid the illusion of "a flag nobody reads", `tools/pack_app.py --type miniapp` **refuses**
`--autostart` outright and points at `mini autostart add <path>`.

The trigger point is **after the first successful volume mount of this boot** (`fs_mount_with()` in
`arkrtos_fs.c` calls `arkrtos_mini_boot_autostart()` at its end, guarded once by
`g_mini_auto_boot_done`): a MiniApp's executable bytes live in the volume, so "volume available" is
the only moment it can come up; the kernel does not guess which device holds a file system (that is
board knowledge), mounting is initiated by the upper layer. The start criteria **all reuse
`arkrtos_mini_run()`** (concurrency limit / crash disable / size limit are not re-implemented) and
every success and failure is logged — autostart is "something that happens with nobody watching", so
the log is its only account.

## 6. Shell commands and error codes

| Command | Semantics |
|---|---|
| `mini` / `mini list` / `mini stat` | list running MiniApps (index / task id / two block bases and sizes / entry / CRC); prints "none" and the current limits when nothing runs |
| `mini run <path>` | load and start; the path is absolute inside the file-system volume |
| `mini stop [n]` | stop all and return both blocks; with `n`, stop only index `n` |
| `mini count [n]` | without an argument: "how many can run / how many are running"; with an argument: tighten the concurrency limit (cannot widen beyond `ARKRTOS_MINI_MAX`) |
| `mini limit [bytes]` | without an argument: show the size limit; with an argument: tighten it (0 = restore default) |
| `mini forget <path>` | clear the crash memory and disabled state of one path |
| `mini autostart [list \| add <path> \| del <path> \| now]` | autostart list: list / register / undo / run the list now |

Under the slot table, the `crash` command prints a separate MiniApp accounting section: the journal
stores only the **path hash** (fixed length, so it fits the UNINIT area), so a path that matches
`/mini.autostart` is shown as the path, and one that does not is shown as the raw value `#<hash>`
with a note — **never a plausible-looking invented path**.

Error codes follow the loader's set (`kernelsrc/include/arkrtos_loader.h`), plus two unique to this
path:

| Code | Meaning |
|---|---|
| `ARKRTOS_LOADER_ERR_MAGIC` / `COMPAT` | not a valid image / `hw_compat_id` mismatch |
| `ARKRTOS_LOADER_ERR_SIZE` | bad size: over the limit, RAM not a power of two, cannot fit the stack, or length wrap-around |
| `ARKRTOS_LOADER_ERR_CRC` | header CRC or payload CRC mismatch |
| `ARKRTOS_LOADER_ERR_RELOC` | invalid relocation table (including a self-contradictory "patch goes backwards" table) |
| `ARKRTOS_LOADER_ERR_NOSPACE` | the pool cannot supply two blocks (not "out of memory" — fragmentation or already taken) |
| `ARKRTOS_LOADER_ERR_BUSY` | the concurrency limit (`mini count`) is full; the running one is never evicted |
| `ARKRTOS_MINI_ERR_FS` (-18) | reading the file failed; the cause is in `arkrtos_fs_last_error()` |
| `ARKRTOS_MINI_ERR_DISABLED` (-19) | this path crashed up to the limit and is disabled (`mini forget <path>` clears it) |

## 7. Known limits (listed honestly)

1. **Crash disabling uses the same threshold as slot images but accounts separately.** A MiniApp's
   main task belongs to no slot, so its identity is a **FNV-1a hash of the path**; each fault calls
   `arkrtos_crash_mini_fault(hash)`, which returns 0 below the limit (the default path **restarts in
   place**) and 1 at the limit (stop the image + return both blocks + reset the MPU + clear the
   slot). The threshold is **not a second set of constants**: like slots it reads the partition
   table's `cfg_restart_max`. Accounting lands in the cross-reset crash journal
   (`mini_hash / mini_cnt / mini_last_reason / mini_dis_reason / mini_dis_tick`, 8 entries), so
   "disabled after 3 crashes" **survives a reset** but **not a power-off** (the journal is in the
   UNINIT RAM area, cleared at power-on — reset is the event to count). Once disabled, `mini run`
   reports `ARKRTOS_MINI_ERR_DISABLED` (-19), cleared by `mini forget <path>`.
2. **The code window is executable and writable.** A MiniApp runs inside its own code block, and the
   MPU grants `RAMX` (unprivileged RW + executable), i.e. **it can modify itself inside its own
   block**. This is the same posture as an App (which also executes inside its own ROM window), and a
   MiniApp releases everything on exit, so this version records it as "posture relaxed" rather than
   treating it as a vulnerability.
3. **Limits can only be tightened**; the ceiling is the compile-time `SLOT_RAM_MAX_BLOCK` (§4).
4. **Concurrency is limited by two gates plus the RAM pool.** Compile-time `ARKRTOS_MINI_MAX`,
   runtime `mini count` (tighten only), on top of whether the pool can supply two blocks — the current
   build on this board measures `pool free` 481 KB (earlier layout numbers no longer apply), boot
   takes 52 KB, leaving only 4 KB + 8 KB, while an 8 KB MiniApp needs 9 KB, so in measurement **two
   8 KB MiniApps can run at the same time** (`SEAMLESS_V1` + `SEAMLESS_V2`, `mini list` reported 2
   running); `NOSPACE` appears only when the pool cannot supply two blocks. To get two running you
   must first free pool space (`app uninstall`, which erases Flash).

### 9.3 A real bug the board exposed and that was fixed

On the first on-board round, `mini autostart add /mini_demo.app` was refused outright:
`Too many arguments (max 3)`. The cause was not a wrong branch but the command registration's
`max_args` being written as `3` (`ARK_SHELL_CMD("mini", ..., 3)`), while
`mini autostart add <path>` is `argc == 4` — the dispatcher rejected the command before entering
`cmd_mini`. After changing it to `4` it passed. **This class of error is invisible in a build-only,
never-flashed version**: the compiler does not warn about an argument limit set too low.

### 9.4 Interaction with the hardware-safe-state ("last words") mechanism on exit

When a MiniApp's main task returns normally, the exit path takes the **planned handover** route
rather than "unplanned death": the hardware-safe-state mechanism only removes that task's device
ledger, and **runs neither last words nor driver callbacks** — because in a seamless upgrade the new
version taking over immediately will `open` the same device again, and forcing it into the safe state
right now would be churn rather than safety. This is controlled by
`ARKRTOS_MINI_EXIT_IS_HANDOVER` (default 1); setting it to 0 makes a normal exit return to the safe
state too. Crashes, forced kills and fault recovery do **not** take the handover route and always
perform a full neutralization.

The number of skipped handovers is counted separately in `hwsafe`'s `handover=` and **not** included
in `neutralized` (it neutralized nothing). See App崩溃硬件安全与遗言机制.md.

### 9.5 Measured on board: planned handover (2026-11-13, STM32F427)

The rule in §9.4 ("a normal exit only removes the ledger, it does not neutralize") previously existed
only as a code path, with no board reading. The criterion (verbatim from 欠账盘点.md §一):

> after a MiniApp exits normally, `hwsafe` reports `handover=1` and the device was not neutralized

The example is in `example/stm32f427/app_sdk/MINI_HANDOVER/`, image `build/mini_handover.svcapp`
(2980 B, payload 2680 B, relocation table 11 entries), board path `/mh.svcm`. The program:
`arkrtos_dev_open("led2", 0)` → `arkrtos_dev_ctrl(led, 1, 0)` to turn it on → wait 3 s in place (to
leave a visual window) → **no `close`** → return normally from `main` with `0`. led2 was chosen
because led0/led1 are held by kernel tasks 1/2 and led2 usually has no owner.

| Item | Method | Measured result |
|---|---|---|
| baseline | `hwsafe` | `enabled, devs=3 owners=3 neutralized=0 (will=0 cb=0 none=0 fail=0 handover=0)`; own entries are led0(task1) / led1(task2) / ttyS0(task6) |
| run | `mini run /mh.svcm` | serial text below; ends with `mini run: /mh.svcm loaded but no longer running` |
| handover count | `hwsafe` again | `... neutralized=0 (will=0 cb=0 none=0 fail=0 handover=1)`; the led2 own entry is gone and no new own entry appeared |
| both blocks reclaimed | `mini stat` | `mini: none running` (code and RAM blocks already returned) |

```
MINI_HANDOVER: mini starts (planned hand-over probe)
MINI_HANDOVER: led2 handle=18874370 ctrl(ON)=0
MINI_HANDOVER: holding, round 1
MINI_HANDOVER: holding, round 2
MINI_HANDOVER: holding, round 3
MINI_HANDOVER: returning from main, device still held
mini run: /mh.svcm loaded but no longer running (a program that exits on its own looks the same; 'dmesg' shows which)
```

Three points of protocol:

- `handover` and `neutralized` are two mutually exclusive destinations and must be **read as a pair**:
  `handover` +1 while `neutralized` stays put. Reading only `neutralized=0` is not sufficient — it
  also does not move when there is no ledger to remove (e.g. a program that `close`d before exiting).
- This image **deliberately does not close**. If it closed before exiting, there would be no ledger
  to remove, `handover` would not move, and the case would be a wasted run.
- The criterion uses only kernel counters and the ledger. **GPIO / LED were not used as evidence**,
  for the reason below.

### 9.6 Why this criterion does not use GPIO / LED as evidence (probe reading protocol)

This round tried reading `GPIOC_ODR` with `pyocd` to "see the LED still on", and concluded the route
is unusable on this machine; both traps produce false "evidence":

1. **Reading peripherals while the target runs returns a constant fake value.** Without `halt`, a
   direct `read32` returned the same `0x03000000` for three completely different addresses
   (`RCC_CR`, `FLASH_OPTCR`, `GPIOC_ODR`); only after `halt` did the same addresses give real values
   (`OPTCR=0x0FFFAAED`, `ODR=0x00000006`). The `0x03000000` quoted in earlier documents is exactly
   this fake value.
2. **`halt` itself disturbs the target.** After several `halt` → `read` → `go` rounds this round,
   `hwsafe`'s `handover` went back to 0 and `tick.isr` restarted from zero, i.e. the target had been
   reset during debugging (watchdog).

So for an instantaneous state like "was the hardware touched at the moment that task exited", a probe
is neither accurate nor stable; what can stand up is only the kernel's own `handover` /
`neutralized` counters and ledger entries. This has been written into 已知限制.md §五.

**Unverified**: the profile with `ARKRTOS_MINI_EXIT_IS_HANDOVER` set to 0 (a normal exit also returns
to the safe state) has not been on board — it needs another kernel build, and the kernel on the board
this round is the default profile (macro = 1).
