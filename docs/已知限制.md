# Ark RTOS 已知限制

**[简体中文](已知限制.md) | English([已知限制.en.md](已知限制.en.md))**

这份是**唯一一页"限制清单"**。此前这些限制散在 `与Linux差距盘点`、`小程序设计`、
`安全认证准备`、`lwIP协议栈接入`、`软总线接入`、`实时性与最坏延迟` 各篇里，读者
要拼起来才知道边界在哪。每条都注明"是取舍还是欠账"，以及证据在哪。

> 分档口径：**取舍** = 定位上不做，写进文档是让人别指望；**欠账** = 该做没做完或
> 没验证，`docs/欠账盘点.md` 里有对应条目。

## 一、执行模型

| 限制 | 性质 | 说明与证据 |
|---|---|---|
| fork+shm 档有低频 INE 停机，**根因未定位** | 缺陷（未修好） | 五档全开（fork+cow+shm+futex+filemap）时，子任务退出之后父任务偶发掉进 `ecode=0x0d`（INE）。两次实跑签名一致：`era=0x0025229b`、`ra=0x00252297`、`PRMD=0`、`crmd=0x10`，且 `era` 不是 4 的倍数。出现率约 1/18 及更低；此后**串行 25 轮 + 并行 3×40 轮 + `-icount shift=0..3` 四档 + 9 次各 8 轮重复 fork（合计 72 轮 fork）全部 0 命中**，因此**不能宣称已修好**，也**不能拿「重跑到绿」当证据**；串口原文留档 `D:/tmp/fork_ine_2.log`。已做三件事，都是真缺陷但**都不是**根因：① `la_pg_cow_fault` 里「这一格只剩本空间一个持有者、窗口里那条条目却还是 fork 时刻的只读」原来 `return 0` 交回原路径（PLV0 停机 / PLV3 重启 App），现已装回可写并计 `s_pg_cow_reclaims`（触发序列：fork → 子进程退出 → 再 fork 一次 → 写自己共享过的页）；② `arkrtos_port_fatal_report` 原来用 `uint32` 接 64 位 CSR、高位被截断，现已改为 64 位打印（`la_board_puthex64`，高位为零时输出与旧口径逐字相同）；③ 切换闸门新增「目标帧 ERA 必须 4 对齐」一条，坏帧原地不切并计 `s_swp_bogus_era`——把「整机 INE 停机」换成「可读数的拒绝」（LA64 没有压缩指令，合法帧的 ERA 只可能来自 `stack_init` 的入口地址或硬件 ERA，两者必然 4 对齐，所以这条闸门没有误伤路径）。**线索（不是结论）**：崩溃时的 HEAD ≈ `9670241`，那时 `la_frame_apply_priv` 是裸写 `s_next_pplv`、所有用户任务都以 PLV0 恢复（这处特权级反转已由 `62e9a99` 修掉）；把 `0x25229b` 套到**当前**镜像布局上，它落在 `eentry+0x2b` 的 GPR 保存循环中间，形态像「内核从一帧已经坏掉的帧 ertn 出去」，但把旧地址套到新镜像上只能算线索，且当时打印被截成 32 位、真实高位未知。已排除：不是 futex 配对错（futex 段 check 全绿）、不是 `-smp 2` 那条老家族（本档单核）。**2026-11-25 又命中一次（第十档 `fork+cow+shm+futex+filemap+mprotect+select+socket+thread+appq`，`ci_gate` 的 `fork` 项因此判红）**：这次的报文是 64 位口径、不再截断——`estat=0xd0800`、`ecode=0x0d`、`era=0x26c58b`、`badv=0x26c58b`、`badi=0x011f0300`、`crmd=0x10`（PLV0），`era` 仍不是 4 的倍数；用 `nm` 对**当前镜像**对账，`0x26c58b` 落在 `eentry` 里（`0x26c460..0x26c6c4`，即 `eentry+0x12b`）——上一次那只是「把旧地址套到新镜像」的线索，这一次是**当前镜像上的直接命中**（同一签名、同一个函数内部）。命中前最后一条读数是 `[fork] child wrote its own marker`。把构建目录恢复默认档之后，同一档连跑 6 次 0 命中 ⇒ 仍是低频形态、不是必现；这 6 次与前面 25+120+72 轮一起登记为「重跑到绿不能当证据」。下一步不是继续重跑，而是加读数：`eentry` 的 GPR 保存循环里每格一条（哪一格先把栈写坏）、`on_task_exit` 释放链逐格（共享对引用计数 / 帧回收 / 空间释放）。再回到 `on_task_exit` 释放链（共享对引用计数 / 帧回收 / 空间释放）逐格加读数 |
| **没有 MMU 的档**：没有虚拟地址空间 | 取舍（窗口后端） | `ARKRTOS_USE_MPU=1` 时 App 在分区内固定 RAM 窗口里跑，所有任务是**同一个地址空间**加逐任务 MPU/PMP 窗口。见 [内存保护与App越权验证](内存保护与App越权验证.md) |
| **有 MMU 的档**：有每 App 地址空间机制，但没有并发与分配器 | 部分欠账（M2） | `ARKRTOS_USE_PAGING=1`（LoongArch64 已实跑）把隔离从窗口换成页表条目 + PLV。2026-11-17 起 `set_app` 会**重写 App 窗口那一条 PS=20 条目**（空间号即帧号，VA 恒 `0x02000000`），所以「同一 VA 两块物理内存」成立。**U-3 三阶（2026-11-17）已做**：第一阶 4 KB 页帧池（开关 `ARKRTOS_USE_PAGING_FRAMES`），第二阶页级 App 窗口（开关 `ARKRTOS_USE_PAGING_PAGES`），第三阶按需缺页（开关 `ARKRTOS_USE_PAGING_DEMAND`，即 U-5；**三档都只在这块 LA64 板级或按需档的独立 `BUILD` 目录里开**，其余板关档体积与行为逐字节不变；读数 `pmap frame` / `pmap look` / `pmap ftest`）。第二阶把窗口从「一条 2 MB 的 PS=20」换成 **256 条 PS=12 条目**，帧来自池（每空间整块 512 帧，`used` 因此是 512）；第三阶让窗口在 `activate` 之后**为空**、第一次摸到某一对 8 KB 才拿两帧装一条（`used` 掉到按需付的 14 那一档）——`tlb_refill_entry` 因此补了「保存/恢复全部 GPR + `tlbfill` + 回原指令重试」那条分支。**空间回收（2026-11-17）已补上**：`arkrtos_paging_space_release(space)` 先把窗口条目撤掉再把帧交回池子（反序会两空间共享物理页且不报错），页级档整块 512 帧、按需档逐对还；`pmap rel <n>` 打前后帧数，装载器在 activate 之前回收该空间的旧窗口；但**只有页级档跑过 QEMU**，`-3`（调用者站在窗口里）分支没有实跑；**页替换**缺省关（`ARKRTOS_USE_PAGING_SWAP=0` 时池空即落回原致命路径）；开档后改为换出一对 8 KB 再重试，但交换区在内核 `.bss`、**不省内存**，且仍无脏页判定；**默认档没有 ASID/TLB shootdown**（U-7 的 ASID 档已做并实测，见 [QEMU模拟器移植与验证](QEMU模拟器移植与验证.md) §5.28；shootdown 仍没有 —— U-7b 已在 QEMU 上逐 op 取证：本载体的 `invtlb` 没有可用的按 ASID 定向失效，见 §5.29），并且 refill **不区分 PLV**（内核经窗口拷贝与 App 自己访问走同一条路）。`copy_from_user`（U-6）已做；退出码通道（U-8）已做但只在 LA64 板级开档；`wait <task id> [timeout ms]` 与 `main` 返回值转码（App / 小程序 / 可下载模块三条路径）已于 2026-11-17 补上，但那是 shell 侧 20 ms 轮询任务表、**不是** POSIX `wait()`（无父子、无僵尸队列、槽复用后读到的是新任务的码）；driver_sdk 刻意不接（驱动任务没有观察者）。详见 [MMU进程模型与ELF装载](MMU进程模型与ELF装载.md) §6 的 U-1..U-7；不得把这一档说成"Ark 有进程了"或"两个程序同时跑通了" |
| `fork` 已有（默认关，fork 档）；swap 一概没有；`execve` 只有「同任务换镜像」 | 取舍 + 部分已补 | `exec`（shell 命令）是"起一个任务并等它"；`execve`（Linux ABI 号 221，2026-11-21，QEMU LA64 实跑）把**当前任务**的镜像就地换掉——任务号不变、fd 保留、堆游标归零。fork 档（`ARKRTOS_USE_LINUX_FORK`，2026-11-23，QEMU LA64 实跑 21 条 check）补上了**父子**：每进程 fd 表与继承、跨任务 `SIGCHLD`、真阻塞的 `wait4`（可重启系统调用）；写时复制已做（`ARKRTOS_USE_PAGING_COW`，2026-11-23，默认关，QEMU LA64 实跑 26 条 check：8 KB 对粒度、引用计数、**栈页强制私有**——trap 帧压在 App 栈上）；仍没有换出。**线程已做**（`ARKRTOS_USE_LINUX_THREAD`，默认关，2026-11-24，QEMU LA64 第九档 186 条 check）：共享地址空间、每线程自己的 trap 帧与用户栈、共用进程槽与 fd 表、`CLONE_SETTLS`/`getpid`=tgid/`gettid`、`exit` 只退自己与 `exit_group` 退整组两条路径、`CHILD_CLEARTID` + `FUTEX_WAIT` 的 join。见 [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.md) §5、§8.10 与 [与Linux差距盘点](与Linux差距盘点.md) |
| 线程档只在**单核**上验证过；`exit_group` 在 SMP 下的强杀没有协议 | 欠账（验证档位） | 线程组的 `exit_group` 要收掉"可能正在另一核上跑"的任务，本内核只有单核就绪集，没有核间停核协议（见本页"单核；SMP 只有骨架"一条）。第九档 QEMU 是 `-machine virt` 单核，**没有**任何多核读数。判据：拿到 `-smp 2` 下 `exit_group` 与线程退出的读数（含被强杀核上的现场）之前，不得把这一档读成"多线程在多核上可用"。见 [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.md) §8.10 |
| `execve` 从**非组长线程**发起属未定义 | 欠账（语义缺口） | `execve` 换的是**当前任务**的映像；Linux 的语义是"结束整组、只留调用者"。本内核既没有实现整组收尾，也**没有**在非组长线程上拒绝——后果是同组其它线程仍指着旧地址空间，行为未定义。已知边界，夹具不覆盖这条路径。判据：`grep -n "lx_execve" kernelsrc/src/arkrtos_linux_abi.c` 附近的线程组判断；补法二选一（收整组，或非组长 `-EINVAL`）。见 [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.md) §8.10 |
| `CLONE_SETTLS` 传 0 表达不出"把 `$tp` 设成 0" | 取舍（接口表达力） | 内核约定 `tls == 0` 表示"没给"（`$tp` 沿父线程），因为 LA64 的 `$tp` 在帧里没有"未初始化"这个态。要区分"设成 0"与"没给"得再加一个位，而 glibc 从不这么用（它总给一个非零 TCB 地址）。判据：`grep -n "child_tls != 0ul" kernelsrc/port/loongarch/la64/arkrtos_port.c` |
| MPU 是区域级，不是页级 | 取舍（硬件决定） | Cortex-M 的 MPU 只有 8 个 region、最小 32 B 粒度，且必须 2 的幂对齐；"一页 4 KB 保护"这种粒度做不到。App 越权验证见 [内存保护与App越权验证](内存保护与App越权验证.md) |
| 单核；SMP 只有骨架 | 取舍 + 欠账 | 调度器仍是单核就绪集：全局当前任务号、全局 256 位就绪位图、全局延迟队列，**没有 per-CPU 调度结构**。`ARKRTOS_USE_SMP`（默认关）只提供多核地基——每核状态表、在线掩码、次核入口（未上线核 WFI 空转）、IPI 通路、`ARKRTOS_CPU_NUM` 1..8，单核 port 的两个钩子直接返回 `-1` 而不是假装成功。**打开开关不会变成多核**，且在无多核板上没有任何板级读数（只有宿主 44 条断言 + 5 文件 ON 档语法 + LA64 pin U）。**LA64 上已补次核停靠与真核号（SMP 档）**，但 QEMU `-kernel` 直启把次核停在 pflash 的 `slave_boot_code`，停靠分支本机不可达（判词 `smp_park_unreachable_on_qemu_kernel_boot`，见 [QEMU模拟器移植与验证](QEMU模拟器移植与验证.md) §9.5）。见 [同步原语与令牌守恒](同步原语与令牌守恒.md) §5.10、[与成熟RTOS对比](与成熟RTOS对比.md) 缺口 ⑦ |
| 等待者容量 **未上板**；递归锁、多级 PI、多对象探测、中断内收发消息、32 位事件集的 App 通道 / 内核侧 ISR 入口 / App 侧 SVC 0x21 在 ISR 里、POSIX 读写锁与屏障已上板 | 欠账（验证档位） | 递归锁与多对象探测 **已在 F427 上板验证**（2026-11-14，`utest` 通过、110 条断言，含递归/探测开关打开档）；多级优先级继承 **已在 F427 上板验证**（2026-11-15，真任务三档链 `mtx_pi_chain_contract`，20 条断言 0 失败，并用「只看基准优先级」的单跳改动做过负对照，报 `got 10 / want 6`）；POSIX 读写锁 / 屏障 **已在 F427 上板验证**（同日，`POSIX_DEMO` 自检 `rwlock : PASS (0 violations)`、`barrier : PASS (arrived=2 serial=1 bad=0)`），但只覆盖单任务锁状态机与 3 参与者一次性屏障，**多读者并发重叠与「写者优先下不发生写者饿死」仍无板级读数**；中断内直接收发消息 **已在 F427 上板验证**（2026-11-15，`utest` 用例 `mq_from_isr_contract`，EXTI0 软件触发进真 handler，发/收/空/满四条路径、36 条断言 0 失败，并用「send 静默丢弃却报成功」做过负对照），但**「ISR 取走一条消息后唤醒阻塞发送者」没有单独板级读数**（要跑到多任务）；32 位事件集的 **App 侧 SVC 0x21 通道已上板验证**（2026-11-15，`ESET_DEMO` 自检 37 条断言 0 失败，覆盖 OR/AND 掩码、`CLEAR` 粒度、非法参数被拒且状态不动、销毁后全拒），**内核侧 ISR 入口也已上板**（同日 `eset_from_isr_contract`：真 EXTI0 handler 里 `set`，断言 handler 返回时等待者只置 READY 不切换、AND 短板不唤醒、`mask 0` 被拒且状态一位不动，40 条断言 0 失败，并把「去掉 `arkrtos_eset_ready`」做成负对照报 3 条红），**App 侧 `arkrtos_eset_set_from_isr()` 走的那条 SVC 0x21 ABI 也已在真 handler 里跑通**（同日把 EXTI0 优先级降到 IP `0x40`、低于 SVCall 的 `0x10` 之后，在同一次 handler 里发 `SVC 0x21`：参数块放共享 RAM 时返回 0 并唤醒等待者，同一 handler 内改用内核栈参数块则被拒 `-1` 且试探位不落图；`eset_from_isr_contract` 因此扩到 61 条断言、全量 190 条断言 0 失败；两组负对照——无条件放行参数窗口校验报 2 条红、优先级改回复位值 0 后板子复位），**仍未覆盖的组合是「未特权 App 代码 + handler 态」**（本工程没有 App / 驱动注册中断的 ABI），本板 `ARKRTOS_ESET_NUM` 为塞进 120 KB 内核 RAM 降为 4 而非默认 8，测试镜像还为这条用例把 idle 栈从 2 KB 收到 1 KB，SVC-in-ISR 段再加 8 B 静态量，收完 `RW 996 + ZI 121840 = 122836 B`，余量只剩 44 B；等待者容量 **开档在 F427 测试镜像放不下**（`L6406E` 满，108 error），只有 `sync` 76 checks（`WQ-SLOTS=48`）与 `mq`/`sbuf`/`event` 编译层。**多对象探测带超时的等待是 1 ms 轮询**（`ARKRTOS_APP_POLL_MS`），且「探测到就绪 → 调用者取用」之间被别人拿走的窗口不可消除。见 [同步原语与令牌守恒](同步原语与令牌守恒.md) §5.6–§5.9 |

| 用户态等待是"登记 + 轮询"，不是内核阻塞 | 取舍（SVC 隔离的代价） | 非特权侧不能自己挂起，只能登记后由内核在派发点 peek。语义上等价，代价上多一层轮询。见 [同步原语与令牌守恒](同步原语与令牌守恒.md) |
| QEMU 上偶发某次 `clock_gettime` 返回无来源的正值 3 | 缺陷（待定位） | QEMU LA64 上跑 fork 第八档时观察到：夹具忙等读 `CLOCK_MONOTONIC` 的某一次调用，`a0` 回来是 `3`——既不是 `-ENOSYS`、也不是内核记账的毫秒值；内核侧既没有 `rc=3` 记录、也没有 Linux 分发落空的记录，可复现率约 1/4~–1/12 次运行（同一份二进制连跑），没有命中规律。影响面只在“用户态读时钟做忙等”这种构造上；夹具已改为不依赖该读数：子进程等待改成 3 次内核记账的 100 ms 定时 `futex(WAIT)`、一个字都不读用户态时钟，父进程墙钟只读两次且带 8 次重试。未定位项：下一次命中时需要同时留下 `a0/a1` 原值、内核分发路径的计数器与 QEMU 的 `-d int` 记录。见 [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.md) §8.9 |
| 支持的核：Cortex-M3 / M4 / M7 | 欠账（范围外） | 没有 M0/M0+/M23/M33 移植，也没有 TrustZone（SAU/安全世界）。上 M33 要新写 port 与 SVC 重定向 |

## 二、应用形态

| 限制 | 性质 | 说明与证据 |
|---|---|---|
| 应用形态由两个开关各自决定，可单开可同开 | 设计决定 | **窗口/MPU 档**：`.svcapp`（app/driver）、arkc 裸镜像（`app run` / `app flash`）、小程序，都是固定 ABI 镜像（[API参考](api/Ark%20RTOS_API参考.md)、`arkrtos_app_image.h`）。**页表/MMU 档**另有两条：`ARKRTOS_USE_ELF`（原生 ELF：LA64 走 ELF64/PLV3，RV32 走 ELF32/PMP+U 模式，`exec /path/prog`）与 `ARKRTOS_USE_MODLOAD`（VxWorks 式可下载 `.o`，PLV0）。四种组合都编得过；ELF 与模块是**并列的两种模型，不是替代**，见 [MMU平台可下载模块-VxWorks式](MMU平台可下载模块-VxWorks式.md) |
| ELF 与可载模块也**没有**动态链接与共享库 | 取舍（当前实现） | ELF 侧出现 `PT_INTERP` 直接 `ERR_FORMAT`；模块侧只做 `ET_REL` 重定位、不加载依赖。两者都要求地址在装载期可定 |
| 小程序有数量与体积上限 | 取舍 | 并发数 `ARKRTOS_MINI_MAX` 默认 2（1..4，超范围 `#error`）；体积上限受装载窗口约束。见 [小程序设计](小程序设计.md) |
| 小程序崩溃后跨复位禁用 | 设计决定 | 崩溃计数落盘，达到上限后不再自启，要人工/上位机卸载重装；没有自动回滚 |
| C++ 基本不可用 | 欠账 | 目前只有 `arkrtos_app_image.h`、`arkrtos_blk.h`、`arkrtos_fs.h` 三个头带 `extern "C"`；没有全局构造器调用表、没有异常支持 |

## 三、系统服务

| 限制 | 性质 | 说明与证据 |
|---|---|---|
| POSIX 是子集 | 取舍 | 有 pthread / mutex / sem / 时间 / socket / select；没有 signal 的 POSIX 接口、fork、文件锁、进程组（`mmap` 只在 Linux ABI 档有最小文件映射一档，见 [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.md) §8.5）。Linux ABI 档（`ARKRTOS_USE_LINUX_ABI`）下另有一档信号——同任务自我投递与跨任务投递（2026-11-23），都在系统调用返回前送达、无抢占、无实时信号、无 `siginfo`，见 [Linux可执行文件兼容-系统调用ABI](Linux可执行文件兼容-系统调用ABI.md) §7。见 [POSIX与Windows兼容层说明](POSIX与Windows兼容层说明.md) |
| VFS 没有 Unix 权限模型 | 取舍 | 没有属主/权限位/`chmod`；访问控制靠"谁能调到哪个 SVC"。见 [VFS路径命名空间](VFS路径命名空间.md) |
| 文件系统是 littlefs 单卷 + ramfs | 取舍 | 没有日志型 FS、没有多卷并发写、没有配额 |
| Shell 只有一路串口控制台 | 取舍 | 控制台独占 USART1，所以软总线拿不到物理串口（这是"两节点未验证"的直接原因） |
| 真实以太网未打通 | 欠账 | 板级没有 PHY 驱动、MDIO 读写、`eth_` 接口与 RMII 引脚分配，网络路径跑的是回环 netif。见 [lwIP协议栈接入](lwIP协议栈接入.md) §1 |
| 软总线只在板内 loopback 上验证过 | 欠账 | 两节点走真实串口线（两块板 / 板 + PC）未验证；MCU 档位还要工程侧自己给 `-DARK_BUS_*`。见 [软总线接入](软总线接入.md) §7 |

## 四、可靠性与安全

| 限制 | 性质 | 说明与证据 |
|---|---|---|
| 镜像签名是对称 HMAC，不是信任链 | 取舍（当前实现） | 32 字节密钥编进构建，**能签就能验**，没有非对称签名、没有证书链、没有密钥轮换。密钥绝不入库（`*_sign_key_local.h` 被 gitignore） |
| 非对称签名档只换了验签凭据，不是信任链 | 取舍（当前实现） | `ARKRTOS_USE_IMAGE_SIGN_ED25519` 打开后设备只存 32 字节 Ed25519 公钥，逆向设备拿不到签名能力；但公钥是**编进固件**的，怎么保证它没被换掉仍是 SEC-G12 的问题。没有多密钥、密钥版本、撤销，也没有证书链。仍是**安装期一次**校验；验签路径的常量时间性未做侧信道实测（宿主 x86 -O1 约 5.7 ms/verify，不代表板上）。见 [安全认证准备](安全认证准备.md) SEC-G10 行 |
| 信任根只补「公钥从哪来」，不是安全启动链 | 取舍（当前实现） | `ARKRTOS_USE_TRUST_ROOT`（2026-11-25，SEC-G12，**默认关**，强制依赖 `ARKRTOS_USE_IMAGE_SIGN_ED25519`）在开机时把镜像公钥的 SHA-256 钉进板级槽位：槽空则写入（TOFU，首次信任窗口），槽已有值则逐字节比对，不一致即**锁存**并拒绝后续认领（`loader_accept` 返回 `FAIL_STATE`）。它只回答「编进固件的那把公钥还是不是我第一次见到的那把」，不回答：**不验内核**（内核自己的完整性另有 CRC 复核）、**不做镜像验签**（签名仍在认领/安装期用同一把钥验）、**没有证明与轮换**（换钥只能改槽或改固件，无远程证明、无撤销、无密钥版本）、**TOFU 首启窗口开着**（第一次开机前谁都能先占位）、以及 **OTP 的一次性语义未上板验证**——端口层 `arkrtos_port_trust_pin` 是弱符号，默认板子返回「不可用」，此时 sec 报 SKIP 而不是 PASS。槽读写失败同样不锁存（零件缺功能不等于被攻击）。见 [安全认证准备](安全认证准备.md) SEC-G12 行 |
| 默认档签名只在安装期校验 | 取舍 | 默认档运行期不重校验**签名**，已经在跑的镜像被改不会被发现（要靠 MPU 与崩溃账本兜）。认领时复验已有开关 `ARKRTOS_USE_IMAGE_ACCEPT_VERIFY`（2026-11-25，SEC-G09，**默认关**），打开后在 `loader_accept` 里按安装期同一套覆盖规则重算一遍。镜像 **CRC** 另有开机复核（`ARKRTOS_USE_IMAGE_CRC_RECHECK`，默认关，SEC-G17），但那只管「字节有没有坏」，不管「是谁写的」 |
| 认领复验的强度取决于有没有签名档 | 取舍（当前实现） | 同一个 `ARKRTOS_USE_IMAGE_ACCEPT_VERIFY` 有两种读法：有签名档（`ARKRTOS_USE_IMAGE_SIGN`）时是**认证**——覆盖区字节 + 凭据，能发现伪造；**没有签名档时只是完整性**——退回 CRC 反算，而 CRC 没有凭据、谁都能算出一个匹配值，所以那一档挡不住伪造。另一条边界：`runtime_ram_base` 未固化时这条路报「算不出来」（`ERR_PARAM`），既不算通过也不算失败；只有 `ARKRTOS_LOADER_ERR_SIGN` 才是「不合格」。宿主门禁只验纯函数，池扫描里真正的认领与开机时序仍要板子或 QEMU。见 [安全认证准备](安全认证准备.md) SEC-G09 行 |
| 开机 CRC 复核只看池内槽位，且只记不处置 | 取舍（当前实现） | 复核对象是分区表里 `slot_type != FREE` 且 `slot_base != 0` 的槽；`runtime_ram_base` 未固化或镜像头读不出时该份报 `unknown`，只记进 `unknown` 不作结论（既不算通过也不算失败）。发现不一致只报 FAIL 与计数，**不自动停用、不回滚槽位**——处置策略要另立 |
| 真 Flash 的电离位翻转没有读数 | 欠账（验证档位） | 现有全部读数来自 QEMU LA64。QEMU 的「Flash」是普通 DRAM，本板只在 `arkrtos_port_board_init()` 里给镜像池那一段做 RAM 后端模拟（擦成 `0xFF`、按字节写），**不模拟位翻转、不要求写前先擦、不保持跨复位/掉电内容**；真板上「重定位表被写坏一个字节」与长期存放的静默损坏都还没测过 |
| 版本闸门在签名闸门之前 | 设计决定 | 版本不递增时先被 `INSTALL:211` 挡住，走不到 `LOADER:1046` 的验签 |
| 不做差分 OTA / A/B 回滚 | 取舍 | 升级是"装新镜像 + 交接控制权"，出错靠崩溃上限与人工卸载，没有自动回滚 |
| 热切换要求新旧版本**布局全等** | 设计决定 | `ARKRTOS_USE_TASK_SWAP` 整块搬运 RAM / 换 Flash 槽，所以块大小、槽类型、RAM 大小必须逐项相等（`ARKRTOS_SWAP_ERR_LAYOUT`），否则拒绝。布局会变的升级只能走 [无缝升级例程](无缝升级例程.md) 的交接协议 |
| 热切换**会重置数据段** | 实测修正 | 整块搬运确实搬了旧块内容，但镜像入口是启动桩（`__main` / `MINISTART`），落地后重跑 `.data` 初值搬运与 `.bss` 清零，探针实测 `bss` 与 `data` 都回到初值（[详情](无缝升级-双缓冲热切换.md) §5）。所以跨版本状态仍须自己序列化，而不是依赖内存连续 |
| 用过 FPU（Cortex-M）的任务不支持热切换 | 欠账 | 判据在端口层：ARM 的扩展异常帧 `[7]` 是 S6 不是 xPSR，按基本帧改写会写坏现场，故直接拒（`ARKRTOS_SWAP_ERR_FRAME`）；RV32 认 `mepc` 对齐与 `mstatus.MPP`、LA64 认 `ERA` 对齐与 `PRMD.PPLV`，认不出同样拒绝。要支持 FPU 帧须整块搬 S0–S31 |
| 热切换只在 STM32F427 上有真机读数 | 覆盖边界 | 旧块还池、旧槽保留 `LOADED`、反向切回、切换 58~233 ms 四条都是 F427 + DAPLink 的读数；M3/M7 与其它板卡未测。RV32IMAC / LA64 另有 **QEMU 内核自检**读数（5/5 与 3/3 次 `swap: PASS`），但两个入口都在内核镜像里，**不覆盖** PIC / 装载路径，也不是硅片。见 [无缝升级-双缓冲热切换](无缝升级-双缓冲热切换.md) §9 / §9.3 |
| 热切换落地可能违约一次心跳契约 | 已知限制 | 四次切换里观测到一次 `GUARD ... violating 1`（`crash` 记 `slot 0 faults=1 last=heartbeat`）：新镜像在新契约注册之前的那一拍没喂狗。契约不随切换结转，修法未做。见 [无缝升级-双缓冲热切换](无缝升级-双缓冲热切换.md) §9.2 与 §10 |
| 热切换没有自动回滚编排 | 欠账 | `app swap` 保留旧槽只是回滚的原材料；「换了之后 N 秒没心跳就切回去」需要先定「谁判定新版本失败」，未做。见 [无缝升级-双缓冲热切换](无缝升级-双缓冲热切换.md) §10 |
| 热切换一次只允许一份在途 | 设计决定 | 内核只有一个挂起槽，第二个 `mini swap` / `app swap` 返回 `BUSY`；多实例升级要排队 |
| 崩溃上限 3 次即禁用，需人工恢复 | 设计决定 | 见 [崩溃恢复与镜像版本把关](崩溃恢复与镜像版本把关.md) §1.7 |
| 实时性不是硬实时认证口径 | 欠账（口径） | `rt` 给的是 DWT 周期计数的实测值（tick.isr / wake.lo / wake.hi / crit.max），没有 WCET 分析、没有最坏执行时间证明。见 [实时性与最坏延迟](实时性与最坏延迟.md) |
| tickless 只在 F427 上板、电流未测 | 现状 | 板端已实测：`rt` 报 `isr=18605 sleeps=18682 skipped=48728 of 67333 tick(s)`，中断降到 27.6%，静置 20 s 不丢拍；非 ARM 两档从 2026-11-20 起也有 QEMU 读数（LA64 `isr=381 sleeps=126 skipped=376 of 757 tick(s) cap=8`、RV32 `isr=557 sleeps=351 skipped=2319 of 2876 tick(s) cap=8`），但那是模拟器上的调度行为。**功耗三档都没有电流表读数**，只有"睡得更久"这一条间接证据。见 [低功耗与 tickless](低功耗与tickless.md) §8 |
| 安全认证未送审 | 现状 | `sec` 的 T1–T12 是**本地用例自测**，不等于任何一张证书；`docs/安全认证准备.md` 是差距表与缺口寄存器，不是合规声明 |
| shell 认证已做但仍是弱口令、Flash 选项字节只能读不能设 | 部分欠账 | shell 登录 = SEC-G01，**已实现（2026-11-17，默认关，`ARKRTOS_USE_SHELL_AUTH`）**，剩余限制：口令明文过串口、摘要可离线爆破弱口令、硬锁只按复位清、无运行期改口令、不是设备身份（设备身份仍 = SEC-G13）；选项字节**读取**已做（2026-11-13，`sec` 的 `flash.protection` 报真实 RDP/WRP），**设置**（RDP/WRP 写入，不可逆、需产线）= SEC-G04 的另一半。见 [安全认证准备](安全认证准备.md) §7 |
| 每 App 资源配额只覆盖任务表与固定块池，不覆盖通用堆 | 已实现但有明确边界（SEC-G07） | **任务表**（2026-11-24）：`ARKRTOS_USE_APP_QUOTA` + `ARKRTOS_APP_MAX_TASKS`（2026-11-24，默认关），同一 owner 的活任务数到上限后 fork / `clone(CLONE_THREAD)` 回 `-EAGAIN`。三条边界：① 只管任务表——fd 表本来每进程只有 `LX_MAX_FD` 个槽、页帧本来被 App 的 2 MB 地址窗口卡住，这两项一个 App 耗不尽，**内存池仍无按 App 配额**；② 线程 `stack_size == 0`，COW 下栈对分类靠栈顶下方 32 KB 的提示窗口（`LA_PG_THREAD_STACK_HINT`）——那是**分类提示不是栈底保证**，栈守卫与栈溢出判定不得依赖它；③ 并发进程数受 `ARKRTOS_PAGING_APPS_MAX`（本板 2）限制，而 `ERR_QUOTA` 与 `ERR_BUSY` 在 `lx_fork_errno()` 里都映射 `-EAGAIN` ⇒ 返回值上分不出「配额用完」与「地址空间用完」，只能靠 `[appq]` 日志（或「线程不占新地址空间」这条性质）区分。**固定块池**（2026-11-25，`ARKRTOS_APP_MAX_POOL_BLOCKS`，默认 0）：取块按调用者 `app_owner` 记账，超限挂回并返回 0（与池空同值，靠 `quota_fail` 与 `mpool list` 的 `quota` / `owner X held Y` 读数分开），free 时按块表核销；**四条边界**：① 每池最多记 128 块，`block_count>128` 的池整池不记账（如实不受管，不是「不会超」）；② 每池最多同时记 8 个 owner，第 9 个在该池拿不到块（失败关闭）；③ 只记账与限额，**不校验块归属**——free 的合法性仍归原有「落在池内 + 按块对齐」判据；④ 只覆盖固定块池（`arkrtos_mempool`），**通用堆 / 伙伴分配器仍无按 App 配额**，且配额档只在宿主两档 + LA64 编译期验证过，真实 App 打满配额需上板用例。见 [安全认证准备](安全认证准备.md) §7 SEC-G07 |

| 持久审计环的边界 | 取舍（当前实现，SEC-G05） | `ARKRTOS_USE_AUDIT_LOG`（默认关）把九类安全事件写进卷上环形文件（`/audit.bin`，32 B 头 + N×32 B 记录；默认 64 条 = 2080 B）。五条边界：① **只在任务上下文记**——panic 路径不碰文件系统（崩溃现场可能正是文件系统所在），故障溯源仍由崩溃台账承担；② **单写者**——并发 `record()` 回 `BUSY` 并计 `dropped`，不静默合并也不排队（排队要在临界区里做，代价与收益不成比例）；③ **无密钥**——能写这个卷的人可以删改伪造记录，篡改检测要 SEC-G10 或只追加介质；④ **不证跨复位**——宿主卷与 QEMU 的 NOR 都是内存数组，复位即失，跨复位只在真 Flash 上成立，且没做「写到一半掉电」的实测；⑤ 卷上占用 32+N×32 字节，路径是**卷内绝对路径**（`/audit.bin`），不是 VFS 的 `/mnt/...` 形态。见 [安全认证准备](安全认证准备.md) §7 SEC-G05 |
| 回滚白名单的边界 | 取舍（当前实现，SEC-G11） | `ARKRTOS_USE_ROLLBACK`（默认关）允许把已经装在池里的旧版本重新装回去。五条边界：① **RAM-only**——条目复位即失效，这是安全前提不是缺陷（持久条目等于一张永久降级通行证），所以每次开机都要重新武装；② **不判断版本好坏**——「已知良好」是操作员的断言，模块只保证这个断言显式、绑定内容、有界且留痕；③ **不删除坏版本副本**——回滚后两个版本都在池里，起哪一个由自启动 / `app start` 决定；④ **crc32 绑定**依赖整机同一 crc32 实现（与安装期复核同口径），换 CRC 参数这条就失效；⑤ **宿主不证跨复位**——宿主池是内存数组，复位即失，真 Flash 上的降级-回滚链没有上板读数。见 [安全认证准备](安全认证准备.md) §7 SEC-G11 |
| 元件自检的边界 | 取舍（当前实现，SEC-G14） | `ARKRTOS_USE_SELFTEST`（默认关）做四类诊断：RAM 专用窗口图案、CPU 12 条已知答案向量、只读区间 crc 基线、时钟比值交叉校验。四条边界：① **两路时钟同源时看不出晶振偏差**——比的是「本侧节拍」与「本侧计数器」，同一个坏晶振会把两边一起带偏，所以它只能发现粗故障（计数器停、节拍停、分频错），不能当频率基准；② **RAM 只覆盖专用窗口**（`ARKRTOS_SELFTEST_RAM_BYTES`，默认 512 B）——运行期往别人的内存里写图案等于把诊断变成故障注入，整片扫描只能在启动早期做，本模块不声称覆盖；③ **只读项只证明「相对开机基线变了」**——基线是开机那次自己算的 crc32，它发现运行期被改写，发现不了出厂值被伪造（那是签名链的事）；④ **判定是 SKIP 不是 PASS**——板级不实现钩子时那一项报 SKIP，「没测」不会被算成「通过」。见 [安全认证准备](安全认证准备.md) §7 SEC-G14 |
| 共享窗口的只读保护在 RV32 上不存在 | 取舍（当前实现，SEC-G03） | 分区表与崩溃台账所在的共享 RAM 在 ARM（M3/M4/M7）上是「特权可读写 / 非特权只读」（`ARKRTOS_MPU_MEM_RAM_RO`，AP=0b010），所以非特权 App 只能读。**RV32 做不到**：PMP 没有特权位，一条条目对 M 模式同样生效，写成只读会连内核在 SVC 处理程序里那次写一起挡住（SVC 进来时任务那份 PMP 还装着），那是把「修一个洞」换成「装不了镜像」。所以该档编码回读读写，**RV32 上这条缓解不成立**，要真做只能改成「陷入时清 PMP、返回前重装」那种设计（登记为欠账，未做）。LA64 走页表隔离，共享窗口在内核 PLV0 恒等映射里，非特权任务本来就到不了，本项在那一档不改变行为。见 [安全认证准备](安全认证准备.md) §7 SEC-G03 |

## 五、开发与工具链

| 限制 | 性质 | 说明与证据 |
|---|---|---|
| 非 ARM 的仪表频率不是硅片口径 | 现状 | RV32 的 `3108533020 Hz [measured]` 是在 QEMU 内部量出来的，与宿主调度有关；LA64 用的分母是板级常量 `ARKRTOS_PORT_RDTIME_HZ = 100000000`。所以这两档的 µs 数字只在同一档内自洽，**不可横向比较，也不是最坏延迟**；只有 ARM 的 DWT `CYCCNT` 分母来自真实时钟 |
| overlay 的 `/delete-node/` 编码是项目自定义 | 取舍 | dtb 里删子节点用一条零长 `__delete` 标记属性，而 Linux dtbo 的 `/delete-node/` 编码本仓库没有核实到权威原文（本机无 `dtc`、外网取原文被拦），所以**不声称与 Linux dtbo 逐字节一致**；`target = <&label>` 那一半（`__fixups__` + `__symbols__`）是照 Linux 机制做的 |
| 三个 QEMU 目标的覆盖不一样 | 现状 | `board/qemu_riscv32` 与 `board/qemu_loongarch64` **实跑取证**；`board/la32_generic` 只到编译/链接（本机没有 LA32 执行载体）。见 [QEMU模拟器移植与验证](QEMU模拟器移植与验证.md) §8 的三目标矩阵 |
| 没有 gdb remote stub；真板调试只能靠 Keil | 欠账 | 调试走 Keil UV4 + pyocd + `mdkdebug` MCP。QEMU 侧重启一次只要几秒，但没有单步/断点接口，只能靠内核自报读数 |
| 源码编码混用 | 现状约束 | 旧源 GBK、新增 UTF-8，`ci_gate` 的 `encoding` 只保证"每个文件各自可解码"，不保证统一；改 GBK 文件要**字节级补丁**，整文件转码会让 diff 变成全文重写 |
| GCC 例程依赖外部工具链 | 现状 | `GCC构建指南` 里那套需要 `arm-none-eabi-gcc`；仓库不自带，本机不一定装了（构建状态见该指南的"验证状态"） |
| `pyocd` 读数不能当证据 | 现状约束 | 目标**运行中** `read32` 外设返回常量假值（`RCC_CR` / `FLASH_OPTCR` / `GPIOC_ODR` 同一地址族全给 `0x03000000`），必须 `halt` 才是真值；而 `halt → read → go` 实测会把目标复位（看门狗）：`hwsafe` 的 `handover` 归 0、`tick.isr` 从头计数。瞬时状态只能靠 shell 读内核自己的计数，见 [小程序设计](小程序设计.md) §9.6 |
| 无真静态分析、内核整体覆盖率仍空 | 部分欠账（2026-11-17） | 覆盖率：`coverage-host` 已接，但只量宿主用例链接到的那 10 个模块（`tools/coverage_baseline.json`），门槛是「不低于钉住的值」；调度、SVC、驱动、shell 在宿主上没被链接，**内核整体覆盖率仍然没有**，板端也没有采集手段。代码检查：`warn-clean` 已接（21 个宿主可编 TU 的 `-Wall -Wextra -Wshadow` 零告警，已抓到 `sync` 的未初始化指针），但**没有 cppcheck / MISRA / clang-tidy**——本机没装 cppcheck，GCC 4.8 也没有 `-fanalyzer`；依赖架构头的内核文件不在告警门禁范围内 |
