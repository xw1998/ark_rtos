# 固定块内存池（`arkrtos_mempool`）

一句话：**在你自己给的一段内存上切等长块，分配释放都是 O(1)、不会碎、也不依赖堆**。
默认**开**（`ARKRTOS_USE_MEMPOOL=1`）；关掉时创建失败、分配一律返回 0。

- 内核实现：`kernelsrc/src/arkrtos_mempool.c`（整个实现被 `#if (ARKRTOS_USE_MEMPOOL == 1)` 包住，关档只留调用桩）
- 内核内部头：`kernelsrc/include/arkrtos_mempool.h`
- 公开 API：`kernelsrc/include/arkrtos.h` 的 `@defgroup mpool`（`arkrtos_mpool_*`，App 用这一组）
- App 侧封装（走 SVC 0x20）：`kernelsrc/sdk/app_sdk/arkrtos_oslib.c`
- 宿主回归：`kernelsrc/tests/test_mempool_host.c` + `tools/mempool_host_gate.py`
- 板端自检：shell `mpool`（9/9 上板通过，走内核侧 API）

---

## 一、为什么不用堆

| | 堆（变长分配） | 固定块池 |
|---|---|---|
| 最坏分配时间 | 取决于空闲链长度 | **常数**（摘链头） |
| 长时间运行 | 反复申请释放会碎，直到某次失败 | **不会碎**，块大小固定，回收不合并 |
| 容量 | 跑着跑着才知道不够 | 创建时就确定，`block_size × block_count` |
| 额外 RAM | 管理结构另占 | **零**：空闲块自己前几个字节存 next |

代价是"一块就是一块"：要 20 字节却只有 32 字节的块，就浪费 12 字节。这正
是工业设备上能算进实时预算的那种取舍。

## 二、App 怎么用

内存区由**调用者**提供——设备上通常就是一块静态数组，位置和大小都写死在
链接期，所以运行期不存在"分配失败是因为没内存了"这种不可复现的故障。

```c
#include "arkrtos.h"

/* 池的内存区：32 字节一块、8 块。必须是本任务可见的 RAM，且按指针宽度对齐 */
static uint32 g_pool_mem[(32u * 8u) / 4u];
static int32  g_pool;

int main(void)
{
    void *p;

    g_pool = arkrtos_mpool_create("blk", g_pool_mem, 32u, 8u);
    if(g_pool < 0)
    {
        return 1;                  /* 名字重复 / 几何非法 / 表满 / 区不在可见 RAM */
    }

    p = arkrtos_mpool_alloc(g_pool);
    if(p != 0)
    {
        arkrtos_mpool_free(g_pool, p);
    }
    return 0;
}
```

> 池是"谁创建谁负责"：任务下线时内核会把这个任务创建的池的表项回收，反复
> 安装/卸载的 App 不会把对象表占满。表项回收**不动内存区**——那块 RAM 属于
> 调用者。

## 三、接口

App 侧（`arkrtos.h`，全部经 SVC 0x20）：

| 接口 | 说明 |
|---|---|
| `int32 arkrtos_mpool_create(char *name, void *pool, uint32 block_size, uint32 block_count)` | 创建，返回 `>=0` 句柄 |
| `void *arkrtos_mpool_alloc(int32 handle)` | 取一块；**不阻塞**，没有空闲块返回 0 |
| `int32 arkrtos_mpool_free(int32 handle, void *p)` | 归还；指针不属于本池或未对齐则拒绝（池状态不动） |
| `int32 arkrtos_mpool_query(int32 handle, arkrtos_mpool_stat_t *out)` | 取只读快照 |
| `int32 arkrtos_mpool_delete(int32 handle)` | 销毁（只释放表项，内存区不受影响） |

内核侧（`arkrtos_mempool.h`）：同名但带 `_internal` 后缀，另有
`arkrtos_mempool_is_alive()` 与 `arkrtos_mempool_release_task()`。

快照 `arkrtos_mpool_stat_t` 的字段（顺序即 SVC 回填顺序）：

| 字段 | 含义 |
|---|---|
| `name` | 池名（最长 7 字节 + 结束符） |
| `block_size` / `block_count` | 几何 |
| `free_count` | 当前空闲块数 |
| `alloc_ok` / `alloc_fail` | 累计分配成功 / 失败次数（"失败"就是池被取空） |
| `free_bad` | 累计被拒绝的非法释放次数 |
| `peak_used` | 历史最大同时占用块数（定容量的依据） |

## 四、SVC 0x20 的子命令

| 子命令 | 参数块 | 返回 |
|---|---|---|
| 1 create | `p[1]=name, p[2]=pool, p[3]=block_size, p[4]=block_count` | 句柄 / 负值 |
| 2 alloc | `p[1]=handle` | 块地址 / 0 |
| 3 free | `p[1]=handle, p[2]=ptr` | 0 / -1 |
| 4 query | `p[1]=handle, p[2]=out` | 0 / -1 |
| 5 delete | `p[1]=handle` | 0 / -1 |

参数块固定 24 字节（6 个 32 位字），返回码与同步原语同一套（0 成功、负值失败）。

**边界上多做两件事，都是必要的**：

1. **池内存区必须整段落在本任务可见 RAM 内**（SHARE_RAM / SLOT_RAM）。不校验
   就等于让 App 借内核之手在任意地址（含内核 RAM）发块——那是提权，不是分配。
2. **`block_size × block_count` 不许回绕**。`free()` 判断"指针是否在池内"用的
   就是这个乘积，回绕之后池外指针会被算成池内，整条空闲链会被写坏。

## 五、错误口径：宁可拒绝，也不给一个看着能用的池

| 情形 | 行为 |
|---|---|
| `block_size < 指针宽度` / 非指针宽度整数倍 | 创建失败（空闲链要把 next 存进块里） |
| 池首址未按指针宽度对齐 | 创建失败（块地址 = base + k×block_size，base 歪了整池都歪） |
| 区大小回绕 | 创建失败 |
| 名字为空 / 长度 ≥ 8 / 重名 | 创建失败 |
| 对象表已满 | 创建失败 |
| `free()` 传入池外 / 未对齐 / 外来指针 / NULL | 拒绝，`free_bad++`，**池状态一个字节都不动** |
| 池已取空 | `alloc` 返回 0（不阻塞、不抢别人的块） |

最后一行值得单独说：`free()` 绝不做"尽力而为"的插入。错误插入一个越界指针，
会把空闲链连到池外内存上，下一次 `alloc` 返回的就是一个野指针——这种错误在
现场表现为"偶尔死机"，比创建失败难查一百倍。

## 六、配置

| 宏 | 默认 | 作用 |
|---|---|---|
| `ARKRTOS_USE_MEMPOOL` | 1 | 关掉后整块实现不进二进制，SVC 0x20 一律返回 -1，`alloc` 返回 0 |
| `ARKRTOS_MEMPOOL_NUM` | 4 | 对象表项数（每个池占一项）。池占用的 RAM 由调用者提供，不在这里算 |

## 七、证据（分档，不混写）

**已验证**

- 宿主：`kernelsrc/tests/test_mempool_host.c` 共 47 条断言全过（`MEMPOOL-HOST OK`），
  覆盖创建守卫（块太小 / 块未对齐 / 池首址未对齐 / 区大小回绕 / 空名 / 重名 /
  零块数）、16 块的发放与耗尽、**"拒绝的释放必须不动池状态"**、统计字段、
  删除后句柄失效、按创建者任务回收（`release_task(5)` 只带走 5 的池，
  `release_task(0)` 不碰内核/无人认领的池）。已并入 `ci_gate`（`mempool-host`）。
- 真实链接（arm-none-eabi-gcc 12.3.1，默认档、`ARKRTOS_USE_MEMPOOL=1`）：
  H743 FLASH 445996 → **446532 B（+536 B）**，RAM 不变；
  F427 FLASH 257324 → **257728 B（+404 B，98.32%，余 4416 B）**，仍能链接。

**未验证**

- SVC 0x20 的参数校验与用户指针可见性检查：需要内核地址空间与 SVC 边界，
  宿主上看不到。**本机没有板子，未上板验证**——这条通道的结论等级是"仅编译通过"。
- App 侧 `arkrtos_mpool_*` 封装：需要真实 SVC 才能跑，同上。
- shell `mpool` 自检的 9/9 是**改动之前**（内核侧 API）的读数，本轮没有重跑。

## 八、与其他 RTOS 对照

| | FreeRTOS | RT-Thread | Zephyr | 本实现 |
|---|---|---|---|---|
| 固定块池 | `heap_4/heap_5`（变长堆 + 合并） | mem pool（`rt_mp_*`） | `k_mem_slab` | `arkrtos_mempool` |
| 存储区 | 堆内 | 静态数组 | 静态数组 | **调用者提供**（通常静态数组） |
| 额外 RAM | 管理结构 | 管理头 | slab 结构体 | **零**（next 存在空闲块里） |
| 跨特权使用 | 无 | 有 | 有（系统调用） | **SVC 0x20**，参数与内存区都在边界上校验 |
