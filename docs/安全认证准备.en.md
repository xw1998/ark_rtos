# Security Certification Preparation: Assets, Threat Model, Standard Gaps and Gap Register

> Condensed English edition. The Chinese page (安全认证准备.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

## 1. What this document is and is not

**Is**: Ark RTOS's current security capabilities laid out as a checkable table — where the
assets are, where the trust boundaries are, what blocks each threat today, how each
standard requirement maps to "present / needs configuration / not implemented", who owns
each gap and what fixing it touches. Every "present" can be reproduced on the board with
`sec` or an example.

**Is not**: a compliance statement. Every standard listed here is used for **gap
comparison only, never for a conformity conclusion**. A real conformity conclusion can
only be issued by an accredited laboratory against the standard text, with a frozen
version, configuration list and test report as inputs.

Companion pages: the security baseline self-check (`sec`'s 12 items), the memory
protection page §5 (five known boundaries), crash recovery and image versioning, the App
crash hardware-safety page, and the real-time / worst-case latency page.

## 2. Assets (what is being protected)

| ID | Asset | Location | What breaks if changed |
|---|---|---|---|
| A1 | Kernel code and constants | Flash from 0x08000000, read-only | changed = whole-device behaviour untrustworthy |
| A2 | Image pool (App / driver images) | Flash unified image pool | swapped image = swapped application logic |
| A3 | Config-area records | Flash `0x08040000 + 128K`, dual records + CRC | changed = slot mapping / boot item changed |
| A4 | Partition table (runtime shared window) | RAM, shared by kernel and App | changed = the App's world is distorted |
| A5 | App private RAM (code/data/stack) | RAM buddy-allocated blocks, per-task MPU window | out-of-bounds read = leak, out-of-bounds write = hijack |
| A6 | Crash ledger | RAM `.noinit`, survives reset | cleared = crash limit defeated (unlimited retries) |
| A7 | Fault ring (recent fault records) | RAM, cleared on reset | cleared = on-site evidence lost |
| A8 | Hardware outputs (LED/relay/radar …) | board devices | stuck "on" after a crash = physical hazard |
| A9 | Console (serial shell) | UART, 115200 | can install / reboot / stop |
| A10 | Softbus / network links | in-board + Ethernet | forged nodes / replay / man-in-the-middle |
| A11 | Time base (tick, cycle counter) | SysTick / DWT | watchdog window and timeout semantics bypassed |

## 3. Trust boundaries

1. **Privileged / unprivileged**: kernel tasks and the driver framework run privileged;
   Apps run unprivileged under MPU windows. Hardware-enforced, and the only boundary an
   App cannot get around.
2. **Install time / run time**: at install the kernel does whole-image CRC, version
   monotonicity, `image_id` dedup and optional signature verification; at run time
   `arkrtos_loader_accept` checks only the header. **Install time is the only strong
   verification window.**
3. **Before / after reset**: RAM contents die on reset; `.noinit` survives (crash
   ledger); Flash is permanent. The three storage classes have different trust levels and
   must not be mixed in security reasoning.
4. **On-board / off-board**: serial and network are externally reachable surfaces; the
   softbus treats in-board nodes as peers too (frame auth / payload encryption / replay
   window, all off by default).
5. **Trusted / untrusted input**: image files, serial command lines, softbus frames,
   network packets and device return values are all untrusted; the kernel's own
   compile-time constants are trusted.

## 4. Threat model (STRIDE, by trust boundary)

| Threat | Concrete form | Existing mitigation | Status |
|---|---|---|---|
| **S**poofing | impersonating an operator on the serial line | `ARKRTOS_USE_SHELL_AUTH`: the device stores only a salt + `sha256(salt \|\| password)`, locked at boot, `login` unlocks, `TRIES` consecutive failures hard-lock until reset; comparison is a 32-byte whole-block XOR (no early return). **Off by default**; when on, missing salt/digest is a `#error` | implemented (needs configuration, SEC-G01); boundaries below |
| S | install a home-made image under someone else's `image_id`/version | install-time `image_id + version + size + crc` dedup; **all forgeable without a signature** | needs configuration (SEC-G02) |
| S | impersonate a node on the softbus | frame authentication (truncated HMAC-SHA256) + PSK handshake (X25519 + HKDF), off by default | present (needs configuration) |
| **T**ampering | App writes the image pool / config area directly | MPU ROM window read-only; config area written only via kernel SVC | present |
| T | App modifies the partition table (shared window is writable) | the shared window is **read-only to unprivileged code** and writable only by the kernel (MPU profile: AP=0b010; see §5 boundary 2) | **implemented** (SEC-G03, 2026-11-25; RV32 PMP has no privilege bit, so that profile stays writable, see §7) |
| T | power loss / interrupt during install leaves a half image | install writes an `INSTALLING` state; after reset CRC decides INVALID | present |
| T | whole-chip dump after read protection is disabled | RDP/WRP can be read now (2026-11-13, `sec`'s `flash.protection` moved from SKIP to FIND), but RDP **setting** is still missing and needs production-line option-byte programming | **half implemented** (SEC-G04: read = done, set = not implemented) |
| **R**epudiation | nothing records what was installed or what crashed | crash ledger (across resets) + fault ring (cleared on reset) + `audit` structure invariants + persistent audit ring (on the volume, readable after a remount, off by default) | present (needs configuration, SEC-G05) |
| **I**nformation disclosure | unprivileged task reads kernel or another App's memory | per-task MPU windows + privilege stripping | present (78 on-board self-checks) |
| I | serial/network side channels | no authentication, no encryption (softbus payload encryption off by default) | partial (SEC-G06) |
| **D**enial of service | App crashes and restarts forever, eating the CPU | crash limit (default 3) survives reset; over the limit the slot is marked INVALID and not auto-started | present (`90f8d2d`) |
| D | task hangs, system falsely alive | kernel guard + board watchdog | present (needs `ARKRTOS_WDG_ENABLE`) |
| D | memory / handle exhaustion | unified pool + buddy allocation + fixed-block pool + per-App **task count** cap | present (the task table has a per-App cap; the fixed-block pool has a per-App block cap too - both are SEC-G07 and both default off, see §7) |
| **E**levation of privilege | App bypasses privilege through SVC arguments | per-argument checks at the SVC entry + handle validation | present |
| E | an App-registered shell callback runs App code in privileged mode | App registration is **refused** on privilege-separated + paging builds (see §5 boundary 3) | **mitigated (fail-closed)** (SEC-G08, 2026-11-26) |
| E | runtime `loader_accept` accepts unverified payload | re-verified at claim time with the install-time coverage rule (off by default, see §5 boundary 4) | **implemented** (SEC-G09, 2026-11-25, off by default; the CRC-only profile catches damage, not forgery) |
| E | the signature scheme is a **symmetric** pre-shared key; a device holding the key can forge images | limitation already stated in the `arkrtos_sign.h` header | needs rework (SEC-G10) |

## 5. Alignment with existing documents: five known boundaries

1. Only unprivileged tasks are constrained; kernel tasks are not MPU-limited — by design.
2. The shared window (partition table + crash journal) is **read-only to Apps** and writable only by the
   kernel (2026-11-25, SEC-G03). The kernel's writes to it (boot rebuild, install bookkeeping, fault
   journal) already run privileged, and nothing App-side writes it at all, so there is **no** SVC
   hand-off half: if a future feature needs a write it must go through an SVC, never through this
   window. One exception is spelled out in §7: RV32 PMP has no privilege bit, so "kernel may write /
   user may only read" cannot be expressed there.
3. An App-registered shell callback executes App code in privileged context - **fail-closed since 2026-11-26 on "privilege-separated + paging" builds**: such builds refuse App-side registration (`ARKRTOS_USHELL_ERR_PRIV`), because isolated execution (SVC trampoline + unprivileged stack) is not landed yet and allowing it would hand PLV0 to the App. Kernel-task registration and builds without privilege separation are unaffected.
4. `arkrtos_loader_accept` re-verifies the payload only when `ARKRTOS_USE_IMAGE_ACCEPT_VERIFY=1`
   (2026-11-25, SEC-G09), off by default. When on it uses the install-time coverage rule:
   the two relocation deltas of the landed form are undone and the bytes go to the same
   streaming entry. With a signature profile that is **authentication** (forgery is caught);
   **with no signature it is integrity only** -- it falls back to a CRC reverse computation,
   and anyone can compute a matching CRC, so that profile cannot stop forgery. It is off by
   default for cost: the check is only worth its price under the assumption that a pool copy
   may be damaged after installation, and a default build has no signature to protect the
   forgery half anyway.
5. The fault ring is cleared on reset; cross-reset crash counting is carried by the
   `.noinit` ledger.

## 7. Gap register

Severity: **H** = directly exploitable from outside or defeats a security function; **M**
= needs preconditions or has limited impact; **L** = record item.

| ID | Gap | Sev | Impact | Fix shape (cost) | Status |
|---|---|---|---|---|---|
| SEC-G01 | console unauthenticated | H | serial access = install/stop/reboot any image | **implemented (2026-11-17, off by default)**: `ARKRTOS_USE_SHELL_AUTH` locks at boot; device stores only a 16-byte salt and the 32-byte `sha256(salt \|\| password)` digest (injected at compile time by `tools/shell_auth_cred.py`, credential header not committed); comparison is a 32-byte whole-block XOR with no early return; `login` / `logout` / `help` allowed; `ARKRTOS_SHELL_AUTH_TRIES` (default 5) consecutive failures hard-lock until reset; the hook sits before command lookup and also blocks the `./prog` exec fallback. Verified by a real QEMU LA64 run; **honest boundaries**: password crosses the serial line in clear text, an image leak allows offline brute force of weak passwords, the hard lock does not survive reset, and it is not device identity (SEC-G13) | implemented (needs configuration) |
| SEC-G02 | images forgeable without a signature | H | anyone with serial or file-system access can swap the App | turn on `ARKRTOS_USE_IMAGE_SIGN` (configuration) | needs configuration |
| SEC-G03 | shared window writable by Apps | M | the partition-table view can be altered | split a read-only window + SVC-mediated writes (high) | **implemented (2026-11-25, always on wherever MPU/paging isolation is on; no switch)**: the MPU region for shared RAM (partition table + crash journal) moved from "read/write" to the new `ARKRTOS_MPU_MEM_RAM_RO` kind — **privileged read/write, unprivileged read-only**, non-executable, Normal memory. Three reasons it is an attribute change rather than a split/move: (1) the kernel is the *only* writer of that region (boot rebuild, install bookkeeping, fault journal all run privileged) and the only published App-side access is a read; (2) so no SVC hand-off half exists — if that ever changes the write must go through an SVC, not through widening this window again; (3) splitting the window into two RAM regions costs two power-of-two aligned MPU regions for a few hundred bytes. **Honest boundaries**: (1) **RV32 PMP has no privilege bit** — a PMP entry applies to M-mode too, so making it read-only would also block the kernel's own store inside an SVC; that port therefore encodes read/write and the mitigation is only real on ARM (M3/M4/M7), see `已知限制.md` §4; (2) LA64 isolates with page tables and the share window lives in the kernel's PLV0 identity map, which an unprivileged task cannot reach anyway, so behaviour there is unchanged; (3) this stops "an App rewrites the view", not "someone who can run privileged code rewrites it" — that needs a trust root (SEC-G12); (4) the crash journal shares the region, so it is kernel-write-only too (it always was). | implemented (MPU profile) |
| SEC-G04 | no RDP/WRP set or read | H | Flash can be wholly dumped or rewritten | ① **read done** (board `arkrtos_port_flash_protection()` + weak-symbol fallback, on-board verified 2026-11-13) ② RDP/WRP **setting** still missing: option-byte unlock/erase/program/reset, and RDP 0→1 is irreversible, needs the production line | half implemented (read = FIND effective, set = not implemented) |
| SEC-G05 | no persistent audit log | M | no post-hoc provenance | **implemented (2026-11-25, off by default)**: `ARKRTOS_USE_AUDIT_LOG` + `ARKRTOS_AUDIT_LOG_RECORDS` (default 64, range 8 512) + `ARKRTOS_AUDIT_LOG_PATH` (default `/audit.bin`, on the already-mounted littlefs volume). The volume holds a ring file: a 32-byte header (magic/version/cap/head/wrapped/seq_next/crc) plus N x 32-byte records (magic/seq/tick/kind/owner/code/spare/crc32); nine event kinds = ring open, root mount, image accepted / refused, exec start / exit, auth failure / lockout, quota refuse. **The record lands before the header does**, so a power cut can only truncate a record outside the readable window; the header is rescanned (two streaming passes, no on-stack slot table - 512 records cost no stack) only when it is broken, and a torn tail record is reported as `BAD_CRC` instead of a half event; a failed write rolls the RAM ring position back and counts `dropped`. One writer at a time: a concurrent `record()` returns `BUSY` and counts `dropped` (nothing is silently merged). Read it with `auditlog` / `auditlog dump [n]`; gate = `tools/audit_log_gate.py` (OFF default / zero-symbol OFF object / seven wired files compile with the switch ON / host cases 231+4 / judge self-check). **Honest boundaries**: (1) task context only - the panic path does not touch the filesystem, crash provenance stays with the crash ledger; (2) no key material - anyone who can write the volume can delete or forge records (detecting that needs SEC-G10 or an append-only medium); (3) the host volume is a RAM array and QEMU's NOR is RAM too, so **this gate does not prove survival across a reset** - only real flash can; (4) off by default, and the OFF build is an empty TU. See `已知限制.md` section 4 | implemented (needs config) |
| SEC-G06 | serial/network unencrypted | M | side channel and replay | reuse softbus encryption (medium) | partial |
| SEC-G07 | no per-App resource quota | M | one App can exhaust the pool | **the task-table half is implemented (2026-11-24, default-off)**: `ARKRTOS_USE_APP_QUOTA` + `ARKRTOS_APP_MAX_TASKS` (default 8). Each ELF load gets a non-zero owner id; fork and clone(CLONE_THREAD) inherit it; when the owner's **live** task count reaches the cap the creation fails with -EAGAIN (plus one `[appq] refused …` line — the only trace that separates "quota exhausted" from "address space exhausted"). Scope fixed: the fd table is already capped per process (`LX_MAX_FD`) and page frames are already bounded by the App's own address window, so neither can be exhausted by one App. **The memory-pool half is implemented (2026-11-25, default-off)**: `ARKRTOS_APP_MAX_POOL_BLOCKS` (0..64, default 0; `depends on ARKRTOS_USE_APP_QUOTA && ARKRTOS_USE_MEMPOOL`). Every block taken from a fixed-block pool is charged to the calling task's `app_owner`; a take past the cap puts the block **straight back on the free list** and returns 0 (the same value an empty pool returns), with a separate `quota_fail` counter and the `mpool list` readout (`quota N blk/owner`, `owner X held Y`) telling them apart; kernel tasks (`app_owner==0`) are never limited. **Accounting bounds, stated so they are not over-read**: (1) at most 128 blocks per pool are tracked, and a pool with `block_count>128` is not charged at all; (2) at most 8 owners are tracked per pool - a 9th owner cannot get a block there (fail closed, not silently allowed); (3) it only accounts and limits, it does **not** validate block ownership - free() legality stays with the existing inside-the-pool + block-aligned check; (4) it covers the fixed-block pool (`arkrtos_mempool`) only, not the general heap/buddy allocator. Readout: `tools/mempool_host_gate.py` builds two profiles (default + quota with `-DARKRTOS_APP_MAX_POOL_BLOCKS=2`) and both must print `MEMPOOL-HOST OK`. The LA64 quota build proves compile-time wiring only; **a real App draining its quota needs a board test**. See section 4 of `已知限制.md` | implemented (needs config) |
| SEC-G08 | shell callback runs App code privileged | H | privilege escalation | SVC trampoline + unprivileged stack (high) | **mitigated (fail-closed, 2026-11-26)**: the trampoline always called `func(argc, argv)` directly on the console task's stack, i.e. at PLV0; on a build with `ARKRTOS_USE_PRIV=1 && ARKRTOS_USE_PAGING=1` that App code therefore held kernel privilege. Isolated execution (start a PLV3 worker plus a `syscall` return trampoline) is expensive and needs new App-side stack and ABI fields, so it is not landed yet; until then the hole is **closed by refusal**: `arkrtos_shell_ext_register()` reads the calling task's `is_priv` and returns the new error code `ARKRTOS_USHELL_ERR_PRIV` (-6) when it is 0, leaving the registry untouched. Kernel tasks (`is_priv != 0`, the board/driver path) register with no change in meaning, and builds without privilege separation (Cortex-M / MPU profiles, which have no such hole absent TrustZone) behave exactly as before. Readings: the `ushell-host` item in `tools/ci_gate.py` now compiles **the same** `test_shell_ushell_host.c` **twice** - the profile with `-DARKRTOS_USE_USHELL_APP_CB=1` runs the existing 141 registry assertions, the one without it runs 17 refusal assertions (App refused / kernel accepted / table untouched / unregister still works) on the paging + privilege-separated board header; both must be green. The ushell entry in `tools/coverage_gate.py` pins that macro explicitly, so the baseline reading does not move. **Honest boundaries**: (1) this **turns the feature off** rather than implementing it safely - App-defined shell commands are unavailable on privilege-separated + paging builds until isolated execution lands; (2) the temporary `arkrtos_kernel_ushell_active` allowance inside the trampoline is still there (kept for kernel-registered commands) and can only be narrowed together with isolated execution; (3) `ushell_func_alive()` still only recognises partition-table slots, not the paging space / ELF window; (4) fail-closed covers the registration entry only - kernel rows already registered are unaffected; (5) the `stm32f427` example's App-side `arkrtos_shell_cmd_register()` has no privilege separation, so it is unchanged. See §5 boundary 3 |
| SEC-G09 | runtime `loader_accept` does not verify payload | M | affects only the runtime load path's trust assumption | share install-time verification (medium) | **implemented (2026-11-25, off by default)**: switch `ARKRTOS_USE_IMAGE_ACCEPT_VERIFY`. Claiming an image no longer rests on the single `state == VALID` word: the check is re-run with the **same coverage rule and the same reverse path** as at install time. Flash holds the *relocated* form, so the two deltas are undone first (`delta_rom = (base + payload_offset) - nominal_base`, `delta_ram = runtime_ram_base - nominal_ram_base`) and the bytes are fed to the same streaming entry the installer uses, `arkrtos_sign_stream_*`; with no signature profile it falls back to `arkrtos_loader_crc_recheck()`. The reverse computation and the feeding both live in one function (`loader_nominal_body()`); CRC and signature differ only in who consumes the bytes -- a second copy of the relocation decoding would be a second place to drift. **The two profiles are not equally strong**: with a signature (HMAC / Ed25519) forgery is detected; with CRC only it detects **damage**, because a CRC has no credential and anyone can compute a matching one. The reading is pinned: `arkrtos_loader_sign_recheck()` returns `ARKRTOS_LOADER_ERR_SIGN` only for 'does not match'; every other negative (`ERR_PARAM` / `ERR_SIZE` / `ERR_RELOC`) must be read as 'could not tell' -- an unpatched `runtime_ram_base`, for instance, reports 'cannot compute', never 'matched'. **P2 (needs production line and key infrastructure)**
The **verification side** of asymmetric signing has landed (SEC-G10, 2026-11-25): Ed25519, the device stores only
the public key, and signing happens at pack time with an offline private key. What still needs the production line is
the **key lifecycle** - public-key distribution, rotation and revocation, private-key custody - and pinning the key
somewhere it cannot be replaced. Still in P2: device identity (SEC-G13) + RDP setting (SEC-G04) + secure boot
**where the key lives** also has a configurable path now (SEC-G12, partial, 2026-11-25): the key may come from board OTP, its digest is pinned into a one-time slot, and a mismatch latches and refuses claiming. real deployment still requires operations to choose a strong password — a process item, not
a code item.

## 10. Three statements that must not be overstepped

1. **Do not say "compliant with a standard".** Every table here is a gap comparison; a
   "present" in the judgement column means only "the corresponding capability exists on
   this product with on-board evidence", not standard conformity.
2. **Do not treat `sec` PASS as a certification conclusion.** It checks whether the
   mechanism exists, not whether an attack succeeds; attack-surface verification relies on
   `APP_BAD` and penetration testing.
