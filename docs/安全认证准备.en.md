# Security Certification Preparation: Assets, Threat Model, Standard Gaps and Gap Register

> Condensed English edition. The Chinese page (安全认证准备.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

## 1. What this document is and is not

**Is**: Ark RTOS's current security capabilities laid out as a checkable table — where the
assets are, where the trust boundaries are, what blocks each threat today, how each
standard requirement maps to "present / needs configuration / not implemented", who owns
each gap and what fixing it touches. Every "present" can be reproduced on the board with
`sec` or an example.

**Is not**: a compliance statement. Every standard listed here is used for **gap
comparison only, never for a conformity conclusion**. A real conformity conclusion can
only be issued by an accredited laboratory against the standard text, with a frozen
version, configuration list and test report as inputs.

Companion pages: the security baseline self-check (`sec`'s 12 items), the memory
protection page §5 (five known boundaries), crash recovery and image versioning, the App
crash hardware-safety page, and the real-time / worst-case latency page.

## 2. Assets (what is being protected)

| ID | Asset | Location | What breaks if changed |
|---|---|---|---|
| A1 | Kernel code and constants | Flash from 0x08000000, read-only | changed = whole-device behaviour untrustworthy |
| A2 | Image pool (App / driver images) | Flash unified image pool | swapped image = swapped application logic |
| A3 | Config-area records | Flash `0x08040000 + 128K`, dual records + CRC | changed = slot mapping / boot item changed |
| A4 | Partition table (runtime shared window) | RAM, shared by kernel and App | changed = the App's world is distorted |
| A5 | App private RAM (code/data/stack) | RAM buddy-allocated blocks, per-task MPU window | out-of-bounds read = leak, out-of-bounds write = hijack |
| A6 | Crash ledger | RAM `.noinit`, survives reset | cleared = crash limit defeated (unlimited retries) |
| A7 | Fault ring (recent fault records) | RAM, cleared on reset | cleared = on-site evidence lost |
| A8 | Hardware outputs (LED/relay/radar …) | board devices | stuck "on" after a crash = physical hazard |
| A9 | Console (serial shell) | UART, 115200 | can install / reboot / stop |
| A10 | Softbus / network links | in-board + Ethernet | forged nodes / replay / man-in-the-middle |
| A11 | Time base (tick, cycle counter) | SysTick / DWT | watchdog window and timeout semantics bypassed |

## 3. Trust boundaries

1. **Privileged / unprivileged**: kernel tasks and the driver framework run privileged;
   Apps run unprivileged under MPU windows. Hardware-enforced, and the only boundary an
   App cannot get around.
2. **Install time / run time**: at install the kernel does whole-image CRC, version
   monotonicity, `image_id` dedup and optional signature verification; at run time
   `arkrtos_loader_accept` checks only the header. **Install time is the only strong
   verification window.**
3. **Before / after reset**: RAM contents die on reset; `.noinit` survives (crash
   ledger); Flash is permanent. The three storage classes have different trust levels and
   must not be mixed in security reasoning.
4. **On-board / off-board**: serial and network are externally reachable surfaces; the
   softbus treats in-board nodes as peers too (frame auth / payload encryption / replay
   window, all off by default).
5. **Trusted / untrusted input**: image files, serial command lines, softbus frames,
   network packets and device return values are all untrusted; the kernel's own
   compile-time constants are trusted.

## 4. Threat model (STRIDE, by trust boundary)

| Threat | Concrete form | Existing mitigation | Status |
|---|---|---|---|
| **S**poofing | impersonating an operator on the serial line | `ARKRTOS_USE_SHELL_AUTH`: the device stores only a salt + `sha256(salt \|\| password)`, locked at boot, `login` unlocks, `TRIES` consecutive failures hard-lock until reset; comparison is a 32-byte whole-block XOR (no early return). **Off by default**; when on, missing salt/digest is a `#error` | implemented (needs configuration, SEC-G01); boundaries below |
| S | install a home-made image under someone else's `image_id`/version | install-time `image_id + version + size + crc` dedup; **all forgeable without a signature** | needs configuration (SEC-G02) |
| S | impersonate a node on the softbus | frame authentication (truncated HMAC-SHA256) + PSK handshake (X25519 + HKDF), off by default | present (needs configuration) |
| **T**ampering | App writes the image pool / config area directly | MPU ROM window read-only; config area written only via kernel SVC | present |
| T | App modifies the partition table (shared window is writable) | none (see §5 boundary 2) | **not implemented** (SEC-G03) |
| T | power loss / interrupt during install leaves a half image | install writes an `INSTALLING` state; after reset CRC decides INVALID | present |
| T | whole-chip dump after read protection is disabled | RDP/WRP can be read now (2026-11-13, `sec`'s `flash.protection` moved from SKIP to FIND), but RDP **setting** is still missing and needs production-line option-byte programming | **half implemented** (SEC-G04: read = done, set = not implemented) |
| **R**epudiation | nothing records what was installed or what crashed | crash ledger (across resets) + fault ring (cleared on reset) + `audit` structure invariants | partial (SEC-G05) |
| **I**nformation disclosure | unprivileged task reads kernel or another App's memory | per-task MPU windows + privilege stripping | present (78 on-board self-checks) |
| I | serial/network side channels | no authentication, no encryption (softbus payload encryption off by default) | partial (SEC-G06) |
| **D**enial of service | App crashes and restarts forever, eating the CPU | crash limit (default 3) survives reset; over the limit the slot is marked INVALID and not auto-started | present (`90f8d2d`) |
| D | task hangs, system falsely alive | kernel guard + board watchdog | present (needs `ARKRTOS_WDG_ENABLE`) |
| D | memory / handle exhaustion | unified pool + buddy allocation + fixed-block pool | present (no per-App quota, SEC-G07) |
| **E**levation of privilege | App bypasses privilege through SVC arguments | per-argument checks at the SVC entry + handle validation | present |
| E | an App-registered shell callback runs App code in privileged mode | none (see §5 boundary 3) | **not implemented** (SEC-G08) |
| E | runtime `loader_accept` accepts unverified payload | trust install time only (see §5 boundary 4) | design trade-off (SEC-G09) |
| E | the signature scheme is a **symmetric** pre-shared key; a device holding the key can forge images | limitation already stated in the `arkrtos_sign.h` header | needs rework (SEC-G10) |

## 5. Alignment with existing documents: five known boundaries

1. Only unprivileged tasks are constrained; kernel tasks are not MPU-limited — by design.
2. The shared window (partition table + crash log) is still writable by Apps.
3. An App-registered shell callback executes App code in privileged context.
4. `arkrtos_loader_accept` does not verify payload CRC / signature (verified at install,
   not at run time).
5. The fault ring is cleared on reset; cross-reset crash counting is carried by the
   `.noinit` ledger.

## 7. Gap register

Severity: **H** = directly exploitable from outside or defeats a security function; **M**
= needs preconditions or has limited impact; **L** = record item.

| ID | Gap | Sev | Impact | Fix shape (cost) | Status |
|---|---|---|---|---|---|
| SEC-G01 | console unauthenticated | H | serial access = install/stop/reboot any image | **implemented (2026-11-17, off by default)**: `ARKRTOS_USE_SHELL_AUTH` locks at boot; device stores only a 16-byte salt and the 32-byte `sha256(salt \|\| password)` digest (injected at compile time by `tools/shell_auth_cred.py`, credential header not committed); comparison is a 32-byte whole-block XOR with no early return; `login` / `logout` / `help` allowed; `ARKRTOS_SHELL_AUTH_TRIES` (default 5) consecutive failures hard-lock until reset; the hook sits before command lookup and also blocks the `./prog` exec fallback. Verified by a real QEMU LA64 run; **honest boundaries**: password crosses the serial line in clear text, an image leak allows offline brute force of weak passwords, the hard lock does not survive reset, and it is not device identity (SEC-G13) | implemented (needs configuration) |
| SEC-G02 | images forgeable without a signature | H | anyone with serial or file-system access can swap the App | turn on `ARKRTOS_USE_IMAGE_SIGN` (configuration) | needs configuration |
| SEC-G03 | shared window writable by Apps | M | partition-table view can be altered | split a read-only window + SVC-mediated writes (high) | not implemented |
| SEC-G04 | no RDP/WRP set or read | H | Flash can be wholly dumped or rewritten | ① **read done** (board `arkrtos_port_flash_protection()` + weak-symbol fallback, on-board verified 2026-11-13) ② RDP/WRP **setting** still missing: option-byte unlock/erase/program/reset, and RDP 0→1 is irreversible, needs the production line | half implemented (read = FIND effective, set = not implemented) |
| SEC-G05 | no persistent audit log | M | no post-hoc provenance | audit ring log to Flash (medium) | not implemented |
| SEC-G06 | serial/network unencrypted | M | side channel and replay | reuse softbus encryption (medium) | partial |
| SEC-G07 | no per-App resource quota | M | one App can exhaust the pool | quota field + allocation check (low) | not implemented |
| SEC-G08 | shell callback runs App code privileged | H | privilege escalation | SVC trampoline + unprivileged stack (high) | not implemented |
| SEC-G09 | runtime `loader_accept` does not verify payload | M | affects only the runtime load path's trust assumption | share install-time verification (medium) | design trade-off |
| SEC-G10 | signature uses a symmetric key | H | reverse-engineering the device yields signing capability | switch to asymmetric (Ed25519/ECDSA) + device stores only the public key (high) | not implemented |
| SEC-G11 | no explicit rollback policy | M | version monotonicity blocks downgrade, but also blocks "roll back to a known-good version" | rollback allow-list / counter (medium) | not implemented |
| SEC-G12 | no root of trust / secure boot chain / attestation | H | prerequisite for PSA L2+ | BootROM → kernel → image verification chain (high, chip-dependent) | not implemented |
| SEC-G13 | no device identity | M | no device-level authentication possible | per-device key or per-device certificate (medium, needs production line) | not implemented |
| SEC-G14 | no RAM/Flash/clock self-test | M | insufficient 61508 diagnostic coverage | boot self-test + runtime patrol (medium) | partial |
| SEC-G15 | no WCET analysis | M | worst-case response time cannot be proven | static analysis + hardware tracing (high) | not implemented |
| SEC-G16 | no fault injection / tamper detection | L | physical attack surface | voltage/clock monitoring, external watchdog (high) | not implemented |
| SEC-G17 | image CRC not rechecked at boot | L | silent corruption can only be caught at install | **implemented (2026-11-18, switch `ARKRTOS_USE_IMAGE_CRC_RECHECK`, off by default, `depends on ARKRTOS_USE_SECCHECK`)**: what lies in Flash is the post-relocation-patched bytes, while the header's `crc32` was computed over the nominal form (at packing time), so the on-disk bytes cannot be compared directly. `arkrtos_loader_crc_recheck()` derives the ROM/RAM deltas from the header's `runtime_ram_base` and the current location, subtracts the patches entry by entry back to the nominal form and recomputes the whole range. Three outcomes are reported separately and never mixed: `0` consistent = PASS (`checked=%u bad=%u unknown=%u first=%u`), `-5` genuinely inconsistent = FAIL, any other negative = not computable right now (`unknown`, e.g. `runtime_ram_base` not yet finalised), counted as neither PASS nor FAIL. An empty pool reports `no pool image to recheck`; a pool with images where none can be computed reports `checked=0 unknown=%u: no image could be rechecked` — both are **SKIP, not PASS** (reporting pass without verifying one real image is false green). **The same round fixed a real defect**: `arkrtos_loader_load_buffer()` wrote the relocation table into the pool without folding it into `crc_written`, while the read-back comparison covers "header + table + payload" ⇒ any image with `reloc_count > 0` installed through it always reported `-5` and left an UNCOMMITTED fragment in the pool (exposed the first time QEMU could really install an image) | implemented (needs configuration; with the switch off this row's SKIP text is character-identical to before the change) |

T1–T9 and T11 were done on F427 with readings kept. All 12 cases were completed on F427
(2026-11-12 added T10/T12). **T13 has only QEMU LA64 readings** (2026-11-18): there is no
DAP probe here, so "corrupt one byte in the pool and reset" on a real board was not done;
it is therefore "mechanism and the three-outcome reporting verified, real Flash bit flip
not verified". The initial T1 snapshot is the default profile (8 PASS / 2 FIND / 2 SKIP);
after enabling the signature the same `sec` becomes 9 PASS / 1 FIND / 2 SKIP — the
difference is exactly the `images.signature` row.

**How T10 was done (without leaving a back door)**: rather than adding a "stop feeding the
watchdog" command to the product firmware (a back door from a certification standpoint),
the debugger clears SysTick's `ENABLE` bit: no tick interrupt → `arkrtos_kernel_tick_body()`
does not run → `arkrtos_guard_tick()` does not feed. Reset source is always read from
`RCC_CSR` (a hardware bit), never from whether the serial line prints a banner — `pyocd`
resets the target on every session start, so judging reset from the serial line yields
false conclusions.

**How T12 was done (key not committed)**:

1. The key header `arkrtos_sign_key_local.h` lives in the project's `Core/Inc` (already on
   the IncludePath) with a single line `#define ARKRTOS_IMAGE_SIGN_KEY { 0x.., ... }`; the
   filename is kept out of the repository by the `*_sign_key_local.h` rule in `.gitignore`.
2. The kernel side opens the channel with a **quote-free** switch:
   `-DARKRTOS_SIGN_KEY_LOCAL=1`, and `arkrtos_features.h` does
   `#if defined(ARKRTOS_SIGN_KEY_LOCAL) → #include "arkrtos_sign_key_local.h"`.
   **Do not write `-DARKRTOS_SIGN_KEY_HEADER=\"xxx.h\"`**: when Keil's Define box holds two
   quoted macros in the same field, the later `ARKRTOS_BOARD_CONFIG` does not get through
   and `drvflash.c` / `arkrtos_port.c` fail with 39 undefined `uint32_t` / `SCB` errors
   (measured; reverted to the quote-free switch). The channel itself is guarded by a new
   set of probes in `tools/sign_host_gate.py` (`sign-host` item in `ci_gate`): with the
   switch, exactly 32 bytes must arrive; without it, not a single byte may (default
   profile unchanged).
3. Pack two images: same payload, same `image_id` (= payload CRC32), differing only in the
   signature area. Note the **version gate (`INSTALL:211`) runs before the signature gate**,
   so the test image must carry a version above the installed copy (here `2.0.0.0`),
   otherwise it is rejected as "version not increasing" before signature verification is
   ever reached.
4. Afterwards restore the `uvprojx` Define (the project must not keep
   `ARKRTOS_SIGN_KEY_LOCAL`, which would reference an uncommitted header and break other
   people's builds), rebuild and reflash the default profile; `sec` returns to 8 PASS /
   2 FIND / 2 SKIP.

a code item.

Penetration testing, side channel, fault injection (SEC-G16), WCET analysis (SEC-G15),
formal assessment against IEC 62443-4-2 / PSA L2.

## 10. Three statements that must not be overstepped

1. **Do not say "compliant with a standard".** Every table here is a gap comparison; a
   "present" in the judgement column means only "the corresponding capability exists on
   this product with on-board evidence", not standard conformity.
2. **Do not treat `sec` PASS as a certification conclusion.** It checks whether the
   mechanism exists, not whether an attack succeeds; attack-surface verification relies on
   `APP_BAD` and penetration testing.
3. **Do not read "off by default" as "absent".** Signature, softbus authentication,
   payload encryption and the watchdog are all off by default; before certification a
   configuration **explicitly turning these on** must be frozen and all §8 cases re-run on
   that configuration.
