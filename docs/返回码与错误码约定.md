# 返回码与错误码约定

想知道某个内核函数失败时那个负数是什么意思，看这一页。

本页回答三件事：**名字从哪来**、**值和以前一不一样**、**哪些数不是错误码**。

## 1. 约定

内核 API 的失败返回一律是**负整数**，0 表示成功，正数表示"成功且带了信息"（如读到的字节数）。这个口径本轮没有动过，以后也不打算动。

本轮补的只是**名字**：

1. 每个模块在**自己的头文件**里定义一组 `ARKRTOS_<模块>_ERR_<原因>`，纯 `#define`，无额外依赖。
2. **每一个宏的值，逐处等于改动前那里写死的那个数字。** 不是重新设计码值，是给既有数字起名。
3. **多个名字共用 `(-1)` 是有意的**，不是漏了错值。分名的目的是让调用方和读代码的人知道"这是哪一种失败"，而不是让每种失败有不同的数。
4. **值不得单独修改。** 想区分某两种失败，是新增一个值域方案（需要动 ABI 和全部调用方），不是把某个宏从 `-1` 改成 `-3`。改一个宏的值等于悄悄改了对外契约。
5. 错误码宏放在各头文件的**功能开关之前**（`timer` / `mempool` / `softbus` 尤其注意），这样 `ARKRTOS_USE_XXX=0` 时 `#else` 分支的桩函数也能用同一套名字。

### 1.1 两套前缀：`_ERR_*` 与 `_FAIL_*`

后 15 个模块里，loader 已有自己的 `ARKRTOS_LOADER_ERR_*`（-1..-18）、mini 已有 -18/-19/-20、fs 的失败原因全记在 `arkrtos_fs_last_error()` 里。硬套一套 `_ERR_*` 会出现「同一个名字在不同返回点展开成不同的值」，所以命名分成三族：

| 前缀 | 含义 | 用在 |
|---|---|---|
| `ARKRTOS_<模块>_ERR_<原因>` | **负值本身携带原因**，读返回值就能分类 | mq / event / timer / mempool / blk / dev / softbus / vfs / guard / sec / ptable / sync / task / hwsafe / installer / rt / log / cfg / layout / apprun / trace |
| `ARKRTOS_<模块>_FAIL_<原因>` | 全部回 `-1`，**原因在函数分支 / last_error 里，值不携带信息** | loader（既有 `ARKRTOS_LOADER_ERR_*` 是 -1..-18，不能动） |
| `ARKRTOS_<模块>_FAIL` | 单值 -1，模块整体只有一个失败返回 | fs（原因看 `arkrtos_fs_last_error()`） |

判据很简单：**看那个 `return -N;` 的 `N` 在原代码里是不是恒等于 -1 且调用方从不按值分支**。是则 `_FAIL_*`，否则 `_ERR_*`。

`mini` 与 `sbuf` 是混合情形：它们既有的 -18/-19/-20（mini）与 -1/-2/-3/-5/-6（sbuf）全部保留原值不改，本轮只给**原值为 -1 的那些返回点**补 `_ERR_*` 名字，两套并存。

## 3. 这些名字不是错误码

下面是**哨兵**（sentinel）或幂等提示，调用方会拿它当分支条件，不要当失败处理：

1. **`ARKRTOS_MQ_WAIT_INFINITE`（-1）/ `ARKRTOS_SBUF_WAIT_INFINITE`（-1）**：`remain_ms` 的"无限等待"标记。所以 `-1` 同时是"无限等待"和若干个失败原因——**同一个数在不同参数位置上语义不同**，靠参数位置区分，不靠值区分。
2. **`ARKRTOS_MQ_WAITER_DUP` / `ARKRTOS_EVENT_WAITER_DUP` / `ARKRTOS_SYNC_WAITER_DUP` / `ARKRTOS_SBUF_WAITER_DUP`（均 -2）**：登记等待者时发现该任务已在队列里。这是"无需重复登记"的提示，不是错误。
3. **`ARKRTOS_CRASH_INDEX_NONE`（-1）**：`arkrtos_crash_mini_find()` 找不到记录时的下标哨兵，不是错误码。
4. **`ARKRTOS_TASK_NONE`（-1）**：调度器返回"没有就绪任务 / 不需要切换"。它和 `ARKRTOS_TASK_ERR_*` 共用 -1，靠**返回位置的语义**区分，不靠值。相邻的 `255` 是"优先级无候选"哨兵，也不要当优先级用（见 `ARKRTOS_TASK_ERR_PRIORITY` 的注释）。

同理 `ARKRTOS_EVENT_WAITER_ABSENT`（-1）与 `ARKRTOS_SYNC_ERR_NOTFOUND`（-1）表示"摘除时本来就不在队列里"，是幂等语义，通常可忽略。

## 4. 不得"统一"的既有契约

补名字的时候最容易犯的错是"顺手把 -1 都改成 -2"（或反过来），下面这些在历史上就是那个值，**改了会破坏调用方**：

1. **mq 的 send 超时是 `-1`，recv 超时是 `ARKRTOS_SYNC_ERR_TIMEOUT`（-2）。** 两侧不对称是既有契约，见 `同步原语与令牌守恒.md`。
2. **dev 注册时"名字或驱动指针为空"是 `ARKRTOS_DEV_ERR_ARG`（-2）**（第 43 行），注册重名是 `ARKRTOS_DEV_ERR_EXIST`（-2）。这两个值特意保留为 -2；曾经误映射成 -1，导致 `arkrtos_dev.o` 涨 4 B、总 Code 220094→220098，是体积账抓出来的。
3. **vfs 的 `-1` 不得改成既有 `ARKRTOS_VFS_EINVAL`（-2）。** VFS 有自己的 `E*` 体系（`-2` 起），新增的 `ARKRTOS_VFS_ERR_*` 全部是 -1，两者并存：`E*` 是给调用方判断的 POSIX 风格错误，`ERR_*` 是内核内部返回点的名字。
4. **ptable 的 `ARKRTOS_PTABLE_ERR_MAGIC` 是 -2，不是 -1。** 镜像头魔数校验失败在历史上就是 `-2`，调用方按 -2 判"不是我们的镜像"。
5. **sync / sbuf 的 `WAITER_DUP` 是 -2**，且与 `ARKRTOS_SYNC_ERR_TIMEOUT`（-2）**同值不同义**：dup 是"已经登记过"，timeout 是"等超时"，调用方按调用点区分。
6. **hwsafe 的 `ERR_ARG` 与 `ERR_EXIST` 都是 -2**（设备名/所有者非法、同名已注册），与 `ERR_PARAM`/`ERR_NOSLOT`/`ERR_NOTFOUND`/`ERR_OWNER`（均 -1）并存。
7. **loader 的既有 `ARKRTOS_LOADER_ERR_*` 是 -1..-18，一个值都不动。** 本轮新增的 `ARKRTOS_LOADER_FAIL_*` 全部是 -1，只给原本就写 `-1` 的返回点起名；**不许**把裸 `-1` 映射成 `-4`（SIZE）或 `-6`（ERASE）之类的"更精确"的值——那会改掉对外返回码。
8. **mini 的 -18/-19/-20 与 sbuf 的 -1/-2/-3/-5/-6 全部保留原值**，本轮只补 -1 档的名字。

## 5. 刻意不改：littlefs 回调契约

`kernelsrc/src/arkrtos_vfs_lfs.c` 里还有 2 处裸 `return -1;`，**它们不是内核错误码**，是 littlefs 目录遍历回调的"停止遍历"约定（返回非 0 即停，具体值无意义）。给它们起个 `ARKRTOS_*_ERR_*` 名字会误导后来者以为那是可判别的失败原因，所以保留原样并在注释里写明。这也是全仓最后 2 处裸 `return -N`。

## 7. 验证口径

只到"0 Error"不算验证完。第二批做了四层：

1. **值一致性脚本**：逐文件比对 `HEAD` 版本里 `return -N;` 的数字与替换后宏展开的值，`checked 234 / mismatch []`。
2. **体积逐项比对**：默认档内核 Keil 构建 `Code=220094 RO-data=19198 RW-data=896 ZI-data=120852`，与第一批提交后的基线**逐项相同**（名字不参与代码生成，理论上必然相同，这里是实测确认没有被 `#define` 意外带进表达式）。

   关于构建里那几条 warning：已用 `git worktree add` 在 `6bb3fa7`（本批之前）做了一次 **`-r` 全量重建**取证——基线同样是 `0 Error(s)`，warning 是 `ark_vfs_procfs.c` 的 1 处 `#111-D statement is unreachable`、3 处 `#167-D uint32_t*/uint32*`，外加全量时才出现的 `arkrtos_context.S` 的 `A1581W Added 2 bytes of padding`。**这几条与本轮改动无关**，且该文件本轮一行未改。
3. **例程构建**：7 个 Keil 例程 + 4 个 GCC 例程链接通过，尺寸与上一轮一致。
4. **关档语法检查**：把 `MQ/TIMER/MEMPOOL/BLK/FS/VFS/VFS_LFS/SOFTBUS/SECCHECK/MINIAPP/PROCFS/MINI/APPPACK/SBUF/RTSTAT` 全设 0，**全部 38 个 `.c` 逐个 `arm-none-eabi-gcc -fsyntax-only`，38/38 exit 0**，证明 `#else` 桩也能看到宏。判 PASS 只看 exit code——`arkrtos_app_image.h` 的 `variably modified` 是 ARMCC 扩展在 GCC 下的既有 warning，不是错误。

**验证档位：仅编译通过 + 体积逐项相同。本轮未上板复验**（改动只涉及名字，不涉及控制流，但按口径仍应记为未上板）。

## 8. 新增一个返回点怎么写

1. 先看那个 `return -N` 属于哪种失败。
2. 到模块头文件里找现有最贴近的 `ARKRTOS_<模块>_ERR_*`；**同义就复用，不要为每一行新建一个名字**。
3. 确实没有合适名字时，才新增一个宏，值仍写 `(-1)`（除非有历史原因必须是别的值），并写一行注释说明判据。
4. 不要为了"看起来更精细"而改值。
5. 改完跑上面第 7 节的四层验证。
