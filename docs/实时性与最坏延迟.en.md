# Real-Time Behaviour and Worst-Case Latency

**[简体中文](实时性与最坏延迟.md) | English**

> Condensed English edition. The Chinese page (实时性与最坏延迟.md) is normative: every
> number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page
> wins. This page adds no new claim and no new measurement.

## 0. In one sentence

Use the DWT cycle counter, take timestamps on the real scheduling path, and report the
**worst** value rather than the average.

All numbers come from a real board (STM32F427 @ 96 MHz, 2 kHz tick), not from estimates or
simulation. And up front: **this is not a formal WCET analysis**. It gives "the worst value
seen on this board, with this configuration, in this firmware, during this measurement
window". Formal WCET needs static path analysis plus a worst-case interrupt nesting model,
which this module does not provide. Section 3 pins down the three boundaries.

## 1. Why tick counts are not good enough

Counting SysTick milliseconds gives you a resolution of 500 µs at this configuration, while
the quantities of interest — one wake-up, one critical section — are tens of microseconds.
Measuring those with a 500 µs ruler yields 0 or 1.

DWT `CYCCNT` is a free-running 32-bit cycle counter: **one count is 10.4 ns** at 96 MHz. Its
limits are equally explicit:

- 32 bits wrap every **≈ 44.7 s** at 96 MHz. Every timestamp in this module is used only as a
  **difference inside one measurement**, far below the wrap period; using `CYCCNT` as absolute
  time is the caller's problem.
- `DEMCR.TRCENA` and `DWT_CTRL.CYCCNTENA` must both be 1. What those bits actually do on
  hardware is section 5, where one trap only appears on a real board.

If the counter is unavailable the module **reports "unavailable" honestly**
(`counter: NOT running`, empty readings in `rt show`) and never falls back to tick counts to
produce a plausible-looking number.

## 2. What each row measures

| Row | Meaning | Start → end |
|---|---|---|
| `tick.isr` | Body of the tick interrupt handler | entry of `SysTick_Handler` → exit (see caveat below) |
| `wake.lo` | Wake-up latency of a low-priority task | "the tick at which it should have woken" → the task actually running |
| `wake.hi` | Wake-up latency of a high-priority task | timestamp before `sem_post` returns → first line of the high-priority task after it gets a timestamp |
| `switch` | The switch alone, excluding the tick body | last line of the tick body (`arkrtos_rt_tick_exit()`) → first instruction of the woken task |
| `crit.max` | Worst critical-section occupancy | `arkrtos_port_enter_critical()` → `arkrtos_port_exit_critical()`, outermost only |

Each row reports `n / min / avg / max` in cycles plus a µs conversion (from the measured
clock and `ARKRTOS_TICK_PERIOD_US`). Two more figures:

- **`jitter`**: signed difference between consecutive `tick.isr` intervals and the nominal
  tick period, in cycles. It answers "does the tick itself jitter", not "how late is a task".
- **`late_n`**: samples woken more than a full tick late. Those are **counted separately and
  excluded from `wake.*`** — they were blocked by higher priority work for a long time, not
  delayed by the wake path, and mixing them into min/max only poisons the reading.
- **`skip_n` on the `switch` row**: samples dropped because the tick sequence numbers did not
  pair up (see 4.1). Their start point is the previous tick's `tick_end`, so the difference has
  no physical meaning; dropping is better than counting.

### The `tick.isr` caveat (important)

`tick.isr` covers only `arkrtos_kernel_tick_handler()`. The context switch is outside it:
`ARKRTOS_SWITCH_TASK()` merely pends PendSV and returns, and the actual register save/restore
happens in the PendSV exception after the tick interrupt exits.

So **`tick.isr` is not "tick interrupt from entry to exit"**. Measuring the full interrupt
including the switch would require moving the timestamp down to PendSV entry, which this
module does not do (listed as not done in section 7). Calling it "tick ISR body" rather than
"total tick interrupt cost" is deliberate.

### Why `crit.max` is often `no sample`

`crit.max` only records when the kernel actually enters a critical section. `rt run` clears
the statistics, and the wake path (`task_wait` timing out) does not go through
`arkrtos_port_enter_critical()`:

```
rt run            → crit.max (no sample)
rt reset
mpool test        → enters critical section
crash             → enters critical section
rt show           → crit.max n=16
```

The table footer states it: a row with no samples means "no such event since the last reset",
not "costs 0".

## 3. Three boundaries (written into the implementation and here)

1. **Not formal WCET.** Readings are measured maxima. Paths that were never exercised have
   their worst case absent from this table. Adding pressure (more tasks, more interrupts,
   longer critical sections) makes these numbers larger, which is normal.
2. **`crit.max` includes measurement overhead.** Entering and leaving a critical section costs
   a few extra register reads and writes, on the order of a dozen cycles, but it is genuinely
   part of the measured object, so "pure critical-section cost" cannot be claimed.
3. **DWT is shared with `mdk_trace`.** Both only set enable bits (`|=`), never clear the
   counter, and never disable bits the other needs, so they can be on together. Conversely:
   any new code that **clears CYCCNT** breaks this module's timestamps and manufactures
   jitter artefacts of order −21 M. That is a hard constraint in the implementation.

Also: **with the feature off, everything is dead code.** `ARKRTOS_USE_RTSTAT` defaults to 0,
the five `#if` blocks never reach the build, and size and behaviour are unchanged; the helper
task stack (1024 B) does not exist either.

## 4. On-board measurements

Conditions: STM32F427VGTx, 96 MHz, 2 kHz tick (500 µs), `ARKRTOS_USE_RTSTAT=1`, flashed via
DAP (`pyocd flash -t stm32f427vg`) and read over the serial console on 2026-11-12.

| Row | N | min (cyc) | avg (cyc) | max (cyc) | min / avg / max (µs) |
|---|---|---|---|---|---|
| `tick.isr` | 7770 | 410 | 603 | 6870 | 4.3 / 6.3 / 71.6 |
| `wake.lo` | 3000 | 4356 | 4393 | 22074 | 45.4 / 45.8 / 229.9 |
| `wake.hi` | 3000 | 3978 | 5047 | 7727 | 41.4 / 52.6 / 80.5 |
| `crit.max` | 16 | 63 | 102 | 294 | 0.7 / 1.1 / 3.1 |
| `jitter` | 7770 | −2181 | — | +2167 | −22.7 / +22.6 |

A second `rt run 200` gave `wake.lo` 2988/3908/4367 cyc and `wake.hi` 3944/5066/7654 cyc.
`late_n` was 0 in both runs — no sample was blocked for a whole tick under this firmware and
load.

How to read it:

- `tick.isr` averages 6.3 µs and peaks at 71.6 µs against a 500 µs tick, leaving margin; the
  worst case happens when the shell, memory pool and similar paths coincide.
- Most of `wake.lo`'s 45.8 µs average is the chain "tick expires → ready table updated in the
  interrupt → interrupt exits", not scheduler lookup. The single 229.9 µs outlier is a one-off,
  not steady state.
- `wake.hi`'s 41.4 µs minimum says the fixed cost of "`sem_post` → first line of the
  high-priority task" is at this level; the 80.5 µs maximum occurs when a tick interrupt
  inserts itself.
- `jitter`'s ±22 µs is the tick being pushed by other interrupts and critical sections, the
  same source as `tick.isr`'s worst case.

These are **measurements on this board and configuration**; another chip, clock or set of
interrupt sources changes them. Do not treat them as device specifications.

### 4.1 Same definition as RT-Thread: the `switch` row (added 2026-11-14)

The problem with the table above is not the numbers but the **start point**: `wake.lo` starts
at tick-interrupt entry and therefore contains the whole tick body (guard, timer list, delay
list, accounting). Mainstream RTOS benchmarks report "scheduling decision point → first
instruction of the selected task", which excludes the tick body. Comparing them means
measuring the same interval with two different rulers.

Facts about the RT-Thread side: there is no published measurement script; the 睿擎 industrial
platform's website states conclusions (< 1 µs task response, < 5 µs jitter) without describing
how they were measured; the community practice is two threads ping-ponging a semaphore with
DWT (or tick timestamps) recording "release → peer's first line", taking typical values.
Therefore the only thing this repository can align with is **the definition of that interval**,
not a reproduction of an unpublished script.

Hence the `switch` row: the start point moves from "tick interrupt entry" to "last line of the
tick body". `wake.lo − switch` is then the tick body itself, so readers need not guess which
segment a third-party number measures.

**Three build profiles, same source** (STM32F427 @ 96 MHz, 2 kHz tick, `rt run 3000`, n=3000):

| Profile | Code (B) | `switch` min / avg / max (cyc) | min / avg / max (µs) | `wake.lo` avg (cyc) | `tick.isr` avg (cyc) |
|---|---|---|---|---|---|
| Default (all instrumentation on) | 220290 | 983 / 3651 / 20960 | 10.2 / 38.0 / 218.3 | 4434 | 619 |
| Only `MDK_TRACE` off | 217714 | 744 / 744 / 745 | 7.75 / 7.75 / 7.76 | 1538 | 548 |
| All instrumentation off | 211726 | 711 / 714 / 2841 | 7.4 / 7.4 / 29.6 | 1392 | 442 |

Reading the three rows:

- **The default profile's 38 µs is not the cost of switching.** Turning `MDK_TRACE` off takes
  `switch` from 3651 to 744 cycles, **2907 cycles (30.3 µs) less**. That profile also turns
  `SCHED_STAT` off through the Kconfig dependency (see 6.1), so the delta mixes the per-switch
  `mdk_trace_send()` with sched_stat bookkeeping; the two were **not measured separately**, and
  from the magnitude the delta belongs to trace — but that is inference, not a reading. The
  remaining instrumentation modules (guard / audit / stack check / cpu load / stack usage)
  account for only 744 → 714, i.e. 30 cycles — **that one is a direct reading**. In other
  words, in the default profile the dominant real-time cost is **observability**, not the
  scheduler.
- **The 744-cycle row barely jitters** (min and max differ by one cycle). With trace removed
  the switch path is deterministic; the 218 µs max in the default profile comes from being
  pushed aside by other interrupts (the board's USB CDC SOF, once per millisecond) — again
  inference, no isolated interrupt-off run was taken.
- **`switch` and `wake.lo` differ by the tick body**: 4434 − 3651 ≈ 783 cycles in the default
  profile, the same order as `tick.isr`'s 619 (plus the delay list and ready table on the
  waking tick). The numbers are consistent.

**Why the filter exists**: if the tick body takes the "switch away directly" path
(`FAST_TICK_SWITCH`, no PendSV), the woken task runs first, `arkrtos_rt_tick_exit()` has not
executed yet, and `tick_end_cyc` still holds the previous tick's value. Subtracting then yields
an unexplainable number (an earlier build reported an impossible 145-cycle minimum). The fix is
pairing by tick sequence number: a sample counts only when the recorded end-of-tick-body and
the current tick share a sequence number; otherwise it is dropped into `skip_n`. All 3000
samples in this run had `skip=0`, i.e. that path was not taken.

**Comparable or not, stated explicitly**:

| What you want to compare | Which row | Note |
|---|---|---|
| Same class as RT-Thread "task response" | `switch` (**average**) | Same start point: scheduling decision → task's first instruction |
| Jitter | `switch` min/max, or `jitter` | RT-Thread's jitter is the spread of the same quantity |
| Task wake-up including the tick body | `wake.lo` | **Not** comparable with RT-Thread response numbers: one tick body extra |
| Synchronous wake-up plus preemption | `wake.hi` | Starts before `sem_post`, includes call overhead |
| Interrupt service body | `tick.isr` | Excludes PendSV and exception-exit cost |
| Longest interrupt-off window | `crit.max` | Only has samples after a real critical section |

Three limits still hold:

1. **Only cycle counts are comparable across clocks.** 744 cycles is 7.75 µs at 96 MHz; the
   same 744 cycles at 400 MHz is 1.86 µs. That is arithmetic, **not a measurement on a second
   board**; do not quote the converted value as a reading.
2. **96 MHz here comes from the internal RC (HSI) through the PLL** with 3 wait states;
   an external crystal would have a different jitter shape.
3. **The board also runs a USB CDC shell**, whose SOF fires every 1 ms as a higher-priority
   interrupt. The default profile's 218 µs max and `tick.isr`'s 78 µs max share that source.

Putting these numbers beside RT-Thread's claim needs one more step: those 744 cycles include
address and privilege isolation. The next section separates them.

### 4.2 Comparison with RT-Thread's claim (added 2026-11-14)

This section only separates **what can be verified** from **what cannot**, then states how far
the local numbers can be aligned.

#### Verifiable: the vendor's own wording

RT-Thread's "platform features" page (睿擎 platform, page dated 2025-09-17) says:

> Hard real-time kernel: the 睿擎 platform integrates the RT-Thread professional kernel, with
> microsecond-level interrupt latency (≤1 µs), microsecond-level task response (≤1 µs) and very
> low jitter (≤5 µs).

This is the only set of real-time numbers the vendor has written down.

#### Not verifiable: every measurement condition

That sentence does not state:

- which core, at what clock;
- which definition (GPIO toggle / DWT cycle count / tick timestamp), and where start and end are;
- sample count and statistics (typical, average, or worst case);
- the test load (a single ping-pong pair, or an interrupt storm).

No measurement script is published either. The community practice — two threads ping-ponging a
semaphore, DWT recording "release → peer's first line", taking typical values — is **a common
practice**, not proof that those numbers were produced that way.

#### Platform facts: not even the conversion is determined

The SoC in the 睿擎 board is RK3506J; public material (the 睿擎 SDK V1.3.0 note posted by an
official RT-Thread account, 2025-08-30) describes **3×Cortex-A7 @ 1.5 GHz + 1×Cortex-M0 @
200 MHz**, with "CPU 2 as the hard real-time core" that real-time tasks can own exclusively.
So where that 1 µs lands changes the conversion by 7.5×:

| If 1 µs was measured on | Equivalent cycle ceiling |
|---|---|
| 200 MHz Cortex-M0 | ≤ 200 cycles |
| 1.5 GHz Cortex-A7 | ≤ 1500 cycles |

**The vendor does not say which side, so not even the direction of "who is faster" is
determined.** This is not a gap in this repository but in the published information; closing it
requires asking the vendor or measuring on the same platform.

#### On this side: decomposing the cost (three builds, differing only in two board macros)

The 744 cycles above are a switch **with address and privilege isolation**. RT-Thread's public
kernel does not rewrite per-task MPU regions, so to compare, both layers must be stripped and
measured. The method: temporarily set `ARKRTOS_USE_PRIV` / `ARKRTOS_USE_MPU` to 0 in
`board/stm32f427/arkrtos_board_config.h` (these are not Kconfig symbols; they derive from
`ARKRTOS_ARCH_HAS_MPU`, so the board header is the shortest path), build three times with all
other sources identical, then restore. **This is a measurement variant, not a recommended
configuration, and is not committed.**

| Profile | Code (B) | `switch` min / avg / max (cyc) | min / avg (µs) |
|---|---|---|---|
| `MDK_TRACE` off (MPU + PRIV on) | 217714 | 744 / 744 / 745 | 7.75 / 7.75 |
| `MDK_TRACE` off, PRIV off | 217646 | 723 / 725 / 2826 | 7.53 / 7.55 |
| `MDK_TRACE` off, PRIV + MPU off | 216546 | 413 / 423 / 10988 | 4.3 / 4.4 |

Each ran `rt run 3000` with n=3000 and `skip=0`. Two **direct readings** follow:

- **Privilege switch (`ARKRTOS_USE_PRIV`) ≈ 20 cycles / 0.2 µs**: 744 − 723 ≈ 20 cycles.
  It is that small because `arkrtos_port_set_thread_priv()` compares CONTROL first and writes
  plus ISB only when the level actually changes; both ping-pong sides are kernel tasks at the
  same level, so it is nearly free.
- **MPU address isolation (`ARKRTOS_USE_MPU`) ≈ 300 cycles / 3.1 µs**: 423 → 723. The two tasks
  have different stack regions, the region set changes on every switch, all 8 regions must be
  compared and will not match, so 24 register writes plus one DSB/ISB are paid in full. **This
  is the difference between "switching with address isolation" and "switching without it"**,
  not an implementation-quality difference between two vendors' features.

The `switch` max column must not be taken seriously: 10988 (114 µs) and 2826 (29 µs) are
one-off outliers from the board's USB CDC SOF (once per millisecond). min/avg are the cost of
this path.

#### Clock conversion: arithmetic, not measurement

423 cycles (the profile without MPU/PRIV) at different clocks:

| Clock | Equivalent |
|---|---|
| 96 MHz (this board) | 4.4 µs |
| 168 MHz (common F4) | 2.5 µs |
| 200 MHz (睿擎 M0) | 2.1 µs |
| 480 MHz (H7) | 0.88 µs |

On this table, 423 cycles may be "slower than the claimed 1 µs" or "faster" depending on the
premise the other side never published. **Cycle counts are the only cross-platform quantity,
but how many cycles counts as fast depends on that unpublished premise.** Cortex-A7 and
Cortex-M4 executing 423 cycles each does **not** mean the same amount of time — A7 is
superscalar, out-of-order, deeply pipelined, and the same C code has a completely different
instruction count. Cross-core conversion is doubly unreliable.

#### Second-hand numbers explicitly not trusted

The following were found in search and are used as evidence for nothing:

- A CSDN "STM32 measured 8 RTOSes" post — carries an AI-generated syndication marker;
- A CSDN "RT-Thread real-time optimization practice" post (claims 1.2 µs @168 MHz M4) — same marker;
- A CSDN Q&A (claims ~8 µs for 16 general-purpose registers @168 MHz) — matches no implementable kernel;
- An aggregator page (claims M3 < 5 µs @72 MHz) — the method uses `rt_tick_get()`, whose
  resolution is one tick, so **microseconds are physically unmeasurable** that way.

Trusting them would mean putting a number of unknown provenance and self-contradictory method
next to a local measurement and drawing an authoritative-looking but indefensible conclusion.
Per this repository's rule, the answer there is "cannot verify".

The only credible academic source was verified at bibliographic level: 徐丽华、王宜怀、奚圣鑫,
"Analysis of the RT-Thread context switch mechanism on Cortex-M4", *Computer Applications and
Software* 2025, 42(1): 213-216, 302, DOI `10.3969/j.issn.1000-386x.2025.01.030`. Its abstract
gives no comparable cycle count and the full text was not obtained, so it is at most
circumstantial evidence that someone did instruction-level analysis — not a source of numbers.

#### Conclusion

**Definitions aligned, values not directly comparable.**

- What aligns is the **interval definition**: this board's `switch` row and the mainstream
  definition are both "scheduling decision point → first instruction of the selected task".
  That comparability is what this round actually achieved.
- The values still cannot be listed side by side: the other side's 1 µs lacks platform and
  statistics, while the local figure is 96 MHz internal RC, 2 kHz tick, 3000-sample average.
  Putting 4.4 µs and 1 µs on one line yields only the **formal statement** "4.4× apart", not
  "how much the implementations differ".
- The only clean comparison path is: port the RT-Thread open-source kernel to **the same F427,
  the same 96 MHz, the same compiler**, and measure its `switch` with the same ping-pong + DWT
  script. **That has not been done** — only then would "who is faster under identical
  conditions" be answerable.

## 5. Two traps that only appear on a real board

### 5.1 The debugger disconnecting clears `TRCENA`, freezing CYCCNT

Observed: after `pyocd` flashes the firmware and disconnects, `DEMCR` reads back
`0x00000000` and `CYCCNT` sits around 1e7 (about 0.1 s after boot), so every reading looks like:

```
raw 10654352 -> 10654352
back-to-back 0 cyc
1 ms delay = 0 cycles
```

Root cause: **the debugger clears `DEMCR.TRCENA` when it disconnects**, and CYCCNT stops
counting. The software is not wrong; the wrong assumption is "enable it once at boot and it
stays on".

Fix: `arkrtos_rt_counter_alive()` rewrites `DEMCR |= (1u<<24)` and `DWT_CTRL |= 1u`
**before every measurement**, then runs a short loop comparing two successive `CYCCNT` values.
`rt run` calls `arkrtos_rt_init()` to re-arm first; `rt show` prints `counter: running` or
`counter: NOT running`.

In a real product with no debugger attached this never happens; **once a DAP is used for
debugging or flashing, this must be handled**.

### 5.2 Never clear CYCCNT

The first version wrote `DWT_CYCCNT = 0` in `arkrtos_port_cyccnt_init()` "so statistics start
at zero". The result: after `last_tick_cyc` had been recorded, the counter was zeroed and the
next tick computed `jitter = −21756208`, invalidating every statistic.

CYCCNT is free-running and **differences are sufficient**; clearing only manufactures jitter
artefacts. The clearing statements were removed from all three port layers; it is a hard
constraint, not a style preference.

## 6. How to use it

### 6.1 Enabling

Two paths, pick one:

- Kconfig: `config ARKRTOS_USE_RTSTAT` (`config/kconfig/Kconfig.features`), `default n`.
- Direct define: `-DARKRTOS_USE_RTSTAT=1`.

The F427 `ARKRTOS_TEST` project currently **builds with it on** (`Define` contains
`ARKRTOS_USE_RTSTAT=1`); that is an intentional "built-in profile": a default-off feature that
no project ever compiles will keep its bugs hidden. Turning it off saves roughly 2.7 KB Code
plus 1.2 KB ZI (including the 1024 B helper task stack).

`ARKRTOS_USE_SCHED_STAT` (the scheduling statistics rows) **depends on
`ARKRTOS_USE_MDK_TRACE`**: those counters and `arkrtos_trace_last_cycles()` live inside the
trace block of `arkrtos_trace.c`. The dependency is now in Kconfig
(`depends on ARKRTOS_USE_MDK_TRACE`). Previously it was missing, so "trace off, sched_stat on"
compiled but failed at link time with `L6218E: Undefined symbol arkrtos_sched_stat_close` — a
real defect found while doing the subtraction experiments in 4.1, now fixed.

### 6.2 Shell commands

```
rt                 # same as rt show
rt show            # print the five rows + jitter + counter state
rt reset           # clear statistics (counter untouched)
rt run [n]         # re-arm + clear, then n wake and n preempt measurements; default 200, range 1..5000
```

`rt run` **actively creates** measurements: it calls `measure_wake(n)` then
`measure_preempt(n)`, so those two rows have equal `n` equal to the value given; `tick.isr`'s
`n` depends only on elapsed time.

On failure the error code from `arkrtos_rt_last_error()` is printed:

| Code | Meaning |
|---|---|
| 1 | `sem_hi` creation failed |
| 2 | `sem_ack` creation failed |
| `4 - tid` | helper task registration failed (tid negative) |

### 6.3 C API

`#include "arkrtos_rt.h"` (the whole block is empty when `ARKRTOS_USE_RTSTAT` is 0, so call
sites must guard with `#if`):

```c
arkrtos_rt_init();                       /* arm the counter + reset statistics */
arkrtos_rt_measure_wake(200);            /* wake-up latency over 200 task_wait(1ms) */
arkrtos_rt_measure_preempt(200);         /* 200 high-priority preemption latencies */
arkrtos_rt_row_t rows[ARKRTOS_RT_ROWS];
uint32 n = arkrtos_rt_snapshot(rows, ARKRTOS_RT_ROWS);
int32 jmin, jmax; uint32 jn;
arkrtos_rt_jitter(&jmin, &jmax, &jn);
arkrtos_rt_reset();
```

`snapshot()` returns how many rows were filled; row names are static strings and need no
freeing. Time conversion uses `unsigned long long` (the kernel has no `uint64` type; that trap
was hit once).

## 7. What this gate guards, and what is not done

### The gate

`tools/rtstat_syntax_gate.py`, wired into `tools/ci_gate.py` (item 18).

The reason is direct: `ARKRTOS_USE_RTSTAT` defaults to 0, and apart from the two test projects
the tree builds at the default profile, so those five `#if` blocks **never pass through any
compiler**. Breaking them stays green until someone enables the feature on a board. The gate
runs `armclang -fsyntax-only -DARKRTOS_USE_RTSTAT=1` over 7 files (4 kernel + the m3/m4/m7
ports), and fails instead of skipping when armclang is absent.

One detail that must be written down: compiling the port layer needs
`-DARKRTOS_BOARD_CONFIG="arkrtos_board_config.h" -DSTM32F427xx -DUSE_HAL_DRIVER`. Without the
last two, `stm32f4xx.h` exits with `#error` at device selection, `core_cm4.h` is never included,
and the reported error is "`SCB` undeclared" — a bogus error unrelated to the change under
test. Those macros are mandatory in the gate, not decoration.

**The gate only checks syntax.** Whether DWT actually runs on a board, and whether the readings
are trustworthy, is outside it.

### Not done (stated honestly)

- **Formal WCET**: no static path analysis, no worst-case interrupt nesting model.
- **Full interrupt latency at port level**: `tick.isr` excludes the PendSV context switch;
  `switch` covers "scheduling decision → first task instruction", but **interrupt pin to first
  ISR line** (normally measured with a GPIO toggle or scope) is not covered, so do not use
  `tick.isr` to represent it.
- **Long-term drift and temperature/voltage effects**: the table is a single run; no hour-level
  statistics, no corner-condition sweep.
- **Multi-priority stress combinations**: `wake.hi` only measures a single priority-1 helper
  task; the full preemption chain is not exercised, and wakes are not measured with many
  interrupts occurring at once.
- **m3/m7 are only syntax-verified**: no on-board readings; F427 is m4.
- **Critical-section breakdown for mempool/shell paths**: `crit.max` is a single total, not
  split per call site.

These are the applicability limits of the current readings, not a promise of later work:
conclusions outside the ranges above are not produced by this module.

## 8. How much of a "real-time guarantee" these readings support

"Has measurements" and "has a real-time guarantee" are different propositions. The former gives
a maximum on this board and configuration; the latter demands a bound independent of the
runtime scenario. This section separates them so the former is not passed off as the latter.

Conditions: STM32F427VGTx, 96 MHz, 2 kHz tick (500 µs budget), `rt run 3000`.

### 8.1 What the readings do support

| Path | Measured (min / avg / max) | Share of tick (avg / max) |
|---|---|---|
| Context switch itself (all instrumentation off) | 711 / 714 / 2841 cyc = 7.4 / 7.4 / 29.6 µs | 1.5% / 5.9% |
| Context switch itself (trace only off) | 744 / 744 / 745 cyc = 7.75 / 7.75 / 7.76 µs | 1.6% / 1.6% |
| Context switch itself (default, all instrumentation) | 983 / 3651 / 20960 cyc = 10.2 / 38.0 / 218.3 µs | 7.6% / 44% |
| Longest interrupt-off `crit.max` | 63 / 102 / 294 cyc = 0.7 / 1.1 / 3.1 µs | 0.2% / 0.6% |
| Tick ISR body `tick.isr` | 410 / 603 / 6870 cyc = 4.3 / 6.3 / 71.6 µs | 1.3% / 14% |
| Full tick wake chain `wake.lo` | 4356 / 4393 / 22074 cyc = 45.4 / 45.8 / 229.9 µs | 9.2% / 46% |
| Tick jitter `jitter` | −22.7 … +22.6 µs | 4.5% |

Five statements that can be made directly:

1. **The switch path is deterministic, not statistical.** With trace off, `switch` min and max
   differ by one cycle (744 / 745). That is the foundation of real-time behaviour, not a nice
   average.
2. **Jitter comes from interrupts, not the scheduler.** The ±22 µs of `jitter` and the 71.6 µs
   max of `tick.isr` share a source: being pushed by higher-priority interrupts such as USB SOF
   and shell paths. The scheduler itself contributes no jitter.
3. **No sample missed a whole tick.** All 3000 samples waited less than one tick, `late_n = 0`.
   That is "the worst case did not slip a tick", not "the average kept up".
4. **The dominant cost is observability, not scheduling.** The default profile's 38 µs switch
   returns to 7.75 µs with trace off and 7.4 µs with all instrumentation off. When real-time
   margin is short, there is an existing knob, no architecture change needed.
5. **The cost is priced.** Address isolation (MPU) 300 cycles / 3.1 µs and privilege switch
   20 cycles / 0.2 µs (direct readings in §4.2). How hard a real-time bound you need determines
   what you pay or which layer you switch off.

### 8.2 What cannot be called a guarantee

| Item | Current state |
|---|---|
| Identity of the worst value | "The maximum in this board, this firmware, this sampling run", not a formal bound |
| `wake.lo`'s 229.9 µs | A single outlier, not steady state, and certainly not a bound |
| USB CDC shell on the board | SOF inserts every 1 ms; no control run with it removed |
| Clock source | Internal RC (HSI) via PLL, 3 wait states; jitter shape with an external crystal untested |
| Formal WCET / interrupt nesting model | None (see §7 "Not done") |
| Interrupt pin → first ISR line | Not measured (`tick.isr` excludes it and must not represent it) |
| Long-term drift, temperature/voltage | Not done |
| Full multi-priority preemption chain | Not done (`wake.hi` measures one priority-1 helper task only) |

### 8.3 The boundary in one line

**"Under the current configuration, the worst case still did not miss a single 500 µs tick" —
that is supported by readings. "A mathematical worst-case upper bound exists" — that is not
supported; this document never claims it and it must not be quoted as if it did.**

Crossing that line requires a different kind of work rather than more samples: static path
analysis or a formal interrupt nesting model, plus pin-level interrupt latency measured with a
GPIO toggle or scope. That is another method, not this table with a larger sample count.
