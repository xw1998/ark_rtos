# Ark RTOS Hardware Coupling Audit

> Condensed English edition. The Chinese page (硬件耦合审计.md) is normative: every number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page adds no new claim and no new measurement.

Audit scope: `kernelsrc/` (kernel), `board/` (board support), `config/` (layout), `example/` (projects)
Audit means: `_nova/w2_audit.py` scanning include relations, cross-layer symbols, HAL/peripheral tokens, uvprojx include paths
Audit date: 2026-09-22

## 1. Conclusion

| Tier | Items |
|---|---|
| **Meets** | kernel source has zero chip-header dependency; the kernel has exactly one injection point into the board layer (`ARKRTOS_BOARD_CONFIG`); the port layer's dependency surface is down to 3 headers; App / driver projects reference neither `board/` nor `port/` |
| **To fix (3 items, see §4)** | `arkrtos_guard.c` includes a board header it does not use; `ARKRTOS_SYSTEM_CLOCK_HZ` is a dead macro with an untrue value; the F401 kernel project borrows F427's HAL source directory |
| **Structural decoupling (do together with feature decoupling)** | `arkrtos_fs.c` is tied directly to `arkrtos_blk` + `arkrtos_partition.h` and cannot be ported on its own (see §6) |

In one line: **no hardware knowledge leaks into the kernel layer; hardware knowledge is concentrated in `board/<chip>/`; what needs cleaning up is three scattered leftovers plus one conceptual binding that blocks filesystem independence.**

## 4. To-fix list

### 4.1 `kernelsrc/src/arkrtos_guard.c:15` — the kernel includes a board header backwards

```c
#include "arkrtos_board_config.h"
```

Grepping the whole file for `board_config` / `BOARD_` hits only this line, and **it uses no symbol from the board configuration**; it is a redundant include. A board header appearing in kernel source makes people believe guard depends on board facts, so it is simply deleted.

(What `arkrtos_guard.c` really needs is the heartbeat contract `ARKRTOS_GUARD_*`, which comes from `arkrtos_guard.h`.)

### 4.2 `ARKRTOS_SYSTEM_CLOCK_HZ` — dead macro with an untrue value

| Location | Value |
|---|---|
| `kernelsrc/include/arkrtos_config.h:277` (`#ifndef` fallback) | 168 000 000 |
| `board/stm32f427/arkrtos_board_config.h:16` | 168 000 000 |
| `board/stm32f401/arkrtos_board_config.h:18` | 84 000 000 |

Fact: **the kernel never reads this macro.** `arkrtos_port_get_system_clock()` is implemented as `return (uint32)SystemCoreClock;` — the only valid source of frequency is CMSIS `SystemCoreClock`, set by the board's clock-init function. The F427 board measures `SystemCoreClock = 96 MHz` while the macro says 168 MHz (the device's nominal ceiling), a factor of 1.75 apart.

Disposition: **delete all three definitions**, leaving a comment at that spot in `arkrtos_config.h` saying "the only source of system frequency is `SystemCoreClock`, do not introduce compile-time frequency macros again". Then host-side conversion trusts only `MDK_TRACE_CPU_HZ` in `config/mdk_trace_config.h`, and nobody can copy a wrong value from a board macro.

### 4.3 The F401 kernel project borrows F427's HAL source directory

Include paths in `example/stm32f401/kernel/ARKRTOS_TEST/MDK-ARM/ARKRTOS_TEST.uvprojx` contain:

```
../../../../stm32f427/kernel/ARKRTOS_TEST/Drivers/STM32F4xx_HAL_Driver/Inc
../../../../stm32f427/kernel/ARKRTOS_TEST/Drivers/CMSIS/Include
```

i.e. the F401 project crosses chip directories to take the common F4 HAL and CMSIS. Functionally fine (F4 series HAL is the same source), but it means "adding a third chip requires another copy". Recorded, not changed this round (the change would touch MDK project files and the HAL tree, more risk than gain).

## 5. Coupling layering principles (established and written into the rules this round)

Four layers, one job each; cross-layer references must be explicit:

| Layer | Question it answers | Sole carrier | Who may provide it |
|---|---|---|---|
| **capability** | what this board/chip **has** | `board/<chip>/arkrtos_board_config.h` + CMSIS | hardware facts; the kernel reads, never writes defaults |
| **feature** | which capabilities **this build wants** | `kernelsrc/include/arkrtos_features.h` | team/project; every switch must be turnable off and still compile |
| **contract** | what interface the kernel **requires from hardware** | `kernelsrc/include/arkrtos_hal.h` | defined by the kernel, implemented by board |
| **layout** | **which address** things live at | `config/arkrtos_partition.h` | the only address source in the whole project |

Decision rules:

* kernel source (`kernelsrc/src/`, `kernelsrc/include/`) may touch the capability layer **only** through the single `ARKRTOS_BOARD_CONFIG` opening;
* for every new feature, first ask which layer it belongs to. A feature-layer capability **must** have a switch in `arkrtos_features.h`;
* after turning a switch off, `kernelsrc` must still compile (this lands gradually through the CI gate's trimmed-build checks).

## 6. Relation to later work

### 6.1 The conceptual binding in `arkrtos_fs.c` (input to VFS independence)

`kernelsrc/src/arkrtos_fs.c` includes all of:

```c
#include "arkrtos_blk.h"        /* block device -- reasonable, a FS needs it */
#include "arkrtos_partition.h"  /* partition layout -- unreasonable, a FS should not know in-machine layout */
#include "lfs.h"              /* bound to a single filesystem implementation */
```

It writes four things in one file: "VFS abstraction + littlefs implementation + block device + in-machine partitions". To make an independent `ark_vfs` project it must be split as:

```
ark_vfs (independent project, zero RTOS / zero hardware dependency)
  +- vfs core       mount table / vnode / file / path resolution / filesystem-type registry
  +- fsdrv          per-filesystem implementations (littlefs, ramfs, devfs...)
  +- backend        block device interface (read/prog/erase/sync), character device interface
Ark RTOS side (port)
  +- block device backend: arkrtos_blk -> ark_vfs block backend
  +- lock and memory injection: arkrtos mutex / malloc
  +- partition layout: Ark RTOS passes (dev, offset, size) at mount time, the VFS never reads the partition header
```

That is: **partition knowledge stays on the Ark RTOS side; the VFS only knows a block device as "start address + length".**

### 6.2 The kernel's current partition-header reference surface

12 files in `kernelsrc/` include `arkrtos_partition.h`:
`arkrtos_config.h`, `shell/platform_arkrtos.c`, `shell/arkrtos_shell.c`, `arkrtos_audit.c`, `arkrtos_crash.c`, `arkrtos_fs.c`, `arkrtos_installer.c`, `arkrtos_layout.c`, `arkrtos_loader.c`, `arkrtos_mpu.c`, `arkrtos_ptable.c`, `arkrtos_task.c`.

11 of them **should** know the layout by design (loader, installer, partition table, MPU windows, crash-diary location, shared memory). The only exception is `arkrtos_fs.c` — it is "a filesystem", not "layout management", and it is the one §6.1 cuts.
