# 无缝升级：A/B 双缓冲热切换

本篇讲 `ARKRTOS_USE_TASK_SWAP` 这个开关背后的机制：**正在跑的任务在原地换成另一个镜像，
不重启任务、不进调度、不写 Flash、不碰文件系统**。

它解决的是「换版本时那一段没人管」的问题。旧方案（[无缝升级例程.md](无缝升级例程.md)）靠
卷上的状态记录 + 请求记录做交接：两个程序各自轮询、自己决定谁该退出，实测交接空洞
27 / 31 / 224 / 407 ms，发布一次状态还要 218 ms（littlefs 提交）。这一篇讲的是把交接搬到
**异常返回路径**上：代价从「几十到几百毫秒」变成「一次整块 memcpy」。

**结论分档**（口径见 `skills/arkrtos/SKILL.md` §6）：

| 结论 | 档位 |
|------|------|
| 开关默认关时默认档构建通过；开关置 1 时 7 个受影响 TU 的 `armclang -fsyntax-only` 通过 | 编译通过 |
| 默认档构建：`0 Error(s), 4 Warning(s)`（4 条全在未改动的 vendored `ark_vfs_procfs.c`） | 编译通过 |
| `mini swap` / `app swap` 在真机上把执行流换过去、旧块归还、旧槽保留 | **未验证**（本机无 DAP 探针，`pyocd list` 报无探针） |
| 换过去之后「数据段连续、不重置」这一条在真机上成立 | **未验证** |
| 失败回滚脚本、批量升级编排 | **未做** |

## 1. 为什么不加第三级缓冲

需求原话是「**再增加一级比较浪费内存和 flash**」。所以这里的缓冲数量**恰好是两份**：

| 形态 | 两份是什么 | 换的那一刻旧的那份 |
|------|-----------|-------------------|
| 小程序（`.svcm`） | 两份**代码块 + RAM 块**（池里两对） | **当场归还池**（帧已在新块、实例表已改指，没有执行流还指着旧块） |
| App（`.svcapp`） | 两个 **Flash 槽**（各带安装时绑好的 RAM 块） | **不擦不还**，退回 `LOADED` —— 这就是回滚能力 |

小程序那边峰值是两份（与旧方案「V1 在 RAM 跑、V2 载入第二块 RAM」相同，没有变多）；
App 那边旧方案没有第二份的说法，现在是两个槽并存——但槽位本来就是 A/B 的语义，
**不额外开辟暂存区**，升级前后占用的槽数不变。

## 2. 机制：异常栈帧就是可改写的现场

SVC 进内核时，硬件已经把被打断的现场压在了任务的 PSP 上，`p_svc_ctx` 就是那个栈帧：

```
[0] R0   [1] R1   [2] R2   [3] R3   [4] R12   [5] LR   [6] PC(=返回地址)   [7] xPSR
```

于是「换一个程序接着跑」在硬件层面只是四步，全部在 SVC 入口一次做完：

1. **整块 memcpy**：旧 RAM 块 → 新 RAM 块（含栈、含当前帧）。此刻元数据一个字都没改，
   任何一步失败都还完整停在旧镜像上，不是「一半新一半旧」。
2. **改写新块里这一帧**：`R0..R3 = R12 = LR = 0`、`PC = 新入口 & ~1`、`xPSR = 0x01000000`
   （只留 Thumb 位）。这就是「新 `main()` 的第一行」，与新建任务时的初始栈帧同形。
3. **挪 PSP**：`arkrtos_port_set_psp(新块同一偏移)`，异常返回从新块弹帧。
4. **改 TCB 与 MPU**：`rom_start/size`、`ram_start/size`、`stack_top/bottom`、`entry`，
   然后 `arkrtos_mpu_build_task()` + `arkrtos_mpu_set_app()` 立刻写进硬件。

代码在 `kernelsrc/src/arkrtos_task.c`：`arkrtos_task_swap_arm / take / cancel / pending`。
`take()` 是唯一真正动现场的地方，**只能在 SVC 入口调用**——那是唯一能确定「这一帧属于这个任务、
且马上就要被硬件弹回去」的时刻。

## 3. 两段式 API：arm 只记账，take 才落地

```
arm(task, 新代码区, 新RAM区, 新入口)   -> 0 / 负错误码    // 只记账，随时可 cancel
   … 任务继续跑旧镜像 …
任务的下一次系统调用 → SVC 入口 → xxx_swap_take()      // 这一刻换成新镜像
```

拆成两段的原因：装载（读文件、校验 CRC、重定位）会放开调度锁、耗时几十毫秒，
而「换帧」必须是一个不可分割的瞬间。`arm` 负责前者，`take` 负责后者。

**同时只允许一份在途。** 内核只有一个挂起槽（`g_task_swap.task_id`），两个消费者
（小程序 / App 槽位）同时挂上去会互相覆盖。两个模块的 `swap` 入口都先查
`arkrtos_task_swap_pending()`，见到非 0 一律返回 `ARKRTOS_LOADER_ERR_BUSY`。
——能排队第二份，就等于承认需要三份缓冲。

## 4. 三条拒绝边界（宁可报错）

| 拒绝条件 | 错误码 | 为什么不能放过去 |
|---|---|---|
| 新旧 RAM 块**大小不同** / 新块不是 2 的幂或未按自身对齐 | `ARKRTOS_SWAP_ERR_LAYOUT` / `_PARAM` | 整块按字节搬，大小不同就没有确定的搬运边界；MPU 一个 region 也盖不住 |
| 存在**同一 `rom_start`** 的其它活任务 | `ARKRTOS_SWAP_ERR_THREAD` | 小程序自建的线程继承创建者的窗口，换块会让它们跑在已归还的块上 |
| 帧形态**不是基本帧**（`xPSR` bit24 为 0 或 `IPSR != 0`，典型是用了 FPU 的扩展帧） | `ARKRTOS_SWAP_ERR_FRAME` | 扩展帧的 `[7]` 是 S6 不是 xPSR，按基本帧改写会写坏现场 |
| 帧不在旧块栈区（例如中断里发的 SVC 走 MSP） | 返回 0，**不作失败** | 那不是这个任务的现场，等它自己再发一次，不猜 |

另外两条**布局全等**也直接拒，不假装无缝：

- 小程序：`code_block`、`ram_block`、`ram_size` 三样必须与旧实例逐项相等；
- App：两个槽的 `slot_type` 必须同类（App 换 Driver 不是升级，是把特权换了），两块 RAM 同大。

布局可变的升级只能走 [无缝升级例程.md](无缝升级例程.md) 那条交接协议。
**这里不做版本兼容性判断**：内核没有能力知道新版本能不能吃旧数据布局，那是打包者的责任。

## 5. 「数据段不重置」正是无缝的含义

整块搬运搬的是**旧块的整块内容**，包括全局变量、堆、栈。所以新版本启动时看到的
`bss`/`data` 是旧版本留下的值，**不是清零后的初始值**。

这是刻意的一致性优先：

- 好处：控制回路的状态（积分项、目标值、滤波器历史）天然跨版本连续，不需要序列化；
- 代价：**新版本必须能接受旧数据布局**。改了结构体字段顺序、加了不兼容的全局量，
  换过去就是读到错的值——这类升级应该走交接协议，或者在版本号里显式拒绝。
- 编译器把哪些东西放在 `.bss` 由链接脚本与镜像头决定；热切换**不搬代码段**，
  新代码是从新块 `rom_start` 取的（小程序是新装载的代码块，App 是新槽里的 Flash 镜像）。

## 6. 两条使用路径

### 6.1 小程序：`mini swap <编号> <新镜像>`

```
mini                                   # 看编号（密集编号，与 mini stop 一致）
mini swap 0 /seamless_v2.svcm          # 把第 0 个实例换成新镜像
```

`arkrtos_mini_swap_at(index, path)` 的动作顺序：

1. 校验路径长度 → 崩溃禁用表（`crash_mini_disabled`）→ 三条互斥（装载串行 / 本模块一份在途 /
   内核一份在途）→ 取第 `index` 个正在跑的实例（`arkrtos_mini_nth_running`）；
2. 拍下旧实例的 `task_id / ram_block / ram_size / code_block`（装载会放开锁，回读时可能已变）；
3. `arkrtos_mini_load_image()` 装载新镜像到**新的一对块**（这一步放开 `g_mini_lock`）；
4. 布局三比对，不等则 `ARKRTOS_SWAP_ERR_LAYOUT`；
5. `arkrtos_task_swap_arm(...)`；
6. 放开装载闸门（别的 `mini run` 可以继续），但「一份在途」由 `g_mini_swap.active` 继续守着。

落地在 `arkrtos_mini_swap_take()`：`rc > 0` 时更新实例表（`pt_index`、`ram_block`、
`info.*`、路径身份）并 `ptable_mini_free(旧 pt_index)`；`rc < 0` 时把新块还池、打 `LOGE`、
实例继续跑旧镜像。`mini stop` 若停的正是被换的那个实例，会先 `arkrtos_task_swap_cancel(0)`
再把在途的新块撤掉——否则它永远留在池里，内核那侧还挂着一个指向已消失任务号的切换。

### 6.2 App：`app swap <运行中的槽> <新槽>`

```
app install 1 /mnt/nor/app_v2.svcapp   # 新版本先按普通安装装进第二个槽（LOADED）
app swap 0 1                           # 让槽 0 的任务换到槽 1 的镜像
```

`arkrtos_loader_swap(old_slot, new_slot)` 的前置条件：

- `old_slot` 必须 `RUNNING` 且有 `task_id`（没在跑就没有「无缝」可言）；
- `new_slot` 必须 `LOADED` 且有 `entry`（必须先装好，且不能已在跑）；
- 两个槽 `slot_type` 同类、两块 RAM 同大且非 0。

落地在 `arkrtos_loader_swap_take()`：旧槽 `ptable_set_slot(old, LOADED, old_entry, 0)`，
新槽 `ptable_set_slot(new, RUNNING, new_entry, task_id)`。**旧槽的镜像与 RAM 块一个都不动**
——回滚就是把参数反过来再切一次（`app swap 1 0`）。这一步没有失败路径（不擦不写），
所以落地是原子的。

### 6.3 落地时机

两处都写在 SVC 入口、`arkrtos_guard_svc()` **之前**：

```c
if(arkrtos_mini_swap_take(p_svc_ctx, arkrtos_current_task_id) > 0)  { ...; return; }
if(arkrtos_loader_swap_take(p_svc_ctx, arkrtos_current_task_id) > 0) { ...; return; }
/* Free liveness evidence: this task called into the kernel. */
arkrtos_guard_svc(arkrtos_current_task_id);
```

两个理由：① 换成功之后这一帧已经是新镜像的 `main()`，本次系统调用不该再执行下去
（不能「换了还继续按旧调用的语义返回」）；② 不该再被记到旧镜像的活体证据上。

任务不会立刻换：它要等到**下一次自己发系统调用**。所以「arm 之后多久生效」取决于它多久发一次
SVC——一个只在算数的回路可能要等一下。这是刻意的：不在装载完成时抢别人的执行流。

## 7. 与旧交接方案的分工

| | 本篇（内核热切换） | [无缝升级例程.md](无缝升级例程.md)（交接协议） |
|---|---|---|
| 谁决定 | 内核在 SVC 入口一次落地 | 两个程序自己轮询卷上的记录 |
| 交接空洞 | 一次整块 memcpy（几十 µs 量级，未上板实测） | 实测 27 / 31 / 224 / 407 ms |
| 布局能否变 | **不能**（块大小三比对全等） | 能（新版本重新分配自己的内存） |
| 需要文件系统 | 不需要 | 需要（`/sx_state.bin`、`/sx_req.bin`） |
| 旧镜像命运 | 小程序：当场还池；App：退回 `LOADED` 可回滚 | 旧版本自己退出 |
| 数据连续性 | 靠整块搬运自动连续 | 靠程序自己写进状态记录 |

两条路不冲突：布局一致的版本用热切换，布局变了的版本用交接协议。

## 8. 开关与验证

```c
/* kernelsrc/include/arkrtos_features.h */
#define ARKRTOS_USE_TASK_SWAP   0   /* 默认关 */
```

Kconfig：`config ARKRTOS_USE_TASK_SWAP`（`bool`，`default n`），见
[Kconfig配置系统.md](Kconfig配置系统.md)；开关清单见 [功能开关.md](功能开关.md)。

- **默认关**：`arkrtos_task.c` 的原语、`arkrtos_mini.c` / `arkrtos_loader.c` 的消费者、
  SVC 入口两行钩子、shell 的 `mini swap` / `app swap` 分支全部不参与编译。
- **默认档实测**（F427 `ARKRTOS_TEST`，Keil AC6）：`0 Error(s), 4 Warning(s)`（4 条全在未改动的
  `ark_vfs_procfs.c`），`Code = 219882`、`RO-data = 19198`、`RW-data = 896`、`ZI-data = 120852`。
  与引入前基线 `Code = 219834` 相比 **+48 B**——原因是 `arkrtos_mini_run()` 改为调用抽出来的
  `arkrtos_mini_load_image()` 后不再内联，**不是逐字节零变化**，如实记账。
- **开档防假绿**：`tools/swap_syntax_gate.py` 强制 `ARKRTOS_USE_TASK_SWAP=1`，对 7 个受影响
  TU 跑 `armclang -fsyntax-only`（`arkrtos_task.c` / `arkrtos_mini.c` / `arkrtos_loader.c` /
  `arkrtos_shell.c` + cortex-m3/m4/m7 三个 `arkrtos_port.c`），成功输出
  `SWAP-GATE OK (7 files, USE_TASK_SWAP=1)`；缺 armclang 是 **FAIL 不是 skip**。
  已注册进 `tools/ci_gate.py`（`swap` 一项，门禁总数 23）。

**为什么不做成默认开**：它改的是「异常返回落到哪里」。没有板上验证之前，默认档不该带这种能力——
一次帧改写错误的表现是任务跑飞，而不是一条错误码。

## 9. 未做项与已知限制

- **没有上板验证**。本机没有 DAP 探针（`pyocd list` 报 `No available debug probes are connected`），
  所以本篇所有结论止于「编译通过 + 语法门禁通过 + shell 命令接线正确」。
  上板要验的四件事：① `mini swap` 后迭代计数与受控量连续；② 旧块确实回到池里（`pool` 读数）；
  ③ `app swap` 后旧槽仍是 `LOADED`（`app list`）；④ 反向 `app swap` 能切回去。
- **失败回滚脚本**：`app swap` 保留旧槽 = 回滚的原材料，但没有「换了之后 N 秒没心跳就自动切回去」
  的看门狗编排——这需要决策（谁判定新版本失败），不在本轮。
- **批量升级编排**：一次只允许一份在途，多任务升级要一个一个排。
- **FPU 扩展帧不支持**：用过 FPU 的任务（`xPSR` bit 4 置位的扩展帧）直接拒，错误码
  `ARKRTOS_SWAP_ERR_FRAME`。要支持得先把 S0–S15/S16–S31 一起搬——搬错一个就是静默的浮点错值。
- **布局必须全等**：块大小、槽类型、RAM 大小任何一条不等都不换。这不是缺陷，是「宁可报错」。
- **`arm` 之后到落地之前，旧镜像还在跑**：这段时间新块已经占着池/槽。若任务永不发系统调用，
  这份新块就一直挂着——`cancel` 可以从外部撤掉（`mini stop` 会顺手撤）。
