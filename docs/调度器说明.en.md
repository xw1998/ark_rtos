# The Scheduler

**[简体中文](调度器说明.md) | English**

> Condensed English edition. The Chinese page (调度器说明.md) is normative: every
> number below is copied from it as of 2026-11-18, but if the two disagree, the
> Chinese page wins. This page adds no new claim and no new measurement.

The scheduler is the one module that runs on every tick and on every block,
wake and preempt. This page covers its model, the change that turned task
selection into O(1) plus the evidence that it is equivalent, the measured
switch cost, and what is explicitly still not done.

Sources: `kernelsrc/src/arkrtos_task.c` (dispatch core, ready set, delay chain,
tick handling), `kernelsrc/src/arkrtos_cfg.c` (task registration).

## 1. Model

| Item | Value / meaning |
|------|-----------------|
| Policy | **Priority preemption** plus **round-robin inside one priority** |
| Priority | `1..254`, **lower number is more urgent**. `255` is the "no candidate" sentinel, not a legal priority; creation rejects it instead of clamping silently |
| Task capacity | `ARKRTOS_TASK_MAX_NUM` (static TCB array) is **derived from the partition**: `ARKRTOS_TASK_NEED_MIN + 8` = `ARKRTOS_TASK_MAX_KERNEL + SLOT_MAX + 8`. This board has `SLOT_MAX = 16` and `ARKRTOS_TASK_MAX_KERNEL = 8`, so 32 slots, of which `ARKRTOS_TASK_MAX_KERNEL = 8` is reserved for kernel and sample tasks |
| Tick | `ARKRTOS_TICK_PERIOD_US = 500` (2 kHz). All timeouts are expressed in milliseconds outside the kernel and converted internally |
| Time slice | `ARKRTOS_TIME_SLICE_TICKS = 10` (= 5 ms), applies only when several tasks share a priority |
| Task states | `INVALID` / `READY` / `RUNNING` / `WAIT` |
| Candidate set | Both `READY` and `RUNNING` count as runnable - the running task must take part in the comparison, otherwise it would lose against itself |
| Tie-break at equal priority | The ready chain is a **ring**; the head is the chosen task, and a slice expiry moves the head to the tail |
| Nothing runnable | Returns `-1`; the caller falls through to idle |

### 1.1 The three scheduling triggers

| Trigger | Where | Behaviour |
|---------|-------|-----------|
| **Preemption** (a higher priority became ready) | Every wake point (semaphore, mutex, queue, event, soft timer, loader) calls `ARKRTOS_SWITCH_TASK()` | Raises PendSV immediately. PendSV takes the highest ready priority from the bitmap and switches if it differs from the current task - **it does not wait for the next tick** |
| **Tick** (slice expiry / delay expiry) | `arkrtos_kernel_tick_handler()` | Expires the delay chain first, then charges the slice of the running task; at zero the task moves to the tail of its own priority ring, then PendSV is raised if needed |
| **Voluntary yield** | A task calls a blocking API (`arkrtos_task_delay`, wait for semaphore, wait for queue, ...) | Unlinks, sets `WAIT`, `ARKRTOS_SWITCH_TASK()` |

Preemption and the tick both call the **same** `arkrtos_sched_next()`, so the two
paths cannot disagree (`arkrtos_sched_is_switching()` is safe to call repeatedly,
and `ARKRTOS_USE_FAST_TICK_SWITCH` depends on that).

The time slice only affects **one priority**: `arkrtos_ready_rotate()` returns
immediately when the bucket holds a single node, so a lone task is not rotated
every 5 ms; a higher priority task is picked straight out of the bitmap and is
never subject to the slice.

## 2. The change: full-table scan to bitmap plus linked lists

### 2.1 Data structures

| Structure | Content |
|-----------|---------|
| `arkrtos_ready_map[8]` | 256-bit priority bitmap; bit `p` = priority `p` has a ready task |
| `arkrtos_ready_group` | "non-empty" bitmap over the eight 32-bit words (two-level bitmap: one 32-bit test picks the non-empty group) |
| `arkrtos_ready_head[256]` | Double-linked **ring** head per priority (stores a task index; `ARKRTOS_TASK_NIL = 0xFF` is empty) |
| TCB `ready_next` / `ready_prev` | Ready-chain links as indices, not addresses |
| TCB `delay_next` / `delay_prev` / `delay_tick` / `delay_queued` | Delay chain, an ascending double-linked list keyed on the **absolute** expiry tick |
| TCB `slice_tick` | Remaining slice of the running task (meaningful only while `RUNNING`) |

The bitmap must be **256 bits**: the kernel soft-timer task uses
`ARKRTOS_TIMER_TASK_PRI = 200`, far above 31, so a single `uint32` cannot hold it.
The lowest set bit is found by `arkrtos_lowbit32()`, a **fixed five-step binary
search** whose step count does not depend on the input and which does not rely on
CMSIS `__CLZ` (kernel sources do not include CMSIS headers).

### 2.2 Selection path

```c
int32 arkrtos_sched_next(void)
{
    if(first schedule ever) { arkrtos_ready_rebuild(); }   /* happens once, see 3.3 */
    if(tasks pending recovery) { recover_pending(); }      /* whole block skipped when arkrtos_recover_cnt==0 */
    return arkrtos_ready_top();                            /* two-level bitmap + chain head, constant steps */
}
```

Cost of `arkrtos_ready_top()` is independent of task count and priority spread:
two `arkrtos_lowbit32()` calls plus one array read. The old implementation scanned
48 entries per decision, comparing `status` and `priority` one by one.

### 2.3 Delay chain

Previously every task carried a countdown and the whole table was scanned each
tick. It is now an ascending double-linked list on the absolute expiry tick:

```c
void arkrtos_delay_tick(void)
{
    while(head exists)
    {
        if((int32)(arkrtos_kernel_tick - p->delay_tick) < 0) break;  /* signed, wrap-safe */
        arkrtos_delay_unlink(idx);
        if(p->status != ARKRTOS_TASK_WAIT) continue;                  /* zombie: already woken */
        ... wake (timeout / periodic re-arm) ...
    }
}
```

Each tick only touches already-expired nodes at the head, usually none:
amortised O(1). **Expiry comparison is a signed difference**, not `a < b`, so the
tick counter wrapping (about 24.8 days) cannot wedge a task.

**Insertion must use the same ruler as expiry (found on hardware, 2026-09-23).**
`arkrtos_delay_link()` originally compared with `delay_tick <= t`, i.e.
**unsigned**, while expiry used the signed difference. The two disagree only
around wrap: a deadline armed shortly before wrap has a small numeric value (say
`0x24`) yet is the *furthest away*, so unsigned sorting put it at the head and
blocked every earlier sleeper behind it until it expired itself (up to one full
period). Measured effect: the application heartbeat went silent for 2140 ticks
(1.07 s), one main-loop iteration stretched to 10.6 s instead of 5 s, the
`heartbeat` watchdog fired three consecutive faults and slot 0 was held; the
fault log lives in `.noinit` so it survived the reset and reproduced on the next
boot. After switching insertion to the same signed form, the two `APP_ALIVE`
stamps across wrap are exactly 5.000 s apart, `fault` has no record and `sched`
reports consistent.

**Early wake does not unlink.** A task woken early only gets
`arkrtos_delay_disarm()`; if that is ever missed, the node is still on the list at
expiry and is discarded by the `status != WAIT` test. This tolerance converts a
hard-to-find "task woken twice" defect into a harmless no-op, at the cost of
possibly holding already-woken nodes for a while.

**Stated honestly**: delay-chain **insertion is still an ordered O(N) insert**
(the same complexity as RT-Thread's `rt_timer_start`); only per-tick processing
became amortised O(1). At these task counts it is not the bottleneck, but it is
not O(1).

### 2.4 Where the index must be kept in step

The ready set is an **index** over `status`, not the truth. Everything that can
change "is this task runnable / what is its priority" must update it:

| Place | Action |
|-------|--------|
| `arkrtos_cfg.c` task registration | Initialise chain fields + `arkrtos_ready_add()`; `arkrtos_cfg_load()` calls `arkrtos_ready_reset()` |
| `arkrtos_task.c` PendSV activation | Before the new task becomes `RUNNING`, the old one goes back to `READY` (still in the set) |
| `arkrtos_task.c` block/delay | `arkrtos_ready_del()` + `arkrtos_delay_arm()` |
| `arkrtos_task.c` stack overflow / fault reap | `arkrtos_ready_del()` + `arkrtos_delay_disarm()` |
| `arkrtos_sync.c` / `arkrtos_mq.c` / `arkrtos_event.c` / `arkrtos_timer.c` | `arkrtos_ready_add()` after waking |
| `arkrtos_sync.c` priority inheritance raise/restore | `arkrtos_ready_reprio(idx, old_prio)`; `old_prio` must be read **before** `priority` is changed |
| `arkrtos_loader.c` forced teardown | `arkrtos_ready_del()` + `arkrtos_delay_disarm()` |
| Tick | `arkrtos_ready_rotate()` on slice expiry |

Missing one of these produces silent errors - "a task that is never chosen" or "a
blocked task that is still chosen" - with no error code and no crash. That is why
this round also added the consistency command in section 5.

## 3. Three backstops against "one update forgotten"

### 3.1 `arkrtos_ready_add/del/unlink` are idempotent

`arkrtos_ready_add()` returns immediately when `ready_next != NIL` (already
linked); `del` does nothing for an unlinked task. Calling twice is safe; only
calling zero times loses a task.

### 3.2 Bitmap and chains are maintained by one path

Buckets are linked and unlinked only inside `arkrtos_ready_link()` /
`arkrtos_ready_unlink()`; nothing else touches `arkrtos_ready_map`. The bitmap
and the lists therefore cannot drift apart independently.

### 3.3 Rebuild once from `status` before the first schedule

```c
static uint8 arkrtos_ready_built = 0u;

int32 arkrtos_sched_next(void)
{
    if(arkrtos_ready_built == 0u) { arkrtos_ready_rebuild(); arkrtos_ready_built = 1u; }
    ...
}
```

`arkrtos_ready_rebuild()` clears every bucket and link field, then walks the task
table and links everything in `READY` / `RUNNING`.

**Why it is needed**: the sample project's `arkrtos_register_tasks()` fills TCBs
**by hand** instead of calling `arkrtos_task_register()`; it only writes
`status = ARKRTOS_TASK_READY`. The old scan-the-table scheduler handled that;
with bitmap plus chains such a task can never be selected. This was not
theoretical - it happened on hardware in this round: `sched` reported
`INCONSISTENT, 3 mismatch(es)`, and the per-task dump showed two LED tasks with
`status=READY` but `ready_next=ready_prev=255` (in no bucket), i.e. silent
starvation. The fix is on both sides: the kernel rebuilds its index from the
truth once (O(N), once, independent of call order), and the sample now also sets
`base_priority` and calls `arkrtos_ready_add()` (a missing `base_priority` would
promote a task to priority 0 when inheritance is restored).

## 4. Cost

With `N` tasks (<= 48) and priorities 1..254:

| Operation | Before | After |
|-----------|--------|-------|
| Pick the next task | O(N) table scan | **O(1)** (two-level bitmap + chain head) |
| Task enters/leaves the ready set | O(N) (implicit, discovered by scanning) | **O(1)** (link/unlink + set/clear bit) |
| Priority change (inheritance raise/restore) | O(N) | **O(1)** (unlink + relink) |
| Round-robin inside a priority | O(N) (rescan comparing `touch_tick`) | **O(1)** (ring head to tail) |
| Per-tick countdown | O(N) decrement over the table | amortised **O(1)** (delay chain head only) |
| Delay/periodic insertion | O(N) (already) | **still O(N)** (ordered insert, not a timer wheel) |
| First schedule | - | O(N) **once** (3.3) |

RAM: each TCB gains `ready_next/prev`, `delay_next/prev` (1 byte each),
`delay_tick` (4), `slice_tick` (4), `delay_queued` (1) - about 576 B over 48
tasks, guarded by a compile-time assertion on `ARKRTOS_TASK_TABLE_RAM_MAX`. The
bitmaps and chain heads are file-scope statics: `8*4 + 1 + 256 + 1 + 4 + 1`, about
290 B.

## 5. Verification

### 5.1 Consistency command

New shell command `sched`:

```
sched: consistent (bitmap/links == task table)
```

It compares what the bitmap and chains say (ready set, per-task priority) against
what the task table says (`status`, `priority`). On mismatch it **prints every
difference** (`#idx prio= status= on_ready= next= prev=`), not just a count - a
count alone is a lock without a key. Before the 3.3 fix it reported
`INCONSISTENT, 3 mismatch(es)` (two LED tasks plus the count); after the fix two
consecutive queries were `consistent`, `ready=1 top=6` (only the kernel task was
ready, the rest were in periodic waits).

### 5.2 Build

* **AC6 syntax check**: `armclang -fsyntax-only`
  (`--target=arm-arm-none-eabi -mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard -std=c99`)
  passes for all `kernelsrc/src/*.c` and `arkrtos_shell.c`, leaving only 3
  pre-existing VLA-folding warnings.
* **Keil UV4 full rebuild** (AC5 V5.06u7): `0 Error(s), 1 Warning(s)`, the only
  warning being the baseline `arkrtos_context.S(134) A1581W` (alignment padding).
  `Code=51326 RO-data=3710 RW-data=320 ZI-data=38896` (before: `Code=49030`,
  +2296 B).
* **On hardware**: UV4 `-f` to the F427, `Verify OK`; app and driver images load
  and run, `info` / `task` / `sched` all behave.

### 5.3 Switch cost (F427 @ 96 MHz, 3 s window, DWT cycle counter)

`pendsv` is measured between the entry and exit of `arkrtos_trace_isr(14, ...)`,
bracketing the whole PendSV; `activate` is measured inside
`arkrtos_sched_activate()` (`ARKRTOS_SCHED_STAT_*`). Both read the delta across
the window and average it, never the since-boot accumulator.

**Instrumentation caveat first**: the board's `arkrtos_port_board_init()` calls
`arkrtos_trace_init()`, so **instrumentation is on by default** (deliberately, so
the reset-to-boot segment can be reproduced). With it on, a switch costs about
1760 cycles by itself. To measure the scheduler, run `trace stop` first.

| Configuration | PendSV trips / 3 s | Round-trip mean | activate mean | PendSV CPU share |
|---------------|--------------------|-----------------|---------------|------------------|
| **Trace off**: table scan (`a9e7b80`) | 3129 | **710.5** | 83.6 | 0.768% |
| **Trace off**: bitmap + chains (this round) | 3129 | **430.9** | 99.5 | **0.448%** |
| Trace on (default firmware): table scan | 3118 | 2480.8 | 958.0 | 2.67% |
| Trace on (default firmware): bitmap + chains | 3121 | 2194.1 | 965.5 | 2.37% |

Four things to read carefully:

* **Trip counts match** (3129 vs 3129), so the means are comparable. This is the
  round's only same-workload A/B: both firmwares ran the **same** app and driver
  images, only the kernel differed.
* **What dropped is the decision part.** `activate` contains no lookup and O(1)
  does not change it (83.6 to 99.5, +16 cycles absolute, not repeated to separate
  noise). The real drop is `710.5 - 83.6 = 627` to `430.9 - 99.5 = 331`, roughly
  **-47%**; the whole PendSV trip is **-39%**.
* **The instrumented numbers drop far less** (2480.8 to 2194.1, only -11.6%)
  because the 1760-cycle instrumentation dominates. Do **not** use instrumented
  figures to talk about scheduler optimisation.
* **Comparing with open-source RTOSes needs care**: FreeRTOS Cortex-M4 figures of
  200-300 cycles are for a path without MPU region reload or isolation checks.
  This window includes `arkrtos_mpu_set_app()` (reprogramming MPU regions on an
  app switch is architectural) and two `arkrtos_trace_isr` hook calls. A
  comparable number needs the other port running on the same board; **that has
  not been done**.

Floating-point context is not counted separately: the kernel saves it lazily
(`FPU_FPCCR_ASPEN`), so only tasks that actually use VFP push more, and the report
does not break it out.

## 6. Not done (listed as not done)

1. **Delay-chain insertion is still O(N)**. A timer wheel or bucketed expiry
   queue would make insertion O(1). The trade-off is the same as for the ready
   set: one more structure means one more set of synchronisation points, and this
   round already paid for "index decoupled from truth" once (3.3). Any new
   structure must ship with its own self-check.
2. **Round-robin has no dedicated stress test**. The code path (`slice_tick`
   decrement, `arkrtos_ready_rotate`, head-to-tail) compiles and runs on
   hardware, but no two CPU-bound equal-priority tasks were built to observe the
   5 ms alternation. Existing app and driver images are all periodic-wait
   workloads and do not create that case.
3. **Round-robin no longer depends on `touch_tick`**. The field still exists and
   is still updated (stack usage, diagnostics), but it no longer participates in
   dispatch; the ring head decides. The older statement about "picking the
   smallest `touch_tick`" no longer holds.
4. **Scheduling latency and jitter are still unmeasured**. What was measured is
   "cycles per switch", not "worst case from interrupt to running". The latter
   needs trace points; `mdkdebug`'s buff backend can reach per-cycle granularity.
5. **Instrumentation on by default costs a fixed amount**: see 5.3 - without a
   host draining it, instrumentation still spends about 1760 cycles per switch
   (about 1.9% CPU at 1 kHz) and keeps dropping events (measured
   `138068 events were dropped`). That is a design trade-off (reproducing the boot
   segment); for steady-state performance "off at boot, `trace start` on demand"
   would be cheaper. **Not changed**, because it changes default behaviour.
6. **`sched` is a manual command**. Someone has to type it. Ideally a failed
   assertion would capture a snapshot, or a cheap self-check counter would exist;
   neither does.

## 6.1 The SMP skeleton does not touch the scheduler

"Groundwork for future multi-core MCUs" in this round means foundation only, with
no scheduler line changed - a deliberate boundary:

| What exists (`ARKRTOS_USE_SMP`, default off) | What is missing (what real SMP needs) |
|---|---|
| Per-core state table (`online`/`started`/`current_task_id`/`tick`/`ipi_count`/`idle_count`) | Per-CPU ready sets and per-core current task pointer |
| Online mask (`uint32`) and `arkrtos_smp_online_count()` | Cross-core spinlocks / atomic kernel paths |
| Secondary entry `arkrtos_smp_secondary_main()`: mark online, enable interrupts, WFI loop | Secondaries taking part in dispatch, task migration, per-core MPU context |
| IPI path `arkrtos_smp_send_ipi()` plus a weak receiver (counts only by default) | Using IPIs for cross-core wakeup and TLB/MPU synchronisation |

Why the scheduler is untouched: its model is one global ready bitmap, one chain
per priority and one global current task id. Splitting that per core would put an
atomic operation on every fast path (`arkrtos_sched_next`, tick handling, delay
insertion, round-robin), which directly conflicts with "default off means zero
change in size and behaviour", and none of it buys anything on the
install-applications / crash-containment promise.

Two rules already pinned:

1. **`started` is not `online`**: the port accepting a start request records
   `started`; the online bit is set by the secondary itself. A core that never
   ran must not appear online.
2. **Single-core ports return `-1`**: `arkrtos_port_cpu_start()` and
   `arkrtos_port_send_ipi()` on cortex-m3/m4/m7 mean "there is no such path", not
   "succeeded doing nothing".

Verification level: **unverified (no multi-core board)**. 44 host assertions plus
five-file ON-path syntax; Keil F427 default build `Code=220290`, unchanged from
before (default off, zero change).
