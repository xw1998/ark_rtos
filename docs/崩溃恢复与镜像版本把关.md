# 崩溃恢复与镜像版本把关

这份文档覆盖两件事，它们都回答"设备上出了事之后会怎样"：

- **B 项**：一个镜像反复崩溃，内核怎么不再让它把整机拖进重启环；
- **C 项**：一个镜像要被装进池子之前，内核怎么判断"该不该装"。

以及两件**边界要说清**的事：签名验签（已实现、默认关、对称密钥）与升级/回滚（见 §5）。

---

## 1. B 项：崩溃终局与跨复位计数

### 1.1 计数存在哪

崩溃计数有**两份**，用途不同：

| 位置 | 生命周期 | 用途 |
|---|---|---|
| 共享 RAM 里的 `slot_crash_cnt` | 本次上电 | 运行期查询（`app` 列表的崩溃数列） |
| 共享 RAM **尾部 UNINIT 区**的 `arkrtos_crash_journal_t` | **活过复位，掉电才清零** | 跨复位累计，挡住"崩溃→复位→再崩溃"的启动环 |

日记落在 `config/arkrtos_partition.h` 定义的区域里：

```c
#define CRASH_LOG_SIZE  (512)
#define CRASH_LOG_BASE  (SHARE_RAM_BASE + SHARE_RAM_SIZE - CRASH_LOG_SIZE)
```

结构体大小在编译期对着 `CRASH_LOG_SIZE` 做静态检查——**加字段加不出空间是编译错误**，
不会静默覆盖共享 RAM 尾部的别的数据。

### 1.2 日记字段

| 字段 | 含义 |
|---|---|
| `magic` | `ARKRTOS_CRASH_MAGIC = 0x5343524A` |
| `version` | `ARKRTOS_CRASH_VERSION = 1` |
| `seq` | 每次提交写入自增 |
| `boots` | 记在这里的启动次数；`>= 2` 说明上一回的内容真的活过了一次复位 |
| `crash_cnt[]` | 每槽连续故障数 |
| `last_reason[]` | 最近一次故障的原因 |
| `dis_reason[]` | 该槽为什么被禁用（0 = 未禁用） |
| `dis_tick[]` | 禁用时刻的 tick（0 = 本次上电之前） |
| `base[]` | 该条目对应的池地址 |
| `check` | 覆盖以上全部字段的校验和 |

### 1.3 三条不猜的规则

1. **magic / version / checksum 任一不过，整本日记作废重开**，而不是"试着信一半"。
   残留 RAM 字节和写了一半的记录看起来都像数据，照着行动就会把一个镜像
   因为它从没做过的事禁用掉。
2. **只对"镜像还停在当初那个地址"的槽位采用计数**。空槽、被换掉的镜像、被搬走的镜像，
   条目一律丢弃——把陈旧计数记到新来者头上，就是拿别人的错罚它。
   但"按地址对齐"不等于"按下标对齐"：槽位表在每次复位后重建（记录按池地址升序回来），
   同一个镜像可能落在和当初记账时不同的下标上。日记里的 `base[]` 就是为这件事存在的——
   开机扫描先在整本日记里找"地址对上"的条目接管，**没有对上的才丢**（见 §1.7）。
3. **禁用理由分三种，不混为一谈**：
   `ARKRTOS_CRASH_REASON_FAULT(1)` 连续故障到上限 /
   `ARKRTOS_CRASH_REASON_HEARTBEAT(2)` 违反自己声明的心跳契约 /
   `ARKRTOS_CRASH_REASON_AUDIT(3)` 运行期结构自审失败。

### 1.4 上限是多少

`config/arkrtos_partition.h`：

```c
#define APP_CRASH_RESTART_MAX 3    /* 连续故障重启上限：达到后禁用该 App 槽位（0=不限次自动重启）*/
```

布局配置里可以用 `fault_restart_max`（1..64）按布局覆盖，`0` 表示沿用上面的编译期值。
**重新安装镜像时计数清零。**

到上限之后：槽位置为 `INVALID`，任务脱离调度，并且**不再自启**。
人工重启用 `arkrtos_loader_start_manual()`（控制台 `app start <slot>` 走的就是它）——
禁用的语义是"除非有人明确要求，否则别再自己跑起来"。

### 1.5 心跳是应用自己的合同，不是内核的猜测

`arkrtos_heartbeat(period_ms)` 让镜像声明"我最久隔这么久报一次到"。

- 周期下限 `ARKRTOS_GUARD_MIN_PERIOD_MS = 100` ms（等于服务采样周期）。
  比采样间隔还短的窗口判断不了，内核**拒绝**而不是看着一组它验证不了的数字下结论。
- 从没声明过周期的镜像，`guard` 报的是 **"未声明"**，不是"健康"——内核没有判健康的基础，就不给判语。
- 判定只看**报到的间隔**，不看任务当时在干什么。所以"睡/阻塞比声明周期还久"就是违约：
  周期是镜像自己的承诺，就得覆盖镜像自己最长的那次等待。豁免阻塞任务会让
  "睡→干活→报到"这种最常见形态失去约束，永远醒不来的镜像反而抓不到。
- 合同随任务结束而结束：任务被删的条目直接丢掉，不会留到 id 复用、记到另一个镜像头上。
- 内核自己收集的证据（每次 SVC 调用、在节拍上正在跑）**单独成列**，不折进合同——
  折进去就会 silently 放过一个卡死但恰好还在 CPU 上的镜像。

### 1.6 `crash` 命令

```
journal: 0x2000BE00 +512 bytes (uninitialized RAM: kept across reset, cleared by power-on)
boots=35 seq=100

slot type  faults last        hold      held_at
 1   app    3      fault       fault     12840
 2   drv    3      fault       fault     12840
 3   app    3      fault       fault     12840
```

（以上为 2026-09-22 F427 实测值：三个演示槽都撞到了上限被保持禁用。）

### 1.7 上板缺陷：`crash-limit` 的禁用不跨复位保持（已修）

**症状**：`HWSAFE_DEMO` 崩 3 次后 `app list` 显示 `INVALID` / `crash=3` /
`held=crash-limit`，`crash` 也记着 `held_at=<tick>`；但 `reboot` 之后它又自启并再崩
一次，`boots` 加到 4、`crash` 变成 3（不是 6）——**跨复位的禁用根本没有生效**。

**根因**：`arkrtos_crash_scan_apply()` 用**槽下标**对齐日记与槽位表，
`p_j->base[i] != p_pt->slot_base[i]` 时直接清条目。槽位表在复位后按池地址升序重建，
下标一旦漂移（实测：低地址槽被卸载后，被禁用的镜像从下标 1 挪到下标 0），
日记里那条 3 次故障的历史就"地址对不上"被清掉，禁用自然不再保持。

**修法**（`kernelsrc/src/arkrtos_crash.c`）把开机对齐改成三遍：

1. 逐槽先找"地址对得上"的条目接管（接管后把源条目的 `base` 置 0，防止重复记账）；
   这一步**只清"整本日记里都找不到这个地址"的条目**——第一版实现在这里踩过坑：
   按下标逐个清，i=0 那个槽的地址对不上时先把日记 0 号清了，而 0 号正好是后面
   i=1 那个槽的历史，于是"接管"永远轮不到。
2. 扫掉没有任何槽位认领的条目（卸载过的镜像、已经离开槽位表的地址），
   防止以后新装在同一个地址上继承旧计数。
3. 发布计数并执行保持：`dis_reason != NONE` 或 `crash_cnt >= limit` 的槽位
   一律 `autostart=0` + 状态置 `INVALID`，并打印
   `CRASH: slot N held: ... 3 faults, last at tick <原 tick>`。

**复验（F427，上板）**：

| 场景 | 期望 | 实测 |
|---|---|---|
| 崩 3 次 → `reboot`（下标不变） | 开机即 `held`、不自启 | 通过：`CRASH:311 slot 0 held: crash-limit, 3 faults, last at tick 61702`，`app list` `auto=no`/`INVALID` |
| 卸载低地址槽让被禁镜像下标 1→0 → `reboot` | 历史被接管、仍 `held` | 通过：`CRASH:311 slot 0 held: crash-limit, 3 faults, last at tick 32`，`fault` 无新增记录（未再自启） |
| 再 `reboot` 一次 | 读数幂等 | 通过：同样的 `held` 行、`crash=3`、`held_at` 不变 |

## 2. C 项：装进池子之前的版本把关

### 2.1 三态判定

`arkrtos_loader_check_install()` 只按 **`image_id`** 比对（`image_id` = 负载的 crc32，
是负载身份；同一个应用两次打包只有版本号不同、`image_id` 相同）：

| 情形 | 结果 |
|---|---|
| 池内没有同 `image_id` 的有效副本 | 放行 |
| 同 `image_id`，且 `image_size` / `crc32` 也相同 | `ARKRTOS_LOADER_ERR_DUP(-17)` 重复副本 |
| 同 `image_id`，版本号不高于已装版本（降级回灌、同版本重建） | `ARKRTOS_LOADER_ERR_VERSION(-16)` 版本回灌 |
| 该槽位正处于 `LOADED` / `RUNNING` | 拒绝（先 `app stop <slot>`） |

设备侧原文：

```
[E][INSTALL] refused: version not increasing (id 0x%08X, incoming v%u.%u.%u.%u <= installed) - bump the version
[E][INSTALL] refused: identical image already installed (id 0x%08X, v%u.%u.%u.%u, %u B) - nothing to do
```

版本号是 4 段式，按大端排在 `version` 一个字里（`v[31:24].[23:16].[15:8].[7:0]`）。

### 2.2 断电恢复为什么不需要日志扇区

提交状态只有一个字段 `state`：搬移时先在新落点写一份 `UNCOMMITTED` 副本，
校验通过后**只把这一个字段**改写成 `VALID`（单字编程，原子），最后才擦旧副本。
上电扫描见到 `UNCOMMITTED` 一律丢弃；同 `image_id` 的两份 `VALID` 保留地址较低的那份。
两条规则合起来，恢复既是幂等的又是确定的。

> `state` **不能**拿来表达"卸载"：镜像提交后它已经是 0，写 `UNCOMMITTED`(=1) 要求把 0 置 1，
> Flash 做不到，硬件会静默保持 0，卸载于是变成空操作、镜像下次上电又回来。
> 卸载走的是清 `type` 字段（`ARKRTOS_APP_OFF_TYPE`），详见
> 《内核Shell控制台使用说明.md》"卸载的语义与空间回收的粒度"。

## 3. 排障入口

| 想知道 | 敲 |
|---|---|
| 跨复位崩溃账本、哪些槽被禁用、为什么 | `crash` |
| 心跳合同是否被违反 | `guard` |
| 结构自审是否通过 | `audit` |
| 故障环形记录（含 `INSTALLFAIL`） | `fault` |
| 某个任务卡在哪 | `task <id> <任意第三参>` |
| 安装为什么被拒 | `fault` + `log`（设备侧 `INSTALL` / `LOADER` 日志行） |

## 4. 结论分档

| 内容 | 档位 |
|---|---|
| 跨复位崩溃计数、上限禁用、`crash` 输出 | **上板验证过**（2026-09-22，F427：`boots=35 seq=100`，槽 1/2/3 撞上限被保持禁用） |
| 上限禁用的**跨复位保持**（含槽位下标漂移） | **上板验证过**（见 §1.7：三种场景，含卸载低地址槽造成的下标 1→0 漂移；修前实测不保持，修后保持且二次重启幂等） |
| `ERR_DUP` / `ERR_VERSION` 三态判定的代码路径 | **仅编译通过**（F427 / F401 / APP_DEMO / BLED_DRV 均 0 Error）；真机上未构造过重复副本与版本回灌两种输入 |
| 心跳违约导致禁用（`REASON_HEARTBEAT`） | **未验证**（未在板上构造过违约镜像） |
| 结构自审失败导致禁用（`REASON_AUDIT`） | **未验证** |
| 签名：内核算出的 MAC 与 `pack_app.py` 写进去的逐个字节相同 | **宿主门禁通过**（`tools/sign_host_gate.py`，`ci_gate` 的 `sign-host` 项；用真实 `arkrtos_sign.c` 对确定性镜像算 MAC 再与打包器 `calc_sign()` 比） |
| 签名：打开开关后未签名镜像被拒绝、签名镜像被接受 | **未验证**（默认关；打开需要一份密钥，密钥不进仓库） |

## 5. 明确不做的事（以及为什么）

| 不做 | 现状 | 原因 |
|---|---|---|
| ~~**签名验签**~~ **（已实现，默认关）** | `ARKRTOS_USE_IMAGE_SIGN=1` 时：`pack_app.py --sign-key` 写 HMAC-SHA256 到 `signature[0..32)`，内核在**安装期**复算并拒收不符的镜像（`loader.c` 两条路径都调 `arkrtos_sign_verify` / `arkrtos_sign_stream_end`）。默认 0，F427 工程没有打开（密钥不该入库） | 机制在，但没有"合规"含义：**对称**预共享密钥（谁读出密钥谁能签）、只在安装期校验（已在 Flash 里的镜像开机不再复核）、没有信任根。局限写在 `arkrtos_sign.h` 文件头 |
| **A/B 双槽 / 自动回滚** | 没有 A/B 双槽，没有备份区 | 暂不做。但「运行中换掉控制程序」已有例程走通：控制回路以小程形态驻 RAM、镜像放外部 NOR，新版接管后接着旧版的状态跑，实测交接耗时 27 ~ 407 ms（`无缝升级例程.md`）——它做的是**交接**，不是回滚 |
| **持久化版本日志** | 只有 `.noinit` 区那本崩溃日记 | 版本日志不做，崩溃计数只在内存里记一下 |

> 因此：**默认档下 `signature` 全 0、内核不读，"有字段"不等于"已签名"。**
> 打开 `ARKRTOS_USE_IMAGE_SIGN` 后它才是真的：那时它回答的是
> "这个镜像是不是持有密钥的人做的、有没有被改过"，**不是**"它可信"（对称密钥）。
> 算法与打包器的一致性由宿主门禁 `tools/sign_host_gate.py` 验（内核 MAC == 打包器 MAC）；
> 板上"未签名镜像被拒"这条用例尚未跑（见 [安全认证准备](安全认证准备.md) §7 SEC-G02）。
