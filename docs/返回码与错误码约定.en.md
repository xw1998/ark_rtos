# Return codes and error code conventions

**[简体中文](返回码与错误码约定.md) | English**

> Condensed English edition. The Chinese page (返回码与错误码约定.md) is normative: every number
> below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins. This page
> adds no new claim and no new measurement.

To know what a negative number from a failing kernel function means, read this page.

It answers three things: **where the names come from**, **whether the values differ from before**, and
**which numbers are not error codes**.

## 1. The conventions

A failing kernel API always returns a **negative integer**; 0 means success and a positive number
means "success with information" (e.g. bytes read). This rule has not changed and is not going to.

What this round added is only **names**:

1. Each module defines a set of `ARKRTOS_<module>_ERR_<reason>` in **its own header**, plain
   `#define`s with no extra dependencies.
2. **Every macro's value equals, at every site, the number that was hard-coded there before.** Values
   were not redesigned; existing numbers were given names.
3. **Several names sharing `(-1)` is intentional**, not a missed value. Naming separates *which kind
   of failure* it is for callers and readers, not so each failure gets a distinct number.
4. **Values must not be changed individually.** Distinguishing two failures means adding a value-range
   scheme (touching the ABI and all callers), not changing a macro from `-1` to `-3`. Changing one
   macro's value is silently changing the external contract.
5. Error-code macros sit **before the feature switch** in each header (`timer` / `mempool` /
   `softbus` especially), so the `#else` stub functions can use the same names when
   `ARKRTOS_USE_XXX=0`.

### 1.1 Two prefix families: `_ERR_*` and `_FAIL_*`

In the last 15 modules, the loader already had its own `ARKRTOS_LOADER_ERR_*` (-1..-18), mini already
had -18/-19/-20, and every fs failure reason lives in `arkrtos_fs_last_error()`. Forcing one
`_ERR_*` scheme would make "the same name expand to different values at different return points", so
naming split into three families:

| Prefix | Meaning | Used by |
|---|---|---|
| `ARKRTOS_<module>_ERR_<reason>` | **the negative value itself carries the reason**; reading the return value classifies it | mq / event / timer / mempool / blk / dev / softbus / vfs / guard / sec / ptable / sync / task / hwsafe / installer / rt / log / cfg / layout / apprun / trace |
| `ARKRTOS_<module>_FAIL_<reason>` | always returns `-1`; **the reason is in the branch or `last_error`, the value carries no information** | loader (the existing `ARKRTOS_LOADER_ERR_*` is -1..-18 and cannot move) |
| `ARKRTOS_<module>_FAIL` | single value -1, the module has only one failure return | fs (reason in `arkrtos_fs_last_error()`) |

The test is simple: **is the `N` in that `return -N;` identically -1 in the original code, and does
the caller never branch on the value?** If yes, `_FAIL_*`; otherwise `_ERR_*`.

`mini` and `sbuf` are mixed: their existing -18/-19/-20 (mini) and -1/-2/-3/-5/-6 (sbuf) all keep
their values, and this round only names the return points whose original value was -1 with `_ERR_*`;
the two sets coexist.

## 3. These names are not error codes

The following are **sentinels** or idempotence hints; callers branch on them, so do not treat them as
failures:

1. **`ARKRTOS_MQ_WAIT_INFINITE` (-1) / `ARKRTOS_SBUF_WAIT_INFINITE` (-1)**: the "wait forever" marker
   for `remain_ms`. So `-1` is at once "wait forever" and several failure reasons — **the same number
   means different things in different parameter positions**, distinguished by position, not value.
2. **`ARKRTOS_MQ_WAITER_DUP` / `ARKRTOS_EVENT_WAITER_DUP` / `ARKRTOS_SYNC_WAITER_DUP` /
   `ARKRTOS_SBUF_WAITER_DUP` (all -2)**: registering a waiter found the task already queued. This is
   "no need to register again", not an error.
3. **`ARKRTOS_CRASH_INDEX_NONE` (-1)**: the index sentinel when `arkrtos_crash_mini_find()` finds no
   record; not an error code.
4. **`ARKRTOS_TASK_NONE` (-1)**: the scheduler reporting "no ready task / no switch needed". It shares
   -1 with `ARKRTOS_TASK_ERR_*`, distinguished by the **semantics of the return position**, not the
   value. The adjacent `255` is the "no candidate at this priority" sentinel and must not be used as a
   priority (see the comment on `ARKRTOS_TASK_ERR_PRIORITY`).

Likewise `ARKRTOS_EVENT_WAITER_ABSENT` (-1) and `ARKRTOS_SYNC_ERR_NOTFOUND` (-1) mean "it was not in
the queue when we tried to remove it" — idempotent semantics, usually ignorable.

## 4. Existing contracts that must not be "unified"

The easiest mistake while adding names is "just change all the -1s to -2" (or the reverse). The
following were that value historically, and **changing them breaks callers**:

1. **mq send timeout is `-1`, recv timeout is `ARKRTOS_SYNC_ERR_TIMEOUT` (-2).** The asymmetry is an
   existing contract; see 同步原语与令牌守恒.md.
2. **dev registration's "name or driver pointer is null" is `ARKRTOS_DEV_ERR_ARG` (-2)** (line 43),
   and a duplicate name is `ARKRTOS_DEV_ERR_EXIST` (-2). These two are deliberately kept at -2; a
   mistaken mapping to -1 once grew `arkrtos_dev.o` by 4 B and total Code from 220094 to 220098, which
   the size accounting caught.
3. **VFS's `-1` must not become the existing `ARKRTOS_VFS_EINVAL` (-2).** The VFS has its own `E*`
   scheme (from -2); the new `ARKRTOS_VFS_ERR_*` are all -1, and the two coexist: `E*` are POSIX-style
   errors for callers, `ERR_*` are names for kernel-internal return points.
4. **ptable's `ARKRTOS_PTABLE_ERR_MAGIC` is -2, not -1.** An image-header magic mismatch has
   historically been -2, and callers use -2 to decide "not our image".
5. **sync / sbuf's `WAITER_DUP` is -2** and is **the same value with a different meaning** from
   `ARKRTOS_SYNC_ERR_TIMEOUT` (-2): dup is "already registered", timeout is "wait timed out";
   callers distinguish by call site.
6. **hwsafe's `ERR_ARG` and `ERR_EXIST` are both -2** (bad device name/owner, name already
   registered), coexisting with `ERR_PARAM`/`ERR_NOSLOT`/`ERR_NOTFOUND`/`ERR_OWNER` (all -1).
7. **The loader's existing `ARKRTOS_LOADER_ERR_*` are -1..-18 and not one value moves.** The new
   `ARKRTOS_LOADER_FAIL_*` are all -1, naming only sites that already wrote `-1`; it is **forbidden**
   to map a bare `-1` onto a "more precise" value such as `-4` (SIZE) or `-6` (ERASE) — that would
   change the external return code.
8. **mini's -18/-19/-20 and sbuf's -1/-2/-3/-5/-6 all keep their values**; this round only names the
   -1 tier.

## 5. Deliberately unchanged: the littlefs callback contract

`kernelsrc/src/arkrtos_vfs_lfs.c` still contains 2 bare `return -1;` — **they are not kernel error
codes** but littlefs's directory-iteration callback convention (return non-zero to stop; the value is
meaningless). Naming them `ARKRTOS_*_ERR_*` would mislead later readers into thinking they were
distinguishable failure reasons, so they are left as is with a comment. They are also the last 2 bare
`return -N` in the whole repository.

## 7. Verification protocol

Reaching "0 Error" is not the end of verification. The second batch did four layers:

1. **Value-consistency script**: file by file, compare the number of every `return -N;` in the `HEAD`
   version with the value the macro expands to after replacement; `checked 234 / mismatch []`.
2. **Item-by-item size comparison**: default-profile kernel Keil build
   `Code=220094 RO-data=19198 RW-data=896 ZI-data=120852`, **identical item for item** to the baseline
   after the first batch (names take no part in code generation, so this is theoretically certain —
   what is measured here is that no `#define` accidentally leaked into an expression).

   About the build warnings: a full `-r` rebuild was done in a `git worktree` at `6bb3fa7` (before
   this batch) to obtain evidence — the baseline is also `0 Error(s)`, and the warnings are 1
   `#111-D statement is unreachable` plus 3 `#167-D uint32_t*/uint32*` in `ark_vfs_procfs.c`, plus
   `A1581W Added 2 bytes of padding` in `arkrtos_context.S` that only appears on full builds. **None
   of them is related to this round**, and that file was not touched.

3. **Example builds**: 7 Keil examples + 4 GCC examples link, with sizes identical to the previous
   round.
4. **Switched-off syntax check**: with `MQ/TIMER/MEMPOOL/BLK/FS/VFS/VFS_LFS/SOFTBUS/SECCHECK/MINIAPP/
   PROCFS/MINI/APPPACK/SBUF/RTSTAT` all set to 0, **all 38 `.c` files are run one by one through
   `arm-none-eabi-gcc -fsyntax-only`, 38/38 exit 0**, proving the `#else` stubs see the macros too.
   PASS is judged on exit code alone — the `variably modified` warning from `arkrtos_app_image.h` is a
   pre-existing ARMCC-extension warning under GCC, not an error.

**Grade: compiles only + sizes identical item by item. Not re-verified on board this round** (the
change involves names only, not control flow, but by the protocol it still counts as not-on-board).

## 8. How to write a new return point

1. First decide which kind of failure that `return -N` is.
2. Find the closest existing `ARKRTOS_<module>_ERR_*` in the module header; **reuse when synonymous,
   do not invent one name per line**.
3. Only when nothing fits, add a macro, still with value `(-1)` (unless history requires another
   value), plus a one-line comment stating the criterion.
4. Never change a value to "look more precise".
5. Afterwards run the four layers of §7.
