# Crash recovery and image version gating

**[简体中文](崩溃恢复与镜像版本把关.md) | English**

> Condensed English edition. The Chinese page (崩溃恢复与镜像版本把关.md) is normative: every
> number below is copied from it as of 2026-11-18, but if the two disagree, the Chinese page wins.
> This page adds no new claim and no new measurement.

The page covers two things, both answering "what happens after something goes wrong on the device":

- **Item B**: an image keeps crashing — how the kernel stops it from dragging the whole machine into
  a reboot loop;
- **Item C**: before an image may be installed into the pool — how the kernel decides "should this
  be installed".

Plus two boundaries that must be stated plainly: signature verification (implemented, off by
default, symmetric key) and upgrade/rollback (§5).

## 1. Item B: crash endgame and cross-reset counting

### 1.1 Where the count lives

There are **two** crash counters with different purposes:

| Location | Lifetime | Purpose |
|---|---|---|
| `slot_crash_cnt` in shared RAM | this power-up | runtime query (the crash column of `app list`) |
| `arkrtos_crash_journal_t` in the **UNINIT area at the tail of shared RAM** | **survives reset, cleared only by power-off** | cross-reset accumulation, blocking the "crash → reset → crash again" boot loop |

The journal lands in the region defined by `config/arkrtos_partition.h`:

```c
#define CRASH_LOG_SIZE  (512)
#define CRASH_LOG_BASE  (SHARE_RAM_BASE + SHARE_RAM_SIZE - CRASH_LOG_SIZE)
```

The struct size is statically checked against `CRASH_LOG_SIZE` at compile time — **adding a field
without adding space is a compile error**, never a silent overwrite of other data at the tail of
shared RAM.

### 1.2 Journal fields

| Field | Meaning |
|---|---|
| `magic` | `ARKRTOS_CRASH_MAGIC = 0x5343524A` |
| `version` | `ARKRTOS_CRASH_VERSION = 1` |
| `seq` | incremented on every commit |
| `boots` | boots recorded here; `>= 2` means the previous content really survived one reset |
| `crash_cnt[]` | consecutive fault count per slot |
| `last_reason[]` | most recent fault reason |
| `dis_reason[]` | why that slot was disabled (0 = not disabled) |
| `dis_tick[]` | the tick when it was disabled (0 = before this power-up) |
| `base[]` | pool address this entry belongs to |
| `check` | checksum over all of the above |

### 1.3 Three rules that never guess

1. **If magic / version / checksum fails, the whole journal is discarded and reopened**, instead of
   "trusting half of it". Leftover RAM bytes and half-written records both look like data, and
   acting on them would disable an image for something it never did.
2. **Counts are only adopted for slots where "the image still sits at the original address"**. Empty
   slots, replaced images and moved images have their entries dropped — charging a stale count to a
   newcomer is punishing it for someone else's mistake. But "aligned by address" is not "aligned by
   index": the slot table is rebuilt after every reset (records come back in ascending pool
   address), so the same image can land on a different index than when it was recorded. The `base[]`
   field exists exactly for this — the boot scan first looks through the whole journal for an entry
   whose address matches and adopts it, and **only drops what matches nothing** (§1.7).
3. **Disable reasons are three, never conflated**: `ARKRTOS_CRASH_REASON_FAULT(1)` consecutive faults
   reached the limit / `ARKRTOS_CRASH_REASON_HEARTBEAT(2)` violated its own declared heartbeat
   contract / `ARKRTOS_CRASH_REASON_AUDIT(3)` runtime structural self-audit failed.

### 1.4 What the limit is

`config/arkrtos_partition.h`:

```c
#define APP_CRASH_RESTART_MAX 3    /* consecutive-fault restart limit: disable the App slot when reached (0 = unlimited auto restart) */
```

A layout may override it with `fault_restart_max` (1..64); `0` means "use the compile-time value
above". **Reinstalling the image clears the count.**

After the limit: the slot is set to `INVALID`, the task leaves the scheduler, and it **no longer
autostarts**. Manual restart uses `arkrtos_loader_start_manual()` (what console `app start <slot>`
calls) — "disabled" means "do not come back by yourself unless somebody explicitly asks".

### 1.5 The heartbeat is the application's own contract, not the kernel's guess

`arkrtos_heartbeat(period_ms)` lets an image declare "I report in at most this often".

- The period floor is `ARKRTOS_GUARD_MIN_PERIOD_MS = 100` ms (equal to the service sampling
  period). A window shorter than the sampling interval cannot be judged, and the kernel **refuses**
  rather than drawing a conclusion from numbers it cannot verify.
- An image that never declared a period is reported as **"not declared"**, not "healthy" — with no
  basis for judging health, the kernel gives no verdict.
- The judgement looks only at the **interval between reports**, not at what the task was doing. So
  "sleeping/blocking longer than the declared period" is a violation: the period is the image's own
  promise and must cover the image's own longest wait. Exempting blocked tasks would remove the
  constraint from the most common shape ("sleep → work → report") and would make an image that never
  wakes up again un-catchable.
- The contract ends with the task: entries for deleted tasks are dropped, never carried over to a
  reused id and charged to another image.
- Evidence the kernel collects on its own (every SVC call, being on-CPU at the tick) is **reported
  in a separate column** and never folded into the contract — folding it in would silently let a
  stuck image that happens to still be on the CPU pass.

### 1.6 The `crash` command

```
journal: 0x2000BE00 +512 bytes (uninitialized RAM: kept across reset, cleared by power-on)
boots=35 seq=100

slot type  faults last        hold      held_at
 1   app    3      fault       fault     12840
 2   drv    3      fault       fault     12840
 3   app    3      fault       fault     12840
```

(The values above are measured on F427 on 2026-09-22: all three demo slots hit the limit and were
held disabled.)

### 1.7 Board defect: `crash-limit` disable did not survive reset (fixed)

**Symptom**: after `HWSAFE_DEMO` crashed 3 times, `app list` showed `INVALID` / `crash=3` /
`held=crash-limit` and `crash` recorded `held_at=<tick>`; but after `reboot` it autostarted again and
crashed once more, `boots` went to 4 and `crash` showed 3 (not 6) — **the cross-reset disable was not
in effect at all**.

**Root cause**: `arkrtos_crash_scan_apply()` aligned journal and slot table by **slot index** and
cleared the entry whenever `p_j->base[i] != p_pt->slot_base[i]`. The slot table is rebuilt in
ascending pool address after reset, so once the index drifted (measured: after a low-address slot was
uninstalled, the disabled image moved from index 1 to index 0) the journal's 3-fault history "did not
match by address" and was cleared, so the disable no longer persisted.

**Fix** (`kernelsrc/src/arkrtos_crash.c`) turns boot alignment into three passes:

1. per slot, first find the entry whose **address matches** and adopt it (after adopting, set the
   source entry's `base` to 0 so it cannot be counted twice); this pass **only clears entries whose
   address is found nowhere in the whole journal** — the first implementation tripped here: clearing
   index by index, when slot i=0's address did not match it cleared journal entry 0 first, and entry
   0 happened to be the history of slot i=1, so adoption never got its turn.
2. sweep away entries no slot claims (uninstalled images, addresses that left the slot table), so a
   future install at the same address does not inherit the old count.
3. publish the counts and enforce holding: any slot with `dis_reason != NONE` or
   `crash_cnt >= limit` gets `autostart=0` + state `INVALID`, and prints
   `CRASH: slot N held: ... 3 faults, last at tick <original tick>`.

**Re-verification (F427, on board)**:

| Scenario | Expected | Measured |
|---|---|---|
| 3 crashes → `reboot` (index unchanged) | `held` at boot, no autostart | pass: `CRASH:311 slot 0 held: crash-limit, 3 faults, last at tick 61702`, `app list` `auto=no`/`INVALID` |
| uninstall a low-address slot so the disabled image moves 1→0 → `reboot` | history adopted, still `held` | pass: `CRASH:311 slot 0 held: crash-limit, 3 faults, last at tick 32`, `fault` shows no new record (it did not autostart) |
| `reboot` once more | readings idempotent | pass: same `held` line, `crash=3`, `held_at` unchanged |

### 1.8 Measured on board: heartbeat violation leading to disable (2026-11-13, F427 + DAPLink)

The "violation" rule of §1.5 previously existed only in code; no real board had ever violated it.
Negative test case `example/stm32f427/app_sdk/APP_BADBEAT/` fills that gap: it declares
`arkrtos_heartbeat(1000)` ("I report in at most every 1 s") and then does `arkrtos_task_wait(3000)`
each round — **it does not crash and does not spin; it just reports too late**.

Right after installing:

```
app list: 0  app  RUNNING  yes  4  1  none  0x08060000 ...
guard   : contracts: 1 declared, 1 violating now
task slot period beat_ms svc_ms cpu_ms misses state
  4    0   1000   2713   2713   2713    17  wait
```

After `reboot` (the third violation) **the boot log prints the conclusion itself**:

```
[ 0.003] <3>CRASH:311 slot 0 held: heartbeat, 3 faults, last at tick 2200
                  (retry with 'app start 0' or 'drv start 0')
```

```
crash   : slot 0  app  3  heartbeat  heartbeat  2200
app list: slot 0  INVALID  auto=no  crash=3  held=heartbeat
```

Manual retry `app start 0`: `crash/held` are cleared and the application runs again (`auto` stays
`no`), and at the same moment the guard stops feeding the watchdog:

```
[10.400] <3>GUARD:348 not feeding: verdict 0x2 (audit 0x0, violating 1)
```

⇒ While the violation persists the watchdog is no longer fed and a hardware reset follows 4 s later.
That is an incidental reading, not a design promise.

Two points, both **in the readings rather than inferred**:

- **At most one record per boot**: `arkrtos_crash_fault()` rate-limits heartbeat violations (see the
  comment block in `arkrtos_guard.c`), so going from install to `hold=heartbeat` takes
  `fault_restart_max` boots. Seeing `faults=1` after a single reboot is normal.
- **`app start` is an explicit retry**: by design it clears `crash`/`held` ("do not come back by
  yourself unless somebody explicitly asks").

**Still unverified**: `REASON_AUDIT` (disable caused by a structural self-audit failure). Constructing
it requires `arkrtos_audit_run()` inside an image to really report a malformed structure, and there
is no safe way to build that this round — so it is not written up as "verified".

## 2. Item C: version gating before an image enters the pool

### 2.1 Three-state decision

`arkrtos_loader_check_install()` compares only by **`image_id`** (`image_id` = crc32 of the payload,
i.e. payload identity; two packs of the same application differing only in version number share the
same `image_id`):

| Situation | Result |
|---|---|
| no valid copy with the same `image_id` in the pool | allowed |
| same `image_id` and same `image_size` / `crc32` | `ARKRTOS_LOADER_ERR_DUP(-17)` duplicate copy |
| same `image_id`, version not higher than the installed one (downgrade reflash, same-version rebuild) | `ARKRTOS_LOADER_ERR_VERSION(-16)` version rollback |
| the slot is in `LOADED` / `RUNNING` | refused (do `app stop <slot>` first) |

Device-side text:

```
[E][INSTALL] refused: version not increasing (id 0x%08X, incoming v%u.%u.%u.%u <= installed) - bump the version
[E][INSTALL] refused: identical image already installed (id 0x%08X, v%u.%u.%u.%u, %u B) - nothing to do
```

The version number has four fields packed big-endian into one word (`v[31:24].[23:16].[15:8].[7:0]`).

### 2.2 Why power-loss recovery needs no journal sector

The commit state is a single field `state`: on a move, an `UNCOMMITTED` copy is first written at the
new location, then after verification **only that one field** is rewritten to `VALID` (single-word
programming, atomic), and only then is the old copy erased. The power-on scan discards anything
`UNCOMMITTED`; if two `VALID` copies share an `image_id`, the one at the lower address is kept.
Together the two rules make recovery both idempotent and deterministic.

> `state` **must not** be used to express "uninstalled": after an image is committed it is already 0,
> and writing `UNCOMMITTED`(=1) requires turning a 0 into a 1 — Flash cannot do that, the hardware
> silently keeps 0, so the uninstall becomes a no-op and the image comes back on the next power-up.
> Uninstall instead clears the `type` field (`ARKRTOS_APP_OFF_TYPE`); see the "uninstall semantics and
> space-reclaim granularity" section of 内核Shell控制台使用说明.md.

## 3. Troubleshooting entry points

| Want to know | Type |
|---|---|
| cross-reset crash ledger, which slots are disabled and why | `crash` |
| whether the heartbeat contract is violated | `guard` |
| whether the structural self-audit passes | `audit` |
| the fault ring record (including `INSTALLFAIL`) | `fault` |
| where some task is stuck | `task <id> <any third arg>` |
| why an install was refused | `fault` + `log` (device-side `INSTALL` / `LOADER` lines) |

## 5. Things deliberately not done (and why)

| Not done | Status | Reason |
|---|---|---|
| ~~**signature verification**~~ **(implemented, off by default)** | With `ARKRTOS_USE_IMAGE_SIGN=1`: `pack_app.py --sign-key` writes HMAC-SHA256 into `signature[0..32)` and the kernel recomputes it **at install time**, refusing mismatches (both paths in `loader.c` call `arkrtos_sign_verify` / `arkrtos_sign_stream_end`). Default 0; the F427 project does not enable it (the key must not enter the repo) | The mechanism exists but carries no "compliance" meaning: **symmetric** pre-shared key (whoever reads the key can sign), verified only at install time (images already in Flash are not re-checked at boot), no root of trust. The limitations are written in the `arkrtos_sign.h` header |
| ~~**asymmetric signature (Ed25519)**~~ **(implemented, off by default, mutually exclusive with `EXEC_SIGN`)** | With `ARKRTOS_USE_IMAGE_SIGN_ED25519=1`: `pack_app.py --sign-ed25519-key` signs the covered-region digest with the private key and writes 64 bytes into `signature[0..64)`; the device stores only the 32-byte `ARKRTOS_IMAGE_SIGN_PUBKEY`, and the kernel recomputes the digest **at install time**, refusing a mismatch | Reversing the device no longer yields signing capability, but **verification is not a root of trust**: the key is compiled in, changing it means changing the firmware, and there is no revocation; coverage and the check point are the same as in the HMAC profile (`crc32` still counts as zero), so this row answers "who signed it", not "can the key be trusted" nor "is the image intact at runtime" |
| **A/B dual slot / automatic rollback** | no A/B slots, no backup region | Not yet. But "replace the control program while running" already has a working example: the control loop lives in RAM as a mini-program and the image sits in external NOR; a new version takes over and continues from the old version's state, with measured handover time 27 ~ 407 ms (无缝升级例程.md) — that is **handover**, not rollback |
| **persistent version log** | only the crash journal in the `.noinit` area | No version log; crash counts are kept in memory only |

> Hence: **in the default profile `signature` is all zeros and the kernel never reads it; "has a
> field" does not mean "signed".** Once `ARKRTOS_USE_IMAGE_SIGN` is on it becomes real: it then
> answers "was this image made by the holder of the key and has it been modified", **not** "is it
> trustworthy" (symmetric key). Algorithm/packer agreement is proven by the host gate
> `tools/sign_host_gate.py` (kernel MAC == packer MAC); on-board "unsigned refused / signed accepted"
> was measured (2026-11-12, see the table above and 安全认证准备.md §8 T12).
> Note the order of the two gates: version monotonicity (`INSTALL:211`) comes before signature
> (`LOADER:1046`), so when re-testing, the test image's version must be higher than the installed
> copy, otherwise the signature check is never reached.
> The asymmetric profile (`ARKRTOS_USE_IMAGE_SIGN_ED25519`) narrows "the holder of the key" to "the
> holder of the private key": the device keeps only the public key, so reversing it no longer yields
> signing capability. The key is still compiled in, so the answer remains "signed by some private key
> and unmodified", **not** "this image is trustworthy" - the last hop needs a root of trust (SEC-G12).
